    レビュー対象¶

    • docs/design/beer-game-scala/ の設計書 10 本と index.md、ADR-001。コミット dcf35539 の時点。
    • 前回: 設計書レビュー（2026-11-25）。高 10 件を反映した。ユーザーの決定は H3・H6・H7・H9 の 4 件だけで、他は AI の案で承認を得ていない。
    • 5 視点とも読み取り専用で実施した。プロダクトは Kotlin 版 ADR のうち 7 件（004・007・009・011・014・017・019）の本文を、UX は実際の apps/beer-game-web のソースと契約を、テスターは Kotlin 版の Execute.kt や共有の .feature を、それぞれ自分で読んで突き合わせた。エージェントの出力はモデルの出力であり、ユーザーの承認ではない。

    総合評価¶

    前回の高 10 件のうち、解消は H8（引き継ぎ表の本文検証）と H10（ポーリングの範囲と推定の訂正）の 2 件、他の 8 件は「一部」である。構造は反映されたが、反映した設計に新たな穴が見つかった。特に重い問題は 3 つある。

    1. 止める設計（H3）と Started の遷移の漏れが組み合わさる: 開始後の復帰（US3.2、U2 の約束）・資格の再発行・観察者の招待が、スケッチでは Ignored になり、研修中にゲームが 500 で止まる。止める設計の安全性は、遷移の表を正本にした状態遷移テストにかかる。
    2. H5 の ProjectionLock を Resource（セッションのアドバイザリロック）にした案は、コマンドごとに接続を 2 本使う: プールの枯渇と接続数の見積もりの破綻を招きうる。
    3. H7 の範囲の決定（CI の新設は後回し）が、team の Mandated と B1 の受入条件と両立しない。

    H8 は、Kotlin 版 ADR 7 件の本文との突き合わせで、判定がすべて一致した。承認の扱い（決定と案の区別）は全体として誠実だが、混ざった箇所が 3 か所ある。

    新たな改善提案（重要度順）¶

    対応方針は案で、人が確定する。

    高¶

    # 提案 指摘元 理由
    N-H1 Started の遷移を、状態遷移図と Kotlin 版の表に揃える。 スケッチに ObserverInvited・ObserverJoined・ObserverInvitationRevoked・CredentialReissued・ParticipationRecovered を足し、EV-G01〜G12・EV-S01〜S10 × 状態の「許す組の表」を規範にして、状態遷移テストと性質テストの生成器をこの表から導く。未知の参加者への ParticipantReplaced は Ignored にする（Kotlin 版の変更表 38）。受入テストに「停止中に入れ替え → 代理入力 → 再開して確定」「入れ替え後の再開で新担当者だけが保存できる」を加える UR、AR、TS 止める設計では、許す組の漏れがそのまま研修の停止（P1）になる。復帰（US3.2）は U2 で約束した範囲。現場で最も起きやすい流れは「停止 → 入れ替え → 代理入力 → 再開」
    N-H2 ProjectionLock の接続の出所を決める。 案: ConnectionIO[A] => ConnectionIO[A] の変換にし、PostgreSQL 版は先頭で pg_advisory_xact_lock_shared（K10 で確認済み。COMMIT で自動解放、接続は 1 本）、H2 版はプロセス内のロックを bracket する。接続数の見積もり（architecture-infrastructure 154 行の式）にロックの接続を含める AR（TS が接続数・解放漏れのテストを補足） 現案はロックの専用接続が書き込みのプールから来るのか不明で、同時のコマンドがプールの大きさに達すると全員がロックを持ったまま接続を待つ。解放に失敗した接続がプールに戻ると再構築が止まり続ける
    N-H3 .transact( の禁止を、許可する入口の一覧つきで設計し直す。 読み取り（ReadXa・ObserverXa）、rebuild-projections・verify-projections・retention・migrate、LISTEN の専用接続の入口を同じファイルに置いて除外を 1 か所にし、FC.commit・FC.rollback・HC.commit・HC.rollback と .transact[IO](・xa.trans も禁止する。受入条件は「落ちるべきもの」と「落ちてはならないもの」の 2 方向の表にする。除外に scalafix:off を使う案は、ADR-001 の 011（無効化コメントを使わない）と矛盾するので外す AR、TS 書いたとおりでは読み取り側とテストの正しいコードが落ち、型引数つきの呼び出しがすり抜ける。「型の上で作れなくする」（backend 298 行）は言いすぎ
    N-H4 範囲の決定と規約・B1 の受入条件の衝突を、人が決める。 案（PM）: 「後回し」を AWS 環境とデプロイ用のワークフロー 4 本に限り、検証用の CI（check ジョブ 1 本）は U1 の約束に含める。ステージングへ自動反映を持たない間の例外は ADR に記録する。あわせて、範囲の決定に「専用 AWS 環境・CI の新設」が含まれていたかを確認し、AI の案が決定に混ざっていれば区別する PM、TS B1 の受入条件に「CI が落ちる」が 2 行あり、team.md・project.md の Mandated は CI での formatter・linter・type-check の実行とステージングへの自動反映を求める。B1 の計画より前に決める必要がある
    N-H5 確認状況の正本の規則を 1 つにする。 案: 「一覧が正。一覧の根拠は実測の記録（data-model の検証 A、テスト戦略の確認した事項）で、一覧を直すときは根拠も直す」。test-strategy.md 22 行と non-functional.md 34 行を直し、index.md 101 行、operation.md の旧名 Tx.rollbackOnLeft を直す TS、AR H1 の目的（判断のぶれをなくす）が文書間の規則の逆で崩れている
    N-H6 domain の文 97% を、ゲートか目安かで 1 つにする。 プロジェクトごとのしきい値を設定できるか（K16）が未確認なので、「設定できなかったらどうするか」まで書く TS tech-stack・NF-O7 はゲート、test-strategy は目安、ADR-001 は B1 で決める、と 3 通り
    N-H7 止まったゲームの運用と画面を、研修の現場で使える形に直す。 (a) #15 の画面文言を実物に合わせ（app.internal は辞書の文言。console は extra が付く）、(b) 画面は「もう一度お試しください」と再操作を促すので、パターン 18 の依頼文言と #15 に「操作を繰り返さず、画面の相関 ID を運営者に伝える」を加え、(c) 依頼文言に判断の期限と次の手（例: 運用担当から 15 分以内に見込みを伝え、立たなければ控えた数字で紙で続ける）を入れ、(d) 止まったゲームでも状態の取得（読み取り）が返ることを B1 の確認項目に入れて、依頼文言に「画面の在庫・受注残・今週の入力を控える」を加える UR、UX 止める設計を選んだ以上、紙で続けられることが研修を続ける唯一の手段。表示まで 500 になると数字が残らない。ポーリングの画面は止まったことに気づけず、気づくのは次に操作した人だけ

    懸念事項（複数視点）¶

    • 止める設計の安全性は、遷移の表にかかる: 許す組の漏れを検知できるのは、状態遷移図ではなく許す組の表から作った状態遷移テストだけ。スケッチを基準に生成器を作ると、漏れを見逃す（TS、AR、UR）。
    • 新しいコードはすべて型検査していない: Tx.run、Resource のロック、Committed は未検査（K3・K6・K10）。B1 の最初のスライドで型を確定してから、後続の振る舞いのテストを先に書く順序が必要（TS、AR）。
    • Kotlin 版で未承認の判断の上に積んでいる: 引き継ぐ行の多く（003〜011・013・014・020）は Kotlin 版でも提案中。Kotlin 版の ADR のステータスが変わったとき、どう検知して追従するかの仕組みが 1 文だけ（PM）。
    • ポーリングの画面は止まったことに気づけない: Ignored はコマンドの経路でだけ起きるので、GET は成功し続ける。気づくのは次に操作した人だけ（UX）。
    • 承認が要る文書が多い: 依頼文言、研修中の原則、パターン 18、Intent の文面はすべて AI の案で、運営者との合意（未決事項 3a）の前に研修で使わない（UR、PM）。

    スコープ外の発見（正本・共有物の側）¶

    • Kotlin 版 ADR-017・019 は、ステータス節は「承認済み」だが、タイトルと決定の見出しは「提案」、冒頭は「ADR としては提案中のまま」で自己矛盾している。Scala 版 ADR-001 はステータス節を根拠に承認済みと数えている（PM）。

    • Kotlin 版の domain-model の EV-S07 と EV-S10 の重複は、正本側の整理が要る。同じ写しの漏れ（ObserverInvitationRevoked）が Rust 版にもないか、正本の遷移表と突き合わせる価値がある（AR）。
