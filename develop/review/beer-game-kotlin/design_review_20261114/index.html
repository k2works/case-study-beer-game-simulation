    設計書レビュー - beer-game-kotlin（2026-11-14）¶

    レビュー対象¶

    • docs/design/beer-game-kotlin/ の設計書 11 本（beer-game2 の Kotlin 版。イベントソーシング + CQRS、Ktor + Arrow、関数型プログラミングガイド（Kotlin 編） 準拠）
    • 状況は draft。実装コードは存在しない。
    • 精読の範囲は視点ごとに異なる。アーキテクトは 5 本（backend、data-model、domain-model、tech-stack、infrastructure）を精読し、残りの 6 本は該当箇所のみを確認した。各視点の「確認していない事柄」は断定していない。

    総合評価¶

    ES+CQRS の骨格は健全である。2 ストリーム、StartGame の原子的な追記、同期投影、一意制約による楽観的並行制御、自動確定を 1 回の decide で返す設計、WeekCommitted に結果を事実として固定する設計（D5）、スキーマ進化の 2 段階リリースは、5 視点とも評価した。

    一方で、実装に入る前に直すべき問題が 3 系統ある。

    1. 利用者に見える振る舞いが黙って変わっている。 一時停止中の代理入力ができない、代理入力で 4 役割が揃っても自動確定しない、最終週の確定が出力の作成の失敗に巻き込まれうる。
    2. ES+CQRS の安全性に穴がある。 冪等記録を認可より前に照合している、再試行の対象になる制約が文書間で矛盾している、CommitWeek の版の意味が誤案内を生む、トランザクションの意味論が未記述である。
    3. 文書間の食い違いと未決事項の取り残し。 WeekAdvanced、DomainError.code、Flyway などの決定が、他の文書の未決事項に残っている。再生の同値性の定義が 4 通りある。

    改善提案（重要度順）¶

    指摘元の略号: PM=プロダクトマネージャー、AR=アーキテクト、UX=インタラクションデザイナー、TS=テスター、UR=ユーザー代表。複数の視点が同じ点を挙げたものは 1 件にまとめた。

    高¶

    # 提案 指摘元 理由
    H1 一時停止中も進行役の代理入力を受け付ける。 不変条件・EV-S06・状態遷移図に明記し、参加者の SaveDecision だけを停止中に拒否する（domain-model） PM, UR UC-09、US3.1、AC3.1.1 の主成功シナリオは「停止 → 代理入力 → 再開」。現設計では停止中の発生条件が「進行中」のみで、中断の運営が成立しない
    H2 代理入力にも requestedWeek を持たせ、4 役割が揃えば自動確定する。 EV-S08 の発生条件に SubmitProxyDecision を加える（domain-model） PM, AR 確定直後に古いコンソールから届いた代理入力が翌週の値として保存される。AC2.4.1 は入力手段を問わず「揃うと一度だけ確定」
    H3 最終週の確定を export_packages の作成から切り離す。 要求時に純粋関数 buildExport で作る案（PM の推奨）か、SessionEnded 後の別トランザクションにする（data-model、ui-design 変更 #7） PM, UR, UX, TS Should の出力の失敗が Must の最終週確定を妨げる。方式を採るなら、beer-game2 にあった「準備中」の表示を残す必要がある
    H4 冪等記録の照合を認可の後に置く。 request_digest に操作者の ID を含め、Left（業務の失敗）を記録に保存しないと明記する（backend、data-model） AR 入れ替えで失効した旧担当者が以前のキーを再送すると、保存済みの応答（参加・復帰では資格の生の値）が返る。project.md の Corrections に同種の規則がある
    H5 再試行の対象になる一意制約の名前を一覧で決める。 events の版の制約に加え、scope='create' の部分一意索引と idempotency_records の主キーの衝突を 500 にしない（backend、data-model） AR 文書間で矛盾している。ゲーム作成の同時の重複や空の列を返す操作の同時送信が 500 になる
    H6 CommitWeek の前提を session ストリームの版から、要求した週（必要なら役割ごとの意思決定の版）へ変える。 または StaleVersion を「週が進んだ」と「状態が更新された」に分け、WeekAdvanced を backend と ui-design の写像の表に反映する AR, UX 共同担当が保存し直しただけで StaleVersion になり、画面に事実と違う「すでに確定されています」が出る
    H7 トランザクションの意味論を書く。 Left を返したら ROLLBACK、分離レベル（READ COMMITTED）と 40001・40P01 の扱い、Ktor のキャンセル時に ROLLBACK/COMMIT を NonCancellable で行い CancellationException を握りつぶさない（backend の EventStore.transaction） AR 追記の後に投影が Left を返しても COMMIT されると、追記と投影の原子性が崩れる
    H8 保存後の画面の更新経路を 1 つに統一する。 応答は版（versions、ストリームごと）だけを返し、画面は SSE を待たずにスナップショットを取得して、表示は常にスナップショットから作る（ui-design と architecture-frontend が逆のことを書いている） UX SSE が切れても自分の保存が画面に出て、更新の経路は 1 つに保てる。自動確定の応答の扱いも同時に決まる
    H9 エラーの code の書式を 1 つに決め、辞書の正本を ui-design に置く。 domain-model は session.week_advanced、backend と frontend は decision-conflict。OpenAPI の type との対応（URI か code そのものか）を明記し、ui-design の表に code の列を足す UX, AR frontend は辞書を Record<ProblemType, …> で網羅する設計で、この鍵が契約になる
    H10 週が SSE 通知で進んだときも、入力欄を空にして直前の値を参考として示す。 「他の人の保存: 入力中の値を保持する」の規則に例外を設ける（ui-design） UX, UR AUTO では共同担当の保存で週が確定する。打ちかけの値が次の週に残って誤って保存される
    H11 「再生の同値性」を別々の名前の 4 つの性質に分け、常に通るテストを除く。 例: 永続化往復の同値性、計算と事実の一致、投影の整合。test-strategy の「1 件ずつ evolve と fold(evolve) の一致」は削除するか往復の性質に置き換える TS replay が fold(evolve) である限り同じ畳み込みを 2 回書くだけで、実装に関係なく通る（construction.md の「常に通るテストを生成しない」に該当）
    H12 追記専用権限の否定テストを加える。 書き込みロールが game_roots を DELETE・events を TRUNCATE できないこと、各ロールが所有者またはそのメンバーでないこと、削除ロールが game_roots 以外を DELETE できないこと。連鎖削除が動くかは最初のスライドの Red で確かめる TS, AR events の UPDATE/DELETE 権限が無いだけでは、連鎖削除や所有者経由で回避できる
    H13 観察者の接続プールの配線を確かめる統合テストを加える。 観察者の HTTP 経路を実 DB で通し、問い合わせの current_user が観察者ロールであることを検査する TS 設定の誤りで書き込み用プールを渡しても、今のテストは通る
    H14 Kover の計測範囲が integrationTest を含むかを明記する。 層ごとの目標が CI のゲートか目安かも書く TS adapters/persistence の行 90% は DB 統合を含めないと到達できない。合算されないと判定が意図とずれる

    中¶

    # 提案 指摘元 理由
    M1 観察者に参加コードを見せない。 game_overview.join_code を列単位の GRANT か別の表に分ける。NF-S18（観察者は week_team_totals のみ）と backend（3 表）の記述を揃える PM, AR FR-17・BR-17 に反し、観察者が参加者として加われる
    M2 小売店の当週の需要と上流の当週の受注・入荷を読む経路を role_current_states に持たせる PM BR-11、AC2.1.1。需要系列は進行役専用の game_settings にしかない
    M3 観察画面の「完了状況」（入力済みの役割数。値は含めない）を session_overview に持たせる PM AC4.1.1。入力済みの情報は current_decisions（参加者と進行役のみ）にしかない
    M4 AC1.2.5 の解釈と付け替え（D9）の関係を設計書に明記する。 UI で移動を明示する PM AC1.2.5 は「割り当てず理由を示す」。D9 は黙って付け替える
    M5 保持の起点を「決定」にする。 PM は作成時起点（画面に示す前提）、UR は終了済みは終了時・未開始は作成時を提案。方針の版（RetentionPolicy）を落とした理由も追記する。削除予定日と「バックアップに最大 7 日残る」をロビーなどの画面に載せる PM, UR 作成時起点では事前作成した研修の振り返りの取り出し期間が短くなる。画面に案内がない
    M6 StaleVersion の week で文言を分ける（H6 と同時に対応）。S06 のワイヤーフレームを追加する UX 画面一覧は変更点に挙げているが図がない
    M7 アプリケーション層の失敗（RetryExhausted、IdempotencyKeyReused）にも安定した type を与える。 「type が retry-exhausted のときだけ『もう一度お試しください』。type のない 5xx・タイムアウト・切断は『結果が不明』として同じキーで再送」と規則化する UX, AR LB からの 503 と区別できないと、新しいキーでゲーム作成が二重になる。HTTP の状態の記述も文書間で揺れている（503 と「競合を返す」）
    M8 自動確定を起こした本人へのフィードバックを決める。 AUTO のゲームでは S05 に「4 役割が揃うとすぐ確定される」と示す UX, UR 保存直後に週が変わり、保存できたのか分からない。共同担当の「仮に保存して話し合う」使い方が壊れる
    M9 反映待ちの表示を見直す。 「現在の入力: （更新中）」でなく「あなたが保存した値: 10（反映中）」と示す。自動再送の記述（「再送する」と「再送を確認する」）を統一し、確認中は入力欄を読み取り専用にする UX 保存済みと言いながら値が消えたように見える。再送する値と画面の値がずれうる
    M10 代理入力が共同担当の入力を上書きしたときの見え方を決める。 「進行役が代理で入力しました」と区別して示し、確認ダイアログに上書きする現在の値と保存者を表示する UR 競合の画面で保存者が進行役になる。上書きを意識できない
    M11 参加・復帰の失敗の文言は「自分が送った資格の種類」から選ぶ。 失効と期限切れを区別する識別子（invitation-expired）をやめる UX 無効な資格と権限不足を同じ形で返す設計（列挙の防止）と両立しない。project.md の Corrections に同じ判断がある
    M12 Projection<Row> を「イベントから行の変更の列へ」（Event -> List<RowChange>）に変える。 export_packages は他の投影を読まずイベントだけから作る AR WeekCommitted 1 件が 5 つの表を書く。再構築の順序に依存する
    M13 evolve の強制キャストをなくす。 不正な遷移の扱い（無視か検知用の状態）を決め、「decide が作る列だけが来る」性質テストと組にする AR, TS ClassCastException でそのストリームのコマンドが止まる。ガイド §9.6 の禁止事項に触れる
    M14 EventStore と execute の型（AppendFailure・AppFailure）の正本を 1 つに決める AR data-model と backend で型が違い、再試行の判定が競合の型に依存する
    M15 問い合わせを一貫した時点で読む。 読み取り専用の REPEATABLE READ か、チェックポイントを先に読む順序を規則にする AR 行より新しい版を返すと、画面が通知を捨てて古い表示のまま残る
    M16 未決事項の取り残しを解消する。 DomainError.code（domain で決定済み）、Flyway、Logback、JSON/アップキャスト、OpenAPI、SSE プラグインが別文書で未決のまま。tech-stack 121 行の「API の契約は変えない」を実態（POST /games/:id/start、2 種類の If-Match、SSE のストリーム種別、problem+json）に合わせる。ui-design の未決事項「SaveDecision は週を持たない」を削除し、frontend の変更表に開始 API の変更を 1 行足す AR, UX, PM 開発チームが古い前提で文言や実装を割り当てる。「承認待ち」と「選定未決」を書き分ける
    M17 detekt と Kotlin 2.4 の互換を受入条件にする。 ウォーキングスケルトンの最初のビルドで「規約違反コードを 1 つ置き、CI が落ちること」を確認し、代替（PMD の XPath、detekt 2 alpha）を選ぶ期限を決める。JDK 25 のサポート期限を使う配布（Temurin）の値に統一する AR 規約の検査の成否が型解決に依存し、未検証のまま。tech-stack は 2031-09-30、infrastructure は 2030-09-30
    M18 純粋性は静的検査で守る。 detekt の ForbiddenMethodCall でドメインでの Instant.now・Clock.system*・UUID.randomUUID・Random を禁止する。「同じ入力から同じ出力」の性質テストは補助とする。D5（evolve が simulateWeek を呼ばない）は、計算結果と違う nextStates を持つ WeekCommitted を Given にして状態が採用することを検証する TS 同一 JVM の同一ミリ秒に 2 回呼ぶだけでは時計の読み取りを検出できない
    M19 プロパティテストの有効なコマンド列の Arb に、分布の記録と生成器の単体テストを加える。 カバレッジの分岐指標は suspend で揺れうるため、domain は変異テストを品質の指標にする判断をウォーキングスケルトンで行う TS 深い状態に届いているか確かめられない。Kotest/Pitest の対応は未確認
    M20 境界値の一覧と、NFR 84 件の「要件 ID → 検証手段 → 頻度」の表を設ける。 NF-S15・S17〜S19、NF-R1 などが上位の NFR に対応付けられていない。WeekAdvanced を decideSession の例に加える。NF-P8、NF-C2、NF-C3、NF-P9 を夜間の負荷試験に含める。上限が未定の値は設定から注入する TS 値が文書に散らばり、テストが書けない。トレーサビリティが不完全
    M21 測定可能性を補う。 NF-P2 は同一の時計で測る、NF-P17 は GC 後か、NF-P15・P18 は試行回数と方法（JMH など）、NF-C8 は最悪ケースの保存回数の上限 TS 合否の基準にならない
    M22 N-1 互換の CI ジョブを加える。 直前のリリースの読み取り側で、現在の書く版の golden を再生する TS 旧イメージが新しいイベントを読めない障害（パターン 16、NF-O11）を防ぐ回帰テストがない
    M23 研修中に投影が不整合になったときの業務手順を決める。 運営者を通じて進行役に「停止」を依頼し、停止中に再構築して再開する。停止中に追記を伴う操作（代理入力、資格の再発行、観察者の参加）を止められるかを確認する。再構築の同時実行制御は pg_advisory_xact_lock_shared(game_id)（コマンド）と排他ロック（再構築）で決められる UR, AR operation の手順 B-1 は研修中の再構築を禁じる一方、障害パターン 13 の目標は 15 分で、矛盾している

    低¶

    # 提案 指摘元 理由
    L1 競合の表に「停止中」「終了後」「IdempotencyKeyReused」の文言を加える。保存者が自分のときは文言を変える（版 N でなく保存者と時刻で示す） UX, UR 「4 種類」以外の競合がある
    L2 role="alert" とフォーカス移動の併用をどちらか一方にする UX 二重に読み上げられうる
    L3 複数の投影行をロックするときの順序の規則を書く。BD6 の FOR UPDATE は今のイベント構成では実際には競合しない旨も記す AR デッドロックの防止
    L4 pg_notify の「ロールバックなら通知が出ない」と LISTEN の再購読を DB 統合テストに入れる。RTO の文言と値、起動時間の測る区間（NF-P16 と operation）を整合させる TS 検証がない、または食い違っている
    L5 Lobby の購読イベント（CredentialRevoked）が domain と data-model で一致していない AR
    L6 AC6.1.3（アウトボックスの遅延）の置き換えを test-strategy のトレーサビリティ表に載せる。「74 件」の出所（要約表の行を含めた数と推測）を記録する PM 受入条件の置き換えは契約の変更
    L7 障害パターン 14 の初動で、進行役への依頼文言まで決める UR 具体的な行動が書かれていない

    矛盾事項¶

    # 視点 A 視点 B 論点 推奨判断
    C1 PM: export_packages は同期投影をやめ、要求時に作る（表が 1 つ減る） UX: 非同期にするなら beer-game2 の「準備中」表示が必要。UR: 方式は開発チームに任せる 出力の作り方 要求時に作る案を第一候補にし、決まるまで ui-design の「準備中」の削除（変更 #7）を条件付きにする
    C2 PM: 保持の起点は作成時 UR: 終了済みは終了時、未開始は作成時 保持の起点 業務の判断。どちらでも削除予定日を画面に示す。人が決める
    C3 PM: 付け替え（D9）は採用し、AC1.2.5 の解釈を書く UR: 開始後の入れ替えが必要（スコープ外の候補） AC1.2.5 と付け替え 付け替えを採用し、解釈を明記する。入れ替えは次の要件の候補として記録
    C4 AR: 競合は再試行で吸収し、バースト試験の結果を ADR にする UX: 再試行の上限が小さいと「混み合っています」が頻発する 再試行の上限 上限を設定から注入し、4 人同時の保存で RetryExhausted が 0 件であることを受入条件にする

    懸念事項（実装前に確認する）¶

    • 追記専用と保持削除の両立。参照整合のトリガーが所有者の権限で動くという理解は未検証（AR、TS）。将来 events に更新・削除を拒否するトリガーを足すと連鎖削除も止まる。NF-S20 に注記する。
    • スナップショットを入れない前提は「1 ストリーム千件前後」に依存する。保存の頻度の約束（debounce か明示的な保存か）がないと崩れる。ストリーム長の上限にアラームを付ける（AR）。
    • 単一の session ストリームが書き込みの集中点になる。バースト試験（NF-C2）の結果で再試行とアドバイザリロックを比較し、ADR にする（AR）。
    • JVM の起動の遅さが研修直前に効く。15 ゲームが一斉に始まる場面で計測する（UR）。
    • AC4.1.3（寄与者 2 未満で合計を抑止）は、WeekCommitted.contributors が常に 4 のため検証する場面を作れない。beer-game2 から引き継いだ曖昧さで、公開範囲の選択肢と合わせて決める（PM）。
    • 終了済みゲームへの参加は NotPreparing になり、「開始済み」と「終了済み」を区別した理由を返せない（D2）（PM）。
    • 運用手順書 13 件が未作成で、通知先・オンコール・研修日時の連絡手順も未決。連絡の仕組みを最優先にする（UR）。
    • カバレッジ（行 85%・分岐 75%）と team.md の Testing Posture（行 80%）の差。team.md は beer-game3 の規則で、本プロジェクトに適用するかは人の判断が要る（AR、TS）。
    • 削除が恒久的に失敗した（FAILED）ときに deletion_runs にゲーム ID が残り、AC5.1.4 の対象外になる（TS）。

    スコープ外の発見¶

    • beer-game2 の要件側の訂正事項: FR-03「4 役割を重複なく割り当てられる」が FR-16・BR-15（1 役割に複数人）と矛盾した文言のまま。non-functional の「74 件」は ID の一意数 69 件と食い違う。NF-O7（80/70）とテスト戦略（85/75）の不一致。
    • ADR 化の候補: ES+CQRS の採用、同期投影、冪等記録と認可の順序、detekt の代替判断（AR）。docs/adr/beer-game-kotlin/ はまだない。
    • 開始後の参加者の追加・入れ替え、観察者の表示名を任意にするか、SetCommitMode(AUTO) を一時停止中に行ったときの扱い（停止中は確定しないと UR は判断）は、次の要件の候補として記録する。
