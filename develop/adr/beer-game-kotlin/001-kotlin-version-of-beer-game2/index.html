    ADR-001: beer-game2 を Kotlin 版として作り、要件と ADR を流用する¶

    beer-game2 と同じ機能と振る舞いを、Kotlin（Ktor + Arrow）のバックエンドと既存の React のフロントエンドで作り直す（beer-game-kotlin）。要件・ユースケース・ストーリー・Unit 定義は beer-game2 のものを参照して流用し、ADR は本書の引き継ぎ表に従って引き継ぐ・変更する・置き換える。

    日付: 2026-11-14

    ステータス¶

    承認済み（2026-11-14、ユーザーの決定）

    ユーザーが決めた事項は、Kotlin 版の作成、技術スタック（Ktor + Arrow + 既存 React）、コーディングを関数型プログラミングガイド（Kotlin 編）に準拠させることである。

    コンテキスト¶

    beer-game2 は、要件（BR-01〜BR-17、FR-01〜FR-18、NFR-01〜NFR-12）、ユースケース、ユーザーストーリー、Unit 定義（U1〜U6）、ADR（001〜013）を持つ。バックエンドの技術は TypeScript（Fastify）である。ユーザーは、同じ学習の価値を、Kotlin の関数型設計とイベントソーシングで、変更を楽に安全にできる形で提供することを求めた（リリース計画 の Intent）。

    この選択で、次の問題が生じる。

    • 要件を作り直すと、beer-game2 との二重管理になり、機能の差が生まれる。
    • beer-game2 の ADR の一部は、バックエンドの言語と永続化の方式（ES + CQRS）に依存しており、そのままでは当てはまらない。どれが有効かを明示しないと、二つの系列の ADR が混在する（beer-game2 の ADR-002 と同じ問題）。

    決定¶

    • 機能と振る舞いは、beer-game2 を正本として引き継ぐ。 要件・ユースケース・ストーリー・Unit 定義は新しく作らず、docs/requirements/beer-game2/ を参照する。範囲は beer-game2 と同じ（Unit U1〜U6、Release 0.1 / 0.2 / 1.0）。
    • 技術スタックは、バックエンドを Kotlin（Ktor + Arrow + kotlinx.coroutines）、フロントエンドを既存の React / TypeScript とする。 言語をまたぐ型の共有はせず、API の契約は contracts/openapi.yaml の手書きを正本にする（技術スタック の選定の方針）。版は ADR-013 で定める。
    • コーディングは、関数型プログラミングガイド（Kotlin 編）に準拠する。 アーキテクチャは ADR-002（ES + CQRS）、中核の構造は ADR-007 による。
    • beer-game2 の ADR は、次の表のとおり扱う。 beer-game2 の ADR のファイルは履歴として変更しない。

    beer-game2 の ADR の引き継ぎ表¶

    各行は、beer-game2 の ADR の本文と、Kotlin 版の設計書の「beer-game2 からの変更」の表で確認した。

    beer-game2 の ADR Kotlin 版での扱い 内容 Kotlin 版の ADR・設計書
    001 作り直し 引き継ぐ（本書で Kotlin 版へ） beer-game2 の要件を正本にして作り直す方針を、Kotlin 版でも取る 本書
    002 v1 の ADR の引き継ぎ 参照のみ v1 から v2 への引き継ぎの記録であり、本書がその Kotlin 版にあたる 本書
    003 ポートとアダプター + lint 変更 層の依存の向きは守る。守り方を、ESLint でなく Gradle のモジュール境界に、ポートとアダプターを関数型コア（関数の束）に変える ADR-007、ADR-011。バックエンド BD1・BD2
    004 Game と Session の分離 引き継ぐ 準備と進行を別の集約にし、開始だけを同時に扱う。ES では 2 ストリーム（game・session）で表す ADR-002。ドメインモデル D1・D3
    005 役割別の行と SQL の読み取りモデル 引き継ぐ（意図を保ち、投影として実現） 役割別の週結果を行として持ち、SQL で返す。WeekCommitted が正本で、week_role_results は投影になる ADR-003。データモデル
    006 SSE は版の通知だけ 引き継ぐ（一部変更） 版の通知だけで再生しない方針は同じ。game と session のストリーム別の版を通知する ADR-002。バックエンド の通知
    007 カスケード削除 置き換える 1 回の削除で漏れなく消す意図は保つ。games が投影になるため、根を game_roots に独立させ、追記専用の events との両立を決める ADR-010
    008 自動確定と監査 変更 同じトランザクションで確定する判断は同じ。「最後の保存と同じ追記」で decide が複数のイベントを返す形にし、監査は events が兼ねる ADR-002。ドメインモデル D6
    009 資格の鍵の版 引き継ぐ 有効期限・失効・複数の鍵の版は同じ。資格のダイジェストと表示名はイベントに入れず周辺ストアに置く ADR-002。ドメインモデル D7
    010 URL ルーターと機能単位 引き継ぐ フロントエンドは beer-game2 を踏襲する。エラーの表示の辞書の鍵が変わる ADR-008。フロントエンド
    011 CloudFront、独自ドメイン、TLS、ヘッダー 引き継ぐ 配信の構成は同じ。JVM のコンテナ（Temurin の JRE 25）に合わせる インフラ
    012 ECR、OIDC、ステージング自動・本番承認、Terraform 引き継ぐ パイプラインの構成は同じ。Gradle の検証、契約テスト、N-1 互換のジョブを加える。AWS への適用は別ゲート インフラ、テスト戦略
    013 技術スタックの版（Node 26、TypeScript 6.0 ほか） 置き換える バックエンドの版が Kotlin / JDK / Gradle などに変わる。PostgreSQL 18 とフロントエンドは引き継ぐ ADR-013

    代替案¶

    • beer-game2 の TypeScript を維持し、ES + CQRS のみを導入する: 言語を変えずに済むが、ユーザーが Kotlin と関数型の設計を求めている。
    • beer-game2 の要件・ストーリーを Kotlin 版にコピーして改訂する: 機能の正本が 2 つになり、差が生まれる。
    • beer-game2 の ADR をすべて有効とする: ポートとアダプターの守り方、削除の方式、技術スタックの版が、Kotlin 版と矛盾する。

    影響¶

    ポジティブ¶

    • 機能の正本が 1 つ（beer-game2）で、Kotlin 版は設計と実装の差に集中できる。
    • どの判断が引き継がれ、どれが変わったかが、本書の 1 か所で分かる。

    ネガティブ¶

    • 二つの系列（beer-game2 と Kotlin 版）の ADR を、読み手が参照する必要がある。
    • beer-game2 の要件が変わると、Kotlin 版にも影響する。要件の変更は、beer-game2 側で行い、Kotlin 版へ追従する。

    コンプライアンス¶

    • 契約の流用: ストーリーの受入条件を、日本語 Gherkin のシナリオにタグ（例: @US2.4 @AC2.4.1）で対応付ける。CI でタグから対応表を生成し、整合を検査する。B1 から継続（テスト戦略 のトレーサビリティ、リリース計画 の測定基準）。
    • API の契約が変わらないこと: beer-game2 の E2E のシナリオが、Kotlin 版でそのまま使えるかを、B4 までに確かめる。変わる場合は設計の矛盾として扱う（テスト戦略の E2E の節）。
    • 引き継ぎ表の整合: 本書の表の各行が参照する Kotlin 版の ADR（002〜013）が存在し、置き換えた beer-game2 の ADR を備考で参照していること。レビューで確認する。
    • beer-game2 の ADR を変更しないこと（履歴）。
