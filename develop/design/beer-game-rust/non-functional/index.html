    非機能要件定義 - ビールゲームシミュレーション（Rust 版）¶

    概要¶

    本書は、beer-game-rust の非機能要件を、測定できる形で定義します。docs/ を正本とします。実装コードはまだ存在せず、Rust 版の性能・メモリ・起動時間の実測値はありません。

    ADR-001 により、beer-game-kotlin の非機能要件（84 件。beer-game2 の 69 件 + Kotlin 版で追加した 15 件）を正本として引き継ぎ、Rust の実行環境で変わるものだけを見直しました。

    • すべての ID を維持しました（削除はありません）。要件定義の NFR-01〜NFR-12 は変えません（要件定義）。
    • 凡例は Kotlin 版と同じです。継続は Kotlin 版と内容が同じ、変更は ID は同じで内容を Rust 版に合わせて変えた、新は Rust 版で追加した要件です。
    • 数値目標は、運営者と合意する前提の提案です。Kotlin 版で提案した数値も、Rust 版の実測で見直す前提で、実測のない数値を Rust 版の都合で厳しくも緩くもしていません（設計判断 RN1）。
    • 新しく加えた要件は 2 件（NF-R18、NF-S22）で、合計 86 件です。

    本書の位置づけと確認の範囲¶

    • 継続の要件は、本文を Kotlin 版と重複して持たず、要約と ID の対応だけを示します。要件の正本の文言は Kotlin 版の表です（本書の「継続」の行に、要件の趣旨を 1 行で書く）。
    • 変更・新の要件は、本書に全文を書き、本書を正本とします。
    • 確認したこと: NF-S20（追記専用）と NF-S16（連鎖削除）の一部は、PostgreSQL 18.6 で SQL として実測しました（データモデル の検証、1 回の実測）。NF-S21・NF-S3 の型による守り（Secret<A> の Debug が伏せ字）は、rustc 1.97.1 で確認しました（バックエンドアーキテクチャ）。それ以外の要件は、すべて未検証です。
    • Kotlin 版の実装の経緯（B3・B6・B15 の実測の注記）は引き継ぎません（Rust 版の値ではないため）。

    品質特性の優先順位と SLO の要約¶

    Kotlin 版と同じです。 優先順位は、1 機能の正確性・信頼性（整合性）、2 セキュリティ、3 性能効率性・使用性、4 保守性・観測性、5 可用性（SLO）、6 拡張性・移植性。SLO は、月間可用性 99.5%、完全停止の検知 1 分以内、RPO 0（確定済み週）、RTO 15 分、入力確定（サーバー側）p95 1 秒以内、週確定から全画面への反映 p95 2 秒以内、保持期限後の削除（期限到達の 99% を 24 時間以内）。

    ES + CQRS と Rust で変わる点¶

    ES + CQRS による変化（再生による書き込み時間、ストリームの版の一意制約と自動再試行、同期投影、投影の再構築、追記専用、個人情報の分離、イベントの互換）は Kotlin 版と同じで、要件もそのまま引き継ぎます。Rust の実行環境で変わる点は次のとおりです。

    観点 Kotlin 版（JVM） Rust 版 関係する要件
    起動とウォームアップ JVM の起動、JIT のウォームアップ。コールドスタート直後の遅さを要件にする JIT がない。ウォームアップ依存の遅さは原則なし。ただし、DB の接続プールの温まりと OS のキャッシュの影響は残るため、コールドスタート直後は NF-P16 の目標（Kotlin 版と同じ 2 秒。RN1）を置いて確認する NF-P1、NF-P16
    メモリ JVM のヒープ、GC 後の使用率、GC の一時停止 GC がない。常駐メモリ（RSS）とコンテナのメモリ上限との関係、tokio のタスク数。メモリ不足は OOM kill として現れる NF-P17、NF-O12
    非同期とキャンセル コルーチン。NonCancellable で COMMIT/ROLLBACK future の drop がキャンセル。Tx の drop で ROLLBACK、execute を spawn して切断から隔離（RB2）。panic のプロセスへの影響も扱う NF-R18（新）、NF-R3、NF-R5、NF-R9
    メモリ安全 JVM が保証 unsafe を使わない方針をドメインと application で機械的に守る NF-S22（新）
    乱数・依存・静的解析 SecureRandom、Gradle の依存検査、detekt・PMD・ktlint OS の暗号論的乱数、cargo-deny、clippy・rustfmt NF-S1、NF-S13、NF-O8
    DB のクライアント JDBC + HikariCP sqlx の接続プール NF-O3、NF-C5
    マイグレーション Flyway sqlx のマイグレーション NF-O11
    ローカル開発の DB H2 を許す PostgreSQL 18（Docker。2026-11-19 決定） NF-S20、NF-S18 の検証範囲

    変更した要件（全文）¶

    ID 要件 測定方法 扱い
    NF-P1 15 チーム（各 4 参加者 + 進行役）の同時利用で、意思決定の送信と役割別の状態取得の p95 を 1 秒以下とする。DB の接続プールが温まった後の定常値で測り、コールドスタート直後の 60 秒間は NF-P16 の目標（p95 2 秒以下）を別に確認する（JIT のウォームアップは存在しない） 75 並行、15 分の定常負荷。検証エラーと認可エラーは別の系列にする 変更
    NF-P15 ストリームの再生（events の読み込みと fold(evolve)）は、SESSION のストリームが 1000 件（想定の長さ。NF-C8）のとき、読み込みを含めて p95 100 ms 以下、再生（fold）だけで p95 20 ms 以下とする（Kotlin 版の提案値を引き継ぐ。Rust での実測で見直す）。最大の長さ（2000 件）でも同じ目標を測り、満たさなければスナップショット（NF-C9）を検討する 1000 件・2000 件のストリームでの計測。計測の道具は未選定（criterion などの候補は未確認。自前の計測でもよい）。先頭の複数回（提案: 5 回以上）は p95 に入れず、試行は 100 回以上、回数と方法を結果に記録する（DB のキャッシュの温まりを除く目的） 変更
    NF-P16 起動時間: コンテナのプロセスの開始から /api/v1/ready が成功するまで、p95 30 秒以下（マイグレーションの適用を除く。アプリの起動時間。ECS のタスクの起動時間とは別の区間で、運用要件の「起動時間の測る区間」に従う）（Kotlin 版の提案値を引き継ぐ上限。Rust の実測で見直す。縮める基準: Fargate での実測（10 回以上の p95）が上限の 3 分の 1 を下回り、運営者と合意できたとき）。コールドスタートの後 60 秒間の p95 は 2 秒以下（Kotlin 版の提案値を引き継ぐ上限。2026-11-21 のレビュー H6 で、1 秒に厳しくしていた誤りを戻した。RN1）とする（接続プールと OS のキャッシュの影響を測る） コールドスタートの計測（夜間） 変更
    NF-P17 メモリ: コンテナのメモリ上限から、プロセスが使える量を明示する。NF-C1 の負荷（15 ゲーム、75 の SSE 接続）の定常で、常駐メモリ（RSS）が、コンテナのメモリ上限の 70% 以下、OOM kill 0 件とする。tokio のタスク数と、確保したメモリの推移（増え続けないこと）を記録する。合否の式は「RSS ≤ コンテナのメモリ上限の 70%」かつ「OOM kill 0 件」（Kotlin 版の提案値を引き継ぐ。RN1）。実測で決めるのは、タスクのメモリの割り当て（上限）であり、この式の閾値ではない（GC の一時停止は存在しない） 負荷試験中の RSS・タスク数の記録 変更
    NF-P18 投影の再構築: 1 ゲーム（SESSION が 1000 件）の投影の再構築は、p95 1 秒以下。保持中の全ゲームの再構築は、100 ゲームを 5 分以内（保持中のゲーム数の想定は未決。提案）。再構築は、ゲームごとの排他ロックを取って行う（運用要件の手順 B） 再構築の計測（夜間）。方法は NF-P15 と同じ（先頭の複数回を除き、試行 100 回以上。回数と方法を記録する） 変更

    継続する要件（要約。正本は Kotlin 版）¶

    ID 要約
    NF-P2 週確定から全ブラウザの表示まで p95 2 秒以下（同一の時計で測る。同期投影のため通知の版以上の状態が取れる）。現行の画面は SSE を使わず 3 秒間隔のポーリングのため、この目標を満たせない見込み（推定。実測していない）。SSE を作る／間隔を詰める／目標を再定義する、のどれにするかは、B1 の実測で決める（2026-11-21 の決定。実測前に数値・方式を変えない。RN1。UI 設計 の影響表 #12）
    NF-P3 週確定のサーバー処理（再生・decide・追記・同期投影・冪等記録）は p95 1 秒以下、p99 2 秒以下（最大の長さ 2000 件）
    NF-P4 SSE が使えない場合、ポーリングに移り、確定から 4 秒以内に最新の版を表示する
    NF-P5 ブラウザでの入力確定から成功の表示まで p95 1 秒以下
    NF-P6 停止・再開・代理入力の API は p95 500 ms 以下
    NF-P7 再接続時の状態取得は 75 並行で p95 1 秒以下。SSE の再接続後 5 秒以内に最新の版
    NF-P8 観察と振り返りの取得は p95 1 秒以下。投影の SQL で返し、観察者は 3 表だけを読む
    NF-P9 エクスポートは受理 1 秒以内、CSV と JSON を 30 秒以内（p95）。build_export で要求時に作る
    NF-P10 保持状態の取得は p95 1 秒以下

    ストリームの最大の長さ¶

    Kotlin 版と同じです（想定 1000 件、保存回数の上限（提案: 1 役割・1 週あたり 9 回。代理入力を含む）を置くと最大 2000 件）。この見積もりと上限は、JVM の値ではなく設計上の見積もりで、Rust の実測で見直します。上限の有無と値は、運営者と合意して決める未決事項です。

    現行の画面の更新方式（ポーリング）による負荷の想定（レビュー H5）¶

    NF-C1・NF-P17・NF-P1 の負荷の想定は、Kotlin 版と同じ「15 ゲーム、75 の SSE 接続」です。現行の画面（既存の web/）は SSE を使わず、PLAY_POLL_MS（3000 ms）の間隔のポーリングで状態を取り直すため、実際の負荷は「ポーリングの GET が毎秒 25 件以上（75 ユーザー ÷ 3 秒に、ロビー・観察などの画面を足した見込み。推定で毎秒 50 件程度）」という形が違う負荷になる。負荷試験（NF-P1・NF-P17・NF-C1）は、実際の画面の更新方式（ポーリング）で行う。SSE を実装した場合は、その負荷（接続の維持）を別に測る。数値は推定で、実測していない。

    設計判断¶

    Kotlin 版の設計判断 N-1〜N-3 との対応¶

    ID Kotlin 版の決定 Rust 版の扱い
    N-1 投影の遅延は、同期投影により 0。非同期の目標は条件付き 引き継ぐ
    N-2 JVM の起動とメモリは、実測してから目標を固める 見直す（RN1）。JVM の項目は実行環境に読み替え、実測のない数値は提案のまま
    N-3 ロールバックのためのイベントの互換を、デプロイの要件にする（読める版を先にリリース） 引き継ぐ（NF-O11）

    RN1: JVM に固有の要件は、実行環境に読み替え、実測のない数値は変えない（承認済み。2026-11-19）¶

    案 内容 評価
    A（採用） JVM に固有の項目（ウォームアップ、ヒープ・GC）を、Rust の実行環境（接続プールの温まり、RSS、タスク数）に読み替える。数値の目標は、Kotlin 版の提案値を上限として引き継ぎ、Rust の実測で見直す（実測前に厳しくも緩くもしない） 根拠のない数値を、確定した要件にしない（Kotlin 版の N-2 と同じ方針）。Rust が速いはずという期待だけで目標を縮めない
    B Rust は JVM より速いとして、起動時間・メモリの目標を先に厳しくする 見かけは意欲的。実測がなく、運営者との合意の根拠にならない
    C JVM の項目を削除する 要件が減る。コールドスタート直後の遅さとメモリ使用の検証が抜ける

    RN2: キャンセル安全性（NF-R18）を要件として新設する（承認済み。2026-11-19）¶

    Kotlin 版は、キャンセルの扱い（NonCancellable、CancellationException の再送出）を実装の方針として持ちますが、非機能要件の ID は持ちません。Rust ではキャンセルが future の drop であり、ハンドラが途中で止まりうるため、要件として検証可能にします（NF-R18）。RB2 の前提が確認できなければ、設計を見直します。

    RN3: カバレッジのゲートは行 80%、分岐は目安（承認済み。2026-11-19）¶

    テスト戦略 の RT3 と同じです（NF-O7）。
