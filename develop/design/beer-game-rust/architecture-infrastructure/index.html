    インフラストラクチャアーキテクチャ - ビールゲームシミュレーション（Rust 版）¶

    概要¶

    本書は、beer-game-rust の実行環境と配信の構成を定義します。ADR-001 により、beer-game-kotlin のインフラ（beer-game2 の構成を踏襲）を正本として引き継ぎ、Rust で変わる点だけを定めます。docs/ を設計の正本とします。実装コードも、インフラのコードも、まだ存在しません。

    引き継ぐ構成は、CloudFront の単一オリジン（静的ファイルは S3、/api/* は ALB）、ECS Fargate、RDS for PostgreSQL 18、ECR、Terraform（リモートの状態・環境ごとに分離・モジュール化）、GitHub Actions の OIDC、ステージング自動・本番承認とブルー/グリーン、構造化ログとメトリクス（EMF）、合成監視、アラームです。非同期・キューは使いません（Kotlin 版と同じ）。

    変わるのは、次の点です。

    • コンテナと起動: JVM のイメージから、Rust の単一バイナリのイメージへ。実行イメージの選択、ヘルスチェックの方法、起動モードと終了コード。
    • ビルドと CI: Gradle から Cargo へ（ツールチェーンの固定、--locked、キャッシュ）。
    • メモリ・終了・起動時間: ヒープ・GC・ウォームアップの前提がなくなる。SIGTERM で完了を待って正常終了する（NF-R18）。
    • データベースの接続: sqlx の接続プール。ロールを用途別に分けるのは同じ。
    • ローカル開発の DB は PostgreSQL 18（Docker）に決定（2026-11-19。H2 を持たない）。

    本書の位置づけと確認の範囲¶

    • 本書で確認したこと: ローカルの環境を調べ、Rust 版のコンテナのビルドと実行は、ここでは検証できないことを確認しました（2026-11-19）。ローカルの Rust のホストは x86_64-apple-darwin のみで、Linux 向けのターゲットも、クロスコンパイルの道具（cross・cargo-zigbuild・zig）もありません。Docker は動きますが（linux/x86_64）、rust のイメージも Rust 向けの軽量ベース（distroless など）もローカルにありません。PostgreSQL 18.6 のイメージはあり、データモデル・運用要件の実測に使いました。
    • 確認していないこと: 本書のコンテナ、起動モード、SIGTERM の振る舞い、起動時間、メモリ、Terraform、CI/CD は、すべて未実装・未検証です。ベースイメージの実在、バイナリの動的／静的リンク、実行イメージに必要なライブラリは未確認で、B1 で確かめます。
    • 引き継ぐ値: Terraform・AWS プロバイダー・PostgreSQL・Node の版は、Kotlin 版が確認した値を引き継ぎ、本書では再確認していません。
    • Kotlin 版の実装の経緯（B2・B3・B14 の注記）は引き継ぎません。Kotlin 版の未決事項は、本書の未決事項に引き継ぎます。

    確認したバージョン¶

    区分 技術 版 出典・備考
    言語 Rust 1.97.1（2026-07-14） ローカルの rustc --version（2026-11-19）。Rust は LTS を持たず、最新の安定版だけがサポートされる（技術スタック）
    ビルド Cargo（ワークスペース） Rust に同梱 rust-toolchain.toml で固定、Cargo.lock をコミットし --locked で実行
    Web・非同期・DB axum 0.8.9、tokio 1.54.1、sqlx 0.9.1 同左 cargo search（2026-11-19）。詳細は 技術スタック
    IaC Terraform / AWS プロバイダー Kotlin 版の値（作業用 1.17.2、required_version >= 1.17.0、~> 6.0）を引き継ぐ 再確認していない
    データベース PostgreSQL 18（RDS） 18 再確認していない（Kotlin 版の確認値）。ローカルの検証は 18.6
    フロントエンドのビルド Node 26 Kotlin 版・beer-game2 の値 再確認していない
    コンテナのイメージ ビルド用・実行用 未確認（下の「イメージ」） Docker Hub などでの実在を B1 で確認する

    決定の整理¶

    Kotlin 版から変更する点を太字で示します。

    決定項目 採用 Kotlin 版との違い・根拠
    クラウド・デプロイ形態・配信・データベース・非同期 AWS（ap-northeast-1）、ECS Fargate、CloudFront の単一オリジン、RDS PostgreSQL 18、キューなし 変更なし
    定期処理 EventBridge による ECS タスク。同じイメージの別の起動引数で起動する 変更なし
    イメージ ECR。Rust の単一バイナリを、軽量な実行イメージに載せる。マルチステージ（設計判断 RI1） JVM のイメージから変更
    実行環境 ネイティブの単一プロセス。SIGTERM で完了を待って正常終了（終了コード 0）。ヘルスチェックはバイナリのサブコマンド JVM のヒープ・GC・ウォームアップ・終了コード 143 の扱いがなくなる
    秘密情報 Secrets Manager（鍵の版を複数保持）、KMS。ロールごとに別の DB の接続情報 変更なし
    IaC Terraform。Rust 版専用に複製して出発する（設計判断 RI5。承認済み。AWS への適用は別のゲート） team の規約は beer-game3 専用の環境のため、Rust 版専用を新設する
    ビルド Cargo（rust-toolchain.toml、Cargo.lock、--locked） Gradle から変更。フロントエンドは npm のまま
    CI/CD GitHub Actions（OIDC）。ステージングは自動、本番は承認 + ブルー/グリーン。ワークフローは beer-game3 用とは別に新設（team の規約） 検証の手順が Cargo になる
    観測 構造化ログ、メトリクス（EMF）、合成監視、アラーム、ダッシュボード JVM の指標が RSS・タスク数・panic・取り残しに変わる（運用要件）

    全体構成¶

    構成要素¶

    CloudFront、S3（Web）、ALB、保持の定期タスク、RDS、ECR、ネットワーク、観測の基本は、Kotlin 版 と同じです。変更する要素を示します。

    要素 設定
    ALB HTTPS、アイドルタイムアウト 60 秒、ヘルスチェックは /api/v1/ready（Kotlin 版の実装のパス。契約を共有する）。ヘルスチェックの猶予期間は、Rust の起動時間の実測で決める（JVM の見込みは引き継がない）
    API サービス Fargate、常時 2 タスク、CPU 60% で 2〜4 に自動増減。ステートレス。本番はブルー/グリーン、ステージングはローリング。タスクのサイズの初期案は 1 vCPU / 2 GiB（Kotlin 版と同じ）。実測の前に小さくしない（設計判断 RI2）
    保持・マイグレーション・再構築・検査のタスク 同じイメージを、起動引数（retention、migrate、rebuild-projections、verify-projections）で切り替える。保持は EventBridge で 5 分ごと、検査は日次、マイグレーションはデプロイの一部（アプリの起動前）に 1 回限り、再構築は運用者が必要なときに起動する（研修中は、運営者を通じて進行役に「停止」を依頼し、停止中に再構築して再開する。運用要件）
    秘密情報 DB の接続情報を、ロールごとに別の秘密として持つ。資格の鍵（複数の版）、応答の暗号鍵は変更なし。実行ロールには、そのタスクに必要な秘密の参照権限だけを与える
    観測 JSON ログとメトリクス（EMF）は標準出力へ出し、コンテナのログドライバが CloudWatch Logs へ送る。RSS・タスク数・接続プールの待ち・panic の件数・idle in transaction の件数のアラームを加える（運用要件）

    データベースのロールと接続¶

    ロールの定義と権限は データモデル の 5 ロール（beergame_writer・beergame_reader・beergame_observer・beergame_deleter・所有者）と同じです。追記専用の権限と連鎖削除は、PostgreSQL 18.6 で実測済みです（1 回）。

    ロール 使うタスク 接続の持ち方（Rust 版）
    書き込み api（コマンド）、rebuild-projections sqlx の PgPool。トランザクション単位。アプリが接続する「ログインユーザー」に idle_in_transaction_session_timeout を設定（NOLOGIN の beergame_writer に設定しても継承されず効かない。運用要件 の障害パターン 17。実測済み）
    読み取り api（問い合わせ） 別の PgPool
    観察者の読み取り api（観察者の問い合わせ） 別の PgPool（beergame_observer で接続。3 表だけ読める）
    通知の受信 api プールの外の専用の接続（1 タスクにつき 1 本。LISTEN 用。sqlx での扱いは未確認）
    削除 retention 小さな PgPool
    所有者 migrate 1 回限りの接続

    接続数の見積もり: タスク数 × （書き込み + 読み取り + 観察者の各プールの最大 + 通知 1 本）+ 運用のタスク。この合計が RDS のインスタンスの接続数の上限を超えないことを、タスクの最大数（4）で確認します。プールの大きさは負荷試験で決めます（未決）。接続を集約するプロキシや接続プーラーは、LISTEN が動かない可能性があるため、置きません（Kotlin 版と同じ）。

    TLS: RDS への接続は、証明書の検証つきの TLS を使う方針です。sqlx の TLS の実装（rustls か OpenSSL か）と、RDS の CA バンドルの配置は未決で、実行イメージの選択（下の RI1）に影響します。

    コンテナ¶

    イメージ（設計判断 RI1）¶

    FROM（ビルド）  rust:<1.97.1 系>            … cargo build --release --locked（ツールチェーンは rust-toolchain.toml で固定）
FROM（実行）    <軽量な実行イメージ>         … バイナリ 1 つと、必要最小限のファイルだけ
                USER <非 root の数値の UID>
                ENTRYPOINT [ "/app/beergame" ]  CMD [ "api" ]     … api / retention / migrate / rebuild-projections / verify-projections / healthcheck
    • マルチステージにし、実行用のイメージには、バイナリと必要最小限のファイル（証明書の束、RDS の CA バンドル）だけを含めます。ビルドの道具（Rust のツールチェーン、ソース）を含めません。
    • 依存のビルドを別の層にして、アプリだけの変更で層のキャッシュが効くようにします（Cargo.toml・Cargo.lock だけを先にコピーしてビルドする方法など。cargo-chef のような道具は未選定で、導入は承認が要る）。
    • 実行は非 root のユーザー（数値の UID）。ファイルシステムは読み取り専用を目指します。
    • イメージのタグは、コミット SHA（ECR の不変のタグ）。以降はダイジェストで固定します（Kotlin 版と同じ）。
    • H2 のような「本番に含めない依存」は無いので、Kotlin 版の「配布から H2 を除外する」作業は不要です。

    実行イメージの候補（どれも実在・動作を未確認。B1 で確認して決める）:

    案 内容 長所 短所
    A（採用） glibc を含む最小のイメージ（distroless の cc など）に、動的リンクのバイナリを載せる 小さい。シェルがなく攻撃面が小さい。標準の Rust のビルドのまま シェルがないので、ヘルスチェックはバイナリのサブコマンドで行う（下記）。運用時にコンテナ内で調査しにくい
    B debian-slim に、動的リンクのバイナリを載せる シェルがあり調査しやすい。OpenSSL の利用が容易 A より大きく、脆弱性の対象が増える
    C scratch に、静的リンク（musl）のバイナリを載せる 最小。依存がない musl のビルドの設定（OpenSSL を避ける）が要る。DNS・証明書の束を自前で持つ。メモリの確保の性能が glibc と異なりうる
    D alpine に、musl のバイナリを載せる 小さく、シェルがある musl の差異。C と同様

    ヘルスチェックの実装（RI3。2026-11-21 のレビュー M5 で対象を見直し）: Kotlin 版は、実行イメージに curl も wget もないため、bash の /dev/tcp で /api/v1/ready に GET を送りました。Rust 版は、案 A・C ではシェルがないので、バイナリに healthcheck サブコマンドを持たせます。ただし、コンテナの生存の検査は /api/v1/health（プロセスが応答するか）を対象にし、/api/v1/ready は ALB のターゲットの検査（負荷分散の対象から外す）に使います。/api/v1/ready は DB の接続に依存するため、これをコンテナの生存の検査に使うと、DB の障害の間に全タスクが unhealthy になり、ECS が入れ替えを繰り返して障害を広げます。healthcheck サブコマンドは、AppConfig::load（秘密が無ければ終了コード 78）を通さない軽い経路で、/api/v1/health を呼び、200 のときだけ終了コード 0 とします（interval 30s、timeout 3s、start-period は起動時間の実測で決める。retries 3）。ECS は Dockerfile の HEALTHCHECK を使わず、タスク定義の healthCheck を使う見込み（未確認。B1 で確認し、必要ならタスク定義に同じコマンドを書く）。

    起動モードと終了コード¶

    同じイメージを、CMD（引数）のモードで切り替えます（Kotlin 版と同じモードと終了コード。API の契約と運用手順書を揃えるため）。

    モード 動作 終了
    api 常駐。SIGTERM で完了を待って正常終了（下記） SIGTERM で 0（目標。Kotlin 版は 143）
    migrate マイグレーションを適用して終了 成功で 0
    retention 保持削除の掃引を 1 回行って終了 放棄したゲームがあれば 1、掃引の失敗は 70
    rebuild-projections [ゲーム ID ...] 投影を events から作り直す 再構築できなかったゲームがあれば 1、ゲームの一覧を読めなければ 70、形が不正なゲーム ID は 64
    verify-projections 投影が、イベントから作り直した結果と一致するかを検査する（日次。投影は変えない） 不一致があれば 1
    healthcheck /api/v1/health を呼ぶ（Rust 版で追加。コンテナの生存の検査用） 200 なら 0、それ以外は 1
    不明なモード 使い方を示す 64
    終了コード 意味（sysexits の慣例に沿う）
    0 1 回限りの処理の成功、api の SIGTERM による正常終了
    1 放棄・再構築の失敗・投影の不一致・healthcheck の失敗
    64 使い方の誤り
    70 起動の失敗（ほか）
    78 設定の誤り（秘密が無い、ほか）。足りない設定の名前だけをログに出す

    メモリ・CPU・起動（設計判断 RI2）¶

    項目 設計
    ヒープ・GC 存在しない。JVM の MaxRAMPercentage・ExitOnOutOfMemoryError に当たる設定はない。メモリ不足は OOM kill として現れ、ECS が再起動する（運用要件の障害パターン 15）
    タスクのサイズ 初期案は 1 vCPU / 2 GiB（Kotlin 版と同じ）。Rust は小さくできる見込みだが、実測の前に小さくしない（RN1 と同じ方針）。負荷試験で RSS・タスク数・接続プールの待ちを測り、十分な余裕を残した上で縮める
    CPU JIT のコンパイルによる起動直後の CPU の高まりはない。自動増減のクールダウンは、JVM のような「起動直後の CPU の高まりを誤解しない」目的では不要だが、値は実測で決める（初期値は設ける）
    起動の短縮 AppCDS のような仕組みは不要。ネイティブコンパイル済みのため、起動は短い見込みだが、実測する（NF-P16。上限 p95 30 秒を維持し、実測で縮める）
    ログ 標準出力（構造化 JSON）。panic も記録する

    起動と終了¶

    局面 設計
    起動 設定を読み込み、検証する（AppConfig::load。失敗なら起動しない。終了コード 78）→ 接続プールを作る → 通知の受信を始める → HTTP の受付を始める。/api/v1/ready は、データベースの接続、通知の受信の接続の生存、スキーマの版が期待と一致することが確認できるまで、503（app.not_ready）を返す。起動のたびに投影の再構築はしない
    マイグレーションとの順序 マイグレーションのタスクが完了してから、アプリのタスクを起動する（デプロイの手順で保証）。アプリは起動時に、期待するスキーマの版が適用済みかを確認し、未適用なら準備できていない
    終了（NF-R18） ECS は、タスクの停止時に SIGTERM を送り、一定の時間（stopTimeout）の後に強制終了する。アプリは SIGTERM で、新しい要求の受付を止め、進行中のコマンドの完了を待ち（待ちの上限は stopTimeout より短く）、SSE の接続を閉じ、接続プールを閉じ、終了コード 0 で終わる。クライアントは、SSE が切れても再接続し、スナップショットを取得して追いつく。重要（2026-11-21 のレビュー H3）: axum の graceful shutdown は接続の完了を待ちますが、切り離された（JoinHandle が drop された）コマンドのタスクの完了は待たない見込みで、SSE の接続は自然には閉じない。そのため、(1) 終了の合図で SSE の stream を止める（止めないと、graceful の待ちが stopTimeout まで続き、SIGKILL で終わって「終了コード 0」を満たせない）、(2) コマンドのタスクを追跡し、完了を待つ（追跡の道具は B1 で承認）。実現は B1 で確認（バックエンドアーキテクチャ の RB2「spawn したタスクの寿命」）
    負荷分散との整合 ALB のターゲットの登録解除の遅延（deregistration delay）と、アプリの終了の待ちを整合させる。長い SSE の接続は、猶予の後に切られてよい
    1 回限りの処理 正常終了は終了コード 0、失敗は 0 以外。失敗は CloudWatch のアラームで通知する

    SIGTERM の終了コード: Kotlin 版は、JVM が停止フックを実行して終わるため 143 で、「正常とみなす条件」が人の判断待ちでした。Rust 版は、シグナルを自分で処理して正常終了できるため、終了コード 0 を目標とし、アラームの扱いの問題をなくします（実装は未確認）。

    10 Flyway（ベンダー別の配置） sqlx のマイグレーション（1 系統） ツールの違い
    11 依存関係の検査ツールは「JVM に対応するもの」を選定（未決） cargo-deny R4 で選定済み
    12 Terraform は Kotlin 版専用の infra/ Rust 版専用に複製して出発する（RI5。承認済み）。AWS への適用は別のゲート team の規約は beer-game3 専用の AWS 環境

    上記以外（CloudFront、S3、ALB、RDS、ECR、EventBridge、Secrets Manager、観測の基本、OIDC、ステージング自動・本番承認、ブルー/グリーン、データベースのロール、LISTEN の専用接続、接続数の見積もり）は変えません。

    設計判断¶

    RI1: 実行イメージは、軽量な最小イメージに単一バイナリを載せる（承認済み。2026-11-19）¶

    上の候補（A〜D）のとおりです。案 A を採用しました（2026-11-19 承認。glibc を含む最小のイメージ。シェルなし）。理由は、攻撃面が小さく、標準の Rust のビルドのまま使えるためです。ただし、実在・動作・必要なライブラリ（OpenSSL を使う場合）は未確認で、sqlx の TLS の実装（rustls か OpenSSL か）によって選択が変わります。B1 で、実際にビルド・起動して確認し、決めます。

    RI2: タスクのサイズは、実測の前に小さくしない（承認済み。2026-11-19）¶

    初期案は Kotlin 版と同じ 1 vCPU / 2 GiB です。Rust のバイナリはメモリの使用量が小さい見込みですが、実測がないため、RN1 と同じ方針（実測前に厳しくも緩くもしない）にします。負荷試験（NF-C1: 15 ゲーム・75 の SSE 接続）で、RSS（NF-P17: 上限の 70% 以下）・タスク数・接続プールの待ちを測り、余裕を残して縮めます。縮めた値は、運用要件の RSS の閾値とあわせて見直します。

    RI3: ヘルスチェックはバイナリのサブコマンドで行う（承認済み。2026-11-19）¶

    実行イメージにシェルも curl もない（案 A・C）ため、healthcheck サブコマンドを持たせます。代替は、シェルのあるイメージ（案 B）で bash の /dev/tcp を使う方法（Kotlin 版と同じ）です。サブコマンドは、イメージの選択に依存せず、テストもできる（テスト戦略）ため、採用します（2026-11-19 承認）。

    RI4: SIGTERM では完了を待って終了コード 0 で終わる（承認済み。2026-11-19）¶

    NF-R18 の要件です。待ちの上限は stopTimeout より短く設定します。終了コード 0 にすることで、Kotlin 版の「143 を正常とみなすか」の未決を設計で解消します。実現（tokio のシグナル処理、axum の graceful shutdown、spawn したタスクの完了待ち）は B1 で確認します。

    RI5: Terraform は Rust 版専用に複製して出発する（承認済み。2026-11-19）¶

    上の案 A を採用しました（2026-11-19 承認）。AWS への適用は別のゲートで、本書は適用を含みません。

    前提と見直しの条件¶

    • 常時 2 タスクで足りる前提: 同時に進行するゲームが少数。負荷試験で確認する。
    • ネイティブコンパイルの利点（起動が短く、メモリが小さい）が実測で確認できない場合は、タスクのサイズを縮めない（RI2）。
    • キューを再導入する条件、非同期投影へ移す条件、WAF の導入の条件は、Kotlin 版と同じ。
