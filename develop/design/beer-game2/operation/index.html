    運用要件定義 - ビールゲームシミュレーション（v2）¶

    概要¶

    本書は、beer-game2（v2）を本番で運用するための要件を、運用フロー、監視、バックアップ、障害対応、変更管理の順に定義します。docs/ を正本とします。

    beer-game（v1）の 運用要件（11 件の差分を記録）を出発点に、v2 の設計（インフラ、ADR-007、ADR-009、ADR-012）と、非機能要件（v2） を反映して改訂しました。表の「v1 の状態」は v1 の実装・設定の状況で、△・✗ は v2 で満たす対象です。

    • 非機能要件（SLO、RPO/RTO、監視の閾値）
    • aidlc/ の Unit ごとの監視・CI/CD・インフラ設計（construction/*/infrastructure-design/）

    運用の体制、通知先、連絡先は、組織に依存するため未決定です。本書では、決めるべき項目として「要確認」にしています。

    凡例（v1 の状態）¶

    記号 意味
    ✓ v1 で、実装または設定があり、確認した（v2 でも引き継ぐ）
    △ 一部のみ
    ✗ 未実装・未整備

    運用の前提¶

    項目 内容
    利用の形態 研修・授業のセッション（数十分〜数時間）。同時に進行するゲームは最大 15（拡張目標 25）。常時の高負荷は無い
    重視する時間帯 研修の実施中。運営者が事前に実施日時を運用側へ伝える仕組みが必要（SLO の「宣言された時間帯」。U1 NFR2.2）
    運用の主体 運営者（進行役の所属組織）と、システムの運用担当（プラットフォーム、アプリケーション）。体制は要確認
    守るべき資産 確定済みの週の記録（RPO 0）、資格、保持期間内のゲームの記録
    主な SLO 月間可用性 99.5%、研修中の完全停止を 1 分以内に検知、RTO 15 分、RPO 0（非機能要件）

    運用フロー¶

    運用は、自動化を前提にします。手動の作業は、判断が要るものと、年次のものに限ります。

    周期 作業 主体 自動化 v1 の状態
    常時 ヘルスチェック、アラートの通知 自動 ALB のヘルスチェック、CloudWatch のアラーム △（アラームは ALB の接続数 1 件）
    研修の前 実施日時の連絡を受け、直前の合成監視（作成から参加、SSE まで）で正常を確認する 運用担当 合成監視を自動化 ✗
    研修の中 アラートに即応できる状態にする（オンコール） 運用担当 — ✗（体制が未定義）
    日次 ダッシュボードで、エラー率、応答時間、削除の滞留（期限超過の経過時間）と失敗の件数を確認する 運用担当 アラートで代替 ✗
    日次 コストの確認（予算の 80% 実績、100% 予測の通知） 自動 AWS Budgets ✓
    週次 失敗した削除（FAILED）の確認。失敗があれば、失敗コードから原因を調べ、再試行する 運用担当 失敗時の通知 ✗
    月次 SLO のレポート（可用性、p95、削除の SLO）、容量のレビュー、依存関係の更新とセキュリティのパッチ 運用担当 レポートを自動生成 ✗
    四半期 復元の訓練（時点復旧）。学習ビューの再構築の訓練 運用担当 手順をスクリプト化 ✗
    年次 鍵のローテーション、権限の棚卸し、ランタイムのサポート期限の確認（Node 22 は 2027-04-30）、監査への対応 運用担当、セキュリティ責任者 — ✗
    随時 リリースとロールバック（変更管理を参照） 開発・運用 CI/CD ✗（デプロイが未実装）

    監視設計¶

    監視項目と閾値¶

    閾値は、非機能要件 の数値と、aidlc/ の監視設計から導きます。両者に無い値（Warning の一部、セキュリティの倍率）は、提案です。警告（Warning）は担当者の確認、重大（Critical）は即時の対応です。アラート疲れを避けるため、対応が必要なものだけを通知にします。

    区分 監視項目 Warning Critical 情報源 v1 の状態
    可用性 研修中の主要な操作（作成、参加、確定）の成功 — 1 分間、成功が無い 合成監視 ✗
    可用性 5xx の割合 1% 超（5 分） 5% 超（1 分） ALB、アプリ ✗
    性能 API の応答（p95） 800 ms 超（5 分） 1 秒超（5 分） ALB、アプリ ✗
    性能 週確定から画面反映（p95） 1.5 秒超（5 分） 2 秒超（5 分） 合成ブラウザ ✗
    性能 SSE の切断・ポーリング切替の割合 5% 超（5 分） 10% 超（5 分） アプリ、ALB ✗
    整合性 週結果の重複、不変条件の違反、イベントの欠落 — 1 件でも発生 アプリのメトリクス ✗
    配信 アウトボックスと SSE の遅延（p95） 1 秒超（5 分） 5 秒超（5 分） アプリ ✗
    データベース CPU、接続プールの使用率 70% 超 80% 超（10 分） RDS、アプリ ✗
    データベース フェイルオーバー、バックアップの失敗 — 発生 RDS イベント ✗
    容量 ECS タスクの CPU 60% 超（自動増減の目標） 80% 超（10 分） ECS △（自動増減は設定済み）
    削除 期限超過の削除の経過時間 18 時間 24 時間 Saga のクエリ ✗
    削除 削除の再試行の回数（上限 5 回に近づいたもの） 3 回目 5 回（上限） アプリのメトリクス ✗
    削除 削除の恒久的な失敗（FAILED） — 発生から 5 分以内に通知 アプリ ✗
    セキュリティ Origin 拒否、認証失敗の急増 平常の 3 倍（提案） 平常の 10 倍（提案） アプリ ✗
    コスト 月次の予算 実績 80% 予測 100% AWS Budgets ✓（この 2 つを設定済み）

    実装済みのアラーム（Bolt 11。Terraform で定義、AWS には未適用）¶

    上の表のうち、Critical の次の項目を、infra/modules/observability に定義しました（Bolt 11 計画）。メトリクスはアプリが EMF で出します（名前空間 BeerGame2、次元 Environment）。通知は SNS のトピック（<name>-alerts）で、メールの購読は変数 alert_email で作ります。

    監視項目 アラーム メトリクス 条件
    研修中の主要な操作の成功 <name>-ready-canary CloudWatchSynthetics の SuccessPercent（合成監視、1 分ごとに /api/ready） 1 回（1 分）でも 100% 未満。データ無しも発報
    5xx <name>-server-errors ServerErrors 5 分で 5 件以上
    API の応答（p95） <name>-api-latency-p95 Latency p95 が 1 秒超（5 分）
    不変条件の違反 <name>-invariant-violations InvariantViolations（500、または DB の一意制約の違反） 1 件で発報
    削除の恒久的な失敗 <name>-retention-permanent-failures RetentionPermanentFailures 1 件で発報

    合成監視は /ready ではなく /api/ready を叩きます（CloudFront は /api/* だけを API へ中継するため）。Warning の通知と、DB・容量・セキュリティの項目は、まだ定義していません。

    ヘルスチェック¶

    種類 内容 v1 の状態
    生存（liveness） プロセスが応答する ✓（GET /health が {"status":"ok"}）
    準備（readiness） データベースに接続できる（SELECT 1）。通らないタスクは ALB の対象から外れる ✗（/health はデータベースを確認しない）

    v1 の /health は、データベースが落ちていても「正常」を返し、ALB がデータベース障害を検知できませんでした。v2 は、GET /ready（SELECT 1）を設け、ALB のヘルスチェックに使います（バックエンド）。

    ログと追跡¶

    項目 要件 v1 の状態
    アプリのログ 構造化 JSON（相関 ID、操作、結果、版、所要時間）。資格、表示名、非公開の値を含めない ✗（出力が無い。非機能要件 の差分 #1）
    集約と保持 暗号化した CloudWatch Logs。本番 90 日、その他 14 日 △（ロググループは作成済み）
    追跡 相関 ID を HTTP、トランザクション、アウトボックス、SSE に伝える △（応答とイベントには付く）
    監査 設定、役割変更、代理入力、週確定、停止、再開、終了、保持の再試行 △（イベントのみ）

    ダッシュボード¶

    次を 1 つの画面で見られるようにします（現状は未整備）: リクエスト量・応答時間・エラー、進行中のゲーム数と SSE の接続数、確定の成功・競合・ロールバック、アウトボックスの遅延、DB の状態、SLO の消費、削除の状況（現在と 30 日の推移）。

    アラートとエスカレーション¶

    重要度 定義 通知 対応の目標
    P1（重大） 研修中の停止、データの整合性の違反、削除の恒久的な失敗、バックアップの失敗 即時にオンコールを呼び出す。インシデントのチャンネルを開く 5 分以内に着手（提案）
    P2（高） 性能の劣化、配信の遅延、削除の遅れ 担当チャンネルへ通知する 研修中は 15 分、それ以外は翌営業日（提案）
    P3（中） 予算、容量の予兆 担当者へ通知する 週次で確認

    要確認: 現状の通知先は、SNS のメール（ops_alert_email）だけです。オンコールの当番、呼び出しの手段、インシデントのチャンネル、運営者への連絡窓口は、未定義です。

    バックアップ設計¶

    対象と方式¶

    対象 方式 保持 v1 の状態
    データベース（ゲームの状態、イベント、出力、保持削除の状態。PostgreSQL 18） RDS の自動バックアップによる時点復旧（PITR）と、Multi-AZ の同期スタンバイ 7 日 ✓（設定済み。本番は削除保護あり）
    Web の静的ファイル S3 のバージョニング、ビルド成果物（版つきで不変） バージョンごと ✓
    イメージ レジストリの不変の版（ダイジェスト固定） 直近の複数世代 △（レジストリが未確定。変更管理を参照）
    インフラの定義 Git（Terraform） 無期限 ✓
    Terraform の状態 暗号化した S3 のリモートの保管と排他ロック。環境ごとに分離（ADR-012） 版つき ✗（v1 は backend の定義が無い）
    秘密情報 Secrets Manager。資格の鍵は複数の版を同時に保持（ADR-009） — △（v1 は注入のみで、版管理とローテーションの手順が無い）
    エクスポートの成果物 保存しない（要求のたびに組み立てる。Bolt 9） — —

    RPO と RTO¶

    指標 目標 根拠 v1 の状態
    RPO 確定済みの週は 0 永続化のコミット後にだけ応答。Multi-AZ の同期スタンバイ △（設計は満たす。訓練で確認していない）
    RTO 15 分 最後の確定済みの週から再開できる ✗（訓練が無く、未測定）

    復元の手順（要件）¶

    1. 復元の対象時点を決める（直前の確定週など）。新しいインスタンスへ時点復旧する。
    2. 復元後は、保持の定期タスクを実行して、期限切れのゲームを再び削除し、削除済みのゲームが残っていないことを確認してから、利用を再開する（復元で、削除済みのゲームが再び現れないようにする）。
    3. アプリの接続先を切り替え、合成監視で、作成、参加、SSE が通ることを確認する。
    4. 進行中だったゲームを確認し、運営者へ連絡する。

    訓練: 四半期に 1 度、およびリリース前、バックアップ方針の変更時に、復元の訓練を行い、RPO と RTO の実測値を記録します。復元の手順がテスト可能な形（手順書とスクリプト）で用意されていなければ、バックアップ設計は完了していません。

    バックアップと削除の関係¶

    保持期間後に削除しても、自動バックアップには最大 7 日間、削除前のデータが残ります。保持方針（「期限後に削除する」）との関係を、運営者に明示する必要があります（例: 「期限後、最大 7 日以内にバックアップからも消える」）。v2 では、この期間を、保持方針に明記し、運営者へ示します（NF-S16）。進行役のロビーに、保持期間・削除予定日と「データベースのバックアップには、削除後も最大 7 日残ります」を表示します（Bolt 10）。復元時は、上の手順 2 で、削除済みのゲームを再び削除します。

    保持の定期タスク（node dist/retention.js）は、EventBridge Scheduler から 5 分ごとに起動します。削除は 1 ゲームずつ 1 つのトランザクションで行い、失敗したら何も消えず、次の起動で再試行します。5 回失敗したゲームは再試行をやめ、エラーのログ（保持の削除で恒久的な失敗があります）と終了コード 1 を残します（通知は観測の完成で扱う）。削除の受領記録（deletion_receipts）は、ゲームを特定できない参照で 1 年残します。

    障害対応設計¶

    障害パターンと復旧¶

    # パターン 検知 影響 初動と復旧 目標
    1 API のタスクの異常（クラッシュ、メモリ） ALB のヘルスチェック、ECS 一部の接続が切れる。SSE は再接続、状態は DB にあるため失われない ECS が自動で置き換える。続く場合は直近のリリースを疑い、ロールバック 自動
    2 API の全停止 合成監視、5xx 研修が止まる 直近の変更なら、ロールバック。それ以外は、DB と依存の状態を確認し、タスクを再起動する 15 分
    3 データベースのフェイルオーバー RDS のイベント 数十秒の接続断。確定の一部が失敗しうる 自動の切替を待つ。失敗した操作は、冪等キーで再送できる。接続の回復を確認 数分
    4 データベースの破損・誤操作 整合性のアラート、利用者の報告 記録の不整合 時点復旧（バックアップ設計の手順）。復元ゲートを守る 15 分
    5 SSE の不通（ALB、CloudFront、タスク） SSE の切断率 反映が 1 秒間隔のポーリングに落ちる（最大 4 秒の遅れ） 利用は継続できる。原因（タイムアウト、ヘッダーの転送）を調べて直す 影響は軽微
    6 デプロイの失敗、またはリリース直後の劣化 ヘルスチェック、SLO の消費、ベイク期間 一部または全体の劣化 ロールバック（直前のダイジェストへ戻す） 15 分
    7 削除の失敗（deletion_runs が FAILED、または再試行の上限に近い） 削除の失敗のアラーム、期限超過の経過時間 保持期間後のデータが残る 失敗コードを確認し、原因（データベースの負荷、ロックなど）を直してから、保持状態の画面（または API）で再試行する。削除は 1 トランザクションのため、「半分だけ削除」は起きない 24 時間（SLO）
    8 資格の漏洩（進行役、復帰、観察用の招待、セッション） 利用者の報告、認証失敗の急増 他人が役割・進行・観察を行える v2 は、進行役が資格を失効・再発行できる（進行役の資格）。観察用の招待は失効して再発行する。必要なら、当該ゲームを停止する。重大な場合は、運用担当が、ゲームを終了して作り直すよう運営者へ依頼する 15 分
    9 鍵の誤設定・漏洩（資格の鍵、暗号鍵） 認証失敗の急増、起動の失敗（本番は、未設定で起動に失敗する） 全資格が無効、または偽造の危険 鍵のローテーション手順: 新しい版を追加 → デプロイ → 新しい資格は新しい版で発行 → 旧版は、資格の期限が切れるまで検証用に残す → 旧版を廃止する。漏洩の場合は、旧版を即時に廃止し、全資格を失効させる 30 分
    10 CloudFront の設定ミス（ヘッダーの転送、キャッシュ） 認証失敗・Origin 拒否の急増 ログインや更新が壊れる 直前の設定へ戻す（IaC） 15 分
    11 利用者側の操作ミス（誤った週確定、誤った終了） 運営者の連絡 元に戻せない 確定は元に戻せない（設計）。終了後は、新しいゲームを作る。確認ダイアログで予防する —
    12 依存関係の重大な脆弱性 脆弱性の検査 攻撃の危険 緊急変更として、パッチを適用してリリース 72 時間以内（Critical。提案）

    各パターンの手順書（コマンド、確認の画面、判断の基準）は、docs/operation/beer-game/ に作成します（運用手順書の一覧を参照）。

    リリースの流れ¶

    ロールバック¶

    対象 ロールバックの手段 テスト
    アプリ（API、保持の定期タスク） 直前のイメージのダイジェストを指定してデプロイ ステージングで、ロールバックの手順を毎回確認する

    変更の承認¶

    区分 例 承認 実施の時間帯
    標準変更 画面の文言、テストの追加、依存関係のパッチ（検査を通過） プルリクエストのレビューと CI 随時（研修の時間帯を避ける）
    通常変更 機能の追加、スキーマの変更、インフラの変更 レビュー、ステージングでの確認、本番は手動承認 研修が無い時間帯
    緊急変更 重大な脆弱性、データの整合性の障害 運用責任者の承認（事後に記録） 随時

    研修の実施日時の前後は、通常変更を凍結します（運営者から連絡された日時を、運用の予定に載せる）。変更は、Git の履歴、ADR、更新ログ（docs/log.md）で追跡します。

    容量・コスト管理¶

    項目 内容
    容量のレビュー 月次。同時ゲーム数、SSE の接続数、API の p95、DB の接続プールの使用率の推移を確認する
    拡張の契機 API の p95 が 800 ms 超（5 分）、DB の接続プールが 70% 超、SSE の遅延が p95 1 秒超のときに、容量アラートを出す
    自動の増減 API は CPU 60% を目標に、2〜4 タスクで自動増減（設定済み）
    上限を超える見込み 25 ゲーム・100 接続を超える利用は、実測の飽和点と DB の競合を見て判断する
    コスト 月次の予算を設定し、実績 80% と予測 100% で通知（設定済み）。開発環境は、夜間に縮小する（提案）

    v1 からの変更（差分への対応）¶

    v1 の差分（11 件）への対応です。すべて v2 の要件として引き継ぎました。

    # v1 の差分 v2 の対応
    1 ログ、メトリクス、ダッシュボードが無い 構造化ログ、エラーの記録、メトリクス（EMF）、ダッシュボードを最初から実装する（NF-O1〜NF-O5）
    2 /health がデータベースを確認しない GET /ready（SELECT 1）を ALB のヘルスチェックにする（NF-O10）
    3 デプロイが未実装。レジストリが GHCR と ECR で不一致 ECR に統一。ステージング自動、本番は承認 + ブルー/グリーン（ADR-012）
    4 通知先と体制が未定義 未決（組織の判断）。下記の未決事項
    5 復元の訓練が無い。バックアップ（7 日）と保持削除の関係が未整理 訓練を四半期とリリース前に行う。バックアップの保持を保持方針に明記する
    6 Terraform の状態の保管先が未定義。ネットワーク・ECR・WAF が定義の外 リモートの状態とネットワークのモジュール（ADR-012）
    7 マイグレーションが手動で、履歴が無い node-pg-migrate で履歴管理し、デプロイ時に自動で適用する
    8 資格の失効と鍵のローテーションの手段が無い 資格の失効・再発行と、鍵の版管理を実装する（ADR-009）
    9 運用手順書がすべて未作成 Bolt の進行に合わせて作成する（優先度「高」から）
    10 研修の実施日時を運用側へ伝える仕組みが無い 未決。運営者が日時を連絡する手順と、運用の予定表を決める
    11 削除の運用のアラートが、インフラに定義されていない 監視項目の表のとおり、アラームを定義する（キューは廃止したため、期限超過の経過時間と失敗の件数が中心）
