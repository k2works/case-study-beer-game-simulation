    非機能要件定義 - ビールゲームシミュレーション（Kotlin 版）¶

    概要¶

    本書は、beer-game-kotlin の非機能要件を、測定できる形で定義します。docs/ を正本とします。実装コードはまだ存在せず、実測値はありません。

    beer-game2 の非機能要件 を正本として引き継ぎ、イベントソーシング（ES）+ CQRS と JVM で変わるものだけを見直しました。

    • すべての ID を維持しました。内容が変わる要件には「変更」、新しい要件には「新」を付け、変更の理由を beer-game2 からの変更 に表で示します。
    • 要件定義の NFR-01〜NFR-12 は変えません（要件定義）。
    • 数値目標は、運営者と合意する前提の提案です。Kotlin 版で新しく追加した数値は、実装後の実測で見直す前提の暫定値です（根拠のない値は「実測で決める」と書いています）。

    要件の件数について¶

    beer-game2 の本文は「測定可能な目標 74 件」と書いていますが、表の ID を数えると 69 件です（性能 14、信頼性 14、セキュリティ 19、保守・観測 11、拡張 7、使用性 4）。本書は ID を正として、69 件すべてを引き継ぎます。「74 件」の根拠は、beer-game2 の文書からは確認できませんでした（未決事項）。Kotlin 版で新しく加えた要件は 15 件で、合計 84 件です。

    凡例（beer-game2 からの扱い）¶

    記号 意味
    継続 beer-game2 の要件と同じ。内容を変えない
    変更 ID は同じで、内容（文言、数値、測定方法）を Kotlin 版に合わせて変えた
    新 Kotlin 版で追加した要件

    品質特性の優先順位¶

    beer-game2 と同じです（非機能要件定義ガイド）。

    優先 品質特性 理由
    1 機能の正確性・信頼性（整合性） 週次計算の忠実性と、確定の一回性が、教材の価値そのもの。ES では、イベントが事実であり、再生しても同じ状態になることが正確性の根拠
    2 セキュリティ（機密性・完全性） 役割ごとの情報制約が、学習条件の前提。資格の漏洩は他人の役割の操作につながる
    3 性能効率性・使用性 研修中の操作が滞らないこと。アクセシビリティは要件
    4 保守性・観測性 研修中の障害に気づき、直せること
    5 可用性（SLO） 研修の時間帯に使えること。常時の高可用性までは求めない
    6 拡張性・移植性 想定規模（15 チーム）を満たし、増やせる余地を残す

    SLO の要約（提案）¶

    beer-game2 の値を維持します（「RTO 15 分」には JVM の起動時間と投影の再構築が含まれることを、NF-R4 で明記しました）。

    項目 目標 出典
    月間可用性 99.5%（事前に通知した計画停止は除外） U1 NFR2.1
    研修中の完全停止の検知 1 分以内に通知 U1 NFR2.2
    確定済み週のデータ損失（RPO） 0 U1 NFR2.3
    障害からの復旧（RTO） 15 分 U1 NFR2.4
    入力確定（サーバー側）の p95 1 秒以内 NFR-03、U1 NFR1.1
    週確定から全画面への反映の p95 2 秒以内 NFR-03、U1 NFR1.2
    保持期限後の削除 期限到達の 99% を 24 時間以内に完了 U4 NFR1.2

    ES + CQRS と JVM で変わる点¶

    要件を見直した観点を、先に示します。

    観点 beer-game2（行の更新 + Node.js） Kotlin 版（ES + CQRS + JVM） 関係する要件
    書き込みの性能 行ロック + 版つきの更新 状態の再生（fold(evolve)）+ decide + 追記 + 同期投影。ストリームの長さに応じて再生の時間が増える NF-P3、NF-P13、NF-P14、NF-P15、NF-P19、NF-C8、NF-C9
    並行性 行ロックと WHERE version = $expected ストリームの版の一意制約 + 自動再試行（ロックなし） NF-R7、NF-R13、NF-R14、NF-R17、NF-C2
    投影の遅延 読み取りは SQL（確定と同じトランザクションで行を書く）。振り返りは v1 で再構築 同期投影（追記と同じトランザクション）。投影の遅延は 0。非同期へ移す場合の目標は、条件付きで定める NF-P2、NF-P8、NF-P19、NF-P20
    投影の再構築 なし イベントからいつでも作り直せる。再構築の時間と一致を要件にする NF-P18、NF-R15
    復元 DB のバックアップ 同じ + イベントの再生で状態と投影を再構築できる NF-R4、NF-R8、NF-R15、NF-R16
    起動時間 Node.js（短い） JVM の起動とウォームアップ。コールドスタート直後の遅さを要件にする NF-P16
    メモリ Node.js のヒープ JVM のヒープ、コンテナのメモリ上限との関係、GC NF-P17、NF-O12
    イベント量と保持 監査用の events。投影の元ではない events が状態の正本。1 ストリームの長さ、保存量、スナップショットの導入基準を要件にする NF-C6、NF-C8、NF-C9、NF-O13
    追記専用 なし events は UPDATE / DELETE を禁止（保持削除は連鎖削除で行う） NF-S20
    個人情報 集約の表に表示名 イベントに入れない（周辺ストア） NF-S14、NF-S21
    デプロイとロールバック スキーマの互換 加えて、旧版のアプリが、新しい版のアプリが書いたイベントを読めること（イベントは書き換えない） NF-O11

    性能要件¶

    ID 要件 測定方法 出典 扱い
    NF-P1 15 チーム（各 4 参加者 + 進行役）の同時利用で、意思決定の送信と役割別の状態取得の p95 を 1 秒以下とする。JVM のウォームアップ（NF-P16）の後の定常値で測る 75 並行、15 分の定常負荷。検証エラーと認可エラーは別の系列にする NFR-03、U1 NFR1.1 変更
    NF-P2 週確定から、接続中の全ブラウザが最新の状態を表示するまでの p95 を 2 秒以下（p99 5 秒以下）とする。投影は追記と同じトランザクションで更新されるため、SSE の版の通知を受けて取得した状態の版は、通知の版以上である 同一の時計で測る: 確定した側のブラウザ（確定を送った進行役、または自動確定を起こした保存者）の確定操作の時刻を基準（時刻 0）とし、全ブラウザの描画の時刻との差を取る。合成ブラウザは同一のホスト（同一の時計）で動かし、サーバーの時刻とブラウザの時刻を混ぜない。相関 ID は、どの操作の計測かを結びつけるために使う NFR-03、U1 NFR1.2、U3 NFR1.2、U5 NFR1.11 変更
    NF-P3 週確定のサーバー処理（ストリームの読み込みと再生、decide（simulateWeek を含む）、追記、同期投影、冪等記録）は、p95 1 秒以下、p99 2 秒以下（4 役割、50 週相当、SESSION のストリームが最大の長さ。定義は「ストリームの最大の長さ」）とする 最大の長さの状態での計測 U1 NFR1.3 変更
    NF-P4 SSE が使えない場合、1 秒間隔のポーリングに移り、確定から 4 秒以内に最新の版を表示する SSE を遮断した E2E U1 NFR1.4、U5 NFR1.12 継続
    NF-P5 ブラウザでの入力確定から成功の表示までの p95 を 1 秒以下とする（描画を含む） ブラウザ E2E で 75 ユーザーの負荷 U5 NFR1.10 継続
    NF-P6 停止・再開・代理入力の API は、p95 500 ms 以下、p99 1 秒以下とする API の計測 U2 NFR10.1 継続
    NF-P7 再接続時の状態取得は、75 並行で p95 1 秒以下。SSE の再接続後 5 秒以内に最新の版を表示する 負荷試験 U2 NFR10.2、10.3 継続
    NF-P8 観察と振り返りの取得は、15 ゲーム・90 読み手で、p95 1 秒以下、p99 2 秒以下とする。投影テーブル（week_role_results、week_team_totals）への SQL で返し、イベントからの再構築をしない。観察者の取得は、観察者が読める 3 表（game_overview（参加コードなし）、session_overview、week_team_totals）だけを読む 30 分の負荷試験 U3 NFR1.1 変更
    NF-P9 エクスポートは、受理 1 秒以内、50 週 × 4 役割の CSV と JSON を 30 秒以内（p95）に完了する。出力は問い合わせ時に、全域の純粋関数 buildExport(settings, weekRoleResults) で week_role_results と設定から作る（checksum と schema_version も要求時に算出。保存せず、export_packages 表は無い）。したがって最終週の確定は、出力の作成に依存しない エンドツーエンドの計測 U3 NFR1.3 変更
    NF-P10 保持状態の取得は、p95 1 秒以下とする HTTP の計測 U4 NFR1.1 継続
    NF-P11 期限に達した削除の手続き（RetentionSaga）の 99% を、24 時間以内に完了する completedAt - deleteAfter U4 NFR1.2 継続
    NF-P12 1 リクエストの処理量に上限を設ける（数量 0〜1000、リクエスト 64 KB、履歴は必要な範囲だけ） 境界値のテスト U1 NFR3.9 継続
    NF-P13 共同入力の保存（競合の検出と、追記の競合の自動再試行を含む）は、p95 1 秒以下とする。競合時は、最新値と保存者を、同じ応答で返す API の計測、並行のテスト FR-16、NFR-03 変更
    NF-P14 自動確定は、最後の意思決定の保存から確定の完了まで、p95 1 秒以下とする（decide が DecisionSaved と WeekCommitted を 1 回の追記で返す） API の計測 FR-18、NFR-03 変更

    ストリームの最大の長さ（NF-P3、NF-P15 の前提。M21）¶

    NF-P3 と NF-P15 の「最大の長さ」は、最悪ケースで SESSION のストリームが到達する件数です。共同担当が同じ週に保存を繰り返しても、次の見積もりを超えないよう、保存回数に上限を置きます（NF-C8）。

    項目 値（提案。実測と運営者の合意で見直す）
    想定の長さ（通常） 1000 件前後（50 週 ×（4 役割 × 数回の保存 + 確定））
    保存回数の上限（提案） 1 役割・1 週あたり 9 回（代理入力を含む）。超えた保存は拒否する（コードと文言は未決）
    最大の長さ 50 週 ×（4 役割 × 9 回 + 確定ほか 4）= 2000 件（確定ほかは、確定、停止、再開、設定の変更など、週あたり 4 件の見込み）

    最大の長さは、NF-P15 の計測（1000 件・2000 件）、NF-O13 のアラート（2000 件超）、NF-P3 の最大の状態と同じ値です。上限（9 回）は、運営者の運用（共同担当の人数と保存の使い方）と合意して決めます（未決事項）。

    設計判断¶

    N-1: 投影の遅延は、同期投影により 0 とし、非同期の目標は条件付きにとどめる¶

    案 内容 評価
    A（採用） 同期投影（追記と同じトランザクション）。投影の遅延の要件は持たず、追記の時間（NF-P19）を測る。非同期の遅延目標（NF-P20）は、移行するときにだけ適用する 週確定後の反映（NF-P2）が、通知の版以上であることを保証できる。投影の遅れによる障害の種類が無い
    B 非同期投影（ワーカー）を前提に、遅延 p95 1 秒を最初から要件にする 書き込みと読み取りを分離できる。結果整合の窓と、ワーカーの運用が増える

    トレードオフ: A は、追記のトランザクションが長くなる。NF-P19 の実測で、書き込みを圧迫する場合に B へ移る（データモデルの設計判断 4）。

    N-2: JVM の起動とメモリは、実測してから目標を固める¶

    案 内容 評価
    A（採用） 起動時間とコールドスタート後の遅さを、提案値として置き、ウォーキングスケルトンの実測で見直す。メモリは、使用率の上限と OOM 0 件だけを要件にし、GC の一時停止の目標は実測で決める 根拠のない数値を、確定した要件にしない。性能の目標（NF-P1）の測定条件を明確にできる
    B 一般的な経験則の数値（例: GC 停止 p99 100 ms）を先に確定する 見かけは完結する。本プロジェクトの実測が無く、根拠がない

    N-3: ロールバックのためのイベントの互換を、デプロイの要件にする¶

    イベントは書き換えません。新しい版のアプリが新しい schema_version のイベントを書いた後に、旧版へロールバックすると、旧版がそのイベントを読めず、ストリームが壊れた状態になる危険があります。

    案 内容 評価
    A（採用） 「読めるようにする版」を先にリリースし、全タスクに展開した後のリリースで、新しい schema_version を書き始める（拡張 → 互換 → 縮小）。NF-O11 に明記する ロールバックが安全。リリースが 2 段階になる
    B 新旧を同じリリースにして、ロールバックでは DB の復元も行う リリースは 1 回。復元の時間（RTO）に影響し、確定済みの週が失われうる

    • Kotlin 版で新しく加えた数値（NF-P15〜NF-P19、NF-O13、NF-C8）は、提案であり、実測で見直す。特に、保持中のゲーム数の想定（NF-P18）、GC の一時停止の目標（NF-P17）。
    • 資格の有効期間の既定値（ブラウザセッション、復帰資格、進行役の資格、観察用の招待）。
    • 負荷試験の実施環境（CI の夜間か、ステージングか）。
    • 追記の競合の自動再試行の上限と間隔（データモデルの未決事項）。決まったら NF-R17 に反映する。
    • 保存回数の上限（共同担当が同じ週に保存を繰り返す最悪ケース。NF-C8、「ストリームの最大の長さ」）。提案は 1 役割・1 週あたり 9 回（代理入力を含む）で、最大の長さは 2000 件。上限の有無、値、超えたときの拒否のコードと文言を、運営者と合意して決める。決まったら NF-P3、NF-P15、NF-O13 の最大の長さを見直す。
    • 研修中の再構築（暫定の決定。人の確認が要る）: 運営者を通じた進行役への停止の依頼と、排他のアドバイザリロックで行う（NF-R15）。排他ロックの待ちの上限と、再構築中のコマンドの応答（短い待ちか、503 か）は未決（運用要件の未決事項と共通）。
    • 保持の起点（暫定の決定。人の確認が要る）: 作成時を起点とする（NF-S16）。終了済みのゲームを終了時から数える案（ユーザー代表の提案）は未決。
    • 連鎖削除が、events に DELETE 権限を持たないロールでも動くか（NF-S20）。最初のスライドの Red のテストで確かめる（データモデルの未決事項）。
    • 出力（buildExport）が大きい場合のキャッシュ（NF-P9）。要求時に作るため、50 週 × 4 役割の実測で必要になったときに検討する。
    • beer-game2 の「74 件」の根拠の確認（ID を数えると 69 件）。beer-game2 の NF-O7（80/70）とテスト戦略（85/75）の不一致の訂正は、本書の範囲外（beer-game2 は変更しない）。
    • JVM のコンテナのメモリの割り当てと、ヒープの設定（インフラの設計と合わせて決める）。
