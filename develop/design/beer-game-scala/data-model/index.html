    データモデル設計 - ビールゲームシミュレーション（Scala 版）¶

    概要¶

    本書は、beer-game-scala のデータモデルを定義します。ADR-001 の決定により、スキーマの構造は beer-game-kotlin のデータモデル を正本として引き継ぎます（ES + CQRS、game_roots を根にした連鎖削除、追記専用の events、同期投影、周辺ストア）。本書は、Scala 版で変わる点（マイグレーションの置き方、doobie での型の対応と制約違反の扱い、ローカル開発だけ H2 を使うこと）と、実際の PostgreSQL 18.6 と doobie で確認した事項を定めます。docs/ を設計の正本とします。実装コードはまだ存在しません（アプリの置き場は apps/beer-game-scala を予定）。

    本書の位置づけと確認の範囲¶

    • 確認状況の正本は、技術スタックの確認状況の一覧 です（レビュー指摘 H1）。本書の「検証の結果」は、その一覧の K5・K8〜K11・K18 の根拠で、本文は一覧にリンクします。正本の規則（再レビュー N-H5。AI の案）: 一覧が正です。一覧の根拠は実測の記録（本書の「検証の結果」、テスト戦略 の「確認した事項」）で、一覧を直すときは根拠も直します（一覧と本書の記述が食い違ったら、両方を見直す）。
    • 本書で確認したこと（2026-11-25。リポジトリの外の使い捨てのプロジェクトで、sbt 1.13.1、Scala 3.7.4、doobie 1.0.0-RC12、testcontainers-scala 0.44.1、ローカルの Docker の postgres:18.6 を使用）。結果は「検証の結果」の表にまとめました。
    • events・game_roots を縮小した DDL（主キー、名前つきの一意制約 uq_events_stream_version、外部キー ON DELETE CASCADE、jsonb、identity の seq）を適用できる。
    • doobie の transact は、ConnectionIO が例外なく完了すれば、値が Left でも COMMIT する。FC.rollback を挟むと、その書き込みは残らない（バックエンドアーキテクチャ の SBD2 の前提を実 DB で確認）。
    • 一意制約違反は、attemptSql で PSQLException として取り出せ、SQLSTATE 23505 と制約名（getServerErrorMessage.getConstraint）が得られる。
    • uuid・timestamptz・jsonb の読み書き、アドバイザリロック（pg_advisory_xact_lock(_shared)）、LISTEN/NOTIFY（doobie.postgres.hi.connection の pgListen・pgNotify・pgGetNotifications。同じ接続）が動く。共有と排他のロックが互いを待つこと、lock_timeout、専用の接続の LISTEN、切断後の再購読は未確認（セッションのロック pg_advisory_lock を使う Resource 案は、再レビュー N-H2 で不採用にした）。
    • 引用したもの: Rust 版のデータモデル が、events・game_roots ほかの DDL と DB ロール・GRANT を PostgreSQL 18.6 に適用して実測した結果（追記専用の拒否、部分一意索引、連鎖削除、制約名）を持ちます。DDL は言語に依存しないため、本書はそれを引用します。Scala 版では、その全文を再適用していません（上の縮小した DDL だけ）。ロールと GRANT を doobie の接続から検証することも、未実施です。
    • 確認していないこと: 投影・周辺ストア・保持削除の他の表の DDL（Kotlin 版の ER 図と実ファイル V002〜V006 に基づく設計で、Scala 版では未適用）、Flyway の実行、HikariTransactor と用途別のロール、SET ROLE、読み取り専用の REPEATABLE READ、circe による jsonb の読み書き（doobie-postgres-circe は技術スタックに載せておらず、未確認）。
    • 引き継ぐだけのもの: 投影テーブルの定義（購読するイベント、閲覧できる人）、読み取りの規則、設計判断のまとめは、Kotlin 版を正本とします。
    • H2（ローカル開発のみ）は Scala 版では実測していません。 H2 の版（2.5.252）とライセンスは Maven Central で確認しましたが、PostgreSQL モードの動作範囲、Flyway の H2 への適用、doobie 経由の SQLSTATE は未確認です。「ローカル開発のデータベース」の表は Kotlin 版の実測（H2 2.5.252、2026-11-14）の引用で、B1 の最初に Scala 版で実測して確定します。
    • Kotlin 版の実装の経緯（B1〜B12 の注記）は引き継ぎません。Kotlin 版の未決事項は、本書の未決事項に引き継ぎます。

    beer-game-kotlin からの設計方針の変更¶

    # beer-game-kotlin beer-game-scala 理由
    1 Flyway（共通・PostgreSQL・H2 の 3 つの場所に分ける。B1 で H2 専用は不要と確定） Flyway の連番を 1 系統で持ち、共通と PostgreSQL の 2 つの場所に分ける（H2 は共通だけを適用。H2 専用の場所は、Kotlin 版の実測を引用して作らない見込み。B1 で確定） ローカルは H2、それ以外は PostgreSQL（技術スタック の ST9。ユーザーの決定、2026-11-25）
    2 共通 V001〜V008 と PostgreSQL V101〜V102。番号の付け替えがあった 最初から連番。表を足す番号と、その表の GRANT の番号を分け、GRANT は表より後ろに置く Kotlin 版で、番号の順序の不整合（V101 と V102）が起きた教訓

    論理データモデル¶

    ER 図（イベントストアと周辺ストア）¶

    列と制約は Kotlin 版・Rust 版と同じです。

    投影テーブルと保持の表¶

    投影テーブル（game_overview、game_join_codes、game_settings、lobby_participants、lobby_observer_invitations、lobby_observers、session_overview、role_current_states、current_decisions、week_commits、week_role_results、week_team_totals、retention_policies）と、保持の表（deletion_runs、deletion_attempts、deletion_receipts）の列・制約・購読するイベントは、Kotlin 版の ER 図とテーブル定義 と同じで、Scala 版でも変えません（ER 図は再掲しない）。次の 3 点だけ、設計上の取り決めを再掲します。

    • deletion_runs と deletion_attempts は game_roots へ外部キーを持ちません（ゲームのデータが消えた後も再試行の記録として生き残るため）。完了と同じトランザクションで、この 2 表の行も削除し、game_id を含む行を残しません。deletion_receipts はゲームを特定しない証跡（ダイジェストだけ）で、1 年後に削除します。
    • lobby_participants は、作成時から replaced_at（入れ替えられた時刻。NULL は未入れ替え）を持ちます。
    • 観察者が読める表は、game_overview（参加コードなし）・session_overview・week_team_totals の 3 表だけです。

    イベントストア¶

    ストリーム（(game_id, stream_type)、1 ゲームにつき GAME と SESSION の 2 本）、stream_version（1 から連続）、seq（ゲームをまたぐ追記の順序。業務上の順序は stream_version）、追記と楽観的並行制御、共同入力の競合（ストリームの版とは別）、冪等性（処理の順は「ロック → 認証 → 認可の前提検査 → 冪等記録の照合 → 読み込み → handle → 追記・投影」。認可が照合より先）、イベントのスキーマ（schema_version とアップキャスト）は、Kotlin 版と同じです。

    Scala 版での実現（バックエンドアーキテクチャ）:

    • 追記は EventStore.append: (Long, List[E]) => ConnectionIO[Either[AppFailure, Long]] で、期待する版は MAX(stream_version)（読み込んだイベントの件数ではない）です。複数のストリーム（StartGame）は、同じ ConnectionIO の中で追記します。
    • 一意制約の違反は ConcurrencyConflict（Left）に写し、execute が再試行します。Left を返しても doobie は COMMIT するため、Left の経路は Tx.run が ROLLBACK を明示します（SBD2。確認済み。下の検証の 2。一覧 の K5）。一意制約違反（23505）の後は、同じ ConnectionIO で次の文を発行しません（SAVEPOINT を使う場合を除く。PostgreSQL は 25P02 で中断し、H2 は中断しないため、ローカルでだけ通るコードが書ける。M2。AI の案。25P02 は PostgreSQL の仕様の知識で、doobie では未確認）。
    • events の payload は jsonb で、書き込みは文字列に ::jsonb を付けます（検証の 3）。ドメインのイベントには codec を付けず、EventCodec（circe の DTO）が JSON との相互変換を担います（BD5）。

    制約名と扱いは Kotlin 版の表と同じです（uq_events_stream_version、uq_idempotency_create、pk_idempotency_records は ConcurrencyConflict に写して再試行し、それ以外の一意制約違反は 500 と相関 ID）。

    追記専用の保護¶

    アプリケーションが使う DB ロールには、events の INSERT と SELECT だけを与え、UPDATE と DELETE と TRUNCATE を与えません。保持削除は、別のロールが game_roots を削除し、外部キーの連鎖で events の行が消えます。ローカル開発の H2 版では、この保護（ロール、GRANT、TRUNCATE の拒否）を省略し、単一の接続ユーザーで動かします。ローカルでは追記専用は守られません（ST9。検証は PostgreSQL の統合テストでだけ行う。下の「ローカル開発のデータベース」）。

    ロールは次の 5 つです（NOLOGIN。ログイン用のユーザーはこれらのメンバーとして運用で作る。作り方は Kotlin 版と同じ未決事項）。

    ロール 権限
    beergame_writer events・game_roots は SELECT・INSERT のみ。投影・周辺ストア・冪等記録・projection_checkpoints・participation_attempts は SELECT・INSERT・UPDATE・DELETE（再構築が行を消すため）
    beergame_reader 投影の表（projection_checkpoints・game_join_codes・game_settings を含む）と display_profiles の SELECT のみ。credentials・browser_sessions・idempotency_records は含めない
    beergame_observer game_overview・session_overview・week_team_totals の SELECT のみ（game_join_codes・役割別の表には到達できない）
    beergame_deleter game_roots の SELECT・DELETE、retention_policies の SELECT、deletion_runs・deletion_attempts の SELECT・INSERT・UPDATE・DELETE、deletion_receipts の SELECT・INSERT・DELETE（events ほかの DELETE は持たない）
    所有者 マイグレーションを実行する接続のユーザー。新しいロールは作らない

    用途別の接続プールは、HikariTransactor（Resource。api の書き込み・読み取り・観察者、削除は retention のタスク、所有者は migrate のタスク）です（ADR-009、バックエンドアーキテクチャ）。プールからロールへの結びつけ（メンバーのログインユーザーで接続するか、接続後に SET ROLE するか）は、Scala 版では未確認です。

    ログインユーザーとセッションの設定: ロールは NOLOGIN で、アプリが接続するのはそのメンバーのログインユーザーです。idle_in_transaction_session_timeout や lock_timeout のようなロールごとの設定は、NOLOGIN ロールに設定してもメンバーのログインユーザーに継承されず、効きません（Rust 版が PostgreSQL 18.6 で再現して確認した事項。Scala 版では再確認していない）。idle_in_transaction_session_timeout のような、接続全体に効かせてよい設定は、ログインユーザー自身に設定するか、接続文字列の options・接続後の SET で設定し、統合テストで SHOW が期待値になることを確かめます（運用要件）。

    lock_timeout は、ログインユーザー・接続の options・接続後の SET に置きません（再々レビュー R-H6）。接続全体に設定すると、投影の行のロック待ち（FOR UPDATE など）にも効き、平常時でも 55P03 が出て 503 になります。Kotlin 版（ProjectionLocks.kt の PostgresProjectionLock。読んで確認した）と同じく、ロックを取る間だけ、set_config('lock_timeout', '<ms>ms', true)（true = このトランザクションの間だけ）で設定し、ロックを取った後に '0'（無効）に戻します。この手順の詳細と SQLSTATE の写像は バックエンドアーキテクチャ の「lock_timeout の手順と SQLSTATE の写像」にあります。統合テストで、(1) ロックの待ちの超過が 55P03 になること、(2) ロックを取った後の投影の行のロック待ちは lock_timeout で切れないこと（SHOW lock_timeout が 0）を確かめます。Scala 版では未確認（B1 の最初）。

    display_profiles（表示名。1〜80 文字）、credentials（進行役の資格・復帰資格・観察用の招待のダイジェストと鍵の版、expires_at、revoked_at）、browser_sessions（24 時間。操作の認証はこの表だけを見る。失効は行の削除）、participation_attempts は、Kotlin 版と同じです。追記と同じトランザクションで書き、書く内容は、コマンドが運んだ値とイベントの ID だけです（書き込みの内容は純粋関数 peripheralWrites で導出）。

    役割の入れ替えと永続化¶

    開始後の入れ替えは、credentials.revoked_at の更新、browser_sessions の行の削除、lobby_participants の role を NULL にして replaced_at を書く、の 3 つを、イベントの追記と同じトランザクションで行います。旧担当者の lobby_participants の行、display_profiles の行、過去のイベント、current_decisions の入力者は消しません。

    保持削除¶

    game_roots(game_id) への外部キー（ON DELETE CASCADE）で、DELETE FROM game_roots WHERE game_id = $1 の 1 回で、イベント・投影・周辺ストア・冪等記録が連鎖して消えます（ADR-010）。deletion_runs・deletion_attempts は、同じトランザクションで明示的に削除します。ゲームに属さない participation_attempts は対象外です。

    削除の網羅は、「削除の完了後に、game_id 列を持つすべての表に、そのゲームの行が残らない」ことを、information_schema から表の一覧を取得して検査するテストで確認します（Kotlin 版と同じ）。保持削除の流れ（5 分ごとのスケジューラ、RetentionSaga の handle、削除用ロールでの 1 トランザクション、失敗時の RecordFailure と最大 5 回の指数バックオフ）と、retention_policies・deletion_* のテーブル定義も同じです。

    マイグレーション¶

    • スキーマの変更は番号つきの SQL マイグレーションで行い、適用の履歴を DB に残します。管理ツールは Flyway（技術スタック。版は 13.12.2。PostgreSQL 用のモジュールの名前と、api で自動適用せず migrate のモードで適用する運用は、B1 で確認する）。
    • 変更は、拡張 → 互換 → 縮小の順に分け、ロールバックできる単位にします（NFR-12）。
    • イベントは、マイグレーションで書き換えません。 形の変更は schema_version とアップキャストで吸収します。投影の形の変更は、マイグレーションで表を直し、再構築で埋めます。
    • 表を足す番号と、その表の GRANT の番号を分け、GRANT は表より後ろの番号に置く（Kotlin 版で、ロールの番号が表の番号と前後して適用できなくなった教訓）。既定の権限は与えない。
    • ファイルの置き場は adapter-persistence の中（バックエンドアーキテクチャ のモジュール構成）。具体的なパスと命名は B1 で決める。
    • PostgreSQL 用と H2 用で、共通の部分を最大化し、差分だけを分ける（Flyway のベンダー別の場所。ST9）。PostgreSQL は「共通 + PostgreSQL 専用」、H2（ローカル開発のみ）は「共通」を適用する。共通に置けるか（text 型の主キー、GENERATED ALWAYS AS IDENTITY、timestamp with time zone、bytea）は、Kotlin 版の実測（Flyway 13.12.2 で共通の V001〜V005 が H2 にそのまま適用できた）の引用で、Scala 版では未確認。B1 の最初に実測し、H2 専用の場所が要るかを確定する。
    • PostgreSQL 専用に置くもの: 部分一意索引 uq_idempotency_create、ロールと GRANT（V007）、jsonb の型。H2 は ${json_type} のプレースホルダで json にする（予定）。H2 でしか通らない記述のために共通の DDL を曲げない（乖離への対策 1）。

    H2 版で省略する制約（ローカルでは守られない）¶

    次の制約は、H2 版では守られません。ローカルで動いたことは、これらの制約が正しいことを意味しません。

    1. uq_idempotency_create（同じキーのゲーム作成の同時の重複。アプリ側の再照合だけ）。
    2. events の追記専用（UPDATE・DELETE・TRUNCATE の拒否）。
    3. DB ロールの分離と、観察者のロールが game_join_codes などへ到達できないこと（NF-S18）。アプリのバグによる漏えいを DB が止めない。
    4. 接続プールの分離（観察者用のプールの配線）。
    5. 複数のプロセスにまたがる、再構築との直列化と SSE の通知（ProjectionLock・ChangeNotifier の H2 版は単一のプロセスでだけ有効）。
    6. 削除用のロールの限定（game_roots 以外を直接削除できないこと）。
    7. 分離レベルによる一貫した読み取り（REPEATABLE READ）の保証。

    乖離のリスクと対策¶

    ローカル（H2）で通っても、CI（PostgreSQL）で落ちる乖離が起きえます。対策は次のとおりです。

    1. H2 でしか通らない記述を禁止する。 PostgreSQL の統合テストが正で、H2 のために共通の DDL や SQL を曲げない（通らない文は PostgreSQL 側と H2 側に分ける）。
    2. ポートの契約テストを両実装で実行する。 ProjectionLock・ChangeNotifier の契約テストを、PostgreSQL 版は統合テスト、H2 版は munit のユニットテストで実行する。テスト用のインメモリ実装との関係はバックエンドアーキテクチャで整理する。
    3. 受け入れ（@api）は PostgreSQL で実行する。
    4. 本番・ステージングでの H2 の拒否（起動時の検査。バックエンドアーキテクチャ、インフラ）。
