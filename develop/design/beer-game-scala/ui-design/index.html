    UI 設計 - ビールゲームシミュレーション（Scala 版）¶

    概要¶

    本書は、beer-game-scala の UI 設計を定めます。結論: 利用者が見る画面は、beer-game-kotlin（および beer-game2）と変わりません。 バックエンドが Scala になっても、API の契約（openapi.yaml、エラーの code、problem+json、versions だけの応答、If-Match、SSE の版の通知）が同じなら、画面・遷移・画面イメージ・インタラクション・アクセシビリティは同じです（ADR-001）。docs/ を設計の正本とします。

    範囲（ユーザーの決定、2026-11-25。M19）: 実装として約束するのは U1〜U3 です。U1〜U3 の間は、実際の研修には使いません（検証・事例用）。 U1〜U3 では、振り返り（S08）・保持状態（S09）・結果の出力は API が無く（U4〜U6）、画面から呼ぶと失敗します（下の #16）。

    このため、本書は UI の設計を複製しません（Rust 版の方針と同じ。Rust 版）。画面の正本は次のとおりです。

    内容 正本
    画面一覧、画面遷移、遷移の条件、表示名、OOUI Kotlin 版の UI 設計 の「画面一覧」「画面遷移」「表示名」「オブジェクトと画面」の各節（beer-game2 を引き継ぎ、ES + CQRS の影響を反映済み）
    画面イメージ（S02〜S10 の salt 図）、確認ダイアログ 同「画面イメージ」の節
    インタラクション（保存直後の表示、競合の種類と表示、エラーの code と表示の辞書、結果が不明なとき、画面の状態） 同「インタラクション設計」の各節
    アクセシビリティ（WCAG 2.2 AA） 同「アクセシビリティ」の節

    基準にした版: 本書は、Kotlin 版 ui-design.md の 2026-11-15 の版（フロントマターの generated.at が 2026-11-15T08:13:26Z）を基準にしています（2026-11-25 に確認）。Kotlin 版が更新されたときは、本書の影響の表（#1〜#16）を見直す（見直したら、基準にした版を更新する）。

    基準にした Kotlin 版の既知の食い違い（実際の画面のソースと合わない記述。正本は画面のソースで、本書は画面のソースに従う。L10）: (1) 「停止中の S05」の節（376 行付近）は「自動更新（SSE）は未実装のため、停止・再開は、手動更新・保存・確定のあとの取得で知ります」と書くが、実際の画面（PlayPage.tsx）は 3 秒間隔のポーリングでも知る。(2) 通信の断の表示（667 行付近）の「1 秒ごとに更新しています」は、実際のポーリングは 3 秒間隔。バックエンドが満たす本文の項目には、missingRoles（game.start_condition_not_met・session.incomplete_decisions の 422）も加える（Kotlin 版の辞書にある。ApiError.missingRoles が読む）。

    本書の位置づけと確認の範囲¶

    • 本書で確認したこと: Rust 版の影響の表（14 項目）を、Scala 版の技術（http4s、Cats Effect、doobie、circe）にあてはめました（2026-11-25）。共有の web/ の現状（SSE を使わない、3 秒のポーリング、X-Tab-Id）は、フロントエンド に記録しています。
    • 実際の画面のソースで確認したこと（2026-11-25、読み取り専用）: apps/beer-game-web/src/features/ の play/PlayPage.tsx（PLAY_POLL_MS = 3000）、lobby/LobbyPage.tsx（LOBBY_POLL_MS = 3000）、observer/ObservationPage.tsx（OBSERVATION_POLL_MS = 3000）に setInterval がある。console/ には setInterval も EventSource もない。api/client.ts は、NetworkError、または status >= 500 で type のない ApiError を「結果が不明」として、500 ms 間隔で最大 2 回（maxResends = 2）、同じキーで自動再送する。api/ に Retry-After を読む処理はない。
    • 確認状況の唯一の一覧は 技術スタック です。
    • 確認状況の正本の規則（N-H5。AI の案で承認を得ていない）: 技術スタックの確認状況の一覧が正です。一覧の根拠は実測の記録（データモデル の「検証の結果」と テスト戦略 の「確認した事項」）で、一覧を直すときは根拠も直します。
    • レビュー（2026-11-25）への対応の承認の状況: ユーザーが決めたのは H3、H6、H7、H9（NF-P2 は p95 4 秒）に加え、再レビューへの対応の次の 4 件です。N-H4（検証用の CI は U1 の約束に含め、AWS 環境・デプロイ用ワークフローは後回し）、N-H6（domain の文 97% は目安）、N-H7（止まったゲームでも状態取得の読み取りは返すことを要件にする）、N-H8（U1〜U3 は実際の研修に使わない）。#12・#15・#16 の記述の直し、画面の改善の受入条件の案を含め、これら以外は AI の案で、承認を得ていません。

    画面一覧と遷移¶

    画面の ID と URL は Kotlin 版・Rust 版と同じです（S01 はじめる /、S02 ゲーム作成 /new、S03 参加・復帰 /join、S04 ロビー /games/:id/lobby、S05 プレイ /games/:id/play、S06 進行役のコンソール /games/:id/console、S07 観察 /games/:id/observation、S08 振り返り /games/:id/review、S09 保持状態 /games/:id/retention、S10 観察者の参加 /observe、S11 ヘルプ /help）。遷移図と遷移の条件（検証エラーはすべて集めて一度に示す、資格が有効なら状態に応じた画面へ、権限の無い URL は S03 へ誘導する、など）は、Kotlin 版 の「画面遷移」の節を参照します。Scala 版でも「検証の誤りはすべて集めて 422 で返す」（ValidatedNec。ドメインモデル の SD3）ため、S02 の「誤りを一度に示す」振る舞いは変わりません。ただし、型の誤りも含めて集められるかは、DTO の作り方に依存します（下の #13）。

    Scala 版のバックエンドが UI に与える影響¶

    UI は API の契約にだけ依存します。Scala の実装が契約から外れる可能性のある箇所を、UI の側から列挙します。いずれも、契約テスト（テスト戦略）と E2E で、契約どおりであることを確認します。

    # UI が前提にしていること Scala 版で起きうる逸脱 対策・検証
    1 エラーは必ず problem+json（type、code）。画面の辞書の鍵は code http4s が自動で返す応答（経路なし、メソッド違い、本文の解析の失敗（circe のデコードの失敗）、不正な Content-Type、サイズ超過）は、既定では problem+json にならない可能性がある（既定の応答の形は未確認） すべての失敗を AppFailure の写像（problem+json）に通す。ルートの orNotFound と、本文の解析の失敗を、request.*・validation.invalid_input・app.* の code に写す（ErrorHandling 相当のミドルウェアか、自前の関数。名前は未確認）。契約テスト「実装の code の全体と仕様の一致」と「ルートの網羅」で検証。画面の実際の扱い: JSON でない本文（HTML など）は本文なしの失敗として扱われ、JSON でない 5xx は type なしと判断されて、「結果が不明」として同じキーで最大 2 回自動で再送される（client.ts）。404・405 などの 4xx は再送されない。自動再送の対象は、状態を変える操作（command）だけで、取得（query。ポーリングの GET など）は自動再送しない（client.ts の command の for のループだけに maxResends がある。L1）
    2 バックエンド自身が返す 503 は必ず type を持つ。type のない 503 は「結果が不明」として同じキーで再送する ミドルウェアが type のない 503 を返すと、画面が「結果が不明」と誤認して再送し、新しいキーで再送すべき場面を取り違える 503 は app.retry_exhausted（同時に走るコマンドの上限超過、プール取得のタイムアウト、lock_timeout を含む）・app.not_ready など type つきだけにする。type のない 503 を返さないことを契約テストで確認。ミドルウェアのタイムアウトは、type を付けない 504 にして「結果が不明」と扱わせる（#11）
    3 結果が不明（通信の切断）のとき、同じ冪等キーで再送すると、同じ結果を受け取る クライアントの切断でルートの Fiber が取り消され、コマンドが途中までしか実行されない恐れ（http4s ember が切断時にハンドラを取り消すかは未確認） SBD4: execute を Supervisor で切り離して起動し、ルートは完了を待つ。失敗の経路では ROLLBACK を明示する（SBD2）。切断後の再送が保存済みの応答を返すことを DB の統合テストで検証する。これが成り立てば、UI の「結果が不明」の設計は変わらない。成り立たなければ、設計を見直す（バックエンド の前提と見直しの条件）
    4 コマンドの応答は versions だけ。画面は応答後にスナップショットを取得し、版に追いつくまで待つ。現行の画面は SSE を使わず、自動更新（ポーリング）と、保存・確定の応答の後の取得で更新する（#12） 同期投影の更新漏れで、応答の versions より古いスナップショットが返る 問い合わせの REPEATABLE READ と projection_checkpoints の同時読み取り（バックエンド）。統合テスト「問い合わせの一貫性」
    5 （SSE を使う場合の前提。現行の画面は使わない） SSE は版の通知だけ。再生なし。60 秒より短い間隔の心拍。遅い接続は切断され、再接続後にスナップショットで追いつく http4s の ServerSentEvent と fs2 の Topic の遅い購読者の扱い（発行側が止まりうるか未確認）。心拍・切断・シャットダウンの動作は未確認（SBD9） 画面が SSE を使い始める時点で、SSE の負荷試験と E2E「SSE の切断」で確かめる。現行は未使用のため、Scala 版のバックエンドは SSE を実装しなくても、既存の画面は動く
    6 資格の Cookie は HttpOnly・Secure・SameSite=Strict。タブごとに名前を変える（X-Tab-Id、bg_session_<id>・bg_recovery_<id>。ADR-020） Cookie の発行・読み取りを自前のミドルウェアで書くため、属性や名前の解決の漏れが起きうる HTTP の統合テスト（ヘッダーのテスト）。Kotlin 版の ADR-020 自体は提案中だが、既存のフロントエンドは X-Tab-Id を送っている（フロントエンド）
    7 失敗の文言は、送った資格の種類から選ぶ（無効な資格は、すべて同じ 403 の本文） 認可の失敗の応答の本文が、種類によって違うと、資格の存在・期限が推測される（NF-S12） 認可の否定テスト（無効な資格はすべて同じ応答。AppFailure.Unauthorized と Forbidden の分類を同じ本文に写す）
    8 予期しない失敗（500）では、相関 ID だけを画面に示す IO の失敗（Throwable）をそのまま返すと、内部の情報が漏れる 境界で IO の失敗を AppFailure.Persistence（500）に写し、利用者へは相関 ID だけを返す。LogRecord は資格・表示名の項目を持たない（SBD10）。画面の実際の扱い: 相関 ID は problem+json の本文の correlationId からだけ読む（ヘッダーは読まない。ErrorNotice が「相関 ID: …」と表示）。予期しない失敗は code: app.internal（辞書に文言がある）で返し、本文に correlationId を必ず入れる
    9 Retry-After ヘッダーを app.retry_exhausted（503）と app.rate_limited（429）に付ける 付け忘れ 契約テスト（Retry-After の存在）。画面は Retry-After を読まない（api/ に読む処理がない。app.retry_exhausted は type つきの「未実行」で、利用者の再操作を待つ）。したがって Retry-After はバックエンドが契約として満たす要求で、画面の振る舞いには効かない
    10 数値（versions、意思決定の版）は、JavaScript で正確に扱える範囲の整数 Scala の Long の値が JSON で大きな数になると、精度を失う 版は 1 から数える小さな整数（ストリーム千件前後）で、実際には問題にならない。型の範囲を契約に書くかは未決（Kotlin 版・Rust 版と共通）
    11 「結果が不明」の扱い: 画面は、type つきの応答を「未実行」として扱い、利用者の再操作を新しい冪等キーで送る。type のない 5xx・通信の失敗は「結果が不明」として、同じキーで最大 2 回だけ自動で再送する（client.ts。対象は状態を変える操作（command）だけで、取得は再送しない。L1） ミドルウェアのタイムアウトが type つきの応答を返すと、処理は COMMIT まで進んでいるのに、画面が未実行と判断して新しいキーで再操作する（二重になる。見込み）。また、切り離した元の処理が実行中のまま、同じキーの再送が届く (a) タイムアウトの応答は、type を付けない 504（または切断）にする。 OpenAPI の ErrorCode にタイムアウトの code を足さない。(b) 元の処理が実行中に同じ Idempotency-Key の再送が届いたときは、先の処理の完了を待ち、保存済みの応答（または同じ失敗）を返す（409 app.idempotency_key_reused を返さない）。実現は B1 で確認（バックエンド の SBD4）。契約テストの検証項目に加える。ゲーム作成は If-Match で守られないため、Kotlin 版と共通の課題として未決事項に残す
    12 現行の画面の更新は、SSE でなくポーリング（実際のソースで確認）: S05 プレイ（features/play/PlayPage.tsx の PLAY_POLL_MS）、S04 ロビー（features/lobby/LobbyPage.tsx の LOBBY_POLL_MS。準備中のときだけ）、S07 観察（features/observer/ObservationPage.tsx の OBSERVATION_POLL_MS。終了後は止まる）が、各 3000 ms の間隔で取り直す。S06 進行役のコンソール（features/console/）にはポーリングがない（手動の操作でしか更新されない。コンソールが自動更新されないことは、全実装共通の画面の課題。未決事項 8）。S05 プレイは、ゲームの終了後と、最初の読み込みが済む前は取り直しを止め、保存中・操作中も飛ばす（L1）。取る GET は、S05 が GET /games/{id}/state と GET /sessions/{id}/state、S04 が GET /games/{id}/lobby、S07 が GET /games/{id}/observation。失敗の扱いは画面ごとに違う: S05・S07 は失敗を黙って無視し、表示は古いまま通知が出ない。S04 は 403 だけを表示して取り直しをやめ、その他の失敗は黙って次の回へ回す レート制限をポーリングの GET に適用すると、制限に達した GET が黙って失敗し、S05・S07 の画面が古いままになる（S04 は 403 のときだけ失敗が見える）。3 秒間隔では、反映の遅れは最大で約 3 秒に GET の時間を足したもの (a) レート制限は、ポーリングの GET を対象外にする: 対象外にする経路は、メソッドつきで GET /games/{id}/state・GET /sessions/{id}/state・GET /games/{id}/lobby・GET /games/{id}/observation（M2。/sessions/* と書くと変更系の POST・PUT まで含むと読めるため、メソッドと経路を揃える。参加・復帰・招待の専用の制限は別。NF-S11）。(b) NF-P2 は p95 4 秒に再定義した（ユーザーの決定、2026-11-25）。根拠の「約 2.86 秒」は Rust 版の推定（GET の実測 + 3 秒間隔からの計算。画面を介した実測ではない。Rust 版の NFR の検証結果）で、Kotlin 版の実測ではない。Scala 版の値は実測していない（B1 以降）。(c) SSE で 2 秒を保つ案は、画面を変えない前提（SU2）と両立しないため、全実装共通の画面の改善として別に扱う。(d) ポーリングの失敗が続くときに画面が古いままであること（S05・S07）は、Kotlin 版・Rust 版と共通の未解決の課題（未決事項 8）
    13 入力の誤りを一度に示す: S02（ゲーム作成）は、422 の errors[] を項目ごと（errors[].field）に、入力欄の近くへ示す circe の Decoder は、既定では最初の型の誤りで止まる（見込み。accumulating に当たる機能の有無は未確認）。根拠にしている ValidatedNec と mapN は、DTO から値を作った後の段階であり、DTO の段階で誤りが集まる保証がない。また、画面は errors[].field の名前で照合するため、フィールド名の一致も契約に含まれる。画面の実際の扱い（CreateGamePage.tsx）: 項目ごとに示すのは status === 422 かつ errors が 1 件以上のときだけで、errors が 0 件の 422 は項目に紐づかず、一般の失敗として示される（validation.invalid_input の文言は辞書で null のため、「処理できませんでした。」と相関 ID）。field の名前は、画面ごとに次のとおり（ソースの fieldProps(...) の呼び出しを読んで列挙。L1）: S02 ゲーム作成（CreateGamePage.tsx・CustomConditionsFields.tsx）= finalWeek・demand・retentionDays・conditions.initialInventory.<ROLE>（RETAILER・WHOLESALER・DISTRIBUTOR・FACTORY）・conditions.initialFlow・conditions.orderDelayWeeks・conditions.shipmentDelayWeeks・conditions.productionDelayWeeks・conditions.holdingCostMinor・conditions.backlogCostMinor・conditions.disclosurePolicy。S03 参加・復帰（JoinPage.tsx）= 参加は joinCode・displayName、復帰は gameId・recoveryCode。S10 観察者の参加（ObserverJoinPage.tsx）= invitationCode・displayName。S05 プレイ（PlayPage.tsx）= quantity だけ（422 で errors に quantity があるとき、数量の欄に「0〜1000 の整数で入力してください。」を示す）。どの field も、要約（「入力に誤りがあります」）には誤りがすべて出る。入力欄に結び付くのは、上の名前と一致した誤りだけで、一致しない名前の誤りは、要約にだけ出て、どの欄にも結び付かない（要約への表示は ValidationSummary）。ドット区切りの入れ子の形（conditions.*）が契約に含まれる DTO を、型の誤りも含めてすべて集められる形（誤りを集める Decoder、または生の JSON から値を取り出して ValidatedNec で検証する）にするか、型の誤りは最初の 1 件で 422 とする。どちらにするかは B1 で決め、契約テストに「複数の誤りが一度に返る」「フィールド名が仕様と一致する」を入れる

    インタラクション設計¶

    Kotlin 版の次の節を、そのまま引き継ぎます（内容は複製しません）。

    • 共通のルール（明示的なボタンで操作を始める、フォーカスと入力だけで状態を変えない）
    • 保存直後の表示と投影の遅延（応答は versions だけ。スナップショットを取得して追いついてから表示。同期投影のため遅延は通常ない。反映待ちの共通部品）
    • 競合の種類と表示（session.decision_conflict、session.week_advanced、session.decisions_changed、app.retry_exhausted）
    • エラーの code と表示の辞書（正本。鍵は code。Scala 版でも code の一覧を変えない。DomainError の code と AppFailure の写像の全体が OpenAPI の一覧と一致することを契約テストで確認する。辞書が全 code を網羅することは、既存のフロントエンドの型検査（Record<ErrorCode, …>）で守られる）
    • 結果が不明なとき（type のない 5xx・タイムアウト・切断は「結果が不明」として同じキーで再送。type つきの 503 は利用者の再操作で新しいキー）
    • 主な操作の流れ、エラーと状態のフィードバック、画面の状態

  かつ 「操作を繰り返さず、相関 ID を運営者に伝えてください。」と相関 ID を示す
  かつ 相関 ID は、まず書き写せるよう、手動更新を押しても消えない

    (b) 相関 ID は、操作した人のタブにだけ出る（他の参加者・進行役の画面には出ない）。(c) 手動更新の成功で消える（PlayPage.tsx の refresh の先頭 90 行の setFailure(null) は現状、押した時点で消える。(a) の最後の「消えない」は現状の挙動と逆で、画面の変更が要る）。(d) S06 コンソールが自動更新（または手動更新のボタン）を持つ（コンソールが自動更新されないことは、全実装共通の画面の課題）。画面を変えない前提（SU2）の間は、この条件は満たせず、依頼文言（運用要件 パターン 18。「まず書き写す、そのあと手動更新」）で補う。 8a. SSE で 2 秒を保つ画面の改善（#12）: 全実装共通の別の課題として扱う。Scala 版だけでは決めない。 8b. ゲーム作成の二重送信（#11。L7）: ゲーム作成は If-Match で守られないため、結果が不明のとき、同じキーの自動再送と、利用者の再操作（新しいキー）で、ゲームが 2 つできうる。Kotlin 版と共通の課題として、未決のまま残す。 8c. 進行役向けの 1 枚の案内（L11。beer-game2 から一貫して欠けている）: 「研修中にシステムが止まったら・人が入れ替わったら」を 1 枚にまとめる案。内容の案は 運用要件 の未決事項 3b。ポーリング失敗の無言（未決事項 8）と合わせてストーリー化する（承認を得ていない案）。1 枚に入れる項目（M11・M8。案）: (i) 準備中に、予備の参加者を参加させておく（開始後の参加は受け付けない）、(ii) 予備がいない場合は、残りを進行役の代理入力で続けられる、(iii) 研修 1 回が 90〜120 分（運営者の想定。出典は要確認）で、長く止まると場が冷えるので止まったら早めに紙に切り替えてよい、(iv) 止まったときは、同じ操作が 2 回続けて失敗したら操作を繰り返さず、まず相関 ID を書き写し（そのあと手動更新）、運営者に伝える、(v) 参加者に伝える、控える数字（S05 の在庫・受注残・入荷・受注と、保存済みの現在の入力と未保存の draft。進行役は S06 を再読み込みして結果表を撮る）。「入荷予定」と「上流へ送って未着の発注」は、画面に項目が無く、結果表の出荷・発注から復元する（運用要件 のパターン 18）。画面に「入荷予定」を出すかは、全実装共通の画面の課題。 9. Kotlin 版の未決事項の引き継ぎ: 手動のアクセシビリティの確認の担当者と時期、保持の表示（暫定。M5）、自動確定の本人へのフィードバックの文言、参加者のロビーの扱い、ヘルプの教材の本文の人による確認。いずれも Kotlin 版の未決事項 に追従する。
