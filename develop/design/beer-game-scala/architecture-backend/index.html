    バックエンドアーキテクチャ - ビールゲームシミュレーション（Scala 版）¶

    概要¶

    本書は、beer-game-scala のバックエンドのアーキテクチャを定義します。ADR-001 の決定により、機能・API の振る舞いは beer-game2、設計の構造は beer-game-kotlin のバックエンドアーキテクチャ、実装規約は 関数型プログラミングガイド（Scala 編）（以下「ガイド」）を正本として引き継ぎます。本書は、その構造を Scala 3（Cats Effect + http4s + doobie） で実現する方法と、Scala で変わる点だけを定めます。docs/ を設計の正本とします。実装コードはまだ存在しません（アプリの置き場は apps/beer-game-scala を予定）。

    本書の位置づけと確認の範囲¶

    • 確認状況の正本は、技術スタックの確認状況の一覧 です（レビュー指摘 H1）。本書の本文は、その一覧へリンクします。正本の規則（再レビュー N-H5。AI の案）: 一覧が正です。一覧の根拠は実測の記録（データモデル の「検証の結果」、テスト戦略 の「確認した事項」）で、一覧を直すときは根拠も直します。本文が一覧と食い違ったら、本文を直します。
    • 確認したこと: AppFailure、EventStore、旧形の Ports（1 本のストリームの store と 1 つの Transactor。新しい形は下の「依存を表す」で、型検査していない）、App（Kleisli）、旧案の Tx.rollbackOnLeft、Execute.step / Execute.execute の型は、-Werror -Wunused:all -Wvalue-discard -Wnonunit-statement と WartRemover 3.6.3 を有効にしてコンパイルできる（K2。2026-11-25）。実 DB で、Left を返しても doobie が COMMIT すること、FC.rollback を挟むと書き込みが残らないことを確認した（K5）。旧案の Tx.rollbackOnLeft が、スタブの Connection で「成功は commit だけ、Left は rollback が呼ばれる」ことも確認した（K6）。
    • 本書の「Tx と execute」「ProjectionLock と ChangeNotifier」の新しい形（Tx.run、ConnectionIO の変換としてのロック、通知の出所、.transact( の入口の一覧）は、2026-11-25 のレビュー対応と再レビュー対応（N-H2・N-H3・M4）で書き直した AI の案で、承認を得ていない。型検査も実行もしていない（旧案がコンパイルできたことは、新案の根拠にならない）。前回の Resource 版のロックは、再レビュー N-H2 で不採用にした（下の「ProjectionLock の接続の出所」）。
    • ユーザーの決定（2026-11-25）と AI の案の区別: ユーザーの決定は、H3（Ignored は止める）・H6（行率を算出する案 C）・H7（U1〜U3 を約束）・H9（NF-P2 は p95 4 秒）と、再レビューの N-H4（検証用の CI は U1 に含める）・N-H6（domain の文 97% は目安）・N-H7（止まったゲームでも状態取得は返す）・N-H8（U1〜U3 の間は実際の研修に使わない）の 8 件（ほかにローカル DB の H2 の 1 件）。N-H1・N-H2・N-H3・N-H5 の直し方など、これら以外は AI の案で、承認を得ていない。
    • 再々レビュー（2026-11-25）の D1〜D5 は、AI が推奨案で決め、ユーザーが承認した（2026-11-25）。ユーザーが承認した決定は 14 件（本人が選んだ 8 件 + ローカル DB の H2 + D1〜D5）: 本書に関わるのは D4（H2 版の ProjectionLock は Kotlin 版と同じ構造にする。R-H5）と D3（失効済みの旧担当者への CredentialRevoked。ドメインモデル）。D1・D2・D5 は ADR・テスト戦略・人の承認の場の側にある（D1 の案 X・Y は未決。D5 は手順の承認で、例外の承認と project.md への記録は未実施）。「文書の検証（verified）」と「設計判断の承認」は別の記録で、文書が stable でも、承認していない判断は未承認のままである。R-H5・R-H6・R-H7・M12・M13・R-H10 の直し方は AI の案で、承認を得ていない。書き直したコード（ProjectionLock・Tx.run・execute の SQLSTATE の写像）は、型検査も実行もしていない。
    • 確認していないこと: ConcurrencyConflict の再試行の実行、キャンセル時の ROLLBACK、Supervisor による切り離し、ember の切断時の挙動（K7）、doobie.postgres.sqlstate の定数と制約名以外の写像（K8）、トランザクションのアドバイザリロックの共有と排他の待ち合い（K10）、専用の接続の LISTEN と再購読（K11）、http4s（0.23.39）のルート・ミドルウェア・SSE（K20）、HikariTransactor（K19）、circe による EventCodec（K9）、各ミドルウェアの名前は、未確認の設計のスケッチです。B1 で確かめます。
    • 引き継ぐだけのもの: 冪等性の表、競合の再試行の一意制約の表、問い合わせ側の開示、API のエンドポイントと認可の表、エラーの写像の表、SSE の仕様（版の通知だけ、再生なし）、保持削除の手順、セキュリティの表は、Kotlin 版の該当節を正本とします。API の契約（openapi.yaml、code、problem+json）は変えません。

    ProjectionLock の接続の出所と見積もり（再レビュー N-H2。AI の案）¶

    項目 内容
    接続の出所 PostgreSQL 版のロックは、コマンドのトランザクションと同じ 1 本の接続で取る（Tx.run が開いた書き込みプールの接続。先頭の pg_advisory_xact_lock_shared）。ロックのための専用の接続を取らない。再構築（排他）も、rebuild-projections モードの 1 ゲーム 1 トランザクションの接続で取る（pg_advisory_xact_lock）
    接続数の見積もり 1 タスクあたりの接続は、3 プール（書き込み・読み取り・観察者）+ LISTEN の専用の接続 1 本のままで、ロックのために増えない。見積もりの式は インフラストラクチャ の式（タスク数 ×（3 プール + 通知 1 本））をそのまま使う
    解放 pg_advisory_xact_lock(_shared) は、トランザクションの終わり（COMMIT・ROLLBACK）で自動的に外れる。解放の呼び出しを書かないので、解放の失敗と、外れないままプールに戻る接続の問題が構造上ない。接続が切れても、サーバーがトランザクションを中止してロックが外れる
    確認状況 ConnectionIO として pg_advisory_xact_lock(42) と pg_advisory_xact_lock_shared を実行できることは確認済み（K10。2026-11-25）。未確認: 共有と排他が互いを待つこと、lock_timeout での 55P03、再構築（排他）の実測、COMMIT・ROLLBACK で外れること、排他を待つ要求の後ろに共有の要求が並ぶこと（飢餓を防ぐ挙動。下の「待ちとプール」）。B1 の最初に確かめる
    再試行との関係 初稿は「ロックを再試行のあいだも持つ」としていたが、トランザクションのロックは ROLLBACK で外れるため、試行ごとに取り直す（execute の loop の中で withShared を包む）。再試行のあいだに再構築が入りうるが、再試行は読み直しから始めるので問題ない
    待ちとプール 再構築（排他）の間、コマンドは自分のトランザクションの接続を持ったままロックを待つ。待つコマンドの数が書き込みプールの大きさに達すると、ほかの要求はプール取得のタイムアウト（RetryExhausted・503）になる。待ちは lock_timeout（55P03 → RetryExhausted）で上限があり、同時に走るコマンドの数の上限（Semaphore）が先に効く。値は実測で決める（未決事項 6）。研修中に再構築しない運用（運用要件）が前提。PostgreSQL のロックの待ち行列（L8。未実測）: 排他（再構築）を待つ要求がいると、後から来た共有（コマンド）もその後ろで待つ（飢餓を防ぐ挙動と理解しているが、本書では実測していない）。再構築の間はそのゲームの新しいコマンドが止まり、lock_timeout を超えると 503 になる。lock_timeout の値は、NF-P18（1 ゲームの再構築が p95 1 秒以下）と比べて決める（再構築が 1 秒以内に終われば、待つコマンドは lock_timeout に届かない見込み。上限は NF-P18 の目標より長く、利用者が待てる長さより短くする。実測の後に決める）
    H2 版（D4。再々レビュー R-H5） Kotlin 版の LocalProjectionLock（ProjectionLocks.kt）と同じ構造にする。(1) StampedLock 系の、Fiber から安全な部品（ゲームごと。取得したスレッドと解放するスレッドが違ってよい。Fiber は別のスレッドで再開しうる）。(2) 待ちの上限（tryReadLock・tryWriteLock 相当。超えたら Left(RetryExhausted)）。(3) トランザクション終了後の後始末の登録（AfterEnd。Tx.run が COMMIT・ROLLBACK の後に guaranteeCase で実行する。Kotlin 版の jdbcTx.afterEnd に当たる）。不適な案: ReentrantReadWriteLock は、ロックを持つスレッドが所有者で、別のスレッドからの解放を IllegalMonitorStateException で拒否する（JDK の仕様の知識で、本書では実行していない）。cats-effect の Fiber は別のスレッドで再開しうるため、取得と解放が別のスレッドになりうる。これで「COMMIT の後まで直列化する」条項を両実装で確かめられる（前回の「bracket の解放は COMMIT の前で、弱点を許容する」は、この形で弱点が解消するため取り下げた）。実測は未実施で、B1 の最初に確かめる（下の「H2 版」）

    lock_timeout の手順と SQLSTATE の写像（再々レビュー R-H6。AI の案、型検査・実行していない）¶

    前提（Kotlin 版の PostgresProjectionLock を読んで確認した）: Kotlin 版は、ロックを取る間だけ set_config('lock_timeout', '<ms>ms', true)（true = このトランザクションの間だけ）で上限を設定し、ロックを取った後に '0'（無効）に戻す。投影の行のロック待ち（FOR UPDATE など）に lock_timeout を効かせないためである。接続全体（ログインユーザー・接続の options・接続後の SET）に lock_timeout を設定すると、投影の行のロック待ちにも効き、平常時でも 55P03 → 503 が出る。Scala 版も同じ手順にする。接続・ロールの設定に lock_timeout は置かない（データモデル の「ログインユーザーとセッションの設定」）。

  private def setLockTimeout(value: String): ConnectionIO[Unit] =
    sql"select set_config('lock_timeout', $value, true)".query[String].unique.void      // true = このトランザクションの間だけ

  /** key は UUID の上位 64 ビット（Kotlin 版と同じ。衝突は不要な待ちを生むだけで、整合性は損なわない） */
  private def acquire(take: ConnectionIO[Unit]): ConnectionIO[Either[AppFailure, Unit]] =
    (setLockTimeout(s"${timeoutMillis}ms") *> take *> setLockTimeout("0"))
      .attemptSomeSqlState { case SqlState("55P03") => AppFailure.RetryExhausted }   // 55P03 は例外で届く。Left にして即返す

final class LocalProjectionLock(timeoutMillis: Long, afterEnd: AfterEnd) extends ProjectionLock:

    コマンド処理の流れ¶

    流れと順序は Kotlin 版と同じです。処理の順は固定で、ロック（共有）→ 認証（操作者・資格の有効性）→ 認可の前提検査 → 冪等記録の照合 → 読み込み → handle → 追記・投影 → 周辺ストア → 冪等記録の保存 → 通知の収集（enqueue） → COMMIT → 通知の配信（deliver）です（M13。再々レビューで、下のコード（program が冪等記録の保存まで、execute が enqueue）と同じ順に直した。前の文は通知を冪等記録の保存の前に書いていた。通知は COMMIT されたときだけ届くため、同じトランザクションの中での前後は結果に影響しない見込み。Kotlin 版の順序との一致は、本書では確認していない）。ロックは ConnectionIO の変換として program を包み、同じトランザクションの先頭で取る（execute が program を withShared で包む。別のトランザクションや Tx.run の外ではない）。認可を冪等記録の照合より先に置くため、入れ替えで失効した旧担当者が過去のキーを再送しても 403 になります（ADR-004）。

    Scala 版（H4・H5・N-H2 の案）での違い: ロックは ConnectionIO の変換（ProjectionLock.withShared。PostgreSQL 版は先頭の pg_advisory_xact_lock_shared）で、トランザクションの先頭で取ります（前回の「transact の外の Resource」は不採用。上の「ProjectionLock の接続の出所」）。認証以降の全体（認証 → 認可の前提検査 → 冪等記録の照合 → 読み込み → handle → 追記・投影 → 周辺ストア → 冪等記録の保存）を 1 つの ConnectionIO（program）として組み、execute が、ロックの変換と通知の enqueue で包んで、1 回の Tx.run で実行します。通知は、execute だけが、program が Right(committed) を返したときに、同じトランザクションの中で集め（notifier.enqueue(committed.notices)。PostgreSQL 版は pg_notify。COMMIT されたときだけ届く）、COMMIT された後に IO で配信します（deliver）。ロールバックした試行の通知は、集められず、配信されません（M4）。

    execute は、ストリームの種類に依存しない汎用の関数です。ストリームごとの初期状態・遷移・handle を引数で受け取り、ルールを持ちません（Kotlin 版と同じ）。Tx.run と execute の形は 2026-11-25 のレビュー対応で書き直した AI の案（H4・H5）で、型検査していません。step と AppFailure・EventStore の型は、コンパイルを確認した旧案の形のままです（K2）。

    Kleisli: ports =>

        ports.lock.withShared(gameId)(program).flatMap:
          case Right(committed) => ports.notifier.enqueue(committed.notices).as(Right(committed))   // PostgreSQL 版: pg_notify。H2 版: 何もしない
          case left             => FC.pure(left)

            case other                                                           => IO.raiseError(other)   // 想定外。ルートが Persistence（500・相関 ID）に写す

            // COMMIT の後。配信の失敗は成功の応答を変えないが、捨てずにログに記録する（L4。コミット済みのため応答は成功）
            ports.notifier
              .deliver(committed.notices)
              .handleErrorWith(e => ports.logSink.write(deliverFailedLog(gameId, e)).handleError(_ => ()))
              .as(Right(committed.value))
          case Left(AppFailure.ConcurrencyConflict) if attempt < ports.maxAttempts => loop(attempt + 1)
          case Left(AppFailure.ConcurrencyConflict)                                 => IO.pure(Left(AppFailure.RetryExhausted))
          case Left(other)                                                          => IO.pure(Left(other))
      loop(1)

    Kotlin 版の EventStore.transaction は、ブロックが Left を返したら ROLLBACK します。doobie の Transactor は、ConnectionIO が例外なく完了すれば、その値が Left でも COMMIT します（IO の失敗でなく、Either の Left を返すため。Scala 版の設計は「業務の失敗は Either、IO の失敗は想定外に限る」。ガイド ADR-050）。そのため、Left を返す経路で ROLLBACK を明示する必要があります。

    インメモリ実装の契約（再レビュー M6。AI の案、承認を得ていない）¶

    インメモリ実装は、ConnectionIO の中で可変の状態（Ref や可変の Map）を書く。FC.rollback は JDBC の接続のトランザクションを取り消すだけで、可変の状態は取り消さないため、「Left で書き込みが残らない」を、インメモリ実装のポートの単体では満たせない。次の 2 つで扱う。

    1. 契約の条項を 2 つに分ける。(T) トランザクションの意味に依存する条項（Left で書き込みが残らない、23505 の後の規則、COMMIT の後にだけ通知が届く、ロックが COMMIT の後まで続く（COMMIT の後まで直列化する）。最後の条項は PostgreSQL 版と H2 版の両実装の共通条項にした。R-H5・D4）と、(N) 依存しない条項（追記の版の一意性の検査、読み出しの順序、MAX(stream_version) など）。(N) は 3 つの実装（PostgreSQL 版、H2 版、インメモリ）で同じ内容を実行する。(T) は、ポート単体でなく execute と Tx.run を通して確かめる（M8）。この (T)・(N) の分類名を、テスト戦略 の契約テストの分類とスナップショットの記述が同じ分け方に揃える（M13。別の担当）。（案）(T) のうち、インメモリ実装が満たすのは、試行単位のバッファで再現できるもの（Left で残らない）だけで、ロックと通知の条項は PostgreSQL 版と H2 版で確かめる。
    2. インメモリ実装は、試行単位でバッファする: インメモリの Tx の実装は、run の前に状態のスナップショットを取り、Left と失敗のときに復元し、Right のときだけ確定する。これで (T) の「Left で残らない」を、インメモリ実装も Tx を通して満たす。限界: スナップショットの復元は、同時に複数の書き込みが走ると壊れる（単一の書き込みを前提とする）。同時実行の競合（ConcurrencyConflict）の検証は、PostgreSQL の統合テストで行い、インメモリ実装には求めない。可変の状態を使うのはテスト用のソースだけ（WartRemover の対象外。K17）。

    どちらも未実装・未検証で、B1 の最初のスライドで、インメモリ実装を書いて (T) の条項が通ることを確かめる。

    キャンセル安全性（設計判断 SBD4）¶

    Kotlin 版は、COMMIT と ROLLBACK を NonCancellable で行い、CancellationException を再送出します（ADR-005）。Cats Effect では、キャンセルは Fiber の取消です。クライアントが切断すると、サーバーが処理中の Fiber を取り消しうる（http4s ember が切断時にハンドラを取り消すかは未確認）ため、次の方針にします。

    リスクの置き場所: 「部分更新が残る」ことは、PostgreSQL のトランザクションの原子性が防ぎます（COMMIT の前に接続が切れれば、サーバーが中止する）。本当のリスクは、(1) ロックと接続が解放されるまでの遅れ（pg_advisory_xact_lock_shared・行ロックを握ったまま接続が残る）、(2) 切り離した処理の寿命（追跡、シャットダウン）、(3) COMMIT の結果が呼び出し側に分からなくなること（タイムアウト・切断）の 3 つです。Rust 版のレビューで整理した見方を引き継ぎます。

    項目 設計
    ROLLBACK 失敗の経路では ROLLBACK を明示する（SBD2 の Tx.run。IO の失敗・取消のときは、doobie の Transactor の後始末に任せる。doobie がキャンセル時に ROLLBACK して接続を返すかは、公式の文書で確認していない（K7）。B1 で挙動を確かめる）
    COMMIT の途中でのキャンセル execute を Supervisor[IO]（cats-effect の標準）で切り離した Fiber として起動し、ルートはその完了（join）を待つ。クライアントが切断してルートの Fiber が取り消されても、コマンドの処理は最後まで走る（COMMIT が中途半端にならない）。Supervisor は Resource で作り、アプリの終了時に追跡している Fiber の完了を待つ（Supervisor(await = true) の指定は要確認）
    タイムアウトと「結果が不明」 ミドルウェアのタイムアウトが応答した後も、切り離した Fiber は COMMIT まで進みうる。タイムアウトの応答は type を付けない 504 とし、画面は「結果が不明」として同じ Idempotency-Key で再送する（UI 設計 の影響表）。元の処理が実行中に同じキーの再送が届いたときは、先の処理の完了を待って、保存済みの応答（または同じ失敗）を返す（実現は B1 で確認。待ちの上限を超えたら app.retry_exhausted）
    プール取得のタイムアウト プールから接続を取れなかった場合は、コマンドは未実行が確実なので、AppFailure.RetryExhausted（503・type つき・Retry-After）に写す。begin の失敗は、Persistence（500）とは区別する
    Fiber の失敗（想定外の例外） IO の失敗（Throwable）を AppFailure.Persistence に写し、500 と相関 ID にする。業務の失敗は Either で返るため、IO の失敗は想定外に限る
    同時に走るコマンドの数 同時に走るコマンドの数に上限を置く（Semaphore など。超えたら RetryExhausted）。上限の値は実測で決める
    シャットダウン SIGTERM で新しい要求の受付を止め、SSE の接続に終了を知らせて閉じ（SSE は自然には閉じない）、Supervisor が追跡している Fiber の完了を待つ（待ちの上限は stopTimeout より短く）。ember のシャットダウンの待ち方は未確認
    案 内容 評価
    A（採用の提案） execute を Supervisor で切り離して起動し、ルートは完了を待つ。失敗の経路は ROLLBACK を明示 切断で処理が途中で止まらない。追跡の仕組みが cats-effect の標準にあり、新規の依存が要らない（Rust 版の TaskTracker に当たる）。ROLLBACK を後始末に頼らない
    B ハンドラの Fiber の中で直接実行する 単純。ただし、クライアントの切断で COMMIT の直前に取り消されうる。IO.uncancelable で包む案は、プール取得の待ちまで取り消せなくなる
    C IO.uncancelable で execute 全体を包み、Supervisor を使わない 切断で止まらない。待ちのキャンセル（シャットダウン）ができず、Fiber を追跡できない

    Scala 版の実現として、用途別に HikariTransactor（Resource）を持ちます（api は書き込み・読み取り・観察者の 3 つと LISTEN の専用接続。削除は retention、所有者は migrate のタスクが持つ。インフラストラクチャ）。プールの配線テスト（SELECT current_user の検査）は書き直します（ADR-009）。

    投影の更新と再構築¶

    投影は、Projection（純粋。Event => List[RowChange]）と、SQL への書き込み（境界）に分けます（ドメインモデル）。再構築は rebuild-projections モードで、1 ゲームを 1 トランザクションで、排他のロック（ProjectionLock.withExclusive）を先頭で取って行います。コマンドは共有のロック（ProjectionLock.withShared）を取るため、再構築と同時には走りません。ロックは ConnectionIO の変換（再レビュー N-H2 の案。上の「ProjectionLock の接続の出所」）で、PostgreSQL 版は、トランザクションの先頭で pg_advisory_xact_lock(_shared) を実行します（COMMIT・ROLLBACK で自動的に外れる。接続は増えない）。ConnectionIO として pg_advisory_xact_lock(_shared) を実行できることは確認済み（K10。2026-11-25）ですが、共有と排他の待ち合い、再構築（排他）の実測、lock_timeout の効き方は未確認で、B1 の最初に確かめます。前回の「transact の外の Resource のセッションのロック」は、接続が 2 本要ることと、解放の失敗が接続に残ることから採りません。

    再生に関する 3 つの性質（永続化往復の同値性、計算と事実の一致、投影の整合）と、検証の場は、ドメインモデル と Kotlin 版のとおりです。

    API 設計方針¶

    REST + JSON（/api/v1）、リアルタイム通知は SSE、エラーは application/problem+json、変更系は Idempotency-Key を必須とし、If-Match は SaveDecision（意思決定の版）だけに付けます。エンドポイントの一覧、コマンドの流れるストリーム、認可、コマンドの応答（versions だけ。資格を渡す操作の例外）は、Kotlin 版の表と同じで、OpenAPI の契約を共有します。POST /games/:id/start は 2 ストリームにまたがる資源として維持します。

    ルートは薄く、関数として呼べる形にする（設計判断 SBD6）¶

    ルートは HttpRoutes[IO] で、本体は「検証 → execute → 写像」の 3 つだけを呼びます（Kotlin 版の BD4 と同じ）。ガイド §7.1 のとおり、ルートは Request を受け取って Response を返す関数なので、サーバーを起こさずに routes.orNotFound.run(Request[IO](...)) で呼べます。API の契約テストと受け入れテストは、この形で書きます（テスト戦略）。

    入力の検証とエラーの写像¶

    エラーの code と HTTP の写像の契約: Kotlin 版は、DomainError の code と分類から HTTP の code への写像の正本の一部を実装ファイル（ProblemMapping.kt）に持ちます。Rust 版と同じく、Scala 版は次をこの文書と openapi.yaml の両方で固定します（実装ファイルを正本にしない）。(1) 分類が Forbidden のドメインの誤り（session.forbidden・game.forbidden）は、HTTP では app.unauthorized（403）と同じ本文に写る（資格の失敗と区別しない。NF-S12）。例外は参加コードの失敗の game.invitation_invalid（同じ本文）。(2) 409 の problem+json は、拡張メンバー（requestedWeek・currentWeek・role・latest・week・current）を操作ごとに持つ。どの操作がどのメンバーを返すかは、openapi.yaml の ConflictProblem を正本とする。(3) HTTP の層の失敗（request.*・app.rate_limited・app.not_ready）と、validation.invalid_input は、DomainError でなく AppFailure と http4s の拒否の写像が持つ。契約テストが、code の全体と openapi.yaml の一覧を突き合わせる。

    • ルートは、DTO を、スマートコンストラクタで Command に変換します。誤りはすべて集め（ValidatedNec。ドメインモデル の SD3）、422 で項目ごとの誤りを返します。本文の構文エラーは 400。
    • ドメインのエラーは、分類で HTTP の状態へ写します。写像は 1 か所（adapter-http）の関数で、AppFailure を match（_ なし）で網羅します（ガイド §3.3 の statusOf。エラーの種類を足すと、写像を忘れた箇所が -Werror でビルドの失敗になる。SBD8）。写像の表（Forbidden → 403、NotFound → 404、InvalidState → 409、Conflict → 409、RuleViolation → 422、Unauthorized → 403、RetryExhausted → 503 と Retry-After、Persistence → 500）、code の一覧、HTTP の層の失敗（request.*、app.rate_limited、app.not_ready）は Kotlin 版と同じです。
    • バックエンド自身が返す 503 は、必ず type（problem+json）を持ちます（画面が「もう一度お試しください」と「結果が不明」を区別するため）。

    認証とミドルウェア¶

    Kotlin 版は、認証を execute の中（トランザクションの中）で行います。Scala 版も同じです。ミドルウェアで認証しません（再試行のたびに、同じトランザクションの中で評価し直す必要があるため）。ミドルウェアは、リクエスト ID、Origin 検査、ヘッダー（CSP、HSTS、nosniff、Referrer-Policy）、本文のサイズ上限、レート制限、タイムアウトを担当します。使うミドルウェアの名前は未確認です（技術スタック の対応表）。ルートは、生の資格（Cookie の値）を取り出し、RequestMeta としてコマンドと一緒に execute へ渡します。

    自動確定¶

    Kotlin 版と同じです。自動確定のための処理はアプリケーション層になく、Session.handle が複数のイベントを返します。一時停止中の扱い、同時に起きること（最後の保存と手動の確定、共同担当の同時の保存、確定と一時停止）の結果の表も同じです。

    通知（SSE）¶

    仕様は Kotlin 版を引き継ぎます。版の通知だけを送り（state-version。ストリームの種別と版）、内容は運びません。再生（Last-Event-ID）は行わず、接続の開始と再接続のたびに、クライアントがスナップショットを取得します。発信は、追記と同じトランザクションで、execute が program の Right(committed) のときに ChangeNotifier.enqueue(committed.notices) を呼んで通知を集め（PostgreSQL 版は中で pg_notify。コミットされたときだけ届く）、Tx.run の後に ChangeNotifier.deliver で配信します（H5・M4 の案。通知の出所は execute の 1 つ。H2 版は enqueue が何もせず、deliver がプロセス内のイベントへ配る）。

    項目 Scala 版の設計（スケッチ。確認状況は 一覧 の K11）
    受信 PostgreSQL の LISTEN 専用の接続を、1 つ、接続プールの外に持つ。受信の Stream[IO, VersionNotice]（fs2）を Resource と Fiber で動かし、切断したら再接続して購読し直す。PHC.pgListen・PHC.pgNotify・PHC.pgGetNotifications（doobie.postgres.hi.connection）が、同じ接続の通知を受け取れることは確認済み（K11。2026-11-25）。専用の接続での受信、別の接続からの通知、切断後の再購読は未確認
    配信 受信した通知を、fs2 の Topic[IO, VersionNotice]（または接続ごとの有限の Queue）に流し、SSE の接続ごとに game_id で絞って送る。遅い接続のために全体を止めない（バッファに上限を置き、あふれた接続は切断して、クライアントが再接続してスナップショットを取得する）。Topic が購読者の遅れで発行側を止めうるかは未確認（fs2 の仕様を B1 で確認し、止めうるなら接続ごとの Queue.dropping などに替える）
    補完 購読中のゲームについて、数秒ごとに projection_checkpoints の版を照会し、通知より新しければ通知を出す（NOTIFY の欠落への備え）

    実装 http4s の ServerSentEvent と、Stream[IO, ServerSentEvent] を本文にした応答を第一候補とする。0.23.39 での API は未確認。使えない場合の逃げ道は、text/event-stream の本文を直接書くこと

    ローカル開発（H2 の PostgreSQL モード）と実行の選択¶

    ユーザーの決定（2026-11-25）により、開発機でのローカル開発（起動と動作確認）だけ、H2 の PostgreSQL モードで動かせます（技術スタック の ST9。Kotlin 版の T7・ADR-014 を読み替えたもの。H2 の依存の導入は承認待ち、動作範囲は B1 の最初に実測して確定する）。PostgreSQL 固有の機能を ProjectionLock と ChangeNotifier のポートの裏に隠し、PostgreSQL 版と H2 版の 2 実装を持ちます。統合テスト、CI、受け入れ、ステージング、本番は PostgreSQL 18 のままです。

    ポート PostgreSQL 版（統合テスト・CI・ステージング・本番） H2 版（ローカルのみ） 契約テスト
    ProjectionLock（withShared・withExclusive: ConnectionIO[Either[AppFailure, A]] => ConnectionIO[Either[AppFailure, A]] の変換。N-H2・R-H6） トランザクションの先頭で lock_timeout を設定して pg_advisory_xact_lock(_shared)（同じ接続。COMMIT・ROLLBACK で外れる。取った後に lock_timeout を 0 に戻す。ConnectionIO として実行できることは確認済み。K10。共有と排他の待ち合いは未確認） プロセス内の StampedLock 系のロック（Fiber から安全な部品。ゲームごと）+ 待ちの上限（超えたら RetryExhausted）+ トランザクション終了後の後始末（AfterEnd。COMMIT・ROLLBACK の後。D4。Kotlin 版の LocalProjectionLock と同じ構造）。単一プロセスでのみ有効（複数のプロセスでは保証しない） 同じ型で、両実装に同じ契約テストを実行する（「COMMIT の後まで直列化する」条項も両実装の共通条項。R-H5。H2 版の実測は未実施）

    • テスト用のインメモリ実装との関係: 既存のテスト用のインメモリ実装（ドメイン・アプリケーションの受け入れで使う関数値の経路）と、H2 版の本体の実装は別のものです。H2 版は、DB（H2）に接続する経路の実装であり、インメモリ実装は DB を使わない。ただし、ロックと通知のプロセス内の実装は共通の部品を使える（プロセス内の読み書きロックと Topic。共通化するかは B1 で決める）。契約テストは、PostgreSQL 版、H2 版、インメモリ実装の 3 つで同じ内容を実行する。
    • 実行する DB の選択: 設定 DB_KIND=postgres|h2（既定は postgres）で選び、app が組み立てる（Transactor・ProjectionLock・ChangeNotifier と、マイグレーションの場所）。H2 版でも Left の明示 ROLLBACK（Tx.run。SBD2）は同じにします（Tx.run は DB に依らない見込みですが、H2 での動作は未確認。K21）。
    • 本番・ステージングでの H2 の拒否（許可リスト方式。APP_ENV × DB_KIND）: AppConfig.load が、APP_ENV が本番・ステージングのとき DB_KIND=h2 を拒否し、起動に失敗する（ValidatedNec の設定の誤りとして、足りない設定と同じ経路で終了する）。DB_KIND だけでなく、JDBC URL の jdbc:h2: も検査して拒否する（設定の組み合わせの誤りで、DB_KIND=postgres のまま H2 の URL が渡る場合を止める。L3。インフラストラクチャ の検査と揃える）。E2E のためにレート制限をゆるめる設定（TS 版の AUTH_RATE_LIMIT_PER_MINUTE に当たるもの）も、本番・ステージングでは既定の値以外を拒否する（SF2 に含める案）。環境ごとの全組み合わせを単体テストで確かめる（インフラ）。H2 は本番イメージに含めないため、H2 のドライバの欠落でも、本番・ステージングでは起動が失敗する（二重の防御）。
    • 乖離への対策: (a) H2 でしか通らない記述を禁止し、PostgreSQL の統合テストを正とする、(b) ポートの契約テストを両実装で実行する、(c) 受け入れは PostgreSQL で実行する（データモデル「乖離のリスクと対策」、テスト戦略）。
    • ローカルで守られない制約（H2 版）: uq_idempotency_create、追記専用、DB ロールとプールの分離、複数プロセスの直列化と通知、分離レベルによる一貫した読み取り（データモデル の 7 項目）。冪等記録の重複は、H2 版ではアプリ側で挿入前に (scope, key_digest) を検索して ConcurrencyConflict を返す（Kotlin 版と同じ方針）。
    • SQLSTATE の写像: PostgreSQL 版は PSQLException から制約名を取る。H2 版は、メッセージ中の制約名（大文字小文字を区別せず）で写し、AppFailure.Persistence にメッセージを載せない。doobie 経由で H2 の SQLSTATE と制約名が取れるかは未確認（B1 で実測）。
