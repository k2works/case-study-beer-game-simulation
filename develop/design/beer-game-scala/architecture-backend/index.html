    バックエンドアーキテクチャ - ビールゲームシミュレーション（Scala 版）¶

    概要¶

    本書は、beer-game-scala のバックエンドのアーキテクチャを定義します。ADR-001 の決定により、機能・API の振る舞いは beer-game2、設計の構造は beer-game-kotlin のバックエンドアーキテクチャ、実装規約は 関数型プログラミングガイド（Scala 編）（以下「ガイド」）を正本として引き継ぎます。本書は、その構造を Scala 3（Cats Effect + http4s + doobie） で実現する方法と、Scala で変わる点だけを定めます。docs/ を設計の正本とします。実装コードはまだ存在しません（アプリの置き場は apps/beer-game-scala を予定）。

    本書の位置づけと確認の範囲¶

    • 本書で確認したこと: 「コマンド処理の流れ」の AppFailure、EventStore、Ports、App（Kleisli）、Tx.rollbackOnLeft、Execute.step / Execute.execute の型は、sbt 1.13.1（JetBrains Runtime 25.0.4.1）、Scala 3.7.4、cats-effect 3.7.1、doobie-core 1.0.0-RC12 で、-Werror -Wunused:all -Wvalue-discard -Wnonunit-statement と WartRemover 3.6.3 を有効にしてコンパイルできることを確認しました（2026-11-25）。実 DB での実行、Left で ROLLBACK される動作、ConcurrencyConflict の再試行、キャンセルの動作は確認していません（コンパイルのみ）。
    • 確認していないこと: http4s（0.23.39）のルート・ミドルウェア・SSE、doobie の HikariTransactor、PostgreSQL の LISTEN/NOTIFY とアドバイザリロック、Supervisor による切り離し、ember の切断時の挙動、circe による EventCodec、各ミドルウェアの名前は、未確認の設計のスケッチです。技術スタック の未決事項と同じで、B1 で確かめます。
    • 引き継ぐだけのもの: 冪等性の表、競合の再試行の一意制約の表、問い合わせ側の開示、API のエンドポイントと認可の表、エラーの写像の表、SSE の仕様（版の通知だけ、再生なし）、保持削除の手順、セキュリティの表は、Kotlin 版の該当節を正本とします。API の契約（openapi.yaml、code、problem+json）は変えません。
    • Kotlin 版の実装の経緯（B1〜B13 の注記）は引き継ぎません。Kotlin 版の未決事項は、本書の未決事項に引き継ぎます（Rust 版と同じ扱い）。

    パターンの選択¶

    Kotlin 版と同じです。業務領域は中核（週次計算と進行）、イベントソーシング（状態はイベントの列。イベントが監査の記録を兼ねる）、CQRS（コマンド側は events へ追記、問い合わせ側は投影テーブルを SQL で読む）。構造は「核の純粋関数 + 外側の薄い副作用の層」です（ガイド §7.9）。核は、入力の検証、handle、Events.apply、投影、simulateWeek、Disclosure で、副作用は HTTP、データベース、時計、乱数、ログです。副作用は IO と ConnectionIO の値として組み立て、実行は IOApp とテストの境界だけです（SBD5）。

    全体構成¶

    層と依存の向き¶

    依存は、外側から内側（ドメイン）への一方向です。domain は cats-core だけに依存します（ドメインモデル の SD5、技術スタック の ST3）。

    層（sbt のプロジェクト。パッケージ） 責務 依存してよい先
    domain（beergame.domain） 値オブジェクト、Command、Event、エラー、handle / Events.apply、再生、startGame、simulateWeek、KitPreset、投影の純粋関数、RetentionSaga の純粋関数。業務ルールはここにある なし（外部は cats-core のみ）
    application（beergame.application） ポート（関数を持つ case class）の定義、コマンド処理 execute、問い合わせ、競合の再試行、周辺ストアへの書き込み内容の導出（純粋）、開示の判定 Disclosure。トランザクションの境界を決める。ルールは持たない domain。外部は cats-effect、doobie-core（ConnectionIO の型だけ。SBD3）
    adapter-http（beergame.adapter.http） http4s のルート、DTO の検証（誤りを集める）、認証の入口（生の資格を取り出す）、Origin 検査、レート制限、ヘッダー、SSE、エラーの写像 application、domain
    adapter-persistence（beergame.adapter.persistence） doobie による EventStore、投影の書き込み、問い合わせ、周辺ストア、冪等記録、ProjectionLock と ChangeNotifier の PostgreSQL 版と H2 版（ST9）、イベントの JSON 変換（EventCodec）、マイグレーション（共通と PostgreSQL 専用の場所） application、domain
    app（beergame.app） 設定の読み込みと検証、ポートの組み立て（ワイヤリング）、IOApp、起動のモード（api、retention、migrate、rebuild-projections） 全プロジェクト

    sbt のプロジェクト名は、ディレクトリ名に合わせて domain・application・adapterHttp（adapter-http/）・adapterPersistence（adapter-persistence/）・app とし、依存は dependsOn で宣言します。この規則は、sbt の依存宣言（宣言していないプロジェクトの型は参照できない）と、依存の検査（下の「モジュール構成と依存の検査」）の二重で守ります。

    依存を表す: 関数を持つ case class（設計判断 SBD1）¶

    Kotlin 版は、依存を typealias と data class の関数の束で表します（BD2）。ガイド §7.2 も、外部とのやり取りを関数を持つ case class（Hub）で受け取り、テストでは渡す関数を差し替えます。Scala 版も同じ形を採り、文脈（ポートの束）は Kleisli で渡します。タグレスファイナルと IOLocal は採りません（ガイド §7.2、§10.1、§10.2。文脈の渡し忘れは Kleisli なら実行前に型で分かる）。

    enum AppFailure:
  case Domain(code: String)         // handle が返した業務上の失敗（実際は DomainError を包む）
  case ConcurrencyConflict          // 追記の競合。execute が再試行する
  case RetryExhausted               // 再試行・ロックの待ちの上限。app.retry_exhausted（503、Retry-After）
  case Unauthorized                 // app.unauthorized（403）
  // … Invalid（境界で集めた入力の誤り）、IdempotencyKeyReused、Persistence（想定外の失敗。500 と相関 ID）

final case class StreamRead[E](events: List[E], version: Long)

final case class EventStore[E](
    read: ConnectionIO[StreamRead[E]],
    append: (Long, List[E]) => ConnectionIO[Either[AppFailure, Long]]
)

final case class Ports[E](store: EventStore[E], xa: Transactor[IO], maxAttempts: Int)

type App[E, A] = Kleisli[IO, Ports[E], A]

    上は、コンパイルを確認した簡略化の型です。実際の EventStore は、ストリームの種別（game / session）と、複数のストリームの追記（startGame）を受け取る形に広げます（スケッチは 1 本のストリーム）。ProjectionLock・ChangeNotifier・IdempotencyStore・PeripheralStore・Generators（時刻・識別子・乱数）・CredentialIssuer も同じ形の case class で、型検査していません。

    コマンド側¶

    コマンド処理の流れ¶

    流れと順序は Kotlin 版と同じです。処理の順は固定で、ロック（共有）→ 認証（操作者・資格の有効性）→ 認可の前提検査 → 冪等記録の照合 → 読み込み → handle → 追記・投影 → 周辺ストア → 通知 → 冪等記録の保存 → COMMIT です。認可を冪等記録の照合より先に置くため、入れ替えで失効した旧担当者が過去のキーを再送しても 403 になります（ADR-004）。

    execute は、ストリームの種類に依存しない汎用の関数です。ストリームごとの初期状態・遷移・handle を引数で受け取り、ルールを持ちません（Kotlin 版と同じ）。コンパイルを確認したスケッチ:

    object Tx:
  /** Left を返したら ROLLBACK してから返す。doobie の既定の戦略は、Left でも COMMIT するため */
  def rollbackOnLeft[A](program: ConnectionIO[Either[AppFailure, A]]): ConnectionIO[Either[AppFailure, A]] =
    program.flatMap:
      case left @ Left(_) => FC.rollback.as(left)
      case right          => FC.pure(right)

object Execute:
  def step[S, E, C](initial: S, evolve: (S, E) => S, decide: (S, C) => Either[AppFailure, List[E]], command: C)(
      store: EventStore[E]
  ): ConnectionIO[Either[AppFailure, Long]] =
    store.read.flatMap: read =>
      val state = read.events.foldLeft(initial)(evolve)
      decide(state, command) match
        case Left(failure) => FC.pure(Left(failure))
        case Right(Nil)    => FC.pure(Right(read.version))     // 空の列は追記しない
        case Right(events) => store.append(read.version, events)

  def execute[S, E, C](initial: S, evolve: (S, E) => S, decide: (S, C) => Either[AppFailure, List[E]], command: C)
      : App[E, Either[AppFailure, Long]] =
    Kleisli: ports =>
      val once: IO[Either[AppFailure, Long]] =
        Tx.rollbackOnLeft(step(initial, evolve, decide, command)(ports.store)).transact(ports.xa)
      def loop(attempt: Int): IO[Either[AppFailure, Long]] =
        once.flatMap:
          case Left(AppFailure.ConcurrencyConflict) if attempt < ports.maxAttempts => loop(attempt + 1)
          case Left(AppFailure.ConcurrencyConflict)                                 => IO.pure(Left(AppFailure.RetryExhausted))
          case other                                                                => IO.pure(other)
      loop(1)

    上のコードについて、コンパイルが通ることだけを確認しました。次の 4 つの性質は、テストを書いて B1 で確かめる（Rust 版が型検査とテストで確かめたものに対応）。(1) 成功は COMMIT だけで、ROLLBACK しない。(2) 競合が 2 回続いても、再試行して成功する。(3) 競合が上限まで続くと、すべて ROLLBACK して RetryExhausted を返す。(4) 業務の失敗（handle が Left）は、ROLLBACK して、再試行も追記もしない。FC.rollback（doobie.free.connection）が期待どおりに ROLLBACK を発行するかは、実 DB で確認していない（要確認。SBD2）。

    Ignored の扱い: 実際の step の再生は Evolution（ドメインモデル の SD2）を畳み込み、コマンドの経路で Ignored が出たら、状態を信用せず AppFailure.Persistence（500・相関 ID）で失敗させます（fail closed）。保存済みの事実を無視した状態で handle すると、不変条件が崩れるためです。StreamRead.version は、読み込んだイベントの件数ではなく、MAX(stream_version) とします（追記の期待する版）。上のスケッチは、簡単のため (S, E) => S の遷移を使っています。

    要点は Kotlin 版と同じです。

    • StartGame と開始後の役割の入れ替えだけは、game と session の両ストリームを読み、両方の期待する版を持って 1 回の追記で書く別の関数にします。
    • 冪等記録に保存するのは、成功した応答だけです。業務の失敗は保存せず、再送は同じ失敗を再計算して返します。
    • 自動確定のための特別な処理はありません。 Session.handle が複数のイベントを返すため、execute から見ると 1 回の追記です。
    • 投影は追記の後に更新します（同じトランザクション）。複数の投影の行を更新するときのロックの順序の規則（表名の辞書順 → 主キーの昇順）も同じです。
    • 周辺ストア（表示名・資格のダイジェスト）の書き込み内容は、純粋関数で導出します（peripheralWrites）。イベントには入れません（D7）。

    トランザクションと Left の ROLLBACK（設計判断 SBD2）¶

    Kotlin 版の EventStore.transaction は、ブロックが Left を返したら ROLLBACK します。doobie の Transactor は、ConnectionIO が例外なく完了すれば、その値が Left でも COMMIT します（IO の失敗でなく、Either の Left を返すため。Scala 版の設計は「業務の失敗は Either、IO の失敗は想定外に限る」。ガイド ADR-050）。そのため、Left を返す経路で ROLLBACK を明示する必要があります。

    案 内容 評価
    A（採用の提案） Tx.rollbackOnLeft が、Left のときに ConnectionIO の ROLLBACK（FC.rollback）を発行して Left を返す。すべての書き込みのトランザクションを、この関数を通して実行する Left が COMMIT されない。1 か所で守れる。Scalafix で .transact の直接の呼び出しを禁止し、Tx 経由に限る（検査の方式は未確認）
    B 業務の失敗を IO.raiseError にして、doobie の既定の ROLLBACK に任せる 既定の動作で ROLLBACK される。業務の失敗を IO の失敗にするため、ガイド ADR-050 に反する
    C EitherT[ConnectionIO, AppFailure, A] の Left を ROLLBACK に結びつける 連鎖が書きやすい。ガイドは EitherT を試していない。導入の承認が要る

    この挙動（「Left でも COMMIT する」）は、ガイドと doobie の仕様の読みによる設計の前提で、実 DB では確認していません。B1 の最初のスライドで、Left を返したときに行が残らないことを、Testcontainers の統合テストで確かめます（前提が成り立たなければ、設計を見直す）。

    ポートの型に ConnectionIO を使う（設計判断 SBD3）¶

    Kotlin 版は、Tx を引数で明示し、ポートの関数は suspend (Tx, …) です。Scala 版は、ガイド §7.6 に従い、ポートの戻り値を doobie の ConnectionIO にします。ConnectionIO は、実行の記述（IO と同じく値）で、モナドです。for で複数の操作を 1 つのトランザクションに束ねられ、Transactor が transact で実行したときに初めて接続が使われます。

    案 内容 評価
    A（採用の提案） application が doobie-core に依存し、ポートは ConnectionIO[...] を返す 1 つのトランザクションへの合成が for で書ける（ガイド §7.6）。application が SQL を知らず、ConnectionIO の型だけを知る。domain は依存しない
    B application 独自の Tx[A] 型（Kleisli[IO, Connection, A] など）を定義し、adapter-persistence が doobie で実装する application が doobie に依存しない。自前のトランザクションの合成とエラー処理を持つことになる
    C ポートは IO を返し、トランザクションの合成は adapter-persistence の内部に閉じる application が単純。複数のポートの呼び出しを 1 つのトランザクションにまとめられない

    トレードオフ: A は、application が doobie-core に依存します（ConnectionIO の型だけ）。ドメインの純粋性は守られます。

    キャンセル安全性（設計判断 SBD4）¶

    Kotlin 版は、COMMIT と ROLLBACK を NonCancellable で行い、CancellationException を再送出します（ADR-005）。Cats Effect では、キャンセルは Fiber の取消です。クライアントが切断すると、サーバーが処理中の Fiber を取り消しうる（http4s ember が切断時にハンドラを取り消すかは未確認）ため、次の方針にします。

    リスクの置き場所: 「部分更新が残る」ことは、PostgreSQL のトランザクションの原子性が防ぎます（COMMIT の前に接続が切れれば、サーバーが中止する）。本当のリスクは、(1) ロックと接続が解放されるまでの遅れ（pg_advisory_xact_lock_shared・行ロックを握ったまま接続が残る）、(2) 切り離した処理の寿命（追跡、シャットダウン）、(3) COMMIT の結果が呼び出し側に分からなくなること（タイムアウト・切断）の 3 つです。Rust 版のレビューで整理した見方を引き継ぎます。

    項目 設計
    ROLLBACK 失敗の経路では ROLLBACK を明示する（SBD2 の Tx.rollbackOnLeft。IO の失敗・取消のときは、doobie の Transactor の後始末に任せる。doobie がキャンセル時に ROLLBACK して接続を返すかは、公式の文書で確認していない。B1 で挙動を確かめる）
    COMMIT の途中でのキャンセル execute を Supervisor[IO]（cats-effect の標準）で切り離した Fiber として起動し、ルートはその完了（join）を待つ。クライアントが切断してルートの Fiber が取り消されても、コマンドの処理は最後まで走る（COMMIT が中途半端にならない）。Supervisor は Resource で作り、アプリの終了時に追跡している Fiber の完了を待つ（Supervisor(await = true) の指定は要確認）
    タイムアウトと「結果が不明」 ミドルウェアのタイムアウトが応答した後も、切り離した Fiber は COMMIT まで進みうる。タイムアウトの応答は type を付けない 504 とし、画面は「結果が不明」として同じ Idempotency-Key で再送する（UI 設計 の影響表）。元の処理が実行中に同じキーの再送が届いたときは、先の処理の完了を待って、保存済みの応答（または同じ失敗）を返す（実現は B1 で確認。待ちの上限を超えたら app.retry_exhausted）
    プール取得のタイムアウト プールから接続を取れなかった場合は、コマンドは未実行が確実なので、AppFailure.RetryExhausted（503・type つき・Retry-After）に写す。begin の失敗は、Persistence（500）とは区別する
    Fiber の失敗（想定外の例外） IO の失敗（Throwable）を AppFailure.Persistence に写し、500 と相関 ID にする。業務の失敗は Either で返るため、IO の失敗は想定外に限る
    同時に走るコマンドの数 同時に走るコマンドの数に上限を置く（Semaphore など。超えたら RetryExhausted）。上限の値は実測で決める
    シャットダウン SIGTERM で新しい要求の受付を止め、SSE の接続に終了を知らせて閉じ（SSE は自然には閉じない）、Supervisor が追跡している Fiber の完了を待つ（待ちの上限は stopTimeout より短く）。ember のシャットダウンの待ち方は未確認
    案 内容 評価
    A（採用の提案） execute を Supervisor で切り離して起動し、ルートは完了を待つ。失敗の経路は ROLLBACK を明示 切断で処理が途中で止まらない。追跡の仕組みが cats-effect の標準にあり、新規の依存が要らない（Rust 版の TaskTracker に当たる）。ROLLBACK を後始末に頼らない
    B ハンドラの Fiber の中で直接実行する 単純。ただし、クライアントの切断で COMMIT の直前に取り消されうる。IO.uncancelable で包む案は、プール取得の待ちまで取り消せなくなる
    C IO.uncancelable で execute 全体を包み、Supervisor を使わない 切断で止まらない。待ちのキャンセル（シャットダウン）ができず、Fiber を追跡できない

    冪等性と競合の再試行¶

    冪等記録の表（idempotency_records、24 時間、応答を暗号化、request_digest に操作者 ID を含める、認可の後に照合する、成功した応答だけを保存する）と、再試行する一意制約の一覧（uq_events_stream_version、uq_idempotency_create、pk_idempotency_records）は、Kotlin 版を引き継ぎます。

    lock_timeout B1 の受入条件に、lock_timeout の初期値を入れる（未設定だと、再構築の間、コマンドがアドバイザリロックを無期限に待つ）。超過（SQLSTATE 55P03）は RetryExhausted に写す。値は実測で決める

    暗号化と HMAC 候補は JDK の javax.crypto（Mac・Cipher）と java.util.Base64。外部の暗号ライブラリを足さない案を第一候補とし、資格の設計時に決める（承認が要る）

    投影の更新と再構築¶

    投影は、Projection（純粋。Event => List[RowChange]）と、SQL への書き込み（境界）に分けます（ドメインモデル）。再構築は rebuild-projections モードで、1 ゲームを 1 トランザクションで、排他のロック（ProjectionLock.acquireExclusive。PostgreSQL では pg_advisory_xact_lock）を取って行います。コマンドは共有のロック（pg_advisory_xact_lock_shared）を取るため、再構築と同時には走りません。ロックは SQL を直接発行します（fr"select pg_advisory_xact_lock($key)"）。doobie でこのクエリを ConnectionIO[Unit] として実行できることは、未確認で、B1 で確かめます。

    再生に関する 3 つの性質（永続化往復の同値性、計算と事実の一致、投影の整合）と、検証の場は、ドメインモデル と Kotlin 版のとおりです。

    API 設計方針¶

    REST + JSON（/api/v1）、リアルタイム通知は SSE、エラーは application/problem+json、変更系は Idempotency-Key を必須とし、If-Match は SaveDecision（意思決定の版）だけに付けます。エンドポイントの一覧、コマンドの流れるストリーム、認可、コマンドの応答（versions だけ。資格を渡す操作の例外）は、Kotlin 版の表と同じで、OpenAPI の契約を共有します。POST /games/:id/start は 2 ストリームにまたがる資源として維持します。

    ルートは薄く、関数として呼べる形にする（設計判断 SBD6）¶

    ルートは HttpRoutes[IO] で、本体は「検証 → execute → 写像」の 3 つだけを呼びます（Kotlin 版の BD4 と同じ）。ガイド §7.1 のとおり、ルートは Request を受け取って Response を返す関数なので、サーバーを起こさずに routes.orNotFound.run(Request[IO](...)) で呼べます。API の契約テストと受け入れテストは、この形で書きます（テスト戦略）。

    入力の検証とエラーの写像¶

    エラーの code と HTTP の写像の契約: Kotlin 版は、DomainError の code と分類から HTTP の code への写像の正本の一部を実装ファイル（ProblemMapping.kt）に持ちます。Rust 版と同じく、Scala 版は次をこの文書と openapi.yaml の両方で固定します（実装ファイルを正本にしない）。(1) 分類が Forbidden のドメインの誤り（session.forbidden・game.forbidden）は、HTTP では app.unauthorized（403）と同じ本文に写る（資格の失敗と区別しない。NF-S12）。例外は参加コードの失敗の game.invitation_invalid（同じ本文）。(2) 409 の problem+json は、拡張メンバー（requestedWeek・currentWeek・role・latest・week・current）を操作ごとに持つ。どの操作がどのメンバーを返すかは、openapi.yaml の ConflictProblem を正本とする。(3) HTTP の層の失敗（request.*・app.rate_limited・app.not_ready）と、validation.invalid_input は、DomainError でなく AppFailure と http4s の拒否の写像が持つ。契約テストが、code の全体と openapi.yaml の一覧を突き合わせる。

    • ルートは、DTO を、スマートコンストラクタで Command に変換します。誤りはすべて集め（ValidatedNec。ドメインモデル の SD3）、422 で項目ごとの誤りを返します。本文の構文エラーは 400。
    • ドメインのエラーは、分類で HTTP の状態へ写します。写像は 1 か所（adapter-http）の関数で、AppFailure を match（_ なし）で網羅します（ガイド §3.3 の statusOf。エラーの種類を足すと、写像を忘れた箇所が -Werror でビルドの失敗になる。SBD8）。写像の表（Forbidden → 403、NotFound → 404、InvalidState → 409、Conflict → 409、RuleViolation → 422、Unauthorized → 403、RetryExhausted → 503 と Retry-After、Persistence → 500）、code の一覧、HTTP の層の失敗（request.*、app.rate_limited、app.not_ready）は Kotlin 版と同じです。
    • バックエンド自身が返す 503 は、必ず type（problem+json）を持ちます（画面が「もう一度お試しください」と「結果が不明」を区別するため）。

    認証とミドルウェア¶

    Kotlin 版は、認証を execute の中（トランザクションの中）で行います。Scala 版も同じです。ミドルウェアで認証しません（再試行のたびに、同じトランザクションの中で評価し直す必要があるため）。ミドルウェアは、リクエスト ID、Origin 検査、ヘッダー（CSP、HSTS、nosniff、Referrer-Policy）、本文のサイズ上限、レート制限、タイムアウトを担当します。使うミドルウェアの名前は未確認です（技術スタック の対応表）。ルートは、生の資格（Cookie の値）を取り出し、RequestMeta としてコマンドと一緒に execute へ渡します。

    自動確定¶

    Kotlin 版と同じです。自動確定のための処理はアプリケーション層になく、Session.handle が複数のイベントを返します。一時停止中の扱い、同時に起きること（最後の保存と手動の確定、共同担当の同時の保存、確定と一時停止）の結果の表も同じです。

    通知（SSE）¶

    仕様は Kotlin 版を引き継ぎます。版の通知だけを送り（state-version。ストリームの種別と版）、内容は運びません。再生（Last-Event-ID）は行わず、接続の開始と再接続のたびに、クライアントがスナップショットを取得します。発信は、追記と同じトランザクションで ChangeNotifier.publish を呼び、コミットされたときだけ配信されます。

    ローカル開発（H2 の PostgreSQL モード）と実行の選択¶

    ユーザーの決定（2026-11-25）により、開発機でのローカル開発（起動と動作確認）だけ、H2 の PostgreSQL モードで動かせます（技術スタック の ST9。Kotlin 版の T7・ADR-014 を読み替えたもの。H2 の依存の導入は承認待ち、動作範囲は B1 の最初に実測して確定する）。PostgreSQL 固有の機能を ProjectionLock と ChangeNotifier のポートの裏に隠し、PostgreSQL 版と H2 版の 2 実装を持ちます。統合テスト、CI、受け入れ、ステージング、本番は PostgreSQL 18 のままです。

    ポート PostgreSQL 版（統合テスト・CI・ステージング・本番） H2 版（ローカルのみ） 契約テスト
    ProjectionLock pg_advisory_xact_lock(_shared)（ConnectionIO の中で取り、トランザクションの終了で解放） プロセス内の読み書きロック（単一プロセスでのみ有効。複数のプロセスでは保証しない） 両実装で同じ契約を実行する

    • テスト用のインメモリ実装との関係: 既存のテスト用のインメモリ実装（ドメイン・アプリケーションの受け入れで使う関数値の経路）と、H2 版の本体の実装は別のものです。H2 版は、DB（H2）に接続する経路の実装であり、インメモリ実装は DB を使わない。ただし、ロックと通知のプロセス内の実装は共通の部品を使える（プロセス内の読み書きロックと Topic。共通化するかは B1 で決める）。契約テストは、PostgreSQL 版、H2 版、インメモリ実装の 3 つで同じ内容を実行する。
    • 実行する DB の選択: 設定 DB_KIND=postgres|h2（既定は postgres）で選び、app が組み立てる（Transactor・ProjectionLock・ChangeNotifier と、マイグレーションの場所）。H2 版でも Left の明示 ROLLBACK（SBD2）は同じです（doobie の Tx.rollbackOnLeft は DB に依らない）。
    • 本番・ステージングでの H2 の拒否（許可リスト方式。APP_ENV × DB_KIND）: AppConfig.load が、APP_ENV が本番・ステージングのとき DB_KIND=h2 を拒否し、起動に失敗する（ValidatedNec の設定の誤りとして、足りない設定と同じ経路で終了する）。環境ごとの全組み合わせを単体テストで確かめる（インフラ）。H2 は本番イメージに含めないため、H2 のドライバの欠落でも、本番・ステージングでは起動が失敗する（二重の防御）。
    • 乖離への対策: (a) H2 でしか通らない記述を禁止し、PostgreSQL の統合テストを正とする、(b) ポートの契約テストを両実装で実行する、(c) 受け入れは PostgreSQL で実行する（データモデル「乖離のリスクと対策」、テスト戦略）。
    • ローカルで守られない制約（H2 版）: uq_idempotency_create、追記専用、DB ロールとプールの分離、複数プロセスの直列化と通知、分離レベルによる一貫した読み取り（データモデル の 7 項目）。冪等記録の重複は、H2 版ではアプリ側で挿入前に (scope, key_digest) を検索して ConcurrencyConflict を返す（Kotlin 版と同じ方針）。
    • SQLSTATE の写像: PostgreSQL 版は PSQLException から制約名を取る。H2 版は、メッセージ中の制約名（大文字小文字を区別せず）で写し、PersistenceFailure にメッセージを載せない。doobie 経由で H2 の SQLSTATE と制約名が取れるかは未確認（B1 で実測）。

    12 Cucumber-JVM の acceptanceTest acceptance プロジェクト（cucumber-scala + 関数値の経路。sbt test に載せない） ST7

    上記以外（ES + CQRS の構造、処理の順、冪等性、再試行の対象、問い合わせの開示、SSE の仕様、保持削除、API の契約）は変えません。

    前提と見直しの条件¶

    • 前提: (1) doobie 1.0.0-RC12 が、ConnectionIO の ROLLBACK（FC.rollback）、PostgreSQL のアドバイザリロック（SQL の直接の発行）、LISTEN/NOTIFY（doobie-postgres）、制約名つきのエラー、HikariTransactor を扱える。(2) http4s 0.23.39 の ember が SSE を提供し、切断時とシャットダウン時の挙動が設計に合う。(3) Supervisor で切り離した Fiber が、ルートの取消後も完了する。いずれも B1 で確認する。
    • 見直しの条件: 上の前提のどれかが成り立たない場合は、SBD2〜SBD4・SBD9、SSE の設計、ProjectionLock と ChangeNotifier の実装を見直す。1 ストリームの再生が千件を大きく超える場合は、スナップショットを検討する（ADR-003）。

    未決事項¶

    1. doobie の機能の確認（B1）: FC.rollback の効果と、Left での COMMIT の挙動（SBD2）、アドバイザリロック、LISTEN/NOTIFY、制約名の取得、キャンセル時の ROLLBACK、HikariTransactor、マイグレーション（Flyway）との連携。
    2. http4s の ember の確認: ミドルウェアの名前、SSE の API、切断時のハンドラの取消、シャットダウンの待ち方。
    3. SBD1〜SBD11 の承認: 人の承認を得る。特に SBD2（Left の ROLLBACK）、SBD3（application が doobie-core に依存）、SBD4（Supervisor）。
    4. Supervisor の使い方: await の指定、タスクの数の上限、待ちの上限（stopTimeout より短く）。値は実測で決める。
    5. 同じ Idempotency-Key の再送が、元の処理の実行中に届いたときの待ち方（先の処理の完了を待つ仕組みと、待ちの上限）。
    6. lock_timeout の初期値、プール取得のタイムアウトの値、同時に走るコマンドの数の上限。
    7. 暗号化と乱数: 応答の暗号化（AES-256-GCM）に JDK の javax.crypto で足りるか。外部ライブラリを足す場合は承認が要る。
    8. 統合のエラー型（DomainError）と Projection の DomainEvent: B1 の最初のスライドで決める（ドメインモデル の未決事項 3）。
    9. 依存の検査の方式: sbt のタスクか、Scalafix の DisableSyntax.regex か。.transact の直接の呼び出しを禁止して Tx 経由に限る方式も同じ検査の仕組みで行えるか。
    10. ログ: フレームワークのログを JSON にするか。JVM のヒープ・GC の指標の採否。
    11. Kotlin 版の未決事項の引き継ぎ: 投影の再構築中のコマンドの応答（短い待ちか、すぐ 503 か）、FOR UPDATE の要否、再試行の間の待ち（ジッター）、観察者への開示、SSE の心拍の間隔、app のモードの環境変数の名前。いずれも Kotlin 版の未決事項 に追従する。
