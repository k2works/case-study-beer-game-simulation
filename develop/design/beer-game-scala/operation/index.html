    運用要件定義 - ビールゲームシミュレーション（Scala 版）¶

    概要¶

    本書は、beer-game-scala を本番で運用するための要件を定義します。ADR-001 により、beer-game-kotlin の運用要件（beer-game2 の運用要件を引き継いだもの）を正本として引き継ぎ、Scala 版で変わるものだけを見直しました。docs/ を正本とします。実装コード、Terraform、アラーム、手順書はまだ存在せず、本書の「アラーム」「手順書」は、作成する対象の設計です。

    Scala 3 は JVM 上で動くため、JVM に由来する運用（ヒープ、GC、起動の遅さ、OOM、ヒープダンプ）は Kotlin 版と同じです。ES + CQRS に由来する運用（events が状態の正本、投影の再構築、投影の整合の検査、追記の競合率、イベントスキーマの進化と 2 段階のリリース、書く版の切り替え）も同じです。変えるのは、次の 4 点だけです。

    • Cats Effect・doobie に固有の監視と障害パターン（Fiber の追跡、Supervisor、HikariTransactor の待ち、IO の失敗の写像）を、Kotlin 版のコルーチン・Ktor・JDBC の項目に読み替える。
    • ログの形を、ガイド §7.8 の LogRecord と LogSink（載せるものを型で決める）にする（バックエンドアーキテクチャ の SBD10）。
    • Left の ROLLBACK とキャンセル後のトランザクションの取り残しを、新しい障害パターンとして加える（SBD2、SBD4。Rust 版の NF-R18 の読み替え）。
    • ツールの違い（sbt、Scalafmt、WartRemover、Scalafix、scoverage）と、team の規約（main の merge で staging へ自動反映、production は手動承認。CI とデプロイのワークフローは beer-game3 とは別に新設）。

    範囲（ユーザーの決定、2026-11-25。M19）: 実装として約束するのは U1〜U3 です。U1〜U3 の間は、実際の研修には使いません（検証・事例用）。 本書の本番運用・復元訓練・監視・手順書の完成は、再開するときに Unit を決めます（指標を見て決める。Unit 定義ではステージングは U1 の US6.2 にあり、U5 への付け替えは AI の整理。L2）。したがって、下の進行役への依頼文言・研修中の原則・パターン 18 は、実際の研修に使い始める前に、運営者と合意するもので、U1〜U3 では設計としてのみ置きます。研修に使い始める前提の時期は「U4 と U5 の判断の後」です（理由は ADR-001 の 97〜100 行付近の 2 つ: U4 の US4.2 振り返りと、U5 の US5.1 保持削除。M17）。U5 に着手する条件として、運営者との合意（依頼文言・15 分・研修中の原則）を 1 つ置きます（案。承認を得ていない）。U1 の範囲（D1・D2。ユーザーの指示に基づき AI が推奨案で決めた。確認は未了）: 検証の CI（check）に加え、統合テスト（PostgreSQL 18）と @api の受け入れを CI で実行する。US6.1 は AC6.1.1（構造化ログ）・AC6.1.2（相関 ID つきの記録）・AC6.1.4（/ready）を U1 に入れる（AC6.1.3 メトリクス・AC6.1.5〜6.1.6 通知は約束の外）。

    運用の体制、通知先、連絡先は、組織に依存するため未決定です（beer-game2・Kotlin 版と同じ。「要確認」）。

    本書の位置づけと確認の範囲¶

    • 本書で確認したこと: Kotlin 版・Rust 版の運用要件と、Scala 版の 技術スタック・バックエンドアーキテクチャ を読み、Scala 版の実行環境で変わる項目を洗い出しました（2026-11-25）。
    • 確認していないこと: 監視の閾値、アラーム、バックアップ・復元の所要時間、デプロイ、ブルー/グリーン、各手順書は、すべて未実装・未検証です。doobie がキャンセル時に ROLLBACK するか、Supervisor の挙動、cats-effect の実行基盤の指標の取り方、IOApp が SIGTERM で返す終了コードは、実 DB・実行で確認していません（バックエンドの未決事項と同じ。B1 で確かめます）。Left でも COMMIT されることと FC.rollback の効果は、使い捨てのプロジェクトの実 DB で確認済みです（データモデル の検証。確認状況の唯一の一覧: 技術スタック）。
    • 確認状況の正本の規則（N-H5。AI の案で承認を得ていない）: 一覧が正です。一覧の根拠は実測の記録（データモデル の「検証の結果」と テスト戦略 の「確認した事項」）で、一覧を直すときは根拠も直します。

    Kotlin 版の表（アプリ、Web の静的ファイル、インフラ、DB のスキーマ、投影の形）を引き継ぎます。新しい schema_version のイベントが書かれた後は、旧イメージへ戻せないことがある点も同じです。ロールバックの入力に、旧イメージが現在のイベントを読めることの確認（confirm_compatible 相当）を必須にする設計を引き継ぎます（手順書は Scala 版で新規に作る）。

    イベントスキーマの進化（ES 固有）¶

    Kotlin 版の節（変更の種類の表、2 段階のリリース（読める版 → 書く版）、A・B・C の比較で A を採用、ロールバックの制約、golden による検証）をそのまま引き継ぎます。Scala 版の実現は次のとおりです。

    • アップキャストは、adapter-persistence の EventCodec（circe の DTO）の純粋関数の列で、読み込み時に遷移へ渡す前に適用する（バックエンドアーキテクチャ）。
    • 新しいイベントの種類を足すと、Events.apply と投影の match の網羅がコンパイルで失敗する（-Werror）。書く側を後にして、読む側を先にリリースする規則は変わらない。
    • 書く版の切り替えの設定名・置き場所は未決（Kotlin 版は WRITE_SCHEMA_VERSION を提案）。本番の環境変数の変更に当たるため、確認必須。

    変更の承認¶

    Kotlin 版と同じです（標準変更・通常変更・緊急変更の 3 区分、研修の実施日時の前後は通常変更を凍結）。通常変更に、イベントの形の変更（読む版・書く版の各段階）、投影の形の変更と再構築を含めます。
