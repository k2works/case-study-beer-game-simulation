    テスト戦略 - ビールゲームシミュレーション（Scala 版）¶

    概要¶

    本書は、beer-game-scala のテスト戦略を定義します。ADR-001 の決定により、受入条件は beer-game2、テストの構造は beer-game-kotlin のテスト戦略、実装規約は 関数型プログラミングガイド（Scala 編）（以下「ガイド」。テストは第 8 章、静的解析は第 9 章）を正本として引き継ぎ、本書は Scala での実現方法と、Scala で変わる点だけを定めます。docs/ を設計の正本とします。実装コードはまだ存在しません（アプリの置き場は apps/beer-game-scala を予定）。

    範囲の約束（ユーザーの決定、2026-11-25）: 実装として約束するのは U1〜U3 です。U1〜U3 の間は、実際の研修には使いません（検証・事例用）。 検証用の CI（check ジョブ 1 本）は U1 に含め、AWS 環境・デプロイ用のワークフロー・本番運用・復元訓練は後回し（U5）です（下の「CI との連携」）。

    本書の位置づけと確認の範囲¶

    • 本書で確認したこと（2026-11-25。リポジトリの外の使い捨てのプロジェクトで、sbt 1.13.1、Scala 3.7.4、JetBrains Runtime 25.0.4.1、ローカルの Docker の postgres:18.6 を使用。下の表）。
    • 確認していないこと: ScalaCheck の状態に応じた操作列の生成、複数プロジェクトの scoverage の合算（coverageAggregate）と統合テストの計測、HttpRoutes を関数として呼ぶ HTTP のテスト、契約テストのスキーマ検証の道具、Gherkin の別プロジェクトからの実行、テスト用の DB の分離方式、scalafixAll、変異テストの道具。いずれも B1 で確かめます。
    • 引き継ぐだけのもの: テスト形状とレベルの責務、層の分担、境界値の一覧、非機能のテストの対応、トレーサビリティの方針、CI の工程の考え方は Kotlin 版を正本とします。
    • Kotlin 版の実装の経緯（B1〜B15 の結果の記述）は引き継ぎません。H2 に関する記述は、ST9（ユーザーの決定、2026-11-25）に従って読み替えて引き継ぎますが、Scala 版では H2 を実測していません。Kotlin 版の未決事項は、本書の未決事項に引き継ぎます。
    • 確認状況の正本の規則（N-H5。AI の案で承認を得ていない）: 技術スタックの確認状況の一覧が正です。一覧の根拠は実測の記録（データモデル の「検証の結果」と、本書の「確認した事項」1〜11）で、一覧を直すときは根拠も直します。
    • レビュー（2026-11-25）への対応の承認の状況: ユーザーが決めたのは、H3（不正な遷移 Ignored は止める設計を維持）、H6（カバレッジは行率を算出する案 C を第一）、H7（範囲は U1〜U3 を約束し U4〜U6 は指標を見て決める）、H9（NF-P2 は p95 4 秒）に加え、再レビュー（2026-11-25）への対応の次の 4 件です。N-H4（検証用の CI の check ジョブ 1 本は U1 の約束に含める。AWS 環境・デプロイ用ワークフロー・ステージングへの自動反映は後回しで、自動反映を持たない間の team 規約の例外は ADR に記録して人が承認する）、N-H6（domain の文 97% は目安。ゲートにするかは B1 の実測後）、N-H7（止まったゲームでも状態取得の読み取りは返すことを要件にする）、N-H8（U1〜U3 の間は実際の研修に使わない）。これら以外（N-H1・N-H2・N-H3・N-H5 の直し方など）は AI の案で、承認を得ていません。本書の N-H1（許す組の表）・N-H2・N-H3 の記述は案です。
    # 確認した事項 結果
    1 munit 1.3.6 の日本語のテスト名 日本語・記号（[US2.4/AC2.4.1]）を含む名前で書けて実行できる。testOnly NameSuite -- "*AC2.4.1*" で名前の絞り込みもできる。sbt が出す JUnit XML（target/test-reports）に名前がそのまま入る
    2 munit-scalacheck 1.3.1、munit-cats-effect 2.2.1 property("…") { forAll { … } } と、IO を返す test が通る
    3 cats-laws 2.13.0 + discipline-munit 2.0.0 checkAll("…", MonoidTests[Totals].monoid) で法則が 18 件のテストとして走る。empty を壊した Monoid は 4 件（left identity・right identity・combineAllOption・reverseCombineAllOption）が落ちる（ガイド §8.4 の「壊れた実装を見分ける」が満たされる）
    4 sbt-scoverage 2.4.4（Scala 3.7.4） coverage test coverageReport で、文（Statement）と分岐（Branch）の率が出る（例: 87.50% と 75.00%）。Cobertura の line-rate は文の率と同じ値（0.88）で、行の独立した指標ではないと見える。coverageMinimumStmtTotal・coverageMinimumBranchTotal・coverageFailOnMinimum := true が効き、分岐 75% < 80% で coverageReport が Coverage minimum was not reached で失敗する
    5 cucumber-scala 9.3.0（cucumber-core 8.1.0 が推移的に入る） # language: ja（機能・シナリオ・前提・もし・ならば）の .feature が、io.cucumber.core.cli.Main で実行できる。タグ（@US2.4 @AC2.4.1）も出る。定義のないステップは Undefined と報告され、CLI の終了コードが 1

    判断項目 Scala 版の答え 帰結

    画面 URL ルーティングを持つ SPA。API の契約は Kotlin 版・beer-game2 と同じ 画面のテストは変えない

    レベル 目標の割合 理由
    ユニット（ドメイン、投影、アプリケーション）+ UI コンポーネント 65% 以上 純粋関数は速く、規則の網羅に向く

    ローカル開発の DB とテストの分担¶

    ローカル開発だけ H2 の PostgreSQL モードを使います（ST9。ユーザーの決定、2026-11-25。Kotlin 版の T7 を読み替えたもの。H2 の導入は承認待ち、動作範囲は B1 の最初に実測して確定する）。ローカルと CI の乖離に備え、Kotlin 版の対策を引き継ぎます。

    対策 内容
    (a) H2 でしか通らない記述の禁止 PostgreSQL の統合テストが正。H2 のために共通の DDL や SQL を曲げない（通らない文は PostgreSQL 側と H2 側に分ける）
    (b) ポートの契約テストを両実装で実行 ポートの型は、H2 版にも合う形にする（案。H5・N-H2。AI の案で承認を得ていない。B1 の最初に実測して確定する）。ProjectionLock は ConnectionIO の変換 withShared(gameId)(program)（PostgreSQL 版は先頭で pg_advisory_xact_lock_shared を発行して同じトランザクションの中で保持し、COMMIT で自動解放する。H2 版はプロセス内の読み書きロックを bracket で取る）。接続は 1 本のままで、接続数の見積もりは増えない。Resource 案は不採用（コマンドごとに接続が 2 本要るため）。ChangeNotifier はトランザクション内で集め、Tx.run の後に IO で配信する（PostgreSQL 版は中で pg_notify）。同じ契約テストを、PostgreSQL 版は testcontainers-scala の統合テスト、H2 版は munit のユニットテストで実行し、テスト用のインメモリ実装にも流す。H2 版で保証する範囲は、契約を満たす範囲のすべて
    (b-2) 契約の条項を分けて列挙する 契約の条項を「両実装に共通」（ロックの排他と共有、コミット後にだけ通知が届く、ロールバックなら届かない（この 2 つは、ポート単体でなく execute と Tx.run を通す契約にする。コミット後にだけ届くことは execute が保証し、H2 版は Committed.notices から出るため。M8）、EventStore の追記の競合を ConcurrencyConflict に写す、payload の往復）と「PostgreSQL だけ」（LISTEN の再購読、追記専用の権限、部分一意索引、jsonb、複数プロセスの排他）に分けて列挙する。制約名の取り出しと json の書き込みは H2 版独自のコードのため、H2 版の契約テストに入れる（M11）
    (c) 受け入れは PostgreSQL @api の受け入れと E2E の CI は PostgreSQL で実行する

    H2 は、統合テストの検証には使いません。 並行性、権限（ロールと GRANT、追記専用）、部分一意索引、連鎖削除、jsonb、接続プールの分離、分離レベルは、PostgreSQL の統合テストでだけ検証します。H2 版のマイグレーションの適用（Flyway の共通の場所）と、本番・ステージングでの H2 の拒否（環境 × DB_KIND の全組み合わせ）は、ユニットテストで確かめます（インフラ）。H2 の PostgreSQL モードでの動作範囲と、doobie 経由の SQLSTATE の取得は未確認で、B1 の最初に実測します。

    レベル間の重複を避ける方針¶

    Kotlin 版と同じです。規則の分岐は、ドメインのユニットで網羅する。HTTP の統合では、境界の契約だけを確認する。永続化の整合性・並行性・再生・再構築・復元は、DB の統合でだけ検証する。画面の分岐は、コンポーネントで確認する。受入条件は Gherkin、実装の細部と網羅は munit が担い、同じ振る舞いを二重に書かない。同じシナリオを @api と @ui の両方で実行しない。

    開発の進め方（BDD と TDD）¶

    team の規約（aidlc/active-memory/team.md の Testing Posture）は、BDD で、Given/When/Then の振る舞い例と失敗する自動テストを実装前に定義し、最小実装で通した後にリファクタリングすることです。Scala 版でも、Kotlin 版と同じ進め方です。

    • BDD（Given/When/Then を先に）: 受入条件・デモ項目は日本語 Gherkin（フィーチャーファイル）で、cucumber-scala が実行する。ドメインの純粋関数・性質・DB と HTTP の細部は、munit の test("…") の日本語の名前で Given/When/Then を書く。ES では、Given は過去のイベントの列、When はコマンド、Then は新しいイベントの列またはエラー。
    • TDD: 失敗するテストを書き、失敗を確認してから最小限を実装し、通ったらリファクタリングする。先回りして実装しない。
    • 土台を変える最初のスライドでは、後続の振る舞いのテストも先に書く（Ports の型や handle の型など）。順序を守れなかったときは、規則を壊すとテストが落ちることを個別に確かめ、記録に残す（プロジェクトの規約）。

    アウトサイドインのサイクルと Gherkin¶

    Kotlin 版と同じです（デモ項目・受入条件をシナリオにして合意 → 実行して Undefined → ステップ定義で Pending → Failing（Red）→ 内側へ一段ずつ TDD で Green → リファクタリング。シナリオは業務の言葉のまま変えない）。Gherkin の書き方・タグ（@US2.4、@AC2.4.1、@api、@ui、@acceptance-criteria、@happy-path、@negative、@core、@wip）・配置も同じで、フィーチャーファイルは beer-game-kotlin と同じ内容になります。

    項目 Scala 版
    フィーチャーファイル 共有の apps/beer-game-features/ を Kotlin 版・Rust 版と共有する（Rust 版の RF1 を引き継ぐ案。Scala 版での承認は未取得。複製しない）。API の契約が同じなので、シナリオは変わらない見込み
    @api の実行 cucumber-scala 9.3.0。日本語 Gherkin の実行は確認した（確認した事項 5）。sbt の別プロジェクト（acceptance）から実行する方式は未確認
    @ui の実行 Cucumber-JS + Playwright（既存。バックエンドが Scala に変わるだけ）
    ステップ定義 acceptance/（モジュール構成）。薄く保ち、業務ロジックを持ち込まない
    実行 sbt test に載せない（ST7、ガイド §10.1）。専用のジョブで実行し、Undefined・Pending があれば失敗とする（CLI は Undefined で終了コード 1 を返すことを確認した）。Scala 側で実行するシナリオは、許可リスト（タグまたは ID の一覧。Scala 側のファイルで管理）で決め、共有する .feature に Scala 専用のタグを書き込まない（Kotlin 版・Rust 版に影響するため）。B1 の最初の許可リストは、ウォーキングスケルトン（1 ゲーム・4 役割・1 週）に必要な Must のストーリーの代表シナリオに限る
    関数値の経路 同じ受入条件を、ドメイン直接・アプリケーション・HTTP の 3 つの経路でも確かめる（case class に関数値を持たせて経路を差し替える。ガイド ADR-049、§8.5）。Gherkin は業務の言葉の契約、関数値の経路は munit での高速な回帰（ST7）

    Kotlin 版は、テスト名に [US2.4/AC2.4.1] を含めます。munit のテスト名は文字列で、日本語・記号を含められ、名前の絞り込みも JUnit XML も動きます（確認した事項 1）。Rust の識別子の制約のような問題はありません。

    案 内容 評価

    純粋関数のテスト（ドメイン）¶

    対象と検証すること（Game.handle の各コマンドと不変条件、Events.apply の全イベントの網羅、Session.handle の保存・共同入力の競合・代理入力・確定・自動確定（1 回の handle で複数イベント）・一時停止中の扱い、CommitWeek の判定の順（週 → basis）、Events.apply が WeekCommitted の nextStates を再計算せず採用すること（意図的に違う値を Given にして確かめる）、startGame、simulateWeek の golden、設定の検証の誤りの集約、KitPreset.classify、Disclosure、RetentionSaga）は、Kotlin 版の表と同じです。Scala 版での違いは次のとおりです。

    項目 Scala 版
    不正な遷移（Kotlin 版の InvalidTransition） Evolution.Ignored を返し、例外を投げない（SD2）。handle が作らない列（SessionStarted の前の DecisionSaved など）を与えると Ignored になり、状態が変わらないことを確かめる。コマンドの経路で Ignored が出たら AppFailure.Persistence（fail closed）になることは、アプリケーションのテストで確かめる（止める設計の維持は、ユーザーの決定、2026-11-25。利用者に見える変更と運用の扱いは 運用要件 のパターン 18）

    アプリケーション層のテスト（ポートの差し替え）¶

    ポート（EventStore・Generators・CredentialIssuer・IdempotencyStore・ProjectionLock・ChangeNotifier）は、関数を持つ case class で、テストでは渡す関数を差し替えます（ガイド §8.2、§7.2。SBD1）。EventStore・IdempotencyStore などデータを読み書くポートの戻り値は ConnectionIO のため（SBD3）、テスト用のポートも ConnectionIO の値になります（FC.pure と、テストの層で許す可変の保持）。ProjectionLock は ConnectionIO の変換 withShared(gameId)(program)（同じトランザクション内。案。N-H2）、ChangeNotifier は集めた通知を Tx.run の後に IO で配信する形（案。H5）なので、テスト用の ProjectionLock は ConnectionIO の恒等（または呼び出しの記録つき）の変換、ChangeNotifier は IO の値です。トランザクションの境界は、スタブの Connection を渡した Transactor.fromConnection で検証します（確認した事項 8）。方式の詳細は B1 で決めます（インメモリの状態を ConnectionIO から読み書く方法は未確認）。

    バックエンドアーキテクチャ の execute について、次の 4 つの性質を、テストを書いて確かめます（現状はコンパイルのみ確認）。

    1. 成功は COMMIT だけで、ROLLBACK しない。
    2. 競合が 2 回続いても、再試行して成功する。
    3. 競合が上限まで続くと、すべて ROLLBACK して RetryExhausted を返す。上限（maxAttempts）は「総試行回数」とする案（execute のスケッチと同じ。再試行回数ではない。承認を得ていない案で、NF-R17 の定義とあわせて人が決める。M10）。根拠: Kotlin 版の Execute.kt の withAppendRetry（総試行回数の形）に倣う（L10。Kotlin 版の実装を読んで写した案で、Scala 版の値は未実測）。境界値のテストは、上限 − 1 回目の競合のあとの試行が成功すれば成功を返す、上限ちょうどの試行まで競合すれば RetryExhausted の 2 件にする。
    4. 業務の失敗（handle が Left）は、ROLLBACK して、再試行も追記もしない。

    （1）と（4）の commit・rollback の記録は、スタブの Connection で DB なしに書ける見込みです（確認した事項 8 は、旧案の合成子（Tx.rollbackOnLeft。不採用）を単体で確かめたもので、Tx.run そのものの確認ではありません）。案（H4・N-H2）では、公開の入口を Tx.run(program: ConnectionIO[Either[E, A]]): IO[Either[E, A]] だけにし、コマンドの ConnectionIO 全体（認証 → 冪等記録 → step → 投影 → 周辺ストア → 通知 → 冪等記録の保存）を 1 回で包む。ロックは ConnectionIO の変換（withShared）として program の中に入り、transact の外には出ない（同じトランザクション内。PostgreSQL 版は pg_advisory_xact_lock_shared）。このため、FC.rollback の後に同じ ConnectionIO で書き込みが続いて新しいトランザクションとして COMMIT される経路がなくなる、と推論しています（この「FC.rollback の後の書き込み」の挙動（K5）は未実行で、B1 の最初のスライドで確かめます。事実として扱いません。M5）。スタブの検証は、呼び出し順の完全一致（setAutoCommit, rollback, commit）にせず、「Left の経路で rollback が呼ばれ、それより前の書き込みが commit されない」「成功で rollback が呼ばれない」に絞ります（doobie の Strategy の内部実装に依存しないため。M13）。

    その他のテスト（Kotlin 版と同じ）: 空のイベントは追記しない、結果が変わる場合（DecisionConflict、WeekAdvanced、DecisionsChanged、AlreadyStarted）は再評価した結果を返す、冪等（同じキー・同じ内容は保存済みの応答、内容が違えば 409）、処理の順（ロック → 認証 → 認可の前提検査 → 冪等記録の照合 → 読み込み → handle → 追記・投影。認可が冪等照合より先）、失効した資格の再送は 403、冪等記録は成功だけ、制約ごとの再試行・再照合、周辺ストアに書かれイベントに含まれない、永続化の失敗で受理済みと表示しない、ログ・計測のラッパーが結果を変えず、ログに表示名・資格が含まれない（LogRecord に項目が無いことの型の検査）。処理の順の検査は、呼び出し順を記録するテスト用のポートで行います。

    案 内容 評価
    A ST4 のとおり、全体の文 85%・分岐 75%、domain の文 97% をゲートにする。team の行 80% の floor は、scoverage の文の率が 85% を超えることで満たすものとみなす ST4・ADR と整合する。「文 85% なら行 80% を満たす」は仮定で、成り立たない。反例: 1 行に 9 文を書いた行（長い for や 1 行の連鎖）が 1 行だけ実行され、残りの 1 行・1 文は実行されない場合、文は 9/10 = 90% だが、行は 1/2 = 50%。文の率は、1 行に多くの文を詰めた行を過大に評価する。実測で関係を確かめるまで、floor を満たしたと言わない
    B team の規約に合わせ、全体は文 80% だけをゲートにし、分岐と層ごとは目安にする team の規約の数値と一致するが、指標が行でなく文のまま（A と同じ仮定が残る）。Kotlin 版・ST4 より緩い

    限界（ガイド §9.4）: Scalafix の DisableSyntax.regex は文字列のパターンで、import の別名やラッパーの中の呼び出しを見逃す。意味（遷移表の許可の漏れ、法則、IO を実行する場所）は検査できない。Wart の名前とメッセージは WartRemover の版で変わりうる。

    層ごとのルールセット（設計判断 STT3）¶

    ルールは、sbt のプロジェクトごとに設定を分けて外す範囲を明示します（ガイド §9.4）。

    層（sbt のプロジェクト） ルールセット 外してよいもの
    domain 全ルールを有効（最も厳格）。純粋性の DisableSyntax を含む なし
    application 全ルールを有効 なし
    adapterHttp・adapterPersistence 全ルールを有効。境界の都合で必要なものだけ外す 例: 外部ライブラリの例外（PSQLException）の型の判定が IsInstanceOf・AsInstanceOf に当たる場合に限り、その Wart。外すルールと範囲は ADR に記録（当たるかは未確認）
    app 境界として扱う IOApp の run で IO を実行する部分（unsafeRun* の禁止は適用外）。println は使わない
    テスト（ステップ定義を含む） scalac のオプションと Scalafmt は有効。WartRemover は適用しない（ガイド §9.4「テストには適用しない」）。Scalafix の DisableSyntax はテストのソースにも有効にし、unsafeRun* だけテストの境界として許す。統合テストの準備と検証の SQL は、.transact( を直接書かず、テストの補助の入口（TestTx など。テストのソースの 1 ファイル）を通す。除外はこの補助のファイル 1 か所だけで、テストの本体からの .transact(・xa.trans・FC.commit は禁止（scalafix:off も使わない。N-H3。案） 外し方は Test / scalacOptions ~= (_.filterNot(_.startsWith("-P:wartremover")))（Test / wartremoverErrors := Seq.empty では外れない。確認した事項 10）。Thread.sleep は外さない（IO.sleep と TestControl 相当の仮想時間を使う。後者は未確認）

    緩和はプロジェクト単位で、@SuppressWarnings は使いません。外したルールの新規違反は、その層では検出されなくなります。この粗さは、人の承認が要ります（記録は ADR-001 の引き継ぎ表の 011 の行の緩和の記録。Scala 版での承認は未取得）。

    範囲（N-H4。ユーザーの決定、2026-11-25）: 検証用の CI（check ジョブ 1 本。Scalafmt、コンパイル -Werror、WartRemover、Scalafix、テスト、カバレッジ）は U1 の約束に含めます。 B1 の受入条件の「CI が落ちる」は、この check ジョブで判定します。AWS 環境と、デプロイ用のワークフロー（インフラの SI5 のうち deploy 側）、ステージングへの自動反映は後回し（U5）です。 team の規約は「main の merge で staging へ自動反映」を求めるため、自動反映を持たない間の例外は、ADR に記録して人が承認します（ADR-001 は別担当。承認を得るまでは規約との衝突が残る）。U1〜U3 の間は実際の研修に使わないため、この例外が研修に影響することはありません。

    B1 の受入条件（未確認の前提を、観察できる形にする）¶

    未確認の前提は、「B1 で確認」だけでなく、合否の基準と、成り立たなかったときに見直す対象を書きます。B1 の範囲は、ウォーキングスケルトンに必要なものに絞り、残りは後の Bolt に移します（範囲の確定は planning-releases で行う）。

    前提 合否の基準（観察できる形） 成り立たなければ
    Fiber の取消と ROLLBACK STT4 の測定: 取消から ROLLBACK までの時間と、その間のロック・接続の状態を記録する。失敗の経路の明示の ROLLBACK で、ロックと接続が一定時間内に解放される SBD2・SBD4 の見直し（明示の ROLLBACK を唯一の手段にする。取消の保険を外す）

    scoverage 統合テストの計測が合算される、しきい値を割ると失敗する（後者は確認済み）、domain だけ高いしきい値にできる（K16。設定できなければ全体のしきい値だけにし、domain の 97% は目安のまま。N-H6）、XML の文の行番号から行率を算出でき、行 80% で失敗にできる（案 C。算出スクリプトのテスト（M7）が通る） 層ごとの目標を目安にとどめ、全体だけをゲートにする。行を出せなければ、文の率での代替を team の「行 80%」とみなしてよいかを、人が再度決める
    ScalaCheck の操作列 Events.apply の腕を 1 つ消すと、性質テストが落ちる。生成列の分類（M19）の下限を判定できる Gen の合成で自前に書く

    契約テストのスキーマ検証 応答・リクエストを openapi.yaml のスキーマで検査でき、未宣言の項目を検出できる。仕様と実装を意図的にずらすと CI が落ちる 別の道具、または自前の検査
