    インフラストラクチャアーキテクチャ - ビールゲームシミュレーション（Scala 版）¶

    概要¶

    本書は、beer-game-scala の実行環境と配信の構成を定義します。ADR-001 により、beer-game-kotlin のインフラ（beer-game2 の構成を踏襲）を正本として引き継ぎ、Scala 版で変わる点だけを定めます。docs/ を設計の正本とします。実装コードも、インフラのコードも、まだ存在しません（アプリの置き場は apps/beer-game-scala を予定）。

    引き継ぐ構成は、CloudFront の単一オリジン（静的ファイルは S3、/api/* は ALB）、ECS Fargate、RDS for PostgreSQL 18、ECR、Terraform（リモートの状態・環境ごとに分離・モジュール化）、GitHub Actions の OIDC、ステージング自動・本番承認とブルー/グリーン、構造化ログとメトリクス（EMF）、合成監視、アラームです。非同期・キューは使いません（Kotlin 版と同じ）。Scala 3 は Kotlin と同じく JVM 上で動くため、JVM に由来する設計（ヒープ、起動の遅さ、SIGTERM、ウォームアップ）は Kotlin 版を引き継ぎます。

    変わるのは、次の点です。

    • ビルド: Gradle から sbt（マルチプロジェクト）へ。成果物の作り方（配布物）は未決。
    • コンテナ: JRE のイメージは同じ（Temurin 25）。依存の JAR とアプリの JAR を別の層に分ける方法が、Gradle の配布から sbt のものに変わる（sbt-native-packager の採否は未決）。
    • データベースの接続: JDBC + HikariCP から doobie の HikariTransactor（用途別。ST8）へ。ロールを用途別に分けるのは同じ。
    • ローカル開発の DB: ローカル開発だけ H2 の PostgreSQL モード（ユーザーの決定、2026-11-25。ST9）。本番・ステージングでは起動時の検査で H2 を拒否し、配布（本番イメージ）から H2 を除外する。H2 の依存の導入は承認待ち。
    • CI/CD: 検証の手順が sbt になる。Scala 版専用のワークフローを新設する（team の規約）。検証用の CI（check ジョブ 1 本）は U1 に含める（N-H4）。加えて、統合テスト（PostgreSQL 18）と @api の受け入れの CI 実行も U1 の約束に含める（D1。AI が推奨案で決め、ユーザーが承認した（2026-11-25））。デプロイは「設計」のみで、ワークフローは、再開するときに Unit を決めるまで作らない（L2）。
    • Terraform: Scala 版専用に複製して出発する案（SI4。提案）。

    アプリは バックエンド、フロントエンド、運用は 運用要件 を参照してください。

    範囲（ユーザーの決定、2026-11-25。N-H4・N-H8・M19）: 実装として約束するのは U1〜U3 です。U1〜U3 の間は、実際の研修には使いません（検証・事例用）。 本書のうち、U1 で約束するのは、検証用の CI の範囲です（ジョブの本数ではなく検証の範囲。D1）。check ジョブ 1 本（Scalafmt、コンパイル、WartRemover、Scalafix、テスト、カバレッジ）に加え、統合テスト（PostgreSQL 18、Testcontainers）と @api の受け入れテストの CI 実行を含みます（R-H2 の案 (a)。check に含めるか、別ジョブ integration・acceptance を U1 に足すかは案で、人が決める。D1 はAI が推奨案で決め、ユーザーが承認した（2026-11-25））。これにより、ADR-001 の「例外の間の条件」（統合と受け入れを CI で実行）と、ADR-012 のコンプライアンス（CI で Undefined・Pending があれば失敗）が U1 で果たせ、adapter-persistence の文 90% の目安（統合を合算する前提）とも整合します。AWS 環境（Terraform、ECS、RDS、CloudFront など）、デプロイ用のワークフロー（SI5 のうちデプロイとロールバックの側）、ステージングへの自動反映、本番運用、復元訓練は後回しです。「後回し（U5）」は AI の整理で、Unit 定義ではステージングは U1（US6.2）にあるため、「後回し（再開するときに Unit を決める）」とします（L2）。team の規約は「main の merge で staging へ自動反映」を求めるため、自動反映を持たない間の例外は、ADR に記録して人が承認します（ADR-001 は別担当。承認を得るまでは、規約との衝突が残る。team 規約が beer-game-scala に及ぶかの確認と、例外の project.md の ## Scope Overrides への記録は、人の承認の場で行う。M1・D5。AI は project.md を編集しない）。以降の AWS・デプロイの記述は、再開するときの設計です。研修に使い始める前提の時期は「U4 と U5 の判断の後」で、再開（U5 の着手）の条件として、運営者との合意（依頼文言・15 分・研修中の原則。運用要件 のパターン 18）を 1 つ置く案です（M17。承認を得ていない）。

    本書の位置づけと確認の範囲¶

    • 本書で確認したこと: Kotlin 版・Rust 版のインフラ設計と、既存の .github/workflows の Kotlin 版・Rust 版のジョブ構成を読み、Scala 版で変わる点を洗い出しました（2026-11-25）。版は 技術スタック の記載のみを使います。
    • 確認していないこと: コンテナのビルドと実行、起動モード、SIGTERM の振る舞い、起動時間、メモリ、sbt の配布物の作り方、Terraform、CI/CD は、すべて未実装・未検証です。実行イメージの実在（eclipse-temurin:25-jre-noble）は、Kotlin 版が 2026-11-15 に確認した値の引用で、本書では再確認していません。

    Kotlin 版の「ローカルの開発環境と H2 の拒否」を、Scala 版に読み替えて引き継ぎます（ST9。ユーザーの決定、2026-11-25）。

    • 実行する DB は DB_KIND=postgres|h2（既定は postgres）で選ぶ。ローカル開発では h2 を選べる。
    • 本番・ステージングでの H2 の拒否: AppConfig.load が、APP_ENV が本番・ステージングのとき、DB_KIND=h2、または JDBC の URL（DB_URL）が jdbc:h2: で始まる設定を起動前に拒否し、起動に失敗する（許可リスト方式。足りない設定と同じ終了の経路。Kotlin 版の同じ検査を引き継ぐ。DB_KIND だけの検査では、DB_KIND=postgres のまま URL を H2 にした設定を止められない。M4）。環境（local・test・ステージング・本番）× DB_KIND × URL の種類の全組み合わせを単体テストで確かめる。Terraform のタスク定義も DB_KIND=postgres を固定で渡す案（二重の防御。AWS は未適用）。
    • H2 は単一プロセスでしか有効でない（プロセス内のロックと通知。ST9）。2 つ目のプロセスを拒否する手段（H2 のファイルのロックなど）を検討する（未決事項 14。M4）。
    • 配布からの H2 の除外: sbt の H2 の依存（com.h2database:h2。必要なら doobie-h2）は、開発用の構成（sbt の独立した設定、または開発用の起動プロジェクト）だけに置き、配布物（本番イメージの JAR の集合）に含めない。構成の具体（sbt の設定名、sbt run と Test のクラスパスに残す範囲）は B1 で確定する（未確認）。イメージの lib に H2 が無いことを、イメージの検査で確かめる。
    • H2 のドライバが無い環境で DB_KIND=h2 を選んだ場合も、起動に失敗する（本番・ステージングは、拒否の検査とドライバの欠落の二重の防御になる）。
    • 起動の失敗（終了コード 70）や設定の誤り（78）の使い分けは、下の終了コードのとおり。

    設定の環境変数（APP_ENV、CREDENTIAL_KEY、IDEMPOTENCY_KEY、RESPONSE_KEY、DB_URL、DB_USER、DB_PASSWORD、PORT、HOST、ALLOWED_ORIGINS、COMMAND_MAX_ATTEMPTS、MIGRATE_ON_START）は、フロントエンドの E2E の案内と手順書の差分を減らすため、Kotlin 版と名前を揃える（提案。DB_KIND を含む）。E2E 用のレート制限をゆるめる設定（TS 版の AUTH_RATE_LIMIT_PER_MINUTE に当たるもの）の名前も、SF2 に含めて揃える（L3。E2E が参加・復帰の専用の制限に当たらないようにする。本番・ステージングでは、ゆるめた値を受け付けない検査を、H2 の拒否と同じ AppConfig.load に置く案。承認を得ていない）。AppConfig.load が全項目の誤りを ValidatedNec で集め、失敗なら、足りない設定の名前だけをログに出して終了する（終了コードは Kotlin 版と同じ 78 を第一候補。未決）。

    起動モードと終了コード¶

    同じイメージを、CMD（引数）のモードで切り替えます。Kotlin 版の表（モード、終了コード 0・1・64・70・78）を引き継ぎます。

    モード 内容 終了
    api 常駐。SIGTERM で新しい要求の受付を止め、SSE を閉じ、追跡している Fiber（Supervisor）の完了を待つ 下の SI3
    migrate マイグレーションを適用して終了 成功で 0
    retention 保持削除の掃引を 1 回行って終了 放棄したゲームがあれば 1、掃引の失敗は 70
    rebuild-projections [ゲーム ID ...] 投影を events から作り直す（省くと全ゲーム。ゲームごとに排他のアドバイザリロック） 再構築できなかったゲームがあれば 1、一覧が読めなければ 70、形が不正な ID は 64
    verify-projections 投影が、イベントから作り直した結果と一致するかを検査する（日次。投影は変えない） 不一致があれば 1
    不明なモード 使い方を示す 64

    終了コードの意味（0 成功、1 一部失敗、64 使い方の誤り、70 起動の失敗、78 設定の誤り）は sysexits の慣例で、Kotlin 版と同じです。起動の失敗（70）は、H2 のドライバの欠落（DB_KIND=h2 のとき）や、接続の失敗などに当てます。モードを CMD で渡し、上書きできる形は、Kotlin 版の実装に倣う案で、人の確認が要る（未決）。

    設計判断¶

    SI1〜SI5 は、AI が起草した案で、ユーザーの承認を得ていません。

    SI1: 配布物の作り方¶

    上の「配布物の作り方」の表のとおり。A（sbt-native-packager）、B（sbt の標準の機能と自前の Dockerfile）、C（fat JAR）。未決で、B1 で比較して人が決める。

    SI2: タスクのサイズ¶

    案 内容 評価
    A（初期案） 1 vCPU / 2 GiB。測定で見直す JVM のヒープ、メタスペース、スレッドの余裕を確保できる見込み（Kotlin 版の ID2 と同じ）。コストが増える
    B 0.5 vCPU / 1 GiB コストが小さい。ヒープと GC の余裕が少なく、再生と JIT の負荷で応答が揺れるおそれがある。cats-effect の実行基盤のスレッド数も CPU 数に連動する

    数値は、実測の前の初期案です。負荷試験で、再生の所要時間、GC の停止時間、ヒープの使用量を測って決めます。

    SI5: Scala 版専用の CI とデプロイのワークフローを新設する（提案）¶

    案 内容 評価
    A（提案） Scala 版専用のワークフローを新設する（CI 1 本、デプロイとロールバック 4 本） 既存の Kotlin 版・Rust 版・beer-game3 のワークフローに触れない。重複するが、独立して動かせる（team の規約）
    B Kotlin 版・Rust 版のワークフローに、Scala 版のジョブを足す ファイルは増えない。パスのフィルターと変数が複雑になり、他の版の CI の失敗が波及する。既存の .github の編集で、確認必須

    提案: A。共有する web・ui のジョブの重複は、運用で許容するか、共有のワークフロー（workflow_call）に切り出すかを、人が決める（未決）。

    前提と見直しの条件¶

    • 常時 2 タスクで足りる前提: 同時に進行するゲームが少数。負荷試験で、JVM の起動とヒープ、cats-effect の実行基盤を含めて確認する。
    • キューを再導入する条件: 削除以外の非同期処理が必要になった場合。
    • 非同期の投影へ移す条件: 同期投影が書き込みの性能を圧迫する場合。
    • ネイティブイメージを検討する条件: 起動時間またはメモリが、運用の設定で吸収できなくなった場合。
    • WAF の導入: 攻撃の兆候、またはセキュリティ要件の強化があった場合。
    • doobie が 1.0 の安定版、または http4s が 1.0 の安定版になった場合（アップグレード計画。技術スタック）。
