    非機能要件定義 - ビールゲームシミュレーション（Scala 版）¶

    概要¶

    本書は、beer-game-scala の非機能要件を、測定できる形で定義します。docs/ を正本とします。実装コードはまだ存在せず、Scala 版の性能・メモリ・起動時間の実測値はありません。

    ADR-001 により、beer-game-kotlin の非機能要件（84 件。beer-game2 の 69 件 + Kotlin 版で追加した 15 件）を正本として引き継ぎ、Scala の言語とツールで変わるものだけを見直しました。Scala は Kotlin と同じ JVM（JDK 25 を第一候補）で動くため、Rust 版と違い、ウォームアップ・ヒープと GC・起動時間に関する要件は読み替えずに継続します。

    • すべての ID を維持しました（削除はありません）。要件定義の NFR-01〜NFR-12 は変えません（要件定義）。
    • 凡例は Kotlin 版と同じです。継続は Kotlin 版と内容が同じ、変更は ID は同じで内容を Scala 版に合わせて変えた、新は Scala 版で追加した要件です。
    • 数値目標は、運営者と合意する前提の提案です。Kotlin 版で提案した数値も、Scala 版の実測で見直す前提で、実測のない数値を Scala 版の都合で厳しくも緩くもしていません（設計判断 SN2）。
    • 新しく加えた要件は 4 件（NF-SC1〜NF-SC4）で、合計 88 件です。NF-C は Kotlin 版で「容量・同時実行」に使われているため、Scala 固有の追加は NF-SC としました（ADR-001）。

    本書の位置づけと確認の範囲¶

    • 継続の要件は、本文を Kotlin 版と重複して持たず、要約と ID の対応だけを示します。要件の正本の文言は Kotlin 版の表です。
    • 変更・新の要件は、本書に全文を書き、本書を正本とします。
    • 確認したこと（2026-11-25。リポジトリの外の使い捨てのプロジェクト。sbt 1.13.1、Scala 3.7.4、doobie 1.0.0-RC12、ローカルの Docker の postgres:18.6）:
    • NF-SC2 の前提: doobie の transact は、ConnectionIO が例外なく完了すれば、値が Left でも COMMIT する。FC.rollback を挟むと残らない（データモデル の検証）。トランザクションの境界（commit・rollback の呼び出し）は、スタブの Connection を渡した Transactor.fromConnection で、DB なしに記録できる（テスト戦略 の確認した事項 8）。
    • NF-SC4 の道具: cats-laws + discipline-munit で MonoidTests が走り、empty を壊した実装は 4 件の法則で落ちる（確認した事項 3）。
    • NF-O7 の道具: sbt-scoverage 2.4.4 が文と分岐の率を出し、しきい値を割ると coverageReport が失敗する。行の独立した指標は無い（確認した事項 4）。
    • NF-O8 の道具: scalac のオプション、WartRemover 3.6.3、sbt-scalafix 0.14.10 が Scala 3.7.4 で動く（確認した事項 9〜11）。
    • NF-S20（追記専用）・NF-S16（連鎖削除）: Rust 版が PostgreSQL 18.6 で SQL として実測した結果を引用します。Scala 版の接続・権限のないロールからは未確認です。
    • それ以外の要件は、すべて未検証です。
    • Kotlin 版の実装の経緯（B3・B6・B15 の実測の注記）は引き継ぎません（Scala 版の値ではないため）。

    品質特性の優先順位と SLO の要約¶

    Kotlin 版と同じです。 優先順位は、1 機能の正確性・信頼性（整合性）、2 セキュリティ、3 性能効率性・使用性、4 保守性・観測性、5 可用性（SLO）、6 拡張性・移植性。SLO は、月間可用性 99.5%、完全停止の検知 1 分以内、RPO 0（確定済み週）、RTO 15 分、入力確定（サーバー側）p95 1 秒以内、週確定から全画面への反映 p95 2 秒以内、保持期限後の削除（期限到達の 99% を 24 時間以内）。

    ES + CQRS と Scala で変わる点¶

    ES + CQRS による変化（再生による書き込み時間、ストリームの版の一意制約と自動再試行、同期投影、投影の再構築、追記専用、個人情報の分離、イベントの互換）と、JVM による変化（起動、ウォームアップ、ヒープ）は Kotlin 版と同じで、要件もそのまま引き継ぎます。Scala の言語・ツールで変わる点は次のとおりです。

    観点 Kotlin 版 Scala 版 関係する要件
    失敗の扱い Either の左。永続化の失敗は境界で左に変換 業務の失敗は Either、IO の失敗は想定外に限る（ガイド ADR-050）。永続化の失敗（例外）は境界で AppFailure.Persistence に写す NF-R9
    トランザクションの終わり ブロックが Left を返したら ROLLBACK doobie は Left でも COMMIT する。Tx.rollbackOnLeft で ROLLBACK を明示（SBD2） NF-SC2（新）、NF-R5
    非同期とキャンセル コルーチン。NonCancellable で COMMIT/ROLLBACK Fiber の取消。execute を Supervisor で切り離し、失敗の経路は ROLLBACK を明示（SBD4） NF-SC1（新）、NF-R3、NF-R5、NF-R9
    純粋性の守り detekt の ForbiddenMethodCall、Gradle のモジュール domain は cats-core だけに依存、WartRemover・Scalafix NF-SC3（新）、NF-O8
    代数構造 使わない（Arrow の Raise） Monoid[TeamTotals]・Functor[RoleMap] を使い、法則をテストする（SD6） NF-SC4（新）
    検証 zipOrAccumulate ValidatedNec + mapN NF-S10
    静的解析・整形・カバレッジ detekt・PMD・ktlint、Kover（行・分岐） scalac のオプション・WartRemover・Scalafix・Scalafmt、scoverage（文・分岐） NF-O7、NF-O8、NF-S13
    実行環境の観測 JVM のヒープ・GC・スレッド・Dispatchers.IO の飽和 JVM のヒープ・GC・スレッド（同じ）+ cats-effect の実行基盤（計算用・ブロッキング用のスレッドプール）の飽和 NF-O12
    DB のクライアント JDBC + HikariCP doobie（ConnectionIO）+ HikariCP（doobie-hikari）。マイグレーションは Flyway（同じ） NF-O3、NF-C5、NF-O11
    ローカル開発の DB H2 を許す 同じ（H2 の PostgreSQL モードを許す。ST9。ユーザーの決定、2026-11-25。導入は承認待ち）。本番・ステージングでは拒否。NF-S20・NF-S18 は H2 版では守られず、PostgreSQL の統合テストでだけ検証する NF-S20、NF-S18 の検証範囲

    性能要件¶

    JVM のウォームアップ・ヒープ・起動に関する NF-P1・NF-P15〜NF-P18 は、Kotlin 版のまま継続します（Scala も JVM のため）。Kotlin 版の数値は Kotlin の実装についての提案値で、Scala の実装の実測で見直します（SN2）。計測の方法（JMH か自前か）は実装開始時に決めます（JMH を Scala から使う場合の道具は未確認）。

    継続する要件（要約。正本は Kotlin 版）¶

    ID 要約

    新しい要件（全文）¶

    ID 要件 測定方法 扱い
    NF-SC1 キャンセル安全性: クライアントの切断（ルートの Fiber の取消）、切り離した処理の想定外の失敗、プロセスへの SIGTERM、COMMIT の前の失敗のいずれでも、(1) トランザクションが部分更新を残さない（COMMIT されるか、全体が ROLLBACK される。これは PostgreSQL が保証する）、(2) 失敗の経路では ROLLBACK を明示し、ロックと接続が一定時間（初期値は B1 で測って決める）以内に解放され、プールに返った接続はトランザクション外の状態である、(3) コマンドの処理（execute）は、切断されても最後まで実行され（COMMIT の途中で止まらない）、結果が返らなかった要求は、同じ Idempotency-Key の再送で保存済みの応答を得る（元の処理が実行中の再送は、完了を待って同じ応答を返す）、(4) SIGTERM では、新しい要求を止め、SSE を閉じ、追跡している Fiber の完了を、stopTimeout より短い上限で待ってから終了コード 0 で終わる DB の統合テスト（失敗の経路の明示の ROLLBACK とロック・接続の解放時間、Fiber の取消、Supervisor による隔離、タイムアウト後の COMMIT と再送、実行中の再送、想定外の失敗、シャットダウン、安全網の設定。テスト戦略 の STT4） 新
    NF-SC2 Left の ROLLBACK: 書き込みを伴うトランザクションは、Left（業務の失敗・追記の競合・再試行の上限）を返す経路で、書き込み（追記・投影・周辺ストア・冪等記録）を一切残さない。doobie は Left でも COMMIT するため、すべての書き込みのトランザクションが Tx.rollbackOnLeft を通る execute の性質（成功は COMMIT だけ、競合の再試行、上限で RetryExhausted、業務の失敗は ROLLBACK して追記しない）のテストと、実 DB で Left の行が残らないこと。.transact の直接の呼び出しの禁止の検査（方式は未決） 新
    NF-SC3 純粋性と依存の制限: domain の外部依存は cats-core だけとし、時計・乱数・識別子の生成・cats.effect・doobie・http4s・circe の参照を持たない。WartRemover と Scalafix の違反は 0 件、ベースラインなし、理由なしの抑制なし CI の検査。規約違反のコードを置くと CI が落ちることを、最初のビルドの受入条件にする（テスト戦略） 新
    NF-SC4 代数構造の法則: ドメインで使う Monoid[TeamTotals]（結合律・単位元）と Functor[RoleMap]（恒等則・合成則）は法則を満たし、法則を破る実装をテストが見分ける cats-laws + discipline-munit（または全パターンの列挙）。empty や map を壊した実装が落ちること 新

    NF-SC1・NF-SC2 は、設計判断 SBD2〜SBD4（バックエンドアーキテクチャ）の前提に依存します。NF-SC2 の「Left でも COMMIT する」ことと FC.rollback の効果は確認しましたが、Fiber の取消時に doobie が ROLLBACK して接続を返すか、Supervisor の追跡、ember の切断時の挙動は未確認です。確認できなければ設計を見直すことを、NF-SC1 の受入条件に含めます。待ちの上限とロック・接続の解放時間の数値は、B1 で測って決めます。

    「継続」と「変更」は、Kotlin 版に対する扱いです（beer-game2 に対する扱いではありません）。

    beer-game-kotlin からの変更¶

    ID Kotlin 版 Scala 版 理由
    NF-R9 永続化の失敗は Either の左として境界で扱う IO の失敗（例外）を境界で AppFailure.Persistence に写す。業務の失敗は Either、IO の失敗は想定外に限る 言語・ガイド（ADR-050）の違い
    NF-S10 zipOrAccumulate による検証 ValidatedNec と mapN による全件の誤りの集約 ライブラリの違い（SD3）
    NF-S13 Gradle の依存関係の検査、detekt sbt の依存関係の検査（選定未決）、scalac のオプション・WartRemover・Scalafix ツールの違い
    NF-O7 行 85%、分岐 75%（Kover） 文 85%、分岐 75%（scoverage。暫定）。team の行 80% との関係は人が決める 計測の指標が違う（STT2）
    NF-O8 detekt、ktlint scalac のオプション、Scalafmt、WartRemover、Scalafix ツールの違い
    NF-O12 JVM のヒープ・GC・スレッド・Dispatchers.IO の飽和 JVM のヒープ・GC・スレッド + cats-effect の実行基盤の飽和 実行基盤の違い
    NF-SC1（新） （なし。NonCancellable による実装の方針だけ） キャンセル安全性を要件にし、検証する Fiber の取消というキャンセルの意味（SBD4、STT4）
    NF-SC2（新） （なし。ブロックが Left を返したら ROLLBACK する実装） Left の ROLLBACK を要件にする doobie は Left でも COMMIT する（SBD2。確認済み）
    NF-SC3（新） （なし。detekt の ForbiddenMethodCall と Gradle のモジュール） 純粋性と依存の制限を要件にする 検査の方式が違い、CI の受入条件にするため（SD5、ST3）
    NF-SC4（新） （なし） 代数構造の法則を要件にする ガイド第 6 章・§8.4（SD6）

    削除した要件はありません。 上記以外（NF-P1〜NF-P20、NF-R の他、NF-S の他、NF-O の他、NF-C、NF-U）は Kotlin 版と同じです。

    設計判断¶

    Kotlin 版の設計判断 N-1〜N-3 との対応¶

    ID Kotlin 版の決定 Scala 版の扱い
    N-1 投影の遅延は、同期投影により 0。非同期の目標は条件付き 引き継ぐ
    N-2 JVM の起動とメモリは、実測してから目標を固める 引き継ぐ（JVM のまま。SN2）
    N-3 ロールバックのためのイベントの互換を、デプロイの要件にする（読める版を先にリリース） 引き継ぐ（NF-O11）

    Scala 固有の判断 SN1〜SN3¶

    SN1〜SN3 は、AI が起草した案で、ユーザーの承認を得ていません。

    ID 判断
    SN1 Scala 固有の追加要件は NF-SC とし、4 件（NF-SC1〜NF-SC4）を新設する。NF-C は Kotlin 版の容量・同時実行で使用済みのため使わない（ADR-001）
    SN2 JVM に由来する要件（NF-P1・NF-P15〜NF-P18・NF-O5 ほか）は、読み替えずに継続する。数値の目標は Kotlin 版の提案値を引き継ぎ、Scala の実測で見直す（実測前に厳しくも緩くもしない）
    SN3 カバレッジのゲートは scoverage の文・分岐とし（NF-O7）、team の行 80% との関係は人が決める

    SN1: NF-SC の 4 件を新設する¶

    案 内容 評価
    A（採用の提案） キャンセル安全性、Left の ROLLBACK、純粋性と依存の制限、代数構造の法則を、測定できる要件にする 設計判断（SBD2〜SBD4、SD5、SD6）の前提が、CI と受入条件で観察できる形になる。要件が 4 件増える
    B 設計判断のまま（要件にしない） 要件が増えない。前提が壊れても、要件の違反として検知されない
    C NF-R・NF-O の番号を続けて足す カテゴリの中に収まる。Scala 版の差が番号から分からなくなる。Kotlin 版・Rust 版と番号がずれる（Rust 版は NF-R18・NF-S22 を足した）

    SN2: JVM の要件は継続する¶

    Rust 版の RN1 は、JVM の要件を実行環境に読み替えましたが、Scala 版は JVM のままなので、読み替える対象がありません。Kotlin 版の数値は Kotlin の実装についての提案値で、実測のない値です。Scala の実装でも実測のない値は、同じ提案値のまま上限として引き継ぎ、実測後に見直します。

    未決事項¶

    1. 数値目標（SLO、保持、容量、資格の有効期間）を、運営者と合意する（Kotlin 版と同じ）。
    2. NF-P2 の扱い: Kotlin 版は p95 2 秒。Rust 版は 2026-11-23 に、現行の画面が SSE を使わず 3 秒間隔のポーリングであることを理由に 4 秒へ再定義した（ユーザーの承認）。Scala 版は同じ画面（beer-game-web）を共有する。同じ再定義を適用するか、2 秒のまま SSE を実装するかを、人が決める。
    3. Scala 版の実測: NF-P15・NF-P16・NF-P17・NF-P18・NF-P19 の目標値は、すべて提案で、Scala の実測で見直す。計測の道具（JMH の採否）は未選定。
    4. SBD2〜SBD4 の前提の確認（B1）: 取消時の ROLLBACK、Supervisor の追跡、ember の切断時の挙動、シャットダウンの待ち方。Left の COMMIT と FC.rollback の効果は確認済み。
    5. NF-O7 の基準（SN3、STT2）: 文を行とみなす仮定と、team の行 80% の floor との整合を人が決める。
    6. NF-O12 の取得方法: cats-effect の実行基盤の指標と、HikariTransactor の接続プールの使用率の取り方。
    7. NF-S13 の依存関係の脆弱性検査の道具（選定未決。Dependabot か Renovate かも未決）。
    8. ローカル開発の DB（ST9）: H2 の採用は決定済み。NF-S20（追記専用）・NF-S18（観察者の権限）は、H2 版（ローカル）では守られないため、検証範囲は PostgreSQL の統合テストに限る。残る未決は、H2 の導入の承認と、B1 の最初の実測（動作範囲、性能は H2 では計測しない）。
    9. 保存回数の上限（NF-C8。最大の長さ 2000 件の根拠）、資格の有効期間の既定値、負荷試験の実施環境、追記の競合の自動再試行の上限と間隔（NF-R17。初期値 10 を引き継ぎ、Scala で再計測）、研修中の再構築の方式（NF-R15。暫定）、保持の起点（NF-S16。暫定）、出力のキャッシュ（NF-P9）。いずれも Kotlin 版の未決事項 に追従する。
    10. コンテナのメモリの割り当て（NF-P17。JVM のヒープの設定をインフラの設計と合わせて決める）と、NF-P16 の Fargate での実測。
