    Bolt 3 計画 - 役割別の振り返り¶

    概要¶

    項目 内容
    Bolt B3（リリース計画）
    Unit U4（振り返りの核）
    所要（計画） 2 稼働日
    ゲート密度 標準（構造が決まっているため。受入条件の照合と、開示の判定だけは密）
    テスト戦略 Standard。開示の判定は否定テストを先に書く
    前提 Bolt 1 の承認（終了報告）。B2（AWS）には依存しない
    状態 承認済み（2026-11-10、「承認」の一言）。実装完了。終了報告。人による実操作とキーボードの手動確認は、申告なし（未実施として扱う）

    ゴール¶

    ゲームの終了後に、需要と役割別の注文・在庫・受注残・出荷・費用を、同じ週の軸で比較できる。指標と役割を切り替えられ、グラフと同じ値の表を常に併記する。これが学習の最優先の価値（ブルウィップ効果の確認）である。

    確認したい仮説¶

    1. 役割別の週結果の行（week_role_results）で、振り返りが単純に実現できるか（リリース計画の仮説）。SQL の直接の問い合わせで足り、集約や投影の再構築が要らないか。
    2. 標準のシナリオ（需要 4 → 8）と反応的な発注で、注文の変動が上流ほど増幅して見えるか。見えなければ、データか表示のどちらかに問題がある。
    3. 手書きの SVG のグラフが、色に頼らず（線の種類・直接のラベル・表）読み取れるか。

    対象の受入条件（原文）¶

    ユーザーストーリーの US4.2 から、原文のまま転記する。B1 の学び（実装後に原文を読み返して食い違いが出た）を踏まえ、Step 1 で期待値を確定してからテストを書く。

    ID Given / When / Then（原文）
    AC4.2.1 ゲーム終了後に分析画面を開くと、需要・注文・在庫・受注残・出荷・費用を、役割別に、同じ週の軸で比較できる
    AC4.2.2 プレイ中に、終了後専用の役割別の値を取得しようとすると、開示しない
    AC4.2.3 データが 0 件の状態で分析画面を開くと、「データなし」と読み込みの失敗を区別する
    AC4.2.4 表示する指標と役割を切り替えられ、グラフと同じ値の表を常に併記する

    関連: AC2.3.5（確定の結果に役割別の値が含まれる。B1 で達成済み）。

    範囲外（後続の Bolt）¶

    観察者への開示（B8）、CSV / JSON の出力（B9）、終了の操作による途中終了（B4）、ブルウィップ比などの派生指標（下記の判断項目 6）、独自ドメインとステージングでの確認（B2 の持ち越し）。

    人の判断が要る項目（着手前の承認）¶

    # 項目 内容 提案
    1 前提の承認 Bolt 1 のゲート承認、マイグレーション 001・002 の承認 先に完了させる。B3 のスキーマ変更は無い（既存の week_role_results を読む）
    2 グラフの実装 技術スタックにグラフのライブラリは無い 手書きの SVG（依存を増やさない、色に頼らない表現を制御しやすい）。折れ線が主で、系列は最大 5 本
    3 新しい依存 @axe-core/playwright 4.14.0（開発依存。技術スタックで採用済み） 承認をお願いします。E2E で、アクセシビリティの自動検査を行う
    4 新規ファイルの作成 src/ports の読み取りのポート、問い合わせの実装、ui/src/features/review.tsx、グラフの部品、テストほか この計画の承認で、作成してよいとする
    5 開示の方針 振り返りは、ゲームが終了してから、そのゲームの進行役と参加者に開示する（観察者は B8）。終了前の要求は 403（Problem JSON）で拒否する この方針で進めます
    6 派生指標（ブルウィップ比） 要件には無い。需要の分散に対する各役割の注文の分散の比は、増幅を数値で示せる 今回は範囲外。表示の確認（仮説 2）で必要性を判断し、必要なら Should として追加する
    7 読み取りの経路 B1 の残課題: 読み取りの問い合わせも行ロック（FOR UPDATE）を取る 振り返りは、ロックを取らない読み取り専用のポート（SQL を直接）にする。ほかの問い合わせへの展開は、必要になった時点で
    8 ゲームの途中の開示（デバッグ用） 開発中に、終了前の値を見たくなる 提供しない。開示の判定は、サーバーの 1 か所（ドメインの純粋な関数）に集める

    ステップ計画¶

    各ステップは、TDD（Red → Green → Refactor）で進める。ステップの終わりが承認ゲート。テスト名には、ストーリー・受入条件の ID を含める。

    凡例: 🔵 設計・準備　🔴 Red　🟢 Green　🟡 Refactor　✅ 検証

    Step 1: 受入条件の期待値を確定する（🔵）¶

    B1 で、受入条件の食い違いが実装の後に見つかった。テストを書く前に、原文から期待値を決めて、人が確認する。

    • 1.1 AC4.2.1〜4.2.4 を、観測できる期待値（入力 → 期待する応答・画面）に書き下す（下の「期待値の案」を人が確認）
    • 1.2 テストデータの設計: 標準の需要（4 → 8）と反応的な発注（受け取った注文をそのまま発注）で simulateWeek を回し、上流ほど増幅することを手計算で確認した golden を用意する（golden は、固定の発注を simulateWeek で回して作った。上流ほど増幅することをテストで確認。手計算での照合は未実施）
    • 1.3 画面の構成（S08）と、メニュー・導線（終了後の「振り返りを見る」）の確認

    期待値の案（人が修正する）:

    AC 期待値
    AC4.2.1 終了後、GET /api/games/:id/review が 200 で、週ごとに需要と、4 役割それぞれの注文・在庫・受注残・出荷・費用を返す。画面は、同じ週の軸で比較できる
    AC4.2.2 進行中の GET …/review は 403。応答に、いかなる役割別の値・需要も含まない。他のゲームの資格は 403、資格なしは 401
    AC4.2.3 終了済みで週結果が 0 件なら、200 で空の週の一覧を返し、画面は「データなし」を表示する。取得の失敗（5xx・通信）は、別の文言で再読み込みの手段を示す
    AC4.2.4 指標（注文・在庫・受注残・出荷・費用）と役割（4 役割 + 需要）を切り替えられる。グラフの系列と、併記の表の値は常に同じ（表は切り替えに追従）。既定は、注文の推移（全役割 + 需要）

    ゲート 1: 期待値と golden を、人が確認する。

    Step 2: 時系列の組み立て（純粋な関数）（🔴🟢🟡）¶

    • 2.1 🔴 buildReview(rows) のテスト: golden（増幅の確認）、指標ごとの系列、需要の系列、週の欠落（連続）、役割の欠落は不正、費用の単位（最小単位）
    • 2.2 🔴 性質（fast-check）: 表の値 = 系列の値（切り替えても一致）、週の昇順、役割別の合計 = チームの合計（B1 の simulateWeek の性質と整合）
    • 2.3 🟢 実装（ドメインの純粋な関数。他の層に依存しない）
    • 2.4 🟡 Refactor

    ゲート 2: golden の増幅が、手計算と一致することを、人が確認する。

    Step 3: 読み取りのポートと開示の判定（🔴🟢🟡）¶

    • 3.1 🔴 開示の判定（ドメインの純粋な関数）の否定テストを先に書く: 進行中は不可、終了は可、未開始は不可
    • 3.2 🔴 ユースケースのテスト（メモリ上のポート）: 認証（資格なし 401、他のゲーム 403）、終了前 403（値を含まない）、終了後 200、0 件は空
    • 3.3 🟢 ReviewReader ポートと review ユースケース。開示の判定は 1 か所
    • 3.4 🔴🟢 PostgreSQL の実装（ロックなしの SELECT）。DB 統合テスト: week_role_results と sessions の結合、順序、0 件
    • 3.5 🟡 Refactor

    ゲート 3: 開示の判定が 1 か所にあること、終了前に値が漏れないことを、人が確認する（密）。

    Step 4: HTTP（🔴🟢）¶

    • 4.1 🔴 API 統合テスト: GET /api/games/:id/review — 終了前 403（Problem JSON、値なし）、終了後 200、資格なし 401、他のゲーム 403、相関 ID、ログに値が出ない
    • 4.2 🟢 ルートと、応答のスキーマ（zod）

    ゲート 4: API の契約を、人が確認する。

    Step 5: UI — 振り返りの画面（🔴🟢🟡）¶

    • 5.1 🔴 コンポーネントテスト（ApiClient を差し替え）: 既定（注文 + 全役割 + 需要）、指標の切り替え、役割の切り替え、表がグラフと同じ値、0 件は「データなし」、取得の失敗は別の文言と再読み込み、終了前は説明（403）、題名とフォーカス
    • 5.2 🟢 /games/:id/review（メニューに「振り返り」、終了後の画面から「振り返りを見る」）。SVG の折れ線（role="img" と要約の aria-label、線の種類、直接のラベル、設計トークンの色）。表は常に併記
    • 5.3 🟡 Refactor（グラフの部品を、系列の描画と軸に分ける）

    ゲート 5: 画面の構造、色に頼らない表現、日本語の文言を、人が確認する。

    Step 6: E2E とアクセシビリティ（🔴🟢）¶

    • 6.1 🔴 Playwright: 最終週まで進める（自動確定 + ボット、または手動）→ 振り返りを開く → 4 役割 + 需要が表示される → 指標と役割を切り替える → 表の値が一致する。進行中に直接 URL を開くと、値が出ない
    • 6.2 🔴 @axe-core/playwright: 振り返りの画面に重大な違反が無い（主要な画面にも適用できるか確認）
    • 6.3 🟢 通るまで、不足を埋める
    • 6.4 手動確認: キーボードだけで、指標・役割の切り替えと表の読み取りができる（E2E で、矢印キーによる指標の切り替えまでは自動で確認。人による手動確認は未実施）

    ゲート 6: ローカルで、実際に操作して確認する（人が操作する）。

    Step 7: 検証と終了（✅）¶

    • 7.1 npm run verify（format、lint、typecheck、カバレッジ 85/85/85/75、対応表、E2E）がすべて合格。CI（GitHub）も合格（ローカルの npm run verify は合格。GitHub の CI は push 後に確認）
    • 7.2 受入条件の対応表（scripts/acceptance-matrix.ts の対象に AC4.2.1〜4.2.4 を追加）。タグの意味が原文と一致することを、人が照合する
    • 7.3 docs/ の更新（アプリの README、手順書の「振り返りの確認」、log.md）
    • 7.4 Bolt 終了報告（bolt_3_report.md）と、判断と学び（ジャーナル）。Release 0.1 の条件の達成状況（ステージングへの自動デプロイは B2 の持ち越しのため未達）を明記する
    • 7.5 コミット（Step ごとに、意味のある単位で）

    ゲート 7（Bolt の承認）: 人が、完了条件を確認し、Bolt を承認する。

    完了条件（Definition of Done）¶

    • AC4.2.1〜4.2.4 が、テストでパスしている（テスト名に ID を含み、原文と意味が一致していると人が確認した）
    • 終了前は、いかなる役割別の値・需要も返さない（API の否定テスト、E2E の直接 URL）
    • 指標と役割を切り替えられ、グラフと同じ値の表が常にある（コンポーネントテストと E2E で一致を確認）
    • 0 件（データなし）と取得の失敗が、画面で区別できる
    • ローカルで、1 ゲームを終えて、振り返りを見られる（人が操作して確認）
    • カバレッジのゲート（85/85/85/75）を満たし、lint・typecheck・format が警告 0
    • axe の自動検査に、重大な違反が無い（キーボード操作の手動確認は未実施）
    • ログに、役割別の値・資格・表示名が含まれない
    • CI が合格している
    • コードを、人が理解して承認した（「承認」の一言で記録。確認した範囲の申告は無い）

    デモ項目¶

    1. ボット（反応的な発注）で 1 ゲームを終えて、振り返りを開く。注文の推移が、上流ほど大きく揺れる（ブルウィップ効果）。
    2. 指標を「在庫」「費用」に切り替え、表の値がグラフと一致することを示す。
    3. 進行中に、振り返りの URL を直接開くと、値が見えない。

    リスクと対策¶

    リスク 影響 対策
    終了前の値が、別の経路（SSE の通知、ほかの問い合わせ）から漏れる 高 開示の判定を 1 か所に集め、否定テストを先に書く。SSE は版の通知だけ（B1 で確認済み）
    受入条件の食い違い（B1 で発生） 高 Step 1 で期待値を確定し、人が確認してから書く。対応表の照合を、原文で行う
    増幅がデータに現れず、学習の価値が伝わらない 中 Step 1.2 で golden を手計算し、反応的な発注のボットでデモを確認。足りなければ派生指標（判断項目 6）を検討
    手書きの SVG が、小さい画面や多い系列で読みづらい 中 系列は最大 5 本、凡例ではなく直接のラベル、表を併記。狭い画面の案内は B13
    週数が多いゲーム（50 週）で、描画・取得が遅い 低 SQL 1 回で返す。性能の測定は B13（NF-P8）
    所要が 2 日を超える 中 人の検証時間を含めて計測する（B1・B2 の実績に、含めていなかった）

    完了後の流れ¶

    • Bolt 終了報告（bolt_3_report.md）、判断と学びをジャーナルへ。
    • Release 0.1 の達成状況を確認する。リリース条件のうち、「ステージングへ、main のマージで自動デプロイされ、ロールバックを確認済み」は、B2 の AWS 上の検証が前提で、未達のまま残る。AWS を使うかの判断が、Release 0.1 の完了を左右する。
    • B4（進行の継続と資格）の計画を作成し、承認を得る。
