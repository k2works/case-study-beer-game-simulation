    Bolt 2 計画 - CI/CD とステージング¶

    概要¶

    項目 内容
    Bolt B2（リリース計画）
    Unit U1 ウォーキングスケルトン（後半）
    所要（計画） 2 稼働日（外部の準備待ちを除く）
    ゲート密度 密（ステップごとに、人が検証する）
    テスト戦略 Standard。インフラは terraform validate / plan と、デプロイ後のスモークテストを「テスト」とする
    前提 Bolt 1 の承認と、マイグレーション 001・002 の承認（終了報告）
    状態 計画は承認済み（2026-11-10）。AWS へのデプロイはせず、準備のみ実施。コードと手順は用意済み。AWS 上の検証と、Step 1 の判断項目 1・2・3・5・7 は持ち越し（回答待ち）

    スコープの変更（2026-11-10、人の指示）¶

    今回、AWS へのデプロイは実施しない。準備だけ行う。 AWS に触れる操作（terraform apply、OIDC、ECR への push、ステージングの作成）は行わない。

    区分 今回（準備） 持ち越し（AWS の準備ができたとき）
    イメージ ビルドし、ローカルと CI で検証する ECR への push
    Terraform コードを書き、fmt / validate まで（plan は認証情報が要るため行わない） plan、apply
    パイプライン ワークフローを書く（手動起動のみ。AWS 向けの実行はしない）。静的検査する 実行して検証する
    ロールバック 手順とワークフローを書く ステージングでの実演
    受入条件 AC6.2.1・6.2.3・6.2.4 は、この Bolt では確認できない（ステージングが無いため） ステージングを作った時点で確認

    したがって、この Bolt の完了は「準備の完了」で、AC6.2.x の達成ではない。リリース計画の B2 は、AWS を使うまで完了にしない。

    ゴール¶

    main へのマージで、ステージングへ自動デプロイされ、スモークテストが通り、ロールバックできることを確認する。ECR、OIDC、Terraform の最小構成（ネットワーク、RDS、ECS、ALB、CloudFront、S3）、マイグレーションの自動適用を含む。

    確認したい仮説¶

    1. パイプラインと環境は、再現でき、戻せるか（Terraform を空の状態から適用でき、直前のイメージと静的ファイルの版へ戻せる）。
    2. SSE が CloudFront と ALB を通るか（アイドルタイムアウト、バッファリング、Cookie・Origin・If-Match・Idempotency-Key の転送）。通らない場合は、ポーリングで十分かを判断する。
    3. 本番用の実行形態（コンパイル済みの JavaScript、非 root、Node 26）で、B1 の挙動が変わらないか。
    4. Cookie（Secure、SameSite=Strict）と Origin の検査が、CloudFront の単一オリジン構成で正しく働くか。

    対象の受入条件¶

    ストーリー 受入条件 備考
    US6.2 AC6.2.1 main へのマージで、ステージングへ自動デプロイされ、スモークテストが通る
    US6.2 AC6.2.3 直前のイメージと静的ファイルの版へ戻せる（ステージングで確認）
    US6.2 AC6.2.4 スキーマの変更は履歴で管理され、拡張 → 互換 → 縮小の順で適用される（マイグレーションの自動適用）

    AC6.2.2（本番の承認とダイジェストの昇格）と AC6.2.5（復元の訓練）は B12。AC6.1.3（メトリクス）の扱いは下記の判断項目 6。

    範囲外（後続の Bolt）¶

    役割別の振り返り（B3）、独自ドメイン・ACM・WAF・ブルー/グリーン・本番（B12）、メトリクス・アラーム・ダッシュボード・合成監視（B11）、保持の定期タスク（B10）、秘密情報の鍵の複数の版（B4）。

    人の判断が要る項目（着手前の承認）¶

    AWS への操作は、外部連携・本番環境・費用に関わるため、承認ゲートとして人が判断する。

    # 項目 内容 提案
    1 前提の承認 Bolt 1 のゲート承認、マイグレーション 001・002 の承認 先に完了させる。未承認のままスキーマを AWS に適用しない
    2 AWS アカウントと権限 ステージング用のアカウント（または厳格に分離した領域）、リージョン ap-northeast-1、Terraform を適用する人（権限）と、GitHub から引き受ける OIDC のロール 人が用意し、AI は認証情報を扱わない。Terraform の apply は、人が plan を確認して実行（または承認）する
    3 費用 ステージングの常時費用（RDS、ALB、Fargate、CloudFront、ネットワーク） 設計は Multi-AZ・2 タスクだが、ステージングは Single-AZ・1 タスクを提案。ネットワークは、NAT ゲートウェイや VPC エンドポイントが月数十ドルかかるため、タスクを公開サブネットに置き（セキュリティグループで ALB からのみ許可）、RDS はプライベートのままを提案。本番の構成は B12 で設計どおり。概算は 手順書の骨子（未確認の概算）
    4 PostgreSQL の版 インフラ設計は RDS / CI を 17 と記載。技術スタックと B1 の実装は 18 18 に統一し、インフラ設計の記載を直す（RDS が 18 を提供していることを Step 1 で確認）
    5 GitHub の設定 Environments（staging、production）、AWS_ROLE_ARN などの変数、main への反映方法（現在の作業ブランチは develop） develop → main はプルリクエストで反映。staging は承認なし、production は必須レビュアーあり（B12 で使用）
    6 AC6.1.3 の扱い B1 計画は「B2」としたが、リリース計画は B11（観測の完成）に置いている B11 に置く（B2 が重いため）。B1 計画の記述を直す
    7 ADR-012 の承認 ECR、OIDC、ステージング自動・本番承認・ブルー/グリーン、リモートの Terraform 提案中のまま着手せず、承認してから進める
    8 新規ファイルの作成 Dockerfile、infra/（Terraform のモジュール）、.github/workflows/ の追加・変更、tsconfig.build.json この計画の承認で、作成してよいとする
    9 新規の依存・ツール node-pg-migrate を本番の依存に移す（イメージ内で実行するため）。CI に tfsec（または trivy config）、コンテナのスキャン 承認をお願いします
    10 v1 の資産 apps/beer-game/infra/main.tf（527 行）は参照のみ（ネットワークや WAF が定義の外、backend なし）。コピーしない 新しく書く

    ステップ計画¶

    スコープの変更により、各ステップの AWS に触れる項目は「持ち越し」。該当する項目に（持ち越し）と付記した。

    各ステップは、検証（テスト）を先に定義してから実装する。ステップの終わりが承認ゲートで、人が確認してから次へ進む。インフラの変更は、plan の差分を人が確認してから適用する。

    凡例: 🔵 設計・準備　🔴 検証の定義（失敗を確認）　🟢 実装　🟡 整理　✅ 検証

    Step 1: 前提の確認と見積もり（🔵）¶

    • 1.1 判断項目 1〜10 を確認し、承認を得る
    • 1.2 費用の概算を作成（ステージング。手順書の骨子。公式料金での確認と、RDS for PostgreSQL 18 の提供の確認は、人のアカウントで行う）
    • 1.3 インフラ設計の PostgreSQL の記載（17 → 18）を直した。ADR-012 の承認は回答待ち
    • 1.4 docs/operation/beer-game2/ に、AWS ステージング環境セットアップ手順書の骨子を作る

    ゲート 1: 費用、アカウント、権限、版を、人が承認する。

    Step 2: 本番用のイメージ（🔴🟢🟡）¶

    • 2.1 🔴 コンテナのスモークテスト（CI）: イメージをビルドし、PostgreSQL に接続して /ready が 200、DB 停止で 503。非 root、tsx を使わない、開発依存を含まないことを検査
    • 2.2 🟢 tsconfig.build.json、npm run build（dist/ へコンパイル）、Dockerfile（node:26-alpine、マルチステージ、非 root、HEALTHCHECK）、.dockerignore
    • 2.3 🟢 マイグレーション用の起動（同じイメージ、node-pg-migrate）。1 回限りのタスクとして実行できる
    • 2.4 🟢 UI のビルド（vite build）を、S3 に置く成果物にする。版つきのプレフィックス（コミット SHA）
    • 2.5 🟡 .github/workflows/beer-game2.yml に、イメージのビルドとスモークテストを追加

    ゲート 2: コンパイル済みで動くこと、イメージの中身（非 root、依存）を、人が確認する。

    Step 3: Terraform の土台（🔴🟢🟡）¶

    • 3.1 🔵 状態の保管先（S3 + ロック）を作る手順（ブートストラップ。人が実行）。環境ごとに分離（手順を手順書に書いた。実行は人が行う）
    • 3.2 🔴 terraform fmt -check / validate / plan を、CI で必ず実行（tfsec を含む）。差分なしを成功とする（fmt / validate / CI。plan と tfsec は持ち越し）
    • 3.3 🟢 モジュール: network（VPC、2 AZ、公開・プライベート、エンドポイント）、ecr（不変のタグ、スキャン、ライフサイクル）、secrets（接続情報、鍵）、rds（ステージング: Single-AZ、暗号化、PITR）
    • 3.4 🟢 モジュール: ecs（API サービス、マイグレーションのタスク定義、ログ）、alb（HTTPS 終端は CloudFront まで。/ready のヘルスチェック）、web（S3 非公開 + CloudFront、OAC、/api/* は ALB、Cookie・Origin・If-Match・Idempotency-Key を転送、キャッシュなし）、iam（GitHub OIDC、最小権限）
    • 3.5 🔴🟢 SSE の検証: CloudFront と ALB を通して、接続が維持され、イベントが届く（アイドルタイムアウトを設定）。届かなければ、人が判断する（ポーリングのみで運用するか）（持ち越し。コードでは、アイドルタイムアウトと転送の設定まで）
    • 3.6 🟡 変数・出力・タグの整理、環境ごとの tfvars

    ゲート 3: Terraform のコード（作られるリソース、権限、公開範囲、費用）を、人が確認する。plan / apply は人が行う（持ち越し）。

    Step 4: デプロイのパイプライン（🔴🟢🟡）¶

    • 4.1 🔴 デプロイ後のスモークテスト（拡張した scripts/smoke.ts）: /ready、作成 → 参加 → 割り当て → 開始 → 入力 → 確定、SSE の受信、SSE 遮断時のポーリング。対象の URL は環境変数
    • 4.2 🟢 ワークフロー deploy-staging: main へのマージで起動 → イメージを一度だけビルドして ECR へ（コミット SHA、ダイジェストを記録）→ OIDC → Terraform の plan / apply（ステージング）→ マイグレーション（1 回限りのタスク。失敗なら中止）→ ECS のローリング → 静的ファイルを版つきで S3 へ → CloudFront の版を切り替え → スモークテスト（ワークフローとスクリプトを書いた。手動起動のみ・AWS で未実行。terraform apply はパイプラインに含めず、人が行う。計画の「Terraform の plan / apply」から変更）
    • 4.3 🟢 concurrency（同時に 1 つのデプロイ）、失敗時の通知（ジョブの失敗）
    • 4.4 🟡 ワークフローの整理（再利用できる部分の抽出）、アクションの版を更新（Node 20 の非推奨に対応）

    ゲート 4: 認証の仕組み（OIDC のロールの信頼条件、権限の範囲）と、ワークフローを、人が確認する。

    Step 5: ロールバック（🔴🟢）¶

    • 5.1 🔴 ロールバックの検証: 意図的に壊した版（/ready が失敗する、または スキーマ互換のある変更）をデプロイし、直前のダイジェストと静的ファイルの版へ戻して、スモークテストが通る
    • 5.2 🟢 rollback-staging（workflow_dispatch）: 直前（または指定）のダイジェストと版へ戻す。マイグレーションは戻さない（拡張 → 互換 → 縮小の順で、旧アプリと互換）（書いた。AWS で未実行）
    • 5.3 ✅ デプロイ時に、ロールバックの手順を毎回確認する（AC6.2.3）（持ち越し）

    ゲート 5: 壊した版 → 戻す、の実演を、人が確認する。

    Step 6: CI の強化と終了（✅）¶

    • 6.1 CI で Playwright の E2E を実行（PostgreSQL 18 のサービス）。npm audit（本番依存）、コンテナのスキャン（CI に E2E と npm audit（本番依存）を追加。コンテナのスキャンは持ち越し。GitHub 上での実行は push 後に確認）
    • 6.2 develop → main のプルリクエストでの流れを確認（デプロイは main のみ）
    • 6.3 docs/ の更新: AWS ステージング環境セットアップ手順書、運用コマンド、ADR-012（承認）、log.md（手順書を作成。ADR-012 の承認は回答待ち）
    • 6.4 Bolt 終了報告（bolt_2_report.md）と、判断と学び（ジャーナル）。B3 以降の所要の再調整
    • 6.5 コミット（Step ごとに、意味のある単位で）

    ゲート 6（Bolt の承認）: 人が、完了条件を確認し、Bolt を承認する。

    完了条件（Definition of Done）¶

    スコープの変更により、AWS 上の確認が要る項目は未達（持ち越し）。今回の「準備」としての達成は、次の小節に分けて示す。

    準備としての達成（2026-11-10）¶

    • 本番用イメージを、ローカルで検証した（非 root、開発依存なし、マイグレーション、/ready、DB 停止で 503、鍵が無ければ起動に失敗、RDS の CA を信頼）
    • Terraform を書き、fmt と validate（認証情報なし）が通る
    • デプロイ・ロールバックのスクリプトとワークフローを書き、shellcheck・actionlint が通る（AWS では未実行）
    • smoke を拡張し（SSE の受信）、ローカルで通る
    • CI を強化した（E2E、コンテナ、Terraform、シェル、本番依存の npm audit）。GitHub 上での実行結果は push 後に確認する
    • 長期のアクセスキーがリポジトリに無い（OIDC の設計。AKIA などの鍵の検索で確認）
    • AWS 上の手順を、手順書に書いた

    持ち越し（AWS の準備ができてから）¶

    • AC6.2.1・AC6.2.3・AC6.2.4 が、ステージングで確認できている（記録あり）
    • main へのマージで、ステージングへ自動デプロイされ、スモークテストが通る
    • ロールバック（直前のイメージのダイジェストと静的ファイルの版）を、ステージングで実演し、記録した
    • マイグレーションが、デプロイの一部として自動で適用される（失敗したらデプロイを中止する）
    • 同じイメージ（ダイジェスト）を、ビルドから ECS まで通して使っている
    • Terraform を、空の状態から適用でき、plan に差分が出ない（再現できる）
    • 長期のアクセスキーが、リポジトリ・GitHub に無い（OIDC のみ）
    • CI で、format、lint、typecheck、カバレッジ付きテスト、E2E、Terraform の検査、コンテナのスキャンが通る
    • ステージングの費用が、概算の範囲に収まっている
    • コードとインフラの変更を、人が理解して承認した

    デモ項目¶

    1. develop → main のマージで、パイプラインが走り、ステージングへデプロイされる。
    2. ステージングの URL で、4 人（またはボット）で 1 ゲームを通す（SSE の通知を含む）。
    3. 意図的に壊した版をデプロイし、ロールバックで戻す。

    リスクと対策¶

    リスク 影響 対策
    SSE が CloudFront / ALB で途切れる 中 Step 3.5 で早期に検証。ポーリングで追いつく設計（B1 で確認済み）なので、機能は損なわれない
    AWS の権限・アカウントの準備が遅れる 高 判断項目 2 を最初に確認。待つ間は、Step 2（イメージ）と Terraform の validate まで進める
    ステージングの常時費用が想定を超える 中 Step 1.2 で概算を出し、Single-AZ・1 タスクで始める。使わない時間の停止を検討
    OIDC のロールの権限が広すぎる 高 最小権限で書き、ゲート 4 で人が確認。環境ごとにロールを分ける
    マイグレーションの失敗で、DB が中途半端になる 高 1 回限りのタスクで適用し、失敗ならデプロイを中止。ステージングで、先に失敗を再現して手順を確認
    Terraform の状態の破損・競合 中 リモートの状態とロック、concurrency、apply は人が実行
    所要が 2 日を超える 中 外部の準備待ちを除いて計測。B1 の実績（人の検証時間を含めていない）を踏まえ、B3 以降の見積もりを再調整

    • B3（役割別の振り返り）の計画を作成し、承認を得る。Release 0.1 は B3 の完了。
