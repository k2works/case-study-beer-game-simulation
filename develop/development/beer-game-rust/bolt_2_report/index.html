    Bolt 2 終了報告（Rust 版）¶

    項目 内容
    Bolt B2（U1。計画は bolt_2_plan）
    期間 2026-11-21（1 セッション。AI の連続実行。計画は 4 稼働日）
    状態 実装と記録は完了。人のゲート（Step 1〜10）、コードの全行理解、デモ項目の実操作は未承認・未実施。

    この報告は、実装の事実と、人が判断・検証すべき点を示すものです。承認の記録ではありません。

    承認ゲートの扱い¶

    セッションの目標（/goal U1）に従い、AI が各ステップの結果を「人の確認待ち」と記録して先へ進みました。承認されたのは、着手前の判断項目 1〜8、DDL（0002〜0005）、暫定の許可・無視（B1 の 2 件と B2 の 3 件）です（2026-11-21、ユーザー）。次は未承認・未実施です。

    • Step 1〜10 のゲート（許可リストの合意、execute と RB2 の検証、投影、ユースケース、HTTP、受け入れ、NF-P2、@ui）
    • 投影の簡略化、認証の位置、冪等記録の暗号化の扱い（下の「人の判断が要る項目」）
    • デモ項目の実操作、コードの全行理解

    認可は冪等記録の照合より先 達成 HTTP で認証 → execute の中で冪等照合。別ゲームの資格・資格なし・参加者による確定を拒否するテスト
    ログに資格・表示名を含まない。/ready が DB 未接続で 503 達成 logging.rs（相関 ID・操作・結果・所要時間だけ。資格・表示名・参加コード・本文・クエリを含まない）、http.rs

    仮説の検証結果¶

    前提 結果 記録
    RB2: execute を spawn し、失敗の経路で ROLLBACK を明示、Tx の drop は保険 成立 明示の rollback の後、同じ版への追記が約 7 ms で通る。drop（rollback なし）の後も約 8 ms で通る（sqlx 0.9.1 は drop で ROLLBACK を送る。測定は 1 回・ローカル）。execute は tokio::spawn で切り離し、待ちの上限を超えると type なしの 504、処理は継続し、同じ Idempotency-Key の再送は保存した成功の応答を返す（実 PostgreSQL で確認）
    sqlx のエラーから制約名を取る 成立 Error::Database の code() == "23505" と constraint() == "uq_events_stream_version"。実際の並行（2 タスク）で一方だけが成功
    testcontainers で postgres:18.6 を固定して起動 成立 SHOW server_version が 18.6。Docker が無いとき CI があれば失敗、無ければスキップ（件数が 0 なら失敗にする検査は B3）
    共有する web/ と features/ が Rust のバックエンドで動く（RF2） 成立（B2 の範囲） web/ は変更していない（RF3 は不要。hooks.mjs は、API の /ready が応えれば Vite を自分で起動する）。@ui 27 シナリオのうち 13 が通る（ウォーキングスケルトンを含む）。残り 14 は、停止・再開、復帰、CSV 出力、カスタム条件、観察、保持、振り返り、自動確定、共同担当（B5 以降の機能）
    テンプレート DB によるテストの分離 未確認 テストごとに別コンテナ（約 5 秒/テスト）。B3 で方式を決める

    NF-P2 の実測¶

    同期投影のため、確定の応答が返った時点で、別の参加者の状態の取得に反映されている。

    項目 p50 p95
    確定の応答まで 28.9 ms 41.8 ms
    確定から、別の参加者の取得が第 2 週を返すまで 45.7 ms 181.9 ms

    n=12、ローカル、実 PostgreSQL 18.6、ネットワークなし。画面の 3 秒のポーリングが支配的で、反映までの最大は「ポーリングの間隔（3 秒）+ 取得の所要（約 0.2 秒）」になる。方式（SSE を作る／間隔を詰める／目標を再定義する）は人が決める（実測前に変えない。RN1）。

    発見・設計への影響¶

    1. テストが見つけた実装漏れ: 冪等記録の照合 find_idempotency が PgEventStore で未実装（既定の「記録なし」）のまま、再送が別の応答になった。HTTP 越しのテストで検出して修正。
    2. 契約との食い違い: 入力の誤りの code は validation.invalid_input（最初は別名で書いていた）。Cookie は、タブの名前の Cookie を優先し、無ければ従来の bg_session を使う（ADR-020。X-Tab-Id を付けない呼び出し元が発行した資格を、付けた要求でも読む。これが無いと @ui が 403）。
    3. sqlx::migrate! の埋め込みは、マイグレーションの変更で再ビルドされない（cargo が追跡しない）。build.rs で rerun-if-changed を指定した。
    4. Rust の gherkin は ルール: を解析できず、ディレクトリ全体を渡すと実行が止まる（B14 の範囲のファイル）。許可したファイルだけを読み取り専用のリンクで並べて回避。B14 で対処が要る（共有物は変更できない）。
    5. cargo-deny は、既定では開発時の依存のライセンスを検査しない（include-dev = true が要る）。
    6. 2 本のストリームの開始: execute_start と PgGameStore（Tx を共有）で、1 つのトランザクションに追記する。メモリと実 PostgreSQL で、原子性・再試行・同時の開始で一方だけが成功することを確認。
    7. 決定の整合の性質テストは B1 で decide と evolve の不整合（同じ参加者の再参加）を見つけた。B2 でも、状態の問い合わせ・開示の規則・冪等記録は、HTTP 越しのテストで多数の食い違いを先に見つけた。

    簡略化と逸脱（人の判断が要る項目）¶

    1. 投影の簡略化: 設計の Projection(Event -> List<RowChange>) の RowChange を、SQL の文と束縛値の列で表した（純粋な関数で導き、同じトランザクションで実行）。表が増える B5 以降に型づけを見直す案。
    2. 認証を execute の外に置いた（設計は RB3: 認証は execute の中）。資格の失効の競合は B6 で、execute の中へ移す想定。
    3. 冪等記録の暗号化: 設計は応答の暗号化を求める。資格を運ぶ応答（作成・参加）は、暗号化クレート（AES-GCM など）の承認が要るため、冪等の対象外。許可リストの game-creation の 1 本目（作成の再送）が、これで外れている。承認があれば導入する。
    4. 開示の規則の置き場: 設計は application の Disclosure。いまは adapter-http の純粋な関数。共同担当（B6）で見直す。
    5. 資格をそのままブラウザセッションの Cookie 値にした（Kotlin 版は、復帰資格とブラウザセッションを別のダイジェストで持つ）。recoveryCode も未実装。B6 の範囲。契約テスト（B3）で差が出る。
    6. sessionId は gameId と同じとして扱った（契約の記述どおり）。
    7. decisionEditor・decisionSavedAt は null（共同担当、B6）。
    8. TDD の順序: Step 4 以降の多くは、テストと実装を同じ作業の中で書いた（失敗を先に確認していない）。代わりに、変異・HTTP 越しの検証で食い違いを見つけた。規約からの逸脱として、人が判断。

    人の判断が要る項目（まとめ）¶

    1. 上記の簡略化と逸脱（1〜8）、特に 3（暗号化クレートの承認）。
    2. NF-P2 の方式（SSE／間隔の短縮／目標の再定義）。
    3. RT1 の区切り（__ と allow(non_snake_case) を続けるか、単一の _ にするか）。
    4. 設計書への反映: 再参加は変化なし、testcontainers-modules の不採用、clippy・cargo-deny の設定、cucumber-rs の書き方、分岐の計測は nightly。反映すると verified の設計書が変わるため、再確認が要る。
    5. 守りの導入（git の hook、Claude Code の hook、CI の必須ジョブ）は、B3 の前に承認が要る。

    B3 への申し送り¶

    • 使える土台: beergame-domain・application（execute・ユースケース・認証・冪等）・adapter-persistence（PgEventStore・PgGameStore・投影）・adapter-http（ルーター・問題の写像・開示）・app（PgBackend・API サーバーの起動）・acceptance（許可リスト 19 シナリオ）・guards。
    • B3 で必要: 規約検査の CI（命名の検査 DS-10・対応表 DS-11・依存・緩和の承認 DS-15・17 など）、契約テスト（jsonschema の導入承認が先）、キャッシュ方式（CI が約 10 分。cargo-deny・cargo-llvm-cov を毎回ビルドしているため）、テンプレート DB による分離、追記専用権限の否定テスト、DB 統合テストの実行件数の検査（DS-13）。
    • B4 で必要: コンテナ（healthcheck サブコマンド、SIGTERM で終了コード 0、panic = "unwind" の確認）。app の main は、環境変数（DATABASE_URL・CREDENTIAL_KEY・PORT）から起動する最小。
