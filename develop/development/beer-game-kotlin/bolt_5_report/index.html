    項目 内容
    Bolt B5（U2 の最初の Bolt）。計画は bolt_5_plan
    期間 2026-11-15（連続したセッション。AI の連続実行とゲートごとの人の承認。計画は 2 稼働日。人の検証時間を含まない実績なので、所要の再調整には使わない）
    状態 実装と記録は完了（Step 0〜8）。ゲート 0〜7 は、ユーザーが 2026-11-15 に承認した（記録は bolt_5_plan の更新履歴）。ゲート 8（Bolt の承認）と B5 のコードの全行理解は、2026-11-15 にユーザーが承認した（記録は bolt_5_plan）。デモ項目の人の実操作は申告がなく、申告欄は空。「Unit U2 が完了した」とは言えない（B6〜B8 が残る）。B6 には進んでいない

    この報告は、実装の事実と、人が判断・検証すべき点を示すものです。承認の記録ではありません。

    計画の「完了条件（Definition of Done）」の各項目を、実測の根拠つきで示す（ローカルの実行）。

    完了条件 結果 根拠・注記
    AC3.1.1〜3.1.3、AC3.2.1〜3.2.5 の Gherkin が PostgreSQL 18 と H2 で green（Undefined・Pending なし） 達成（自動） @api 70 件が両方で成功、失敗 0。@ui 7 シナリオ・53 ステップが passed（H2 のバックエンド。PostgreSQL のバックエンドでの @ui は未実施）。人の実操作は未実施
    鍵のローテーションの否定テスト（旧版は期限まで有効、外すと 403） 達成 credentials.feature の 2 シナリオ、CredentialLifecycleSpec・永続化の契約・変異テスト
    失効後の再送の否定テスト（以前に成功したキーの再送は 403。保存済みの応答を返さない） 達成 application（冪等記録を検索しない）、実 DB、HTTP、受け入れ（保存の再送・復帰の再送・入れ替えで失効した旧担当者の再送）の 4 層
    期限切れ・失効・不明の資格の応答が区別されない（NF-S12） 達成 同じ 403 app.unauthorized。復帰は同じ Unauthorized。契約テストと HTTP の試験
    参加・復帰の専用のレート制限が働き、複数のインスタンスで合算される 達成（DB の窓。値は仮置き） 別の接続プール 2 つの合算を H2・PostgreSQL で確認。実環境の複数タスクでは未検証。上限 10 回・10 分は未計測の仮置き。ALB の背後の接続元は B14 で決める
    代理入力のイベントに値・操作者・役割・時刻が残る（AC3.1.2） 達成 ProxyDecisionSubmitted（値・入力者）と封筒（操作者・時刻）。受け入れの「監査履歴に…残る」
    新しいイベントが EventCodec の往復と golden に含まれ、投影が反映する。Lobby は資格のイベントを購読しない 達成 全 17 種類の golden。Projection.kt の購読の一覧は生成物で確認（資格のイベントと RoleHolderReplaced はどの投影も購読しない）
    復帰の再送（失効した復帰資格）が 403 達成 Auth.RECOVERY を冪等記録の照合より前に検証
    代理入力を含む保存回数の上限（1 役割・1 週 9 回） 達成 session.save_limit_reached（409）。受け入れのシナリオ 2 件
    契約テストと型の生成物の差分 0 達成 ApiContractSpec 13 件、api:lint・api:check

    デモ項目の実操作の申告欄（人が行う）¶

    この欄は、人が実際に操作して記入する。AI は記入していない（空のまま）。 自動の受け入れ（Gherkin）が通ることは、人が操作したことの代わりにならない。

    # デモ項目 手順の目安 自動の確認（参考） 実施日 実施者 結果（できた・できなかった・気づき）
    1 進行役が停止 → 代理入力 → 再開 進行役のコンソールで停止 → API で代理入力 → 再開 → 参加者が入力できる pause-resume.feature（@api）、pause-resume-ui.feature（@ui。停止と再開）
    2 参加者が切断 → 復帰 参加者のブラウザセッションを失う（Cookie を削除）→ 復帰の画面で復帰 → 同じ役割の画面に戻る recovery.feature（@api）、recovery-ui.feature（@ui）
    3 進行役の復帰（端末を替える） 作成時に控えた復帰コードとゲーム ID で、進行役のコンソールへ戻る recovery-ui.feature・recovery.feature（AC3.2.4）
    4 漏れた資格の失効 → 再発行 → 旧資格の再送が 403 API で失効 → 再発行 → 新しい復帰コードで復帰 → 旧資格での操作が 403 credentials.feature（失効、再発行、再送が 403）

    画面の範囲（人が確認する）: 代理入力・資格の失効・再発行の画面は無い（API だけ。B6 以降）。項目 1 の代理入力と項目 4 は、画面ではなく API（HTTP の呼び出し）での操作になる。

    仮説の検証結果（リリース計画）¶

    仮説 結果 根拠と限界
    1. 資格の設計は、漏洩時に被害を止められるか（期限切れ・失効・旧版の鍵で、規則どおり受け付けるか・拒否するか。旧版の資格は期限まで有効か） 自動テストの範囲で確認できた。ただし限界がある 参加者の漏れた資格は、失効でブラウザセッションの行の削除と復帰資格の失効が同じトランザクションで起き、再発行しても復活しない（変異テスト 5 件）。鍵のローテーションで旧版は期限まで有効、外すと 403。限界: (a) 進行役自身の資格は、失効・再発行の対象外（ゲート 1 の決定）。進行役の復帰資格が漏れたときに止める手段は、鍵の版を外すことだけ（その版の全資格が使えなくなる）。(b) 参加者の復帰コードが漏れたとき、進行役が失効させるまでは期限（30 日）まで使える。(c) 期限（24 時間・30 日）は、運営者と未合意の仮の既定値（R11）。(d) 鍵のローテーションの運用手順・Terraform の秘密の形は未整備（B14）
    2. 失効した資格の再送は 403 か 確認できた 認可を冪等記録の照合より前に置く順序を、application・実 DB・HTTP・受け入れの 4 層で否定テストした。失効と復帰の同時実行も、実 DB（PostgreSQL 18）で、ストリームの版の競合により直列化され、復帰で得たセッションも失効後は使えないことを確認した（Step 8.4b）
    3. 参加・復帰の総当たりを、タスク数に依らず抑えられるか DB に窓を持つ方式で、複数インスタンスの合算は確認できた。実環境では未検証 別の接続プール 2 つの合算、同時 24 回の連番を H2・PostgreSQL で確認。未検証: 実環境の複数タスク、ALB の背後の接続元（全利用者が同じ窓に入りうる）、負荷。上限と窓の値は根拠のない仮置き

    B5 で足したイベント（N-1 互換の確認用。本実装は B12）¶

    新しいイベント種別を足すと、旧版のアプリが読めない（N-1）。本 Bolt で足した 8 種類（全体は イベント一覧（生成））:

    ストリーム イベント 備考
    game CredentialRevoked（EV-G08）、CredentialReissued（EV-G09）、ParticipationRecovered（EV-G10）、ParticipantReplaced（EV-G12） 資格の値・表示名は含めない
    session SessionPaused（EV-S02）、SessionResumed（EV-S03）、ProxyDecisionSubmitted（EV-S06）、RoleHolderReplaced（EV-S09） 代理入力は値と入力者を含む

    これらは EventCodec の golden に含まれる。旧版が新しい種別を読めるかの検査（N-1）は未実施（B12）。冪等記録の本文の形式は v2（v1 の記録は読まない）。

    学び¶

    • 項目単位の検査: 本文の部分文字列の検索は、ランダムな ID で偶発的に一致して不安定になる。「この値がどの項目にも無い」は、構造を平らにして確かめる。変異（検査の対象を変える）で、検査が働くことを確かめる。
    • 並行の試験は、待ち合わせで状況を確実に作る: 「競合が起きるはず」を確率に頼らず、追記の直前で待ち合わせて、毎回ちょうど 1 回の競合を作る。勝者は決まらないので、両方の順で成り立つ不変条件を確かめる。
    • 生成の副作用: Gradle の計測（Kover）は、Test 型の task をすべて先に実行する。ドキュメントを書き換える task は、計測の対象から外す。
    • 人の検証が要る点を、AI の自己申告に頼らない: 8.4b の試験が最初から緑だったことも、Red を観察していないことも、そのまま記録した。
