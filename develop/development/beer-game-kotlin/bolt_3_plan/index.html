    Bolt 3 計画 - CI/CD とデプロイの定義¶

    概要¶

    項目 内容
    Bolt B3（リリース計画）
    Unit U1 ウォーキングスケルトン（後半）
    所要（計画） 2 稼働日（仮定）
    ゲート密度 標準（構造が決まっている。ただし本番環境・デプロイ設定は確認必須のため、定義のレビューは人が行う）
    アプローチ 序盤（開発戦略）。定義を、適用せずに、検証できる範囲で検証する（terraform validate、ローカルのコンテナ、スモークテスト）
    状態 定義と記録は完了（2026-11-15）。AWS には適用していない。ステップ計画（本書）は、2026-11-15 にユーザーが承認した（実装の後の事後の承認。ユーザーの選択: 「B2 と B3 のステップ計画を承認」）。人のゲート 1〜4 は、2026-11-15 に別途、ユーザーが承認した（ユーザーの選択: 「B3 ゲート 1〜4」）。ゲート 5（AWS への適用）は承認の対象外で、別ゲート（未判断）。コードの全行理解の個別の承認は、指示がなく未記録。ユーザーのゴール（U1）に従い、B1・B2 が未承認のまま、2026-11-15 に実行を開始した。結果は Bolt 3 終了報告

    範囲の線引き（重要）¶

    • AWS への適用はしない（terraform apply を実行しない。リソースを作らない）。適用・デプロイの実行は、別の承認ゲート（AWS アカウントと費用の判断）。
    • 本番環境・デプロイ設定は確認必須（プロジェクトの規約）。本書は定義の作成まで。ワークフローは、workflow_dispatch のみで、自動で起動しないように定義する。
    • 秘密情報（資格の鍵、DB のパスワードなど）は、リポジトリに置かない。AWS の Secrets Manager から注入する定義にとどめる。
    • 実行環境の制約: ローカルの Terraform は 1.5.7（設計は 1.17 以上）。AWS の認証情報はローカルに無いため、terraform plan はローカルでは実行できない見込み（validate までを、作業用の新しい Terraform で行う）。plan が通ることは、未確認として扱う。

    ゴール¶

    JVM のアプリケーションを、再現できるコンテナにし、起動モード（api・migrate、将来の retention・rebuild-projections）を定義し、ステージング・本番の AWS 構成（Terraform）と、デプロイ・ロールバックの手順を、適用せずに定義する。

    確認したい仮説¶

    1. コンテナ（マルチステージ、JRE 25）が再現でき、ローカルで api・migrate が起動し、スモークテストが通るか。
    2. JVM の起動時間は、目標（NF-P16: p95 30 秒）に収まるか。
    3. 起動時の設定の検査（H2 の拒否、秘密情報が無ければ失敗）は、コンテナでも働くか。
    4. beer-game2 のインフラ定義（Terraform）を、JVM に合わせて流用できるか。変更点は何か。

    範囲外¶

    AWS への適用、独自ドメイン・ACM・CloudFront の本番設定の完成（B14）、観測（メトリクス・アラーム。B13）、retention・rebuild-projections の実装（B11・B12。モード名の定義のみ）。

    B2 の申し送りのうち、B3 の範囲外・未実施としたもの（完了時の validating-design 軸 C で追記。計画の作成時には取り込まれていなかった）: GitHub Actions 上の実行の確認（push していない）、用途別の接続プール・所有者ロール（マイグレーション用ユーザー）・LISTEN 専用接続の配線、V101 と V102 の順序の決定、N-1 のタグ名、Kover の残り、契約テストの SSE。

    設計（4 図の確認）¶

    B3 は、新しい集約・テーブル・画面を作らない（コンテナ、Terraform、ワークフロー、運用手順書の定義）。ドメインモデル図、状態遷移図、ER 図、画面遷移図は、いずれも変わらないため、計画に図を載せない。インフラ構成の図（インフラ設計書）は、実装との差（ECS は公開サブネット、本番はローリングなど）を注記で記録した（図そのものは、人の判断が済むまで直さない）。

    進め方の注（検証による追記）¶

    Step 1 は、単体テストとスモークテストを先に書いた（Red を確認。スモークの検査項目そのものの Red はイメージが無く未確認）。Step 2・3 は定義（Terraform、ワークフロー、手順書）であり、テストを先に書く対象ではない。検証は、terraform fmt・validate、YAML の構文検証、ローカルのコンテナでのスモークテストで行った（plan・AWS での実行は未実施）。

    ステップ計画¶

    各ステップは、可能な範囲でテスト（検証）を先に書きます。ゲートは、人の確認待ちとし、承認済みとは書きません。

    Step 1: コンテナと起動モード（🔴🟢）¶

    • 1.1 🔴 コンテナのスモークテスト（api が /ready に応答、migrate がマイグレーションを適用して終了、本番相当の設定で秘密が無ければ起動に失敗、DB_KIND=h2 を拒否）を先に書き、失敗を確認する
    • 1.2 🟢 Dockerfile（マルチステージ。実行イメージは JRE 25。非 root。H2 のドライバを含めない。ヘルスチェック）と、起動モード（api・migrate。retention・rebuild-projections はモード名の定義と、未実装の旨の明確な失敗）
    • 1.3 ローカルで、コンテナをビルドして起動し、スモークテストを通す。起動時間を計測（仮説 2）。イメージの内容（H2 を含まないこと、サイズ）を確認

    ゲート 1: コンテナと起動モードを、人が確認する。状態: 人の確認待ち（承認済みではない）。

    Step 1 の結果（2026-11-15）¶

    作ったもの: apps/beer-game-kotlin/Dockerfile、.dockerignore、scripts/container-smoke.sh（恒久のスモークテスト）、app/build.gradle.kts（配布から H2 を除外）、Main.kt（未実装のモード）、MainSpec.kt（モードの単体テスト）。コミットしていない。AWS・ECR には触れていない。

    Red の確認（先に書いて失敗を確認） - 単体テスト（MainSpec に、未実装モード 2 件と、使えるモードの案内を追加）: 実装前に ./gradlew :app:test --tests 'beergame.app.MainSpec' が「8 tests completed, 3 failed」で失敗した。 - スモークテスト: Dockerfile が無い状態で ./scripts/container-smoke.sh を実行し、failed to read dockerfile: open Dockerfile: no such file or directory で失敗した。注意: スクリプトの検査項目そのもの（終了コード 78 など）の Red は、イメージが無いため確かめられていない（検査の中身は、実装後の Green で初めて動いた）。(c)(d) と未実装モードの終了コードは、単体テスト（MainSpec）でも別に押さえている。
