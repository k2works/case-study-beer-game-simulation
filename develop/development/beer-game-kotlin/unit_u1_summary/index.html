    # 事実 反映
    1 人のゲートを通さずに進めると、決めるべき仮置き（環境変数の名前、code、既定値、サイズ・猶予）が多く積み上がる。ゲートを通っていないので、AI の出力の質を測る実測が取れていない 次の Bolt では、ステップごとに人のゲートで仮置きを決めてから進む。ゲート密度の判断は、人の検証を含めた実績を取ってから
    2 設計の「想定」は、実測すると崩れることがある（H2 の動かない機能、detekt と JDK 25、SIGTERM の終了コード 143、実行イメージに curl が無い、連鎖削除は両立した） 設計の不安は、先に小さく実測する。実測の結果を、設計書の変更表と ADR に残す
    3 人の目の照合は、機械の照合の代わりにならない（B1 で手で照合した仕様に、契約テストが 7 件の不一致を見つけた） 仕様 → 契約テスト → 実装の順を、API を足す Bolt の完了条件にする
    4 静的解析のツールは JDK・Kotlin の版に強く依存する。層単位のルールの緩和は粗い 版を上げる前にツールの対応を確認する。緩和は ADR と承認を要件にする
    5 「ローカルで通った」と「CI で通る」「AWS で動く」は別の事実。定義だけの Bolt は、動く根拠が無い 達成の記述に、確認の範囲（ローカル、CI、AWS）を必ず書く
    6 AI の報告は機械で確かめる（@Suppress の grep、成果物の存在の確認） 検査を CI または Bolt の終了の標準の手順に入れる
    7 前の Bolt の申し送りは、計画に項目として取り込むか、範囲外と明記する。取り込まないと、黙って落ちる Bolt の計画の作成後の validating-design の軸 C で、申し送りを項目ごとに照合する

    9. 次への申し送り¶

    次の Unit・Bolt の候補¶

    リリース計画の順序は、B4（U4 の振り返りの核。Release 0.1）→ B5〜B8（U2・U3。Release 0.2）→ B9〜B15（Release 1.0）。「U4 の振り返り」（B4）が次。

    着手前に、次を確認してほしい。

    1. 優先度 A の #1〜#7。特に、U1 のゲートを検証するか（#1）、B2 の判定（#2）、plan の受入条件（#4）、push して GitHub Actions の実行を確認するか（#5）。
    2. B4 の前提: 参加の応答の gameId（#12。B4 は画面を含む）。契約テストの運用（仕様 → 契約テスト（Red）→ 実装 → 型の再生成 → 画面）。@ui の拡張（参加者の画面）。B4 の受入条件 AC4.2.1〜4.2.4 を、実装の前に人が Gherkin で検証する。
    3. B4 の計画: 前の Bolt の申し送りを項目として取り込む（学び 7）。計画の作成後に validating-design を実施し、着手前の記録を残す。
    4. AWS の適用は別ゲート。決まるまで、デプロイのワークフロー（push のトリガー）を有効にしない。
    5. 所要の再調整: 実績が 3 例（B1・B2・B3）で、いずれも人の検証時間を含まないため、リリース計画の所要（Release 0.1 は 2026-11-30、1.0 は 2027-01-06）は変更しない。人の検証を含めた実績を取ってから判断する。

    以降のゲート密度の判断¶

    リリース計画は、B1〜B3 を「密」、以降の Bolt を高リスクは密・他は標準とする。U1 では人のゲートが機能しておらず、密度を下げる根拠が無い。B4 は標準だが、U1 の判断（#1）が済むまでは、ステップごとに人の確認を入れることを勧める。
