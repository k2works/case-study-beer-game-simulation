    Unit U1 人のゲート確認手順（B1〜B3、Kotlin 版）¶

    この資料は、U1 のゲートをユーザーが自分で確認するための手順です。各ゲートで、何を見て・どう再現して・何を判断するかを順に示します。チェック欄はすべて空です。この資料は承認の記録ではありません。

    1. 冒頭¶

    1.1 承認の意味¶

    • ゲートの承認は、ユーザー自身がコードとテストを確認することで意味を持ちます。AI が代わりに「承認済み」と記録することはありません。
    • 2026-11-15 に、ユーザーが B1（ゲート 1〜12）・B2（ゲート 1〜6）・B3（ゲート 1〜4）を承認した。 以下の「未承認」の記述は承認前のもの。コードの全行理解の個別の承認と、AWS への適用（B3 ゲート 5）は含まれない。
    • 状態の根拠は Unit U1 総括、Bolt 1・Bolt 2・Bolt 3 の終了報告です。いずれも「人の確認待ち（未承認）」と記録されています。

    1.2 承認の記録方法¶

    • ユーザーが指示した項目だけを、指示どおりに記録します（例文は第 6 章）。指示の無い項目は「未承認」のままにします。
    • 直す判断（却下）も同じ形で記録します。理由を添えてください。ガードレールにすべきものは CLAUDE.md・PROJECT.md に反映します。

    1.3 確認の優先順位（リスクの高いものから）¶

    順 対象 理由
    1 B1 ゲート 6・7・8（集約、イベントストアと冪等、処理の順序） 下流へ誤りが膨らむ。リリース計画で「高」リスク
    2 B1 ゲート 4（golden と BR）、ゲート 3（シナリオと原文） 契約。教材とのずれは後で直しにくい
    3 B2 ゲート 3（権限と V101）、B1 ゲート 7（マイグレーション 001〜005） スキーマ・権限は確認必須
    4 B3 ゲート 2・3（Terraform、デプロイ）。AWS 適用は別ゲート 本番環境・デプロイ設定は確認必須
    5 残りのゲート 構成・道具・画面

    3.4 コードの全行理解を要するゲートの観点¶

    読む順序の目安: domain → persistence → application → adapter-http → app → web。層ごとに、テストを先に読んでからコードを読みます。

    観点 見る場所 何を確かめるか
    decide・evolve の全域性 domain/.../Game.kt、Session.kt と各 *DecideSpec・*EvolveSpec すべての（状態 × コマンド／イベント）の組が、when の else なしで網羅されているか。evolve が計算せず、イベントの内容を畳むだけか。InvalidTransition の性質テストは未実施（B2 #20）
    冪等と認可の順序 application/.../Execute.kt、IdempotencyDigest.kt、ExecuteSpec.kt、ADR-004 順序が「認可 → 冪等の照合 → 実行」であり、失効した旧担当者が以前に成功した識別子を再送しても 403 になるか（認可が先）
    版と原子性 JdbcEventStore.kt、JdbcTransactionRunner.kt、各 *Contract.kt 版の不一致で追記が失敗するか。投影の更新が同一トランザクションか。両実装（H2・PostgreSQL）で同じ契約を通るか
    権限の否定テストの意味 RolePrivilegesSpec.kt、V101__database_roles.sql 「書き込みロールが events を UPDATE・DELETE・TRUNCATE できない」等を実際に拒否されることで確かめているか（変異で 6 件が失敗した記録がある）。保証しないこと: アプリが用途別ロールの接続を使うこと（アプリは単一の接続ユーザーのまま。B3 #5、B2 #17）

    5. AWS 適用の前に確認すること¶

    AWS への適用は、本資料の範囲外の別ゲートです（terraform apply・デプロイ・OIDC・状態用 S3 の作成を含み、いずれも未実施）。確認項目の全体は Bolt 3 終了報告「AWS への適用前に人が確認すべき項目」 にあります。要点は次のとおりです。

    • 費用: Multi-AZ の RDS（db.t4g.small）、Fargate（本番 2〜4 タスク、各 1 vCPU / 2 GiB）、ALB、CloudFront、Secrets Manager 4 本ほか。月額の概算は未実施。beer-game2 でリリースが止まった原因（R10）と同じ。
    • アカウントと GitHub 側: 環境ごとのアカウント分離、OIDC プロバイダーの有無、状態用の S3、GitHub Environment（production は必須レビュアー）と変数一覧。
    • IAM とセキュリティ: デプロイロールとワークフローの突合（未実施）、公開サブネットの判断、秘密が Terraform の状態に入る点。
    • 手順の不足: ECR を先に作る適用順（手順書に無い）。適用前は、デプロイのワークフローの push トリガーを有効にしません。

    6. 承認の記録の依頼の例文¶

    記録は、ユーザーが指示した範囲だけを、指示された状態（承認・却下・保留）で行います。範囲外は「未承認」のままです。

    依頼の例 記録される範囲
    「B1 のゲート 1〜12 を承認して記録して」 bolt_1_plan.md と bolt_1_report.md と index.md のゲート 1〜12 の状態のみ。B2・B3 は変えない
    「B1 のゲート 6 と 7 だけ承認。ゲート 3 は AC1.2.5 の解釈を直す必要があるので保留として記録して」 ゲート 6・7 は承認、ゲート 3 は保留と理由。他は未承認のまま
    「判断項目 #3 は承認（domain 100%）、#4 は (a) で。記録して」 総括の #3・#4 のみ。選択した案を明記
    「B3 のゲート 2 は却下。ECS をプライベートサブネットにする方向で直して」 ゲート 2 を却下と記録し、修正の作業項目を計画に追加
