    Bolt 2 終了報告（Kotlin 版）¶

    項目 内容
    Bolt B2（U1 後半）。計画は bolt_2_plan
    期間 2026-11-14〜15（連続したセッション。AI の連続実行。計画は 3 稼働日。人の検証時間を含まない）
    状態 実装と記録は完了。人のゲート（B2 の 1〜6）は、2026-11-15 にユーザーが承認した（以下の本文は承認前の記述。記録は bolt_2_plan の変更履歴）。ステップ計画も承認済み。コードの全行理解の個別の承認は、指示がなく未記録

    この報告は、実装の事実と、人が判断・検証すべき点を示すものです。承認の記録ではありません。

    承認ゲートの扱い¶

    B2 は、ユーザーのゴール（U1）に従い、B1 のゲートが未承認のまま、B2 のステップ計画も人が承認しないまま、2026-11-14 に実行を開始しました（ユーザーの決定 4 件を除く）。ステップごとの結果は「人の確認待ち」と記録して先へ進みました。したがって、次はすべて未承認・未実施です。

    • B2 のゲート 1〜5（ルールと fixture・層ごとの緩和、Kover の実測とゲート、権限の設計と V101、CI の構成、契約テストの実装）と、Bolt の承認（ゲート 6）
    • B2 のステップ計画そのものの承認
    • コードの全行理解の承認
    • B1 のゲート 1〜12（Bolt 1 終了報告）。B2 は B1 の成果の上に積んだため、B1 が否認されれば B2 も影響を受ける
    • GitHub Actions 上の実行（push していない）

    承認されたのは、着手前のユーザーの決定（2026-11-14）だけです。

    # 決定 内容
    1 PMD の導入 承認（PMD 7.29.0）
    2 detekt 1.23.8 の JDK 25 の問題 JDK 21 専用ジョブで維持（アプリは JDK 25 のまま）
    3 契約テストの道具 候補を調べて提示し、ユーザーが選定・導入を承認した（@redocly/cli 2.78.0、networknt json-schema-validator 3.0.9、openapi-typescript 7.13.0）
    4 B1 のゲート 1〜12 未承認のまま B2 へ進む

    完了条件の達成状況¶

    計画の完了条件（bolt_2_plan）と、開発戦略・リリース計画の B2 の受入条件を合わせて、正直に記す。

    完了条件・受入条件 結果 根拠・注記
    規約違反コードを置くと CI が落ちる（detekt（JDK 21）と PMD のそれぞれ） 達成（ローカルの同じ Gradle タスク） domain に var と Instant.now を置き、PMD が 2 件、detekt の ForbiddenMethodCall が 1 件で失敗した。GitHub Actions 上の失敗は未確認
    PMD の fixture のテストが期待どおり 達成 期待 17 件と一致（pmdFixtureTest）。処理エラー・設定の誤りも失敗にする
    PMD が Kotlin 2.4 の構文を解析できる 達成（今回のコードの範囲） 5 モジュールの全ソースセットで構文エラーなし。PMD が Kotlin 2.4 の全構文を保証するとは確認していない
    detekt が Kotlin 2.4 を解析できる 達成（JDK 21 上） JDK 25 では動かないまま（ユーザーの決定で専用ジョブ維持）
    違反 0 件・ベースラインなし・@Suppress なしで全コードが緑 達成（層単位の緩和つき） PMD は 4 層とも違反 0。detekt は JDK 21 で緑。@Suppress の実使用 0、ベースラインなし。層ごとのルールセットで外したルールは、その層の新規違反を検出しない（粗い）。ADR の記録は ADR-011 に追記したが人の承認は未
    ktlint の .editorconfig の調整が実際の版で動く 未確認 ktlint は緑。ただし調整が動くことの個別の確認は B2 で記録していない（計画に項目が無かった）
    追記専用権限の否定テストが通る 達成 PostgreSQL 18 で 11 件。変異（権限を足す）で 6 件が失敗することも確認
    連鎖削除の可否の確定 達成 events に DELETE 権限が無いロールで、game_roots の 1 回の DELETE が game_id を持つ全表から消す（R6 解消。SECURITY DEFINER は不要）。PostgreSQL 18 での 1 回の実測
    Kover の合算の可否とゲートの設定の記録 達成 合算できる。全体のゲート（行 85%・分岐 75%）設定済み
    CI で domain の行 100% のゲートが有効 ローカルで達成（2026-11-15 の追補）。CI での実行は未確認 domain の行は 100%。ゲートを 100% に設定（除外・引き下げなし。テスト 54 件の追加と -jvm-default=no-compatibility）。ゲートと設定の確認は人の判断待ち（下の #1）
    API の契約テストと型の生成が CI に組み込まれ、仕様と実装をずらすと落ちる 達成（ローカル） 契約テスト 13 件。変異 6 件で失敗を確認。api:lint・api:check あり。GitHub Actions 上は未確認
    契約テストの道具の候補が提示されている 部分的 候補の提示と選定は、ユーザーとの対話で 2026-11-14 に行われた。比較表は文書に残していない（計画の 5.1 は [ ] のまま）
    Cucumber の CI への組み込み（Undefined・Pending で失敗） 一部のみ Undefined の失敗は実測（@api）。Pending は未実測。Cucumber-JS（@ui）の Undefined も未実測
    DB の統合が 1 件も実行されなければ失敗 一部のみ 検査の手順は実際の結果で合格を確認。0 件で落ちる分岐は、条件式の確認だけで未実測
    N-1 互換ジョブの雛形 達成（雛形） タグが無ければ実行せず、タグがあって本実装が無ければ意図的に失敗する。タグ名は仮（beer-game-kotlin-v*）。本実装は B12
    InvalidTransition の性質テスト（リリース計画の B2 の行） 未実施 bolt_2_plan に Step が無かった（下の軸 A）
    完了時の validating-design（不整合 0 件または人が判断済み） 未達 実施して下に記録した。人の判断待ちが残る
    コードを人が全行理解して承認 未実施 人の承認待ち
    人による実操作の申告 無し B2 はテスト基盤で、デモ項目の実操作を求める構成ではなかった。人の申告は無い

    仮説の検証結果¶

    # 仮説 結果
    1 PMD は Kotlin 2.4 を解析でき、14 ルールの fixture の期待件数（17 件）と一致するか。Gradle で実行でき、層ごとのルールセットの分割と両立するか 支持された。7.29.0 で 17 件が一致し、今回のコードの全範囲で構文エラーなし。Gradle の pmd プラグインは Java 用なので使わず、PmdCli を JavaExec で実行する。層ごとに 4 つのルールセットを分けて、違反 0。ただし層単位の緩和が粗いこと、pmdTest の実行時間が負荷下で 2〜15 分とばらつくことが残る。PMD が Kotlin 2.4 の全構文を保証するとは確認していない

    学び（以降の Bolt への反映）¶

    # 事実 反映
    1 契約テストは、B1 の「手で照合した」一致の中に、7 件の仕様の後追いの不一致を見つけた（初回は 13 件中 8 件が失敗。テスト側の誤りも 3 点あり、直した）。人の目の照合は、機械の照合の代わりにならない API を足す Bolt の完了条件に、仕様 → 契約テスト → 実装の順を維持する。仕様の後追い修正が出たら、ADR-008 の「仕様が先」に照らして理由を残す
    2 required が実装より緩い仕様（GameState.sessionId）は、応答の適合では検出できず、型の生成と typecheck で見つかった 型の生成と契約テストの二重の網を維持する。それでも網羅は保証しない
    3 Kover は既定で全 Test タスクを合算するが、統合・受け入れのソースセットのクラスが本番コードの行に入る（excludedSourceSets で外した）。ルールにパッケージで絞る filters が無く、domain の行は domain モジュールの koverVerify に置くしかなかった ゲートは測って設定する。数値を黙って下げず、事実と選択肢を記録する
    4 連鎖削除は、表の所有者の権限で参照の整合性のトリガーが動くため、events に DELETE が無いロールでも動いた。最小権限と連鎖削除は両立した R6 を解消。SECURITY DEFINER の代替は不要。ただし 1 回の実測（PostgreSQL 18）で、設計の前提の変更時は再確認する
    5 層単位のルールセットの緩和は粗い。外したルールの新規違反は、その層で検出されない ADR に残し、再検討の条件（誤検出の頻発など）を事象で決める。コードで直せるものは直す（#5）
    6 PMD の pmdTest は、負荷下で 2〜15 分とばらついた。CI の timeout-minutes に収まるかは未確認 GitHub Actions 上で実測し、必要なら PMD のジョブを分割する
    7 Flyway は、適用済みの最大の版より小さい未適用の版を既定で拒否する（V101 < V102） 永続環境の前に決める（#6）。以降のマイグレーションの番号付けの規約にする
    8 AI のエージェントが、規律に反するファイルの書き方（ruby・sed）を繰り返し試みる 権限の分類器が拒否したが、頼りにしない。指示の冒頭に置く、検査で見つける仕組みを考える
    9 規約検査（PMD・detekt）は JDK・Kotlin の版に強く依存する（detekt は JDK 21 専用、PMD の Kotlin の構文の保証は無い） 版を上げる前にツールの対応を確認する（B1 の学び #3 の継続）
    10 B1 の申し送りのうち、計画に取り込まれなかったものがあった（#20） Bolt の計画を作るとき、前の Bolt の申し送りを項目ごとに取り込むか、範囲外と明記する

    B3 への申し送り¶

    B3（CI/CD とデプロイの定義）の計画は、すでに作成されている（承認待ち）。着手前に、次を確認してほしい。

    • 判断: 上の #1〜#14。特に、domain の行 100%（#1）、層単位の緩和の承認と ADR（#3）、V101 と V102 の順序（#6）、仕様の後追い修正の確認（#2）、B3 以降を止めるかの判定（#14）。
    • 確認: GitHub Actions 上の実行（#13）。B3 は CI/CD を作るため、B2 で作ったジョブ（contract・test・detekt・pmd・web・ui・n1）の実行を、最初に確認する。action の SHA 固定（#12）。
    • 接続・権限: 用途別の接続プール（書き込み・読み取り・観察者・削除）の配線、所有者ロール（マイグレーション用ユーザー）の作り方、LISTEN の専用接続、V101 の適用の順序。
    • N-1: タグの規約（#7）。本実装は B12。
    • Kover: app の起動部の除外、分岐の揺れの測定、GitHub Actions 上の合算。
    • 契約テスト: 以降の Bolt で API を足すときの、仕様 → 契約テスト → 実装の運用。SSE の検査は B1 の範囲に無いまま。
    • 持ち越し: B1 の申し送りのうち未実施のもの（#20）、B1 の人の判断が要る項目 #1〜#16（参加の応答の gameId を含む）。

    • CI に Node の工程（web・ui ジョブ）と contract ジョブを追加した。ui ジョブはローカルで同じ手順を実行した（Playwright の Chromium、H2 のバックエンド、ポート 3100）。
