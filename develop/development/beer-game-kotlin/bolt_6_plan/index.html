    Bolt 6 計画 - 共同担当と共同入力¶

    概要¶

    項目 内容
    Bolt B6（リリース計画）
    Unit U2 進行の継続（共同担当・資格）。U2 の 2 つ目の Bolt。前は B5（計画、終了報告）。次は B7（U3。カスタム条件）
    所要（計画） 2 稼働日（リリース計画の仮定）。ステップ数に対して厳しい見込み（下のリスクと判断項目 2）。B5 の実績（1 セッション）は人の検証時間を含まず、根拠にしない
    日程（仮定） リリース計画の稼働日の目安は、累計 15 日目・2026-12-04 終了（B5 の後。B5 は B4 より先に実施済みなので、この日付は使えない）。実施日は着手時に人が決める。リリース計画の日程・進捗の更新は、人の判断待ち
    ゲート密度 密（リリース計画の「B6 は高リスク（並行性）」。ステップごとに人が検証する）。B5 のゲート 0〜8 は人が通した実績があるが、並行の試験と計測は AI の自己申告が効きにくいため、密度は下げない
    アプローチ 中盤（開発戦略）。インサイドアウト（ドメイン → 永続化・投影 → 並行の試験と計測 → アプリケーション・HTTP → UI）。仕様（contracts/openapi.yaml）と日本語 Gherkin を先に書き、契約テストを Red にしてから実装する。否定テストと並行テストを実装より先に書く（開発戦略の中盤の手順の要点）
    状態 ステップ計画は、2026-11-15 にユーザーが承認した（選択: 「計画を承認し、17 件を提案どおりに決定」）。着手前の判断項目 17 件は、同日に提案どおりに決定された（更新履歴）。ゲート 0〜8 は人の確認待ち（未承認）。 実装・コード変更は未着手。Step 0（0.1〜0.4）は 2026-11-15 に実施済み（validating-design（着手前）の結果、設計と実装の差、ベースラインの実測は本書に記録。ゲート 0 は人の確認待ち（未承認）。Step 1 以降には進んでいない）

    承認の状態について: 本書の「提案」は AI の案で、承認ではありません。承認は、ユーザーが指示した範囲だけを、更新履歴に記録します。各ゲートは「人の確認待ち（未承認）」です。

    ゴール¶

    同じ役割に複数の参加者を割り当てて（共同担当）、同じ状況・入力値・版を見ながら入力でき、同時の保存で、受理した更新を失わず、拒否された側に最新値と保存者を返すようにする。確定は、確定の根拠にした入力が変わっていないことと、週が進んでいないことを、別の理由として区別して拒否する（DecisionsChanged と WeekAdvanced）。さらに、追記の競合の再試行が、上限の中で収まるかを、実 DB（PostgreSQL 18）の並行の統合テストと計測で確かめ、再試行の上限・間隔と、アドバイザリロックによる直列化の要否（R4）を、数値の根拠つきで決める。

    確認したい仮説（リリース計画）¶

    1. 同時の保存で、更新を失わないか。 同じ役割の 2 人以上が同時に保存したとき、受理された書き込みが失われず、拒否された側は最新値と最後の保存者を受け取れるか（NF-R14）。
    2. 追記の競合の再試行は、上限内で収まるか。 現状は上限 5 回・間隔なし（COMMAND_MAX_ATTEMPTS の既定。ADR-005 は「実装開始時（B6）に競合の頻度を測って決める」としている）。リリース計画の測定基準は「RetryExhausted は 4 人同時の保存で 0 件」。
    3. （R4）再試行が集中して RetryExhausted が頻発するなら、アドバイザリロックで直列化する案は、再試行の調整より良いか。

    対象の受入条件¶

    出典は ユーザーストーリー（Kotlin 版は beer-game2 の要件を引き継ぐ）。シナリオの期待値は、原文の意味と一致させる（タグ @US・@AC）。

    ID 内容（原文の要点） 現状（実コードで確認。Step 0 で再確認）
    AC1.2.4 進行役は、同じ役割に複数の参加者を割り当てられる。各役割に 1 人以上いれば開始できる 準備中の割り当ては、すでに複数人を拒否しない（decideGame の AssignRole に既存の担当者の検査が無い。SessionData.assignments は RoleMap<Set<ParticipantId>>。startGame は各役割が空でないことだけを検査）。ただし、受入のシナリオが無い（features/ に @AC1.2.4 が無い）。要件の v1 の状態は「✗」
    AC2.1.4 同じ役割の共同担当は、同じ状況と、入力値・版を見る 状況・入力値・版は役割単位の投影で、同じ値になる見込み（Disclosure.kt の RoleStatus）。シナリオが無い。保存者は状況の応答に含まれない（decision・decisionVersion だけ）。他の役割へ開示しない否定テストが要る
    AC2.2.3 同一役割の複数の参加者が同時に更新すると、更新の競合を示し、変更を黙って失わず、最新値との差を示す ドメインの DecisionConflict は B1 から実装済み（Session.kt。版が違えば最新の DecisionEntry を返す）。HTTP の 409 の本文は最新値と版だけ（ProblemMapping.kt の entryJson）で、保存者・時刻を含まない（設計は保存者を含める。UI 設計 の S05 共同入力の競合）。シナリオ・並行の試験が無い
    AC2.2.4 共同担当の一人が入力すると、同じ役割の全員の画面に、同じ値と版が反映される API は同じ値・版を返す見込み。画面の自動更新（SSE）は未実装（B1 から。B5 終了報告「未達・未実施」）。反映の手段は判断項目 8

    対象外の受入条件だが、リリース計画の B6 のゴールに含まれる「WeekAdvanced と DecisionsChanged の区別」: 実コードで確認した事実として、ドメイン（commitWeekEvents の判定順: 週 → 根拠の版）、HTTP（ProblemMapping.kt）、仕様（openapi.yaml）、画面の辞書（web/src/api/problems.ts）、進行役の画面（ConsolePage.tsx）に、すでに実装がある。受入の Gherkin には無い。したがって B6 では「新しく実装する」でなく、シナリオで固定し、共同担当が保存した場合の挙動と、応答の中身（保存者）を確かめて補う（出典: 設計の AC2.3.1 と テスト戦略 の decideSession（CommitWeek、H6））。

    範囲外（後続の Bolt、または未割り当て）¶

    自動確定（B8。共同担当の保存で週が確定する場合を含む。ただしドメインの判定が、B8 が使える形を壊さないことを回帰で確かめる）、カスタム条件（B7）、観察者・出力（B9・B10）、削除（B11）、投影の再構築・N-1 互換の本実装（B12。新しいイベントを足す場合は一覧を終了報告に残す）、観測のメトリクス・アラーム（B13。本 Bolt の計測はテスト用の道具に限る。判断項目 11）、AWS・Terraform（B14。変更しない）。開始後の共同担当の追加（ドメインモデルの未決事項「当面は準備中だけ」。判断項目 3）。

    前の Bolt（B5）の申し送り・持ち越しの取り込み（Unit U1 総括の学び 7: 取り込まないと黙って落ちる。出典は Bolt 5 終了報告の「B6 への申し送り」「未達・未実施」「人の判断が要る項目」）:

    申し送り・持ち越し 扱い
    SaveDecision に触れる。B6 の共同入力（DecisionConflict の拡張）と、B5 で足した保存回数の上限（9 回）が同じ判定にある 取り込む（Step 2。判断項目 5）
    保存回数は意思決定の版で数える（ドメインモデルの差の表 34: 「共同入力（B6）が版の意味を変えるなら、そのとき回数を分ける」） 取り込む（判断項目 5、Step 0.3・Step 2）。提案は「版の意味は変わらない」。変わる場合だけ、回数を別の項目に分ける。拒否された保存は版を進めないので、競合で上限を消費しない（Step 2 で試験する）
    入れ替え（assignRoleAfterStart）と共同担当。B5 の入れ替えは、担当者全員が外れる設計（ゲート 3.5 で承認）で、共同担当の追加を含まない（未決） 取り込む（回帰）: 共同担当のいる役割の入れ替えで、全員の資格が失効し、写しが更新されることを確かめる。Step 0.3 で確認した事実: 受入の Gherkin（credentials.feature）に共同担当を含むシナリオは無い。ドメインの Kotest（ReplaceRoleSpec「共同担当（小売店に参加者 4 と 6）… 担当者全員が外れ、失効する」）にはある。追加は判断項目 3
    試験の道具: credentialConcurrencyContract の待ち合わせ（Barrier・racing）、項目単位の検査 leafValues()・integerValues() 取り込む（Step 4・3）。並行の試験は待ち合わせで状況を確実に作り、勝者に依存しない不変条件で判定する。開示の否定は項目単位で確かめ、変異で検査が働くことを確かめる
    N-1 互換: 新しいイベントを足す前に方針を確認 取り込む: 既定は新しいイベントを足さない案（判断項目 7）。足す場合は一覧を残す
    生成物: 足すイベント・用語に @EventSpec・@Term を付ける（付け忘れ・設計書との不一致は試験が落ちる） 取り込む（足す場合。用語「共同担当」の追加を提案。Step 8）
    UI: 代理入力・資格の失効・再発行の画面を B6 で足すか。S03 の案内「進行役に復帰コードの再発行を依頼」を実行する画面が無い 人の判断待ち（判断項目 9）。提案は範囲外
    @ui が PostgreSQL のバックエンドで未実施（H2 のみ） 取り込む案（Step 8。共同担当の @ui は PostgreSQL でも 1 回実行する。判断項目 9 と合わせて人が決める）
    SSE（自動更新）未実装。AC2.2.4 の画面への反映 人の判断待ち（判断項目 8）
    進行役自身の資格の失効・再発行の扱い（B5 判断項目 6）、復帰の入口（#7）、マイグレーション番号 006 の予約（#8）、ALB の背後の接続元（#9） 範囲外（B6 の受入条件に無い）。ただし、本 Bolt でスキーマを変える場合は、006（B11 の予約）と衝突しない番号にする。
    資格の期限・参加の上限・参加コードの試行の窓の仮置き（R11） 範囲外。共同担当の人数と保存回数の上限（9 回）は運営者との合意が要る（非機能要件 の NF-C8）。仮の既定値で進め、合意の前に永続環境へ出さない（判断項目 4・5）
    U1 総括の持ち越し H5（@US・@AC タグの整合検査、@Suppress・ベースラインの機械検査、生きたドキュメントの公開の導線、Kover の残り、SSE の契約テスト） 範囲外・未割り当て（B16 へ送る決定。割り当ては人が決める）。ただし、新しいシナリオのタグ（@US・@AC）は手で整合させる（機械検査が無いため）
