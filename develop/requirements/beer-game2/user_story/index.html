    ユーザーストーリー - ビールゲームシミュレーション（v2）¶

    概要¶

    本書は、システムユースケース から導出した、開発可能な粒度のユーザーストーリーと受入条件を定義します。ストーリーと受入条件は、人と AI の間の契約です。リリース計画・イテレーション計画は docs/development/beer-game2/ で別に扱います。

    docs/ を正本とします。beer-game（v1）のユーザーストーリー（11 件）を出発点に、v2 で改訂しました。

    • v1 の受入条件ごとに、v1 の状態（実装の状況）を記録しています。✓ は引き継ぎ、△ と ✗ は v2 で満たすべき不足です。
    • v2 の範囲（共同担当、カスタム条件、観察者、自動確定）と、運用・観測性のストーリーを追加しました（新規は「v1: 新規」）。

    凡例（v1 の状態）¶

    記号 意味
    ✓ v1 で実装済みで、コードで確認した
    △ v1 で一部実装（不足を備考に記載）。v2 で満たす
    ✗ v1 で未実装。v2 で満たす
    新 v2 で追加した受入条件・ストーリー

    アクター（ペルソナ）¶

    ペルソナ 対応するアクター ストーリー上の呼び方
    P1 進行役 進行役 進行役
    P2 生産役 工場 生産役
    P3 流通役 一次卸、二次卸、小売店 流通役
    P4 観察者 観察者 観察者
    P5 運用担当（新） システムを運用する担当者 運用担当

    生産役と流通役は、同一役割に複数人が参加できます（共同担当）。

    Epic 1: ゲーム準備と参加¶

    US1.1 ゲームを作成する¶

    として 進行役、したい JSD 準拠またはカスタム条件でゲームを作成したい、なぜなら 同一条件の学習セッションを再現できるからだ。

    • 優先度: Must
    • 依存: なし
    • ユースケース: UC-01（要件: FR-01、FR-18、BR-13、BR-14、SR-05）

    受入条件:

    ID Given / When / Then v1 の状態
    AC1.1.1 有効なキット準拠設定で作成すると、参加コード付きの準備中ゲームが一度だけ作成される ✓
    AC1.1.2 無効な需要系列を保存しようとすると、作成せず、対象週と修正内容を表示する △（対象週を示さない）
    AC1.1.3 準拠値を変更した設定で作成すると、「カスタム」としてゲームに記録し、画面と出力で明示する △（画面の区別だけで、保存しない）
    AC1.1.4 進行役が、初期在庫、遅延、費用単価、公開範囲を変更して作成できる。値は、範囲外のとき、作成せず修正内容を表示する ✗
    AC1.1.5 最終週は 1〜50 の整数に限る △（画面は 52 まで）
    AC1.1.6 自動確定の有効・無効を設定できる。既定は無効 新

    INVEST: 単独でデモ可能。条件入力は交渉可能。検証可能。

    US1.2 参加して役割を受け取る¶

    として 生産役または流通役、したい 参加コードでロビーに入り、役割を受け取りたい、なぜなら アカウント登録なしで学習を始められるからだ。

    • 優先度: Must
    • 依存: US1.1
    • ユースケース: UC-02、UC-03、UC-04（要件: FR-02、FR-03、FR-16）

    受入条件:

    ID Given / When / Then v1 の状態
    AC1.2.1 有効な参加コードで表示名を入力すると、ロビーに参加し、復帰資格が保存される ✓
    AC1.2.2 無効または終了済みのコードで参加しようとすると、参加せず、理由を表示する △（理由の表示の内容は要確認）
    AC1.2.3 4 役割のいずれかに参加者がいない状態で進行役が開始すると、開始を拒否し、不足している役割を示す ✓
    AC1.2.4 進行役は、同じ役割に複数の参加者を割り当てられる。各役割に 1 人以上いれば開始できる ✗
    AC1.2.5 1 人の参加者に、複数の役割を割り当てようとすると、割り当てず理由を示す ✓

    INVEST: 参加と割当ての価値を一貫して提供する。

    US1.3 観察者を招待する（新）¶

    として 進行役、したい 観察用の招待を発行して観察者を招きたい、なぜなら 参加者と区別して、学習条件を壊さずに観察してもらえるからだ。

    • 優先度: Should
    • 依存: US1.1
    • ユースケース: UC-16（要件: FR-17、BR-17、SR-07）

    受入条件:

    ID Given / When / Then v1 の状態
    AC1.3.1 進行役が観察用の招待を求めると、参加コードと別の招待が発行される 新
    AC1.3.2 進行役以外が求めると、発行しない 新
    AC1.3.3 観察用の招待で参加した人は、役割を持たず、状態を変更できない 新
    AC1.3.4 進行役が招待を失効させると、その招待での新しい参加はできなくなる 新

    INVEST: 招待の発行と失効に限定した、独立したストーリー。

    Epic 2: ウォーキングスケルトン（1 週の意思決定）¶

    US2.1 役割別の週次状況を確認する¶

    として 生産役または流通役、したい 自分の役割に許された週次状況だけを見たい、なぜなら 情報制約を保って意思決定できるからだ。

    • 優先度: Must
    • 依存: US1.2
    • ユースケース: UC-05（要件: FR-04、FR-05）

    受入条件:

    ID Given / When / Then v1 の状態
    AC2.1.1 プレイ中に自分の役割の画面を開くと、自役割の在庫・受注残・入荷・受注だけを表示する ✓
    AC2.1.2 他の役割のリソース ID を UI または API で取得しようとすると、権限エラーとして、値を返さない ✓
    AC2.1.3 小売店以外の役割が、将来の需要または当週の需要を取得しようとすると、開示しない ✓
    AC2.1.4 同じ役割の共同担当の参加者は、同じ状況と、入力値・版を見る 新

    INVEST: 読み取り範囲に限定した独立ストーリー。

    US2.2 発注または生産要請を決定する¶

    として 生産役または流通役、したい 当週の数量を入力・確定したい、なぜなら 分散した意思決定でサプライチェーンを運営できるからだ。

    • 優先度: Must
    • 依存: US2.1
    • ユースケース: UC-06、UC-07（要件: FR-07、FR-16、BR-10、BR-15）

    受入条件:

    ID Given / When / Then v1 の状態
    AC2.2.1 未確定の当週に非負整数を入力すると、流通役は発注、生産役は生産要請として保存できる ✓
    AC2.2.2 負数・小数・空白を確定しようとすると、入力を保持し、修正方法を示す ✓
    AC2.2.3 同一役割の複数の参加者が同時に更新すると、更新の競合を示し、変更を黙って失わず、最新値との差を示す △（版の競合の検出のみ。共同担当が無い）
    AC2.2.4 共同担当の参加者の一人が入力すると、同じ役割の全員の画面に、同じ値と版が反映される 新

    INVEST: 意思決定の操作に限定。

    US2.3 1 週を原子的に確定する¶

    として 進行役、したい 4 役割の入力後に、1 週を一度だけ確定したい、なぜなら 手作業のミスなしに、正しい状態を残せるからだ。

    • 優先度: Must
    • 依存: US2.2
    • ユースケース: UC-08（要件: FR-05、FR-06、FR-08〜FR-10、BR-02〜BR-09、BR-12）

    受入条件:

    ID Given / When / Then v1 の状態
    AC2.3.1 4 役割の入力が完了して週を確定すると、12 ステップ順の遅延・入荷・出荷・在庫・受注残・費用が、一度の取引で保存される ✓
    AC2.3.2 同じ確定要求が重複または同時に届くと、結果と費用は一度だけ計上される ✓
    AC2.3.3 確定中に障害で処理が中断すると、部分更新を残さず、再試行できる △（実装は満たすが、障害の注入テストが無い）
    AC2.3.4 同一の初期状態と意思決定から再計算すると、全状態と費用が一致する ✓
    AC2.3.5 確定の結果に、役割別の値（注文、在庫、受注残、出荷、費用）が含まれ、振り返りと出力で使える 新

    INVEST: ウォーキングスケルトンの核心の価値。

    US2.4 週を自動で確定する（新）¶

    として 進行役、したい 4 役割の入力がそろったら、週が自動で確定されるようにしたい、なぜなら 確定の操作を待たせず、進行を滑らかにできるからだ。

    • 優先度: Should
    • 依存: US2.3、US1.1（AC1.1.6）
    • ユースケース: UC-08（要件: FR-18、BR-16）

    受入条件:

    ID Given / When / Then v1 の状態
    AC2.4.1 自動確定が有効なゲームで、4 役割の入力がそろうと、週が一度だけ確定される 新
    AC2.4.2 自動確定が無効なゲームでは、入力がそろっても確定されない（進行役の確定を待つ） 新
    AC2.4.3 一時停止中は、入力がそろっても確定されない。再開後に、そろっていれば確定する 新
    AC2.4.4 自動確定と、進行役の手動の確定が同時に起きても、結果と費用は一度だけ計上される 新
    AC2.4.5 進行役は、いつでも自動確定を無効にできる 新

    INVEST: 自動確定の条件と保証に限定したストーリー。

    Epic 3: 継続と復旧¶

    US3.1 停止・代理入力・再開を管理する¶

    として 進行役、したい セッションを停止し、必要な代理入力のあとに再開したい、なぜなら 不在者や一時的な中断があっても、学習を継続できるからだ。

    • 優先度: Must
    • 依存: US2.3
    • ユースケース: UC-09、UC-10（要件: FR-11、FR-15、NFR-09）

    受入条件:

    ID Given / When / Then v1 の状態
    AC3.1.1 一時停止中に参加者が新規の確定をすると、拒否し、既存の入力を失わない ✓
    AC3.1.2 進行役が代理入力して確定すると、操作者・役割・時刻・値を監査履歴に残す △（値が残らない）
    AC3.1.3 再開すると、最後の確定済みの週から入力できる ✓

    INVEST: 運営の継続性に限定。

    US3.2 切断後に同じ役割へ復帰する¶

    として 生産役、流通役または進行役、したい 一時切断のあとに、元の役割（進行役は進行のコンソール）へ戻りたい、なぜなら 確定済みのデータと作業を失わずに継続できるからだ。

    • 優先度: Must
    • 依存: US1.2
    • ユースケース: UC-14（要件: ASM-05、NFR-05、NFR-06）

    受入条件:

    ID Given / When / Then v1 の状態
    AC3.2.1 有効な復帰資格で再接続すると、同じゲームと役割の最新の状態を表示する ✓
    AC3.2.2 無効または削除済みの資格で再接続すると、復帰せず、進行役への確認方法を示す ✓
    AC3.2.3 複数のタブで一方が週を確定すると、他方は古い応答を適用せず、最新の状態を反映する ✓
    AC3.2.4 進行役が画面を再読み込みまたはブラウザを再起動しても、資格で同じゲームの進行コンソールへ戻れる ✗
    AC3.2.5 資格には有効期限があり、進行役は、漏れた資格を失効させて再発行できる ✗

    INVEST: 復帰の経路だけを縦に貫くストーリー。

    Epic 4: 観察と振り返り¶

    US4.1 公開範囲内でプレイを観察する¶

    として 観察者、したい 進行状況とチーム合計を見たい、なぜなら 役割別の非公開情報を壊さずに、学習を観察できるからだ。

    • 優先度: Should
    • 依存: US1.3、US2.3
    • ユースケース: UC-13（要件: FR-04、FR-17、SR-07、BR-17）

    受入条件:

    ID Given / When / Then v1 の状態
    AC4.1.1 プレイ中に観察画面を開くと、現在週・ステップ・完了状況・在庫・受注残・注文のチーム合計を表示する △（ステップは要確認）
    AC4.1.2 観察者が役割別の値や未来の需要を取得しようとすると、権限エラーとして、値を返さない ✓
    AC4.1.3 集計の対象が 1 役割だけで、逆算により個別の値が漏れる状態では、合計を非表示にする ✓
    AC4.1.4 観察用の招待で参加した観察者だけが、観察画面を開ける（招待の無い人は開けない） ✗
    AC4.1.5 観察者は、入力、確定、進行の操作をできない 新

    INVEST: 読み取り専用で独立。

    US4.2 終了後に Bullwhip Effect を振り返る¶

    として 進行役、参加者または観察者、したい 需要と全役割の時系列を比較したい、なぜなら 遅延と意思決定が変動を増幅する過程を説明できるからだ。

    • 優先度: Must
    • 依存: US2.3
    • ユースケース: UC-11（要件: FR-13、SR-03、SR-06）

    受入条件:

    ID Given / When / Then v1 の状態
    AC4.2.1 ゲーム終了後に分析画面を開くと、需要・注文・在庫・受注残・出荷・費用を、役割別に、同じ週の軸で比較できる △（全役割の合計のみ）
    AC4.2.2 プレイ中に、終了後専用の役割別の値を取得しようとすると、開示しない ✓
    AC4.2.3 データが 0 件の状態で分析画面を開くと、「データなし」と読み込みの失敗を区別する ✓
    AC4.2.4 表示する指標と役割を切り替えられ、グラフと同じ値の表を常に併記する △（切り替えが無い）

    INVEST: 学習の成果を完結させるストーリー。

    US4.3 結果を CSV / JSON で出力する¶

    として 進行役、したい 全記録を CSV と JSON で出力したい、なぜなら 表計算での比較と、システム間の再利用ができるからだ。

    • 優先度: Should
    • 依存: US4.2
    • ユースケース: UC-12（要件: FR-14、RP-01）

    受入条件:

    ID Given / When / Then v1 の状態
    AC4.3.1 終了済みのゲームで CSV と JSON を出力すると、設定（「カスタム」の別を含む）・全週・全役割・意思決定・費用・履歴を識別できる ✗（合計の推移のみ）
    AC4.3.2 同じゲームで両形式を比較すると、数量と費用が一致し、スキーマ版が記録される ✓
    AC4.3.3 出力の一部が失敗して処理を完了できないと、部分的な結果を完全な出力として示さない ✓

    INVEST: 分析 UI と独立してテストできる。

    Epic 5: 保持と品質¶

    US5.1 保持期限後にデータを削除する¶

    として 進行役、したい ゲーム記録の保持期間を設定したい、なぜなら 不要な参加者のデータを残さないためだ。

    • 優先度: Must
    • 依存: US1.1
    • ユースケース: UC-15（要件: NFR-07）

    受入条件:

    ID Given / When / Then v1 の状態
    AC5.1.1 未設定でゲームを作成すると、保持期間を 90 日とする ✓
    AC5.1.2 保持期限に達して削除処理すると、ゲーム記録・履歴・復帰資格を削除し、実行結果を記録する △（イベント履歴と冪等記録が削除対象外）
    AC5.1.3 削除中に障害が起きて再試行すると、半分の状態を完了と扱わず、最終的に一度だけ削除される ✓
    AC5.1.4 削除の完了後に、そのゲームの ID を含む行が、どの表にも残らない ✗
    AC5.1.5 バックアップに削除前のデータが残る期間が、保持方針に明記され、運営者へ示される ✗

    INVEST: 保持の運用として独立。

    Epic 6: 運用と観測性（新）¶

    US6.1 障害と性能の劣化を検知する（新）¶

    として 運用担当、したい 研修中の停止や性能の劣化を、すぐ知りたい、なぜなら 運営者へ連絡し、復旧に取りかかれるからだ。

    • 優先度: Must
    • 依存: US2.3
    • ユースケース: なし（要件: NFR-11、NFR-09、非機能要件）

    受入条件:

    ID Given / When / Then v1 の状態
    AC6.1.1 リクエストの処理のたびに、構造化ログ（相関 ID、操作、結果、所要時間）が出力され、資格、表示名、非公開の値を含まない ✗
    AC6.1.2 予期しないエラーが起きると、相関 ID つきで記録される ✗
    AC6.1.3 応答時間、エラー率、確定の競合、アウトボックスの遅延、SSE の接続数が、メトリクスとして得られる ✗
    AC6.1.4 準備のヘルスチェックが、データベースに接続できないタスクを、負荷分散の対象から外す ✗
    AC6.1.5 研修中に、主要な操作が 1 分間成功しないと、通知される ✗
    AC6.1.6 週結果の重複や、不変条件の違反が起きると、通知される ✗

    INVEST: 運用に必要な観測に限定した、イネーブラーのストーリー。

    US6.2 安全にリリースし、元に戻し、復元する（新）¶

    として 運用担当、したい 本番へ自動でデプロイし、問題があれば直前の版へ戻し、障害時にはデータを復元したい、なぜなら 変更を楽に安全に行えるからだ。

    • 優先度: Must
    • 依存: US6.1
    • ユースケース: なし（要件: NFR-12、運用要件）

    受入条件:

    ID Given / When / Then v1 の状態
    AC6.2.1 main へのマージで、ステージングへ自動でデプロイされ、スモークテストが通る ✗
    AC6.2.2 本番へのデプロイは、手動の承認のあとに、同じイメージ（ダイジェスト）で行われる ✗
    AC6.2.3 問題を検知した場合、直前のイメージと静的ファイルの版へ戻せる ✗
    AC6.2.4 スキーマの変更は、履歴で管理され、旧アプリと互換の順（拡張 → 互換 → 縮小）で適用される ✗
    AC6.2.5 復元の訓練で、RPO 0 と RTO 15 分を実測し、記録する ✗

    INVEST: 変更管理と復旧に限定した、イネーブラーのストーリー。

    v1 の不足と v2 での扱い¶

    v1 で、受入条件を満たしていなかったものを、優先度の高い順に示します。すべて v2 の受入条件として引き継ぎました。

    # v1 の不足 関連する受入条件 v2 の扱い
    1 振り返りと出力が、役割別でなく全役割の合計だけ AC4.2.1、AC4.3.1、AC2.3.5 週確定の結果に役割別の値を含める（最優先）
    2 ログ・メトリクス・ヘルスチェックが無い US6.1 運用の前提として最初から実装する
    3 観察者という独立した立場が無い AC4.1.4、US1.3 観察用の招待を実装する
    4 保持期間後の削除に漏れがある AC5.1.2、AC5.1.4 削除対象を網羅し、残らないことをテストする
    5 代理入力の履歴に値が残らない AC3.1.2 履歴に入力値を含める
    6 「カスタム」を保存せず、初期値・費用を変更できない AC1.1.3、AC1.1.4 カスタム条件を実装する
    7 同一役割の共同担当が無い AC1.2.4、AC2.2.3、AC2.2.4 共同担当を実装する
    8 進行役の復帰手段と、資格の失効・再発行が無い AC3.2.4、AC3.2.5 実装する
    9 自動確定が無い US2.4 実装する
    10 デプロイが未実装 US6.2 CI/CD を実装する
