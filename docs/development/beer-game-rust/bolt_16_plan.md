## 現状の確認（読み取りで確かめた事実）

- **画面（`web/`）は Kotlin 版と共有**で、Rust のバックエンドに対する `@ui` は **27/27 通過**（ヘルプ・狭い画面の案内・アクセシビリティ・復帰・観察者・出力・保持を含む）。つまり、**Rust 固有の画面の作業は無い**。ブラウザは、手元に Firefox・WebKit の Playwright 版がある（Edge・実機の Safari は無い）。
- **`@api` は 158/159**。残り 1 件は Kotlin 版の JVM のヒープのシナリオ（Rust 版に JVM が無い。B14 で、許可しないと決めた）。
- **NF-P2（確定から反映 p95 2 秒以下）**: B2 の実測で、確定から別の参加者の取得が新しい週を返すまで p50 46 ms・p95 182 ms（n=12）。**現行の画面は 3 秒間隔のポーリングで、反映までの最大は「3 秒 + 約 0.2 秒」**。つまり、**目標（p95 2 秒）を満たさない**（推定。B2 の方式の判断は、いまも人に渡されたまま）。SSE は、API にも画面にも**無い**。
- **NF-P18（投影の再構築）**: B13 の外挿で、1 ゲーム SESSION 1000 件の再構築は約 4〜6 秒で、**目標（p95 1 秒以下）を超える見込み**（実測は 72 件まで）。
- **サイズ・メモリ**: 実行イメージ 46.4 MB（B4 の実測）。**メモリ（RSS）は未実測**（手元の macOS では `/proc` が無く、アプリの RSS メトリクスも出ない）。Kotlin 版との比較は未了。
- **性能の計測は、Rust 版では未実施**（NF-P1・P3・P9・P15・P16・P17 など）。Kotlin 版には、`PerformanceSpec` 相当の自前の計測がある。
- **NFR 検証表**: `docs/design/beer-game-rust/test-strategy.md` にある（`non-functional.md` の NF は約 100 件）。**B16 の結果の列は無い**。

## ステップ計画（各ステップの終わりで人のゲート）

1. **読み取り**: Kotlin 版の B15（`PerformanceSpec`、NFR 検証表の結果の列、`release_readiness.md`、`unit_u6_summary.md`）と、Rust 版の NFR 検証表（`test-strategy.md`）を読み、**Rust 版の NF の一覧（約 100 件）を、検証の方法ごとに分ける**（自動の試験・計測・手動・AWS 上のみ）。
2. **判断 1〜3 の承認（人のゲート）**。
3. **Red（先に書く）**: 性能の計測テスト（縮小した規模で、上限つき）を、実装の前に書く。**測るだけで、アプリのコードは変えない**（判断 2 で最適化を選んだ場合は、別の Bolt）。
4. **性能・負荷の計測**: NF-P1（75 並行の定常）、NF-P3（週確定のサーバー処理）、NF-P9（50 週 × 4 役割の出力）、NF-P15（ストリームの再生）、NF-P18（再構築。1000 件）、NF-C1 系。**ネットワーク・ブラウザ・複数タスクを含まない**ことを明記。
5. **起動時間・メモリ（NF-P16・P17）**: Docker のコンテナで、プロセスの開始から `/ready` が通るまで、負荷の下の RSS を実測する。**イメージのサイズ**を再確認する。
6. **ブラウザ行列**: Playwright の Chromium・Firefox・WebKit で、共有の `@ui` を実行する（既存の設定の `BROWSER` 環境変数）。Edge・実機の Safari は**未実施**。
7. **NFR 検証表の記録**: `test-strategy.md` に「B16 の結果」の列を足す（達成／未達／未測定／未実施と短い根拠）。他の列は変えない。
8. **Release 1.0 の準備状況**: `release_readiness.md`（B1〜B16 のゲートの状態、人の判断項目、AWS 適用の前提、リリース 0.1／0.2／1.0 の完了条件に対する現状）。
9. **品質ゲート・記録**: `just backend-check`、`just acceptance`、`just ui-acceptance`（Node 26）、`terraform fmt -check`、報告書、`index.md`、`mkdocs.yml`、`docs/log.md`、`okf:check`。
10. **コミット・push・CI**（区切りごと）。

## 範囲外

SSE の実装（判断 1 で (c) の場合は B17）、再構築の最適化、AWS への適用・実環境での計測、スクリーンリーダーの確認（人）、axe-core の導入、メモリ・panic のアラームの追加、DB のログインロールの分離、守りの導入（別計画）。
