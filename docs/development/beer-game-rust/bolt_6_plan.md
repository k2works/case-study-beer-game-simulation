### ゴール

停止・再開・代理入力、復帰（`recover`）、資格の失効・再発行、署名鍵の版、参加のレート制限を実装し、**失効した資格が以前に成功した要求を同じキーで再送しても 403** になることを示す（認可は冪等記録の照合より先）。

### 確認したい仮説

1. **失効した資格の再送は 403 か**（認証を `execute` の中へ移し、失効との競合を同じトランザクションで判定できるか）。
2. 資格をそのままセッション Cookie にした簡略化（B2 の簡略化 5）を、復帰資格とブラウザセッションの別ダイジェストに直せるか。
3. 冪等記録の暗号化（AES-GCM 系）を、作成・参加の応答に適用できるか。

## ステップ計画（各ステップの終わりで人のゲート）

1. **契約と feature の確認（読み取り）**: 上の 4 つの feature、`openapi.yaml` の該当パス、Kotlin の実装の振る舞いを読み、差を一覧にする。
2. **スキーマ（DDL）の提示**: マイグレーション 0007 以降の案とデータモデルとの差。承認後に作成。
3. **認証を `execute` の中へ（Red 先）**: 失効後の再送が 403 になる否定テストを先に書いて失敗を確認。そのうえで移動。
4. **停止・再開・代理入力**: ドメイン（`decide`/`evolve`）→ application → HTTP。`pause-resume.feature` を許可リストへ。
5. **資格**: 失効・再発行・復帰・鍵の版・期限切れ、役割の入れ替えでの自動失効。復帰資格とブラウザセッションを分ける。`credentials.feature`・`recovery.feature` を許可リストへ。
6. **レート制限**: 試行の窓（接続元の鍵付き要約。IP を DB に残さない）。`join-rate-limit.feature`。
7. **冪等記録の暗号化**: 作成・参加の再送を可能にし、`game-creation.feature` の 1 本目を許可リストへ。
8. **品質ゲート・記録**: `just backend-check`、`just acceptance`、`just ui-acceptance`（B6 で増える `@ui` の数を記録）。`bolt_6_report.md`、`index.md`、`mkdocs.yml`、`docs/log.md`。`apply-okf` と `okf:check`。
9. **コミット・push・CI**（区切りごと。Red の間は push しない）。

共同担当（B7）、カスタム条件（B8）、自動確定（B9）、観察者（B10）。コンテナ・インフラの変更。
