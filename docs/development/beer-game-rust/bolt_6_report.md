## 簡略化と未達（人の判断が要る項目）

1. **認証が `execute` の外**（B2 の簡略化 2 の継続）。認証から追記のコミットまでの間に、資格が失効する競合の窓が残る。失効の結果は次の要求から 403 になるので、実害は小さい見込みだが、設計の RB3（認証は `execute` の中）とは異なる。移す場合は `execute*` の引数の変更（広い）になるので、方針を人が決める。
2. **契約テストのクレートを導入していない**。承認はあるが、B6 で追加した API（`pause`・`resume`・`proxy-decisions`・`recover`・`credentials/*`・`review`）は、共有する `contracts/openapi.yaml` との照合を、まだ機械的に行っていない（共有の feature と、HTTP テストで挙動を確認しているだけ）。B7 の前か並行で導入を計画する。
3. **復帰（`recover`）は冪等記録を持たない**。`Idempotency-Key` を受けるが保存しない。失効後の再送は 403 になるが、有効な資格の再送は別のセッションを発行する。
4. **参加・再発行の再送の版**は、保存した版でなく、再送の時点の最新を返す（応答に版を保存するのに、追記前に版が分からないため）。作成は版 1 で固定。
5. **同じキーの作成の同時の重複**は、部分一意索引（`uq_idempotency_create`）に任せていて、再照合の処理は未実装（まれ）。
6. **資格のダイジェストの鍵の更新**（`CREDENTIAL_KEY_VERSION`・`CREDENTIAL_RETIRED_KEYS`）を環境変数で受ける形にした。運用手順（Secrets Manager との対応）は B15 で定義する。
7. **復帰資格 30 日・ブラウザセッション 24 時間**は、契約の記述に合わせた値（設定の既定）。
8. **`X-Forwarded-For` を信頼**して接続元を決める（リバースプロキシの内側の前提）。`unknown` に束ねられる場合は、全員が同じ窓になる。本番の定義（B15）で、信頼するプロキシの扱いを決める。
9. **TDD の順序**: 停止・再開・代理入力は、ドメイン → ステップの順で、受け入れのステップを先に書いて失敗を確認した箇所は少ない（失敗の確認は、各スライスの結合時）。B5 のような Red 先行は、全体では守れていない。人が判断。

## 発見・設計への影響

1. 設計の `participation_attempts` は 0002 に含める想定だったが、Rust 版の 0002 には無かった。0007 で追加した（設計書の記述「0002 に含む」との差。設計書への反映は、`verified` の再確認が要る）。
2. 作成の冪等キーは、ゲームが分からない状態で照合するため、`(scope, key_digest)` だけで引く。**テストで同じキーを別のシナリオが使うと、別のゲームの作成を再生してしまう**（受け入れテストのキーを世界ごとに一意にして解消）。実運用では、クライアントが作るキーが衝突しない前提（UUID）。
3. `events.actor_kind` は B2 まで常に `ANONYMOUS` だった。`EventCodec::actor` を足し、入力者がイベントに残るものは `PARTICIPANT`・`FACILITATOR` を書くようにした（監査の要件 FR-15）。
4. clippy の `indexing_slicing` が、`serde_json::Value` への代入（`body["x"] = ...`）を拒否する。テストでも `json!` で組み立てる。
