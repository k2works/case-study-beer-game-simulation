## 仮説の検証

1. **連鎖削除で全表から消えるか**: 成立。`game_id` を持つ全表を機械的に検査するテスト（AC5.1.4）が通る。新しい表を足して外部キーを忘れると落ちる。
2. **途中の失敗でも最終的に一度だけ削除されるか**: 成立。偽の Store（application）と、実 DB の受入（失敗の差し込み）の両方で確認した。
3. **削除ロールの最小権限で連鎖削除が動くか**: 成立。`beergame_deleter` が `game_roots` を消すと `retention_policies` が連鎖で消える。読み取りロールは削除の記録を消せない（42501）。

## 実施中に見つけた不具合

1. **ゲーム作成が 500 になっていた**: 投影の `make_interval(days => $2)` の `$2` が bigint になり、PostgreSQL が拒否した。`$2::integer` で直した。受入が 11 シナリオ落ちて気づいた。
2. `retention_policies` の追加で、`GameCreated` の投影の文が 3 から 4 に増えた。投影の純粋性のテストの期待値を更新した。
3. `app` の `tracing` が dev-dependencies にだけあり、`retention` モードのログでビルドできなかった。同じ版（0.1.44）を `[dependencies]` に移した。**新しいクレートの追加ではない。**
4. `RetentionState` の import 漏れ（`adapter-http`・`app`）。
5. **資格の値に鍵の版の接頭辞 `v<版>.` が付いていなかった（B10 から。2026-11-23 に @ui の計測で発見、修正）**: 設計（architecture-backend.md）は `v<版>.<乱数>` と定めるが、`issue` は乱数だけを返していた。観察者の @ui 2 シナリオが「招待コードが表示されていない」で落ちた。許可リスト（`@api`） は資格の形式を検査しておらず検出できなかった。テストを先に書いて失敗を確かめ（`http.rs` の復帰コードの形式）、`issue` で接頭辞を付けた。新テスト `nf_s3__招待コードは鍵の版の接頭辞と乱数の形で発行される`。検証側は鍵を順に試す既存の方式のまま動く。接頭辞なしで発行済みの資格も引き続き使える（開発 DB のみで実機の確認は未実施）。

## 簡略化と未達（人の判断が要る項目）

1. **保持の起点は作成時（暫定。M5。人の確認が要る）**。Kotlin 版と同じ。
2. **TDD の順序**: 受入は、許可リストへの追加で Red（11 シナリオが未定義）を確かめてからステップを書いた。一方、AC5.1.x の Rust のテスト（`ac5_1_*`）は、DS-11 の守りが落ちたため**実装の後に足した**。順序を守れていない。規則を壊すと落ちることの個別の確認はしていない。
3. ~~`@ui` は未計測~~ → 2026-11-23 に計測し 27 / 27（Node 25 では cucumber が動かないため、Node 26 で実行）。
4. **定期の起動は未定義**。`retention` モードは 1 回実行して終了するだけで、定期の起動は運用側（B15 の定義）。
5. **再試行をやめたゲームの通知は、ログ（`tracing::error!`）だけ**。アラームは B14。
6. **新規ファイル**: `acceptance/tests/acceptance/retention_steps.rs`（`steps.rs` が 4000 行を超えるため分けた）、`application/tests/retention.rs`、`app/tests/retention.rs`。確認なしで作った。
7. `acceptance` に `beergame-domain` を dev-dependency として足した（内部の path 依存。`Cargo.lock` は 1 行）。
8. **テスト環境**: テスト用の `postgres:18.6` コンテナが約 81 個 Docker に残っており、並列で起動すると DB への接続がタイムアウトした（B12 の変更とは無関係）。`--test-threads=2` で回避した。コンテナの掃除は未実施（ユーザーの開発用 DB が混ざっていないか確認が要る）。
