## 計画との対応

| 計画の手順 | 結果 |
| :--- | :--- |
| 1 契約の確認 | `Review` スキーマ（`results` は `RoleWeekResult` の配列）、`game.not_ended`（409）を確認。差分なし |
| 2 許可リストに追加（Red） | `review/retrospective.feature` を追加し、ステップを足して 4 シナリオが失敗することを確認 |
| 3〜4 実装 | `GET /api/v1/games/{id}/review`。`adapter-http` の `review` ハンドラ、`review_view`、`game_not_ended_problem`。既存の `session_snapshot`（`week_role_results`）を再利用 |
| 5 テスト | `crates/app/tests/review.rs` の 4 件（`ac4_2_1__`・`ac4_2_2__`）。順序、参加者と進行役の同一内容（決定論）、終了前・開始前の 409、資格なしと別ゲームの 403 |
| 6 品質ゲート | `just backend-check` 終了コード 0（domain 100%、全体 99.5%、`cargo deny` 緑）。`just acceptance` 28 シナリオ・170 ステップがすべて通る |

仮説「役割別の週結果の行で、振り返りが単純に実現できるか」は**成立**。新しい表・スキーマ・依存関係は不要で、既存の投影の読み出しだけで足りた。

## 簡略化と逸脱（人の判断が要る項目）

1. `settingsKind` を `"KIT"`、`changedSettings` を空で固定した（カスタム条件は B7 以降）。Kotlin 版の契約の形は満たす。
2. 開示の規則（終了後だけ）を `adapter-http` の `review` ハンドラに置いた（設計は application の `Disclosure`。B2 の簡略化 4 と同じ。共同担当の B6 で見直す）。
3. 観察者の認可は B9。
4. 結果の並びは「週 → 工場・一次卸・二次卸・小売店」（`Role::ALL` の順）。契約は「週・役割の順」としか書いておらず、Kotlin 版の並びとは未突き合わせ（契約テストは B3 で承認待ち）。
5. TDD の順序: ステップ定義を先に書いて 4 シナリオの失敗を確認したうえで実装した（Red 確認あり）。HTTP のテストは実装後に追加した。
