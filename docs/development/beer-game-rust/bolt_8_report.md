## 簡略化と未達（人の判断が要る項目）

1. **DB スキーマの変更なし**（見込みどおり）。`game_overview.settings_kind`・`settings_changes`、`game_settings` の既存の列に書く。
2. **`GameCreated` の JSON に `conditions` を足した**（後方互換: 無い従来のイベントはキットとして読むテストがある）。イベントのスキーマ版（`schema_version`）は 1 のまま。**版を上げるかは人が判断**（B13 の `EventCodec` とアップキャストの設計）。
3. **`commitMode`（自動確定）の指定を受け取り保存する**（`AUTO` も受け付ける）。動作は B9。AC1.1.6 の API の検証は B9。
4. **公開範囲の実際の開示**（観察者）は B10。ここでは設定として保存するだけ。
5. 範囲（初期在庫 0〜1000、遅延 1〜8、単価 0〜100000）は契約の仮置きのまま（契約は共有物で、変更していない）。
6. TDD の順序: 性質テストとドメインのテストを、実装と同じ作業の中で書いた（失敗を先に確認していない）。受け入れのステップは、実装後に書いて通った。人が判断。
7. 契約テストに、カスタム作成の応答と 422 を足した。

## 発見

- 契約テスト（B7 で導入）の `Problem` の `correlationId` は、B8 の 422 でも緑（`ValidationProblemBody`）。
- 受け入れテスト・HTTP テストで、**文字列（相関 ID の UUID）に数字の並び（例 `77`）が現れて偶然一致する**不安定なアサーションを 1 件見つけて直した（`co_input.rs`）。応答全体の文字列検索は、数値の検査に使わない。
