### ゴール

ゲームの終了後に、需要と**役割別**の注文・在庫・受注残・出荷・費用を、同じ週の軸で比較できる。指標と役割を切り替えられ、グラフと同じ値の表を常に併記する。**これが学習の最優先の価値（ブルウィップ効果の確認）**である。

### 確認したい仮説

1. **役割別の週結果の行（`week_role_results`）で、振り返りが単純に実現できるか**（[リリース計画](./release_plan.md)の仮説）。SQL の直接の問い合わせで足り、集約や投影の再構築が要らないか。
2. **標準のシナリオ（需要 4 → 8）と反応的な発注で、注文の変動が上流ほど増幅して見えるか**。見えなければ、データか表示のどちらかに問題がある。
3. 手書きの SVG のグラフが、**色に頼らず**（線の種類・直接のラベル・表）読み取れるか。

### 対象の受入条件（原文）

[ユーザーストーリー](../../requirements/beer-game2/user_story.md)の US4.2 から、**原文のまま**転記する。B1 の学び（実装後に原文を読み返して食い違いが出た）を踏まえ、**Step 1 で期待値を確定してからテストを書く**。

| ID | Given / When / Then（原文） |
| :--- | :--- |
| AC4.2.1 | ゲーム終了後に分析画面を開くと、需要・注文・在庫・受注残・出荷・費用を、**役割別に**、同じ週の軸で比較できる |
| AC4.2.2 | プレイ中に、終了後専用の役割別の値を取得しようとすると、開示しない |
| AC4.2.3 | データが 0 件の状態で分析画面を開くと、「データなし」と読み込みの失敗を区別する |

## リスクと対策

| リスク | 影響 | 対策 |
| :--- | :--- | :--- |
| 終了前の値が、別の経路（SSE の通知、ほかの問い合わせ）から漏れる | 高 | 開示の判定を 1 か所に集め、否定テストを先に書く。SSE は版の通知だけ（B1 で確認済み） |
| 受入条件の食い違い（B1 で発生） | 高 | Step 1 で期待値を確定し、人が確認してから書く。対応表の照合を、原文で行う |
| 増幅がデータに現れず、学習の価値が伝わらない | 中 | Step 1.2 で golden を手計算し、反応的な発注のボットでデモを確認。足りなければ派生指標（判断項目 6）を検討 |
| 手書きの SVG が、小さい画面や多い系列で読みづらい | 中 | 系列は最大 5 本、凡例ではなく直接のラベル、表を併記。狭い画面の案内は B13 |
| 週数が多いゲーム（50 週）で、描画・取得が遅い | 低 | SQL 1 回で返す。性能の測定は B13（NF-P8） |
| 所要が 2 日を超える | 中 | 人の検証時間を含めて計測する（B1・B2 の実績に、含めていなかった） |
