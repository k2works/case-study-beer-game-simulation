### ゴール

main へのマージで、**ステージングへ自動デプロイ**され、スモークテストが通り、**ロールバックできる**ことを確認する。ECR、OIDC、Terraform の最小構成（ネットワーク、RDS、ECS、ALB、CloudFront、S3）、マイグレーションの自動適用を含む。

### 確認したい仮説

1. パイプラインと環境は、**再現でき、戻せる**か（Terraform を空の状態から適用でき、直前のイメージと静的ファイルの版へ戻せる）。
2. **SSE が CloudFront と ALB を通る**か（アイドルタイムアウト、バッファリング、`Cookie`・`Origin`・`If-Match`・`Idempotency-Key` の転送）。通らない場合は、ポーリングで十分かを判断する。
3. **本番用の実行形態**（コンパイル済みの JavaScript、非 root、Node 26）で、B1 の挙動が変わらないか。
4. Cookie（`Secure`、`SameSite=Strict`）と Origin の検査が、CloudFront の単一オリジン構成で正しく働くか。

## ステップ計画

各ステップは、**検証（テスト）を先に定義**してから実装する。ステップの終わりが承認ゲートで、**人が確認してから次へ進む**。インフラの変更は、`plan` の差分を人が確認してから適用する。

凡例: 🔵 設計・準備　🔴 検証の定義（失敗を確認）　🟢 実装　🟡 整理　✅ 検証

### Step 1: 前提の確認と見積もり（🔵）

- [ ] 1.1 判断項目 1〜10 を確認し、承認を得る
- [ ] 1.2 RDS for PostgreSQL 18 の提供、ECS Fargate / ALB / CloudFront の構成で、**費用の概算**を作成（ステージング・本番）
- [ ] 1.3 インフラ設計の PostgreSQL の記載（17 → 18）を直す。ADR-012 を承認済みにする
- [ ] 1.4 `docs/operation/beer-game2/` に、AWS ステージング環境セットアップ手順書の骨子を作る

**ゲート 1**: 費用、アカウント、権限、版を、人が承認する。

### Step 2: 本番用のイメージ（🔴🟢🟡）

- [ ] 2.1 🔴 コンテナのスモークテスト（CI）: イメージをビルドし、PostgreSQL に接続して `/ready` が 200、DB 停止で 503。**非 root、`tsx` を使わない、開発依存を含まない**ことを検査
- [ ] 2.2 🟢 `tsconfig.build.json`、`npm run build`（`dist/` へコンパイル）、`Dockerfile`（`node:26-alpine`、マルチステージ、非 root、`HEALTHCHECK`）、`.dockerignore`
- [ ] 2.3 🟢 マイグレーション用の起動（同じイメージ、`node-pg-migrate`）。1 回限りのタスクとして実行できる
- [ ] 2.4 🟢 UI のビルド（`vite build`）を、S3 に置く成果物にする。版つきのプレフィックス（コミット SHA）
- [ ] 2.5 🟡 `.github/workflows/beer-game2.yml` に、イメージのビルドとスモークテストを追加

**ゲート 2**: コンパイル済みで動くこと、イメージの中身（非 root、依存）を、人が確認する。

### Step 3: Terraform の土台（🔴🟢🟡）

- [ ] 3.1 🔵 状態の保管先（S3 + ロック）を作る手順（ブートストラップ。**人が実行**）。環境ごとに分離
- [ ] 3.2 🔴 `terraform fmt -check` / `validate` / `plan` を、CI で必ず実行（`tfsec` を含む）。差分なしを成功とする
- [ ] 3.3 🟢 モジュール: `network`（VPC、2 AZ、公開・プライベート、エンドポイント）、`ecr`（不変のタグ、スキャン、ライフサイクル）、`secrets`（接続情報、鍵）、`rds`（ステージング: Single-AZ、暗号化、PITR）
- [ ] 3.4 🟢 モジュール: `ecs`（API サービス、マイグレーションのタスク定義、ログ）、`alb`（HTTPS 終端は CloudFront まで。`/ready` のヘルスチェック）、`web`（S3 非公開 + CloudFront、OAC、`/api/*` は ALB、`Cookie`・`Origin`・`If-Match`・`Idempotency-Key` を転送、キャッシュなし）、`iam`（GitHub OIDC、最小権限）
- [ ] 3.5 🔴🟢 SSE の検証: CloudFront と ALB を通して、接続が維持され、イベントが届く（アイドルタイムアウトを設定）。**届かなければ、人が判断する**（ポーリングのみで運用するか）
- [ ] 3.6 🟡 変数・出力・タグの整理、環境ごとの `tfvars`

**ゲート 3**: `plan` の差分（作られるリソース、権限、公開範囲、費用）を、人が確認する。**`apply` は人が行う**。

### Step 4: デプロイのパイプライン（🔴🟢🟡）

- [ ] 4.1 🔴 デプロイ後のスモークテスト（拡張した `scripts/smoke.ts`）: `/ready`、作成 → 参加 → 割り当て → 開始 → 入力 → 確定、SSE の受信、SSE 遮断時のポーリング。対象の URL は環境変数
- [ ] 4.2 🟢 ワークフロー `deploy-staging`: main へのマージで起動 → イメージを**一度だけ**ビルドして ECR へ（コミット SHA、ダイジェストを記録）→ OIDC → Terraform の `plan` / `apply`（ステージング）→ マイグレーション（1 回限りのタスク。失敗なら中止）→ ECS のローリング → 静的ファイルを版つきで S3 へ → CloudFront の版を切り替え → スモークテスト
- [ ] 4.3 🟢 `concurrency`（同時に 1 つのデプロイ）、失敗時の通知（ジョブの失敗）
- [ ] 4.4 🟡 ワークフローの整理（再利用できる部分の抽出）、アクションの版を更新（Node 20 の非推奨に対応）

**ゲート 4**: 認証の仕組み（OIDC のロールの信頼条件、権限の範囲）と、ワークフローを、人が確認する。

### Step 5: ロールバック（🔴🟢）

- [ ] 5.1 🔴 ロールバックの検証: 意図的に壊した版（`/ready` が失敗する、または スキーマ互換のある変更）をデプロイし、直前のダイジェストと静的ファイルの版へ戻して、スモークテストが通る
- [ ] 5.2 🟢 `rollback-staging`（`workflow_dispatch`）: 直前（または指定）のダイジェストと版へ戻す。マイグレーションは戻さない（拡張 → 互換 → 縮小の順で、旧アプリと互換）
- [ ] 5.3 ✅ デプロイ時に、ロールバックの手順を毎回確認する（AC6.2.3）

**ゲート 5**: 壊した版 → 戻す、の実演を、人が確認する。

### Step 6: CI の強化と終了（✅）

- [ ] 6.1 CI で Playwright の E2E を実行（PostgreSQL 18 のサービス）。`npm audit`（本番依存）、コンテナのスキャン
- [ ] 6.2 `develop` → `main` のプルリクエストでの流れを確認（デプロイは `main` のみ）
- [ ] 6.3 `docs/` の更新: AWS ステージング環境セットアップ手順書、運用コマンド、ADR-012（承認）、`log.md`
- [ ] 6.4 **Bolt 終了報告**（`bolt_2_report.md`）と、**判断と学び**（ジャーナル）。B3 以降の所要の再調整
- [ ] 6.5 コミット（Step ごとに、意味のある単位で）

**ゲート 6（Bolt の承認）**: 人が、完了条件を確認し、Bolt を承認する。

## リスクと対策

| リスク | 影響 | 対策 |
| :--- | :--- | :--- |
| SSE が CloudFront / ALB で途切れる | 中 | Step 3.5 で早期に検証。ポーリングで追いつく設計（B1 で確認済み）なので、機能は損なわれない |
| AWS の権限・アカウントの準備が遅れる | 高 | 判断項目 2 を最初に確認。待つ間は、Step 2（イメージ）と Terraform の `validate` まで進める |
| ステージングの常時費用が想定を超える | 中 | Step 1.2 で概算を出し、Single-AZ・1 タスクで始める。使わない時間の停止を検討 |
| OIDC のロールの権限が広すぎる | 高 | 最小権限で書き、ゲート 4 で人が確認。環境ごとにロールを分ける |
| マイグレーションの失敗で、DB が中途半端になる | 高 | 1 回限りのタスクで適用し、失敗ならデプロイを中止。ステージングで、先に失敗を再現して手順を確認 |
| Terraform の状態の破損・競合 | 中 | リモートの状態とロック、`concurrency`、`apply` は人が実行 |
| 所要が 2 日を超える | 中 | 外部の準備待ちを除いて計測。B1 の実績（人の検証時間を含めていない）を踏まえ、B3 以降の見積もりを再調整 |
