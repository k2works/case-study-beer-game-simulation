## 仮説の検証結果

1. **資格の設計は、漏洩時に被害を止められるか**: 止められる。再発行で、対象の**ブラウザセッションと復帰コードの両方**が即座に使えなくなり、他の主体（進行役・他の参加者）は影響を受けないことを、メモリ版と PostgreSQL 版の同じ契約のテストで固定した。進行役自身の再発行では、同じ応答で新しい Cookie を設定するため、操作中の進行役は締め出されない（E2E で確認）。
2. **有効期限の境界のテスト**: できる。期限の判定を DB の `now()` ではなく、注入した時計の時刻で行うようにし、期限の直前（有効）と期限ちょうど（無効）を、ユースケースと PostgreSQL の両方で確かめた。
3. **停止と代理入力を、`Session` 集約の状態遷移として単純に表せるか**: 表せた。`PAUSED` の追加と、保存の共通化（`storeDecision`）で足りた。代理入力でも自動確定が働く（停止中は確定しない）。

## 計画と異なる点（人の判断が必要）

| #   | 内容                                                                                    | 理由                                                                                                                                                                                                                                             |
| :-- | :-------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | レート制限の既定値を **1 分 10 回から 60 回**に変えた（`AUTH_RATE_LIMIT_PER_MINUTE`）   | E2E で、同じ送信元からの参加が 10 回で止まった。研修会場では参加者が同じ送信元の IP（社内の NAT）を共有しやすく、10 回では 20 人規模の研修で参加が止まる。復帰コードは 256 ビット、参加コードは約 8.5×10¹¹ 通りで、60 回でも総当たりは成立しない |
| 2   | 復帰コードは、集約（`Game`）ではなく、資格のリポジトリが持つ                            | 既存の資格（ブラウザセッション）と同じ扱いにして、集約の不変条件から認証を外した。保存先はデータモデルのとおり `participants`・`games` の列                                                                                                      |
| 3   | 鍵の版は、データモデルの `key_version` 列ではなく、ダイジェストの接頭辞（`v1:…`）で持つ | B1 の保存形式を引き継いだ。検証は、すべての版のダイジェストを候補にして引く                                                                                                                                                                      |
| 4   | 進行役のコンソールに、役割ごとの**入力の版**を加えた（値は含めない）                    | 代理入力の楽観的排他に必要                                                                                                                                                                                                                       |

## 見つけた欠陥（修正済み）

- **AC3.2.3: 遅れて届いた古い応答が、新しい状態を上書きできた**。画面の再取得（変化の通知とポーリング）が重なると、先に出した要求の応答が後から届き、表示が古い週に戻る余地があった。`useLiveSnapshot` で要求に通し番号を付け、最後の要求の応答だけを適用するよう修正し、テストで固定した。v1 の評価は ✓ だったが、v2 の UI では保証されていなかった。
