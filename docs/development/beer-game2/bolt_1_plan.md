### ゴール

キット準拠のゲームを、**作成 → 参加 → 役割の割り当て → 開始 → 入力 → 確定 → 状態の表示**まで、**ローカルで**、実 PostgreSQL、構造化ログ、`/ready`、層の lint、役割別の週結果の保存つきで、縦に通す。

### 確認したい仮説

1. `Game` と `Session` の集約の粒度、層の構造（ポートとアダプター）は、妥当か（[ADR-003](../../adr/beer-game2/003-ports-and-adapters-with-lint.md)、[ADR-004](../../adr/beer-game2/004-separate-game-and-session-aggregates.md)）。
2. Node 26 / TypeScript 6.0 / PostgreSQL 18 の組み合わせで、ツール（Vitest 5、ESLint 10、Vite 8、Playwright）が問題なく動くか（[ADR-013](../../adr/beer-game2/013-tech-stack-versions.md)）。
3. AI の出力の質は、どの密度の承認ゲートが要るか（以降の Bolt のゲート密度を決める）。

## ステップ計画

各ステップは、**TDD（Red → Green → Refactor）**で進めます。ステップの終わりが承認ゲートで、**人が、テストとコードを全行理解して**承認してから、次へ進みます。テスト名には、ストーリー・受入条件の ID を含めます（例: `[US2.3/AC2.3.2] ...`）。

凡例: 🔵 設計・準備　🔴 Red（失敗するテスト）　🟢 Green（最小の実装）　🟡 Refactor　✅ 検証

- [x] 1.3 `vitest.config.ts`: カバレッジのゲート（行・関数・文 85%、分岐 75%）、`adapters/http` を計測対象に含める

## リスクと対策

| リスク | 影響 | 対策 |
| :--- | :---: | :--- |
| 集約の粒度（`Game` と `Session`）が誤っている | 高 | Step 3〜6 で早期に検証し、誤りが分かればゲートで止めて設計を見直す |

| AI が層の規則を破る、ルールをユースケースに書く | 中 | lint とゲート。Step 5 で重点的に確認 |
| 計算の期待値が、教材とずれる | 高 | golden の期待値を、要件定義（BR）と照合してから実装する（ゲート 2） |
| 所要が 2 日を超える | 低 | UI（Step 8）を最小にする。超過は、B1 の実績としてリリース計画を再調整する |
