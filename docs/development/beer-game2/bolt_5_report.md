## 仮説の検証結果

1. **同時の保存で、受理済みの更新を失わないか**: 失わない。`sessions` の行ロック（`FOR UPDATE`）で保存が直列になり、後の保存は、ロックが外れた後の最新の行を読んで版の不一致で拒否される。拒否された側には、勝った値・版・保存者の表示名を同じ応答（409）で返す。
2. **集約を分けずに表せるか**: 表せた。`Game.assignments` と `Session.holders` を「役割 → 参加者の一覧」にし、担当の検査を「一覧に含まれるか」にするだけで足りた。[アーキテクチャ設計](../../design/beer-game2/architecture-backend.md)の「集約をさらに分ける条件」（共同担当の競合が利用に影響する）は、50 回の並行の試行でも現れていない。

## 人の承認が必要な項目

- 判断項目 2: 409 の応答に `latest: { quantity, version, savedBy }`（表示名）を含める。競合は同じ役割の担当にだけ起き、他の役割の担当には権限エラー（403）で値を含めない（否定テストあり）。
- 判断項目 3: 「この値で保存し直す」に確認ダイアログを挟まない。
- 上の「計画と異なる点」1〜3。

## U2 の完了の判定

U2（共同担当と進行の継続）の受入条件は、B4 の 8 件（AC3.1.1〜3.1.3、AC3.2.1〜3.2.5）と B5 の 4 件（AC1.2.4、AC2.1.4、AC2.2.3、AC2.2.4）の **12 件すべてがテストでパス**しました。[Unit 定義](../../requirements/beer-game2/unit_definition.md)の測定基準「同一役割の共同入力で、変更を失わない（並行テストで失われた更新 0 件）」も満たしました。

**実装としては U2 は完了**です。ただし、B4・B5 とも人の承認（計画、判断項目、マイグレーション 003、Bolt）が未実施のため、**Unit の完了の承認は人の判断を待ちます**。NF-S11 のレート制限と NF-S3 の鍵のローテーションは、ステージング（B2 の持ち越し）での確認が残ります。
