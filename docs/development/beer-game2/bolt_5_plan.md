### ゴール

進行役が、同じ役割に複数の参加者（共同担当）を割り当てられる。共同担当は、同じ状況と、1 つの入力値・版を共有する。同時に保存すると、後の人は拒否され、**最新の値と保存者**を同じ応答で受け取り、自分の未保存の値を保持したまま、どちらにするかを選べる。

### 確認したい仮説

1. **同時の保存で、受理済みの更新を失わないか**（[リリース計画](./release_plan.md)の仮説、NF-R14）。実際の PostgreSQL で、同じ版から並行に保存して、ちょうど 1 件だけが受理され、拒否された側が勝った値を受け取るか。
2. 共同担当を、`Game.assignments` と `Session.holders` を「役割 → 参加者の一覧」にするだけで表せるか（集約を分けずに済むか）。

## ステップ計画

### Step 1: 受入条件の期待値を確定する（🔵）

### Step 2: 共同担当の割り当て（`Game`）（🔴🟢🟡）

同じ役割に複数人。1 人に複数の役割は拒否（AC1.2.5）。各役割に 1 人以上で開始できる。

### Step 3: 共同入力（`Session`）（🔴🟢🟡）

`holders` を一覧に。共同担当の誰でも保存でき、版が古い保存は、最新の値・版・保存者を持つ競合として拒否する。

### Step 4: ユースケースと永続化（🔴🟢）（マイグレーション 004 は不要になった）

状況の取得に、共同担当の表示名、入力値・版・保存者を含める。PostgreSQL で、**並行の保存のテスト**（同じ版から同時に保存して、受理は 1 件）。

### Step 5: HTTP（🔴🟢）

409 の Problem JSON に `latest` を含める。

### Step 6: UI（🔴🟢🟡）

ロビーの共同担当の表示と割り当て。プレイの共同担当の表示、保存者と版、競合の表示（最新の値を使う／この値で保存し直す）。

### Step 7: E2E と検証（✅）

2 つのブラウザの共同担当で、一方の保存が他方に反映され、同じ版からの保存が競合になる流れを E2E で通す。`npm run verify`。
