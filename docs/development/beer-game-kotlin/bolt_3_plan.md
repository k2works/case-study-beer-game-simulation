### 範囲の線引き（重要）

- **AWS への適用はしない**（`terraform apply` を実行しない。リソースを作らない）。適用・デプロイの実行は、別の承認ゲート（AWS アカウントと費用の判断）。
- **本番環境・デプロイ設定は確認必須**（プロジェクトの規約）。本書は**定義の作成まで**。ワークフローは、`workflow_dispatch` のみで、**自動で起動しない**ように定義する。
- 秘密情報（資格の鍵、DB のパスワードなど）は、リポジトリに置かない。AWS の Secrets Manager から注入する**定義**にとどめる。
- 実行環境の制約: ローカルの Terraform は 1.5.7（設計は 1.17 以上）。AWS の認証情報はローカルに無いため、**`terraform plan` はローカルでは実行できない見込み**（`validate` までを、作業用の新しい Terraform で行う）。`plan` が通ることは、**未確認**として扱う。

### ゴール

JVM のアプリケーションを、**再現できるコンテナ**にし、起動モード（`api`・`migrate`、将来の `retention`・`rebuild-projections`）を定義し、ステージング・本番の AWS 構成（Terraform）と、デプロイ・ロールバックの手順を、**適用せずに**定義する。

### 確認したい仮説

1. コンテナ（マルチステージ、JRE 25）が再現でき、ローカルで `api`・`migrate` が起動し、スモークテストが通るか。
2. JVM の起動時間は、目標（NF-P16: p95 30 秒）に収まるか。
3. 起動時の設定の検査（H2 の拒否、秘密情報が無ければ失敗）は、コンテナでも働くか。
4. beer-game2 のインフラ定義（Terraform）を、JVM に合わせて流用できるか。変更点は何か。

### 範囲外

AWS への適用、独自ドメイン・ACM・CloudFront の本番設定の完成（B14）、観測（メトリクス・アラーム。B13）、`retention`・`rebuild-projections` の実装（B11・B12。モード名の定義のみ）。

## ステップ計画

各ステップは、可能な範囲で**テスト（検証）を先に**書きます。**ゲートは、人の確認待ち**とし、承認済みとは書きません。

### Step 1: コンテナと起動モード（🔴🟢）

- [ ] 1.1 🔴 コンテナのスモークテスト（`api` が `/ready` に応答、`migrate` がマイグレーションを適用して終了、**本番相当の設定で秘密が無ければ起動に失敗、`DB_KIND=h2` を拒否**）を先に書き、失敗を確認する
- [ ] 1.2 🟢 `Dockerfile`（マルチステージ。実行イメージは JRE 25。非 root。H2 のドライバを含めない。ヘルスチェック）と、起動モード（`api`・`migrate`。`retention`・`rebuild-projections` はモード名の定義と、未実装の旨の明確な失敗）
- [ ] 1.3 ローカルで、コンテナをビルドして起動し、スモークテストを通す。**起動時間を計測**（仮説 2）。イメージの内容（H2 を含まないこと、サイズ）を確認

**ゲート 1**: コンテナと起動モードを、人が確認する。

### Step 2: Terraform の定義（🔵）

- [ ] 2.1 beer-game2 の `apps/beer-game2/infra`（定義）を読み、**JVM に合わせた変更点**（ポート、ヘルスチェックのパス `/api/v1/ready`、環境変数 `DB_KIND=postgres`・`APP_ENV`、秘密情報の注入、CPU・メモリの初期案、起動猶予）を洗い出す
- [ ] 2.2 `apps/beer-game-kotlin/infra/` に、最小構成（ネットワーク、RDS for PostgreSQL 18、ECR、ECS Fargate、ALB、CloudFront、S3、Secrets Manager、IAM、環境ごとの分離）の**定義**を作る。**リソースを作らない**。秘密の値を含めない。リモートの状態（S3 とロック）は設計書のとおり
- [ ] 2.3 検証: `terraform fmt -check`、`terraform validate`（作業用の新しい Terraform。設計の `required_version` を満たす版を、公式の配布から作業用ディレクトリに取得して使う。**システムの Terraform は入れ替えない**）。**`terraform plan` は、認証情報が無いため未実行（未確認）**と記録

**ゲート 2**: Terraform の定義を、人が確認する（**本番環境・デプロイ設定は確認必須**）。

### Step 3: デプロイ・ロールバックの定義とスモークテスト（🟢）

- [ ] 3.1 CI/CD の定義（ビルド → ECR への push → マイグレーション → ECS の更新 → スモークテスト → 失敗時のロールバック）。**`workflow_dispatch` のみ**（自動で起動しない）。AWS の資格は OIDC（秘密を持たない）。**実行しない**
- [ ] 3.2 スモークテストの手順（ローカルのコンテナで実行できるもの）と、ロールバックの手順（直前のタスク定義へ戻す。マイグレーションの前方互換の注意: 読む版 → 書く版の 2 段階リリース）を、運用の文書にまとめる

**ゲート 3**: デプロイ・ロールバックの定義を、人が確認する。

### Step 4: 検証と終了（✅）

- [ ] 4.1 全テストと静的解析（B2 の工程）が緑のままであること。コンテナのスモークテストの結果
- [ ] 4.2 設計書（インフラ設計、運用要件）の更新と、`validating-design` の完了時の実施。Bolt 終了報告（`bolt_3_report.md`）。人の確認待ちの項目と、**AWS への適用の判断（別ゲート）**の一覧
