## 重要な判断（人の判断が要る）

**共有の `operations/projection-rebuild.feature`（5 シナリオ）を、許可リストに入れていない。** このフィーチャーは、Kotlin 版の投影表（`game_overview` など）と、ストリームの「進んだ版」の記録を、試験が直接書き換える前提である。Scala 版は、B1 から**投影表を持たず、イベントの再生で状態を復元する**簡略化を採っているため、対応する表が無く、そのままは実行できない。

- Release 1.0 の完了条件「許可リスト（全シナリオ）の 100%」から、この 1 ファイルを除外してよいか、人が決める（B15 の前提）。
- 投影表を作る（設計どおりにする）か、簡略化を続けるかも、人が決める。NF-P2（確定から反映）・NF-P18（再構築）・B9 の観察者専用 DB ロールに関わる。

代わりに、Scala 版の設計で同じ目的（データを失わずに状態を作り直せる・不整合を検出できる・形の進化に耐える）を満たす検査を実装した。

### 最大のゲームの再生の実測（NF-P18）

最終週 50・4 役割・各 3 回の保存と確定で、652 イベント。**再生（`Replay.session`）の中央値は約 1〜3 ms**（7 回の測定の中央値を、3 回の実行で 1.2・1.6・2.7 ms。初回は JIT で約 6〜12 ms、外れ値は約 12〜18 ms）。ただし、これは**メモリ上の畳み込みだけ**で、実際の要求では、データベースからの読み出しと JSON の復号が加わる。それは B15 の実 DB の負荷試験で測る（本報告では未測定）。目標値は、実測で決める。

## 手順についての注記

- `StreamVerifierSpec` は実装と同時に書き、**先に Red を確認していない**（TDD の逸脱）。検査の実装を壊したときに落ちることの確認も、整合の検査では未実施（黄金のデータでは確認した）。
- 黄金のデータの初回の生成は、更新モード（`BGS_GOLDEN_UPDATE=true`）で行った。差分は人が確認する運用。
