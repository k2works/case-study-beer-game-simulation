### ゴール

ゲームの終了後に、進行役が全記録を CSV と JSON で出力できるようにする。両形式は同じ記録から作り、数量と費用が一致する。スキーマ版とチェックサム（SHA-256）を記録し、表示名・参加コードを含めない。要求時に生成する（投影にしない）。

### 確認したい仮説

1. 出力が完全で再利用できるか（週・役割ごとの受注・出荷・発注・在庫・受注残・費用が、CSV と JSON で一致するか）。
2. 最終週の確定が、出力に依存しないか（出力は終了後に要求時に作る）。
3. 表計算での数式の解釈（CSV インジェクション）を防げるか。

### 対象の受入条件

| 対象 | 内容 |
| :--- | :--- |
| AC4.3.1 | 終了後、進行役が CSV・JSON で出力でき、設定の種別・全週・全役割・発注・費用を識別できる。表示名・参加コードを含まない。終了前は出力しない。進行役以外は出力できない |
| AC4.3.2 | 両形式の数量と費用が一致し、スキーマ版が記録される。本文の SHA-256 がチェックサムのヘッダーと一致する |
| AC4.3.3 | 組み立てられなければ本文を返さず、problem+json（500）を返す |
| カスタム条件 | カスタムのゲームは、出力でも「カスタム」と変更した項目で識別できる |

### 範囲外（後続の Bolt）

入力の保存の履歴（イベント）の出力（契約どおり含めない）。最大の長さでの生成時間（NF-P9）は B15。

## 人の判断が要る項目（着手前の承認。**未承認**）

1. スキーマ版の値（契約の例は `beer-game-kotlin.export.v1`。本実装は `beer-game-scala.export.v1` とする）。**人が決める**。
2. CSV は RFC 4180（CRLF）。文字列の列の先頭が `=`・`+`・`-`・`@`・タブ・CR のときは `'` を付ける（契約）。
3. 新しいマイグレーションは要らない（要求時にイベントの再生から作る）。
4. `format` の省略・不明は 422（`errors[].field` が `format`）。
