### ゴール

ゲームごとの保持期間（既定 90 日）を決め、期限に達したゲームの全データ（記録・資格・招待・履歴）を、定期のタスクで削除する。削除は 1 つのトランザクションで行い、失敗したら何も消さず、指数バックオフで最大 5 回再試行し、上限に達したら再試行をやめて通知する。削除後は、ゲームの ID を持つ行がどの表にも残らず、ゲームの ID を含まない受領記録だけが残る。

### 確認したい仮説

1. 削除後に何も残らないか（`game_id` を持つ全表を `information_schema` で検査して確かめられるか）。
2. 削除の失敗で半分の状態を完了としない（トランザクションの原子性）か。再試行で最終的に一度だけ削除されるか。
3. 時計と障害を注入して、再試行の動作を決定論的に試験できるか。

### 対象の受入条件

| 対象 | 内容 |
| :--- | :--- |
| AC5.1.1 | 保持期間は作成時に指定（既定 90 日）。進行役だけが保持状態を取得でき、削除予定日・状態を示す |
| AC5.1.2 | 期限に達したゲームだけを削除し、ゲーム記録と資格が消える。実行結果（受領記録。ゲームの ID を含まない）が残る。期限前・別のゲームは影響を受けない |
| AC5.1.3 | 失敗時は何も消さず再試行（指数バックオフ）。次の試行の時刻より前には再試行しない。5 回失敗で再試行をやめ、通知する |
| AC5.1.4 | 削除後、`game_id` を持つ全表に行が残らない |
| AC5.1.5 | バックアップに削除前のデータが残る期間（7 日）を示す |

## 人の判断が要る項目（着手前の承認。**未承認**）

1. マイグレーション V007（`game_retention`・`deletion_receipts`）（データベース。確認必須）。
2. 削除の方式: 外部キーを連鎖削除に変えず、アプリケーションが 1 つのトランザクションで、子の表から順に明示して削除する（既存の外部キーを変更しない）。
3. 再試行の間隔は 1 時間 × 2^(試行 − 1)（仮置き。未計測）。上限は 5 回（契約）。
4. 保持の開始は作成時（暫定。契約の M5）。
5. 通知は、構造化ログ（`retention.abandoned`）に出す。SNS への配線は B13 の定義まで。
6. 定期のタスクは、サーバーの起動時に開始する（既定 10 分ごと。環境変数で変更・停止）。
7. 削除の受領記録はゲームの ID を含まない（件数と時刻だけ）。
