### ゴール

投影表を持たない Scala 版の設計（状態はイベントの再生で復元する。B1 から継続）に合わせて、B12 の目的（データを失わずに状態を作り直せること・整合の検査・スキーマの進化）を満たす。(1) 全ゲートのイベントのストリームの整合（版の連続・再生の妥当性・game と session の整合）を検査する。(2) イベントの読み出しにアップキャストの口を設け、保存済みの形（スキーマ版 1）を固定する黄金のデータで、後方互換（N-1）を検査する。(3) 最大のゲームの再生の時間を実測する（NF-P18 の根拠）。

### 確認したい仮説

1. イベントの列だけから、状態を過不足なく作り直せるか（再構築がそのまま再生であること）。
2. 整合の検査は、版の欠落・不正な遷移・game と session の食い違いを、研修中でも読み取りだけで検出できるか。
3. 最大のゲーム（最終週 50）の再生が、要求ごとに行える時間に収まるか（実測する。目標は実測で決める）。

## 人の判断が要る項目（着手前の承認。**未承認**）

1. **共有の `operations/projection-rebuild.feature`（5 シナリオ）は、許可リストに入れない**。Kotlin 版の投影表（`game_overview` など）と、進んだ版の記録を直接書き換える前提のため。Scala 版に投影表が無いのは B1 からの簡略化（読み取りモデルなし）による。**Release 1.0 の「許可リストの 100%」から、この 1 ファイルを除外してよいかを、人が決める**（B15 の前提）。
2. 投影表を作る（設計どおりにする）か、現行の簡略化を続けるか。NF-P2・NF-P18・B9 の DB ロール分離に関わる。人が決める。
3. マイグレーションは足さない（スキーマ版は `events.schema_version` の既存の列を使う）。
4. 未知のスキーマ版（現在の版より新しい）のイベントは、読まずにそのゲームを止める（`stopped`）。「読む版 → 書く版の 2 段階リリース」の読む側の保護。
5. 整合の検査は、サーバーの起動時に日次で実行し、不一致を構造化ログに出す（`BGS_VERIFY_INTERVAL_HOURS`。既定 24。0 で停止）。
