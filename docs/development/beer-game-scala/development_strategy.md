# 開発戦略 - ビールゲームシミュレーション（Scala 版）

## 概要

本書は、[リリース計画](./release_plan.md)（草案）の Bolt 群を局面に分け、各局面の TDD のアプローチと横断的な進め方を定めます。**AI の草案で、人の承認を得ていません。**

- **Single Source of Truth**: Bolt の割り当てと日程は [リリース計画](./release_plan.md)、テストの種類・静的解析・BDD の細部は [テスト戦略](../../design/beer-game-scala/test-strategy.md) を正とします。本書は「どの局面でどう進めるか」の判断だけを書き、それらを複製しません。
- Kotlin 版（[開発戦略](../beer-game-kotlin/development_strategy.md)）と Rust 版の進め方を引き継ぎます。Scala 版で変わるのは道具（sbt、munit、cucumber-scala、WartRemover、Scalafix）と、CI を 3 ジョブに分ける点（案 Y）です。
- **範囲は U1〜U6（B1〜B15、予備 B16。Release 1.0 まで）です。** 約束の範囲を U1〜U6 に広げる承認は、リリース計画の承認で行います（未実施）。
- リリース計画は日本語のイテレーション計画（`iteration_plan-N.md`）でなく Bolt 計画（B1〜B7）で進めるため、「イテレーション」を「Bolt」と読み替えます。

## 戦略の全体像

### 局面とアプローチの対応

| 局面 | Bolt | Unit | 主アプローチ | 狙い |
| :--- | :--- | :--- | :--- | :--- |
| 序盤 | B1〜B3 | U1 | アウトサイドイン | 縦に薄く貫通させ、Scala 固有の不確実性（H2、`ConnectionIO`、scoverage）を早期に検証し、CI の 3 ジョブを成立させる |
| 中盤 | B4〜B14 | U2〜U5 | インサイドアウト | 資格・冪等・並行性・可変遅延・投影・削除・再構築を、ドメイン層・永続化から堅牢に作り込む。B7（自動確定）と B8（振り返り）は例外として、業務シナリオ起点で束ねる（下記） |
| 終盤 | B15 | U6 | アウトサイドイン | 既存の集約を業務シナリオで束ね、NFR の検証表と Release 1.0 の一貫性を担保する |

**中盤の中の例外**: B7（自動確定）は既存の確定の経路を組み合わせるだけなので、手動との競合を業務シナリオで確かめるアウトサイドインで進めます（Release 0.2 の区切り）。B8（役割別の振り返り）も、既存の週結果を読む投影で、画面（共有 `web`）から入るアウトサイドインで進めます。

### アプローチ選択の根拠

- **序盤（アウトサイドイン）**: API も基盤も未実装で、Scala・Cats Effect・doobie・H2 の組み合わせに未確認の前提が多い。受入シナリオから API を導出して薄く貫通させるのが安全（「API 未実装 → アウトサイドイン」）。
- **中盤（インサイドアウト）**: U2 の資格・冪等記録・競合検出、U3 の可変遅延の `simulateWeek`、U4 の観察者の権限、U5 の削除・再構築は、ドメインと永続化の正しさが外側の見た目より先に決まる。純粋関数・性質テスト・実 DB の統合テストで固めてから上へ展開する（「基盤確立後の複雑なドメイン → インサイドアウト」）。
- **終盤（アウトサイドイン）**: 基本実装は済み、U6 は既存の機能を横断の受入条件と性能の実測で束ねる。業務シナリオを起点に検証するのが要点（「基本実装済み × 複雑 → アウトサイドイン」）。

## 共通の TDD サイクル

### Red-Green-Refactor（全局面で不変）

- 失敗するテストを書き、**失敗を確認してから**最小限を実装し、通したらリファクタリングする。先回りして実装しない。
- 1 コミット 1 変更。コミットは Conventional Commits（日本語）。
- **土台を変える最初のスライド**（`Ports` の型、`handle` の型など）では、後続の振る舞いのテストも先に書いて失敗を確かめる。守れなかったときは、規則を壊すとテストが落ちることを個別に確かめて記録する（プロジェクトの規約）。
- 編集は、python・sed・perl・heredoc を使わず、ファイルツールで行う（Kotlin 版の B7・B4 の規律違反の反省）。

### テストの種類とレイヤー

[テスト戦略](../../design/beer-game-scala/test-strategy.md) の「テストレベルの定義」を正とします。要点だけ示します。

| レイヤー | テスト | 局面での主役 |
| :--- | :--- | :--- |
| domain（純粋関数） | munit（日本語の Given/When/Then）、ScalaCheck、cats-laws | 中盤 |
| application | ポートを差し替えたテスト、キャンセル安全性 | 中盤 |
| adapters（永続化・HTTP） | Testcontainers の実 PostgreSQL（`integration` ジョブ）、http4s の HTTP テスト | 序盤・中盤 |
| 受入 | 日本語 Gherkin（cucumber-scala の `@api`、Cucumber-JS + Playwright の `@ui`）（`acceptance` ジョブ） | 序盤・終盤 |

### CI の 3 ジョブ（案 Y。2026-11-26 にユーザーが選択）

| ジョブ | 内容 | 方針 |
| :--- | :--- | :--- |
| `check` | scalac の警告（`-Werror`）、Scalafmt、WartRemover、Scalafix、単体・性質テスト、行カバレッジ | **速く保つ**。ここに統合・受け入れを入れない |
| `integration` | Testcontainers の実 PostgreSQL 18 の統合テスト | `check` と並列 |
| `acceptance` | `@api` の受け入れ（許可リスト）。Undefined・Pending で失敗 | `check` と並列 |

3 ジョブすべてが緑でなければマージしません（team の規約）。実行時間は B2 で計測し、遅くなる場合はキャッシュを見直します（SR6）。

### 品質チェック（予定。B1 の実測で確定）

コマンドは `build.sbt` が決まる B1 で確定します。想定する構成は次のとおりです（憶測を避けるため、実コマンドは B1 の計画で確認して置き換える）。

- 整形: `sbt scalafmtCheckAll`
- 静的解析: scalac の `-Werror`、WartRemover、Scalafix（`scalafix --check`）
- テスト: `sbt test`（単体）、統合・受け入れは別プロジェクトから別ジョブで実行（ST7: `sbt test` に載せない）
- カバレッジ: scoverage の XML から行率を算出（案 C。算出スクリプトとそのテストは B1 の最初のスライド）

次の「静的解析とルール設定」の節に従います。**Bolt 1 で設定し、以降の全 Bolt で厳密に守ります。**

## 静的解析とルール設定（厳格に適用）

[関数型プログラミングガイド（Scala 編）第 9 章](../../reference/関数型プログラミングガイド_Scala編.md) の「静的解析とルール設定」を、**Bolt 1（B1）で設定し、以降の全 Bolt で、例外なく厳密に従います。** 設計の正本は [テスト戦略](../../design/beer-game-scala/test-strategy.md) の「静的解析と規約の検査」（厳格さの定義、層ごとのルールセット STT3）で、本書は進め方の判断だけを書き、内容を複製しません。

### なぜ B1 で、厳格に適用するのか

- 関数型の規約（`var`・`null`・`head` のような部分関数を避ける、副作用を境界に寄せる）は、レビューだけに頼ると漏れる（ガイド第 9 章の冒頭）。コードが増えてからの導入は、違反の一括の修正になる。
- ガイド §9.3 は「実際に起きた問題を数えてから入れる」と書くが、本プロジェクトは**複数人・長期の保守**（ガイドの推奨は「scalac のオプションと WartRemover を CI で止める。Scalafmt で整形を揃える」）にあたり、Kotlin 版・Rust 版の実績（違反 0 件、ベースラインなし）に揃える。
- ガイド §9.4「導入の進め方」の「新しいコードだけに適用する」は、**最初のコードから適用する**ことで満たされる。したがって `-Werror` を外したまま件数を数える段階は不要で、B1 の最初のスライドで全ルールを有効にする。
- **例外はルールを緩めるのでなく、プロジェクトを分けて外す範囲を明示する**（ガイド §9.4 の 3）。

### 厳格さの定義（例外なく守る）

| 項目 | 内容 |
| :--- | :--- |
| 違反の件数 | scalac の警告、Scalafmt、WartRemover、Scalafix の違反を **0 件**にする（`-Werror`） |
| ベースライン | **使わない**（既存の違反の許容リストを持たない） |
| 抑制 | **`@SuppressWarnings`・`scalafix:off` などの無効化コメントを使わない** |
| 緩和 | 外すルールと範囲を sbt のプロジェクトごとの設定で明示し、**ADR を記録して人が承認する**。「通らないから外す」は認めない |
| マージ | 1 つでも失敗したら、マージしない（team の規約）。ローカルでも同じコマンドで再現できる |
| 対象 | domain・application・adapters・テスト（ステップ定義を含む）のすべて。ただし WartRemover はテストに適用しない（ガイド §9.4「テストには適用しない」） |

### 使うツールと役割（ガイド §9.1）

| ツール | 役割 | 設定 |
| :--- | :--- | :--- |
| scalac のオプション | 警告をビルドの失敗にする。未使用・捨てた値を検出する | `-deprecation -feature -Werror -Wunused:all -Wvalue-discard -Wnonunit-statement` |
| Scalafmt | 整形 | `.scalafmt.conf`。CI で `scalafmtCheckAll` |
| WartRemover | 危険な書き方（Wart）をコンパイル時に禁止する。関数型の規約の中心 | 下の 13 個の Wart |
| Scalafix | 副作用を持つ呼び出しの禁止（`DisableSyntax.regex`） | `.scalafix.conf` |

PMD・detekt・ktlint は使いません（ガイド §9.1。Scala のソースは対象にならない、または Scala 3 の対応が未確認）。

### 守る規約と設定（ガイド §9.4 の「章とルールの対応」）

| 規約 | 設定 |
| :--- | :--- |
| `var` を使わない | WartRemover の `Var` |
| 可変コレクションを使わない | `MutableDataStructures` |
| 部分関数を避ける | `IterableOps`（`head`・`reduce` など）、`Return` |
| `null` と例外を使わない | `Null`、`Throw` |
| 失敗しうる取り出しを避ける | `OptionPartial`、`TryPartial`、`EitherProjectionPartial` |
| 型を偽らない | `AsInstanceOf`、`IsInstanceOf` |
| 未実装を残さない | `TripleQuestionMark`、`DefaultArguments` |
| 捨てた値を見逃さない | scalac の `-Wvalue-discard`、`-Wnonunit-statement`、`-Wunused:all`、`-Werror` |
| 標準出力・時計・スリープ・`unsafeRun*` を `IO` の外で呼ばない | Scalafix の `DisableSyntax.regex`（`println`、`System.currentTimeMillis`・`nanoTime`、`Thread.sleep`、`unsafeRun*`） |
| トランザクションの入口を 1 か所に限る | Scalafix の `DisableSyntax.regex`（`.transact(` ほか。許可する入口は `Transactions.scala` の 1 ファイル。設計は [バックエンドアーキテクチャ](../../design/beer-game-scala/architecture-backend.md) とテスト戦略） |
| 法則を守っていること | ルールでは表せない。cats-laws のテストで確かめる |
| `IO` を実行する場所を入口に限る | ルールでは表せない。レビューで守る（Scalafix の `unsafeRun*` の禁止が補助） |
| テストの中の例外 | WartRemover をテストのソースに適用しない |

### B1 で設定する手順（最初のスライドから）

1. **使う版でルールの確認を先に実行する。** ガイドの確認は Scala 3.7.0・WartRemover 3.4.1・Scalafix 0.14.3（Scala CLI）で、**sbt では未確認**。本プロジェクトの版（Scala 3.7.4、WartRemover 3.6.3、Scalafix 0.14.10 ほか。[技術スタック](../../design/beer-game-scala/tech-stack.md)）で、ガイドの確認用コード（期待 14 件、`pureOk`・`sumOk` は報告されない）と Scalafix の確認用コード（期待 3 件）を実行し、結果を記録する。期待と異なれば、B2 以降を止めて代替を選ぶ（技術スタックの ST4）。
2. **全 Wart と scalac オプションを、最初のコードより前に `build.sbt` に有効化する。** 層ごとのルールセットを sbt のプロジェクトに分ける（`domain`・`application`・`adapterHttp`・`adapterPersistence`・`app`・テスト）。
3. **Scalafmt と Scalafix の設定ファイルを置く。** `scalafix --check` が Scala 3 のインデント構文を解析できることを確かめる（`--scala-version` の指定。`scalafixAll` が全プロジェクトで動くかは B1 で確認する）。
4. **ルールそのものをテストファーストで確かめる。** 違反するコードとしないコードを並べた fixture を用意し、期待件数と行を使う版で確かめ、その確認を CI に組み込む。
5. **違反コードを 1 つ置くと失敗することを確かめる**（`domain` で `println`・`var`・`head`・`cats.effect` の `import`）。ローカルの同じコマンドと、CI の `check` ジョブの両方で確認する。確認後は違反コードを消す。
6. **全コードが違反 0・ベースラインなし・`@SuppressWarnings` なしで緑**であることを B1 の完了条件にする。

### CI との連携

- `check` ジョブが、scalac の警告（`-Werror`）、`scalafmtCheckAll`、WartRemover、`scalafix --check` を判定する（案 Y。`check` は速く保つ）。B1 のローカルの設定を、B2 で `check` ジョブに載せる。
- **ルールを後から緩める変更は、設定の差分として必ずレビューの対象にする**（ADR と人の承認が要る）。

### 限界と、補う方法（ガイド §9.4）

| 限界 | 補う方法 |
| :--- | :--- |
| `DisableSyntax.regex` は文字列のパターン。`import` の別名やラッパーの中の呼び出しを見逃す | レビューで確認する。記号に対する検査（`Disable`）は SemanticDB が要り未確認のため、必要になったら ADR で導入を判断する |
| 意味（遷移表の許可の漏れ、法則、`IO` を実行する場所）は検査できない | テスト（遷移表の拒否側、cats-laws）とレビューで守る |
| 文字列から読み戻す境界の `match` は、型で止まらない | 境界で未知の値を失敗として扱い、性質テストで確かめる |
| Wart の名前とメッセージは、WartRemover の版で変わりうる | 版を上げるときに fixture を再実行する |

### 守り続けるために

- ルールを増やすのは、同じ指摘をレビューで繰り返したときに限る（ガイド §9.4 の 4）。増やすときは fixture と期待件数を足す。
- Bolt 終了報告に、静的解析の状態（違反 0 件、緩和の有無、ADR）を記録する。
- WartRemover・Scalafix・Scala の版を上げるときは、fixture を再実行し、結果を ADR または Bolt 終了報告に記録する。

## デモ項目を受け入れ基準とする

Bolt の「完了条件」の受入シナリオを、局面横断の受け入れ基準とします。**当該 Bolt の受入条件の Gherkin シナリオがすべて green であることを、Bolt の完了条件に含めます。** green でなければ Bolt を閉じません。追加したシナリオは以降も実行し、回帰を防ぎます。

- Scala 側が実行するシナリオは、共有 `features/` の `@AC` タグから導く**許可リスト**で決めます。共有する `.feature` に Scala 専用のタグを書き込みません（Kotlin 版・Rust 版に影響するため）。
- 許可リストの入力となる U1〜U3 の AC の一覧は、B1 の計画で番号まで確定し、人が承認します。

### アウトサイドインの入口を BDD で定義する（採用）

**採用します。** team の規約（BDD。Given/When/Then と失敗する自動テストを実装前に定義）に従い、記法・処理系・手順は [BDD 導入ガイド](../../reference/BDD導入ガイド.md) と [テスト戦略](../../design/beer-game-scala/test-strategy.md) を正とします。

| 項目 | 方針 |
| :--- | :--- |
| 使う局面 | 序盤・終盤のアウトサイドインで主役。中盤は munit の単体・性質が主役で、Gherkin は既存分の回帰実行 |
| 合意 | シナリオは、実装の前に人が検証して合意する（AI が書いた場合も同じ。Mob Elaboration） |
| 記述言語 | 日本語 Gherkin（`# language: ja`）。プロジェクト内で混在させない |
| 処理系 | `@api` は cucumber-scala（sbt の別プロジェクト `acceptance`。実行方式は B1 で確認）、`@ui` は Cucumber-JS + Playwright |
| ステップ定義 | 薄く保ち、業務ロジックを持ち込まない。「まだ無い内側」の設計を駆動する |

サイクルは、シナリオに翻訳して合意 → Undefined → ステップ定義で Pending → Red → 内側へ一段ずつ TDD で Green → リファクタリング（シナリオは業務の言葉のまま）です。

## ドキュメントをコードと同期させる（Living Documentation）

**採用します。ただし、これから書くコードから適用し、既存の設計書への一括適用はしません。** 手法は [Living Documentation 導入ガイド](../../reference/LivingDocumentation導入ガイド.md) と個別の導入ガイドを正とします。

### 局面ごとの重点

| 局面 | 重点 |
| :--- | :--- |
| 序盤 | アーキテクチャ（層の依存）を sbt の `dependsOn` と検査で守り、図を生成する仕組みをスケルトンに含める。生きたドキュメント（Gherkin の公開）の最小の導線を作る |
| 中盤 | ドメインの用語集（Living Glossary）をコードから生成し、ユビキタス言語を一本化する。判断の根拠は ADR に残す |
| 終盤 | 手動と自動確定の競合の処理チェーンをガイドツアーとして案内する。タグでシナリオダイジェストを作る |

### 決めること

- **コードに持たせるもの**: 構造・用語・依存関係。`docs/design/` に手で複製しない。`docs/design/` には、コードから読み取れない意図・判断・却下した代替案を残す。
- **重複する知識の検証**: 公開 API の契約は契約テスト（CI）で、シナリオとコードは受け入れテストで守る。
- **生成と公開**: 用語集・図・ツアーの生成を CI のどの段階で行い、どこに公開するかは B1 の計画で決める（手作業で更新する一覧は作らない）。
- **根拠の記録先**: 設計判断は ADR、変更の意図はコミットメッセージ。

### Bolt の完了条件に加えること

- 生成するドキュメントの生成が CI で成功している。
- その Bolt で下した設計判断が ADR に記録され、コードで表せない根拠だけが `docs/design/` に反映されている。
- 手書きでコードの内容を複製した一覧・図が新たに増えていない。
- **Bolt 完了後のレビューで、毎回必ず `apply-living-documentation` を実施し、結果を Bolt 終了報告に記録している**（プロジェクトの規約。`bolt_*_report.md` の書き込み後にリマインドする hook を併用する）。

## 序盤: アウトサイドイン（B1〜B3）

### 目的

Scala 版の未確認の前提を早く確かめ、1 ゲーム・4 役割・1 週のウォーキングスケルトンと、検証用 CI（3 ジョブ）を成立させる。AI の出力の質を見て、以降の承認ゲートの密度を決める。

### 対象

U1（US1.1・1.2・2.1・2.2・2.3（基本）、US6.1 の AC6.1.1・6.1.2・6.1.4）。

### 手順の要点

1. **B1 の最初に**、H2（PostgreSQL モード）の動作範囲と、テスト戦略の「B1 の受入条件」の表の未確認の前提を実測する。結果は成立・不成立で記録する。
2. **静的解析を、最初のコードより前に設定する**（「静的解析とルール設定」の節の B1 の手順。全 Wart・scalac オプション・Scalafmt・Scalafix、層ごとのルールセット、fixture による確認、違反コードで失敗することの確認）。以降のコードは、すべて違反 0 件・ベースラインなしで書く。
3. 行率の算出スクリプトとそのテストを、最初のスライドに置く（カバレッジのジョブが赤のままでマージが止まるのを避ける）。
4. 作成 → 参加 → 割り当て → 開始 → 入力 → 確定 → 状態の表示を、日本語 Gherkin から内側へ貫通させる（H2 と PostgreSQL の両方）。
5. API を追加・変更するときは、仕様（`contracts/openapi.yaml`）→ 契約テスト（Red）→ 実装 → 型の再生成 → 画面の順に進める。契約テストの基盤は B2 で CI に組み込む。
6. B2 で、B1 で設定した静的解析を CI の `check` ジョブに載せて 3 ジョブを成立させ、B3 で入力・週確定を完成させて Release 0.1 とする。

### 承認ゲート

密（ステップごとに検証）。B1 では、Gherkin のシナリオ、依存関係の導入と版、AC の一覧、静的解析のルールと層ごとの除外の理由を、人が検証する。

### 完了条件

- 当該 Bolt の受入シナリオが green（Undefined・Pending が 0）。
- **B1 の終わりに、静的解析が設定済みで、ガイドの確認用コードと fixture の期待件数が使う版で一致し、全コードが違反 0 件・ベースラインなし・抑制なしで緑**（ローカル）。規約違反コードを 1 つ置くとローカルで失敗する。
- B2 の終わりに、同じ検査が CI の `check` ジョブで判定され、規約違反コードを置くと CI が失敗する。
- B1 の終わりに、未確認の前提の表の全行が確認済み。
- B2 の終わりに、3 ジョブが GitHub Actions で緑。
- Release 0.1: U1 の許可リストの 100%。

**B1 の結果が悪ければ（H2・`ConnectionIO`・scoverage）、B2 以降を止めて設計を見直す。**

## 中盤: インサイドアウト（B4〜B14）

### 目的

資格・冪等・競合検出・可変遅延の計算（U2・U3）、観察者の権限と出力（U4）、保持・削除・再構築・観測・本番の定義（U5）を、純粋関数・性質テスト・実 DB の統合テストで堅牢に作り込む。

### 対象

B4（進行の継続と資格）、B5（共同担当と共同入力。D3 の入れ替え）、B6（カスタム条件。可変遅延の `simulateWeek`）、B7（自動確定。アウトサイドインの例外）、B8（役割別の振り返り。アウトサイドインの例外）、B9（観察者）、B10（出力）、B11（保持と削除）、B12（投影の再構築・スキーマ進化）、B13（観測の完成）、B14（コンテナ・本番の定義）。

### ワークフロー

ドメイン（`decide`・`evolve`・`simulateWeek` の性質、golden テスト）→ アプリケーション（ポートの差し替え、キャンセル安全性）→ 永続化（Testcontainers の実 DB。版の一意制約、追記の競合）→ HTTP → 受入シナリオ。

### 要点

- **判定の順は「占有 → 割当てと資格の再検査 → 再送の照合 → 状態の検査」**（冪等記録の照合を認可の後に置く）。失効した旧担当者の再送は 403 にする。
- D3: 失効済みの旧担当者の入れ替えは、未失効の旧担当者にだけ `CredentialRevoked` を出す。
- 同時の保存で更新を失わないことを、並行の統合テストで確かめる。
- 遅延 0 を含む可変遅延でも、`simulateWeek` の性質が保たれることをプロパティテストで確かめる。
- B7（自動確定）: 手動との競合を業務シナリオで確かめ、「一度だけ確定される」ことを 2 プロセスの並行テストで担保する。
- B9（観察者）: 他役割の値・将来の需要・参加コードが取得できないことの否定テストと、DB ロール・接続プールの分離の検査（`current_user`）を先に書く。
- B11（保持と削除）: **マイグレーションの承認と個別の計画書を先に取る。** 削除後に `game_id` を持つ全表に行が残らないことを `information_schema` で検査する。
- B12（再構築）: 再構築の時間を実測する（Kotlin 版の NF-P18 が目標を超えた反省。SR13）。再構築中のコマンドの応答（待つか 503 か）を、人が決める項目として計画に載せる。
- B14（本番の定義）: **AWS には適用しない**（定義と `terraform validate` まで）。RPO・RTO は机上確認で、障害の種類ごとに区別して記録する。

### 承認ゲート

B4・B5・B7・B9・B11・B12・B14 は密（高リスク）、B6・B8・B10・B13 は標準。

### 完了条件

- 当該 Bolt の受入シナリオが green。
- 否定テスト（鍵のローテーション、失効後の再送、観察者の開示、削除後の残り）が通る。
- 並行の統合テストが通る。
- **Release 0.2（B7）**: U1〜U3 の許可リストの 100% が通り、CI の 3 ジョブが緑。
- 指標（許可リストの通過割合、パリティ、未確認の前提、カバレッジ）を Bolt ごとに確認し、Bolt 終了報告に記録する。

## 設計ドキュメントの整合

各 Bolt の着手時・実装中・完了時に、Bolt の計画と `docs/design/beer-game-scala/` の整合を確認します。Bolt の計画は局所ビュー、設計書は全体の「正」です。実装で設計判断が変わったら、その場で設計書を更新します（`verified` の再確認が要る）。着手時は `validating-iteration-plan`、広域の検証は `validating-design` を使います。

**Kotlin 版の ADR の追従**: ADR-001 の引き継ぎ表は Kotlin 版の ADR を時点で写したものです。各 Bolt の開始時に、`git log -- docs/adr/beer-game-kotlin/` を 1 回確認し、変更があれば該当行に反映します（担当と頻度は人が決める）。

## 局面移行時の一貫性維持

- 局面が変わっても不変の規律: Red-Green-Refactor の三原則、1 コミット 1 変更、静的解析 0 件、CI の 3 ジョブ緑。
