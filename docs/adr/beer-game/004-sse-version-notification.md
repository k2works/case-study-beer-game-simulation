# ADR-004: リアルタイム通知は SSE で版を通知し、状態は再取得する

画面の更新は、SSE で「版が進んだ」ことだけを通知し、状態は API から再取得する。

日付: 2026-11-09

## ステータス

提案中（実装済みの決定を事後に記録したもの。レビュー待ち）

## コンテキスト

進行役の操作や他の参加者の入力を、画面に 2 秒以内に反映する必要がある。API は複数タスクで動き、プロセスをまたいで更新が起きる。役割ごとに見える情報が違うため、通知に状態そのものを載せると漏洩の危険がある。

- 参考: [フロントエンドアーキテクチャ](../../design/beer-game/architecture-frontend.md)

## 決定

- サーバーは SSE（`/api/v1/games/:id/events`）で、イベントの版と相関 ID だけを `state-version` として送る。内容は運ばない。
- クライアント（`LiveStateAdapter`）は通知を受けたら、権限に応じた状態を API から再取得する。取得した版が現在より古ければ捨て、同じ版で内容が違えば反映する。
- SSE が切れたら 1 秒間隔のポーリングに切り替え、再接続したら止める。接続状態を画面に表示し、自動更新の停止と手動更新を利用者に提供する。
- サーバー側は、PostgreSQL の `LISTEN/NOTIFY` を合図に、永続化済みのイベントの版から読み直す。`NOTIFY` が失われても、定期的な照合で補う。

### 変更箇所

- `apps/beer-game/src/api/app.ts`（`events`）
- `apps/beer-game/src/infrastructure/postgres-game-repository.ts`（`subscribeEvents`）
- `apps/beer-game/src/ui/LiveStateAdapter.ts`

### 代替案

- WebSocket: 双方向だが、本システムでは通知だけで足り、プロキシや CloudFront 越しの扱いが複雑になる。
- SSE で状態も送る: 役割別の開示制御を通知経路にも実装する必要があり、漏洩の危険が増える。
- ポーリングのみ: 実装は単純だが、2 秒以内の反映に短い間隔が要り、負荷が増える。

## 影響

### ポジティブ

- 通知に情報が載らないため、役割別の開示制御は既存の取得 API だけで済む。
- 通知の順序入れ替えや重複に強い（版で比較する）。
- 複数タスクでも、永続化済みの版を基準にそろう。

### ネガティブ

- 通知のたびに再取得するため、取得 API の負荷が増える。
- ALB のアイドルタイムアウト（60 秒）より短いハートビート（15 秒）を保つ必要がある。

## コンプライアンス

- SSE の応答に状態の内容が含まれないこと。
- 接続断のテスト（SSE 失敗時にポーリングで自分の状態だけが見えること）が通ること（`tests/e2e/u5.spec.ts`、`tests/u5/live-adapter.test.ts`）。
