# ADR-002: 状態を持たない API とゲーム単位の行ロックで整合性を保つ

API プロセスにゲームの状態を持たせず、リクエストごとに集約を読み込み、ゲームの行をロックして保存する。

日付: 2026-11-09

## ステータス

提案中（実装済みの決定を事後に記録したもの。レビュー待ち）

## コンテキスト

本番では API を複数タスクで動かす（常時 2 タスク、最大 4）。同じゲームの操作が別のタスクに届いても、4 役割の意思決定を揃えて週を一度だけ確定する整合性を保つ必要がある（BR-12）。

- ゲーム 1 件のデータ量は小さい（4 役割、数十週）。
- 同じゲームに同時に書き込むのは、最大でも参加者 4 人と進行役。
- 参考: [データモデル設計](../../design/beer-game/data-model.md)、[バックエンドアーキテクチャ](../../design/beer-game/architecture-backend.md)

## 決定

API は状態を持たず、書き込みのたびに次の手順をとる。

1. トランザクションを開始し、`games` の行を `SELECT ... FOR UPDATE` でロックする。
2. データベースからゲーム 1 件を `GameService` に読み込み、ユースケースをメモリ上で実行する。
3. 変更点（セッション、参加者、意思決定、結果、イベント、冪等記録）を同じトランザクションで保存する。

読み取りは `REPEATABLE READ READ ONLY` のトランザクションで行う。メモリのみで動かす場合（`DATABASE_URL` なし）は、同じ `GameService` を単一プロセスで使う。

### 変更箇所

- `apps/beer-game/src/infrastructure/postgres-game-repository.ts`（`read`、`write`）
- `apps/beer-game/src/api/app.ts`（`readGame`、`writeGame`）

### 代替案

- プロセス内に状態を持ち、ゲームを特定のタスクに固定する（スティッキー）: タスクの入れ替えや障害でゲームが失われる。
- 楽観的排他だけ（`version` の比較）にする: 競合時の再試行が必要になり、4 人が同時に操作する場面で体験が悪くなる。版の比較は API の契約（`If-Match`）としては併用する。
- 分散ロックを別に用意する: 構成要素が増える。PostgreSQL の行ロックで足りる。

## 影響

### ポジティブ

- タスクを自由に増減でき、ゲームが特定のタスクに依存しない。
- 同じゲームへの書き込みが直列になり、週確定の一回性を保てる。

### ネガティブ

- 同じゲームの書き込みが待ち合う。参加人数が増えるとロック待ちが目立つ可能性がある。
- 毎回ゲーム全体を読み込む（イベントや冪等記録を含む）ため、ゲームが長いほど読み込みが増える。

## コンプライアンス

- 書き込み経路が `PostgresGameRepository.write` を通ること（`GameService` を直接更新しない）。
- 2 つの API プロセスから同じゲームを操作する統合テストが通ること（`tests/u5/multi-process.integration.test.ts`）。
