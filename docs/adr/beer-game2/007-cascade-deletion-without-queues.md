# ADR-007: 保持削除を 1 トランザクションのカスケード削除にし、キューを廃止する

保持期間後の削除を、`games` の削除と、外部キーの `ON DELETE CASCADE` による 1 トランザクションで行う。所有者別の SQS キューとワーカーは廃止する。

日付: 2026-11-09

## ステータス

提案中（レビュー待ち）

## コンテキスト

v1 の保持削除は、所有者（U1〜U3）別の SQS キューとワーカーによる Saga だった。しかし、すべてのデータが 1 つの PostgreSQL にあるため、所有者別の削除は、分散の整合性の問題を、自ら作っていた。結果として、`outbox_events` と `idempotency_records` が、どの所有者の削除にも含まれず、削除後にデータが残る漏れがあった。

## 決定

- すべての表が、`games(game_id)` への外部キー（`ON DELETE CASCADE`）を持つ。**`DELETE FROM games WHERE game_id = $1` の 1 回で、関連するデータがすべて消える。**
- 保持方針と、削除の進行（`retention_policies`、`deletion_runs`、`deletion_attempts`）、受領記録（`deletion_receipts`）は、証跡のため、`games` を参照せず、ゲーム ID のダイジェストだけを持つ。
- 削除は、EventBridge で 5 分ごとに起動する ECS タスクが、期限に達したゲームを検出して実行する。失敗は、最大 5 回、指数バックオフで再試行し、続けて失敗したら通知する。
- SQS、所有者別のワーカー、学習用のキュー、エクスポート用の S3 バケットは作らない。
- 削除の網羅は、**`game_id` 列を持つすべての表に、削除後に行が残らない**ことを、テストで確認する（表の一覧は `information_schema` から取得する）。

### 代替案

- v1 のまま（所有者別のキューとワーカー）: 分散の整合性の問題と、削除漏れの危険が残る。
- アプリケーションで、表ごとに削除: 表を足したときの削除漏れが、再発する。
- データベースの TTL に任せる: 完了の判定と、証跡を残す要件を満たせない。

## 影響

### ポジティブ

- 削除漏れが、構造的に起きにくい（外部キーが保証する）。
- 構成要素が大きく減る（SQS、ワーカー、所有者別の進捗表）。
- 削除が、原子的になる。

### ネガティブ

- 1 回の削除が、大きなゲームで重い場合に、ロックの影響を確認する必要がある（1 ゲームのデータは小さく、問題になりにくい）。
- 将来、別のストア（S3 など）にデータを置くと、削除の範囲が広がる（その時点で再検討する）。

## コンプライアンス

- 削除後に、`game_id` 列を持つすべての表に、そのゲームの行が残らないこと（テスト）。
- 削除の失敗が、通知されること。
