# ADR-012: ECR、OIDC、ステージング自動・本番承認・ブルー/グリーンのパイプラインと、リモートの Terraform を採用する

イメージを ECR に保管し、GitHub Actions から OIDC でデプロイする。ステージングは自動、本番は手動の承認後にブルー/グリーンで行う。Terraform の状態は、環境ごとに分離したリモートに持つ。

日付: 2026-11-09

## ステータス

提案中（レビュー待ち）

## コンテキスト

v1 では、CI の staging と production が `echo` のプレースホルダーで、デプロイが実装されていなかった。イメージは GHCR に公開されていたが、インフラ定義は ECR を想定し、ECR の定義も無かった。Terraform には `backend` が無く、状態の保管先が未定義で、ネットワークや WAF が定義の外にあった。

## 決定

- イメージは **ECR**（不変のタグ、プッシュ時のスキャン）に保管し、コミット SHA で固定する。
- GitHub Actions は、**OIDC** で、環境ごとの最小権限のロールを引き受ける（長期のアクセスキーを置かない）。
- main へのマージで、**ステージングへ自動デプロイ**（マイグレーションを 1 回限りのタスクで適用 → ローリング → スモークテスト）。
- 本番は、**手動の承認**後、ステージングで承認した同じダイジェストを、**ブルー/グリーン**（CodeDeploy）でデプロイし、ベイク期間（合成監視・SLO）で劣化を検知したら、直前の版へ戻す。
- Terraform の状態は、**暗号化した S3 とロック**の**リモート**に、**環境ごとに分けて**持つ。ネットワークも Terraform のモジュールで管理する。
- スキーマは、拡張 → 互換 → 縮小の順で、旧アプリと互換の期間を設ける。

### 代替案

- 手動のデプロイ: 属人的で、ロールバックが遅い。
- 本番もローリングのみ: 劣化時の切り戻しが遅い（小規模なので、ステージングはローリングで足りる）。
- GHCR を使い続ける: ECS から取得する認証と、スキャンの整備が別に要る。

## 影響

### ポジティブ

- デプロイとロールバックが自動化され、再現できる。
- 環境の再現と、複数人での変更が、安全になる。

### ネガティブ

- CodeDeploy と、ブルー/グリーンの設定の工数がかかる。
- ブルー/グリーンのために、一時的にタスクが 2 倍になる（費用）。

## コンプライアンス

- ステージングへのデプロイが、main のマージで自動で行われること（AC6.2.1）。
- ロールバックの手順が、ステージングで、毎回確認されること（AC6.2.3）。
