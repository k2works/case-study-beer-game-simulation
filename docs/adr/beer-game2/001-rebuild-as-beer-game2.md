# ADR-001: beer-game2 として要件と設計を改訂し、作り直す

beer-game の分析と実装から得た知見をもとに、`beer-game2`（v2）として、要件・設計・実装を新しく作る。

日付: 2026-11-09

## ステータス

承認済み（2026-11-09、ユーザーの指示と、範囲・技術・既存の扱いの回答による）

## コンテキスト

beer-game（v1）は、ウォーキングスケルトン（U1）から U5 まで実装され、199 件のテストが通る状態にある。一方、`docs/` を正本として分析を整理する過程で、実装と要件・設計の間に、次の不足と差分が見つかった。

- 学習の主目的に関わる不足: 振り返りと出力が、役割別でなく全役割の合計だけ（US4.2、US4.3）
- 運用の前提の不足: ログとメトリクスが無い。`/health` がデータベースを確認しない。デプロイが未実装
- セキュリティの不足: 資格のダイジェスト用の鍵が、本番で固定の開発用の値。資格の有効期間が設計と異なる。セキュリティヘッダーが無い。CI に脆弱性の検査が無い
- 未実装の要件: 同一役割の共同担当、カスタム条件、観察者の独立した立場、週の自動確定
- 設計の偏り: ルールが `GameService` に集中し、ドメインは週次計算しか持たない。`api/app.ts` に機能が同居している
- 削除対象の漏れ（`outbox_events`、`idempotency_records`）

これらは、後付けで直すより、**要件と設計を改訂したうえで、最初から正しい構造で作る**ほうが、変更を楽に安全にできる状態に近づくと判断した。参考: [ユーザーストーリー](../../requirements/beer-game/user_story.md) の「実装との差分のまとめ」、[非機能要件](../../design/beer-game/non-functional.md)、[運用要件](../../design/beer-game/operation.md)。

## 決定

- `beer-game2` として、`docs/` と `apps/` に、新しいプロジェクトを作る（`apps/beer-game2/`）。
- 分析成果物（要件、ユースケース、ストーリー、設計）は、beer-game の `docs/` を複製して出発点とし、差分を反映して**改訂**する。
- v2 の範囲に、次の 4 件を含める（beer-game で未実装・未決定だったもの）。
  - 同一役割の共同担当
  - カスタム条件（初期在庫、遅延、費用単価、公開範囲の変更と、「カスタム」の記録）
  - 観察者の独立した立場
  - 週の自動確定（進行役の確定操作は残す）
- 技術スタックは、beer-game を踏襲し、版だけ更新する（TypeScript、Fastify、React、Vite、PostgreSQL、AWS、Terraform）。版は [技術スタック](../../design/beer-game2/tech-stack.md) に従う（確認の結果、Node は、決定時に想定した 24 ではなく、最新の LTS である 26 を採用した。[ADR-013](./013-tech-stack-versions.md)）。
- beer-game は、未コミットだった U3〜U5 の作業をコミットして保全し（`1af35d2`、`9615c9e`）、参照用に残す。beer-game2 の完成後に、廃止を判断する。
- beer-game の ADR（`docs/adr/beer-game/001`〜`008`）は、履歴として残す。v2 で引き継ぐ判断は、v2 の ADR として改めて記録する。

### 代替案

- beer-game に、不足を足し続ける: 差分の多くが構造（集約の分割、観測性、デプロイ）に関わり、継ぎ足しでは、変更しにくい形が残る。
- 白紙から再分析する: 分析の積み重ね（用語、ユースケース、数値目標、差分の整理）を捨てることになる。
- 要件だけ引き継ぎ、設計は作り直す: 設計にも、再利用できる判断（純粋な週次計算、冪等性、SSE の版の通知など）が多い。

## 影響

### ポジティブ

- 不足を、要件と設計の段階で解消できる（役割別の振り返り、観測性、デプロイを最初から含める）。
- beer-game の実装は動く参照として残り、v2 の振る舞いの比較や、移植の元になる。

### ネガティブ

- 二重のメンテナンスが、一定期間発生する（beer-game と beer-game2）。
- 実装を作り直す工数がかかる。v1 のコードを、そのまま使えない部分が出る。
- 共同担当と自動確定は、集約の設計と整合性（同時操作、確定の一回性）に影響し、設計の見直しが必要になる。

## コンプライアンス

- beer-game2 の分析成果物が、`docs/*/beer-game2/` に置かれ、`apply-okf` と構成の検査が通ること。
- beer-game の ADR を、v2 で引き継ぐものは、v2 の ADR に記録されていること。
- beer-game2 の完成時に、beer-game の廃止の判断（ADR）を行うこと。
