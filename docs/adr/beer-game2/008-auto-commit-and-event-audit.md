# ADR-008: 自動確定を最後の意思決定と同じトランザクションで行い、監査をイベントに統一する

自動確定は、最後の意思決定を保存した同じトランザクション内で `Session` 集約が判断して行う。監査は、専用のテーブルを作らず、イベントに操作者と入力値を残す。

日付: 2026-11-09

## ステータス

提案中（レビュー待ち）

## コンテキスト

v2 では、4 役割の入力がそろった時点で、週を自動で確定する（FR-18）。確定の直前に別の人が変更する隙間があると、確定される値が、利用者の意図と異なる。また、v1 は、監査のための `operation_audit` を定義していたが使われず、代理入力の履歴には入力値が残らなかった。

## 決定

- **自動確定は、最後の意思決定の保存と同じトランザクション内**で、`Session` 集約が判断して実行する（確定方式が AUTO で、4 役割がそろい、進行中のときだけ）。ユースケースは判断しない。
- 一時停止中は確定しない。再開時に、そろっていれば確定する。
- 手動の確定と同時に起きても、`sessions.version` と `week_results` の主キーにより、確定は一度だけ。
- 猶予の時間は設けない（保存の操作が、明示的な意思表示であるため）。
- **監査は、イベントに残す**（操作者の種別と ID、役割、入力値、時刻、相関 ID）。`operation_audit` は作らない。

### 代替案

- 別のタスクで、非同期に自動確定する: 入力がそろってから確定までの隙間で、変更が入り、不整合な体験になる。
- 猶予（数秒）を設ける: 訂正の余地は生まれるが、確定が遅れ、実装が複雑になる。
- 専用の監査テーブル: イベントと二重管理になり、整合を保つ手間が増える。

## 影響

### ポジティブ

- 自動確定の隙間が無く、整合性が保たれる。
- 監査が 1 か所（イベント）に集約される。

### ネガティブ

- 入力の保存のトランザクションが、確定の計算を含み、長くなる（計算は純粋で軽い）。
- 最後の入力者が、他の人の確定を引き起こす（学習の体験として、許容する前提）。

## コンプライアンス

- 自動確定が有効なゲームで、4 役割の入力がそろうと一度だけ確定されること（AC2.4.1〜AC2.4.4）。
- 代理入力のイベントが、入力値と操作者を含むこと（AC3.1.2）。
