# ADR-006: イベントのスキーマ進化を EventCodec のアップキャストと 2 段階リリースで行う

イベントの `payload` の JSON は、kotlinx.serialization と `adapter-persistence` の `EventCodec` で変換し、ドメインのイベントにシリアライズの注釈を付けない。アップキャストは `EventCodec` に置く。イベントの形を変えるリリースは 2 段階（読める版を先に展開し、次のリリースで書く版を上げる）で行い、N-1 互換の CI ジョブで守る。

日付: 2026-11-14

## ステータス

提案中（レビュー待ち）。ただし、JSON の方式（kotlinx.serialization と `EventCodec`）は、設計書で決定済みとされている。

## コンテキスト

ES では、イベントが正本であり、書き換えない。復元（FR-12）、監査、過去のゲームの再生は、保存済みのイベントを読めることに依存する。機能が増えれば、イベントの形（項目の追加、名前・型の変更、新しい種類の追加）は変わる。

変換の置き場所には、2 つの問題がある。ドメインのイベントに注釈を付けると、`domain` がシリアライズの基盤に依存し、`schema_version` の管理がドメインに漏れる（バックエンドの設計判断 BD5）。

もう 1 つは、ロールバックである。新しい版のアプリが新しい `schema_version` のイベントを書いた後に旧版へ戻すと、旧版がそのイベントを読めず、ストリームが壊れた状態になる（運用の障害パターン 16、NF-O11）。ローリングデプロイの途中でも、新旧のアプリが混在する。

## 決定

- **変換の置き場所**: `adapter-persistence` の `EventCodec` が、永続化用の DTO（kotlinx.serialization。`@Serializable`、`@SerialName` で `event_type` を固定）とドメインのイベントを相互に変換する。**ドメインのイベントには、シリアライズの注釈を付けない**。変換は `when` で網羅し、イベントの追加でコンパイルが失敗するようにする。DTO には、表示名・資格の値・招待コードの値のフィールドを持たせない（型で防ぐ）。
- **アップキャストの置き場所**: `EventCodec`（`adapter-persistence`）に置く。旧版の DTO を新版へ変換する純粋関数の列で、読み込み時に、`evolve` へ渡す前に適用する。1 件を複数件へ展開できる関数にする（ストリームの版は変えない）。
- **イベントは書き換えない**。マイグレーションで過去のイベントを新しい形へ書き換えない。
- **2 段階のリリース（読む → 書く）**:
  1. **読める版を上げる**: 新しいアプリは、新旧の両方を読め、書くのは旧 `schema_version` のまま。ローリングデプロイの途中で旧アプリと混在しても、旧アプリは新しい版のイベントに出会わない。
  2. **書く版を上げる**: 全タスクが新しいアプリになり、ベイク期間（合成監視、整合性）を通した後、設定で新しい `schema_version` を書くように切り替える。設定の変更は、本番の環境変数の変更に当たるため、確認必須（承認ゲート）とする。
- **新しいイベントの種類の追加**は、`schema_version` では制御できない。そのため、新しい種類を書き始める前に、読む側を 1 リリース以上先行させる。
- **N-1 互換の CI ジョブ**: 直前のリリースの読み取り側（アップキャストと `evolve`）で、現在の書く版の golden（各イベントの種類を網羅したイベント列の JSON）を再生し、期待する状態になることを確かめる。落ちたら、新しい種類を書き始めるのを 1 リリース以上遅らせる。
- **未決**: 書く版の設定をどこで持つか（環境変数か、設定サービスか）。N-1 互換ジョブが使う「直前のリリース」の取得方法（タグから取得してビルドするか、保存した成果物を使うか）。

詳細は [データモデル](../../design/beer-game-kotlin/data-model.md) の「イベントのスキーマ」、[バックエンドアーキテクチャ](../../design/beer-game-kotlin/architecture-backend.md) の「イベントの JSON 変換」と設計判断 BD5、[運用要件](../../design/beer-game-kotlin/operation.md) の変更管理（イベントスキーマの進化）、[非機能要件](../../design/beer-game-kotlin/non-functional.md) の NF-O11 を参照。

### 代替案

- **ドメインのイベントにシリアライズの注釈を付ける（却下）**: 設計判断 BD5 の案 B。変換のコードが無いが、ドメインが基盤に依存し、`schema_version` の管理がドメインに漏れる。
- **イベントを一括で移行する（却下）**: 運用要件の案 C（マイグレーションで過去のイベントを新しい形へ書き換える）。読み込み時のアップキャストが不要になるが、イベントは変更しないという原則に反し、監査と再生の信頼を失う。
- **1 回のリリースで読み書きを同時に切り替え、問題があれば前進で直す（却下）**: 運用要件の案 B。リリースは 1 回で済むが、新しい版のイベントが書かれた後は旧イメージへ戻せず、研修中の障害時に取れる手段が減る。
- **新旧を同じリリースにして、ロールバックでは DB の復元も行う（却下）**: 非機能要件の案 B。復元の時間（RTO）に影響し、確定済みの週が失われうる。

## 影響

### ポジティブ

- `domain` がシリアライズの基盤に依存しない。形の変更を、永続化の層で閉じられる。
- 書く版を戻せば、旧イメージへ戻せる。ロールバックの余地が最大になる。
- イベントが不変のため、監査と再生の信頼が保たれる。`WeekCommitted` は結果を事実として含み、計算規則を後で直しても、過去のゲームの再生結果が変わらない。

### ネガティブ

- 変換のコードが増える。往復の性質テストと golden で守る。
- イベントの形を変えるリリースが 2 回に分かれ、書く版の切り替えの設定と承認が要る。
- 書く版を上げ、新しい版のイベントが `events` に書かれた後は、旧イメージへ戻せない。復旧は、前進して直すか、書く版を戻して DB を復元する（データを失う。研修の途中では避ける）かである。リリースの記録に、旧イメージへ戻せる期間を記載する。
- アップキャストの漏れは、イベントの読み込み失敗（未知の `event_type`・`schema_version`、デコード失敗）として現れる。1 件でも発生したら調べる。

## コンプライアンス

- **B1（基盤と縦の最小）**: `EventCodec` を最初のイベントから `adapter-persistence` に置く。`domain` と `application` が kotlinx.serialization に依存しないことを、依存関係の宣言の検査で確認する（違反は CI が失敗する）。
- **B2（規約検査・CI・テスト基盤）**: N-1 互換ジョブの雛形を CI に入れる。直前のリリースが無い間（最初のリリース前）は実行しない。
- **B12（投影の再構築・整合検査・スキーマ進化）**: `EventCodec` とアップキャスト、読む版 → 書く版の 2 段階リリースを完成させる。N-1 互換ジョブを完成させ、通ることを完了条件にする（リリース計画 R9）。
- 次のテストを CI で実行する（[テスト戦略](../../design/beer-game-kotlin/test-strategy.md)）。
  - 全イベントの往復（`encode` → `decode`）の性質テスト。
  - アップキャスト: 旧い `schema_version` のイベントの JSON（保存済みのフィクスチャ。変更しない）をアップキャストして `evolve` した結果が、期待する状態と一致する。
  - 永続化往復の同値性（実 DB の統合）。メモリ上の状態と、DB から読んだイベントを再生した状態が一致する。
  - 個人情報の不在: DTO に、表示名・資格の値・招待コードの値が含まれない。
  - N-1 互換ジョブ（毎回）。
- リリース前に、ステージングで、旧版が書いたイベントを新版で再生し、投影が一致することを確認する。
- 運用で、イベントの読み込み失敗を 1 件でも検知したら通知する（B13 のアラーム）。
