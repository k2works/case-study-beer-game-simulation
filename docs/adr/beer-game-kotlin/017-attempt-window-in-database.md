# ADR-017: 参加・復帰の失敗の窓を DB に持つ（提案）

参加コード（約 60 ビット）と復帰コードの総当たりを、タスク（インスタンス）の数に依らず抑えるため、失敗の窓を DB に持つ。本書は、**AI の提案であって、決定ではない**。実装は B5 Step 5 で済んでおり、人のゲート 5 は 2026-11-15 に承認済み（報告どおりに確定。窓は DB、10 回・10 分は未計測の仮置き）。**本書全体のレビュー・承認（`verify`）は未実施のため、ADR としては提案中のまま**。

日付: 2026-11-15

## ステータス

承認済み（2026-11-15、ユーザー。B5 ゲート 8）。

## コンテキスト

- 現状の全体の制限は、接続元ごとの固定窓（600 件/分）で、状態は**プロセス内**にある。設計書にも「タスク数が増えれば実効の上限が増える」と明記されている。NF-S11・NF-S19 は、参加・復帰の専用の制限の実効の上限が、タスク数で増えないことを要求する。
- ALB の背後では、接続元が ALB になり、`X-Forwarded-For` の信頼の範囲が未決（B14）。
- 制約: 生の IP を DB・ログに残さない。スキーマ変更は確認必須。ゲームの連鎖削除（B11）と衝突させない。

## 決定（提案）

- 失敗の窓を、表 `participation_attempts`（V008。`scope`・`key_digest`・`window_start`・`failure_count`。主キーは 3 列）に持つ。`game_id` を持たず、連鎖削除の対象外。窓が終わった行は、新しい窓の最初の記録で掃除する。
- 窓の鍵は、**正規化した接続元の鍵付き要約**（HMAC-SHA256。冪等キーの鍵を、部分の並び `"attempt-source"` で分けて流用）。IPv4 はそのまま、IPv4 射影の IPv6 は IPv4、IPv6 は上位 64 ビット。生の IP は DB にもログにも残さない（ログの `src` は同じ要約）。
- 順序: **窓に 1 を足す（別のトランザクション）→ 上限を超えていたら検査せずに 429（`app.rate_limited`、`Retry-After`）→ 検査・実行 → 認可の失敗（無効な復帰資格、不明な参加コード）でなければ 1 を戻す**。成功と入力の誤りは数えない。窓を保存できないときは通さない（閉じる側に倒す）。
- 上限と窓の長さは設定値（`ATTEMPT_MAX_FAILURES` 既定 10、`ATTEMPT_WINDOW_SECONDS` 既定 600）。**根拠のない仮置き**で、運営者との合意・実測が要る。
- 適用は、参加と復帰だけ（観察用の招待の参加は B9）。書き込みロールだけが窓の表を読み書きできる（V102 の GRANT）。

## 影響

### ポジティブ

- 複数のインスタンスで窓が合算される（別の接続プール 2 つの `charge` が合算されること、同時の 24 回が連番を 1 回ずつ受け取ることを、H2・PostgreSQL で確認）。
- 「検査の前に足す」ので、同時の要求が上限を超えて検査を通り抜けない。
- 生の接続元が、どの表の全列にも残らないことを、全表の走査で確認した。

### ネガティブ・リスク

- 上限に達した接続元は、**正しい参加コードでも 429**（当たりを知らせないため）。**同じ接続元（NAT・研修会場の共有 IP）の別の参加者も、その窓の間は参加できない**。
- ALB の背後では、全利用者が同じ窓に入りうる。接続元の取り方は B14 で決める（設計書の未決事項のまま）。
- 冪等キーの鍵を流用しているので、鍵を替えると窓が切れる（失敗の数がリセットされる）。専用の鍵・鍵の版を持つかは人の判断。
- 参加・復帰のたびに DB の書き込みが 1〜2 回増える。性能の実環境での測定は無い。
- 失敗の専用のログ行・アラートは無い（観測の完成は B13）。

## 代替案

| 案 | 内容 | 不採用の理由 |
| :--- | :--- | :--- |
| B: プロセス内のまま | 現状の `RateLimiter` を参加・復帰にも使う | タスク数で実効の上限が増え、NF-S11 を満たせない（仮説 3 が確認できない） |
| C: ALB・WAF に任せる | 基盤のレート制限を使う | インフラの変更で B5 の範囲外。復帰コード・参加コードの失敗（認可の失敗だけを数える）の区別ができない |
| D: 失敗してから数える | 検査の後に失敗を記録する | 同時の要求が、記録の前に上限を超えて検査を通り抜ける |

## 未確認

- 上限（10 回）・窓（10 分）の根拠。運営者との合意と実測。
- ALB の背後での接続元の取り方（B14）。
- 窓の表の掃除の負荷（新しい窓の最初の記録で行う方式が、大量の失敗でも許容できるか）。
