# ADR-005: 楽観的並行制御と自動再試行を基本とし、投影の再構築との直列化にだけアドバイザリロックを使う

書き込みは、`events` のストリームの版の一意制約による楽観的並行制御と、上限つきの自動再試行（SQLSTATE 40001・40P01 を含む）で制御する。行ロック（`SELECT ... FOR UPDATE`）は使わない。アドバイザリロック（コマンドは共有、再構築は排他）は、研修中に投影を再構築するためだけに使う。

日付: 2026-11-14

## ステータス

提案中（レビュー待ち）。ただし、研修中の再構築の運用（停止を依頼し、停止中に再構築して再開する）は**暫定**であり、人の確認が要る（設計レビュー M23）。

## コンテキスト

ES + CQRS では、状態はイベントの列であり、集約の行がない。同じストリームへの同時の書き込みを、どう整合させるかを決める必要がある。beer-game2 は、集約を `SELECT ... FOR UPDATE` で読み、版つきで更新していた。

共同担当の同時入力（FR-16）と、手動と自動の確定の競合（NF-R13）は、一方を成立させ、他方を再評価させる必要がある。再試行のたびに、認可を含めて `decide` を最初から評価し直せば、再読み込みの後に権限や状態が変わっていても、正しく判定できる。

さらに、投影が不整合になったときに、研修中に再構築できるかが問題になった。運用の手順は研修中の再構築を禁じる一方、障害パターンの復旧目標は 15 分であり、矛盾していた（M23）。停止中でも、代理入力、資格の再発行、観察者の参加など、追記を伴う操作は走るため、再構築とコマンドを、同じゲームについて同時に走らせない制御が要る。

## 決定

- **書き込みは、`events` の一意制約 `uq_events_stream_version`（`game_id`、`stream_type`、`stream_version`）による楽観的並行制御**とする。違反は `AppFailure.ConcurrencyConflict` に写す。行や版のロックは取らない。
- **`ConcurrencyConflict` は `execute` が自動で再試行する**（読み込みからやり直し、`decide` を再評価する）。上限は小さな固定回数で、競合の頻度を測って実装開始時に決める。上限に達したら `AppFailure.RetryExhausted`（503、`Retry-After`）とする。SQLSTATE **40001**（直列化失敗）と **40P01**（デッドロック）も、同じく `ConcurrencyConflict` に写して再試行する。
- 業務上の競合（`DecisionConflict`、`WeekAdvanced`、`DecisionsChanged`、`AlreadyStarted`）は、再試行せず、`decide` の結果を 409 で返す。
- **アドバイザリロックは、再構築との直列化のためだけに使う（暫定）。** コマンドはトランザクションの先頭で `pg_advisory_xact_lock_shared(game_id)`（共有）を取り、投影の再構築は排他の `pg_advisory_xact_lock(game_id)` を取る。共有どうしは待ち合わないため、コマンドの並行性は変わらない。トランザクションの終わりで自動的に解放される。
- 再試行の対象にする一意制約を、名前つきの表で定める（正本は [データモデル](../../design/beer-game-kotlin/data-model.md)）。

  | 制約名 | 衝突の意味 | 扱い |
  | :--- | :--- | :--- |
  | `uq_events_stream_version` | 同じストリームへの同時の追記 | 読み直して `decide` からやり直す（上限つき） |
  | `uq_idempotency_create` | 同じキーのゲーム作成の同時の重複 | 記録を再照合し、保存済みの応答を返す |
  | `pk_idempotency_records` | 同じキー・同じ対象の同時の重複 | 記録を再照合し、本文が同じなら保存済みの応答、違えば 409 |

  この 3 つ以外の一意制約違反は、設計上起きないはずなので、500 と相関 ID で返す。
- トランザクションの終わり（COMMIT と ROLLBACK）は `NonCancellable` で行い、`CancellationException` は握りつぶさず再送出する。クライアントの切断でコルーチンがキャンセルされても、トランザクションを必ず閉じる。`Left` を返したら ROLLBACK する。分離レベルは READ COMMITTED とする。
- **暫定の決定**: 研修中の再構築は、運営者を通じて進行役に「停止」を依頼し、停止中に再構築して再開する。停止を依頼する理由は、再構築中の入力の待ちを避けるためで、データの整合のためではない。
- **未決**: ロック待ちの上限（`lock_timeout`）と、再構築中のコマンドの応答（短く待つか、すぐ 503 を返すか）。再試行の上限の値と、間隔（ジッター）の要否も、計測して決める。

詳細は [バックエンドアーキテクチャ](../../design/beer-game-kotlin/architecture-backend.md) の「競合の再試行」と設計判断 BD6・BD7、[データモデル](../../design/beer-game-kotlin/data-model.md) の「追記と楽観的並行制御」と「再構築の同時実行制御」を参照。

### 代替案

- **行ロック（`SELECT ... FOR UPDATE`）による悲観的並行制御（却下）**: beer-game2 の方式。ES では集約の行がなく、イベントの列を読んで `decide` する構造と合わない。追記の一意制約と自動再試行に置き換える（バックエンドの beer-game2 からの変更 #2）。
- **アドバイザリロックで常に直列化する（却下）**: コマンドも排他のロックを取ると、同じゲームのコマンドが互いに待つ。データモデルの設計判断 #2 は、「並行性が落ちる」として退けている。
- **競合をクライアントへ 409 で返し、再送を促す（却下）**: 設計判断 BD7 の案 B。サーバーは単純になるが、共同担当の同時入力で、利用者に見える失敗が増え、`DecisionConflict` と区別できない。
- **研修中は再構築しない（暫定の決定により不要になった前提）**: 運用の手順 B-1 の旧い制約。復旧目標（15 分）と矛盾するため、アドバイザリロックで外す（M23）。

## 影響

### ポジティブ

- 通常のコマンドは、ロックを取らず、共有ロックも互いを待たないため、並行性が高い。
- 手動と自動の確定が同時に起きても、一方が追記の版の違反で負け、再試行後の `decide` が `WeekAdvanced` などを返し、確定は一度だけになる。
- 再構築が 1 トランザクションで行われ、コマンドが見るのは再構築の前後のどちらかで、途中の投影は見えない。

### ネガティブ

- 競合が続くと、再試行が上限に達し、利用者に 503 が見える（`RetryExhausted`）。上限の値は、実測するまで決まらない。
- 再構築中は、コマンドが排他ロックの解放を待つ。待ちが上限を超えると 503 になりうる。研修中は、停止の依頼を先に行う運用が必要になる。
- アドバイザリロックのキーは、UUID から導いた 64 ビット整数に写すため、衝突すると不要な待ちが生まれる（整合性は損なわない）。
- 複数の投影の行を更新するため、デッドロックを避けるロックの順序の規則に従う必要がある。なお、設計判断 BD6 の `game_overview` の `FOR UPDATE` は、今のイベント構成では実際には競合を防がない（残すかは実装時に判断）。

## コンプライアンス

- **B1（基盤と縦の最小）**: `uq_events_stream_version` と追記専用の権限を実装する。統合テストは、実際の PostgreSQL 18（Testcontainers）で、同じストリーム・同じ版への 2 つの追記のうち一方だけが成功することを検証する。
- **B6（共同担当と共同入力）**: 制約ごとの再試行・再照合を実装し、並行の統合テストで次を検証する。`RetryExhausted` の発生率も計測する（リリース計画 B6）。
  - 同じ役割の 2 人が同時に保存すると、自動再試行の後、一方が `DecisionConflict` と最新値・最後の保存者を受け取り、保存された値が失われない（NF-R14）。
  - 競合を意図的に続けたとき、上限で止まり、`app.retry_exhausted` を返す。
  - 同時の重複（`uq_idempotency_create`、`pk_idempotency_records`）が 500 にならない。
- **B8（自動確定）**: 最後の入力と進行役の手動の確定が同時でも、`WeekCommitted` は 1 件で、費用は一度だけ（NF-R13）。2 つの API プロセスで検証する。
- **B12（投影の再構築）**: 再構築の同時実行制御（M23）のテストを CI で実行する。排他ロックの最中にコマンドを送り、ロックの待ちの後に実行されるか、待ちの上限で 503 を返し、再構築の結果の行と、その間に追記したイベントの投影が一致する（取りこぼし・二重適用が無い）。コマンド同士は互いを待たない。ロック待ちの上限の値は未決のため、設定から注入できるようにする。
- トランザクションの境界のテスト（H7）: `Left` で ROLLBACK され、追記と投影が残らない。40001・40P01 が再試行の対象になる。COMMIT / ROLLBACK が `NonCancellable` で行われ、`CancellationException` が再送出される。
- **B13（観測の完成）**: 再試行の回数、追記競合率、再構築の排他ロックの待ちのメトリクスとアラームを定義する。
- 研修中の再構築の運用の成立は、B12 のレビューで人が確認する（暫定の決定の確定条件）。
