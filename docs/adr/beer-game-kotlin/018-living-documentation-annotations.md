# ADR-018: 用語集とイベント一覧を、型の注釈とソースから生成する（提案）

開発戦略が「B1〜B2 で決める」とした未決（注釈の語彙と生成の仕組み）の、最小の案。本書は、**AI の提案であって、決定ではない**。B5 Step 8.4 で実装した。

日付: 2026-11-15

## ステータス

提案中（レビュー待ち）。

## コンテキスト

- 開発戦略（中盤）: ドメインの型から生成する用語集・イベント一覧で、ユビキタス言語をコードに一本化する。手で複製せず、重複する知識は不一致を検出するテストで守る。**手作業で更新する一覧は作らない**。
- 注釈の語彙・生成方式（コンパイラ連携か、ソースの走査か）は、B1〜B3 で決まらないまま残っていた。domain は Kotlin 標準と Arrow だけに依存する規約。
- ドメインイベントは、設計書の表（EV-G*、EV-S*）、コード（sealed な部分型）、`EventCodec` の golden に重複して表れる。B5 で 8 種類が増え、手で一致を保つ限界が近い。

## 決定（提案）

- **注釈**: domain に標準ライブラリだけの 2 つ（`Term`: 用語・定義・出典。`EventSpec`: 設計書の ID・発生する条件）を置く。実行時まで残るだけで、業務の振る舞いに関わらない。付ける対象は、これから書くコードと B5 で足した概念から（既存コードへの一括適用はしない）。
- **生成**: domain の試験 `LivingDocumentationSpec`（追加の依存なし）。イベントは、sealed の部分型（`permittedSubclasses`）を全件（ストリームは親から、ペイロードの項目は型のフィールドから）、購読する投影は `Projection.kt` の走査から導く。用語は、クラスパスのクラスから `Term` を集める。
- **出力**: `docs/design/beer-game-kotlin/generated/events.md`・`glossary.md`（フロントマター以外は生成物。手で編集しない）。`./gradlew :domain:generateLivingDocs` で再生成する（同じ試験を更新モードで実行）。
- **検査（CI の `check` に含まれる）**: (1) 注釈の無いイベント、(2) ID の重複・ストリームの接頭辞違い、(3) 設計書の表と、ID・名前が違うこと、(4) コミット済みの生成物との差、を失敗にする。設計書にあって未実装のイベントは、一覧に「未実装」として載せる（失敗にしない）。

## 影響

### ポジティブ

- 新しいイベントに `@EventSpec` を付け忘れる、設計書の ID とずれる、生成物を更新し忘れる、のいずれも CI で落ちる。
- 追加の依存・新しいモジュールがない。

### ネガティブ・リスク

- 生成が試験の中にあり、`main` の成果物ではない（ビルドの成果物として公開する場合は、別の task か別のモジュールが要る）。
- 設計書の EV 表と生成物が、やむを得ず重複する（検査はするが、手で書く表は残っている）。EV 表を生成物への参照に置き換えるかは人の判断。
- 設計書の変更だけの PR では、CI のパスフィルター（`apps/beer-game-kotlin/**`）に当たらず、不一致の検査が走らない（CI の変更が要る。人の判断）。
- 「発生する条件」は注釈の手書きで、実装との一致は検査しない。購読する投影の走査は、`Projection.kt` の書き方（`val <名前> =` と `Projection {`）に依存する。
- 公開（サイトへの掲載）の導線は未実装。

## 代替案

| 案 | 内容 | 不採用の理由 |
| :--- | :--- | :--- |
| B: 別モジュール＋注釈処理（KSP） | 注釈を別モジュールに置き、コンパイル時に生成 | 新しい依存と構成の変更が要る。最小の案で足りる間は過剰 |
| C: 走査のスクリプト（beer-game2 の方式） | Node のスクリプトがソースを走査して生成 | 型情報が無く、名前・項目を正規表現に頼る。Kotlin の試験のほうが型で確かめられる |
| D: 手書きのまま | 設計書の表だけを正本にする | 手作業の一覧は更新されなくなる（開発戦略の方針に反する） |
