# ADR-015: 復帰資格の受け渡しと、失効でブラウザセッションを止める結び付き（提案）

Bolt 5（進行の継続と資格）で、(H2) 資格の失効で発行済みのブラウザセッションを止める結び付きと、(H3) 進行役の復帰用の値・再発行した資格の受け渡し・`recover` の本文の形を決める必要がある。本書は、**AI の提案であって、決定ではない**。人が [bolt_5_plan](../../development/beer-game-kotlin/bolt_5_plan.md) のゲート 1 で決める。

## ステータス

**提案中（人の決定待ち）。** 承認は記録していない。承認されるまで、実装（Step 4 以降）は本書の案に依存しない。H3 の案は、設計書（アーキテクチャ設計の「コマンドの応答」、UI 設計の「資格を含む応答」）の記述と異なる点を含む。

## コンテキスト

- 資格は、**ブラウザセッション**（`browser_sessions`。24 時間）と**復帰資格**（`credentials`。参加者は 30 日、進行役はゲームの保持期間内）に分ける設計（[bolt_5_plan](../../development/beer-game-kotlin/bolt_5_plan.md) の「資格の状態」）。B1 は、1 つの値を両方の表に同じダイジェストで書き、認証は、同じダイジェストで両表を結んで検査している（`JdbcPeripheralStore.kt` の `AUTHENTICATE_SQL`）。分けると、**失効で発行済みのブラウザセッションを止める結び付きが無くなる**（`browser_sessions` に `revoked_at` も `credentials` への参照も無い。V002）。
- 設計では、資格の生の値は `Set-Cookie` だけが運び、コマンドの応答の本文は `versions` だけである（DTO に資格の値のフィールドを持たせない）。しかし、(1) 端末を替えた進行役、(2) 進行役が再発行した参加者の資格は、Cookie では渡せない。復帰の手段が無いと、AC3.2.4（ブラウザの再起動・端末の変更後の復帰）と AC3.2.5（再発行）が成り立たない。
- ADR-004: 認可は冪等記録の照合より前に行う。復帰（`RecoverParticipation`）は、**提示した復帰資格の有効性が認可**であり、`ANONYMOUS`（参加コードが認可の代わり）で実装すると、失効した復帰資格の再送に、保存済みの新しいセッションが返る。
- 制約: スキーマ変更は確認必須。資格の値を URL・ログ・本文に含めない（NF-S4）。個人情報（アカウント）を集めない。

## 決定（提案）

### H2: 失効でブラウザセッションを止める結び付き

| 案 | 内容 | 長所 | 短所 |
| :--- | :--- | :--- | :--- |
| **A（推奨）** | `RevokeCredential` の書き込みと**同じトランザクション**で、対象の主体（`game_id`、`actor_id`）の `browser_sessions` の行を**削除**する。スキーマ変更なし | 追加の列・索引が要らない。認証の検査（`s.expires_at > now`）が変わらず、失効後の再送は 403（ADR-004） | 失効の痕跡は `credentials.revoked_at` とイベント（`CredentialRevoked`）にあり、`browser_sessions` には残らない |
| B | `browser_sessions` に `revoked_at`（または `credentials` への参照）を追加し、認証が見る。**スキーマ変更（確認必須）** | 失効の痕跡が行に残る | マイグレーションの追加（番号は保持の `006` と衝突させない）、権限（GRANT）の確認、連鎖削除の検査との整合が要る |
| C（不採用） | 認証が、主体の未失効の `credentials` の存在を確かめる | 列の追加が要らない | **再発行で新しい資格が有効になると、失効したはずの古いブラウザセッションが復活する**ため、漏洩の被害を止められない |

提案は A。`writer` ロールは `browser_sessions` への `DELETE` を持つ（V101）が、**実際の GRANT は Step 4 で確かめる**（未確認）。

### H3: 復帰資格の受け渡し

**案 A（推奨）**

1. **復帰資格を、ブラウザセッションとは別の Cookie `bg_recovery`**（`HttpOnly`、`SameSite=Strict`、HTTPS では `Secure`、`Path` は復帰の経路だけ、30 日）で発行する。参加（`joinGame`）と作成（`createGame`）の応答で、`bg_session`（24 時間）とともに `Set-Cookie` する。
2. **復帰コード**（復帰資格と同じ 256 ビットの乱数の値）を、次の応答の**本文に、一度だけ**示す。保存は鍵付き HMAC のダイジェストだけで、再表示しない。
   - `createGame` の 201: 進行役の復帰コード（`recoveryCode`）。進行役が控え、端末を替えたときに使う（AC3.2.4）。
   - `reissueCredential` の 200: 新しい復帰コード（`recoveryCode`）と有効期限（`expiresAt`）。進行役が、参加者へ口頭などで渡す（AC3.2.5）。
3. `POST /participations/recover`: 本文は `{ gameId, recoveryCode? }`。`recoveryCode` を省略すると Cookie `bg_recovery` を使う。有効なら、新しい `bg_session` を発行し、復帰資格の期限を更新して、`{ gameId, kind, role?, versions }` を返す。不明・失効・期限切れ・別のゲームは、区別しない同じ 403（`app.unauthorized`。NF-S12）。
4. `RecoverParticipation` の認可は**復帰資格の有効性**とし、`Auth` に新しい種類（例: `RECOVERY`）を足して、**冪等記録の照合より前に**検証する（ADR-004。R5）。
5. 新しい code: `game.credential_already_revoked`（409）ほか。`contracts/openapi.yaml` に書いた（提案として）。

**案 B**: 復帰資格を足さず、Cookie の寿命（`bg_session`）だけに頼る。端末の変更で復帰できず、**再発行した資格を参加者へ渡す手段が無い**ため、AC3.2.5 の「再発行」が意味を持たない（AC3.2.4 のうち「ブラウザの再起動」だけを満たす）。

**案 C（不採用）**: 復帰コードを URL（リンク）で渡す。資格を URL に含めない規則（NF-S4）に反し、ログ・履歴に残る。

#### 設計書との差（案 A を採るとき）

- 「コマンドの応答は `versions` だけ」「DTO に資格の値を持たせない」に**例外**が 2 つ（`createGame`・`reissueCredential` の `recoveryCode`）できる。型で防ぐ規則は、「`recoveryCode` を持つ応答の DTO を、この 2 つに限る」に書き換える（アーキテクチャ設計、UI 設計、DTO の検査）。
- `createGame` の冪等な再送は、保存済みの応答を返す。**`recoveryCode` を含む応答を暗号化して保存する**必要がある（未確認。`idempotency_records.response` は暗号化済みだが、本文に資格の値を含める前提では設計していない）。

## 影響

### ポジティブ

- 漏洩した資格の被害を、失効（H2）と再発行（H3）で止められる（仮説 1）。
- 失効後の再送が 403（保存済みの応答を返さない）になる順序を、復帰にも適用できる（仮説 2）。

### ネガティブ・リスク

- 案 A は、本文に資格の値が載る応答を 2 つ作る（ログ・相関 ID・エラーの本文に値が出ないことを、否定テストで確かめる）。
- `bg_recovery` の `Path` を絞るため、Cookie の設定が 2 つになる（HTTP の層とブラウザの両方の検査が要る）。
- 参加・復帰の専用のレート制限（NF-S11。Step 5）は、復帰コードの総当たりの防止に必要。窓の保存先の決定（判断項目 4）と合わせて確認する。
