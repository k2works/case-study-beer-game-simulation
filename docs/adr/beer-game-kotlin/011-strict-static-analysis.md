# ADR-011: 静的解析とルール設定を厳格に適用する（detekt を中心に PMD で補完）

関数型の規約を、レビューだけに頼らず機械で守らせる。detekt を中心に、PMD の XPath の関数型ルール 14 個を補完とし、ktlint を整形に使う。違反は 0 件、ベースラインなし、`@Suppress` なしとする。

日付: 2026-11-14

## ステータス

提案中（レビュー待ち）。厳格に適用する方針は**ユーザーの指示**である。PMD の導入（新規の CI ツール）は**承認待ち**であり、承認までは detekt と ktlint で進める。detekt と PMD の Kotlin 2.4 との互換は**未確認**で、B2 の受入条件である。

## コンテキスト

本プロジェクトは、変更を楽に安全にできる、長く保守するプロダクトである。AI が大量にコードを生成するため、規約違反（`var`、可変コレクション、例外の握りつぶし、ドメインでの時計・乱数の直接呼び出し）を人の目だけでは拾えない。ガイド §9.5 は、複数人の開発や長く保守するプロダクトには detekt を `check` に組み込む構成を推奨している。

また、設計レビューは、純粋性を静的検査で守るよう求めた（M18）。同一 JVM の同一ミリ秒に 2 回呼ぶだけの性質テストでは、時計の読み取りを検出できない。さらに M17 は、detekt と Kotlin 2.4 の互換が未検証であり、代替を選ぶ期限を決めるよう求めた。

本プロジェクトは新規の実装で、既存の違反がない。段階的な緩和（新しいコードだけに適用）は要らず、最初から全ルールを有効にできる。

## 決定

- ガイド第 9 章の静的解析とルール設定を、全コード（ドメイン、アプリケーション、アダプター、テスト）に、最初のコードから厳格に適用する。
- **厳格さの定義**: 違反を 0 件にする（detekt の `build.maxIssues: 0`、コンパイラの警告をエラーとして扱う）。ベースラインを使わない。`@Suppress` とルールの無効化コメントを使わない。除外が要る層は、**層ごとにルールセットのファイルを分けて**外す。ルールの緩和・除外は、理由を ADR に記録し、人が承認する。
- **役割分担**: detekt が中心（複雑度、潜在的なバグ、例外、`ForbiddenMethodCall`）。PMD（7.29.0）の XPath のカスタムルール 14 個が、detekt に無い関数型の規約（`var` の禁止、可変コレクション、`!!`、`throw`、`runBlocking`、`GlobalScope` など）を補う。ktlint は整形で、`.editorconfig` で副作用の大きいルール（日本語のテスト名など）だけを調整し、整形の中核のルールは外さない。
- **純粋性の静的検査**: detekt の `ForbiddenMethodCall` で、ドメインのモジュールでの `Instant.now`・`Clock.system*`・`UUID.randomUUID`・`Random` を禁止する（M18）。
- **ルール自体のテスト**: PMD のルールは、違反するコードとしないコードを並べた fixture で、期待件数と行を使う版で確かめる（ガイドの例は PMD 7.29.0 で 17 件）。このテストを CI に組み込む。ルールの `message` に `{` と `}` を書かない。
- **detekt の代替判断の期限**: B2 の最初のビルドで「規約違反コードを置き、CI が落ちること」を確認する。落ちれば detekt 1.23.8 を確定する。落ちなければ（解析できない、または規則が効かない）、**B2 の中で**代替を選び、選択を ADR に記録する。B2 で確定できなければ B3 以降を止める。**Kotlin の版は下げない**。
- 設定値（ルール名と既定値）は、ガイドの例が実行して確認していないため、導入する版の公式ドキュメントで確認して確定する。

### 代替案

設計書の案の表（技術スタック T5）から取る。

- detekt 2.0 の alpha（`dev.detekt` 2.0.0-alpha.6）: Kotlin 2.4 に対応する見込みはあるが、alpha であり安定性を確認していない。1.23.8 が Kotlin 2.4 を解析できない場合の代替とする。
- PMD だけを使う（PMD の XPath の拡充）: 標準の Kotlin ルールが 4 つしかなく、複雑度などの標準ルールを自作することになる。単独では採らず、補完とする。拡充は detekt が使えない場合の代替の 1 つ。
- 自作の検査（ガイド §9.5 の小さなスクリプト）: 1 人の教材・記事のコード向けの推奨で、本プロジェクトの規模と保守の長さに合わない。

## 影響

### ポジティブ

- 規約違反が、レビューでなく CI で止まる。AI の生成量に比例してレビューの負担が増えない。
- 純粋性が、性質テストに頼らず静的に守られる。
- 後から入れるより、最初から入れるほうが修正が安い。

### ネガティブ

- B1・B2 の所要が増える（B2 を 2 日から 3 日）。R17 のように、所要が膨らみ以降の Bolt を圧迫しうる。緩和（ルールの無効化、ベースライン、`@Suppress`）で時間を節約しない。
- detekt と PMD の Kotlin 2.4 との互換が未確認で、不可なら代替の選択で B2 が延びる（R1、R16）。
- ルールの読み間違いで、違反の見逃しや誤検出が起きうる（fixture で緩和する）。
- 静的解析は検出できる種類の問題にしか効かない。設計書とコードの食い違い（イベント名、`code`、制約名）は、契約テストと golden で守る。

## コンプライアンス

- **B2 の受入条件**: 規約違反コードを 1 つ置くと CI が落ちる（detekt と PMD のそれぞれで確認）。PMD の fixture のテストが期待どおり。detekt と PMD が Kotlin 2.4 を解析できる。違反 0 件・ベースラインなし・`@Suppress` なしで全コードが緑。ktlint の `.editorconfig` の調整が実際の版で動く。ドメインでの `Instant.now` が `ForbiddenMethodCall` で落ちる。
- **B2 の承認ゲートの追加項目**: 静的解析のルールと fixture の期待件数、層ごとのルールの除外の理由を、人が検証する。
- **全 Bolt**: 各 Bolt の完了条件に「静的解析の違反が 0 件」を含める。ルールの緩和・除外を足した場合は ADR と承認がある。
- **CI**: 1 つでも失敗したらマージしない。ローカルでも同じ Gradle のタスクで再現できる。
- B2 の結果が悪ければ、B16（予備）を先に使い、設計を見直す（リリース計画）。
