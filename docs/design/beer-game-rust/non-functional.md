# 非機能要件定義 - ビールゲームシミュレーション（Rust 版）

## 概要

本書は、beer-game-rust の非機能要件を、**測定できる形**で定義します。**`docs/` を正本**とします。実装コードはまだ存在せず、**Rust 版の性能・メモリ・起動時間の実測値はありません**。

[ADR-001](../../adr/beer-game-rust/001-rust-version-of-beer-game-kotlin.md) により、[beer-game-kotlin の非機能要件](../beer-game-kotlin/non-functional.md)（84 件。beer-game2 の 69 件 + Kotlin 版で追加した 15 件）を**正本として引き継ぎ**、Rust の実行環境で変わるものだけを見直しました。

- **すべての ID を維持**しました（削除はありません）。要件定義の NFR-01〜NFR-12 は変えません（[要件定義](../../requirements/beer-game2/requirements_definition.md)）。
- 凡例は Kotlin 版と同じです。**継続**は Kotlin 版と内容が同じ、**変更**は ID は同じで内容を Rust 版に合わせて変えた、**新**は Rust 版で追加した要件です。
- 数値目標は、運営者と合意する前提の**提案**です。**Kotlin 版で提案した数値も、Rust 版の実測で見直す前提**で、実測のない数値を Rust 版の都合で**厳しくも緩くもしていません**（設計判断 RN1）。
- 新しく加えた要件は 2 件（NF-R18、NF-S22）で、合計 **86 件**です。

### 本書の位置づけと確認の範囲

- **継続の要件**は、本文を Kotlin 版と重複して持たず、**要約と ID の対応だけ**を示します。**要件の正本の文言は Kotlin 版の表**です（本書の「継続」の行に、要件の趣旨を 1 行で書く）。
- **変更・新の要件**は、本書に全文を書き、**本書を正本**とします。
- **確認したこと**: NF-S20（追記専用）と NF-S16（連鎖削除）の一部は、PostgreSQL 18.6 で SQL として実測しました（[データモデル](./data-model.md) の検証、1 回の実測）。NF-S21・NF-S3 の型による守り（`Secret<A>` の Debug が伏せ字）は、rustc 1.97.1 で確認しました（[バックエンドアーキテクチャ](./architecture-backend.md)）。**それ以外の要件は、すべて未検証**です。
- Kotlin 版の実装の経緯（B3・B6・B15 の実測の注記）は引き継ぎません（Rust 版の値ではないため）。

## 品質特性の優先順位と SLO の要約

**Kotlin 版と同じです。** 優先順位は、1 機能の正確性・信頼性（整合性）、2 セキュリティ、3 性能効率性・使用性、4 保守性・観測性、5 可用性（SLO）、6 拡張性・移植性。SLO は、月間可用性 99.5%、完全停止の検知 1 分以内、RPO 0（確定済み週）、RTO 15 分、入力確定（サーバー側）p95 1 秒以内、週確定から全画面への反映 p95 2 秒以内、保持期限後の削除（期限到達の 99% を 24 時間以内）。

## ES + CQRS と Rust で変わる点

ES + CQRS による変化（再生による書き込み時間、ストリームの版の一意制約と自動再試行、同期投影、投影の再構築、追記専用、個人情報の分離、イベントの互換）は **Kotlin 版と同じ**で、要件もそのまま引き継ぎます。**Rust の実行環境で変わる点**は次のとおりです。

| 観点 | Kotlin 版（JVM） | Rust 版 | 関係する要件 |
| :--- | :--- | :--- | :--- |
| 起動とウォームアップ | JVM の起動、JIT のウォームアップ。コールドスタート直後の遅さを要件にする | JIT がない。**ウォームアップ依存の遅さは原則なし**。ただし、DB の接続プールの温まりと OS のキャッシュの影響は残るため、**コールドスタート直後も定常と同じ目標**を置いて確認する | NF-P1、NF-P16 |
| メモリ | JVM のヒープ、GC 後の使用率、GC の一時停止 | **GC がない**。常駐メモリ（RSS）とコンテナのメモリ上限との関係、tokio のタスク数。メモリ不足は OOM kill として現れる | NF-P17、NF-O12 |
| 非同期とキャンセル | コルーチン。`NonCancellable` で COMMIT/ROLLBACK | **future の drop がキャンセル**。`Tx` の drop で ROLLBACK、`execute` を spawn して切断から隔離（RB2）。**panic のプロセスへの影響**も扱う | **NF-R18（新）**、NF-R3、NF-R5、NF-R9 |
| メモリ安全 | JVM が保証 | `unsafe` を使わない方針をドメインと application で機械的に守る | **NF-S22（新）** |
| 乱数・依存・静的解析 | `SecureRandom`、Gradle の依存検査、detekt・PMD・ktlint | OS の暗号論的乱数、`cargo-deny`、clippy・rustfmt | NF-S1、NF-S13、NF-O8 |
| DB のクライアント | JDBC + HikariCP | sqlx の接続プール | NF-O3、NF-C5 |
| マイグレーション | Flyway | sqlx のマイグレーション | NF-O11 |
| ローカル開発の DB | H2 を許す | PostgreSQL 18（Docker。2026-11-19 決定） | NF-S20、NF-S18 の検証範囲 |

### ストリームの最大の長さ

Kotlin 版と同じです（想定 1000 件、保存回数の上限（提案: 1 役割・1 週あたり 9 回。代理入力を含む）を置くと最大 2000 件）。**この見積もりと上限は、JVM の値ではなく設計上の見積もり**で、Rust の実測で見直します。上限の有無と値は、運営者と合意して決める未決事項です。

NF-R18 は、設計判断 RB2（[バックエンドアーキテクチャ](./architecture-backend.md)）の前提（sqlx のトランザクションが drop で ROLLBACK される）が B1 で確認できることに依存します。**確認できなければ設計を見直す**ことを、本要件の受入条件に含めます。

## beer-game-kotlin からの変更

| ID | Kotlin 版 | Rust 版 | 理由 |
| :--- | :--- | :--- | :--- |
| NF-P1 | JVM のウォームアップ後の定常値 | 接続プールが温まった後の定常値。コールドスタート直後も同じ目標 | JIT がない（NF-P16） |
| NF-P15 | 目標値に「JVM のウォームアップ後」、JMH または自前 | 目標値は提案として引き継ぎ、Rust で実測して見直す。道具は未選定 | 言語の違い |
| NF-P16 | 起動 p95 30 秒以下 + コールドスタート後 60 秒間 p95 2 秒以下（JIT の影響） | 起動 p95 30 秒以下（上限として引き継ぎ、実測で縮める）+ コールドスタート後 60 秒間も NF-P1 と同じ 1 秒以下 | JIT がない |
| NF-P17 | JVM のヒープの GC 後の使用率 70% 以下、GC の一時停止は実測で決める | 常駐メモリ（RSS）がコンテナ上限の 70% 以下、OOM kill 0 件、タスク数の記録 | GC がない |
| NF-P18 | 計測の方法に JMH | NF-P15 と同じ（道具は未選定） | 言語の違い |
| NF-R4 | JVM の起動を含む | アプリの起動を含む | 言語の違い |
| NF-R9 | `Either` の左として扱う | `Result` の `Err`（`AppFailure::Persistence`）として扱う。panic のまま漏らさない | 言語の違い |
| NF-R18（新） | （なし。`NonCancellable` による実装の方針だけ） | キャンセル安全性を要件にし、検証する | future の drop というキャンセルの意味（RB2、RT2） |
| NF-S1 | JVM の `SecureRandom` | OS の乱数源に基づく生成器 | 言語の違い |
| NF-S10 | `zipOrAccumulate` による検証 | 誤りをすべて集める検証 | 言語の違い |
| NF-S13 | Gradle の依存関係の検査、detekt | `cargo-deny`、clippy | ツールの違い |
| NF-S22（新） | （なし。JVM が保証） | `unsafe` を使わない | メモリ安全の方針 |

## 設計判断

### Kotlin 版の設計判断 N-1〜N-3 との対応

| ID | Kotlin 版の決定 | Rust 版の扱い |
| :--- | :--- | :--- |
| N-1 | 投影の遅延は、同期投影により 0。非同期の目標は条件付き | **引き継ぐ** |
| N-2 | JVM の起動とメモリは、実測してから目標を固める | **見直す**（RN1）。JVM の項目は実行環境に読み替え、実測のない数値は提案のまま |
| N-3 | ロールバックのためのイベントの互換を、デプロイの要件にする（読める版を先にリリース） | **引き継ぐ**（NF-O11） |

### RN1: JVM に固有の要件は、実行環境に読み替え、実測のない数値は変えない（承認済み。2026-11-19）

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| **A（採用）** | JVM に固有の項目（ウォームアップ、ヒープ・GC）を、Rust の実行環境（接続プールの温まり、RSS、タスク数）に読み替える。**数値の目標は、Kotlin 版の提案値を上限として引き継ぎ、Rust の実測で見直す**（実測前に厳しくも緩くもしない） | 根拠のない数値を、確定した要件にしない（Kotlin 版の N-2 と同じ方針）。Rust が速いはずという期待だけで目標を縮めない |
| B | Rust は JVM より速いとして、起動時間・メモリの目標を先に厳しくする | 見かけは意欲的。実測がなく、運営者との合意の根拠にならない |
| C | JVM の項目を削除する | 要件が減る。コールドスタート直後の遅さとメモリ使用の検証が抜ける |

### RN2: キャンセル安全性（NF-R18）を要件として新設する（承認済み。2026-11-19）

Kotlin 版は、キャンセルの扱い（`NonCancellable`、`CancellationException` の再送出）を実装の方針として持ちますが、非機能要件の ID は持ちません。**Rust ではキャンセルが future の drop であり、ハンドラが途中で止まりうるため、要件として検証可能にします**（NF-R18）。RB2 の前提が確認できなければ、設計を見直します。

### RN3: カバレッジのゲートは行 80%、分岐は目安（承認済み。2026-11-19）

[テスト戦略](./test-strategy.md) の RT3 と同じです（NF-O7）。
