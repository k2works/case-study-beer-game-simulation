# 非機能要件定義 - ビールゲームシミュレーション（Kotlin 版）

## 概要

本書は、beer-game-kotlin の非機能要件を、**測定できる形**で定義します。**`docs/` を正本**とします。実装コードはまだ存在せず、**実測値はありません**。

[beer-game2 の非機能要件](../beer-game2/non-functional.md) を正本として引き継ぎ、**イベントソーシング（ES）+ CQRS と JVM で変わるものだけ**を見直しました。

- **すべての ID を維持**しました。内容が変わる要件には「変更」、新しい要件には「新」を付け、変更の理由を [beer-game2 からの変更](#beer-game2-からの変更) に表で示します。
- 要件定義の NFR-01〜NFR-12 は変えません（[要件定義](../../requirements/beer-game2/requirements_definition.md)）。
- 数値目標は、運営者と合意する前提の**提案**です。**Kotlin 版で新しく追加した数値は、実装後の実測で見直す**前提の暫定値です（根拠のない値は「実測で決める」と書いています）。

### 要件の件数について

beer-game2 の本文は「測定可能な目標 74 件」と書いていますが、**表の ID を数えると 69 件**です（性能 14、信頼性 14、セキュリティ 19、保守・観測 11、拡張 7、使用性 4）。本書は **ID を正として、69 件すべてを引き継ぎます**。「74 件」の根拠は、beer-game2 の文書からは確認できませんでした（未決事項）。Kotlin 版で新しく加えた要件は 15 件で、合計 **84 件**です。

## 品質特性の優先順位

beer-game2 と同じです（[非機能要件定義ガイド](../../reference/非機能要件定義ガイド.md)）。

| 優先 | 品質特性 | 理由 |
| :---: | :--- | :--- |
| 1 | 機能の正確性・信頼性（整合性） | 週次計算の忠実性と、確定の一回性が、教材の価値そのもの。**ES では、イベントが事実であり、再生しても同じ状態になることが正確性の根拠** |
| 2 | セキュリティ（機密性・完全性） | 役割ごとの情報制約が、学習条件の前提。資格の漏洩は他人の役割の操作につながる |
| 3 | 性能効率性・使用性 | 研修中の操作が滞らないこと。アクセシビリティは要件 |
| 4 | 保守性・観測性 | 研修中の障害に気づき、直せること |
| 5 | 可用性（SLO） | 研修の時間帯に使えること。常時の高可用性までは求めない |
| 6 | 拡張性・移植性 | 想定規模（15 チーム）を満たし、増やせる余地を残す |

## ES + CQRS と JVM で変わる点

要件を見直した観点を、先に示します。

| 観点 | beer-game2（行の更新 + Node.js） | Kotlin 版（ES + CQRS + JVM） | 関係する要件 |
| :--- | :--- | :--- | :--- |
| 書き込みの性能 | 行ロック + 版つきの更新 | 状態の再生（`fold(evolve)`）+ `decide` + 追記 + 同期投影。**ストリームの長さに応じて再生の時間が増える** | NF-P3、NF-P13、NF-P14、NF-P15、NF-P19、NF-C8、NF-C9 |
| 並行性 | 行ロックと `WHERE version = $expected` | ストリームの版の一意制約 + **自動再試行**（ロックなし） | NF-R7、NF-R13、NF-R14、NF-R17、NF-C2 |
| 投影の遅延 | 読み取りは SQL（確定と同じトランザクションで行を書く）。振り返りは v1 で再構築 | **同期投影（追記と同じトランザクション）。投影の遅延は 0**。非同期へ移す場合の目標は、条件付きで定める | NF-P2、NF-P8、NF-P19、NF-P20 |
| 投影の再構築 | なし | **イベントからいつでも作り直せる**。再構築の時間と一致を要件にする | NF-P18、NF-R15 |
| 復元 | DB のバックアップ | 同じ + **イベントの再生で状態と投影を再構築できる** | NF-R4、NF-R8、NF-R15、NF-R16 |
| 起動時間 | Node.js（短い） | **JVM の起動とウォームアップ**。コールドスタート直後の遅さを要件にする | NF-P16 |
| メモリ | Node.js のヒープ | JVM のヒープ、コンテナのメモリ上限との関係、GC | NF-P17、NF-O12 |
| イベント量と保持 | 監査用の `events`。投影の元ではない | **`events` が状態の正本**。1 ストリームの長さ、保存量、スナップショットの導入基準を要件にする | NF-C6、NF-C8、NF-C9、NF-O13 |
| 追記専用 | なし | `events` は UPDATE / DELETE を禁止（保持削除は連鎖削除で行う） | NF-S20 |
| 個人情報 | 集約の表に表示名 | **イベントに入れない**（周辺ストア） | NF-S14、NF-S21 |
| デプロイとロールバック | スキーマの互換 | 加えて、**旧版のアプリが、新しい版のアプリが書いたイベントを読めること**（イベントは書き換えない） | NF-O11 |

## セキュリティ・プライバシー要件

| :--- | :--- | :--- | :--- | :---: |
| NF-S1 | 進行役の資格と復帰資格は、128 ビット以上の暗号論的乱数（JVM の `SecureRandom` など）とし、生の値は発行時に一度だけ返す | 乱数長と一意性のテスト | U1 NFR3.1、NFR-06 | 継続 |

## 設計判断

### N-1: 投影の遅延は、同期投影により 0 とし、非同期の目標は条件付きにとどめる

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| **A（採用）** | 同期投影（追記と同じトランザクション）。投影の遅延の要件は持たず、追記の時間（NF-P19）を測る。非同期の遅延目標（NF-P20）は、移行するときにだけ適用する | 週確定後の反映（NF-P2）が、通知の版以上であることを保証できる。投影の遅れによる障害の種類が無い |
| B | 非同期投影（ワーカー）を前提に、遅延 p95 1 秒を最初から要件にする | 書き込みと読み取りを分離できる。結果整合の窓と、ワーカーの運用が増える |

トレードオフ: A は、追記のトランザクションが長くなる。NF-P19 の実測で、書き込みを圧迫する場合に B へ移る（データモデルの設計判断 4）。

### N-2: JVM の起動とメモリは、実測してから目標を固める

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| **A（採用）** | 起動時間とコールドスタート後の遅さを、**提案値**として置き、ウォーキングスケルトンの実測で見直す。メモリは、使用率の上限と OOM 0 件だけを要件にし、GC の一時停止の目標は実測で決める | 根拠のない数値を、確定した要件にしない。性能の目標（NF-P1）の測定条件を明確にできる |
| B | 一般的な経験則の数値（例: GC 停止 p99 100 ms）を先に確定する | 見かけは完結する。本プロジェクトの実測が無く、根拠がない |

### N-3: ロールバックのためのイベントの互換を、デプロイの要件にする

イベントは書き換えません。新しい版のアプリが新しい `schema_version` のイベントを書いた後に、旧版へロールバックすると、旧版がそのイベントを読めず、**ストリームが壊れた状態になる**危険があります。

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| **A（採用）** | 「読めるようにする版」を先にリリースし、全タスクに展開した後のリリースで、新しい `schema_version` を書き始める（拡張 → 互換 → 縮小）。NF-O11 に明記する | ロールバックが安全。リリースが 2 段階になる |
| B | 新旧を同じリリースにして、ロールバックでは DB の復元も行う | リリースは 1 回。復元の時間（RTO）に影響し、確定済みの週が失われうる |

## 未決事項

- **数値目標（SLO、保持、容量、資格の有効期間）を、運営者と合意する**。合意した値で本書を確定する。
- Kotlin 版で新しく加えた数値（NF-P15〜NF-P19、NF-O13、NF-C8）は、**提案**であり、実測で見直す。特に、保持中のゲーム数の想定（NF-P18）、GC の一時停止の目標（NF-P17）。
- 資格の有効期間の既定値（ブラウザセッション、復帰資格、進行役の資格、観察用の招待）。
- 負荷試験の実施環境（CI の夜間か、ステージングか）。
- 追記の競合の自動再試行の上限と間隔（データモデルの未決事項）。決まったら NF-R17 に反映する。
- 連鎖削除が、`events` に DELETE 権限を持たないロールでも動くか（NF-S20。データモデルの未決事項）。
- beer-game2 の「74 件」の根拠の確認（ID を数えると 69 件）。beer-game2 の NF-O7（80/70）とテスト戦略（85/75）の不一致の訂正は、本書の範囲外（beer-game2 は変更しない）。
- JVM のコンテナのメモリの割り当てと、ヒープの設定（インフラの設計と合わせて決める）。
