# 非機能要件定義 - ビールゲームシミュレーション（v2）

## 概要

本書は、beer-game2（v2）の非機能要件を、**測定できる形**で定義します。**`docs/` を正本**とします。

beer-game（v1）の [非機能要件](../beer-game/non-functional.md)（61 件、実装の状況と 12 件の差分）を出発点に、v2 の設計と範囲を反映して**改訂**しました。表の「v1 の状態」は、v1 の実装の状況です。**△・✗・未測定は、v2 で満たす対象**です。

- 要件定義（v2）の NFR-01〜NFR-12、`aidlc/` の Unit ごとの NFR 要件（U1〜U5）、v1 の実測を統合しています。
- 数値目標は、運営者（ビジネス側）と合意する前提の**提案**です。出典の ID（例: U1 NFR1.1）は `aidlc/spaces/default/intents/261027-beer-game-development/construction/` 配下の各 Unit の記録を指します。

## 品質特性の優先順位

[非機能要件定義ガイド](../../reference/非機能要件定義ガイド.md) の ISO/IEC 25010 の分類で、学習教材としての性格から優先順位を付けます。

| 優先 | 品質特性 | 理由 |
| :---: | :--- | :--- |
| 1 | 機能の正確性・信頼性（整合性） | 週次計算の忠実性と、確定の一回性が、教材の価値そのもの |
| 2 | セキュリティ（機密性・完全性） | 役割ごとの情報制約が、学習条件の前提。資格の漏洩は他人の役割の操作につながる |
| 3 | 性能効率性・使用性 | 研修中の操作が滞らないこと。アクセシビリティは要件 |
| 4 | 保守性・観測性 | 研修中の障害に気づき、直せること |
| 5 | 可用性（SLO） | 研修の時間帯に使えること。常時の高可用性までは求めない |
| 6 | 拡張性・移植性 | 想定規模（15 チーム）を満たし、増やせる余地を残す |

## SLO の要約（提案）

| 項目 | 目標 | 出典 |
| :--- | :--- | :--- |
| 月間可用性 | 99.5%（事前に通知した計画停止は除外） | U1 NFR2.1 |
| 研修中の完全停止の検知 | 1 分以内に通知 | U1 NFR2.2 |
| 確定済み週のデータ損失（RPO） | 0 | U1 NFR2.3 |
| 障害からの復旧（RTO） | 15 分 | U1 NFR2.4 |
| 入力確定（サーバー側）の p95 | 1 秒以内 | NFR-03、U1 NFR1.1 |
| 週確定から全画面への反映の p95 | 2 秒以内 | NFR-03、U1 NFR1.2 |
| 保持期限後の削除 | 期限到達の 99% を 24 時間以内に完了 | U4 NFR1.2 |

学習ビューの可用性は U3 が 99.9% としていますが、システム全体の SLO（99.5%）を超える目標は意味を持たないため、**全体の 99.5% に統一**します。

## v1 からの変更（差分への対応）

v1 の差分（12 件）への対応です。**すべて v2 の要件として引き継ぎました**。

| # | v1 の差分 | v2 の対応 |
| :--- | :--- | :--- |
| 1 | アプリがログを一切出力しない。メトリクスも無い | NF-O1〜NF-O5。構造化ログ（Pino）、エラーの記録、メトリクス（EMF）を最初から実装する |
| 2 | 本番の資格の鍵が、固定の開発用の値 | NF-S3。**本番では必須。未設定なら起動に失敗する**。鍵に版を持たせる（[ADR-009](../../adr/beer-game2/009-credential-key-versions.md)） |
| 3 | 資格の有効期間が設計と異なる（進行役は期限なし） | NF-S4。すべての資格に期限と失効。進行役の失効・再発行 |
| 4 | セキュリティヘッダーが無い。TLS の最低版を指定できない | NF-S9、NF-S15。CloudFront と API でヘッダーを付け、独自ドメインで TLS 1.2 以上（[ADR-011](../../adr/beer-game2/011-cloudfront-domain-tls-headers.md)） |
| 5 | CI に依存関係・秘密情報・SAST の検査が無い | NF-S13。CI に加える（[ADR-012](../../adr/beer-game2/012-delivery-pipeline-and-terraform.md)） |
| 6 | 可用性の SLI と停止の検知（1 分以内）が無い | NF-R1、NF-R2、NF-O4。合成監視とアラームを設計に含める（[インフラ](./architecture-infrastructure.md)） |
| 7 | 性能の主要な目標が未測定 | NF-P1〜NF-P3、NF-P5。実 DB の負荷試験と、確定から反映までの計測を、夜間に実行して記録する（[テスト戦略](./test-strategy.md)） |
| 8 | 復元の訓練が無い。保存途中の障害の注入テストも無い | NF-R3〜NF-R5、NF-R8。復元の訓練を、四半期とリリース前に行う。障害の注入は DB 統合に含める |
| 9 | 冪等記録の保持が、設計 24 時間に対し実装 30 日 | NF-R6。24 時間に統一（`idempotency_records` は `games` へのカスケードで削除される） |
| 10 | 復帰エンドポイント専用のレート制限が無い。制限がプロセス内 | NF-S11、NF-S19。参加・復帰・招待の専用の制限と、状態の共有 |
| 11 | 数値目標が、運営者と合意されていない | 引き続き、合意を取る（下記の未決事項） |
| 12 | Unit 間で数値が一部食い違っていた | 全体の可用性 99.5%、基準 15 ゲーム、拡張目標 25 ゲームに統一済み |
