# 非機能要件定義 - ビールゲームシミュレーション（Scala 版）

## 概要

本書は、beer-game-scala の非機能要件を、**測定できる形**で定義します。**`docs/` を正本**とします。実装コードはまだ存在せず、**Scala 版の性能・メモリ・起動時間の実測値はありません**。

**範囲（ユーザーの決定、2026-11-25）**: 実装として約束するのは U1〜U3 です。**U1〜U3 の間は、実際の研修には使いません（検証・事例用）。** 本番・復元・観測の完成と、範囲外（U6）の性能の実測は約束ではありません。**U1 の約束は、ジョブの本数ではなく検証の範囲**です（D1。ユーザーの指示に基づき AI が推奨案で決めた。確認は未了）: 検証用の CI（`check`）に加え、統合テスト（PostgreSQL 18）と `@api` の受け入れテストの CI 実行を含みます（[テスト戦略](./test-strategy.md)）。**U1 に入れる US6.1（障害と性能の劣化を検知する）の AC は AC6.1.1（構造化ログ）・AC6.1.2（相関 ID つきの記録）・AC6.1.4（`/ready`）**です（D2。同上。AC6.1.3 メトリクスと AC6.1.5〜6.1.6 通知は約束の外）。**対応する NF の見立て（AI の案）**: AC6.1.1・6.1.2 は NF-O1・NF-O2、AC6.1.4 は NF-O10 に当たり、これらは U1 の範囲。NF-O3・NF-O4・NF-O5（メトリクス・アラート・ダッシュボード）の完成は約束の外です。

[ADR-001](../../adr/beer-game-scala/001-scala-version-of-beer-game-kotlin.md) により、[beer-game-kotlin の非機能要件](../beer-game-kotlin/non-functional.md)（84 件。beer-game2 の 69 件 + Kotlin 版で追加した 15 件）を**正本として引き継ぎ**、Scala の言語とツールで変わるものだけを見直しました。**Scala は Kotlin と同じ JVM（JDK 25 を第一候補）で動くため、Rust 版と違い、ウォームアップ・ヒープと GC・起動時間に関する要件は読み替えずに継続**します。

- **すべての ID を維持**しました（削除はありません）。要件定義の NFR-01〜NFR-12 は変えません（[要件定義](../../requirements/beer-game-ts/requirements_definition.md)）。
- 凡例は Kotlin 版と同じです。**継続**は Kotlin 版と内容が同じ、**変更**は ID は同じで内容を Scala 版に合わせて変えた、**新**は Scala 版で追加した要件です。
- 数値目標は、運営者と合意する前提の**提案**です。**Kotlin 版で提案した数値も、Scala 版の実測で見直す前提**で、実測のない数値を Scala 版の都合で厳しくも緩くもしていません（設計判断 SN2）。
- 新しく加えた要件は 4 件（NF-SC1〜NF-SC4）で、合計 **88 件**です。**`NF-C` は Kotlin 版で「容量・同時実行」に使われているため、Scala 固有の追加は `NF-SC` としました**（ADR-001）。

### 本書の位置づけと確認の範囲

- **継続の要件**は、本文を Kotlin 版と重複して持たず、**要約と ID の対応だけ**を示します。**要件の正本の文言は Kotlin 版の表**です。
- **変更・新の要件**は、本書に全文を書き、**本書を正本**とします。
- **確認したこと**（2026-11-25。リポジトリの外の使い捨てのプロジェクト。sbt 1.13.1、Scala 3.7.4、doobie 1.0.0-RC12、ローカルの Docker の `postgres:18.6`）:
  - **NF-SC2 の前提**: doobie の `transact` は、`ConnectionIO` が例外なく完了すれば、値が `Left` でも COMMIT する。`FC.rollback` を挟むと残らない（[データモデル](./data-model.md) の検証）。トランザクションの境界（commit・rollback の呼び出し）は、スタブの `Connection` を渡した `Transactor.fromConnection` で、DB なしに記録できる（[テスト戦略](./test-strategy.md) の確認した事項 8）。
  - **NF-SC4 の道具**: cats-laws + discipline-munit で `MonoidTests` が走り、`empty` を壊した実装は 4 件の法則で落ちる（確認した事項 3）。
  - **NF-O7 の道具**: sbt-scoverage 2.4.4 が文と分岐の率を出し、しきい値を割ると `coverageReport` が失敗する。行の独立した指標は無い（確認した事項 4）。**行率を XML の文の行番号から算出できるかは未確認**（B1）。
  - **NF-O8 の道具**: scalac のオプション、WartRemover 3.6.3、sbt-scalafix 0.14.10 が Scala 3.7.4 で動く（確認した事項 9〜11）。
  - **NF-S20（追記専用）・NF-S16（連鎖削除）**: Rust 版が PostgreSQL 18.6 で SQL として実測した結果を引用します。**Scala 版の接続・権限のないロールからは未確認**です。
- **それ以外の要件は、すべて未検証**です。
- **確認状況の正本の規則（N-H5。AI の案で承認を得ていない）**: [技術スタックの確認状況の一覧](./tech-stack.md#確認状況の一覧)が正です。一覧の根拠は実測の記録（[データモデル](./data-model.md) の「検証の結果」と [テスト戦略](./test-strategy.md) の「確認した事項」）で、**一覧を直すときは根拠も直します**。
- **レビュー（2026-11-25）への対応の承認の状況**: ユーザーが決めたのは H3（`Ignored` で止める設計を維持）、H6（カバレッジは行率を算出する案 C を第一）、H7（範囲は U1〜U3 を約束）、H9（NF-P2 は p95 4 秒）に加え、再レビューへの対応の次の 4 件です。**N-H4（検証用の CI の `check` ジョブ 1 本は U1 の約束に含める。AWS 環境・デプロイ用ワークフロー・ステージングへの自動反映は後回し。自動反映を持たない間の team 規約の例外は ADR に記録して人が承認する）、N-H6（`domain` の文 97% は目安。ゲートにするかは B1 の実測後）、N-H7（止まったゲームでも状態取得の読み取りは返すことを要件にする）、N-H8（U1〜U3 は実際の研修に使わない）**。**これら以外（N-H1・N-H2・N-H3・N-H5 の直し方など）は AI の案で、承認を得ていません**。
- **再々レビュー（2026-11-25）への対応の区分**: ユーザーが「決定を行い、高 10 件を設計書に反映」と指示したため、AI が推奨案で決めたものがあります（**ユーザー本人が選択肢を選んだ決定ではなく、確認は未了**）。**D1**=統合テストと `@api` の受け入れを U1 の約束に含める、**D2**=US6.1 は AC6.1.1・6.1.2・6.1.4、**D3**=失効済みの旧担当者の入れ替えは未失効の旧担当者にだけ `CredentialRevoked`、**D4**=H2 版の `ProjectionLock` は Kotlin 版と同じ構造（`StampedLock` 系 + 待ちの上限 + 後始末）、**D5**=team 規約が beer-game-scala に及ぶかの確認と例外の記録は人の承認の場で行う（M1。AI は `project.md` を編集しない）。**これら以外はすべて AI の案で、承認を得ていません。**

## 品質特性の優先順位と SLO の要約

**Kotlin 版と同じです。** 優先順位は、1 機能の正確性・信頼性（整合性）、2 セキュリティ、3 性能効率性・使用性、4 保守性・観測性、5 可用性（SLO）、6 拡張性・移植性。SLO は、月間可用性 99.5%、完全停止の検知 1 分以内、RPO 0（確定済み週）、RTO 15 分、入力確定（サーバー側）p95 1 秒以内、週確定から全画面への反映 **p95 4 秒以内（Scala 版は NF-P2 を再定義した。ユーザーの決定、2026-11-25。Kotlin 版は 2 秒）**、保持期限後の削除（期限到達の 99% を 24 時間以内）。

## ES + CQRS と Scala で変わる点

ES + CQRS による変化（再生による書き込み時間、ストリームの版の一意制約と自動再試行、同期投影、投影の再構築、追記専用、個人情報の分離、イベントの互換）と、JVM による変化（起動、ウォームアップ、ヒープ）は **Kotlin 版と同じ**で、要件もそのまま引き継ぎます。**Scala の言語・ツールで変わる点**は次のとおりです。

| 観点 | Kotlin 版 | Scala 版 | 関係する要件 |
| :--- | :--- | :--- | :--- |
| 失敗の扱い | `Either` の左。永続化の失敗は境界で左に変換 | 業務の失敗は `Either`、**`IO` の失敗は想定外に限る**（ガイド ADR-050）。永続化の失敗（例外）は境界で `AppFailure.Persistence` に写す | NF-R9 |
| トランザクションの終わり | ブロックが `Left` を返したら ROLLBACK | **doobie は `Left` でも COMMIT する**。書き込みの公開の入口を `Tx.run` だけにして ROLLBACK を明示（SBD2）。**案（H4・N-H3）: 許可した入口（`Tx`・`ReadTx`・`ModeTx`・`LISTEN` の専用接続）のファイルの外での `.transact(` などの直接呼び出しを Scalafix で禁止**（旧案の合成子 `Tx.rollbackOnLeft` は不採用） | **NF-SC2（新）**、NF-R5 |
| 非同期とキャンセル | コルーチン。`NonCancellable` で COMMIT/ROLLBACK | `Fiber` の取消。`execute` を `Supervisor` で切り離し、失敗の経路は ROLLBACK を明示（SBD4） | **NF-SC1（新）**、NF-R3、NF-R5、NF-R9 |
| 純粋性の守り | detekt の `ForbiddenMethodCall`、Gradle のモジュール | `domain` は `cats-core` だけに依存、WartRemover・Scalafix | **NF-SC3（新）**、NF-O8 |
| 代数構造 | 使わない（Arrow の `Raise`） | `Monoid[TeamTotals]`・`Functor[RoleMap]` を使い、法則をテストする（SD6） | **NF-SC4（新）** |
| 検証 | `zipOrAccumulate` | `ValidatedNec` + `mapN` | NF-S10 |
| 静的解析・整形・カバレッジ | detekt・PMD・ktlint、Kover（行・分岐） | scalac のオプション・WartRemover・Scalafix・Scalafmt、scoverage（文・分岐） | NF-O7、NF-O8、NF-S13 |
| 実行環境の観測 | JVM のヒープ・GC・スレッド・`Dispatchers.IO` の飽和 | JVM のヒープ・GC・スレッド（同じ）+ cats-effect の実行基盤（計算用・ブロッキング用のスレッドプール）の飽和 | NF-O12 |
| DB のクライアント | JDBC + HikariCP | doobie（`ConnectionIO`）+ HikariCP（`doobie-hikari`）。マイグレーションは Flyway（同じ） | NF-O3、NF-C5、NF-O11 |
| ローカル開発の DB | H2 を許す | **同じ（H2 の PostgreSQL モードを許す。ST9。ユーザーの決定、2026-11-25。導入は承認待ち）**。本番・ステージングでは拒否。NF-S20・NF-S18 は H2 版では守られず、PostgreSQL の統合テストでだけ検証する | NF-S20、NF-S18 の検証範囲 |

## 性能要件

JVM のウォームアップ・ヒープ・起動に関する NF-P1・NF-P15〜NF-P18 は、**Kotlin 版のまま継続**します（Scala も JVM のため）。**Kotlin 版の数値は Kotlin の実装についての提案値で、Scala の実装の実測で見直します**（SN2）。**ただし NF-P2・NF-P4 は、画面の実態に合わせて Scala 版で再定義した**（下の表）。計測の方法（JMH か自前か）は実装開始時に決めます（**JMH を Scala から使う場合の道具は未確認**）。

### 継続する要件（要約。正本は [Kotlin 版](../beer-game-kotlin/non-functional.md)）

**NF-P2・NF-P4 は、Scala 版で内容を変えた**（下の表に全文を書く。変更の理由は「beer-game-kotlin からの変更」）。他は継続です。

| ID | 要約 |
| :--- | :--- |
| NF-P1 | 15 チーム（各 4 参加者 + 進行役）の同時利用で、意思決定の送信と役割別の状態取得の p95 を 1 秒以下。**JVM のウォームアップ（NF-P16）の後の定常値で測る**。75 並行、15 分 |
| NF-P2 | 週確定から全ブラウザの表示まで **p95 4 秒以下**。同一の時計（確定した側のブラウザの時刻を基準）で測る（**この「同一の時計」は複数端末では成り立たない。B1 では同じ機械の複数タブで測る前提を置く**。L4）。同期投影のため、通知の版以上の状態が取れる。**目標の再定義（2026-11-25 にユーザーが決定。旧: p95 2 秒以下・p99 5 秒以下）**: 現行の画面は SSE を使わず、3 秒間隔のポーリング（`PlayPage`・`LobbyPage`・`ObservationPage` が各 `*_POLL_MS = 3000`。console にはポーリングがない）で、Scala 版は画面を変えない（SU2・SF1）。2 秒は 3 秒間隔のポーリングでは満たせないため、ポーリングの間隔（3 秒）＋取得の所要に収まる 4 秒に定めた（Rust 版が 2026-11-23 に同じ再定義をした先例と揃える）。**根拠の数値は Rust 版の推定**（GET の実測 + 3 秒間隔からの計算で p95 約 2.86 秒。画面を介した実測ではない。[Rust 版の NFR の検証結果](../../development/beer-game-rust/nfr_results.md)）で、**Scala 版の値は実測していない**。**SSE で 2 秒を保つことは、全実装共通の画面の改善として別に扱う**（画面を変えない前提と両立しない。[UI 設計](./ui-design.md) の #12、[フロントエンド](./architecture-frontend.md)）。**扱いの補足（M3）**: (1) **旧の「p99 5 秒以下」を外したのは、AI の解釈**（ユーザーの決定は「p95 4 秒」。p99 を持たないことまでは決めていない）。(2) 「全ブラウザ」のうち、**S06（進行役のコンソール）には自動更新が無く、手動の操作でしか更新されないため、ポーリングの測定の対象にならない**。測るのは S05・S07 に限る案（AI の案。**S04 ロビーのポーリングは準備中だけで、週確定の反映の対象ではないので外した**。L4）。コンソールが自動更新されないことは、全実装共通の画面の課題（[UI 設計](./ui-design.md) の未決事項 8）。(3) 実測の方法（画面を通すか、GET の実測 + 計算か）は B1 で決める（[テスト戦略](./test-strategy.md)）。**範囲外（U6）の性能を早めに計測することは約束ではない** |
| NF-P3 | 週確定のサーバー処理（再生・`handle`・追記・同期投影・冪等記録）は p95 1 秒以下、p99 2 秒以下（最大の長さ 2000 件） |
| NF-P4 | SSE が使えない場合（現行の画面は常にこの状態）、**3 秒間隔のポーリング**（現行の画面の実態）で、確定から 4 秒以内に最新の版を表示する。**Rust 版の推定では最大約 3.0 秒**（画面を介した実測ではない）。Scala 版の値は未測定。**分位は p95（AI の案。M3）**。**Play は 1 回の取得で GET を直列に 2 回**（`/games/{id}/state` のあと `/sessions/{id}/state`）取り、保存中・操作中は取り直しを飛ばし、失敗は黙って無視するため、**6 秒を超える場合がありうる**。したがって、最大値の保証ではなく p95 の目標とする |
| NF-P5 | ブラウザでの入力確定から成功の表示まで p95 1 秒以下 |
| NF-P6 | 停止・再開・代理入力の API は p95 500 ms 以下 |
| NF-P7 | 再接続時の状態取得は 75 並行で p95 1 秒以下。SSE の再接続後 5 秒以内に最新の版。**SSE の部分は、現行の画面が SSE を使わないため、画面を通したテストでは検証できない。API 層の検証に移す、または画面が SSE を使い始めるまで保留**（M12。AI の案） |
| NF-P8 | 観察と振り返りの取得は p95 1 秒以下。投影の SQL で返し、観察者は 3 表だけを読む |
| NF-P9 | エクスポートは受理 1 秒以内、CSV と JSON を 30 秒以内（p95）。`buildExport` で要求時に作る |
| NF-P10 | 保持状態の取得は p95 1 秒以下 |
| NF-P11 | 期限に達した削除の 99% を 24 時間以内に完了する |
| NF-P12 | 1 リクエストの処理量の上限（数量 0〜1000、リクエスト 64 KB） |
| NF-P13 | 共同入力の保存（競合の検出と自動再試行を含む）は p95 1 秒以下 |
| NF-P14 | 自動確定は、最後の保存から確定の完了まで p95 1 秒以下（1 回の追記） |
| NF-P15 | ストリームの再生（`events` の読み込みと `foldLeft`）は、`SESSION` が 1000 件のとき読み込みを含めて p95 100 ms 以下、再生だけで p95 20 ms 以下。最大の長さ（2000 件）でも測り、満たさなければスナップショット（NF-C9）を検討。**ウォームアップの先頭 5 回以上は p95 に入れず、試行は 100 回以上**（提案） |

| NF-P19 | 同期投影を含む追記のトランザクション全体の DB 側の時間は p95 100 ms 以下（提案） |
| NF-P20 | （条件付き）非同期投影へ移した場合の投影の遅延は p95 1 秒以下。現在の設計では適用しない |

### ストリームの最大の長さ

Kotlin 版と同じです（想定 1000 件、保存回数の上限（提案: 1 役割・1 週あたり 9 回。代理入力を含む）を置くと最大 2000 件）。**この見積もりと上限は設計上の見積もり**で、Scala の実測で見直します。上限の有無と値は、運営者と合意して決める未決事項です。

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |

## 未決事項

3. **Scala 版の実測**: NF-P15・NF-P16・NF-P17・NF-P18・NF-P19 の目標値は、すべて提案で、Scala の実測で見直す。計測の道具（JMH の採否）は未選定。

7. **NF-S13 の依存関係の脆弱性検査の道具**（選定未決。Dependabot か Renovate かも未決）。
8. **ローカル開発の DB**（ST9）: H2 の採用は決定済み。NF-S20（追記専用）・NF-S18（観察者の権限）は、**H2 版（ローカル）では守られない**ため、検証範囲は PostgreSQL の統合テストに限る。残る未決は、H2 の導入の承認と、B1 の最初の実測（動作範囲、性能は H2 では計測しない）。
9. **保存回数の上限**（NF-C8。最大の長さ 2000 件の根拠）、**資格の有効期間の既定値**、**負荷試験の実施環境**、**追記の競合の自動再試行の上限と間隔**（NF-R17。初期値 10 を引き継ぎ、Scala で再計測。**上限が「総試行回数」か「再試行回数」かを 1 つに決める**。`execute` のスケッチは総試行回数で、案は総試行回数。境界値は [テスト戦略](./test-strategy.md)。M10）、**研修中の再構築の方式**（NF-R15。暫定）、**保持の起点**（NF-S16。暫定）、**出力のキャッシュ**（NF-P9）。いずれも [Kotlin 版の未決事項](../beer-game-kotlin/non-functional.md) に追従する。
10. **コンテナのメモリの割り当て**（NF-P17。JVM のヒープの設定をインフラの設計と合わせて決める）と、**NF-P16 の Fargate での実測**。
