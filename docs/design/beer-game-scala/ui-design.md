## Scala 版のバックエンドが UI に与える影響

UI は API の契約にだけ依存します。Scala の実装が**契約から外れる可能性のある箇所**を、UI の側から列挙します。いずれも、契約テスト（[テスト戦略](./test-strategy.md)）と E2E で、契約どおりであることを確認します。

| # | UI が前提にしていること | Scala 版で起きうる逸脱 | 対策・検証 |
| :--- | :--- | :--- | :--- |
| 1 | **エラーは必ず problem+json**（`type`、`code`）。画面の辞書の鍵は `code` | http4s が自動で返す応答（**経路なし、メソッド違い、本文の解析の失敗（circe のデコードの失敗）、不正な Content-Type、サイズ超過**）は、**既定では problem+json にならない**可能性がある（**既定の応答の形は未確認**） | **すべての失敗を `AppFailure` の写像（problem+json）に通す**。ルートの `orNotFound` と、本文の解析の失敗を、`request.*`・`validation.invalid_input`・`app.*` の `code` に写す（`ErrorHandling` 相当のミドルウェアか、自前の関数。名前は未確認）。契約テスト「実装の `code` の全体と仕様の一致」と「ルートの網羅」で検証。**画面の実際の扱い**: JSON でない本文（HTML など）は本文なしの失敗として扱われ、**JSON でない 5xx は `type` なしと判断されて、「結果が不明」として同じキーで最大 2 回自動で再送される**（`client.ts`）。404・405 などの 4xx は再送されない。**自動再送の対象は、状態を変える操作（`command`）だけ**で、取得（`query`。ポーリングの GET など）は自動再送しない（`client.ts` の `command` の `for` のループだけに `maxResends` がある。L1） |
| 2 | **バックエンド自身が返す 503 は必ず `type` を持つ**。`type` のない 503 は「結果が不明」として**同じキーで再送**する | ミドルウェアが `type` のない 503 を返すと、画面が「結果が不明」と誤認して再送し、新しいキーで再送すべき場面を取り違える | **503 は `app.retry_exhausted`（同時に走るコマンドの上限超過、プール取得のタイムアウト、`lock_timeout` を含む）・`app.not_ready` など `type` つきだけ**にする。`type` のない 503 を返さないことを契約テストで確認。**ミドルウェアのタイムアウトは、`type` を付けない 504 にして「結果が不明」と扱わせる**（#11） |
| 3 | **結果が不明（通信の切断）のとき、同じ冪等キーで再送すると、同じ結果を受け取る** | クライアントの切断でルートの `Fiber` が取り消され、コマンドが**途中までしか実行されない**恐れ（**http4s ember が切断時にハンドラを取り消すかは未確認**） | **SBD4**: `execute` を `Supervisor` で切り離して起動し、ルートは完了を待つ。失敗の経路では ROLLBACK を明示する（SBD2）。切断後の再送が保存済みの応答を返すことを DB の統合テストで検証する。**これが成り立てば、UI の「結果が不明」の設計は変わらない**。成り立たなければ、設計を見直す（[バックエンド](./architecture-backend.md) の前提と見直しの条件） |
| 4 | コマンドの応答は `versions` だけ。画面は応答後に**スナップショットを取得し、版に追いつくまで待つ**。現行の画面は SSE を使わず、自動更新（ポーリング）と、保存・確定の応答の後の取得で更新する（#12） | 同期投影の更新漏れで、応答の `versions` より古いスナップショットが返る | 問い合わせの REPEATABLE READ と `projection_checkpoints` の同時読み取り（[バックエンド](./architecture-backend.md)）。統合テスト「問い合わせの一貫性」 |
| 5 | **（SSE を使う場合の前提。現行の画面は使わない）** SSE は版の通知だけ。再生なし。60 秒より短い間隔の心拍。遅い接続は切断され、再接続後にスナップショットで追いつく | http4s の `ServerSentEvent` と fs2 の `Topic` の遅い購読者の扱い（**発行側が止まりうるか未確認**）。心拍・切断・シャットダウンの動作は未確認（SBD9） | **画面が SSE を使い始める時点で、SSE の負荷試験と E2E「SSE の切断」で確かめる**。現行は未使用のため、Scala 版のバックエンドは SSE を実装しなくても、既存の画面は動く |
| 6 | 資格の Cookie は `HttpOnly`・`Secure`・`SameSite=Strict`。**タブごとに名前を変える**（`X-Tab-Id`、`bg_session_<id>`・`bg_recovery_<id>`。ADR-020） | Cookie の発行・読み取りを自前のミドルウェアで書くため、属性や名前の解決の漏れが起きうる | HTTP の統合テスト（ヘッダーのテスト）。Kotlin 版の ADR-020 自体は提案中だが、既存のフロントエンドは `X-Tab-Id` を送っている（[フロントエンド](./architecture-frontend.md)） |
| 7 | 失敗の文言は、**送った資格の種類**から選ぶ（無効な資格は、すべて同じ 403 の本文） | 認可の失敗の応答の本文が、種類によって違うと、資格の存在・期限が推測される（NF-S12） | 認可の否定テスト（無効な資格はすべて同じ応答。`AppFailure.Unauthorized` と `Forbidden` の分類を同じ本文に写す） |
| 8 | 予期しない失敗（500）では、**相関 ID だけ**を画面に示す | `IO` の失敗（`Throwable`）をそのまま返すと、内部の情報が漏れる | 境界で `IO` の失敗を `AppFailure.Persistence`（500）に写し、利用者へは相関 ID だけを返す。`LogRecord` は資格・表示名の項目を持たない（SBD10）。**画面の実際の扱い**: 相関 ID は **problem+json の本文の `correlationId`** からだけ読む（ヘッダーは読まない。`ErrorNotice` が「相関 ID: …」と表示）。予期しない失敗は `code: app.internal`（辞書に文言がある）で返し、**本文に `correlationId` を必ず入れる** |
| 9 | `Retry-After` ヘッダーを `app.retry_exhausted`（503）と `app.rate_limited`（429）に付ける | 付け忘れ | 契約テスト（`Retry-After` の存在）。**画面は `Retry-After` を読まない**（`api/` に読む処理がない。`app.retry_exhausted` は `type` つきの「未実行」で、利用者の再操作を待つ）。したがって `Retry-After` は**バックエンドが契約として満たす要求**で、画面の振る舞いには効かない |

## インタラクション設計

Kotlin 版の次の節を、そのまま引き継ぎます（内容は複製しません）。

- 共通のルール（明示的なボタンで操作を始める、フォーカスと入力だけで状態を変えない）
- **保存直後の表示と投影の遅延**（応答は `versions` だけ。スナップショットを取得して追いついてから表示。同期投影のため遅延は通常ない。反映待ちの共通部品）
- **競合の種類と表示**（`session.decision_conflict`、`session.week_advanced`、`session.decisions_changed`、`app.retry_exhausted`）
- **エラーの `code` と表示の辞書**（正本。鍵は `code`。**Scala 版でも `code` の一覧を変えない**。`DomainError` の `code` と `AppFailure` の写像の全体が OpenAPI の一覧と一致することを契約テストで確認する。辞書が全 `code` を網羅することは、既存のフロントエンドの型検査（`Record<ErrorCode, …>`）で守られる）
- **結果が不明なとき**（`type` のない 5xx・タイムアウト・切断は「結果が不明」として同じキーで再送。`type` つきの 503 は利用者の再操作で新しいキー）
- 主な操作の流れ、エラーと状態のフィードバック、画面の状態

## アクセシビリティ

## 設計判断

**SU1〜SU2 は、AI が起草した案で、ユーザーの承認を得ていません**（Rust 版の RU1・RU2 は承認済みで、Scala 版はそれに倣った提案）。

### SU1: UI 設計は複製せず、Kotlin 版を正本として参照する（提案）

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| **A（提案）** | Scala 版の UI 設計は差分の文書にとどめ、画面・遷移・画面イメージ・辞書は Kotlin 版を正本として参照する | 食い違いが生まれない。API の契約が同じ間は変更が一度で済む。参照先を読む手間が増える |
| B | Kotlin 版の UI 設計を Scala 版に複製して持つ | 文書が自己完結する。ワイヤーフレームと辞書が二重になり、片方の更新漏れが起きる |
| C | UI 設計をプロジェクトに属さない共通の文書へ移す | 正本が 1 つになる。ドキュメント構成のガイド（プロジェクト別のカテゴリ）に反する。**構造の変更で確認が要る** |

### SU2: 契約から外れる実装の逸脱は、画面でなくバックエンドで直す（提案）

画面は API の契約にだけ依存し、実装の違いを知りません。上の影響の表の逸脱は、**バックエンドを契約に合わせて直す**（画面を実装ごとに分岐させない）。画面の変更が避けられないときは、設計の矛盾として扱います。

## 未決事項

1. **SU1・SU2 の承認**。
2. **http4s の既定の応答**（#1・#2）: 経路なし、メソッド違い、本文の解析の失敗、タイムアウトの形と、problem+json への写像の方法（B1 で確認）。
3. **ember の切断時のハンドラの取消と `Supervisor` による切り離し**（#3・#11）: B1 の統合テストで確かめる。
4. **同じ `Idempotency-Key` の再送が、元の処理の実行中に届いたときの待ち方**（#11。バックエンドの未決事項と共通）。
5. **circe による誤りの集約**（#13）: 型の誤りも含めて集められるか。集められない場合の扱い。
6. **SSE の API と、遅い購読者の扱い**（#5）。
7. **数値の型の範囲**（#10）: 契約に整数の範囲を書くか。
8. **ポーリングの失敗が黙って無視される**（#12。S05・S07。S04 は 403 だけ表示）: Kotlin 版・Rust 版と共通の課題。**数回続けて失敗したら、最終更新の時刻と「接続を確認しています」を示す**ことを、全実装共通の画面の課題として優先度を上げ、ストーリー化する案（M16。承認を得ていない）。画面側の対応は、Kotlin 版の UI 設計と合わせて決める。`Ignored` で止まったゲームの知らせ方（#15）も同じ枠で扱う。**受入条件の案（承認を得ていない。R-H8）**:

(a) **「続くとき」の判定は、同じタブで同じゲームへの操作が `app.internal` で 2 回続けて失敗したとき**（画面は、パターン 17 と 18 を見分けられないため、1 回目では再操作を促し、2 回目で止める）。Given/When/Then で書くと次のとおり。

```gherkin
シナリオ: 同じ操作が 2 回続けて app.internal で失敗したら、再操作を促さず運営者への連絡を促す
  前提 参加者が S05 で、同じゲームへの保存が app.internal（500・相関 ID つき）で 1 回失敗した状態である
  もし 同じタブで、もう一度同じ操作が app.internal で失敗する
  ならば 画面は「もう一度お試しください」「再度操作してください」を出さない
  かつ 「操作を繰り返さず、相関 ID を運営者に伝えてください。」と相関 ID を示す
  かつ 相関 ID は、まず書き写せるよう、手動更新を押しても消えない
```

(b) 相関 ID は、**操作した人のタブにだけ出る**（他の参加者・進行役の画面には出ない）。(c) 手動更新の成功で消える（`PlayPage.tsx` の `refresh` の先頭 90 行の `setFailure(null)` は現状、押した時点で消える。(a) の最後の「消えない」は現状の挙動と逆で、**画面の変更が要る**）。(d) S06 コンソールが自動更新（または手動更新のボタン）を持つ（コンソールが自動更新されないことは、全実装共通の画面の課題）。**画面を変えない前提（SU2）の間は、この条件は満たせず、依頼文言（[運用要件](./operation.md) パターン 18。「まず書き写す、そのあと手動更新」）で補う**。
8a. **SSE で 2 秒を保つ画面の改善**（#12）: 全実装共通の別の課題として扱う。Scala 版だけでは決めない。
8b. **ゲーム作成の二重送信**（#11。L7）: ゲーム作成は `If-Match` で守られないため、結果が不明のとき、同じキーの自動再送と、利用者の再操作（新しいキー）で、ゲームが 2 つできうる。Kotlin 版と共通の課題として、未決のまま残す。
8c. **進行役向けの 1 枚の案内**（L11。beer-game2 から一貫して欠けている）: 「研修中にシステムが止まったら・人が入れ替わったら」を 1 枚にまとめる案。内容の案は [運用要件](./operation.md) の未決事項 3b。ポーリング失敗の無言（未決事項 8）と合わせてストーリー化する（承認を得ていない案）。**1 枚に入れる項目（M11・M8。案）**: (i) 準備中に、**予備の参加者を参加させておく**（開始後の参加は受け付けない）、(ii) 予備がいない場合は、**残りを進行役の代理入力で続けられる**、(iii) 研修 1 回が 90〜120 分（運営者の想定。出典は要確認）で、長く止まると場が冷えるので**止まったら早めに紙に切り替えてよい**、(iv) 止まったときは、同じ操作が 2 回続けて失敗したら操作を繰り返さず、**まず相関 ID を書き写し**（そのあと手動更新）、運営者に伝える、(v) 参加者に伝える、控える数字（S05 の在庫・受注残・入荷・受注と、保存済みの現在の入力と未保存の `draft`。進行役は S06 を再読み込みして結果表を撮る）。**「入荷予定」と「上流へ送って未着の発注」は、画面に項目が無く、結果表の出荷・発注から復元する**（[運用要件](./operation.md) のパターン 18）。画面に「入荷予定」を出すかは、全実装共通の画面の課題。
9. **Kotlin 版の未決事項の引き継ぎ**: 手動のアクセシビリティの確認の担当者と時期、保持の表示（暫定。M5）、自動確定の本人へのフィードバックの文言、参加者のロビーの扱い、ヘルプの教材の本文の人による確認。いずれも [Kotlin 版の未決事項](../beer-game-kotlin/ui-design.md) に追従する。
