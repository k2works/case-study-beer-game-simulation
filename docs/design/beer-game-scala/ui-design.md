## 画面一覧と遷移

画面の ID と URL は Kotlin 版・Rust 版と同じです（**S01 はじめる `/`、S02 ゲーム作成 `/new`、S03 参加・復帰 `/join`、S04 ロビー `/games/:id/lobby`、S05 プレイ `/games/:id/play`、S06 進行役のコンソール `/games/:id/console`、S07 観察 `/games/:id/observation`、S08 振り返り `/games/:id/review`、S09 保持状態 `/games/:id/retention`、S10 観察者の参加 `/observe`、S11 ヘルプ `/help`**）。遷移図と遷移の条件（検証エラーはすべて集めて一度に示す、資格が有効なら状態に応じた画面へ、権限の無い URL は S03 へ誘導する、など）は、[Kotlin 版](../beer-game-kotlin/ui-design.md) の「画面遷移」の節を参照します。**Scala 版でも「検証の誤りはすべて集めて 422 で返す」**（`ValidatedNec`。[ドメインモデル](./domain-model.md) の SD3）ため、S02 の「誤りを一度に示す」振る舞いは変わりません。ただし、**型の誤りも含めて集められるかは、DTO の作り方に依存します**（下の #13）。

## Scala 版のバックエンドが UI に与える影響

UI は API の契約にだけ依存します。Scala の実装が**契約から外れる可能性のある箇所**を、UI の側から列挙します。いずれも、契約テスト（[テスト戦略](./test-strategy.md)）と E2E で、契約どおりであることを確認します。

| # | UI が前提にしていること | Scala 版で起きうる逸脱 | 対策・検証 |
| :--- | :--- | :--- | :--- |
| 1 | **エラーは必ず problem+json**（`type`、`code`）。画面の辞書の鍵は `code` | http4s が自動で返す応答（**経路なし、メソッド違い、本文の解析の失敗（circe のデコードの失敗）、不正な Content-Type、サイズ超過**）は、**既定では problem+json にならない**可能性がある（**既定の応答の形は未確認**） | **すべての失敗を `AppFailure` の写像（problem+json）に通す**。ルートの `orNotFound` と、本文の解析の失敗を、`request.*`・`validation.invalid_input`・`app.*` の `code` に写す（`ErrorHandling` 相当のミドルウェアか、自前の関数。名前は未確認）。契約テスト「実装の `code` の全体と仕様の一致」と「ルートの網羅」で検証 |
| 2 | **バックエンド自身が返す 503 は必ず `type` を持つ**。`type` のない 503 は「結果が不明」として**同じキーで再送**する | ミドルウェアが `type` のない 503 を返すと、画面が「結果が不明」と誤認して再送し、新しいキーで再送すべき場面を取り違える | **503 は `app.retry_exhausted`（同時に走るコマンドの上限超過、プール取得のタイムアウト、`lock_timeout` を含む）・`app.not_ready` など `type` つきだけ**にする。`type` のない 503 を返さないことを契約テストで確認。**ミドルウェアのタイムアウトは、`type` を付けない 504 にして「結果が不明」と扱わせる**（#11） |
| 3 | **結果が不明（通信の切断）のとき、同じ冪等キーで再送すると、同じ結果を受け取る** | クライアントの切断でルートの `Fiber` が取り消され、コマンドが**途中までしか実行されない**恐れ（**http4s ember が切断時にハンドラを取り消すかは未確認**） | **SBD4**: `execute` を `Supervisor` で切り離して起動し、ルートは完了を待つ。失敗の経路では ROLLBACK を明示する（SBD2）。切断後の再送が保存済みの応答を返すことを DB の統合テストで検証する。**これが成り立てば、UI の「結果が不明」の設計は変わらない**。成り立たなければ、設計を見直す（[バックエンド](./architecture-backend.md) の前提と見直しの条件） |
| 4 | コマンドの応答は `versions` だけ。画面は応答後に**スナップショットを取得し、版に追いつくまで待つ**。現行の画面は SSE を使わず、自動更新（ポーリング）と、保存・確定の応答の後の取得で更新する（#12） | 同期投影の更新漏れで、応答の `versions` より古いスナップショットが返る | 問い合わせの REPEATABLE READ と `projection_checkpoints` の同時読み取り（[バックエンド](./architecture-backend.md)）。統合テスト「問い合わせの一貫性」 |
| 5 | **（SSE を使う場合の前提。現行の画面は使わない）** SSE は版の通知だけ。再生なし。60 秒より短い間隔の心拍。遅い接続は切断され、再接続後にスナップショットで追いつく | http4s の `ServerSentEvent` と fs2 の `Topic` の遅い購読者の扱い（**発行側が止まりうるか未確認**）。心拍・切断・シャットダウンの動作は未確認（SBD9） | **画面が SSE を使い始める時点で、SSE の負荷試験と E2E「SSE の切断」で確かめる**。現行は未使用のため、Scala 版のバックエンドは SSE を実装しなくても、既存の画面は動く |
| 6 | 資格の Cookie は `HttpOnly`・`Secure`・`SameSite=Strict`。**タブごとに名前を変える**（`X-Tab-Id`、`bg_session_<id>`・`bg_recovery_<id>`。ADR-020） | Cookie の発行・読み取りを自前のミドルウェアで書くため、属性や名前の解決の漏れが起きうる | HTTP の統合テスト（ヘッダーのテスト）。Kotlin 版の ADR-020 自体は提案中だが、既存のフロントエンドは `X-Tab-Id` を送っている（[フロントエンド](./architecture-frontend.md)） |
| 7 | 失敗の文言は、**送った資格の種類**から選ぶ（無効な資格は、すべて同じ 403 の本文） | 認可の失敗の応答の本文が、種類によって違うと、資格の存在・期限が推測される（NF-S12） | 認可の否定テスト（無効な資格はすべて同じ応答。`AppFailure.Unauthorized` と `Forbidden` の分類を同じ本文に写す） |
| 8 | 予期しない失敗（500）では、**相関 ID だけ**を画面に示す | `IO` の失敗（`Throwable`）をそのまま返すと、内部の情報が漏れる | 境界で `IO` の失敗を `AppFailure.Persistence`（500）に写し、利用者へは相関 ID だけを返す。`LogRecord` は資格・表示名の項目を持たない（SBD10） |
| 9 | `Retry-After` ヘッダーを `app.retry_exhausted`（503）と `app.rate_limited`（429）に付ける | 付け忘れ | 契約テスト（`Retry-After` の存在） |
| 10 | 数値（`versions`、意思決定の版）は、JavaScript で正確に扱える範囲の整数 | Scala の `Long` の値が JSON で大きな数になると、精度を失う | 版は 1 から数える小さな整数（ストリーム千件前後）で、実際には問題にならない。**型の範囲を契約に書く**かは未決（Kotlin 版・Rust 版と共通） |
| 11 | **「結果が不明」の扱い**: 画面は、`type` つきの応答を「**未実行**」として扱い、利用者の再操作を**新しい冪等キー**で送る。`type` のない 5xx・通信の失敗は「結果が不明」として、**同じキーで最大 2 回だけ自動で再送**する（`client.ts`） | ミドルウェアのタイムアウトが `type` つきの応答を返すと、**処理は COMMIT まで進んでいる**のに、画面が未実行と判断して新しいキーで再操作する（二重になる。見込み）。また、切り離した元の処理が**実行中のまま**、同じキーの再送が届く | **(a) タイムアウトの応答は、`type` を付けない 504（または切断）にする。** OpenAPI の `ErrorCode` にタイムアウトの `code` を足さない。**(b) 元の処理が実行中に同じ `Idempotency-Key` の再送が届いたときは、先の処理の完了を待ち、保存済みの応答（または同じ失敗）を返す**（`409 app.idempotency_key_reused` を返さない）。**実現は B1 で確認**（[バックエンド](./architecture-backend.md) の SBD4）。契約テストの検証項目に加える。ゲーム作成は `If-Match` で守られないため、Kotlin 版と共通の課題として未決事項に残す |
| 12 | **現行の画面の更新は、SSE でなくポーリング**: `features/play/PlayPage.tsx` は `PLAY_POLL_MS`（3000 ms）の間隔で、黙って状態を取り直す。**ポーリングの失敗（403・レート制限・タイムアウト）は黙って無視され、画面は古いまま何の通知も出ない** | **レート制限をポーリングの GET に適用すると**、制限に達した GET が黙って失敗し、画面が古いままになる。3 秒間隔では、反映の遅れは最大で約 3 秒に GET の時間を足したもの | (a) **レート制限は、ポーリングの GET を対象外にする**（参加・復帰・招待の専用の制限は別。NF-S11）。(b) **NF-P2 の値は、Scala 版で実測して決める**（Kotlin 版・Rust 版の実測を参考にするが、Scala 版の値ではない）。(c) ポーリングの失敗が続くときに画面が古いままであることは、Kotlin 版・Rust 版と共通の未解決の課題 |
| 13 | **入力の誤りを一度に示す**: S02（ゲーム作成）は、422 の `errors[]` を**項目ごと（`errors[].field`）に**、入力欄の近くへ示す | **circe の `Decoder` は、既定では最初の型の誤りで止まる**（見込み。`accumulating` に当たる機能の有無は未確認）。**根拠にしている `ValidatedNec` と `mapN` は、DTO から値を作った後の段階**であり、DTO の段階で誤りが集まる保証がない。また、画面は `errors[].field` の名前で照合するため、**フィールド名の一致も契約**に含まれる | DTO を、**型の誤りも含めてすべて集められる形**（誤りを集める `Decoder`、または生の JSON から値を取り出して `ValidatedNec` で検証する）にするか、型の誤りは最初の 1 件で 422 とする。**どちらにするかは B1 で決め**、契約テストに「複数の誤りが一度に返る」「フィールド名が仕様と一致する」を入れる |
| 14 | **自動切断（`idle_in_transaction_session_timeout`）の利用者への見え方** | 切断されるのは**取り残されたトランザクション**で、利用者の要求の応答を返すものではない。要求の処理中に接続が切られた場合は、`Persistence`（500・相関 ID。`type` つき）として返る | 画面は失敗として扱い、利用者は再操作できる（COMMIT 前なら ROLLBACK されるため二重にならない）。COMMIT の応答が失われた場合の回復は、同じ `Idempotency-Key` での再送（#11）。[運用要件](./operation.md) の障害パターン 17 |

**画面の変更が必要になる場合の扱い**: 上の逸脱を契約どおりに直せず、画面側の対応が必要になったときは、**設計の矛盾として扱い**、Kotlin 版の UI 設計と合わせて更新する（Scala 版だけ画面を変えない）。

## インタラクション設計

Kotlin 版の次の節を、そのまま引き継ぎます（内容は複製しません）。

- 共通のルール（明示的なボタンで操作を始める、フォーカスと入力だけで状態を変えない）
- **保存直後の表示と投影の遅延**（応答は `versions` だけ。スナップショットを取得して追いついてから表示。同期投影のため遅延は通常ない。反映待ちの共通部品）
- **競合の種類と表示**（`session.decision_conflict`、`session.week_advanced`、`session.decisions_changed`、`app.retry_exhausted`）
- **エラーの `code` と表示の辞書**（正本。鍵は `code`。**Scala 版でも `code` の一覧を変えない**。`DomainError` の `code` と `AppFailure` の写像の全体が OpenAPI の一覧と一致することを契約テストで確認する。辞書が全 `code` を網羅することは、既存のフロントエンドの型検査（`Record<ErrorCode, …>`）で守られる）
- **結果が不明なとき**（`type` のない 5xx・タイムアウト・切断は「結果が不明」として同じキーで再送。`type` つきの 503 は利用者の再操作で新しいキー）
- 主な操作の流れ、エラーと状態のフィードバック、画面の状態

## アクセシビリティ

**WCAG 2.2 AA を目標とし、Kotlin 版（と beer-game2）の内容をそのまま引き継ぎます**（キーボードだけで完了、色だけで状態を表さない、200% 拡大で横スクロールなし、操作対象の大きさ、フォーカスの管理）。検証は、コンポーネントテストと E2E の axe、手動の確認（スクリーンリーダー）です（NFR-08。担当者と時期は [Kotlin 版の未決事項](../beer-game-kotlin/ui-design.md) のとおり）。

### SU1: UI 設計は複製せず、Kotlin 版を正本として参照する（提案）

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| **A（提案）** | Scala 版の UI 設計は差分の文書にとどめ、画面・遷移・画面イメージ・辞書は Kotlin 版を正本として参照する | 食い違いが生まれない。API の契約が同じ間は変更が一度で済む。参照先を読む手間が増える |

### SU2: 契約から外れる実装の逸脱は、画面でなくバックエンドで直す（提案）

画面は API の契約にだけ依存し、実装の違いを知りません。上の影響の表の逸脱は、**バックエンドを契約に合わせて直す**（画面を実装ごとに分岐させない）。画面の変更が避けられないときは、設計の矛盾として扱います。

6. **SSE の API と、遅い購読者の扱い**（#5）。
7. **数値の型の範囲**（#10）: 契約に整数の範囲を書くか。
8. **ポーリングの失敗が黙って無視される**（#12）: Kotlin 版・Rust 版と共通の課題。画面側の対応は、Kotlin 版の UI 設計と合わせて決める。
9. **Kotlin 版の未決事項の引き継ぎ**: 手動のアクセシビリティの確認の担当者と時期、保持の表示（暫定。M5）、自動確定の本人へのフィードバックの文言、参加者のロビーの扱い、ヘルプの教材の本文の人による確認。いずれも [Kotlin 版の未決事項](../beer-game-kotlin/ui-design.md) に追従する。
