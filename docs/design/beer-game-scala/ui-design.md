## Scala 版のバックエンドが UI に与える影響

UI は API の契約にだけ依存します。Scala の実装が**契約から外れる可能性のある箇所**を、UI の側から列挙します。いずれも、契約テスト（[テスト戦略](./test-strategy.md)）と E2E で、契約どおりであることを確認します。

| 13 | **入力の誤りを一度に示す**: S02（ゲーム作成）は、422 の `errors[]` を**項目ごと（`errors[].field`）に**、入力欄の近くへ示す | **circe の `Decoder` は、既定では最初の型の誤りで止まる**（見込み。`accumulating` に当たる機能の有無は未確認）。**根拠にしている `ValidatedNec` と `mapN` は、DTO から値を作った後の段階**であり、DTO の段階で誤りが集まる保証がない。また、画面は `errors[].field` の名前で照合するため、**フィールド名の一致も契約**に含まれる。**画面の実際の扱い**（`CreateGamePage.tsx`）: 項目ごとに示すのは `status === 422` かつ `errors` が 1 件以上のときだけで、**`errors` が 0 件の 422 は項目に紐づかず、一般の失敗として示される**（`validation.invalid_input` の文言は辞書で `null` のため、「処理できませんでした。」と相関 ID）。`field` の名前は、画面が使う `finalWeek`・`demand`・`retentionDays`・`displayName`・`invitationCode` と、**ドット区切りの入れ子の形**（`conditions.disclosurePolicy`）。この形に合わない名前の誤りは、どの欄にも結び付かない | DTO を、**型の誤りも含めてすべて集められる形**（誤りを集める `Decoder`、または生の JSON から値を取り出して `ValidatedNec` で検証する）にするか、型の誤りは最初の 1 件で 422 とする。**どちらにするかは B1 で決め**、契約テストに「複数の誤りが一度に返る」「フィールド名が仕様と一致する」を入れる |
| 14 | **自動切断（`idle_in_transaction_session_timeout`）の利用者への見え方** | 切断されるのは**取り残されたトランザクション**で、利用者の要求の応答を返すものではない。要求の処理中に接続が切られた場合は、`Persistence`（500・相関 ID。`type` つき）として返る | 画面は失敗として扱い、**利用者は再操作すればよい**（COMMIT 前なら ROLLBACK されるため二重にならない。運用の `pg_terminate_backend` による切断も同じ見え方で、[運用要件](./operation.md) のパターン 17 の初動に同じ案内を置いた）。COMMIT の応答が失われた場合の回復は、同じ `Idempotency-Key` での再送（#11）。[運用要件](./operation.md) の障害パターン 17 |

| 15 | **不正な遷移（`Ignored`）で止まったゲームの見え方**（Kotlin 版との利用者に見える違い） | コマンドの経路で `Ignored` が出ると、該当ゲームのコマンドが `Persistence`（500・`code: app.internal`・相関 ID）で失敗し続ける。Kotlin 版は記録して続行するため、操作は止まらない。**止める設計の維持は、ユーザーの決定（2026-11-25）** | 画面は一般の失敗（「サーバーで問題が発生しました。…」と相関 ID）として示し、**再操作しても同じ失敗になる**（`type` つきの 500 は自動再送されない）。進行役が取る行動は、[運用要件](./operation.md) のパターン 18 の依頼文言（「このゲームは一時的に操作できません。運用担当が復旧中です。参加者には手元で数量をメモして待つよう伝えてください」）。**画面にこの状態を知らせる文言は無く、全実装共通の画面の課題**（未決事項 8 と同じ扱い） |

**画面の変更が必要になる場合の扱い**: 上の逸脱を契約どおりに直せず、画面側の対応が必要になったときは、**設計の矛盾として扱い**、Kotlin 版の UI 設計と合わせて更新する（Scala 版だけ画面を変えない）。

## インタラクション設計

Kotlin 版の次の節を、そのまま引き継ぎます（内容は複製しません）。

- 共通のルール（明示的なボタンで操作を始める、フォーカスと入力だけで状態を変えない）
- **保存直後の表示と投影の遅延**（応答は `versions` だけ。スナップショットを取得して追いついてから表示。同期投影のため遅延は通常ない。反映待ちの共通部品）
- **競合の種類と表示**（`session.decision_conflict`、`session.week_advanced`、`session.decisions_changed`、`app.retry_exhausted`）
- **エラーの `code` と表示の辞書**（正本。鍵は `code`。**Scala 版でも `code` の一覧を変えない**。`DomainError` の `code` と `AppFailure` の写像の全体が OpenAPI の一覧と一致することを契約テストで確認する。辞書が全 `code` を網羅することは、既存のフロントエンドの型検査（`Record<ErrorCode, …>`）で守られる）
- **結果が不明なとき**（`type` のない 5xx・タイムアウト・切断は「結果が不明」として同じキーで再送。`type` つきの 503 は利用者の再操作で新しいキー）
- 主な操作の流れ、エラーと状態のフィードバック、画面の状態

## アクセシビリティ

**WCAG 2.2 AA を目標とし、Kotlin 版（と beer-game2）の内容をそのまま引き継ぎます**（キーボードだけで完了、色だけで状態を表さない、200% 拡大で横スクロールなし、操作対象の大きさ、フォーカスの管理）。検証は、コンポーネントテストと E2E の axe、手動の確認（スクリーンリーダー）です（NFR-08。担当者と時期は [Kotlin 版の未決事項](../beer-game-kotlin/ui-design.md) のとおり）。

## 設計判断

**SU1〜SU2 は、AI が起草した案で、ユーザーの承認を得ていません**（Rust 版の RU1・RU2 は承認済みで、Scala 版はそれに倣った提案）。

### SU1: UI 設計は複製せず、Kotlin 版を正本として参照する（提案）

| 案 | 内容 | 評価 |
| :--- | :--- | :--- |
| **A（提案）** | Scala 版の UI 設計は差分の文書にとどめ、画面・遷移・画面イメージ・辞書は Kotlin 版を正本として参照する | 食い違いが生まれない。API の契約が同じ間は変更が一度で済む。参照先を読む手間が増える |
| B | Kotlin 版の UI 設計を Scala 版に複製して持つ | 文書が自己完結する。ワイヤーフレームと辞書が二重になり、片方の更新漏れが起きる |
| C | UI 設計をプロジェクトに属さない共通の文書へ移す | 正本が 1 つになる。ドキュメント構成のガイド（プロジェクト別のカテゴリ）に反する。**構造の変更で確認が要る** |

トレードオフ: A は、Scala 版を単独で読む人が Kotlin 版に移る必要がある。**将来 UI が実装ごとに分かれる場合は、複製（B）に切り替える**（その時点の差分を ADR に記録する）。

### SU2: 契約から外れる実装の逸脱は、画面でなくバックエンドで直す（提案）

画面は API の契約にだけ依存し、実装の違いを知りません。上の影響の表の逸脱は、**バックエンドを契約に合わせて直す**（画面を実装ごとに分岐させない）。画面の変更が避けられないときは、設計の矛盾として扱います。

## 未決事項

1. **SU1・SU2 の承認**。
2. **http4s の既定の応答**（#1・#2）: 経路なし、メソッド違い、本文の解析の失敗、タイムアウトの形と、problem+json への写像の方法（B1 で確認）。
3. **ember の切断時のハンドラの取消と `Supervisor` による切り離し**（#3・#11）: B1 の統合テストで確かめる。
4. **同じ `Idempotency-Key` の再送が、元の処理の実行中に届いたときの待ち方**（#11。バックエンドの未決事項と共通）。
5. **circe による誤りの集約**（#13）: 型の誤りも含めて集められるか。集められない場合の扱い。
6. **SSE の API と、遅い購読者の扱い**（#5）。
7. **数値の型の範囲**（#10）: 契約に整数の範囲を書くか。
8. **ポーリングの失敗が黙って無視される**（#12。S05・S07。S04 は 403 だけ表示）: Kotlin 版・Rust 版と共通の課題。**数回続けて失敗したら、最終更新の時刻と「接続を確認しています」を示す**ことを、全実装共通の画面の課題として優先度を上げ、ストーリー化する案（M16。承認を得ていない）。画面側の対応は、Kotlin 版の UI 設計と合わせて決める。`Ignored` で止まったゲームの知らせ方（#15）も同じ枠で扱う。
8a. **SSE で 2 秒を保つ画面の改善**（#12）: 全実装共通の別の課題として扱う。Scala 版だけでは決めない。
9. **Kotlin 版の未決事項の引き継ぎ**: 手動のアクセシビリティの確認の担当者と時期、保持の表示（暫定。M5）、自動確定の本人へのフィードバックの文言、参加者のロビーの扱い、ヘルプの教材の本文の人による確認。いずれも [Kotlin 版の未決事項](../beer-game-kotlin/ui-design.md) に追従する。
