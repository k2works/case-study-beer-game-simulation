# ロールバック手順書

> **状態: 定義のみ。AWS では実行していない・検証していない。** 設計は [運用要件](../../design/beer-game-kotlin/operation.md) の「変更管理」（ロールバック、ロールバックの制約）と [インフラストラクチャ](../../design/beer-game-kotlin/architecture-infrastructure.md)。デプロイは [デプロイ手順書](./deploy.md)。

> **Bolt 14（本番の定義）**: 本番の api の更新は、ブルー/グリーン（待ち時間 10 分）になった。待ち時間の間は旧版が残り、アラームで自動で戻る。待ち時間の後のロールバックも、戻す版をブルー/グリーンで展開し直す（待ち時間つき）。手順は [本番の運用手順書](./production.md) の 4。データの復元は [復元の手順書](./restore.md)。上のロールバックのワークフローの待ち方（`rolloutState`）は、AWS 上で未確認。

## 何を戻し、何を戻さないか

| 対象 | ロールバックでの扱い |
| :--- | :--- |
| api のイメージ（タスク定義） | **戻す**。直前のダイジェストのタスク定義を、サービスに指定する |
| 静的ファイル（フロントエンド） | **戻す**。S3 の `releases/<SHA>/` を `current/` へ戻し、CloudFront を無効化する |
| データベースのスキーマ（マイグレーション） | **戻さない**。拡張 → 互換の期間 → 縮小の順で、旧アプリと互換にする。旧アプリが動く間は、必須の列・表を消さない |
| イベント（`events`） | **戻さない・書き換えない**。追記専用。形の変更は `schema_version` とアップキャストで扱う |

## 手順

### 自動（デプロイ中の失敗）

デプロイのワークフローは、api の更新またはスモークテストが失敗すると、直前のタスク定義と静的ファイルの版へ自動で戻す。api の更新が健全にならない場合は、ECS のサーキットブレーカーも直前の版へ戻す。

### 手動

1. **戻してよいかを確認する**（下の「2 段階リリース」と「戻せないケース」）。確認できなければ、戻さずに、新しい版を直して前進する。
2. GitHub の Actions で、環境に合わせて `beer-game-kotlin-rollback-staging` または `beer-game-kotlin-rollback-production` を手動で起動する（本番は保護ルールの承認が要る）。
3. 入力:
   - `target_release`（任意）: 戻す先のコミット SHA。省略すると、現在のタスク定義と違う直近の履歴（S3 の `deployments/`）の版。
   - `confirm_compatible`（必須）: 旧イメージが現在のイベントを読めることを確認したときだけ `true`。`false` では中止する。
4. ワークフローが、戻す先を履歴から選び、api のタスク定義と静的ファイルを戻し、スモークテスト（`/api/v1/ready`、`/api/v1/health`）で確認する。
5. 戻した後、原因を調べる。ステージングでは、**ロールバックの手順を毎回確認する**（設計）。

戻す先の候補は、デプロイの成功ごとに記録した履歴だけである。ECR の保持は直近の件数（Terraform の `keep_images`）で、それより古いイメージには戻せない。

## 2 段階リリース（読む版 → 書く版）

新しいイベントの種類や新しい `schema_version` を書き始める変更は、次の 2 段階で行う（NF-O11、N-1 互換）。旧版のアプリが新しい版のイベントを読むと、イベントの読み込みに失敗するため。

| 段階 | 内容 | 旧イメージへ戻せるか |
| :--- | :--- | :--- |
| 1（読む版） | 新しい形を**読める**版を先にリリースする（アップキャストと `evolve`・投影の分岐）。まだ新しい形を書かない | 戻せる（新しいイベントはまだ無い） |
| 2（書く版） | 次のリリースで、新しい形を**書く**設定に上げる。1 リリース以上の間隔を空ける | **新しいイベントが書かれた後は、段階 1 より前の旧イメージへ戻せない** |

書く版を戻す設定の操作で、旧イメージへ戻せる余地を最大にする。リリースの記録に「旧イメージへ戻せる期間（書く版を上げる前まで）」を書く。CI の N-1 互換のジョブ（直前のリリースの読み取り側で、現在の書く版の golden を再生）で、読む側が先行していることを検査する。ただし、このジョブは**雛形で未実装**（直前のリリースのタグが無い間は実行しない）。

書く版を設定でどこに持つか（環境変数か設定サービスか）は、設計の**未決**である。AI の提案（環境変数 `WRITE_SCHEMA_VERSION`。未実装・未承認）は [本番の運用手順書](./production.md) の 8。

## 戻せないケース

次のときは、旧イメージへ戻さない。

- 書く版を上げた後で、新しい `schema_version` のイベントが `events` に既にある。
- 直近のリリースが、旧アプリが読めないイベントの種類を追加し、すでに書かれている。
- 症状が、イベントの読み込み失敗（未知の `event_type`、未知の `schema_version`、デコード失敗）のアラームである。この場合、旧版への巻き戻しは悪化させる。

この場合の復旧は、設計の次のどちらかで、**人が判断する**。

1. **前進する（第一の選択）**: 新しい版を直して、再度デプロイする。旧版の読み取り側を新しい版に対応させる緊急変更もここに含まれる。
2. 書く版を戻し、新しい版のイベントが書かれる前の状態まで DB を復元する。**データを失う**。研修の途中では避ける。復元の手順は [復元の手順書](./restore.md)（B14。訓練は未実施）。
