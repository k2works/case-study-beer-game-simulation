# 復元の手順書

> **状態: 定義のみ。復元の訓練は一度も実施していない（AWS が無い）。** 設計は [運用要件](../../design/beer-game-kotlin/operation.md) の「バックアップ設計」「復元の手順」、[データモデル](../../design/beer-game-kotlin/data-model.md)。手順は、スクリプト `apps/beer-game-kotlin/scripts/restore-pitr.sh`（既定はドライラン）で、テスト可能な形にした（ドライランの出力を `ProductionDefinitionSpec` が検査する）。

## バックアップの定義

| 項目 | 定義 |
| :--- | :--- |
| 自動バックアップ | RDS の自動バックアップ 7 日（時点復旧）。時間帯は UTC 17:00〜17:30（日本時間 02:00。研修のない時間。日次の整合の検査の前） |
| Multi-AZ | 本番は同期スタンバイ（RPO 0 の根拠） |
| 暗号化 | 保存時に暗号化（`storage_encrypted`。**顧客管理の KMS 鍵は未定義**） |
| 削除保護 | 本番は有効。削除するときは最終スナップショットを取る |
| デプロイ前のスナップショット | 本番のデプロイの前に手動で 1 つ（`<RDS>-pre-<SHA 8 桁>`）。**手動のスナップショットは自動で消えない**ので、デプロイのワークフローが 7 日より古いものを消す |
| 削除後のバックアップ | 保持期間後にゲームを削除しても、**自動バックアップには最大 7 日、削除前のデータが残る**（NF-S16。画面にも表示）。手動のスナップショットも 7 日までにそろえる（上） |

## RPO・RTO の机上確認

目標は、RPO 0（確定済みの週）・RTO 15 分（NF-R3・NF-R4）。**以下は、定義と設計からの机上の確認で、実測ではない**。

| # | 障害 | 手段 | RPO | RTO の内訳（机上） | 15 分に収まるか |
| :-: | :--- | :--- | :--- | :--- | :--- |
| 1 | api のタスクの停止 | ECS が置き換える（常時 2 タスク以上） | 0（追記のコミットの後にだけ応答する） | 検知（`/ready` 失敗。約 1 分）＋タスクの起動時間（目標: 警告 60 秒・重大 120 秒。ローカルのコンテナで 3.6〜6.0 秒。Fargate のイメージ取得は未実測）。残りのタスクが受ける間、利用者への影響は小さい | 収まる見込み（未実測） |
| 2 | DB のインスタンス・AZ の障害 | Multi-AZ のフェイルオーバー | **0**（同期スタンバイ） | 検知（約 1 分）＋フェイルオーバー（AWS の説明では通常 60〜120 秒。未実測）＋接続プールの再接続（**アプリの再接続は未確認**） | 収まる見込み。**再接続の確認が要る** |
| 3 | 投影だけの障害 | `rebuild-projections`（B 手順） | 0（`events` は無事） | 検知（日次の検査または利用者の連絡）＋停止の依頼・再開の連絡（人の時間が大半）＋再構築（1 ゲーム p95 1 秒。NF-P18）。**検知が日次の場合、検知の時間が支配的**（1 日） | 再構築の実行は収まる。**検知の遅れは別**（連絡窓口が未決） |
| 4 | `events` の破損・誤操作 | PITR または手動のスナップショットから新しいインスタンスへ復元（A 手順） | **0 にならない**。時点復旧の復元可能な最新時刻は、現在より数分遅れる（AWS の説明では通常 5 分程度）。**その数分の確定済みの週は失われうる**。設計の「RPO 0」の根拠は同期スタンバイ（2）であり、PITR ではない | 新しいインスタンスの作成（容量とクラスに依存。**数分〜数十分。未実測**）＋切り替え（名前の付け替えは再起動を伴う）＋`retention`・`verify-projections` の実行＋運営者への連絡 | **収まる保証がない**。訓練で実測する |

机上確認の結論（人が判断する）:

1. **RPO 0 は、1・2 では成り立つ。4（PITR）では成り立たない。** 設計書の「確定済みの週は RPO 0」は、障害の種類を限る必要がある（インスタンス・AZ の障害は 0、破損の復元は復元時点まで）。復元の時点より後の確定済みの週は、`events` が壊れているなら元に戻せない（壊れる前の時点を選ぶので、その後の操作は、利用者が入力し直す）。
2. **RTO 15 分は、4 で収まる保証がない。** 設計書は「パターン 4 が 15 分に収まるかも訓練で確かめる」としている。収まらなければ、パターン 4 だけ別の値にするか（設計書は「投影だけの障害にも別の値は置かない」としている）、復元の手順を短くするか（スタンバイ用のリードレプリカ・スナップショットの共有など。費用が要る）を、人が決める。
3. 3 の検知の遅れ（日次）が、RTO の実質を決める。研修中の不一致は、利用者の連絡で気づく可能性が高い。

## A. データベース全体の復元

**研修中は、運営者を通じて進行役へ連絡する（停止の依頼）。** 復元の時点より後の、利用者が行った操作は失われる。

1. **対象を決める**: 復元の時点（直前の確定週など）、またはスナップショット（直近のデプロイ前の `-pre-` など）。
2. **新しいインスタンスへ復元する**（元は残す）。ドライランで、実行するコマンドを確かめる:

   ```bash
   cd apps/beer-game-kotlin
   scripts/restore-pitr.sh --instance <元のインスタンス> --new-instance <復元先の名前> --target-time <UTC の時刻>   # または --latest、--snapshot <ID>
   scripts/restore-pitr.sh ... --execute    # 実行する（復元と完了待ちだけ。所要時間が出る。RTO の実測に記録する）
   ```

   スクリプトは、元のインスタンスのサブネットグループ・セキュリティグループ・パラメータグループ・クラスを読み、同じ設定で復元する。**切り替え以降は、人が行う**（スクリプトは手順を表示するだけ）。
3. **切り替える**: api の台数を 0 にして書き込みを止める → 定期の起動を止める（`scheduled_tasks_enabled = false`）→ インスタンスの名前を付け替える（元を `-old` へ、復元先を元の名前へ。エンドポイントは名前に従うので、アプリの接続先は変わらない）→ api の台数を戻す。**付け替えると、Terraform の状態とずれる**（`terraform import` か状態の整理が後で要る）。
4. **復元後の確認（必須。この順で）**:
   1. **保持削除を 1 回実行する**: `retention` のタスクを `run-task`。**復元で、削除済みのゲームが再び現れないようにするため**（削除済みのゲームは、復元の時点より前の状態に戻っている）。
   2. **整合性の検査**: ストリームの版の連続性、`projection_checkpoints` と `MAX(stream_version)` の一致（アプリの検査）。
   3. **投影の整合の検査**: `verify-projections` のタスクを `run-task`。不一致なら B の再構築。
   4. 合成監視と `/api/v1/ready` で、作成・参加・SSE が通ることを確認する。
5. 進行中だったゲームを確認し、運営者へ連絡する。元の `-old` は、確認が済むまで残す（削除は人の判断。**削除後も、元のインスタンスの自動バックアップは削除保護のあるとき残る**。7 日の扱いに注意）。

## B. 投影の再構築（`events` は正常で、投影だけが不整合）

1. 対象を決める（1 ゲーム、または全ゲーム）。研修のない時間なら、2 を省く。
2. **研修中のゲームの停止の依頼**: 運営者を通じて進行役に「停止」を依頼し、ゲームが「停止中」になったことを確認する。依頼の文言は、設計書の障害パターン 13。
3. `rebuild-projections <ゲーム ID>` を `run-task` で実行する（[本番の運用手順書](./production.md) の 5）。排他のアドバイザリロックで、停止中の追記を伴う操作（代理入力、資格の再発行、観察者の参加）と直列になる。
4. 結果を、`verify-projections` で確認する。
5. 進行役に「再開」を依頼する。差が残るときは、投影の純粋関数のバグとして、再構築を繰り返さず、緊急変更で直す。

**再構築で復元されないもの**: 周辺ストア（`display_profiles`＝表示名、`credentials`＝資格、`browser_sessions`、`idempotency_records`、`participation_attempts`）と、削除の受領記録（`deletion_receipts`）・削除の進行（`deletion_runs`・`deletion_attempts`）は、`events` から作り直せない。再構築は、`events` を読むだけで、投影と `projection_checkpoints` だけを書く。これらが壊れたときは、A の復元（時点より前の状態へ戻る）を使う。

## 訓練の記録の様式

四半期に 1 度、およびリリース前、バックアップ方針の変更時に、A と B の訓練を行い、次を記録する（**未実施。記録は空**）。

| 項目 | 記録する内容 |
| :--- | :--- |
| 日時・担当・環境 | ステージング（本番の構成と同じ Multi-AZ・クラスで行う） |
| 障害の模擬 | どの障害（上の 1〜4）を、どう起こしたか |
| 検知までの時間 | 障害の発生からアラームまで |
| RPO の実測 | 復元で失われた確定済みの週の数（0 であること。4 は復元時点による） |
| RTO の実測 | 障害の検知から、最後の確定済みの週から再開できるまで（15 分以内か）。復元の完了までの秒数（スクリプトが出す）、切り替え、`retention`、`verify-projections`、連絡の各区間 |
| 復元後の確認 | 削除済みのゲームが残っていないこと、投影の不一致が 0 であること |
| 見つかった問題と対処 | 手順・スクリプト・定義への反映 |
