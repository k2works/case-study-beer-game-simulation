# 復元の手順書

> **状態: 定義のみ。復元の訓練は一度も実施していない（AWS に適用していない）。** 手順は、スクリプト `apps/beer-game-rust/scripts/restore-pitr.sh`（既定はドライラン）で、テスト可能な形にした（ドライランの出力を `app/tests/production_definition.rs` が検査する）。

## RPO・RTO の約束の範囲（2026-11-23 にユーザーが承認した区別）

| 障害の種類 | 手段 | RPO | RTO |
| :--- | :--- | :--- | :--- |
| api のタスクの停止 | ECS が置き換える（本番は常時 2 タスク以上） | **RPO 0**（追記のコミットの後にだけ応答する） | **RTO 15 分**（検知約 1 分 + タスクの起動。**起動時間は AWS で未実測**） |
| DB のインスタンス・AZ の障害 | **Multi-AZ のフェイルオーバー**（同期スタンバイ） | **RPO 0**（確定済みの週） | **RTO 15 分**（検知約 1 分 + フェイルオーバー。AWS の説明では通常 60〜120 秒。**アプリの再接続は未確認**） |
| 投影だけの障害 | `rebuild-projections`（B 手順） | 0（`events` は無事） | 再構築の実行は収まる。**検知が日次なら、検知の遅れが支配的**（NF-P18 の目標超過の見込みは別。B13 報告） |
| `events` の破損・誤操作 | **PITR**（時点復旧）またはスナップショットから、新しいインスタンスへ復元（A 手順） | **RPO は数分**（復元できる最新時刻は、現在より数分遅れる。その数分の確定済みの週は失われうる）。**RPO 0 は約束しない** | **約束しない。実測してから決める**（新しいインスタンスの作成は、数分〜数十分で、AWS で未実測） |

要点: **RPO 0 と RTO 15 分は、Multi-AZ のフェイルオーバー（とタスクの置き換え）に対する約束**。PITR は破損・誤操作向けの手順で、RPO は数分、RTO は訓練で実測する。設計書（`non-functional.md`）の「RPO 0・RTO 15 分」は、障害の種類を限って読む（**設計書の改訂は未実施**。人が確認する）。

## バックアップの定義

| 項目 | 定義 |
| :--- | :--- |
| 自動バックアップ | RDS の自動バックアップ 7 日（時点復旧） |
| Multi-AZ | 本番は同期スタンバイ（RPO 0 の根拠） |
| 暗号化 | 保存時に暗号化。**顧客管理の KMS 鍵は未定義**（人の判断が要る） |
| 削除保護 | 本番は有効 |
| デプロイ前のスナップショット | 本番のデプロイの前に手動で 1 つ（`<RDS>-pre-<SHA 8 桁>`）。手動のスナップショットは自動で消えないので、デプロイのワークフローが 7 日より古いものを消す |
| 削除後のバックアップ | 保持期間後にゲームを削除しても、**自動バックアップには最大 7 日、削除前のデータが残る**（NF-S16）。手動のスナップショットも 7 日までにそろえる |

## A. データベース全体の復元

**研修中は、運営者を通じて進行役へ連絡する（停止の依頼）。** 復元の時点より後の、利用者が行った操作は失われる。

1. **対象を決める**: 復元の時点（破損の前）、またはスナップショット（直近のデプロイ前の `-pre-` など）。
2. **新しいインスタンスへ復元する**（元は残す）。ドライランで、実行するコマンドを確かめる:

   ```bash
   cd apps/beer-game-rust
   scripts/restore-pitr.sh --instance <元のインスタンス> --new-instance <復元先の名前> --target-time <UTC の時刻>   # または --latest、--snapshot <ID>
   scripts/restore-pitr.sh ... --execute    # 実行する（復元と完了待ちだけ。所要時間が出る。RTO の実測に記録する）
   ```

   **切り替え以降は、人が行う**（スクリプトは手順を表示するだけ）。
3. **切り替える**: api の台数を 0 にして書き込みを止める → 定期の起動を止める（`scheduled_tasks_enabled = false`）→ インスタンスの名前を付け替える（元を `-old` へ、復元先を元の名前へ）→ api の台数を戻す。**付け替えると、Terraform の状態とずれる**（`terraform import` か状態の整理が後で要る）。
4. **復元後の確認（必須。この順で）**:
   1. **保持削除を 1 回実行する**: `retention` のタスクを `run-task`。**復元で、削除済みのゲームが再び現れないようにするため**。
   2. **投影の整合の検査**: `verify-projections` のタスクを `run-task`。**復元前に作られたゲームは、進んだ版の記録（`projection_checkpoints`）が無いことがあり、「記録なし」が報告される**（B13 の変更より前のゲーム）。不一致・記録なしは、B の再構築で直る。
   3. `/api/v1/ready` と合成監視で、作成・参加が通ることを確認する。
5. 進行中だったゲームを確認し、運営者へ連絡する。元の `-old` は、確認が済むまで残す（削除は人の判断）。

## B. 投影の再構築（`events` は正常で、投影だけが不整合）

1. 対象を決める（1 ゲーム、または全ゲーム）。
2. **研修中のゲームの停止の依頼**: 運営者を通じて進行役に「停止」を依頼し、ゲームが「停止中」になったことを確認する。
3. `rebuild-projections <ゲーム ID>` を `run-task` で実行する（[本番の運用手順書](./production.md)）。**ゲームごとの排他ロックを取り、コマンドは `lock_timeout`（2 秒）の後に 503 になる**。
4. 結果を、`verify-projections` で確認する。
5. 進行役に「再開」を依頼する。差が残るときは、投影の純粋関数のバグとして、再構築を繰り返さず、緊急変更で直す。

**再構築では復元されないもの**: 周辺ストア（`display_profiles`＝表示名、`credentials`＝資格、`browser_sessions`、`idempotency_records`、`participation_attempts`）と、削除の受領記録・削除の進行は、`events` から作り直せない。再構築は、`events` を読むだけで、投影と `projection_checkpoints` だけを書く。これらが壊れたときは、A の復元（時点より前の状態へ戻る）を使う。

## 訓練の記録の様式

四半期に 1 度、およびリリース前、バックアップ方針の変更時に、A と B の訓練を行い、次を記録する（**未実施。記録は空**）。

| 項目 | 記録する内容 |
| :--- | :--- |
| 日時・担当・環境 | ステージング（本番の構成と同じ Multi-AZ・クラスで行う） |
| 障害の模擬 | どの障害（上の表）を、どう起こしたか |
| 検知までの時間 | 障害の発生からアラームまで |
| RPO の実測 | 復元で失われた確定済みの週の数（Multi-AZ は 0。PITR は復元時点による） |
| RTO の実測 | 検知から、最後の確定済みの週から再開できるまで。復元の完了までの秒数（スクリプトが出す）、切り替え、`retention`、`verify-projections`、連絡の各区間 |
| 復元後の確認 | 削除済みのゲームが残っていないこと、投影の不一致が 0 であること |
| 見つかった問題と対処 | 手順・スクリプト・定義への反映 |
