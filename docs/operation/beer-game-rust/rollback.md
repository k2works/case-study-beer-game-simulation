# 戻しの手順書

> **状態: 定義のみ。AWS で一度も実行していない。**

## 戻し方

- ステージング: `beer-game-rust-rollback-staging`（手動）。本番: `beer-game-rust-rollback-production`（手動。環境の保護ルールで承認）。
- 既定は直前の版。デプロイのたびに、履歴（`deployments/<時刻>-<SHA>.json`）が静的ファイルのバケットへ残る。指定するときは、その SHA を渡す。
- 戻すもの: api のタスク定義（と、4 つのタスク定義のイメージ）、静的ファイルの版。本番はブルー/グリーンで、戻す更新も、旧版を別の対象グループで起動し、健全を確かめてから切り替える。
- **自動の戻し**: デプロイの途中で失敗したときは、ワークフローが直前の版へ戻す。ブルー/グリーンの待ち時間（10 分）の間に、デプロイのアラームが鳴れば、ECS が旧版へ戻す。**いずれも AWS 上で未確認**。

## マイグレーションは戻さない

スキーマの変更は、**拡張 → 互換 → 縮小**の順で、旧版のアプリと互換にする（戻しで、旧版のアプリが新しいスキーマ・イベントで動けるように）。そのため、**マイグレーションは戻さない**。

- イベントは書き換えない。形の変更は、`schema_version` とアップキャストで吸収する。
- **読める版を先に展開し、書く版は次のリリースで切り替える**（2 段階）。旧版が新しい版のイベントを読めないと、戻しが効かない。リリース前に `scripts/n1-compat.sh` で確かめる（[デプロイ](./deploy.md)）。
- 縮小（列・表の削除）は、旧版が使わなくなってから、別のリリースで行う。

## 戻した後

1. `/api/v1/ready` と合成監視で、通ることを確認する。
2. 戻した原因を調べる（実行自体は失敗のまま）。
3. データの破損が疑われるなら、[復元](./restore.md)（PITR の RPO は数分、RTO は未実測）。
