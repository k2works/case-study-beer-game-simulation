# リリース前の確認票

beer-game3 のリリースの前に、自動の試験では確かめられない範囲を、人が確かめて記録します。最新の世代の Chromium、Firefox、WebKit、Edge は、CI の画面の試験（`e2e` ジョブ）が主要な操作を毎回確かめます。この確認票が受け持つのは、次の 2 つです。

- 1 つ前の世代の Chromium、Firefox、WebKit、Edge
- 実機の Safari（WebKit の代わりの自動の試験では、実機の違いを確かめられない）

要件の出どころは、NFR10.2 と NFR9.4（`performance-requirements.md`、`observability-design.md`）です。**記録がない世代は、「確かめた」と扱いません。**

## 確かめる項目

自動の試験の主要な操作（NFR10.1）と同じ 6 項目を、ブラウザごとに確かめます。

| 番号 | 項目 | 確かめること |
| :--- | :--- | :--- |
| 1 | ゲームの作成 | 設定を入れて作成でき、参加コードと進行役用コードが表示される |
| 2 | 参加 | 4 人が、参加コードと表示名で参加し、ロビーに入れる |
| 3 | 役割の割当て | 進行役が、4 人に役割を割り当てられる |
| 4 | 開始 | 4 役割がそろうと開始でき、各画面に第 1 週が表示される |
| 5 | 入力 | 各役割が発注数を入力して保存でき、「入力: 保存済み」と表示される |
| 6 | 週の確定 | 進行役が週を確定でき、すべての画面に次の週が表示される |

## 確認の手順

1. 確かめるブラウザの、1 つ前の世代を用意する（各ブラウザの配布元から入手する。実機の Safari は、手元の端末の Safari を使う）。
2. `staging`（または、確認用に起動した beer-game3）で、上の 6 項目を順に行う。進行役 1 人と参加者 4 人は、別のブラウザの文脈（別のウィンドウまたは別の端末）で入る。
3. 下の「記録」の、そのリリースの節に、ブラウザごとに 1 行を足す。所見には、動かなかった項目の番号と症状を書く。

## 記録

リリースのたびに、新しい節を足します。確認ごとに 1 行です。合否は「合格」または「不合格」と書きます。不合格のブラウザがあるまま、リリースしません。

## リリースの条件

リリースの手順書（`developing-release`）の条件として、次の 3 つを確かめます。

| 条件 | 確かめ方 |
| :--- | :--- |
| リリース用のプルリクエスト（`develop` から `main`）の `load-main`（10 分間の本試験）が成功している | プルリクエストの `gate` と、成果物 `verify-summary-main`（30 日保存）の `verdict` が `pass` |
| 夜間の定期実行が有効である | `gh workflow list` で `beer-game3` が有効。公開リポジトリは、60 日間活動がないと GitHub が定期実行を自動で無効にするため、無効なら有効にし直して、手動実行で動くことを確かめる |
| この確認票に、そのリリースの節の記録がある | 上の「記録」の表に、5 行（4 ブラウザと Safari）の合否がすべて埋まっている |

本試験の合否は、手元の実行（`npm run verify:load:main`）を証拠にしません。実行環境の記録、成果物の保存、コミットの固定がないためです。
