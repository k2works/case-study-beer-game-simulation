## 学び

- 人の目の照合は、機械の照合の代わりにならない。B1 で「手で照合した」仕様に、7 件の不一致があった。
- ゲートの数値は、測って設定する。届かないときは、閾値を黙って下げず、事実と選択肢を記録して人に渡す。
- 層単位のルールの緩和は粗い。外したルールの新規違反は、その層で検出されなくなるため、ADR に残し、承認を求める。
- 連鎖削除と最小権限は、PostgreSQL の所有者権限の仕組みで両立した。設計の不安は、先に実測すると消える。
- Flyway は、適用済みの最大の版より小さい未適用の版を拒否する。マイグレーションの番号の付け方は、環境を作る前に決める。
- エージェントが規律に反するファイルの書き方を繰り返し試みる。分類器の拒否に頼らず、指示や検査で見つける仕組みが要る。
- 前の Bolt の申し送りは、計画に項目として取り込むか、範囲外と明記する。取り込まないと、黙って落ちる。
- （Bolt 3）「ローカルで通った」と「CI で通る」「AWS で動く」は別の事実。定義だけの Bolt は、確認の範囲（ローカル、CI、AWS）を、達成の記述に必ず書く。
- （Bolt 3）`terraform validate` は構文と参照の整合までで、データソースの解決や版の受理は確認できない。`plan` が通るまで「適用できる」とは言えない。
- （Bolt 3）設計の「想定」は、イメージを作った時点で実測して直す（SIGTERM の終了コード 143、実行イメージに `curl` が無い）。防御を重ねるときは、それぞれが独立に失敗することを別々の検査項目にする（H2 の 78 と 70）。
- （Unit U1）人のゲートを通さずに進めると、決めるべき仮置きが積み上がり、AI の出力の質を測る実測も取れない。次の Bolt では、ステップごとに人のゲートで仮置きを決める。
