# ユーザーストーリー - ビールゲームシミュレーション

## 概要

本書は、[システムユースケース](./system_usecase.md) から導出した、開発可能な粒度の**ユーザーストーリーと受入条件**を定義します。ストーリーと受入条件は、人と AI の間の契約です。リリース計画・イテレーション計画は `docs/development/beer-game/` で別に扱います。

## Epic 1: ゲーム準備と参加

### US1.1 ゲームを作成する

**として** 進行役、**したい** JSD 準拠またはカスタム条件でゲームを作成したい、**なぜなら** 同一条件の学習セッションを再現できるからだ。

- **優先度**: Must
- **依存**: なし
- **ユースケース**: UC-01（要件: FR-01、BR-13、BR-14、SR-05）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC1.1.1 | 有効なキット準拠設定で作成すると、参加コード付きの準備中ゲームが一度だけ作成される | ✓ |
| AC1.1.2 | 無効な需要系列を保存しようとすると、作成せず、対象週と修正内容を表示する | △ |
| AC1.1.3 | 準拠値を変更した設定で作成すると、「カスタム」と明示する | △ |

**備考**:

- AC1.1.2: 作成は拒否され、「最終週までの 0〜1000 の整数が必要」と示すが、**対象の週は示さない**。
- AC1.1.3: 画面に「キット準拠 / カスタム条件」の選択はあるが、**ゲームに保存されず**（BR-14）、変更できるのは最終週と需要系列だけ（初期在庫・遅延・費用単価・公開範囲は固定。FR-01）。

**INVEST**: 単独でデモ可能。条件入力は交渉可能。検証可能。

### US1.2 参加して役割を受け取る

**として** 生産役または流通役、**したい** 参加コードでロビーに入り、役割を受け取りたい、**なぜなら** アカウント登録なしで学習を始められるからだ。

- **優先度**: Must
- **依存**: US1.1
- **ユースケース**: UC-02、UC-03、UC-04（要件: FR-02、FR-03）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC1.2.1 | 有効な参加コードで表示名を入力すると、ロビーに参加し、復帰資格が保存される | ✓ |
| AC1.2.2 | 無効または終了済みのコードで参加しようとすると、参加せず、理由を表示する | △ |
| AC1.2.3 | 4 役割が揃っていない状態で進行役が開始すると、開始を拒否し、不足している役割を示す | ✓ |

**備考**:

- AC1.2.2: 拒否は実装済み（準備中でないゲームは参加できない）。拒否理由の画面表示の内容は要確認。
- AC1.2.3: 画面では、4 役割が揃うまで開始を無効にしている。API は不足する役割を返す。
- 同一役割の複数人担当（ASM-04）は未実装（二人目は拒否される）。

**INVEST**: 参加と割当ての価値を一貫して提供する。

## Epic 2: ウォーキングスケルトン（1 週の意思決定）

### US2.1 役割別の週次状況を確認する

**として** 生産役または流通役、**したい** 自分の役割に許された週次状況だけを見たい、**なぜなら** 情報制約を保って意思決定できるからだ。

- **優先度**: Must
- **依存**: US1.2
- **ユースケース**: UC-05（要件: FR-04、FR-05）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC2.1.1 | プレイ中に自分の役割の画面を開くと、自役割の在庫・受注残・入荷・受注だけを表示する | ✓ |
| AC2.1.2 | 他の役割のリソース ID を UI または API で取得しようとすると、権限エラーとして、値を返さない | ✓ |
| AC2.1.3 | 小売店以外の役割が、将来の需要または当週の需要を取得しようとすると、開示しない | ✓ |

**INVEST**: 読み取り範囲に限定した独立ストーリー。

### US2.2 発注または生産要請を決定する

**として** 生産役または流通役、**したい** 当週の数量を入力・確定したい、**なぜなら** 分散した意思決定でサプライチェーンを運営できるからだ。

- **優先度**: Must
- **依存**: US2.1
- **ユースケース**: UC-06、UC-07（要件: FR-07、BR-10）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC2.2.1 | 未確定の当週に非負整数を入力すると、流通役は発注、生産役は生産要請として保存できる | ✓ |
| AC2.2.2 | 負数・小数・空白を確定しようとすると、入力を保持し、修正方法を示す | ✓ |
| AC2.2.3 | 同一役割の複数参加者が同時に更新すると、更新の競合を示し、変更を黙って失わない | △ |

**備考**:

- AC2.2.3: 版の不一致による競合の検出は実装済み（別のタブからの同時更新など）。同一役割に複数人が参加する構成は未実装（US1.2 の備考）。

**INVEST**: 意思決定の操作に限定。

### US2.3 1 週を原子的に確定する

**として** 進行役、**したい** 4 役割の入力後に、1 週を一度だけ確定したい、**なぜなら** 手作業のミスなしに、正しい状態を残せるからだ。

- **優先度**: Must
- **依存**: US2.2
- **ユースケース**: UC-08（要件: FR-05、FR-06、FR-08〜FR-10、BR-02〜BR-09、BR-12）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC2.3.1 | 4 役割の入力が完了して週を確定すると、12 ステップ順の遅延・入荷・出荷・在庫・受注残・費用が、一度の取引で保存される | ✓ |
| AC2.3.2 | 同じ確定要求が重複または同時に届くと、結果と費用は一度だけ計上される | ✓ |
| AC2.3.3 | 確定中に障害で処理が中断すると、部分更新を残さず、再試行できる | ✓ |
| AC2.3.4 | 同一の初期状態と意思決定から再計算すると、全状態と費用が一致する | ✓ |

**INVEST**: ウォーキングスケルトンの核心の価値。

## Epic 3: 継続と復旧

### US3.1 停止・代理入力・再開を管理する

**として** 進行役、**したい** セッションを停止し、必要な代理入力のあとに再開したい、**なぜなら** 不在者や一時的な中断があっても、学習を継続できるからだ。

- **優先度**: Must
- **依存**: US2.3
- **ユースケース**: UC-09、UC-10（要件: FR-11、FR-15、NFR-09）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC3.1.1 | 一時停止中に参加者が新規の確定をすると、拒否し、既存の入力を失わない | ✓ |
| AC3.1.2 | 進行役が代理入力して確定すると、操作者・役割・時刻・値を監査履歴に残す | △ |
| AC3.1.3 | 再開すると、最後の確定済みの週から入力できる | ✓ |

**備考**:

- AC3.1.2: イベントに操作者と役割と時刻は残るが、**入力値は残らない**。専用の監査テーブル（`operation_audit`）は定義だけで使われていない。

**INVEST**: 運営の継続性に限定。

### US3.2 切断後に同じ役割へ復帰する

**として** 生産役または流通役、**したい** 一時切断のあとに、元の役割へ戻りたい、**なぜなら** 確定済みのデータと作業を失わずに継続できるからだ。

- **優先度**: Must
- **依存**: US1.2
- **ユースケース**: UC-14（要件: ASM-05、NFR-05）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC3.2.1 | 有効な復帰資格で再接続すると、同じゲームと役割の最新の状態を表示する | ✓ |
| AC3.2.2 | 無効または削除済みの資格で再接続すると、復帰せず、進行役への確認方法を示す | ✓ |
| AC3.2.3 | 複数のタブで一方が週を確定すると、他方は古い応答を適用せず、最新の状態を反映する | ✓ |

**備考**: 進行役が画面を再読み込みした場合にコンソールへ戻る手段は、現状の画面に無い（[フロントエンドアーキテクチャ](../../design/beer-game/architecture-frontend.md) の差分 #1）。

**INVEST**: 復帰の経路だけを縦に貫くストーリー。

## Epic 4: 観察と振り返り

### US4.1 公開範囲内でプレイを観察する

**として** 観察者、**したい** 進行状況とチーム合計を見たい、**なぜなら** 役割別の非公開情報を壊さずに、学習を観察できるからだ。

- **優先度**: Should
- **依存**: US2.3
- **ユースケース**: UC-13（要件: FR-04、SR-07）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC4.1.1 | プレイ中に観察画面を開くと、現在週・ステップ・完了状況・在庫・受注残・注文のチーム合計を表示する | △ |
| AC4.1.2 | 観察者が役割別の値や未来の需要を取得しようとすると、権限エラーとして、値を返さない | ✓ |
| AC4.1.3 | 集計の対象が 1 役割だけで、逆算により個別の値が漏れる状態では、合計を非表示にする | ✓ |

**備考**:

- AC4.1.1: 現在週・完了状況・合計は表示される（ステップは要確認）。
- **観察者という独立した立場が無い**。観察画面を開けるのは、そのゲームの進行役か参加者に限られ、観察者が入る手段が無い。

**INVEST**: 読み取り専用で独立。

### US4.2 終了後に Bullwhip Effect を振り返る

**として** 進行役または観察者、**したい** 需要と全役割の時系列を比較したい、**なぜなら** 遅延と意思決定が変動を増幅する過程を説明できるからだ。

- **優先度**: Must
- **依存**: US2.3
- **ユースケース**: UC-11（要件: FR-13、SR-03、SR-06）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC4.2.1 | ゲーム終了後に分析画面を開くと、需要・注文・在庫・受注残・出荷・費用を、同じ週の軸で比較できる | △ |
| AC4.2.2 | プレイ中に、終了後専用の役割別の値を取得しようとすると、開示しない | ✓ |
| AC4.2.3 | データが 0 件の状態で分析画面を開くと、「データなし」と読み込みの失敗を区別する | ✓ |

**備考**:

- AC4.2.1: 同じ週の軸での比較はできるが、**全役割の合計だけ**で、役割別の推移を比べられない。イベントが役割別の値を含まないため。ブルウィップ効果の説明には、役割別の注文の推移が必要で、**このストーリーの主目的を満たしていない**。

**INVEST**: 学習の成果を完結させるストーリー。

### US4.3 結果を CSV / JSON で出力する

**として** 進行役、**したい** 全記録を CSV と JSON で出力したい、**なぜなら** 表計算での比較と、システム間の再利用ができるからだ。

- **優先度**: Should
- **依存**: US4.2
- **ユースケース**: UC-12（要件: FR-14、RP-01）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC4.3.1 | 終了済みのゲームで CSV と JSON を出力すると、設定・全週・全役割・意思決定・費用・履歴を識別できる | ✗ |
| AC4.3.2 | 同じゲームで両形式を比較すると、数量と費用が一致し、スキーマ版が記録される | ✓ |
| AC4.3.3 | 出力の一部が失敗して処理を完了できないと、部分的な結果を完全な出力として示さない | ✓ |

**備考**:

- AC4.3.1: 出力は週次のチーム合計（週・在庫・受注残・注文・需要・出荷・費用）だけで、設定、役割別の値、意思決定、履歴を含まない。

**INVEST**: 分析 UI と独立してテストできる。

## Epic 5: 保持と品質

### US5.1 保持期限後にデータを削除する

**として** 進行役、**したい** ゲーム記録の保持期間を設定したい、**なぜなら** 不要な参加者のデータを残さないためだ。

- **優先度**: Must
- **依存**: US1.1
- **ユースケース**: UC-15（要件: NFR-07）

**受入条件**:

| ID | Given / When / Then | 状況 |
| :--- | :--- | :---: |
| AC5.1.1 | 未設定でゲームを作成すると、保持期間を 90 日とする | ✓ |
| AC5.1.2 | 保持期限に達して削除処理すると、ゲーム記録・履歴・復帰資格を削除し、実行結果を記録する | △ |
| AC5.1.3 | 削除中に障害が起きて再試行すると、半分の状態を完了と扱わず、最終的に一度だけ削除される | ✓ |

**備考**:

- AC5.1.2: ゲーム記録と復帰資格は削除されるが、**イベント履歴（`outbox_events`）と冪等記録（`idempotency_records`）が削除対象に含まれない**（[ADR-008](../../adr/beer-game/008-retention-saga.md)）。

**INVEST**: 保持の運用として独立。

## 実装との差分のまとめ

受入条件の不足（△・✗）のうち、学習の目的に直結するものを優先度の高い順に示します。

| # | 不足 | 関連 | 提案 |
| :--- | :--- | :--- | :--- |
| 1 | 振り返りと出力が、役割別でなく全役割の合計だけ | US4.2 AC4.2.1、US4.3 AC4.3.1 | 週確定のイベントに役割別の値を含め、投影と出力を役割別に拡張する（最優先） |
| 2 | 観察者という独立した立場が無い | US4.1 | 観察者の参加方法（参加コードに別の立場を設ける等）を決める |
| 3 | 保持期間後の削除に漏れ | US5.1 AC5.1.2 | ADR-008 のとおり、削除対象を見直す |
| 4 | 代理入力の履歴に値が残らない | US3.1 AC3.1.2 | 監査履歴に入力値を加える（資格は含めない） |
| 5 | 「カスタム」を保存せず、初期値・費用を変更できない | US1.1 AC1.1.3 | BR-14 と FR-01 を要件として残すか判断する |
| 6 | 同一役割の共同担当が無い | US1.2、US2.2 | ASM-04 を要件として残すか判断する |
| 7 | 作成時のエラーに対象の週を示さない | US1.1 AC1.1.2 | 画面のメッセージを改善する |
