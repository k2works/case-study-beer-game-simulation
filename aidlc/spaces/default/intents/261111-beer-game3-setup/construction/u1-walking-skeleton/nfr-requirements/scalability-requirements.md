# 拡張性の要件 - U1 u1-walking-skeleton

U1（薄い一通り）の同時利用と規模の要件です。元の要件は `requirements.md` の NFR4 です。1 ゲームは小さく（50 週、4 役割）、競合するのは同じゲームの中だけです。

出典: `requirements.md`（NFR3、NFR4）、`rules.md`（BR4.6）、`entities.md`、`components.md` の ADR-003、`performance-requirements.md`（負荷の前提）。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR4.1 | 少なくとも 15 チーム（各チーム 4 役割と進行役）が同時に利用できる。通常負荷は 75 台の画面、最大想定は 270 台の画面（`performance-requirements.md` の表）で、どちらでも応答の目標を満たす | U6 の負荷試験（通常負荷と最大想定の両方）。U1 は、複数のゲームを並行して処理する自動試験を持つ |
| NFR4.2 | 同じゲームへの書き込みは 1 つずつ順に処理する。別のゲームの処理は、待たされない | 2 つのゲームの同時の書き込みが互いを待たないことの試験（BR4.6） |
| NFR4.3 | 1 つのゲームの保存の大きさは、50 週 × 4 役割の記録、遅延の枠、冪等性の記録で上限が決まる。上限を超えて増え続ける項目を作らない | 50 週のゲームの保存の大きさを測る試験 |
| NFR4.4 | 読み取り（状態の取得）は、書き込みの順番待ちに入らない。最大想定の毎秒およそ 270 回の取得を、書き込みと独立に処理できる | 書き込み中も状態の取得が応答する試験。最大想定での負荷試験は U6 |

## 想定する負荷

| 項目 | 通常負荷 | 最大想定 |
| :--- | :--- | :--- |
| 同時のチーム数 | 15 | 15 |
| 画面の数 | 75 | 270（1 チーム 18 台） |
| 状態の取得 | 毎秒およそ 75 回 | 毎秒およそ 270 回 |
| 週の確定 | 1 チームあたり 1 分に 1 回（全体で毎秒 0.25 回） | 同じ |
| 1 ゲームの寿命 | 数時間から数日 | 同じ |

## 拡張の方針

- 単一のアプリケーションで足りる規模のため、水平に増やす設計は U1 では行わない。ゲーム単位の直列処理は、データベースの仕組みで行い、アプリケーションが複数あっても成り立つ作りにする（アプリケーションのメモリにだけ頼らない）。
- 直列処理の方式の候補（行の占有、アドバイザリロック）と、待ちの間に接続を占有する影響（接続数への影響）は、NFR Design に引き継ぐ。
- 想定を超える負荷が出たときの対処（アプリケーションを増やす、データベースの接続数を調整する）は、後の NFR Design と Operation で扱う。
