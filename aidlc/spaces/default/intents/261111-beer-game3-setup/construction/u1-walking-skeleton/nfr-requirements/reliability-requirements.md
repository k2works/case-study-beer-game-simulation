# 信頼性の要件 - U1 u1-walking-skeleton

U1（薄い一通り）の正確性、整合性、可用性の要件です。元の要件は `requirements.md` の NFR1、NFR2、NFR5 です。教材として最も大切なのは、同じ入力から常に同じ結果が出ること、週の確定が壊れないことです。

出典: `requirements.md`（NFR1、NFR2、NFR5）、`functional-spec.md`、`rules.md`（BR4.6、BR4.7、BR5.3、BR5.7、BR5.8、BR5.9）、`contract-summary.md`（C2、C3）。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR1.1 | 同じ初期状態と意思決定系列からは、常に同じ週次状態と費用を再現する。週の計算（SimulationEngine）は、時計、乱数、保存、通信に触れない | 既知の入力で、2 回実行して結果が一致する自動試験。50 週すべての golden test は U2 が持つ。U1 は、AC1.5.3〜AC1.5.9 の数値の試験を持つ |
| NFR1.2 | 金額は、整数の最小単位で扱い、浮動小数点を使わない | 費用の計算の自動試験（端数の誤差が出ないこと） |
| NFR2.1 | 週の確定は、結果、遅延の枠の前進、週の進行を、1 回の保存で行う。途中で失敗したら、確定前の状態のままにする | 保存の失敗を注入する試験。強化は U2（US2.4） |
| NFR2.2 | 直列に処理する場合も、保存の版の検査を安全装置として残す。版が食い違う保存は拒否する | 版が食い違う保存の拒否の試験 |
| NFR2.3 | 同じゲームへの同時の書き込みでも、週は一度だけ確定される | 同時の確定の試験（BR4.6、BR5.7）。強化は U2 |
| NFR5.1 | 入力は、入力した時点で保存する。保存の成功を返してから、画面に反映する | 入力の直後にサービスを再起動しても残ることの試験。再起動からの復元は U4（US3.1） |
| NFR5.2 | 復帰用 token は、最後の操作から 24 時間有効とする。超えた token は拒否し、進行役による入れ替えが必要と案内する。実装は U4。U1 の token は失効しない | U4 の自動試験（AC3.2.3）。U1 の token が失効しないことは、NFR6 の脅威の表に記録した |
| NFR5.3 | 参加者の端末が 30 分以内に切断されても、確定済みのデータと確定前の入力を失わず、同じ役割に戻れる。実装は U4。U1 は、データを PostgreSQL にだけ置く | U4 の自動試験（AC3.2.2）。U1 は NFR5.1 の試験 |

## 障害の扱い

| 障害 | 振る舞い |
| :--- | :--- |
| 保存の失敗 | 確定前の状態のまま。500 の `internal` を返す。画面が取り直して確かめる |
| 順番待ちの時間切れ | 最大 3 秒待って、超えたら `unavailable`（503）を返す（NFR3.7）。画面が取り直す。サーバーは自動で再試行しない |
| アプリケーションの再起動 | 保存済みの状態から続けられる。未確定の入力も保存済み |
| データベースの接続断 | `internal` を返す。接続が戻れば、そのまま続けられる |

## 可用性の目標

U1 の時点では、可用性の数値目標（SLA）を置かない。教室の数時間の利用が中心で、一時的な停止の後に、確定済みのデータを失わずに続けられることを目標にする（NFR5.1）。本番の目標値は、後の Operation で定める。

## バックアップと復旧

バックアップと復元の手順は、後の Operation で定める。U1 は、データを PostgreSQL にだけ置き、アプリケーションのメモリに唯一の写しを持たない。
