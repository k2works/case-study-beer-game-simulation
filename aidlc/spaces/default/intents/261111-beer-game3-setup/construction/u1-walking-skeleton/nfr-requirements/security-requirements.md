# セキュリティの要件 - U1 u1-walking-skeleton

U1（薄い一通り）のセキュリティの要件です。元の要件は `requirements.md` の NFR6 と NFR7 です。ログインやアカウントはなく、コードと token だけで本人と権限を判定します。最も守りたい制約は、他の役割の非公開情報を、画面ではなくサーバーの応答の段階で出さないことです。

出典: `requirements.md`（NFR6、NFR7）、`functional-spec.md`、`rules.md`（BR1.4、BR1.5、BR2.6、BR4.1、BR4.7）、`entities.md`、`contract-summary.md`（C1、C4）、`nfr-requirements-questions.md`（Q3 暗号化、Q4 ログ）。

## 認証と認可の前提

- ログイン（アカウント）は作らない。資格情報は、参加コード、進行役用コード、観察者用コード、参加者の token の 4 種類だけ。
- 参加コードは参加の入口にだけ使う。参加後の要求は、参加者の token で判定する（BR2.6）。
- 進行役の操作は、進行役用コードを持つ人だけができる（BR1.5）。観察者用コードの入口と、観察者の投影は U4 が作る。U1 は、観察者用コードの発行と保存までを持つ。
- 権限の判定は、毎回の要求で、サーバー側で行う。画面で隠すだけにしない。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR6.1 | 参加コードは 8 文字以上の英数字で、暗号論的乱数で発行する。進行役用コード、観察者用コード、参加者の token は、暗号論的乱数による 128 ビット以上にする | コードの発行の自動試験（長さと文字種）。乱数は試験で固定の乱数に差し替えられる |
| NFR6.2 | 権限の判定は、毎回の要求でサーバー側で行う。他の役割の在庫、受注残、意思決定値、将来の需要は、応答に含めない。他のゲームの識別子や他の役割の識別子を指定した要求は、拒否する（403） | 役割別の投影の自動試験。他の役割、他のゲームを指定した要求の拒否の試験（AC1.4.1） |
| NFR6.3 | 進行役用コードと参加者の token は、ハッシュだけを保存する（照合用）。参加コードと観察者用コードは、照合用の値と、再表示のための暗号化した値（AES-256-GCM）の両方を保存する。照合用の値は、8 文字の参加コードを DB の漏えいから総当りで割り出されないよう、保存用の鍵と別の秘密の鍵を使う鍵付きハッシュ（HMAC-SHA-256）にする。鍵はどちらも環境変数か秘密情報の管理から渡し、ソースにも DB にも置かない | 保存された値から平文を復元できないこと（ハッシュ）と、鍵なしで復号も照合もできないことの試験 |
| NFR6.11 | 暗号化の鍵には、鍵の識別子を付ける。鍵を変えるときは、新しい鍵で暗号化し直す手順を用意し、移行の間は古い鍵でも復号できる。起動のときに鍵が無ければ、アプリケーションを起動しない。復号に失敗した再表示は、エラー（`internal`）を返し、コードを推測で返さない | 鍵の欠落での起動拒否の試験、鍵の入れ替えの試験、復号失敗の試験 |
| NFR6.4 | ログとエラーの応答に、コード、token、暗号化の鍵、参加者の表示名以外の個人情報を出さない | ログの出力の自動試験（資格情報の文字列が出ない） |
| NFR6.5 | 入力は、サーバー側で検証する。型、範囲、長さ、列挙の値を、zod などの検証で拒否する。SQL は、パラメータ化して組み立て、文字列連結にしない | 不正な入力の拒否の自動試験（BR4.2、BR1.1 など）。SQL の連結がないことの静的な確認 |
| NFR6.6 | 通信は、staging と production では HTTPS だけを許す。HTTP の要求は拒否するか、HTTPS へ転送する。コードや token を URL の問い合わせ文字列に載せない | 資格情報を HTTP ヘッダ（Authorization）で渡すことの確認。HTTP の要求が拒否または転送されることの検査（staging で実施） |
| NFR6.7 | 同じ識別子（`Idempotency-Key`）で内容が違う再送は拒否する（409）。別の人の記録の結果は返さない。識別子が欠けている、または 16〜128 文字の範囲外なら、422 の `validation` で拒否する。判定の順は、認可のあと、再送の照合の前に置く | 再送の自動試験（BR4.7、BR4.8）。識別子の欠落と長さ違反の試験 |
| NFR6.8 | 無効なコードによる参加の試行は、同じ接続元から 1 分あたり 10 回までとし、超えたら一時的に拒否する（`rate_limited`）。実装は U4 | U4 の自動試験（AC5.4.2）。U1 は、失敗の応答を同じ形にする |
| NFR6.9 | 表示名は 1〜40 文字とし、他の参加者の画面に出すときは、出力の時点でエスケープする（スクリプトが実行されない）。HTML として解釈しない | 表示名に `<script>` を含む参加者を参加させ、他の画面で実行されないことの試験 |
| NFR6.10 | 参加者の token は、ブラウザの `localStorage` に保存し、`Authorization` ヘッダで送る。画面は同じオリジンから配信し、CORS を許可しない。コンテンツセキュリティポリシー（CSP）で、自分のオリジン以外のスクリプトを許さず、HTTPS の強制（HSTS）を staging と production で有効にする | 応答ヘッダの検査（CSP、HSTS）。別のオリジンからの要求が拒否されることの試験 |
| NFR7.1 | 表示名以外の個人情報を、必須にも任意にも集めない。保存するのは、表示名と参加順の番号だけ | 参加の入力項目の確認 |
| NFR7.2 | 保持期間の既定は、ゲーム終了後 30 日とし、運営者がアプリケーションの設定で変えられる。期限を過ぎたデータを削除し、参加コードを無効にする。実装は U5 | U5 の自動試験（AC5.1.1、AC5.1.2） |
| NFR7.3 | 終了しないまま放置されたゲームは、最後の操作から 30 日で自動的に終了させ、その時点から保持期間を数える。実装は U5 | U5 の自動試験（AC5.1.3） |

## 脅威の考慮

| 脅威 | 対処 |
| :--- | :--- |
| 参加コードの推測 | 8 文字以上の乱数。無効なコードの試行回数の制限（毎分 10 回、NFR6.8）は U4 が足す（US5.4）。U1 の時点では、失敗の応答を同じ形にする |
| 参加コードの総当り（DB の漏えい後） | 照合用の値は鍵付きハッシュ（NFR6.3）。鍵が漏れない限り、DB だけでは総当りできない |
| 表示名によるスクリプトの注入 | NFR6.9（出力時のエスケープ）、NFR6.10（CSP） |
| 参加者の token の盗用（画面のスクリプト経由） | NFR6.9、NFR6.10。token の有効期間（24 時間）と失効は U4 が足す |
| 他の役割の情報の取得 | NFR6.2。応答は呼び出した人の投影だけから作る |
| 進行役の操作のなりすまし | 進行役用コード（128 ビット）。参加コードや参加者の token では進行役の操作ができない（BR1.5） |
| 参加者の token の盗用 | 128 ビットの乱数。HTTPS。有効期間（最後の操作から 24 時間、NFR5.2）と失効は U4 が足す。U1 では token が失効しないが、これは staging の試験用のゲームに限られ、U4 の完成まで本番には出さない |
| データベースの漏えい | ハッシュ（進行役用コード、token）と、鍵付きハッシュと暗号化（参加コード、観察者用コード）。鍵が別に管理されている限り、DB だけでは、進行役の操作や参加者のなりすまし、参加コードの割り出しはできない |
| SQL インジェクション | NFR6.5 |
| ログからの漏えい | NFR6.4 |
| 同時要求・再送による二重計上 | NFR6.7、BR4.6、BR5.7 |

## コンプライアンス

個人情報の保護（表示名のみ）は NFR7.1 で最小にする。保持期間と削除は U5 が足す。
