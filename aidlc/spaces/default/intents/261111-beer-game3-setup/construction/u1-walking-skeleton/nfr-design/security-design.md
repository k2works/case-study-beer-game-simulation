# セキュリティの設計 - U1 u1-walking-skeleton

`security-requirements.md`（NFR6.1〜NFR6.11、NFR7.1〜NFR7.3）を満たす設計です。

## 認証と認可の構造

- すべての要求は、入口の 1 か所（AccessControl）で資格情報（`Authorization: Bearer`）を判定し、`Principal`（参加者／進行役／観察者、ゲーム、役割）にする。業務の処理は Principal だけを受け取る。
- 応答は、GameSession の内部の状態から、Principal の投影だけを作って返す。GameSession を直接返す経路を作らない（ADR-002）。
- パスの `gameId` と Principal の `gameId` が食い違う要求は、403 で拒否する。資格情報が無い・不正な要求は 401 ではなく 403 に統一し、失敗の応答の形を同じにする（コードの推測に手がかりを与えない）。

## コードと token

| 対象 | 発行 | 保存 | 照合 |
| :--- | :--- | :--- | :--- |
| 参加コード | 8 文字以上の英数字（暗号論的乱数） | 鍵付きハッシュ（HMAC-SHA-256）と、暗号化した値（AES-256-GCM） | HMAC で照合 |
| 観察者用コード | 128 ビット以上 | 同上 | 同上 |
| 進行役用コード | 128 ビット以上 | SHA-256 のハッシュのみ | ハッシュで照合 |
| 参加者の token | 128 ビット以上 | SHA-256 のハッシュのみ | ハッシュで照合 |

128 ビット以上の乱数は総当りできないため、鍵なしのハッシュで足りる。8 文字の参加コードだけは、DB の漏えいで総当りされないよう、鍵付きにする。

## 鍵の管理（NFR6.3、NFR6.11）

- 鍵は 2 種類: 暗号化の鍵と、照合の鍵（HMAC）。どちらも環境変数か秘密情報の管理から渡し、鍵の識別子を付ける。
- 起動のとき、鍵が無ければ起動しない。
- 鍵の入れ替え（Q2 の A）: 新しい鍵を追加し、新規の保存は新しい鍵で行う。照合は、識別子が付いた旧鍵と新鍵の両方で行う。暗号化した値は識別子で復号の鍵を選ぶ。移行の手順（再暗号化と再計算）が終わったら、旧鍵を外す。
- 復号に失敗した再表示は `internal` を返し、コードを推測で返さない。

## 入力とブラウザ

- 入力は、型・範囲・長さを zod で検証する。SQL はパラメータ化し、文字列連結にしない。
- 表示名は 1〜40 文字。画面は React の既定のエスケープで出力し、HTML として解釈する出し方（危険な挿入）を使わない。
- token は `localStorage` に保存し、`Authorization` ヘッダで送る。画面は同じオリジンから配信し、CORS は許可しない。CSP は自分のオリジンのスクリプトだけ許し、HSTS は staging と production で有効にする。HTTP は拒否または転送する。

## 再送

- `Idempotency-Key` は、認可のあと再送の照合の前に検査する。欠落・長さ違反は 422。照合は（ゲーム、操作、呼び出した人、識別子）で行い、別の人の結果を返さない（BR4.7、BR4.8）。

## 個人情報と保持

- 保存する個人情報は表示名と参加順の番号だけ（NFR7.1）。
- 保持期間の削除と自動終了は U5 が行う。U1 は、ゲームの削除でコードと token と冪等性の記録も消せる構造（ゲームへの参照）にする（NFR7.2、NFR7.3）。
- 試行回数の制限（毎分 10 回、NFR6.8）は U4。U1 は、無効なコードの失敗の応答を同じ形にし、接続元を判定できるログを残す。
