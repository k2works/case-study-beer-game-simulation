# 信頼性の設計 - U1 u1-walking-skeleton

`reliability-requirements.md`（NFR1.1〜NFR1.2、NFR2.1〜NFR2.3、NFR5.1〜NFR5.3）を満たす設計です。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR1.1 再現性 | 週の計算は SimulationEngine の純粋な関数（入力は週の初めの状態、受注、意思決定、設定。時計・乱数・保存・通信なし）。同じ入力から同じ出力 |
| NFR1.2 金額 | 整数の最小単位（セント）。浮動小数点を使わない。データベースでも整数型 |
| NFR2.1 原子的な確定 | 確定の処理を 1 つのトランザクションにする。4 役割の記録、枠の前進、週の進行、冪等性の記録、版の更新を、まとめてコミットする。途中で失敗したらロールバックし、確定前の状態に戻す |
| NFR2.2 版の検査 | ゲームの版を、保存のたびに 1 増やす。更新は「版が読んだ値と同じ」を条件にし、食い違えば拒否する（安全装置） |
| NFR2.3 一度だけの確定 | ゲームの行の占有（直列処理）のあと、当週が確定済みか・同じ識別子の記録があるかを調べる。あれば前回の結果を返す（BR5.7） |
| NFR5.1 入力の保存 | 入力は、占有の中で保存し、コミットの成功を返してから応答する |
| NFR5.2 token の有効期間 | 実装は U4。U1 の token の表は、最後の操作の時刻を足せる形（列の追加で済む）にしておく |
| NFR5.3 切断からの復帰 | 実装は U4。U1 は状態を PostgreSQL にだけ置く |

## 障害の扱い

| 障害 | 設計 |
| :--- | :--- |
| 保存の失敗 | ロールバック。500 `internal`。画面が取り直して確かめる |
| 順番待ちの時間切れ | 3 秒で `unavailable`（503）。サーバーは自動で再試行しない |
| 接続断 | `internal`。接続が戻れば続けられる。冪等性の記録があるため、画面の再送は安全 |
| アプリケーションの再起動 | 状態はすべて保存済み。起動時に鍵が無ければ起動しない |

再試行をサーバー側で行わない理由: 冪等性は利用者が付ける識別子で担保しており、再試行は画面側の再送で足りる。サーバーの自動再試行は、占有の時間を延ばす。

## ヘルスチェック

ヘルスチェックの入口は、アプリケーションの稼働とデータベースへの接続を確かめる（NFR3.6）。
