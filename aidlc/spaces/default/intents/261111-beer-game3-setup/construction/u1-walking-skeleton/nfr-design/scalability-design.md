# 拡張性の設計 - U1 u1-walking-skeleton

`scalability-requirements.md`（NFR4.1〜NFR4.4）を満たす設計です。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR4.1 15 チーム、75〜270 台 | 状態を持たない（ステートレスな）アプリケーションにする。状態は PostgreSQL にだけ置く。1 台で足りる規模だが、複数台に増やしても成り立つ |
| NFR4.2 ゲーム単位の直列 | Q1 の A: 書き込みの処理の始めに、そのゲームの行を占有する（行の占有）。別のゲームの行は占有されないため、待たされない。占有は 1 回の処理の間だけで、処理の終わりに解く |
| NFR4.3 保存の大きさ | 週ごとの記録は（週 × 役割）の行、枠は固定数の行、冪等性の記録は操作ごとに 1 行。履歴は U3 が足す。上限を超えて増える項目はない |
| NFR4.4 読み取りの独立 | 取り直しは行を占有しない読み取りにする。データベースの既定の分離（読み取りがロックを待たない）を使う |

## 行の占有の扱い

- 占有を待つ間は接続を 1 つ使う。プールの大きさは、同時に占有を待つ書き込みの数（最大 15 チーム × 4 役割の同時入力）と、取り直しの読み取りを合わせて支える値にする。実装時に負荷試験（U6）で確かめる。
- 占有の待ちは最大 3 秒（NFR3.7）。時間切れは `unavailable` で返し、画面が取り直す。
- 占有しても、保存の版の検査は残す（BR5.9）。

## 増やすときの順序

1. アプリケーションの台数を増やす（ステートレスのため可能）。
2. データベースの接続数を調整する。
3. それでも足りなければ、取り直しを読み取り専用のレプリカへ向ける、またはサーバーからの通知へ変える（契約 C1 の見直し）。後の NFR Design と Operation で扱う。
