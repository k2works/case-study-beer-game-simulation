# 性能の設計 - U1 u1-walking-skeleton

`performance-requirements.md`（NFR3.1〜NFR3.4、NFR3.7）を満たす設計です。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR3.1 入力の確定 1 秒以内 | 入力は、ゲームの行の占有（直列処理）の中で、1 行の更新だけにする。集約全体を読み書きしない。冪等性の記録の照合は同じ処理の中で行う |
| NFR3.2 反映 2 秒以内 | 確定を要求した進行役の画面は、確定の応答に新しい状態を含めて即時に表示する。ほかの画面は 1 秒おきの取り直しで、確定の完了から最大 1 秒 + 応答時間 |
| NFR3.3 確定の処理 500 ミリ秒 | 計算は SimulationEngine の純粋な関数で、メモリ上で完結する。保存は 1 回の処理（1 回の保存）。ゲームの行を占有している時間を短くするため、占有の中でネットワーク越しの呼び出しをしない |
| NFR3.4 取り直し | 読み取り専用の処理にする。ゲームの行を占有せず、1 つの読み取りで投影に必要な行をまとめて取る（役割の行、当週の記録、枠）。応答は呼び出した人の投影だけで、小さくする |
| NFR3.7 順番待ち 3 秒 | 行の占有の待ちに時間切れを設定し（3 秒）、超えたら `unavailable`（503）を返す |

## 資源

- データベースの接続は、プールで共有する。プールの大きさは、最大想定の取り直し（毎秒およそ 270 回）と書き込みの占有を同時に支えられる値にし、実装時に測って決める。
- 取り直しの応答に、状態の版を含め、画面は版が変わったときだけ描画し直す。
- キャッシュは作らない（1 秒の鮮度が必要で、投影は人ごとに異なるため）。

## 却下した案

- 取り直しの結果をサーバー内で短時間キャッシュする案: 人ごとの投影があり、鍵が複雑になる。鮮度の要件とも合わない。
