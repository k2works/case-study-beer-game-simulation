# 性能の設計 - U5 u5-results-retention

`performance-requirements.md`（NFR3.1〜NFR3.5、NFR8.1、NFR8.2、NFR11.1、NFR11.2）を満たす設計です。接続プール、取り直しの 1 秒の周期、占有しない読み取り、応答の形は U1 の `performance-design.md` を、観察者と小売店の投影、認可の検査の設計は U4 の `performance-design.md` を引き継ぎます。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR3.1 結果の応答 | 結果は `Store.readSnapshot(gameId)`（既存。`REPEATABLE READ READ ONLY` の 1 つのトランザクション）で集約を 1 回読み、純粋な関数 `buildResultsView(snapshot)` で整える。読む行は設定 1、参加者数人、週の記録 200、遅延の枠 8 前後で、追加の問い合わせは要らない。資格情報の検査（`requireResultsViewer`）は U4 の検索と同じ索引 1 回の検索で、合わせて数回の問い合わせに収まる。応答の本文は 200 行 × 8 項目の JSON で、約 20 キロバイト。圧縮は U1 の入口の設定に従う |
| NFR3.2 出力の応答 | 出力も `readSnapshot` を 1 回呼び、`buildExportRecords(snapshot)`（1 週・1 役割の行の配列）から、CSV は `renderCsv`、JSON は `renderJson` で作る。整形は 200 行の文字列の連結と `JSON.stringify` だけで、数ミリ秒。大きなバッファやストリームは要らない（約 30 キロバイト）。測定は、50 週のゲーム 1 件で CSV と JSON の応答時間を自動試験が記録する |
| NFR3.3 取り直しへの影響 | 結果と出力は行を占有せず（`select ... for update` を使わない）、読み取り専用のトランザクションで読む。書き込みの順番待ちに入らず、書き込みを待たせない。接続プールからは 1 要求あたり 1 本を短時間だけ借りる。結果と出力の要求は終了後に 1 回ずつなので、プールを使い切る負荷にならない |
| NFR3.4 定期処理の影響 | 1 ゲームの自動終了と削除は、それぞれ 1 つの短いトランザクションで行う。行の占有の待ちは U1 の `lock_timeout`（3 秒）、処理そのものは 1 ゲームあたり 1 秒以内。ゲームの行を `select ... for update` で占有する時間は、再検査と 1 回の更新（削除は 1 回の `delete`）だけ。1 回の処理は、ゲームを 1 件ずつ順に処理する（並行にしない）ため、通常の要求が使うプールの接続を最大 1 本しか占有しない。所要時間は `retention_run` のログの `durationMs` で観測する。5 分または 1 秒を超えたら上限（`RETENTION_BATCH_LIMIT`）を下げる（調整手段は設定値） |
| NFR3.5 起動を待たせない | 定期処理の最初の実行は、`listen` の完了後に `void runOnce()`（待たない）で始める。実行中の失敗は例外にせず、ログに出して終える。ヘルスチェックは定期処理の状態に依存しない |

## 画面（NFR8）

| 要件 | 解決 |
| :--- | :--- |
| NFR8.1 キーボード操作と色以外の区別 | 指標の選択は、同じ `name` を持つ `<input type="radio">` の並び（`role="radiogroup"`、`aria-label="指標"`）にし、矢印キーで移動し、フォーカスの輪郭を表示する。費用の週ごと・累積の切り替えも同じ形のラジオ。選択中の状態は、ラジオの印と、ラベルの太字・下線で示す（色だけにしない）。系列は線種（`stroke-dasharray`: なし、`8 4`、`2 4`、`8 3 2 3`）と印（丸、四角、三角、ひし形）で区別し、凡例に同じ線種と印と役割名を置く。凡例と線の色は、白い背景に対して 3:1 以上の 4 色（試験で比を計算する）。文字は 4.5:1 以上。グラフの `<svg>` は `role="img"` と `aria-label` を持ち、グラフと同じ数値の `<table>`（`<caption>`、`<th scope>`）を併記して、グラフを読めない人の代替にする |
| NFR8.2 描画の時間 | 描画する点は 1 指標・4 系列・最大 50 週の 200 点と、表の 200 セルで、再計算は指標の切り替えのときだけ。系列の計算は `useMemo` で結果の応答に紐づけ、切り替えは再取得をしない（応答は一度だけ）。印は 25 週を超えるときは 5 週ごとに間引き、線は全点を結ぶ。描画の時間を Playwright が測って記録する |

## 画面と出力の言語（NFR11）

| 要件 | 解決 |
| :--- | :--- |
| NFR11.1 日本語の文言 | 結果画面、出力ボタン、注意書き、列名の説明、エラーの理由・直し方の文言は、画面の文言の一覧（`web/messages.ts` 相当）に日本語で置く。金額は `formatCents(cents)`（整数の割り算と剰余。`$` と小数 2 桁）で整える。画面の試験で文言を確かめる |
| NFR11.2 出力の識別子 | CSV と JSON の列名・項目名と役割の値は、英語の識別子のまま出す。日本語の説明は、出力ボタンの近くの `ExportPanel` に、列名の表（列名、意味、単位）と役割の対応（`factory`＝工場、`wholesaler1`＝卸売店 1、`wholesaler2`＝卸売店 2、`retailer`＝小売店）として常に表示する。日本語の表示名は UTF-8 で出す（CSV は BOM 付き） |

## 根拠

- 結果と出力は、集約を 1 回読んで純粋な関数で整えるだけの作りにして、応答時間のばらつきを減らす。キャッシュは設けない（終了後に 1 回ずつ開く要求で、読み取りが小さいため。キャッシュは古い内容を返す余地を生み、削除との整合を難しくする）。
- 定期処理を 1 ゲームずつ順に処理し、トランザクションを短く保つのは、通常の要求の接続と行の占有への影響を、1 ゲーム 1 秒という上限で抑えるためである。並行にして速く終わらせる価値は、1 時間に最大 200 件の規模ではない。
