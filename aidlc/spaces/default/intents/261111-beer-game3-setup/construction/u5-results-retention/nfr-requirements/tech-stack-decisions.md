# 技術スタックの決定 - U5 u5-results-retention

U5（結果と出力、保持と削除）は、U1 で決めた技術スタックをそのまま使い、新しい技術や依存を足しません。U1 の `tech-stack-decisions.md` が正本です。この文書は、U5 の要件がその構成のどこを使うかを記録します。

出典: `requirements.md`（NFR3、NFR4、NFR6、NFR7、NFR8）、U1 の技術スタックの決定（Q1）、`nfr-requirements-questions.md`（Q1〜Q4）。

## 決定

U5 は新しい技術を導入しない。外部ライブラリの導入は確認必須のため、追加が必要になったときは理由を記録して確認を取る。

| 区分 | 使うもの（U1 の決定） | U5 での使い方 | 関連する要件 |
| :--- | :--- | :--- | :--- |
| データベース | PostgreSQL 18 | `games.last_operation_at` の列を別の移行として足す。削除は 1 回の保存の中で、ゲームに紐づくすべての表を対象にする（外部キーの連鎖削除、または明示的な削除の順序は NFR 設計で決める）。定期処理の二重実行の防止に、アドバイザリロックを使う（取った接続を処理の間じゅう使い続ける）。自動終了と削除の対象を選ぶ索引を、NFR 設計で確かめて足す。結果と出力の読み取りは、読み取り専用の `REPEATABLE READ` の 1 つのトランザクションで行う | NFR2.1、NFR2.3、NFR4.2、NFR2.5 |
| データベース移行 | node-pg-migrate | 既存の表の列を削除も意味の変更もしない（`contract-summary.md` の C3）。既存のゲームの `last_operation_at` を、実際の最後の操作より古くならないように埋める（`reliability-requirements.md` の NFR2.5） | NFR2.5 |
| Web サーバー | Fastify | 結果と出力の入口を足す。入口は AccessControl 経由でだけ Reporting を呼ぶ。定期処理に入口は足さない。出力は `Content-Disposition` と `Cache-Control` を付けて返す | NFR6.1、NFR6.3、NFR6.5 |
| 入力の検証 | zod | 出力の `format` と、設定値（保持期間、自動終了の期間、周期、1 回の上限）を検証する。参加と担当者の入れ替えの表示名の検証に、先頭が `=`、`+`、`-`、`@`、タブ、復帰のものの拒否を足す（U1・U3 の既存の検証の変更） | NFR6.6、NFR6.8 |
| 定期処理 | Node.js 標準のタイマー | アプリケーションの内部のタイマーで起動する。外部のスケジューラや、定期実行の基盤を足さない。タイマーは停止を妨げない。時刻は注入した時計から得る | NFR3.5、NFR5.1、NFR5.2 |
| CSV と JSON | 自前の小さな関数 | CSV の組み立て（RFC 4180 の引用、BOM、CRLF）を、外部ライブラリを足さずに書く。JSON は標準の機能で組み立てる。CSV の読み戻しの試験には、試験専用の小さな読み取りの関数を置く（本番の依存に足さない） | NFR1.2 |
| 画面 | React、Vite | 結果画面を足す。グラフは SVG を自分たちで描き、外部のグラフのライブラリを足さない（線種、印、凡例、表の併記を自分たちで制御するため）。取り直しは 1 秒のまま | NFR8.1、NFR8.2 |
| ログ | 構造化ログ（JSON） | 定期処理の結果、ゲームごとの自動終了と削除、結果と出力の取得の行を足す。資格情報と個人情報は出さない | NFR9.1〜NFR9.4 |
| 構造の検査 | ESLint、Vitest | 入口から Reporting と Retention への直接の import が AccessControl 経由に限られることを、U4 の構造の試験に含める | NFR6.1 |
| 試験 | Vitest、Testing Library、Playwright | 時計を進めて期限の境界（30 日、7 日、期限ちょうど）を確かめる。CSV の読み戻し、障害の注入、アプリケーション 2 つでの二重実行の防止、再起動を挟んだ結果の一致を試験する | NFR1.1、NFR1.2、NFR2.1、NFR2.2、NFR4.2 |

## 方針

- 時刻は注入した時計から得る（保持期間、自動終了の期間、定期処理の周期）。試験は、時計を進めて期限の境界を確かめ、1 回の処理を時刻を指定して直接呼べるようにする。
- 定期処理のタイマーと、1 回の処理の本体は分ける。本体は、時計とデータベースの保存を引数に取り、試験から直接呼べる形にする。
- 出力の組み立ては、保存先にも画面にも触れない純粋な関数にして、ExportRecord の列から CSV と JSON を作る。
- 版は U1 と同じく、実装（Code Generation）の時点で公式情報で確かめて決める。

## 却下した案

- 外部のグラフのライブラリを足す案: 線種、印、凡例、表の併記を細かく制御する必要があり、依存が増える割に得られるものが少ない。SVG を自分たちで描く。
- CSV の外部ライブラリを足す案: 書式が RFC 4180 の小さな規則で足り、依存を増やす価値が小さい。ただし、読み戻しの試験で規則を確かめる。
- 外部のスケジューラから管理用の入口を叩いて定期処理を起動する案（Q9 の B）: 秘密の値を持つ入口が攻撃面を増やすため、Functional Design で却下した。
- 削除済みのゲームの表をデータベースに持つ案（Q8 の B）: 個人情報とゲームの痕跡をデータベースに残さないため、却下した。
