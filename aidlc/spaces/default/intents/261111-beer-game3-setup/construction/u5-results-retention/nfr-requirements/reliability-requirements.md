# 信頼性の要件 - U5 u5-results-retention

U5（結果と出力、保持と削除）の正確性、整合性、可用性の要件です。元の要件は `requirements.md` の NFR1、NFR2、NFR5 です。保存の版の検査、ゲーム単位の直列処理、障害の扱いは U1 の `reliability-requirements.md` を、操作と履歴を同時に保存する要件は U3 の `reliability-requirements.md` を、再起動と切断からの復帰は U4 の `reliability-requirements.md` を引き継ぎます。U5 は、結果と出力の内容の正確さ、自動終了と削除の原子性と再検査、定期処理の失敗の扱いが中心です。

出典: `requirements.md`（NFR1、NFR2、NFR5）、`functional-spec.md`、`rules.md`（BR21.3、BR21.5、BR23.4、BR24.3、BR24.5、BR25.4、BR26.2〜BR26.6）、`entities.md`、`contract-summary.md`（C3、C5）。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR1.1 | 結果と出力の内容は、確定済みの週の記録の写しである。終了したゲームは書き込みを受けないため、同じゲームの結果と出力は、何度取得しても、再起動を挟んでも、同じ内容になる。確定前の入力は含めない（BR21.3）。金額は整数のセントで扱い、浮動小数点を使わない（FR10.2） | 終了したゲームの結果と出力を 2 回取得し、再起動を挟んでもう 1 回取得して、3 回が一致する試験。確定前の入力が含まれない試験 |
| NFR1.2 | 同じゲームの CSV と JSON は、同じ中間表現（ExportRecord の列）から作り、件数・順序・値が一致する。CSV を RFC 4180 の規則で読み戻した records は、JSON の records と一致する。区切り文字・引用符・改行・先頭が `=` の表示名を含んでも、読み戻した値は元の値と一致する（BR23.3、BR23.4） | 表示名にカンマ、二重引用符、改行、先頭が `=` を含む参加者のゲームで、CSV を読み戻して JSON と突き合わせる試験（AC4.2.2、AC4.2.3） |
| NFR2.1 | 削除は、ゲームに紐づくすべてのデータ（ゲーム、設定と需要系列、参加者、割当て、週の記録、遅延の枠、各コード、復帰用 token、冪等の記録、操作の履歴）を、1 回の保存の中で、全部か全くなしかで行う。途中で失敗したらすべて元に戻し、一部だけ残った状態を作らない（BR24.3） | 削除の途中に障害を注入して、ゲームのすべての表の行が元のまま残ることの試験。成功したときにすべての表の行が消えることの試験 |
| NFR2.2 | 自動終了と削除は、ゲームの行を占有した中で、対象であることを再検査する。選んだあとに操作があったゲームは自動終了せず、条件を満たさなくなったゲームは削除しない。すでに終了または削除されたゲームは、何もせず、失敗に数えない（冪等）。自動終了は、U3 の `autoEnd` が期限の時刻を受け取って再検査する（BR24.5、BR25.4） | 選んだあとに参加者が入力したゲームが自動終了しないことの試験。同じゲームの自動終了と削除を 2 回続けて行っても、結果が変わらないことの試験。2 つのインスタンスが同じゲームを同時に削除しても、片方が見つからないだけで失敗にならないことの試験 |
| NFR2.3 | 結果と出力は、読み取り専用の 1 つのトランザクション（`REPEATABLE READ` の分離の水準。複数の問い合わせが同じ時点のスナップショットを読む）の中で行う。読み取りの開始より前に削除が完了していれば、存在しないゲームと同じ 403 の本文で拒否する。読み取りの開始のあとに削除が完了しても、読み取りは開始時点の完全な結果を 200 で返す。どちらの場合も、一部の行だけが欠けた結果や、空の結果を 200 で返さない（BR21.5、BR24.4）。期待値はこの 2 通りだけである | 読み取りの開始前に削除を完了させて 403 になる試験。読み取りの途中（最初の問い合わせのあと）にゲームを削除して、結果が完全な 200 になる試験。どちらでも、欠けた結果にならないこと |
| NFR2.4 | 1 つのゲームの失敗は、ほかのゲームの処理を止めない。さらに、失敗が続くゲームが 1 回の上限（既定 100 件）以上たまっても、後ろの正常なゲームが処理されなくなるのを防ぐ。方法は、直近の処理で失敗したゲームを、失敗から 1 周期の間、選択から外し（識別子をプロセスのメモリに持つ。再起動で消えてよい）、正常なゲームを先に上限まで選ぶことである。失敗から 1 周期たったゲームは対象に戻る（BR26.3、BR26.4） | 恒久的に失敗するゲームを上限と同じ数だけ作り、その後ろの正常なゲームが、数回の処理のうちに処理されることの試験 |
| NFR2.5 | 最後の操作の時刻（`lastOperationAt`）は、状態を変える操作の保存と同じ保存の中で更新する。閲覧と状態を変えない再送では更新しない。移行では、既存のゲームの `lastOperationAt` を、`createdAt`、履歴の最後の `occurredAt`、参加者の参加の時刻、週の記録の `decidedAt` のうち最も遅いもので埋める（参加と開始と参加者の入力は履歴に残らないため、履歴だけで埋めると古く見積もり、移行の直後に早すぎる自動終了が起きる）。この規則は Functional Design の `entities.md` に反映済みである（BR25.2） | 各操作のあとに `lastOperationAt` が進むことと、閲覧で進まないことの試験。参加者の入力だけが進んだ既存のゲームを移行して、自動終了の対象にならないことの試験 |
| NFR5.1 | 定期処理の失敗（個々のゲームの失敗、データベースへの接続の失敗、ロックを取れないこと）は、参加者と進行役の要求に影響しない。タイマーは例外で止まらず、次の周期でやり直す。判定は毎回データベースの状態から行い、前の回の状態を持ち越さない（BR26.4） | 定期処理の途中に障害を注入して、同時に送った取り直しと入力が成功することと、次の周期で処理が再開することの試験 |
| NFR5.2 | アプリケーションの停止（SIGTERM、SIGINT）は、実行中のゲームの保存が終わるまで待ってから閉じる。待つ時間の上限は 10 秒とし、超えたら閉じる（コンテナの停止の猶予より短くする。猶予の値はインフラの設計の工程で確かめ、10 秒がそれを超えるなら猶予より短く直す）。途中で止まっても、保存はコミットされたか戻されたかのどちらかで、部分更新を残さない。再起動後は、次の周期で残りの対象を処理する（BR26.6） | 処理の最中に停止を要求して、保存が全部か全くなしかのどちらかであることと、再起動後に処理が続くことの試験 |

## 障害の扱い

| 障害 | 振る舞い |
| :--- | :--- |
| 1 つのゲームの自動終了または削除の失敗 | そのゲームを失敗に数え、ログに出し、残りのゲームを続ける。保存は全部戻る。次の周期でやり直す |
| データベースへの接続の失敗（定期処理） | その回を終え、ログに出す。次の周期でやり直す。要求には影響しない |
| ロックを取れない | 今回は何もせず、skipped としてログに出す |
| 結果と出力の読み取りの失敗 | `Problem` の `unavailable`（503）を返し、画面が再試行を案内する。空の結果を返さない |
| 結果の取得中にゲームが削除された | 存在しないゲームと同じ 403 の本文で拒否する |
| アプリケーションの停止または再起動 | 実行中のゲームの保存を待って閉じる。保存は全部か全くなし。再起動後に残りを処理する |

## 可用性の目標

U1 と同じく、U5 でも可用性の数値目標（SLA）を置かない。授業の数時間の利用が中心で、結果と出力は終了後に何度でも取得でき、定期処理が一時的に止まっても、次の周期で追いつける。本番の目標値は、後の Operation で定める。

## バックアップと復旧

削除したデータは、DB の通常の運用では復元しない。バックアップに残るデータの扱い（保持期間を削除の期限と揃えるか）は、個人情報の保持に関わるため、後の Operation で定める（`security-requirements.md` の NFR7.3）。
