# 監視の設計 - U6 u6-nfr-verification

U6 が監視するのは、アプリケーションではなく「検証そのものが健全に動いているか」です。アプリケーションの運用の監視（メトリクスの保存先、警告のしきい値、通知先）は、後の Operation で決めます。この文書は `nfr-design/observability-design.md` の戦略を、GitHub Actions の上で実現する仕組みに落とします。新しい監視の基盤（メトリクスの保存先、ダッシュボードの製品）は足しません。

出典: `nfr-design/observability-design.md`、`performance-design.md`、`reliability-design.md`、`infrastructure-specification.md`、`cicd-pipeline.md`。

## 番号の付け方

`NFR9.x` は、U6 の検証の結果を追跡できるようにする要件で、上流の NFR9（操作の履歴。u3-facilitation）とは別である。

## メトリクスと指標

| 指標 | 出どころ | 閾値 | 重要な理由 |
| :--- | :--- | :--- | :--- |
| 入力の確定、反映（仮想の利用者と実ブラウザ）、取り直しの応答時間（50、95、99 パーセンタイル）と件数 | 要約の `phases`（`verify-summary.json`） | 合否の閾値は要件のとおり（`performance-design.md` の性能の予算）。要件を満たしたうえでの余裕を見るため、閾値の 80% を超えたら要約の表に注意の印を付ける | 劣化の傾向を、閾値を超える前に気づく |
| サーバーの異常、`timeout`、`connect` の件数 | 要約の `errors` | 0 件 | NFR3.4 の合否の条件 |
| 整合性の検査の結果 | 要約の `consistency` | 崩れ 0 件 | データの正しさ（NFR2.1） |
| 測定器のイベントループの遅れ（99 パーセンタイル） | 要約の `harness` | 100 ミリ秒（超えたら「無効」） | 測定器の限界とアプリケーションの限界の切り分け |
| 実行環境の情報（CPU、メモリ、Node.js と PostgreSQL の版） | 要約の `environment` | 記録のみ | 閾値超過の原因の切り分け（NFR4.4） |
| ジョブの所要時間 | ワークフローの実行の記録（GitHub） | 下の SLO | 待ち時間の増加を把握する |
| 失敗時の成果物の有無 | アーティファクトの一覧 | 失敗したジョブに、トレースと画像が 1 つ付くこと | NFR9.3 |
| `gate` の所要時間 | ワークフローの実行の記録（GitHub） | 24 分（PR）、44 分（`main` への PR）で注意 | SLO の違反より前の注意（警告の表） |

## 警告

| 警告 | 条件 | 重大度 | 届け先 |
| :--- | :--- | :--- | :--- |
| 必須のチェックの失敗 | 集約のジョブ `gate` が失敗（`verify`、`e2e`、`a11y`、`load-smoke` の失敗、「無効」、`changes` の失敗を含む） | P2（チケット。原因を直すまで統合しない） | プルリクエストの状態表示と、GitHub の通知（作成者） |
| 本試験の失敗 | `load-main` が失敗（不合格または無効）。`main` へのプルリクエストでは、`gate` を通して統合を止める | P2（`main` への PR の場合は統合を止める） | GitHub の通知。夜間の失敗は、ワークフローの実行の失敗として見える |
| 夜間の本試験が動かない | 最初のリリースの前は、夜間の定期実行が `main` に定義がなく動かない（想定内）。リリースの後は、リポジトリの活動が長くないと GitHub が定期実行を自動で無効にする | 情報（前）、P3（後） | リリースの手順書の条件に、PR の本試験と、定期実行が有効であることの確認を書く（`cicd-pipeline.md` の最初のリリースの前と後） |
| 閾値の 80% 超え | 要約の注意の印 | P3（ダッシュボードの扱い） | ジョブの要約の表。通知しない |
| 所要時間の注意 | `gate` の所要時間が、SLO の窓の 80%（PR は 24 分、`main` への PR は 44 分）を超えた | P3 | ジョブの要約に所要時間を出し、月に 1 度の見直しで確認する |

専用の警告の仕組み（外部の通知）は作らない（`observability-requirements.md` の NFR9.2）。警告のしきい値は SLO の違反より前に出すため、閾値の 80% の注意の印と、所要時間の 80% の注意を置く。

## SLI と SLO（検証の仕組みそのもの）

下の値は、**設計時点の初期の目標**であり、実測の前に置いた仮説である。最初の 4 週間の実測で見直す。

所要の目標（`cicd-pipeline.md`）は、`changes` の 1 分と実行機の待ちを足した合計より、SLO の値が余裕を持つように置いている。

| SLI | SLO の目標 | 測定の窓 | 測り方（誰が、いつ、何を見て） |
| :--- | :--- | :--- | :--- |
| プルリクエストの必須のチェック（`gate`）が、起動から終了まで 30 分以内に終わる割合（`e2e` の目標 20 分 ＋ `changes` 1 分 ＋ 待ち） | 95% 以上 | 直近 30 日 | 月に 1 度の見直しで、リポジトリの担当者が `gh run list --workflow beer-game3.yml --json` の結果（開始と終了の時刻）から数える |
| `main` へのプルリクエストの `gate`（`load-main` を含む）が、起動から終了まで 55 分以内に終わる割合（`load-main` の目標 40 分 ＋ `changes` 1 分 ＋ 待ち） | 95% 以上 | 直近 90 日（リリースが少ないため長い窓） | リリースのたびに、リリース担当が同じ方法で確認する |
| 夜間の本試験（`develop`）の実行が、設計どおりに起動する割合（最初のリリースの後） | 95% 以上 | 直近 30 日 | 月に 1 度、`gh run list --event schedule` で起動の回数を数える。起動していなければ定期実行の状態（`gh workflow list`）を見る |
| 「無効」（終了コード 2）で終わる本試験の割合 | 5% 未満 | 直近 30 日 | 保存した要約の `verdict` を、月に 1 度の見直しで数える |
| 失敗した必須のチェックのうち、同じコミットの再実行だけで通った割合（不安定さ） | 0%（再実行で通すことを合格にしない。NFR2.3） | 直近 30 日 | 月に 1 度、実行の試行回数（`run_attempt`）が 2 以上で成功した実行を数える |

測り方は、自動の仕組みを足さず、月に 1 度の見直しで人が `gh` の結果から数える。見直しの手順は、リリースの手順書（Operation）に足す。「無効」が 5% を超えたら、実行機の大きさ（`infrastructure-specification.md`）または負荷のスクリプトの設定を見直す。

## ログと追跡

| 項目 | 設計 |
| :--- | :--- |
| ログの集約 | GitHub Actions の実行のログを使う。負荷試験のスクリプトは、標準エラー出力に 1 行 1 件の構造化ログを出す（`observability-design.md`）。実行のログの保持は GitHub の既定に従う |
| 追跡 | 相関の識別子は、実行の識別子（`bg3_verify_<実行の識別子>`）で、ログ、要約、使い捨てのデータベースの名前に共通して現れる。分散トレースは、検証の仕組みには導入しない |
| ダッシュボード | 作らない。ジョブの要約（`GITHUB_STEP_SUMMARY`）の表と、30 日保存する要約の JSON で足りる。傾向の比較が必要になったら、成果物を取得して比べる（自動化は作らない） |
| 個人情報と資格情報 | 要約とログに書かない（許可リスト方式。`security-design.md`） |
