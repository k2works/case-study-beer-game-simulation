# 性能の要件 - U6 u6-nfr-verification

U6（非機能の検証）が、完成した画面とサーバーの全体で測って確かめる、応答性と画面の品質の目標です。元の要件は `requirements.md` の NFR3、NFR8、NFR10、NFR11 です。U1〜U5 は、それぞれ自分の範囲を自動試験で確かめ、全体の負荷と全画面の検査は U6 が行うと決めてありました（`unit-of-work.md`）。U6 は新しい業務機能を足さないため、ここに書くのは「何を、どの値で、どう測って合否にするか」です。

測定の値（15 チーム、95 パーセンタイル 1 秒、2 秒、コントラスト 4.5:1、WCAG 2.2 AA、最新 2 世代）は、仮の値のまま使わず、`nfr-requirements-questions.md` の Q1 の A で、そのまま確定しました。負荷の前提（通常負荷 75 台、最大想定 270 台、取り直しの周期 1 秒）は、U1 の `performance-requirements.md` を引き継ぎます。

出典: `requirements.md`（NFR3、NFR4、NFR8、NFR10、NFR11）、`unit-of-work.md`（U6）、`contract-summary.md`（C1 のポーリング）、`nfr-requirements-questions.md`（Q1 測定値の確定、Q2 負荷試験の道具、Q3 頻度、Q4 ブラウザ、Q5 アクセシビリティと日本語、Q6 反映が収まらない場合）。

## 番号の付け方と、上流の NFR との対応

`NFRn.m` の詳細番号は、Unit ごとに 1 から振る（U1〜U5 と同じ慣例。NFR Requirements の手順が、詳細な要件に上流の NFR の番号を引き継ぎ、小番号を足すと定めている）。したがって U6 の `NFR3.3` は、U1 の `NFR3.3` と同じ要件ではない。Unit をまたいで参照するときは、Unit 名を添える。

U6 が検証する上流の NFR の範囲は、次のとおり。U6 が検証しない部分は、担当の Unit が自分の自動試験で確かめる。

| 上流の NFR | U6 が検証する部分 | U6 が検証しない部分（担当） |
| :--- | :--- | :--- |
| NFR3 応答性 | 通常負荷での入力確定・反映・取り直しの応答（本ファイルの NFR3.x） | 週確定の処理そのものの時間（u1-walking-skeleton。U1 の NFR3.3）、書き込みの順番待ち（U1 の NFR3.7） |
| NFR4 同時利用 | 15 チームの同時利用（`scalability-requirements.md` の NFR4.x） | 取り直しが書き込みの順番待ちに入らない作り（U1 の NFR4.4） |
| NFR8 アクセシビリティ | 全画面・全状態の検査（本ファイルの NFR8.x） | 各 Unit の自分の画面の検査（各 Unit。U6 は重ねて検査する） |
| NFR10 可搬性 | 主要ブラウザでの主要な操作（本ファイルの NFR10.x） | - |
| NFR11 言語 | 全画面の日本語表示（本ファイルの NFR11.x） | 出力の識別子の扱い（u5-results-retention の Q6 の A） |

## 応答性（NFR3）

| ID | 要件 | 測定の条件 | 確かめる場所 |
| :--- | :--- | :--- | :--- |
| NFR3.1 | 入力の確定（意思決定の保存）の応答は、95 パーセンタイルで 1 秒以内 | 通常負荷（15 チーム、各 4 役割と進行役の 75 台が 1 秒おきに取り直し、各チームが 1 分あたり 1 週を確定）を 10 分間 | 10 分間の本試験（夜間と手動。NFR3.5 の説明を参照） |
| NFR3.2 | 週の確定後、確定を要求した進行役以外の画面にも、新しい状態が 2 秒以内（95 パーセンタイル）に反映される | 通常負荷。確定の応答を受け取った時刻から、ほかの画面の取り直しが新しい週を返すまでの時間で測る | 10 分間の本試験 |
| NFR3.3 | 画面の取り直しの応答は、通常負荷で 95 パーセンタイル 500 ミリ秒以内、最大想定（270 台。1 チームあたり同じ役割を 4 人が担当し、観察者もいる場合）で 95 パーセンタイル 1 秒以内 | 通常負荷と最大想定の両方。最大想定は 10 分間の本試験の中の別の区間で測る | 10 分間の本試験 |
| NFR3.4 | 負荷の間、サーバーの異常（5xx、`unavailable`（503）を含む）は 0 件。通常負荷では、書き込みの順番待ち（U1 の NFR3.7）が 3 秒を超える状況は起きない | 通常負荷と最大想定の両方で、全要求の状態コードを集計する | 短い負荷試験と本試験の両方 |
| NFR3.5 | 負荷試験は 2 段で動かす（Q3 の A）。プルリクエストごとの CI で、1 分間・15 チームの短い負荷試験を動かす。10 分間の本試験は、夜間の定期実行と手動実行で動かし、結果を記録する。夜間の定期実行は、`develop` を明示して取得した内容を検査する（GitHub の定期実行は既定の branch のワークフローで動くため、team の方針の `develop` 統合に合わせて、取得する branch を指定する）。手動実行は、検査する branch を指定でき、リリースで `develop` を `main` へ merge する前にも実行する。**合否の判定の範囲**は、標本の数で分ける。短い試験は、標本が多い指標だけで合否を決める（NFR3.3 の通常負荷の取り直し（1 分で約 4500 件）、NFR3.4 のサーバーの異常 0 件、整合性の検査（`reliability-requirements.md` の NFR2.1））。入力の確定（NFR3.1。1 分で約 60 件）と反映（NFR3.2。1 分で約 60 件）は、短い試験でも測って記録するが、標本が少なく 95 パーセンタイルが外れ値 1 件で決まるため、合否には使わず、10 分間の本試験（それぞれ約 600 件）で合否を決める。最大想定の区間（NFR3.3 の 270 台）は、10 分間の本試験だけに含める。どちらの試験も、開始から 10 秒は立ち上げ期間として集計から除く。**超過したときの扱い**は、合否に使う指標が 1 つでも閾値を超えたら失敗とし、再実行で通ったことを合格にしない（`reliability-requirements.md` の NFR2.3）。原因が実行環境にあると判断できる根拠（実行環境の記録、同じコミットでの繰り返しの測定）があるときは、その根拠を記録したうえで、閾値でなく環境（実行環境の見直し）を直す | 短い負荷試験は 1 分、本試験は 10 分。合否の指標は上のとおり。立ち上げ期間は 10 秒 | CI（`beer-game3.yml`。Q7 の A）と、夜間の定期実行 |
| NFR3.6 | 目標を満たさなかったとき、目標の数値は緩めない。まず測って原因（取り直しの周期、保存の待ち、描画）を切り分け、周期や保存の見直しで解消できるかを先に確かめる。それでも満たせない場合は、サーバーからの通知（Server-Sent Events）への変更を提案し、あなたが判断する（契約 C1 の見直しになる。Q6 の A） | 満たさなかった測定の結果と切り分けの記録 | U6 の Code Generation と、満たさなかった場合の前の Unit への戻し |

| ID | 要件 | 確かめ方 |

| NFR8.2 | 全画面と主要な状態（エラー、一時停止、終了、結果、出力の注意書き）で、WCAG 2.2 AA の違反が 0 件である。コントラスト 4.5:1 以上の検査を含む | axe-core を Playwright から動かし、各画面と各状態を検査する（Q5 の A） |
| NFR8.3 | 通常の文字は背景とのコントラスト比 4.5:1 以上。結果のグラフの線と印は背景に対して 3:1 以上（U5 の NFR8.1 を引き継ぐ）。axe-core は文字以外の要素のコントラストを測れないため、グラフの系列の色と背景の比は、色の値から計算する別の試験で確かめる | axe-core の検査と、系列の色の比の計算の試験 |
| NFR8.4 | 状態の表示（一時停止中、終了、エラー、入力済みと未入力、選択中の指標や切り替え）は、色だけに頼らず、文字または記号と、支援技術に伝わる名前（アクセシブルな名前または状態の属性）でも示す。axe-core は色だけに頼った表示を一般には検出しないため、状態を示す要素ごとに、文字または名前が存在することを確かめる別の試験を足す | Playwright の画面の試験。各状態を作り、状態を示す要素の文字またはアクセシブルな名前が空でないことを検査する |
| NFR10.1 | 最新の世代の Chromium、Firefox、WebKit（Safari の代わり）、Edge の安定版で、ゲームの作成から週の確定までの主要な操作を完了できる | CI で自動に動かす Playwright の試験（Q4 の A） |
| NFR10.2 | 1 つ前の世代の 4 つのブラウザと、実機の Safari は、リリースの前に確認票で確かめて、結果を記録する。確認票の項目は、NFR10.1 の主要な操作と同じにする | リリース前の手順書（確認票）と、その記録（NFR9.4） |
| NFR11.1 | 画面の文言は日本語のみで、英語の文が混じらない。画面の文言の一覧（`messages.ts`）を検査する試験と、各画面の表示された文言を検査する試験の両方で確かめる。識別子（列名、役割の値、コード）と金額の記号は対象から除く | Vitest の検査と、Playwright の画面の試験（Q5 の A） |
| NFR11.2 | 出力（CSV と JSON）の列名と役割の値を英語の識別子のままにする解釈は、U5 の Q6 の A のとおり引き継ぐ。U6 は、出力ボタンの近くに日本語の説明が常に表示されることを、全画面の検査の対象に含める | NFR8.2 の検査の中で、出力の導線の画面を対象にする |

## 根拠と設計への影響

- 応答の合否を決める値は、通常負荷では U1 と同じ値（NFR3.1〜NFR3.3）を使う。U6 が値を決めるのではなく、確定した値で測るだけで、緩めることはしない（NFR3.6）。
- 本試験の 10 分は、要件（NFR3）の条件そのものである。変更のたびに 10 分を動かすと、CI の待ち時間が長くなるため、短い試験で劣化を早く検知し、本試験で要件を確かめる 2 段にした（Q3 の A）。
- 画面の通し試験と axe-core の検査は、U1〜U5 が自分の画面について行ったものを、全画面と全状態へ広げる。各 Unit の試験は残し、U6 は重ねて検査する。
- 週確定後の反映が 2 秒に収まらなかった場合の変更（通知への切り替え）は、U6 の測定の結果が出てから決める。先に変えない（Q6 の A）。
