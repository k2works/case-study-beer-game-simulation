# 可観測性の要件 - U6 u6-nfr-verification

U6 が出す検証の結果を、後から読めるように残すための要件です。アプリケーションの運用の監視（メトリクス、警告のしきい値）は、U1 の最小の方針を引き継ぎ、後の Operation で決めます。ここでは、検証そのものの結果の記録だけを定めます。元の要件は `requirements.md` の NFR9（監査性）の考え方に沿います。

出典: `requirements.md`（NFR3、NFR9）、`unit-of-work.md`（U6）、`nfr-requirements-questions.md`（Q3、Q4、Q5、Q7）。

## 番号の付け方と、上流の NFR との対応

`NFRn.m` の詳細番号は、Unit ごとに 1 から振る（U1〜U5 と同じ慣例）。U6 の `NFR9.x` は、上流の NFR9（ゲーム設定、役割変更、代理入力、週確定、停止、再開、終了の履歴を追跡できる監査性）そのものではなく、U6 の検証の結果を後から追跡できるようにする要件である。上流の NFR9 の履歴の機能は u3-facilitation が作り、U6 は検証しない。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR9.1 | 負荷試験は、終了時に結果の要約を機械で読める形（JSON）で出力する。要約には次を含める: 実行の日時、コミットの識別子、設定（チーム数、画面の数、時間、種）、実行環境の情報（NFR4.4）、入力の確定・週の確定の反映・取り直しの応答時間（50、95、99 パーセンタイル）と件数、サーバーの異常の件数（NFR3.4）、整合性の検査の結果（NFR2.1）、閾値ごとの合否 | 要約の形の試験。必須の項目が含まれること |
| NFR9.2 | 10 分間の本試験の要約は、ワークフローの成果物として 30 日間保存する（検査した branch とコミットを要約に含める。NFR9.1）。本試験が失敗した場合は、ワークフローの実行が失敗として見え、GitHub の通知で気づける。専用の警告の仕組みは、U6 では作らない | ワークフローの定義の検査。保存の日数の設定 |
| NFR9.3 | 画面の試験が失敗したときは、Playwright のトレースと画面の画像を成果物として保存する（保持 7 日。試験用以外の接続先では保存しない。`security-requirements.md` の NFR6.1、NFR7.2）。成功したときは保存しない | ワークフローの定義の検査 |
| NFR9.4 | リリース前の確認票（1 つ前の世代のブラウザと実機の Safari。NFR10.2）の結果は、確認した日、確認した人、ブラウザの版、合否と所見を、リポジトリ内の文書に記録する | 確認票の様式があること。リリースのたびに記録が追加されること |

## 根拠と設計への影響

- 要約を機械で読める形にするのは、後で結果を比較（傾向の変化の確認）できるようにするためである。新しい仕組み（メトリクスの保存先、ダッシュボード）は足さず、ワークフローの成果物で足りる範囲にとどめる。
- 失敗の検知は、GitHub の標準の通知に任せる。警告のしきい値と通知先の設計は、後の Operation に渡す（U1 の Q4 の方針、U5 の Q4 の A と同じ）。
- 確認票の記録は、自動で確かめられない範囲（1 つ前の世代、実機の Safari）の根拠として残す。記録がなければ、「確かめた」と言えない。
