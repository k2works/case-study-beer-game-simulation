# セキュリティの設計 - U6 u6-nfr-verification

U6 は新しい認証・認可の機能を足しません。ここで設計するのは、U6 が作る試験の仕組みと CI が、守るべき環境（本番、staging）と情報（資格情報、個人情報）を傷つけないための防御です。

出典: `security-requirements.md`（NFR6.1〜NFR6.4、NFR7.1、NFR7.2）、`reliability-requirements.md`（NFR2.2）、`observability-requirements.md`（NFR9.2、NFR9.3）、`tech-stack-decisions.md`、`contract-summary.md`（C1 の認可）。

## 番号の付け方

U6 の `NFR6.x`、`NFR7.x` は、上流の NFR6、NFR7 そのものではなく、U6 の試験と CI を安全に動かすための要件である。上流の部分（参加コードの強度、権限の検証、保持と削除）は u1-walking-skeleton、u4-access-recovery、u5-results-retention が担当する。

## 脅威と防御の対応

| 脅威 | 防御（多層） | 対応する要件 |
| :--- | :--- | :--- |
| 負荷試験や画面の試験を、うっかり本番や staging に向けてしまう | (1) **既定の動作は 1 つ**: 試験のスクリプトが自分でアプリケーションと使い捨てのデータベースを `localhost` に起動する。接続先の指定を受け付けるのは、外部接続のモード（`VERIFY_TARGET_URL`、`VERIFY_DATABASE_URL` を明示した場合）だけである。(2) 接続先の検査（`TargetGuard`）が、**スクリプトが組み立てた最終の接続設定**（アプリケーションの URL、データベースの接続先のホスト、`host=` パラメーターを含む接続文字列の解析結果）を実行前に検査し、`localhost`（`127.0.0.1`、`::1` を含む）以外なら、許可の設定（`VERIFY_ALLOW_REMOTE=1`）がない限り、何も送らず終了する。(3) 許可して `localhost` 以外を指した場合、成果物（トレース、画面の画像）の保存設定を強制的に無効にする | NFR6.1、NFR7.2 |
| 試験用の接続の設定が、本番の接続情報を読み込む | 試験は、アプリケーションの設定ファイルや `.env` を読まない。起動する子プロセス（アプリケーション、Playwright の試験の実行器）には、**許可リスト方式で選んだ環境変数だけ**を渡し、実行環境の `PG*`、`DATABASE_URL` などの外部の接続情報を継承させない（環境を空から組み立てる）。検査は、子プロセスに渡す最終の環境と接続設定に対して行う。試験用の環境変数名は接頭辞 `VERIFY_` で分ける | NFR6.1 |
| CI のトークンの権限が広い | ワークフローの最上位に `permissions: contents: read` だけを置く。ジョブごとの追加は行わない（U6 の CI にはデプロイも OIDC もない）。成果物のアップロードは、実行のトークンで足りるため追加の権限を要しない。シークレットは使わない。試験用のデータベースのパスワードは、使い捨てのサービスコンテナのための固定値で、シークレットではない | NFR6.2 |
| 生成した資格情報（参加コード、進行役用コード、復帰用 token）が、ログや要約に漏れる | (1) 資格情報を保持する型（`Secret`）を作り、文字列化、JSON 化、検査の出力のいずれも `[秘匿]` を返す。(2) 試験のスクリプトのログと要約は、許可リスト方式の項目だけを書く（`observability-design.md`）。(3) 要約とログに生成した値が含まれないことを、実際に資格情報を生成する試験で確かめる | NFR6.3 |
| 失敗時の成果物（トレース、画面の画像）に資格情報が写る | 伏せる手段には頼らない（標準の設定で確かめられていない）。代わりに 3 点で危険を抑える。(1) 資格情報は使い捨てのデータベースの中でだけ有効で、試験の終了時に破棄される。(2) 保持は 7 日。(3) `localhost` 以外を指した実行では、保存しない。さらに、負荷試験の中の実ブラウザの測定（`performance-design.md`）は、負荷試験と同じプロセスの中で Playwright のライブラリを使い、**資格情報をプロセスの外へ渡さない**（環境変数にも標準出力にも出さない）。トレース、画面の画像、動画は取らず、試験の実行器とレポーターは使わない。ページやブラウザのエラーは、許可リスト方式の事象名と件数だけをログに出し、Playwright のエラー文の全文やページの内容は出さない | NFR6.3、NFR7.2 |
| 画面の試験（Playwright の試験の実行器）の失敗時の出力に資格情報が出る | 実行器のエラー文や失敗時の追加の出力には、画面に出た参加コードなどが含まれうる。試験のデータは使い捨てで、終了時に無効になるため（上と同じ理由）、CI のログに出ても使えない。これは NFR7.2 の保持の考え方で扱い、「スクリプトが書く出力」（NFR6.3）の対象には含めない。ただし、負荷試験のスクリプト（LoadRunner）は、自分の出力に資格情報を書かない | NFR6.3、NFR7.2 |
| 個人情報の持ち込み | 試験のデータは生成した架空の値にする。表示名は、種付きの規則で作る（例: 「試験チーム 03 発注役」）。実在の個人や組織を指す語を使わない。生成規則の単位試験で、すべての表示名がこの規則に合うことを確かめる | NFR7.1 |
| 新しい依存による供給網の危険 | Playwright、axe-core とその連携は、`dependencies` ではなく `devDependencies` に入れ、版は範囲指定でなく固定（`^` や `~` を使わない）する。ロックファイルに記録する。導入前に配布元と既知の脆弱性を確かめ、`npm audit` の結果を記録する。本番の成果物（`dist/`、コンテナ）の作成は `npm ci --omit=dev` で行い、試験の依存が含まれないことを `npm ls --omit=dev` の検査で確かめる | NFR6.4 |
| 負荷試験が負荷として扱われ、本番の防御（試行回数の制限）を巻き込む | 契約 C1 の `rate_limited` は無効な資格情報の試行だけを数える。負荷試験は有効な資格情報だけを使うため、制限に当たらない。試験が `rate_limited` を受け取ったら、その応答を失敗として数え、原因（無効な資格情報の送信）を結果に記録する | NFR3.4 |

## 接続先の検査（TargetGuard）の設計

| 入力 | 判定 | 結果 |
| :--- | :--- | :--- |
| アプリケーションの URL | ホスト名が `localhost`、`127.0.0.1`、`::1` のいずれか | 合格 |
| データベースの接続先 | ホスト名が同じ集合に含まれる、または Unix ドメインソケット | 合格 |
| 上のいずれでもない、かつ `VERIFY_ALLOW_REMOTE` が `1` でない | - | 実行前に終了コード 2 で失敗。理由は「接続先が試験用でない」と、検査した項目名だけを出す（URL の値は出さない） |
| 上のいずれでもない、かつ `VERIFY_ALLOW_REMOTE=1` | - | 実行を許可し、成果物の保存を無効にし、要約の欄に「外部接続で実行」と記録する |

検査は、通信を開始する前に 1 度だけ実行し、その結果を実行の設定に固定する。Playwright の設定も同じ検査の結果を参照して、トレースと画像の設定を決める（別々に判定しない）。

## CI の定義の検査

ワークフローの定義を読む試験（Vitest。YAML を解析する）で、次を機械的に確かめる。

- 最上位の `permissions` が `contents: read` だけである。ジョブに `id-token` や `contents: write` がない。
- `secrets.` の参照がない。デプロイ用の環境（`environment:`）の指定がない。
- 成果物のアップロードの `retention-days` が、トレースと画像は 7、短い負荷試験の要約は 7、本試験の要約は 30 である。トレースと画像のアップロードは `if: failure()` の条件を持ち、本試験の要約のアップロードは成功でも失敗でも保存する条件（`if: always()`）を持つ。
- `schedule` の取得が `ref: develop` を明示している。`workflow_dispatch` が、検査する branch の入力（既定は `develop`）を持つ。
- Playwright の設定が `retries: 0` で、`localhost` 以外を指したときにトレースと画像を取らない設定になる（接続先の検査の結果を参照する）。
