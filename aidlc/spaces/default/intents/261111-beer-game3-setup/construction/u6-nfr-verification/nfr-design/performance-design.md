# 性能の設計 - U6 u6-nfr-verification

U6 は、アプリケーションの性能を上げるのではなく、完成した画面とサーバーの性能を「測って合否を決める」仕組みを作ります。ここでは、負荷を生成して測る側（負荷試験のスクリプト）の設計と、画面の品質の検査（キーボード、axe-core、日本語表示）の性能上の配慮を定めます。アプリケーション側の応答の設計は U1 の `performance-design.md` が担当し、U6 は変えません。

出典: `performance-requirements.md`、`scalability-requirements.md`、`reliability-requirements.md`、`tech-stack-decisions.md`、`nfr-design-questions.md`（Q1 の A、Q2 の A）。

## 番号の付け方

`NFRn.m` は U6 の要件の番号である（U1〜U5 の同番号とは別の要件）。Unit をまたぐ参照には Unit 名を添える。

## 測定の設計（負荷試験のスクリプト）

| 設計項目 | 決定 | 理由 | 対応する要件 |
| :--- | :--- | :--- | :--- |
| 実行の単位 | リポジトリ内の 1 本の Node.js スクリプト。設定値（チーム数、画面の数、時間、確定の頻度、種、最大想定の区間の有無）だけを変えて、短い試験（1 分）と本試験（通常負荷 10 分 ＋ 最大想定の区間）を表す。設定の既定は要件の表の値 | スクリプトが 1 本なら、短い試験が通って本試験で落ちる食い違いが起きない | NFR3.5、NFR4.3 |
| 仮想の利用者 | 1 画面 = 1 つの非同期の繰り返し。1 秒周期で状態を取り直す（U1 の画面と同じ周期）。周期は「k 回目の予定時刻 = 開始時刻 + k 秒」で刻み、**取り直しを飛ばさない**。前の応答が遅れて予定時刻に送れなかった取り直しは、前の応答を受け取った直後に送る。取り直しの応答時間の標本は、**実際の送信時刻でなく予定時刻**から応答の受信までを測る（遅れて送った分の待ちも標本の値に含める）。予定の回数と送った回数の差（遅れの累積）は `behind` として別に数える | 負荷の形を実際の画面に合わせる。サーバーが遅いほど取り直しが減り、遅い標本も減って 95 パーセンタイルが良く出る誤り（応答待ちで測定が止まる coordinated omission）を避ける。予定時刻から測れば、遅れた分も標本に残る | NFR3.3、NFR4.1 |
| 失敗とタイムアウト | 要求のタイムアウトは 5 秒。タイムアウトと接続の失敗は、標本から落とさず、**標本の値を 5 秒（上限値）として百分位に入れ**、同時に `errors` の `timeout`、`connect` として数える。NFR3.4 のサーバーの異常（5xx、503）と同様、`timeout` と `connect` も 0 件を合否の条件にする。週確定後の反映は、新しい週が 10 秒たっても現れなかった画面を、標本の値 10 秒として入れ、`reflectionMissing` として数える（件数は記録する。合否は、その標本の値 10 秒が百分位に入ることで決まる） | 生き残った標本だけで合否が決まるのを避ける | NFR3.3、NFR3.4、NFR3.2 |
| 通信 | Node.js 標準の `fetch`（接続の再利用あり）。依存は増やさない | 追加の依存を持たない（`tech-stack-decisions.md`） | NFR3.5 |
| 時刻の取得 | すべての測定は、負荷試験の 1 つのプロセスの中の `performance.now()`（単調時計）で行う。実ブラウザの測定もこのプロセスの中で動かすため（下の節）、壁時計（`Date.now()`）は測定に使わない | 時計の巻き戻りと、プロセスをまたぐ時計の差の影響を受けない | NFR3.2 |
| 入力の確定の応答 | 確定の要求を送ってから応答の受信までを 1 標本とする | NFR3.1 の定義 | NFR3.1 |
| 反映の時間（仮想の利用者） | 進行役の「週の確定」の応答を受け取った時刻から、同じチームのほかの 4 画面それぞれの取り直しの応答が新しい週を返した時刻（応答の受信時刻）までを 1 標本にする。新しい週の判定は、応答の週の番号が確定前より進んだことで行う。標本数は、仮想のチーム 14 × 10 週 × 4 画面 = 560 件（本試験） | 取り直しの周期（1 秒）が下限の遅れとして含まれる実際の体験に近い | NFR3.2 |
| 取り直しの応答 | 各取り直しの要求から応答の受信までを 1 標本とする | NFR3.3 の定義 | NFR3.3 |
| 百分位 | 最近順位法（昇順に並べた n 件の `ceil(p × n)` 番目）で 50、95、99 パーセンタイルを計算する。標本の配列は全件を保持する（1 本試験で数万件。メモリは問題にならない） | 計算の定義を固定し、結果を再計算で再現できる | NFR9.1 |
| 立ち上げ期間 | 開始から 10 秒の標本は、集計から除く。ただし件数と別の欄に記録する | 接続の確立と JIT の影響を除く | NFR3.5 |
| 区間の分け方 | 標本に区間の名前（`normal`、`peak`）を付けて集計を分ける。最大想定の区間は、通常負荷の 10 分の後に続けて動かす別の区間とし、追加の取り直し専用の画面（各チーム 13 台、合計 195 台）を加える。確定の頻度は通常負荷と同じ | NFR4.1 の 10 週を保ったまま、NFR3.3 の最大想定（270 台）を別の区間として測る（要件の「10 分間の本試験の中の別の区間」を、本試験の実行の中の続きの区間として解釈する。診断欄に記録） | NFR3.3、NFR4.2 |
| 測定器の飽和の検出 | 負荷を生成するプロセスのイベントループの遅れ（`monitorEventLoopDelay`）の 99 パーセンタイルを記録する。100 ミリ秒を超えたら、その実行は「無効」と判定して失敗として扱い、アプリケーションの性能の結果とは分けて報告する | 測定器が詰まると、アプリケーションが遅く見える誤判定が起きる。原因の切り分けを機械で行う | NFR3.6、NFR4.4 |
| 合否 | 閾値ごとに判定する。短い試験は、標本が多い指標（取り直し、サーバーの異常 0 件、整合性）だけを合否に使い、入力の確定と反映は記録のみ。本試験はすべてを判定する | 標本数が少ない指標で判定すると外れ値 1 件で決まる | NFR3.5 |

## 性能の予算

| 指標 | 通常負荷 | 最大想定 | 短い試験で合否に使うか |
| :--- | :--- | :--- | :--- |
| 入力の確定の応答（95 パーセンタイル） | 1 秒以内 | 通常負荷と同じ頻度のため判定は通常負荷の区間のみ | 使わない（記録のみ） |
| 週確定後の反映（仮想の利用者。95 パーセンタイル） | 2 秒以内 | - | 使わない（記録のみ） |
| 週確定後の反映（実ブラウザ 1 チーム。95 パーセンタイル） | 2 秒以内（本試験のみ。合否に使う） | - | 実行しない |
| 取り直しの応答（95 パーセンタイル） | 500 ミリ秒以内 | 1 秒以内 | 通常負荷の取り直しのみ使う |
| サーバーの異常（5xx）、`timeout`、`connect`、`reflectionMissing` | それぞれ 0 件 | 0 件 | 使う（`reflectionMissing` は記録のみ。反映の標本が少ないため） |
| 測定器のイベントループの遅れ（99 パーセンタイル） | 100 ミリ秒以内（超えたら無効） | 同じ | 使う |

## 週確定後の画面反映の測り方（Q1 の A）

仮想の利用者による測定は「応答までの時間」で、ブラウザが画面を描き直す時間を含まない。そこで、本試験の間だけ、実際のブラウザを 1 チーム分（5 画面）、負荷の中で動かして、描画までの時間を測る。

| 項目 | 設計 |
| :--- | :--- |
| 対象 | 15 チームのうち 1 チームを、仮想の利用者ではなく実際の Chromium（5 画面）で見せる。したがって仮想のチームは 14（通常負荷の画面は 70 台）で、実ブラウザの 5 台と合わせて 75 台（最大想定は 270 台）は変わらない |
| 動かす場所 | 別の試験のプロセスにせず、**負荷試験のスクリプトの同じプロセスの中で、Playwright のライブラリ（`chromium.launch`）を直接使う**。Playwright の試験の実行器とレポーターは使わない。資格情報はプロセスの外へ渡さない（環境変数にも標準出力にも出さない）。実行に必要な Chromium は、本試験のジョブでだけ導入する |
| 駆動 | そのチームの 4 役割の入力の確定と「週の確定」は、ほかの 14 チームと同じく、LoadRunner が `SeededPlan` に従って HTTP で行う（進行役の画面のボタンの操作は含めない。画面の操作は NFR8.1、NFR10.1 の試験が確かめる）。入力の確定の標本は 15 チームすべてから取る。実ブラウザの 5 画面は、画面を開いて実際の取り直しを動かし、表示を観察するだけである |
| 観察 | 各画面のページに、週の表示の変化を検出する小さな観察の仕組み（`MutationObserver`）を入れ、検出したらノード側の関数（`page.exposeFunction`）を呼ぶ。ノード側の関数が受け取った時刻を `performance.now()` で記録する。測定の始点は、LoadRunner が「週の確定」の応答を受け取った時刻（同じ `performance.now()`）である。呼び出しの経路の遅れ（数ミリ秒）は 2 秒の判定に対して無視でき、保守的（遅く出る側）である |
| 標本 | 10 週 × 5 画面 = 50 件。新しい週が 10 秒たっても現れなかった画面は、標本の値を 10 秒として入れ、`reflectionMissing` として数える（`thresholds` の判定には、その標本の値が入る） |
| 返し方 | `Recorder` へ関数の呼び出しで直接返す（同じプロセス）。要約の `phases.normal` に、実ブラウザの反映（件数、50、95、99 パーセンタイル）を別の欄で出す |
| 判定 | 50 件の最近順位法の 95 パーセンタイル（48 番目）が 2 秒以内であることを、本試験の合否の閾値（`reflectionBrowserP95`）にする。超えたら `verdict` は `fail`。標本が少ないため、NFR3.2 の主の判定は仮想の利用者の反映（560 件。同じ 2 秒の閾値）で、実ブラウザの判定は画面の描画の遅れを見張る補助である。ブラウザ側だけが超えた場合は、描画の遅れとして原因を切り分ける（NFR3.6）。再実行で通ったことを合格にしない |
| 負荷への影響 | ブラウザは 5 画面で、仮想の利用者より重いが、同じ機械に同居する。測定器の飽和の検出（上の表）で影響を監視し、飽和したら実行は「無効」になる |
| 記録の安全 | 資格情報がプロセスの外に出ない。トレース、画面の画像、動画は取らない。ページのエラーは許可リスト方式の事象名と件数だけをログに出し、ページの内容や Playwright のエラー文の全文は出さない（`security-design.md`） |

## 画面の品質の検査の対象（NFR8.1、NFR8.2、NFR8.4、NFR11.1、NFR11.2）

### キーボードだけの通し試験（NFR8.1）の工程

マウスを使わず、キーボードだけで次の順に完了する。各工程は表示の状態の変化を待って進む（固定の待ちを使わない。`reliability-design.md`）。

| 工程 | 画面 | 操作 |
| :--- | :--- | :--- |
| 1 | ゲームの作成 | 設定を入力してゲームを作成する |
| 2 | 参加 | 進行役用コードで入り、4 役割の参加者が参加コードで参加する（別のブラウザの文脈で 4 人分） |
| 3 | ロビー | 役割の割当てを確認し、ゲームを開始する |
| 4 | プレイ | 各役割が発注量を入力して確定する |
| 5 | 進行管理 | 週を確定する |
| 6 | 結果 | 終了後に結果を表示し、出力を開始する |

### 画面 × 状態の検査の対象（axe-core。NFR8.2、NFR8.4、NFR11.1、NFR11.2）

| 画面 | 検査する状態 |
| :--- | :--- |
| ゲームの作成 | 通常、入力エラー |
| 参加 | 通常、無効な資格情報のエラー |
| ロビー | 通常（役割の割当て中、未割当てあり） |
| プレイ | 通常（入力済みと未入力）、一時停止、終了、エラー（接続の失敗や無効な資格情報） |
| 進行管理 | 通常、一時停止、終了、エラー |
| 結果 | 結果の表示、出力の注意書き（出力の導線に日本語の説明が常に表示されること。NFR11.2）、終了後 |

状態は、公開の API で作る試験用の補助で用意し、各画面と状態の組を axe-core の検査の対象にする（色のコントラスト 4.5:1 を含む）。同じ組で、状態を示す要素の文字またはアクセシブルな名前が空でないこと（NFR8.4）と、画面の文言に英語の文が混じらないこと（NFR11.1）を確かめる。

## 画面の品質の検査の性能上の配慮

| 検査 | 配慮 | 対応する要件 |
| :--- | :--- | :--- |
| ブラウザごとの実行（Q2 の A） | キーボードだけの通し試験と主要な操作の試験は、4 つのブラウザを並列のジョブで動かす。axe-core、状態の表示、色の比の計算、日本語表示の検査は Chromium の 1 ジョブにまとめる。CI の時間は、最も長いジョブで決まる | NFR8.1、NFR10.1 |
| 検査の状態の作り方 | 状態（エラー、一時停止、終了、結果、出力の注意書き）は、画面の操作で毎回作らず、試験用の補助（公開の API で状態を作る関数）で短い手順で作る。画面の操作の通しは NFR8.1 の試験が別に確かめる | NFR8.2、NFR8.4 |
| 色の比の計算 | 色の値から比を計算する純粋な関数で、ブラウザを使わず Vitest で動かす（ミリ秒単位） | NFR8.3 |
| 日本語表示の検査 | 文言の一覧は Vitest で（ブラウザなし）、表示された文言は Chromium のジョブの中の画面の試験で確かめる | NFR11.1 |
