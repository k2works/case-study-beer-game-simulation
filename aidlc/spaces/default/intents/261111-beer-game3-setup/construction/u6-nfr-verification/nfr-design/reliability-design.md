# 信頼性の設計 - U6 u6-nfr-verification

U6 に可用性や復旧の目標はありません（上流の NFR5 は u4-access-recovery が担当）。ここで設計するのは、検証が「同じ入力から同じ判定が出る」「負荷の後にデータが壊れていない」「試験が環境を汚さない」「不安定な試験を成功として扱わない」ことです。

出典: `reliability-requirements.md`、`performance-requirements.md`、`security-requirements.md`、`tech-stack-decisions.md`。

## 番号の付け方

U6 の `NFR1.x`、`NFR2.x` は、上流の NFR1（再現性）、NFR2（整合性）の検証を、全体の負荷と CI で重ねて行う部分である。計算そのものの正しさ（golden test。u2-weekly-rules）と、週確定の原子性の作り（u1-walking-skeleton、u2-weekly-rules）は、各 Unit が担当する。

## 再現性（NFR1）

| 設計 | 内容 | 対応する要件 |
| :--- | :--- | :--- |
| golden test の位置づけ | U2 が作る golden test は、通常の単位試験の一部として `npm run verify` に含まれる。CI の必須のジョブ（`verify`）がこれを動かし、失敗したら統合させない（保護された branch の必須のチェックに指定する） | NFR1.1 |
| 種付きの乱数 | 負荷試験の意思決定は、種から決める自前の小さな擬似乱数生成器（32 ビットの状態を持つ生成器。依存を増やさない）で作る。チームごとに「種 + チームの番号」から別の列を作り、チーム間で互いに影響しない | NFR1.2 |
| 要求の列の再現 | 「要求の列」は、時刻や応答に依存しない項目（チーム、週、役割、意思決定の値）だけで定義する。同じ種と設定から作った列が、2 回の生成で一致することを単位試験で確かめる。実行の間隔と応答の時間は変わってよい | NFR1.2 |
| 失敗の再現 | 要約に種と設定を記録し、同じ種で再実行すると、同じ内容の要求の列で調べ直せる | NFR1.2、NFR9.1 |

## 整合性（NFR2）

### 負荷の後の整合性の検査

| 設計 | 内容 |
| :--- | :--- |
| 入口 | 負荷をかけるのは HTTP の公開の面だけ。整合性の検査だけが、試験用のデータベースへの読み取り専用の接続で SELECT を行う（`ConsistencyChecker`）。応答の投影は役割ごとに見える範囲が違い、全ゲームの全週を確かめられないため |
| 読み取り専用の担保 | 接続のセッションを `default_transaction_read_only=on`（接続オプション）にし、検査を `BEGIN READ ONLY` のトランザクションの中で行う。書き込みを試みる試験（INSERT を投げて PostgreSQL のエラー `25006` を受け取ること）を単位試験で確かめる |
| 検査の内容 | 各ゲームについて、(1) 確定済みの週の番号が 1 から欠けず連続している。(2) 同じ週が二重に確定されていない（週ごとの確定の件数が 1）。(3) 入力の確定の応答で成功を返した値が、保存されている |
| 記録の突き合わせ | (3) のため、`Recorder` が、成功応答を受け取った入力（ゲーム、週、役割、値）を台帳として持ち、終了時に保存済みの値と突き合わせる。台帳に載らなかった保存（応答前に切れた要求）は、保存されていても異常とは扱わない（冪等な再送で扱われる範囲） |
| 結果 | 崩れが 1 件でもあれば、負荷試験は失敗。崩れたゲームと週の識別子（資格情報でない）を要約に出す |
| 構造への依存 | 検査の SQL は、1 つの部品（`schema-adapter`）に閉じ込める。移行でテーブルの構造が変わったら、この部品だけを更新する。移行を足したときに検査が壊れることは、短い負荷試験（CI）がすぐに検知する |
| 切断からの復帰（NFR5.1） | 負荷の途中で、一部の仮想の利用者の取り直しを数秒止めて再開する動作（切断の模擬）を入れる。再開後も、確定済みのデータが失われていないことを同じ検査で確かめる。復帰用 token の有効期間の検証は含めない（u4-access-recovery） |

### 環境を汚さない起動と破棄

| 設計 | 内容 |
| :--- | :--- |
| 責任 | 負荷試験と画面の試験のスクリプト自身（`Lifecycle` 部品）が、起動と破棄を行う。CI のワークフローは、PostgreSQL 18 のサービスコンテナを用意するだけ |
| 起動 | データベースサーバーの管理用の接続で、実行ごとに一意の名前（`bg3_verify_<実行の識別子>`）の使い捨てのデータベースを作る。アプリケーションの移行を適用し、アプリケーションを空いているポート（ポート 0 で OS に選ばせる）の子プロセスとして起動し、健全性の確認（`/health` など公開の面）が通るのを待ってから試験を始める。待ちは上限付き（失敗として終了） |
| 破棄 | `finally` で、アプリケーションの子プロセスを止め（まず SIGTERM、5 秒待って SIGKILL）、`DROP DATABASE ... WITH (FORCE)` で使い捨てのデータベースを削除する。`SIGINT`、`SIGTERM`、未処理の例外でも同じ破棄の処理を通す |
| 残りの掃除 | 起動時に、`bg3_verify_` で始まる名前のうち、実行の識別子に埋め込んだ時刻が 1 時間より古いデータベースを削除する。ほかの実行中の試験を巻き込まないため、新しいものは触らない。ローカルでの強制終了の残りが、次の実行に影響しないようにする |
| 検査 | 失敗を注入した実行（アプリケーションの起動の失敗、試験の途中の例外、中断）のあとで、残ったプロセスと `bg3_verify_` のデータベースがないことを確かめる試験を用意する |

## 試験の信頼性（NFR2.3）

| 設計 | 内容 |
| :--- | :--- |
| 固定の待ちの禁止 | Playwright の試験で `page.waitForTimeout` と、固定の `setTimeout` による待ちを使わない。ESLint の規則（`no-restricted-properties`）で禁止し、CI の lint で落とす。代わりに表示の状態を待つ（`expect(...).toBeVisible()`、`expect.poll`、`waitForFunction`） |
| 時刻の注入 | 時刻に依存する振る舞い（一時停止の経過など）は、Playwright の `page.clock` またはアプリケーションの時計の注入の口で時刻を進めて確かめる |
| 再実行の禁止 | Playwright の設定で `retries: 0` を固定する。CI のワークフローにも再実行の仕組みを入れない。失敗した試験は、再実行でなく原因を直す。この設定を検査する試験（設定を読んで `retries` が 0 であること）を置く |
| 並列の安全 | ブラウザの試験は、試験ごとに独立したゲームを作る（資格情報も試験ごと）。試験の間で状態を共有しない |

## 実行結果の分類

| 分類 | 条件 | CI での扱い |
| :--- | :--- | :--- |
| 合格 | 合否に使う閾値がすべて満たされ、整合性の検査が通り、測定器が飽和していない | 成功 |
| 不合格 | 合否に使う閾値のどれかを超えた、または整合性の検査が失敗した | 失敗 |
| 無効 | 測定器の飽和、起動の失敗、設定の検査の失敗など、アプリケーションの性能を判定できない | 失敗（結果に「無効」と理由を明示し、アプリケーションの不合格と区別する） |

終了コードは、合格 0、不合格 1、無効 2 とする。

**短い負荷試験（`load-smoke`）が「無効」で失敗したとき**: 必須のチェックのため、統合は止まる。原因（測定器の飽和、起動の失敗、実行環境の揺れ）を要約の `harness` と `environment` で切り分け、原因の側（負荷のスクリプトの設定、アプリケーション、実行環境）を直す。同じコミットでの再実行は、環境の影響を調べるための測定として行ってよいが、**通ったことを合格の根拠にしない**（NFR2.3、`performance-requirements.md` の NFR3.5 と同じ方針）。最初の失敗の要約は、原因の記録として残す。実行環境の揺れが原因と判断できる根拠があるときは、その根拠を記録したうえで実行環境（機械の仕様や同居の構成）を見直し、閾値を緩めない。
