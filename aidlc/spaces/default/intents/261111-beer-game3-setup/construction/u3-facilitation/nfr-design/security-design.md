# セキュリティの設計 - U3 u3-facilitation

`security-requirements.md`（NFR6.1〜NFR6.7、NFR7.1）を満たす設計です。コードと token の発行、鍵付きハッシュと暗号化、CSP と HSTS、入口の共通の検証は、U1 の `security-design.md` を引き継ぎます。U3 は、進行役の強い操作の認可、入れ替えの token の扱い、投影の境界を設計します。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR6.1 進行役の認可 | AccessControl の `authorize(principal, action)` に、進行役だけの操作の表を持つ（pause、resume、end、replaceAssignee、submitDecisionAsFacilitator、viewDashboard、viewHistory）。入口は、経路ごとにこの判定を通してから GameSession を呼ぶ。参加者の token、観察者用コード、無資格は 403。終了の reason が finalWeek と autoEnd は、入口の経路を持たず、GameSession の内部の関数（週の確定の保存と、U5 の定期処理）からだけ呼ばれる。外部の要求の本文に reason を取らず、入口は reason を facilitator に固定する |
| NFR6.2 token の平文 | 入れ替えは、暗号論的乱数 16 バイト以上で token を作り、ハッシュだけを保存する。平文は、入れ替えの応答の本文でだけ返し、応答に `Cache-Control: no-store` を付ける。入れ替えは `Idempotency-Key` を使わないため、平文を冪等性の記録に残さない。履歴の detail は、参加者のラベルと識別子だけを持つ。画面は、token を表示用のコンポーネントの状態にだけ置き、閉じたら破棄する。`localStorage`、URL、ログには出さない |
| NFR6.3 失効 | 入れ替えのトランザクションで、旧担当者の token に `revoked_at` を設定し、新しい参加者と token を作る。1 回のコミットで行うため、失効だけが残る状態も、新しい token だけが残る状態も作らない。以後の要求の判定は、`revoked_at` が null でない token を拒否する（403）。入口の認可は占有の前に行うため、入れ替えのコミットより前に認可を通った旧担当者の入力が、占有の待ちの後に処理される競合がありうる。これを防ぐため、参加者の入力は、占有の中で「入力者が現在その役割に割り当てられていること（RoleAssignment が存在すること）」と「その token が失効していないこと」を再検査する。合わなければ 403 `forbidden` で拒否し、decision を書かない。判定の順は、入口の認可（token と種類）、占有の取得、再送の照合、状態の検査、割当てと token の再検査、入力の検証 |
| NFR6.4 投影の境界 | 投影は GameSession の集約を直接返さず、AccessControl の `project` が、呼び出した人の種類ごとの専用の型へ変換する（ADR-002）。進行役の投影の型は、入力値の項目を持たず、入力済みの真偽だけを持つ。参加者の投影の型は、自分の役割の入力者のラベルを持ち、他の役割の担当者の項目を持たない。型に項目が無いため、誤って含めることができない |
| NFR6.5 入力の検証と出力 | 入れ替えの表示名（1〜40 文字）、旧担当者の識別子（uuid）、役割（列挙）は zod で検証する。画面は React の既定のエスケープで表示し、HTML として解釈しない。ラベルは「表示名 #参加順」の文字列として、サーバーで組み立てる |
| NFR6.6 拒否のログ | 入口の共通のエラー処理が、403 と 409 を情報の水準で記録する。出す項目は許可した一覧（種類、操作、理由、要求の識別子、ゲームの識別子）だけで、一覧に無い項目は出力されない（許可リスト方式、U1） |
| NFR6.7 ログの許可リスト | 構造化ログは、認可ヘッダ、リクエストの本文、レスポンスの本文を、出力の対象にしない。出力する項目を許可リストで固定する。入れ替えを成功させた後のログを調べる自動試験で、token と進行役用コードの文字列が無いことを確かめる |
| NFR7.1 履歴の個人情報 | 履歴の detail は zod の厳密な型（未知の項目を拒否）で検証してから保存する。自由な文章の項目を持たず、表示名はラベルの一部としてだけ入る。`operation_log_entries.game_id` は games への外部キーとし、`ON DELETE CASCADE` で、ゲームの削除と同時に消える（実装の削除は U5） |

## 試験（NFR6.3 の確かめ方への追加）

- 入れ替えと、旧担当者の入力を同時に送る試験を持つ。どちらの順で占有を取っても、入れ替え後に旧担当者の decision が書かれないこと、decidedByParticipantId が割当てのない参加者にならないことを確かめる。
- 入れ替え後の旧 token での入力、状態の取得が 403 になることを確かめる。

## 脅威への対応

| 脅威 | 設計 |
| :--- | :--- |
| 参加者による進行役の操作 | NFR6.1 の操作の表。経路ごとに判定を通す |
| reason の外部からの指定による不正な終了 | 入口が reason を固定し、finalWeek と autoEnd の経路を公開しない |
| 入れ替えた旧担当者の継続操作 | NFR6.3。同じコミットで失効する |
| 進行管理からの入力値の漏えい | NFR6.4。型に項目が無い |
| 発行した token のログやキャッシュからの漏えい | NFR6.2、NFR6.7 |
| 履歴の改ざん | 更新と削除の処理を持たない（`observability-design.md` の NFR9.2） |
