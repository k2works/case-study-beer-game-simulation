# 性能の設計 - U3 u3-facilitation

`performance-requirements.md`（NFR3.1〜NFR3.4）を満たす設計です。ゲーム単位の行の占有、接続プール、1 秒の取り直し、確定の応答での即時表示は、U1 の `performance-design.md` を引き継ぎます。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR3.1 操作の応答 | 一時停止、再開、終了、入れ替え、代理入力は、いずれも「ゲームの行を占有 → 状態を検査 → 数行の更新と履歴 1 行の追記 → コミット」の 1 トランザクションで行う。更新は集約の一部の数行に限り、占有の時間は短い。入れ替えの token の発行（乱数 16 バイトとハッシュ）はメモリ上の計算で、占有の時間に占める割合は小さい。計算の重い処理を占有の中に置かない |
| NFR3.2 進行管理の投影 | 読み取り専用で `REPEATABLE READ` のトランザクション（`BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY`）を開き、ゲームの行、当週の WeekRecord（4 行）、PipelineSlot（現在の状態の導出に必要な分）、Participant と RoleAssignment を読み、メモリ上で投影を作る。トランザクションの最初の文で時点が固定されるため、読み取りの途中で週の確定や入れ替えがコミットされても、投影は 1 つの時点の一貫した見え方になる（古い currentWeek に新しい週の記録が混ざらない）。行の占有はしない。入力値は投影に入れず、入力済みかどうかだけを導く。参加者の投影の取得も同じ形で読む |
| NFR3.2 履歴の取得 | `operation_log_entries` を (game_id, sequence) の索引で昇順に 1 回読む（1 文の読み取りで、文の中は一貫した見え方）。ページングなしで全件を返す。1,000 件でも 1 行は小さく（数百バイト）、応答は 1 MB 未満に収まる想定。応答は gzip で圧縮する（入口の共通設定） |
| NFR3.3 反映 | 画面の取り直しは U1 のとおり 1 秒周期。一時停止中も周期を変えない。操作を要求した進行役の画面は、応答の状態をすぐ表示する。再開と終了は、ほかの画面に次の取り直し（最大 1 秒後）で反映され、操作の応答 1 秒以内と合わせて 2 秒以内に収まる |
| NFR3.4 共同担当の通知 | 参加者の投影に、自分の役割の当週の decisionRevision、入力者のラベル、入力者の種類（参加者か進行役か）を含める。WeekRecord と Participant の結合は、当週の 1 役割の 1 行だけで、追加のクエリは増えない |

## 試験

- 週の確定や入れ替えを繰り返し実行しながら、進行管理の投影と参加者の投影を取得し続ける試験を持つ。どの取得も、現在の週の WeekRecord が currentWeek と一致し、担当者の一覧と入力済みの数が互いに矛盾しないことを確かめる（NFR3.2）。

## 索引

| 表 | 索引 | 用途 |
| :--- | :--- | :--- |
| operation_log_entries | (game_id, sequence) の一意 | 履歴の取得、連番の一意の担保 |
| participants | (game_id, join_order) の一意（U1） | 同名の区別、ラベルの導出 |
| role_assignments | participant_id の一意（U1） | 担当者の一覧 |

## 予算

| 処理 | 予算（サーバー内） |
| :--- | :--- |
| 一時停止、再開、終了 | 100 ミリ秒以内（占有の待ちを除く） |
| 入れ替え | 150 ミリ秒以内（ハッシュと数行の更新） |
| 代理入力 | 100 ミリ秒以内 |
| 進行管理の投影 | 100 ミリ秒以内 |
| 履歴の取得（1,000 件） | 300 ミリ秒以内 |
