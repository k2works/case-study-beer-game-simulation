# 拡張性の設計 - U3 u3-facilitation

`scalability-requirements.md`（NFR4.1〜NFR4.4）を満たす設計です。ステートレスなアプリケーションと、ゲーム単位の行の占有は、U1 の `scalability-design.md` を引き継ぎます。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR4.1 共同担当の同時入力 | 入力は、ゲームの行の占有の中で保存する。同じ役割の 4 人が同時に送っても順に処理される。decisionRevision は、占有の中で WeekRecord を読んで 1 増やすため、欠けず重複しない。後に保存した値が有効になる |
| NFR4.2 履歴の規模 | 履歴は、各操作が 1 件ずつ足す。目安は 50 週で約 300 件、保証は 1,000 件まで。1 行は数百バイトで、1,000 件でも 1 ゲームの保存の大きさに占める割合は小さい。件数が保証を超えても取得は全件を返す（応答時間は保証しない）。ページングは、必要になったら取得の入口に後方互換の引数として足す。履歴の表の分割や整理は設計しない |
| NFR4.3 進行管理の取得 | `REPEATABLE READ` の読み取り専用のトランザクションで（`performance-design.md` の NFR3.2）、占有せずに読む。書き込みの占有に待たされず、書き込みも読み取りを止めない（PostgreSQL の MVCC）。進行役の取得は毎秒およそ 15 回で、全体の取得（最大およそ 270 回）に含まれる |
| NFR4.4 重なる操作 | 最終週の確定、進行役の終了、一時停止は、すべて同じゲームの行の占有に入る。占有の中で状態の遷移の表を検査するため、どの順に届いても、一度だけ終了し、二重の履歴が残らない。別のゲームは待たされない |

## 履歴の連番の採番（Q1）

- ゲームの行に `next_log_sequence`（整数、初期値 1）の列を持つ。
- 占有した中で、この値を読んで履歴の連番にし、1 増やして更新する。履歴の追記と同じトランザクションにあるため、コミットされなかった操作は連番を消費しない。連番は欠けず、重複しない。
- 1 つのトランザクションで履歴を複数件足すときは、足す順に連番を使う。最終週の確定は、weekConfirm を N、続く end を N+1 として、同じ占有の中で連続する 2 つの番号を使う。`appendLog` は呼ばれるたびに、読んで 1 増やすことを 1 件ずつ行う。
- 履歴の表を走査しない。履歴が増えても追記の費用は変わらない。

## 容量の考え方

- 水平に増やす設計は行わない。アプリケーションが複数あっても、直列処理はデータベースの行の占有で成り立つ。
- 想定を超える負荷への対処は、後の Operation で扱う。
