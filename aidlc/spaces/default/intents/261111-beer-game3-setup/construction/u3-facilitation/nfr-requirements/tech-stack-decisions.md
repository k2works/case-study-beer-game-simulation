# 技術スタックの決定 - U3 u3-facilitation

U3（運営操作）は、U1 で決めた技術スタックをそのまま使い、新しい技術や依存を足しません。U1 の `tech-stack-decisions.md` が正本です。この文書は、U3 の要件がその構成のどこを使うかを記録します。

出典: `requirements.md`（NFR2、NFR3、NFR4、NFR6、NFR9）、U1 の技術スタックの決定（Q1）、`nfr-requirements-questions.md`。

## 決定

U3 は新しい技術を導入しない。外部ライブラリの導入は確認必須のため、追加が必要になったときは理由を記録して確認を取る。

| 区分 | 使うもの（U1 の決定） | U3 での使い方 | 関連する要件 |
| :--- | :--- | :--- | :--- |
| データベース | PostgreSQL 18 | 履歴の表（`operation_log_entries`）と、`games.end_reason`、`week_records` の入力した主体の項目、`participants` の交代した印を、別の移行として足す。操作と履歴を 1 回の保存で書く | NFR2.1、NFR9.1、NFR9.2 |
| データベース移行 | node-pg-migrate | U3 の移行は既存の表の列を削除も意味の変更もしない（`contract-summary.md` の C3）。移行で、既存の ended の行の endReason に finalWeek を補う | NFR2.1 |
| 入力の検証 | zod | 入れ替えの表示名、旧担当者の識別子、役割、代理入力の値を検証する | NFR6.5 |
| Web サーバー | Fastify | 一時停止、再開、終了、入れ替え、履歴の取得の入口を足す。入れ替えの応答に `Cache-Control: no-store` を付ける | NFR6.2、NFR3.1 |
| 暗号 | Node.js 標準の暗号 | 入れ替えで発行する token は、128 ビット以上の暗号論的乱数で発行し、ハッシュで保存する（U1 と同じ方式） | NFR6.2 |
| 画面 | React、Vite | 進行管理画面（S4）、共同担当の置き換わりの通知、一時停止中の表示を足す。取り直しは 1 秒のまま | NFR3.3、NFR3.4 |
| 試験 | Vitest、Testing Library、Playwright | 状態の組み合わせ、権限、保存の失敗の注入、共同担当の同時入力、履歴の 7 種類を試験する | NFR2.1、NFR6.1、NFR9.1 |

## 方針

- 時刻は注入した時計から得る（履歴の時刻、終了の時刻）。乱数は、token の発行で試験用に差し替えられる形にする。
- 履歴の追記、ゲームの状態の更新、入れ替えは、ゲーム単位の直列処理の中で、1 回の保存で行う（U1 の NFR4.2、NFR2.1）。
- 版は U1 と同じく、実装（Code Generation）の時点で公式情報で確かめて決める。

## 却下した案

- 履歴を専用の外部サービスやログの基盤に送る案: 履歴は集約の一部として操作と同じ保存の中で残す決定（ADR-004）に反し、保存の失敗時に操作と履歴が食い違うため、却下した。
- 履歴をデータベースの更新の仕組み（トリガー）で作る案: 誰が（進行役かシステムか）を、アプリケーションの文脈なしには決められないため、却下した。
