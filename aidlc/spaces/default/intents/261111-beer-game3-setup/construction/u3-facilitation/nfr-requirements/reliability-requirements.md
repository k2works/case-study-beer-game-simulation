# 信頼性の要件 - U3 u3-facilitation

U3（運営操作）の正確性、整合性、可用性の要件です。元の要件は `requirements.md` の NFR1、NFR2、NFR5 です。U3 の操作は、ゲームの状態を変えると同時に履歴を残すため、操作と履歴が同時に成功するか、同時に失敗することが中心です。保存の版の検査、ゲーム単位の直列処理、障害の扱いは、U1 の `reliability-requirements.md` を引き継ぎます。

出典: `requirements.md`（NFR1、NFR2、NFR5）、`functional-spec.md`、`rules.md`（BR9.1〜BR9.7、BR10.2、BR10.6、BR13.1）、`entities.md`、`contract-summary.md`（C3、C5）。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR1.1 | 一時停止、再開、担当者の入れ替えは、週の計算の結果を変えない。代理入力は、入力した主体（担当者か進行役か）にかかわらず、同じ値なら同じ結果になる。同じ初期状態と意思決定系列からは、これらの操作を挟んでも、常に同じ週次状態と費用を再現する。入れ替えで役割の在庫、受注残、遅延の枠、確定前の入力が変わらない | 一時停止と再開、入れ替えを挟んだゲームと挟まないゲームで、確定後の状態と費用が一致する試験。同じ値を担当者が入力したゲームと進行役が代理入力したゲームで結果が一致する試験（BR10.3、BR9.2、BR11.2） |
| NFR2.1 | 状態を変える操作（一時停止、再開、終了、入れ替え、代理入力、週の確定）と、その履歴は、1 回の保存で行う。履歴を残せなければ、操作も残らない。入れ替えは、新しい参加者の作成、割当ての付け替え、旧 token の失効、新しい token の発行、履歴を、1 回の保存で行う | 履歴の保存の失敗を注入して、操作の結果が残らないことの試験。入れ替えの途中の失敗で、旧担当者の token が有効なままになる試験（BR13.1、BR10.2） |
| NFR2.2 | 最終週の確定による自動終了は、週の確定と同じ保存の中で行う。確定が失敗したら終了にもならず、終了の履歴も残らない。進行役の終了と最終週の確定が重なっても、順に処理し、終了は一度だけ記録する | 最終週の確定の保存の失敗を注入する試験。終了と確定の同時の要求の試験（BR9.7、BR9.6） |
| NFR2.3 | 状態に合わない操作（進行中の再開、終了後の一時停止など）は、状態を変えずに 409 `state` で拒否する。終了だけは冪等で、終了済みなら現在の状態を返し、履歴を足さない。代理入力の再送は、以前に成功した識別子なら一時停止中や終了後でも前回の結果を返す | 状態の組み合わせごとの自動試験（BR9.1〜BR9.6、BR11.4） |
| NFR5.1 | 一時停止中と終了後の状態は、保存し、アプリケーションが再起動しても保たれる。一時停止の前に保存した入力は、一時停止中も、再開後も残る。入力は入力した時点で保存する（U1 の NFR5.1） | 一時停止の後にサービスを再起動して、状態と入力が残る試験。再起動からの復元の全体は U4（US3.1） |
| NFR5.2 | 入れ替えられた旧担当者の token は即座に失効する。参加者の端末が切断されても、確定済みのデータと確定前の入力は失われない。切断からの復帰（30 分以内）と token の有効期間（最後の操作から 24 時間）は U4 が実装する | 入れ替え直後の旧 token の拒否の試験。復帰の試験は U4（AC3.2.2、AC3.2.3） |

## 障害の扱い

| 障害 | 振る舞い |
| :--- | :--- |
| 操作と履歴の保存の失敗 | 状態は操作の前のまま。500 の `internal` を返す。画面が取り直して確かめる |
| 入れ替えの応答が届かない | 平文の token は一度しか返さない。進行管理の担当者一覧に新しい担当者が出ていれば、その担当者を旧担当者として、もう一度入れ替える。参加者が 1 人余分に作られ、参加順の番号が飛ぶことを許容する（`functional-spec.md` の前提） |
| 順番待ちの時間切れ | 最大 3 秒待って、超えたら `unavailable`（503）を返す（U1 の NFR3.7）。画面が取り直す |
| アプリケーションの再起動 | 保存済みの状態（一時停止、終了を含む）から続けられる |

## 可用性の目標

U1 と同じく、U3 でも可用性の数値目標（SLA）を置かない。教室の数時間の利用が中心で、一時的な停止の後に、確定済みのデータと履歴を失わずに続けられることを目標にする。本番の目標値は、後の Operation で定める。

## バックアップと復旧

履歴は PostgreSQL にだけ置く。バックアップと復元の手順は、後の Operation で定める。
