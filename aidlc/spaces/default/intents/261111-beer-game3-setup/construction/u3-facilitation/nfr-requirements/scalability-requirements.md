# 拡張性の要件 - U3 u3-facilitation

U3（運営操作）の同時利用と規模の要件です。元の要件は `requirements.md` の NFR4 です。負荷の前提（通常負荷 75 台、最大想定 270 台）は、U1 の `performance-requirements.md` を引き継ぎます。U3 が足すのは、共同担当による同じ役割への同時入力、操作の履歴の増え方、進行管理の取得です。

出典: `requirements.md`（NFR3、NFR4）、`rules.md`（BR12.1、BR13.1、BR13.2、BR14.1）、`entities.md`（OperationLogEntry）、`functional-spec.md`、`nfr-requirements-questions.md`（Q1 履歴の規模）。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR4.1 | 同じ役割を 4 人が共同で担当し、ほぼ同時に入力を送っても、ゲーム単位の直列処理（U1 の NFR4.2）で順に処理し、最後に保存した値が有効になる。入力の順で置き換わりを通知する revision が欠けたり重複したりしない | 4 人が同時に入力する試験（BR12.1）。revision が 1 ずつ増えることの確認 |
| NFR4.2 | 1 ゲームの履歴は、50 週のゲームで約 300 件が想定の目安（週の確定 50 件、週・役割ごとに代理入力 1 回で 200 件、役割変更・一時停止・再開・終了・設定が数件）。代理入力の上書き（BR11.3）、一時停止と再開、入れ替えには回数の上限がないため、300 件は保証する上限ではない。保証するのは、履歴が 1,000 件までなら、取得を p95 1 秒以内で全件返すこと。1,000 件を超えたゲームは想定外で、取得は失敗させず全件を返すが、応答時間は保証しない。必要になったら、ページングを後方互換の追加として足す。参加者の通常の入力は履歴に残さない（BR11.3）。1 ゲームの保存の大きさに、履歴の件数が加わる | 50 週すべてで代理入力し、同じ役割への上書きを重ねて 1,000 件にした履歴を作り、件数、保存の大きさ、取得の応答時間を測る試験 |
| NFR4.3 | 進行管理の取得は読み取りだけで済み、書き込みの順番待ちに入らない。最大想定の毎秒およそ 270 回の取得のうち、進行役の分（15 チームで毎秒およそ 15 回）を含めて、書き込みと独立に処理する（U1 の NFR4.4） | 書き込み中も進行管理の取得が応答する試験。負荷の下での測定は U6 |
| NFR4.4 | 一時停止、再開、終了、入れ替え、代理入力は、別のゲームの処理を待たせない（U1 の NFR4.2）。最終週の確定と進行役の終了が重なっても、順に処理して、終了が二重にならない（BR9.6） | 同じゲームへの週の確定と終了の同時の要求の試験。別のゲームが待たされないことの試験 |

## 想定する負荷（U3 が足す分）

| 項目 | 通常負荷 | 最大想定 |
| :--- | :--- | :--- |
| 進行管理の取得 | 毎秒およそ 15 回（既存の 75 台のうち、進行役の分） | 同じ |
| 共同担当の同時入力 | 1 役割あたり最大 4 人 | 同じ |
| 一時停止・再開・終了・入れ替え・代理入力 | 1 チームあたり 1 ゲームに数回から数十回 | 同じ |
| 履歴の取得 | 進行役が必要なときに 1 回（毎秒ではない） | 同じ |

## 拡張の方針

- U1 と同じ単一のアプリケーションで足りる規模のため、水平に増やす設計は行わない。直列処理は、データベースの仕組みで行い、アプリケーションが複数あっても成り立つ作りにする。
- 履歴の増え方に上限があるため、履歴の表の分割や古い行の整理は設計しない。ゲームの削除（U5）と同時に消える。
