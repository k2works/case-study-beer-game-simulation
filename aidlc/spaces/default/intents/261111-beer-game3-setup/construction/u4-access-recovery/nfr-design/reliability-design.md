# 信頼性の設計 - U4 u4-access-recovery

`reliability-requirements.md`（NFR1.1、NFR2.1〜NFR2.3、NFR5.1〜NFR5.4）を満たす設計です。トランザクション、版の検査、障害の扱い、ヘルスチェックは U1 の `reliability-design.md` を、操作と履歴の同時の保存は U3 の `reliability-design.md` を引き継ぎます。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR1.1 再起動を挟んでも同じ結果 | 集約は要求のたびに PostgreSQL から読み直し、プロセスのメモリに状態を持たない。週の計算（SimulationEngine）は、再起動を知らない。再起動を挟んだゲームと挟まないゲームの比較を試験にする |
| NFR2.1 lastUsedAt の書き込みの失敗 | 応答のあとに条件付きの更新を 1 回行い、失敗はログに出すだけにする（例外を要求の結果に伝えない）。更新は `return_tokens` の 1 行だけを書き、集約の版の検査と履歴の対象にしない。競合は条件付きの更新により「先に書いた方が有効、後の更新は条件に合わず何もしない」となる。期限の判定は、直前の値で続く |
| NFR2.2 窓の失敗の扱い | 窓のトランザクションの中で、追加に失敗したらロールバックして、参加を成功させずに 500 `internal` を返す（安全な側）。読み取りや削除に失敗しても同じ。ロックの待ちが 3 秒を超えたら 503 `unavailable`。どの場合も、制限なしでコードの検証へ進まない |
| NFR2.3 窓の原子性 | 検査と追加を、接続元の鍵のアドバイザリロック（`pg_advisory_xact_lock`）の中で 1 つのトランザクションとして行う。窓が空のときもロックが効く。待ちは `lock_timeout = 3s`。アプリケーションが複数でも、同じ接続元の試行は PostgreSQL のロックで直列になる |
| NFR5.1 再起動からの復元 | 復元のための新しい仕組みは足さない。要求のたびに集約を読み直すことが復元である。確定済みの週の状態、確定前の入力、割当て、token、冪等の記録は、書き込みのたびにコミットされているため、再起動の前後で一致する。再起動の前に成功した識別子の再送は、冪等性の記録の照合（U1）が前回の結果を返す。試験は、第 10 週まで確定したゲームと、第 5 週で小売店が入力済みで未確定のゲームを再起動して確かめる |
| NFR5.2 切断からの復帰 | 復帰は保存した token での状態の取得である。token は再接続しても作り直さず、`last_used_at` だけを延ばす。有効期間は `isExpired(lastUsedAt, now, ttl)` の 1 つの関数（`ttl` は設定値、既定 24 時間）で判定し、時刻は注入した時計から得る。間引きにより期限は最大 1 分短くなることを許容し、境界の試験は 24 時間 − 1 分の前は有効、24 時間 + 1 分の後は無効とする。同じ token を複数のタブで使っても、同じ参加者として扱う |
| NFR5.3 入れ替えの token | U3 の入れ替えが新しい token を発行するとき、`last_used_at` を発行の時刻にする（`issued_at` と同じ値）。旧 token は `revoked_at` で失効している |
| NFR5.4 切断中の画面 | 画面の取り直しは、失敗しても 1 秒の周期のまま続け、失敗の間は文字で「接続が切れています。自動で再接続を試みます」を示す。送信に失敗した入力は欄に残し、ブラウザの保存には書かない。再起動の直前に保存に失敗した入力は残らず、画面が失敗を示す |

## 障害の扱い

| 障害 | 設計 |
| :--- | :--- |
| アプリケーションの再起動 | 保存済みの状態から続ける。復元の操作や起動時の検査は無い |
| lastUsedAt の更新の失敗 | ログに出し、要求は成功のまま。期限の判定は直前の値 |
| 窓の保存の失敗 | 参加を成功させない（500、または 503）。制限なしで通さない |
| 窓のロックの待ちの時間切れ | 3 秒で 503 `unavailable`。サーバーは自動で再試行しない |
| 信頼するプロキシの設定の欠落 | staging と production では起動しない |
| 掃除の失敗 | warn の水準でログに出し、次の周期で再実行する。掃除の失敗はログの種類（`join_attempt_cleanup_failed`）で区別し、気づく手段は Operation で定める |

## 窓の掃除

起動時と 10 分ごとに、`attempted_at` が 60 秒より古い全接続元の行を、`DELETE ... WHERE ctid IN (SELECT ctid FROM join_attempts WHERE attempted_at < $now - 60s FOR UPDATE SKIP LOCKED)` の形で、ロック中の行を飛ばして削除する。参加の要求の処理と行を奪い合わず、別の接続元を待たせない。残る行は最大でも約 10 分で、24 時間の上限（`security-requirements.md` の NFR7.1）に収まる。時刻の列に索引を持つ。実行は各アプリケーションが行ってよく、複数台で重なっても結果は同じである（冪等）。

試験:

- IPv6 の /64 を回転させた 1,000 件の試行のあとに、掃除を実行すると、60 秒を過ぎた行が残らない。掃除が走るまでは、60 秒を過ぎた他の接続元の行が残ってよく、その最大は掃除の周期（10 分）である（`security-requirements.md` の NFR7.1 の試験を、この形に読み替える）。
- 起動時に掃除が実行され、起動前から残っていた古い行が消える。
- 掃除が失敗したら、`join_attempt_cleanup_failed` がログに出て、次の周期で再実行される。参加の要求は影響を受けない。
- 2 台のアプリケーションで掃除が同時に走っても、結果が同じで、エラーにならない。
- 掃除と、参加の要求の窓のトランザクションが同時に走っても、互いを待たせない（ロック中の行は掃除が飛ばす）。

掃除の失敗に気づく手段（通知）は、Operation への引き継ぎ事項とする。U4 が出すのは `join_attempt_cleanup_failed` のログ（warn の水準）までで、通知の仕組み（alert）は持たない。

## 移行

- `return_tokens.last_used_at` を足し、既存の行は `issued_at` で埋める。`join_attempts` の表と 2 つの索引を足す。どちらも追加だけで、既存の列を削除も意味の変更もしない。ロールバックの手順は、追加した列と表を落とす逆の移行として用意する。
