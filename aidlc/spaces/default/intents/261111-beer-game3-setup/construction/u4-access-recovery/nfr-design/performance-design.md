# 性能の設計 - U4 u4-access-recovery

`performance-requirements.md`（NFR3.1〜NFR3.5、NFR8.1）を満たす設計です。接続プール、読み取り専用の取り直し、ゲーム単位の占有の短さ、占有の待ちの上限 3 秒は、U1 の `performance-design.md` を引き継ぎます。U4 は、全要求に加わる資格情報の検査、観察者と小売店の投影、参加の要求の窓、lastUsedAt の書き込みを設計します。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR3.1 観察者・小売店の取り直し | 取り直しは、ゲームの行を占有しない読み取り専用の処理にする（U1）。資格情報の検査は、資格情報のハッシュ（または鍵付きハッシュ）を索引で 1 回引く検索だけにする: 参加者の token は `return_tokens` を `token_hash` で、進行役用コードと観察者用コードは `access_codes` を照合用の値で引く。要求のゲームの識別子と一致するかは、その行の `game_id` で判定する。観察者の投影は、最新の確定済みの週の週末の値の合計を、`week_records` の当該の週の 4 行から SUM で求めて返す（確定済みの週がまだないときは、初期状態の合計を返し、費用は 0）。`inputtedRoleCount` は、当週の確定前の入力の保存済みの行（役割ごとに高々 1 行）の数で、入力が無ければ 0 である。集約全体を読まない。小売店の投影の顧客需要は、第 1 週から currentWeek までの顧客需要の列を 1 回の範囲読み取りで取る |
| NFR3.2 参加の要求 | 窓の処理は 1 つの短いトランザクションにまとめる: アドバイザリロックの取得、接続元の古い行の削除、件数の検査、（10 件未満なら）参加コードの検証、必要な場合の追加、コミット。検証は照合用の値の索引を 1 回引くだけである。ゲームへの参加（参加者の作成）は、この窓のトランザクションをコミットしたあとの別の処理で行い、窓のロックを持ったまま集約を書かない。制限中（11 件目以降）はコードの検証を行わないため、軽い |
| NFR3.3 lastUsedAt の延長 | 応答を返したあとの処理（Fastify の `onResponse`）で、`UPDATE return_tokens SET last_used_at = $now WHERE id = $id AND last_used_at <= $now - interval '1 minute'` を 1 回だけ実行する。応答の時間に書き込みが乗らない。条件により、複数のアプリケーションが同時に更新しても実質 1 回になる。この更新は `return_tokens` の 1 行だけを書き、ゲームの行を占有せず、集約の版を変えない |
| NFR3.4 再起動直後 | 集約は要求のたびに読み直し、プロセスのメモリに持たない（U1）。起動時に接続プールを温めて（最小の接続数を先に開く）、準備完了（ヘルスチェック）はデータベースへの接続が通ってから返す。再起動直後の最初の要求が接続の確立で遅れないようにする |
| NFR3.5 切断中の再接続 | 画面は、取り直しの応答が返ってから 1 秒後に次の取り直しを予約する（重ならない）。失敗しても間隔を延ばさず、1 秒のままにする。連続して失敗している間は「接続が切れています。自動で再接続を試みます」を表示し、最初に成功した取り直しで消す。送信に失敗した入力は欄に残し、ブラウザの保存には書かない |
| NFR8.1 U4 の画面 | 切断中の表示は、色だけでなく文字で示す（`role="status"` の領域に文を出す）。参加画面の「観察者として見る」は、ラベル付きの入力欄と送信ボタンで、キーボードだけで操作できる。観察画面は、表と見出しで状態を示し、色だけに頼らない。全体のコントラストの検査は U6 |

## 予算

| 処理 | 予算 | 内訳の目安 |
| :--- | :--- | :--- |
| 観察者・小売店の取り直し（通常負荷 p95） | 500 ミリ秒 | 資格情報の検索 1 回 + 投影の読み取り 1〜2 回。応答の大きさは小さい |
| 参加の要求（p95） | 1 秒 | ロックの取得 + 削除・件数・追加 + 検証 1 回 + 参加の書き込み |
| lastUsedAt の延長の差（p95） | 50 ミリ秒 | 応答のあとに行うため、通常は応答時間に乗らない。測定は書き込みを含む要求と含まない要求の差 |

## 試験

- 1 分間に同じ token で 60 回の要求を送り、`last_used_at` の更新が 1 回であることを確かめる。2 つのアプリケーションから同時に送っても 1 回である。
- 窓の処理（ロック、削除、件数、検証、追加）を含む参加の応答時間を測って記録する。
