# セキュリティの設計 - U4 u4-access-recovery

`security-requirements.md`（NFR6.1〜NFR6.10、NFR7.1）を満たす設計です。コードと token の発行、鍵付きハッシュと暗号化、CSP と HSTS、入口の共通の検証、ログの許可リストは U1 の `security-design.md` を、進行役の操作の認可と投影の専用の型は U3 の `security-design.md` を引き継ぎます。U4 は、観察者の資格情報、顧客需要の境界、無効な token の同一の応答、参加の試行の窓、接続元の特定、入口の構造の強制を設計します。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR6.1 観察者の資格情報 | `AccessControl.authenticate` が、`Authorization` ヘッダの資格情報から呼び出した人を特定する。種類はヘッダの形からは決めず、照合の結果で決める: 資格情報から `return_tokens`（参加者の token、ハッシュ）と `access_codes`（進行役用コードと観察者用コード、照合用の値。`kind` が facilitator または observer）の両方を索引で引き（順序は問わず、一致は高々 1 行）、一致した行の種類を呼び出した人の種類とする。どちらにも一致しなければ `invalid`（NFR6.4）。観察者は、要求のゲームの `kind = observer` で `revoked_at` が空の行に一致したときだけ特定される（別のゲームのコードは通らない）。許可する操作の表（`authorize(principal, action)`）で、観察者に許す操作は状態の取得（`viewState`）だけにする。入力、代理入力、週の確定、一時停止、再開、終了、入れ替え、役割の割当て、開始、履歴の取得は表に無く、403 `forbidden` になる。観察者用コードは U1 の発行（暗号論的乱数 16 バイト以上）を使い、失効の操作は設けない |
| NFR6.2 観察者の投影 | `project(principal, game)` が、観察者には `ObserverView` の専用の型へ変換する。型の項目は `currentWeek`、`status`、`inputtedRoleCount`、`weekCostTotal`、`cumulativeCostTotal`、`inventoryTotal`、`backlogTotal` だけで、役割の名前を鍵にした項目、役割ごとの配列、週ごとの系列、参加者の表示名を持たない。型に項目が無いため、含めることができない。応答は zod の厳密な型（未知の項目を拒否）で検証してから返す。合否は `security-requirements.md` の NFR6.2 の基準（a）（b）（c）とし、試験は 50 週の golden の系列と「1 役割だけ非ゼロ」の週で、応答の鍵の集合が固定のリストと一致し、役割名や配列が無いことを確かめる |
| NFR6.3 顧客需要 | 小売店の参加者の投影の型だけが `customerDemand`（第 1 週から currentWeek までの配列）を持つ。小売店以外の参加者と観察者の投影の型には項目が無い。`status` が `preparing` のときは項目を空にする。専用の経路は作らない。将来、直接取得の経路を足すときは、操作の表で小売店の参加者と進行役だけを許す |
| NFR6.4 無効な token の同一の応答 | 参加者の token の検査は `resolveParticipant(tokenHash, now)` の 1 つの関数に集め、「不明、`revoked_at` あり、`last_used_at + 24 時間` を過ぎた」のいずれも同じ結果 `invalid` を返す。入口は `invalid` を、固定の応答（403 `forbidden`、種類を含まない 1 つの共通の本文）に変換する関数 1 つでだけ返す。比較の対象は、状態コード、本文（要求の識別子を除く）、固定のヘッダで、3 つの場合で完全に同じになる。文言は画面が決める: 画面は自分が送った資格情報の種類を知っているため、参加者の token が拒否されたときは BR17.3 の文言（理由「この端末の参加情報は使えません」、直し方「進行役に担当者の入れ替えを依頼してください」）を、観察者用コードの入力が拒否されたときは観察者の入口の文言（「観察者用コードが正しくありません」）を、画面側で選ぶ。サーバーの応答は種類で変わらないため、応答の違いから種類や存在を明かさない。期限は行を変えずに時刻を比べて決める。応答時間の差の隠蔽はしない（残余リスク。token は 128 ビット以上で、時間差から割り出せない）。画面は、この応答を受けたら保存した token を消して参加画面に戻す |
| NFR6.5 参加の試行の窓 | 表 `join_attempts(source_key text, attempted_at timestamptz)` を持ち、索引は `(source_key, attempted_at)` と `(attempted_at)`。参加コードによる参加の要求は、1 つのトランザクションで次の順に行う。表には連番の列 `id bigserial` も持つ。時刻は注入した時計（アプリケーション側）から得て、パラメータとして渡す。複数台の時計のずれは、60 秒の窓と 1 分の間引きに対して無視できる大きさ（1 秒程度）として許容し、「最新 11 件」の順序は `(attempted_at, id)` で決めて、同じ時刻の行は `id` の大きい方を新しいとする。（1）`SET LOCAL lock_timeout = '3s'` のあと `pg_advisory_xact_lock(classid, hashtext(source_key))` を取る。2 つの整数の形で、`classid` は窓専用の固定の定数にする（ロックはコミットで解放される。U1 のゲーム単位の占有は行の占有のため、鍵の空間は交わらない）。（2）その接続元の `attempted_at` が 60 秒より古い行を削除する。（3）その接続元の行を数える。（4）10 件以上なら、コードを検証せずに、この試行の行を追加し、`DELETE FROM join_attempts WHERE source_key = $1 AND id NOT IN (SELECT id FROM join_attempts WHERE source_key = $1 ORDER BY attempted_at DESC, id DESC LIMIT 11)` で新しい 11 件を超える行を削除して、429 `rate_limited` で拒否する（hint「しばらく待ってからやり直してください」）。（5）10 件未満なら参加コードを検証する。無効なら行を追加して通常の拒否（403）、有効なら行を足さずにコミットして参加の処理へ進む。ロックの待ちが 3 秒を超えたら（`lock_timeout` の SQLSTATE `55P03`）、制限なしで通さずに 503 `unavailable` で拒否する。窓が空でもロックは接続元の鍵に対して効くため、並行した試行でも通れるのは 10 件までである。ロックは接続元ごとで、別の接続元の処理を待たせない。無効な token、進行役用コード、観察者用コードは窓の対象にしない（128 ビット以上） |
| NFR6.6 接続元の特定 | 設定 `TRUSTED_PROXY_HOPS`（0 以上の整数）を zod で検証して読み込む。`APP_ENV` が staging または production のときは必須で、未設定または不正なら起動しない（暗号化の鍵と同じ起動時の検査）。開発とテストでは未設定を許し、接続の相手のアドレスを使う。設定があるときは Fastify の `trustProxy` に段数を渡し、設定した段数の範囲でだけ転送元のヘッダを信じる。窓の鍵は `normalizeSource(ip)` で作る: ポートを除く、IPv4 射影アドレス（`::ffff:a.b.c.d`）は IPv4 に直す、IPv4 は完全なアドレス、IPv6 は上位 64 ビット（/64）に丸める。試験は、段数ごとの接続元の特定、偽の転送元のヘッダが窓を回避しないこと、同じ /64 の別アドレスの 11 回目が 429 になること、射影アドレスの正規化を確かめる |
| NFR6.7、NFR6.8 認可の位置（共通） | 認可（資格情報の特定、ゲーム・役割への権限）は、Fastify の `onRequest` フックで行う。本文の解析、スキーマ検証、zod の検証より前であるため、権限のない人には 422 や 409 が先に返らない。判定の順は、認可（`onRequest`）、入力の検証（422）、占有、再送の照合、状態の検査、占有の中の割当てと token の再検査（U3）で、認可が U1 と U3 の判定の順の先頭に入る。要求のゲームの識別子が、存在しない場合も、別のゲームの資格情報の場合も、同じ 403 `forbidden` を返す（404 を返さず、存在を明かさない）。参加の要求（資格情報を持たない）は、`onRequest` で窓の検査（NFR6.5）を行い、その後に本文を検証する |
| NFR6.7 入口の構造 | 入口のモジュール（`src/http/**`）は GameSession を import しない。ESLint の `no-restricted-imports`（パターンで GameSession のモジュールを禁止）で lint を失敗させ、同じ検査を構造の自動試験（入口のモジュールの import を走査する）でも行う。GameSession を呼ぶ経路は `AccessControl` が公開する関数に限る。違反を含むコードで試験が失敗することを確かめる試験も置く |
| NFR6.8 網羅試験 | 入口は 1 つの経路の表（`routeCatalog`）から登録する。各行は、メソッド、経路、必要な操作、受け付ける資格情報の種類を持つ。構造の試験が、Fastify に登録された経路の全部が表にあること（表に無い経路が登録されたら失敗する）を確かめる。網羅試験は表の全行について、無資格、別のゲームの資格情報、存在しないゲームの識別子、別の役割の識別子（役割を指定する経路）、観察者の各場合で 403 `forbidden` を確かめる。さらに、権限のない資格情報で不正な本文を送っても 422 でなく 403 が返ること（認可が先）を、本文を取る全行で確かめる。他のゲームの役割の識別子が、そのゲームのコードや token で通らないことも含める |
| NFR6.9 拒否のログ | 入口の共通のエラー処理が、資格情報の拒否を `invalid_token`（`Authorization` ヘッダの資格情報が無効）、`invalid_code`（参加コードの試行が無効）、`rate_limited`（429）に分類して記録する。出す項目は許可リスト（種類、操作、理由、接続元の正規化したキー、ゲームの識別子（特定できるとき）、要求の識別子）だけで、一覧に無い項目は出力されない（U1）。コード、token、鍵は出さない。履歴には書かない |
| NFR6.10 画面の保存 | 観察者用コードは、`localStorage` の専用のキーに保存し、`Authorization` ヘッダで送る。URL には含めない。無効なコードは理由を示して保存しない。参加者の token が無効と分かったら、画面が保存した値を消す。U1 の CSP、HSTS、同一オリジンの設計を引き継ぐ |
| NFR7.1 接続元の保持 | 窓の表の保持は `reliability-design.md` と `scalability-design.md` に定める（接続元ごとに最新 11 件、60 秒、定期の削除、最大でも約 10 分の残り）。接続元は窓の表だけに置き、投影、履歴、応答に出さない。構造化ログの接続元の保持期間は Operation で定め、ゲームの保持期間（既定 30 日）を超えない |

## 脅威への対応

| 脅威 | 設計 |
| :--- | :--- |
| 参加コードの総当たり | NFR6.5。接続元ごとに直近 60 秒で 10 回、アドバイザリロックで原子的に数える。複数のアプリケーションでも通算 |
| 偽の転送元のヘッダ、IPv6 のアドレス回転 | NFR6.6。段数だけ信じ、IPv6 は /64 に丸める |
| 設定の誤りで全員が 1 つの接続元になる | NFR6.6。staging と production は未設定で起動しない |
| 観察者による書き込み | NFR6.1。操作の表に状態の取得だけ |
| 観察者の合計から役割別の値を知る | NFR6.2。専用の型に役割別の項目が無い |
| 小売店以外が顧客需要を知る | NFR6.3。専用の型の違い |
| token の無効の理由の推測 | NFR6.4。同一の関数と同一の応答 |
| 他のゲームの識別子の指定 | NFR6.8。経路の表と網羅試験 |
| 入口が GameSession を直接呼ぶ | NFR6.7。lint と構造の試験 |
| ログからの漏えい | NFR6.9 の許可リスト |

## 試験

- 3 種類の無効な token（不明、失効、期限切れ）の応答が、状態コード、本文、ヘッダまで完全に一致する。
- 窓の並行した試行（アプリケーション 2 つ、同じ接続元）で、通れるのが 10 件までである。
- 経路の表と、登録された経路の差が無い。入口から GameSession への import を含むコードで構造の試験が失敗する。
