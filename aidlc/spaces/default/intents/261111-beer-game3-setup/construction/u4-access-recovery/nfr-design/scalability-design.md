# 拡張性の設計 - U4 u4-access-recovery

`scalability-requirements.md`（NFR4.1〜NFR4.6）を満たす設計です。ゲーム単位の行の占有、読み取りの独立、ステートレスなアプリケーションは、U1 の `scalability-design.md` を引き継ぎます。U4 は、試行の窓の保存と大きさ、lastUsedAt の間引き、観察者を含む負荷を設計します。

## 設計

| 要件 | 解決 |
| :--- | :--- |
| NFR4.1 観察者を含む同時利用 | 観察者の取り直しは参加者と同じ読み取り専用の処理で、投影は小さい。通常負荷 105 台、最大想定 330 台を、U1 の接続プールと読み取りの独立で処理する。負荷試験（U6）は観察者を 1 ゲーム 2 人含める |
| NFR4.2 窓の大きさ | 表 `join_attempts` は、接続元ごとに最新 11 件までを保持する（追加のたびに、新しい 11 件を超える行を削除する）。行は 60 秒を過ぎると削除される。参加の要求ではその接続元の行を排他の中で削除し、これに加えて、起動時と 10 分ごとの掃除（`reliability-design.md`）が全接続元の古い行を削除する。そのため表の行数は、「直近 60 秒の試行の数」に「掃除の周期（10 分）の間に残る分」を足した範囲に収まり、接続元の数に比例して増え続けない。他の接続元の古い行は、掃除が走るまで最大約 10 分残る（`security-requirements.md` の NFR7.1 の（b）は参加の要求のたびの全接続元の削除を求めていたが、Q2 の A でこの設計に置き換えた。上限は NFR7.1 の（c）の 24 時間に収まる） |
| NFR4.3 複数のアプリケーションでの通算 | 窓は PostgreSQL にあり、接続元のアドバイザリロック（`pg_advisory_xact_lock`）の中で、削除、件数、追加を行う。アプリケーションが何台でも、同じ接続元の試行はロックで直列になり、通れるのは 10 件までである。ロックの鍵は接続元ごとで、別の接続元は待たない。待ちは `lock_timeout = 3s` で、超えたら 503 `unavailable` |
| NFR4.4 lastUsedAt の間引き | 応答のあとに `UPDATE ... WHERE last_used_at <= now - 1 minute` を実行する。条件により、複数のアプリケーションが同時に実行しても、1 分の間に実質 1 回しか書かれない。書き込みは `return_tokens` の 1 行だけで、ゲームの行の占有に入らない。最大想定（270 の token）で毎秒およそ 4.5 回に収まる |
| NFR4.5 観察者の見込み | 1 ゲームあたり 2 人を見込む。人数を制限する機能は持たない。見込みを超える利用は、負荷の見込みを見直す |
| NFR4.6 読み取りの独立 | 観察者と小売店の取り直しは、ゲームの行を占有せず、書き込みを起こさない（lastUsedAt の更新は応答のあと、別の行への書き込み）。データベースの既定の分離（読み取りがロックを待たない）を使う |

## 容量の見積もり

| 項目 | 見積もり |
| :--- | :--- |
| 窓の表の行数 | 接続元ごとに最大 11 行。授業の開始時に 75 人が同じ NAT から参加しても 1 接続元で 11 行 |
| 窓のロック | 同時に保持するロックは、同時に参加の要求を処理している接続元の数。1 つのロックの保持は数ミリ秒 |
| 接続の使用 | 窓のトランザクションは 1 接続を短時間使う。プールの大きさは U1 の設計に含め、U6 で確かめる |

## 拡張の方針

- U1 と同じ単一のアプリケーションで足りる。窓を PostgreSQL に置くため、台数を増やしても制限が緩くならない。
- 窓の表は分割しない。行は 60 秒で消えるため、古い行の整理は掃除（`reliability-design.md`）が受け持つ。U5 の保持期間の処理には送らない。
