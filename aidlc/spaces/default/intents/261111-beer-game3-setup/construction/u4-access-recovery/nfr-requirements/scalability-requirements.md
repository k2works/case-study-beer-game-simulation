# 拡張性の要件 - U4 u4-access-recovery

U4（復帰と権限）の同時利用と規模の要件です。元の要件は `requirements.md` の NFR4 です。負荷の前提（通常負荷 75 台、最大想定 270 台）は、U1 の `performance-requirements.md` を引き継ぎます。U4 が足すのは、観察者の画面、試行の窓の保存と大きさ、復帰用 token の延長の書き込みです。

出典: `requirements.md`（NFR3、NFR4）、`rules.md`（BR15.3、BR17.2、BR18.1、BR18.2）、`entities.md`、`functional-spec.md`、`nfr-requirements-questions.md`（Q1 窓は PostgreSQL、Q3 観察者は最大 2 人）。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR4.1 | 観察者が加わっても、少なくとも 15 チーム（各チーム 4 役割と進行役、観察者最大 2 人）が同時に利用できる。通常負荷は 105 台の画面、最大想定は 330 台の画面で、どちらでも応答の目標（`performance-requirements.md` の NFR3.1）を満たす | U6 の負荷試験（通常負荷と最大想定の両方、観察者を含む）。U4 は、観察者を含めて複数のゲームを並行して処理する自動試験を持つ |
| NFR4.2 | 参加の試行の窓（JoinAttemptWindow）は PostgreSQL に保存し、接続元ごとに最新 11 件までを保持する。それより古い行と、60 秒を過ぎた行は、書き込みのときに（接続元に関わらず）削除する。接続元の数に上限は置かないが、行は 60 秒で消えるため、表の行数は直近 60 秒の参加の試行の数を超えない。1 つの接続元の行は 11 件を超えない（保持の詳細は `security-requirements.md` の NFR7.1）。拒否された試行も窓に加えるため（BR18.2）、連打されても窓は無制限に伸びない | 同じ接続元から 100 回連打しても、行が 11 件を超えないことの試験。60 秒を過ぎた行が削除される試験 |
| NFR4.3 | アプリケーションが複数あっても、同じ接続元の試行が通算で数えられ、制限（直近 60 秒で 10 回）が台数に比例して緩くならない。同じ接続元から複数のアプリケーションに同時に届いた試行でも、通れるのは 10 件までである。窓の検査と追加は、接続元ごとに互いを待たせず（別の接続元の試行を待たせない）、同じ接続元の間でだけ直列に処理する。排他は窓が空でも効く方法（アドバイザリロックまたは直列化できる分離レベル）で行い、待ち時間は最大 3 秒、超えたら 503 `unavailable` とする（`security-requirements.md` の NFR6.5） | アプリケーションを 2 つ起動して、同じ接続元から交互・同時に試行する試験。別の接続元が待たされない試験 |
| NFR4.4 | 復帰用 token の lastUsedAt の延長は、1 つの token につき 1 分に 1 回までの書き込みとする。最大想定の毎秒およそ 330 回の取得でも、書き込みは token の数 ÷ 60 秒（最大 270 の token で毎秒およそ 4.5 回）に収まる。アプリケーションが複数でも 1 分に 1 回を保つため、書き込みは最後の書き込みの時刻を条件にした更新（時刻が 1 分以上前の場合だけ更新する）で行う。書き込みは、ゲームの集約の直列処理（U1 の NFR4.2）に入らず、return_tokens の行だけを更新する | 1 分間の同じ token の要求で、書き込みが 1 回であることの試験。集約の書き込みの順番待ちに入らない試験 |
| NFR4.5 | 観察者は、1 ゲームあたり最大 2 人を見込む。観察者も参加者と同じく状態を 1 秒おきに取り直すが、観察者の投影は、参加者の投影より小さい（チーム全体の集計値と現在週だけ）。通常負荷を 105 台（75 + 30）、最大想定を 330 台（270 + 60）として、応答の目標を満たす。観察者の人数を制限する機能は設けない。1 ゲームあたり 2 人を超える利用が見込まれる場合は、負荷の見込みを見直す | U6 の負荷試験で、観察者を見込んだ台数を使う。観察者の投影の大きさを測る試験 |
| NFR4.6 | 読み取り（観察者・小売店の状態の取得）は、書き込みの順番待ちに入らない。最大想定の毎秒およそ 330 回の取得を、書き込みと独立に処理する（U1 の NFR4.4）。観察者の取得は、集約を読み取るだけで、書き込みを起こさない | 書き込み中も観察者の取得が応答する試験。負荷の下での測定は U6 |

## 想定する負荷（U4 が足す分）

| 項目 | 通常負荷 | 最大想定 |
| :--- | :--- | :--- |
| 画面の状態の取得（観察者を含む） | 毎秒およそ 105 回 | 毎秒およそ 330 回 |
| 観察者の画面 | 30 台（15 ゲーム × 最大 2 人） | 60 台 |
| 参加の要求 | 授業の開始時に、1 分以内に最大 75 件。制限中の接続元からは窓に加わる試行 | 同じ |
| lastUsedAt の書き込み | token 1 つにつき 1 分に 1 回まで（最大 75 token で毎秒およそ 1.3 回） | 最大 270 token で毎秒およそ 4.5 回 |
| 試行の窓の行 | 接続元ごとに最大 11 件 | 同じ |

## 拡張の方針

- U1 と同じ単一のアプリケーションで足りる規模のため、水平に増やす設計は行わない。ただし、試行の窓をアプリケーションのメモリに置くと、台数を増やしたときに制限が緩くなるため、PostgreSQL に置く（Q1）。アプリケーションが複数あっても成り立つ作りにする。
- 試行の窓は、接続元ごとの件数と時間（60 秒）の両方に上限があるため、表の分割や古い行の整理は設計しない。ゲームの削除とは独立で、試行が止まった接続元の行は保持期間の処理（U5）で整理する（`security-requirements.md` の NFR7.1）。
