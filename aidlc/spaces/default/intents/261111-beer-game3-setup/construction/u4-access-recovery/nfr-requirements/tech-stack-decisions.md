# 技術スタックの決定 - U4 u4-access-recovery

U4（復帰と権限）は、U1 で決めた技術スタックをそのまま使い、新しい技術や依存を足しません。U1 の `tech-stack-decisions.md` が正本です。この文書は、U4 の要件がその構成のどこを使うかを記録します。

出典: `requirements.md`（NFR3、NFR4、NFR5、NFR6）、U1 の技術スタックの決定（Q1）、`nfr-requirements-questions.md`（Q1 窓は PostgreSQL、Q2 信頼するプロキシは必須設定）。

## 決定

U4 は新しい技術を導入しない。外部ライブラリの導入は確認必須のため、追加が必要になったときは理由を記録して確認を取る。

| 区分 | 使うもの（U1 の決定） | U4 での使い方 | 関連する要件 |
| :--- | :--- | :--- | :--- |
| データベース | PostgreSQL 18 | 試行の窓の表（接続元と試行の時刻）と、`return_tokens.last_used_at` の列を、別の移行として足す。窓は接続元ごとに最新 11 件までを保持し、60 秒を過ぎた行は書き込みのときに削除する。窓の検査と追加は、接続元ごとの排他（データベースの仕組み）で原子的に行う | NFR4.2、NFR4.3、NFR6.5、NFR2.3 |
| データベース移行 | node-pg-migrate | 既存の表の列を削除も意味の変更もしない（`contract-summary.md` の C3）。既存の token の行は issued_at で last_used_at を埋める | NFR5.2 |
| Web サーバー | Fastify | 信頼するプロキシの段数を設定で受け取り、接続元の特定に使う（staging と production では必須で、未設定なら起動しない）。参加の要求に 429 `rate_limited` の応答を足す。入口は AccessControl 経由でだけ GameSession を呼ぶ | NFR6.6、NFR6.7 |
| 入力の検証 | zod | 観察者用コードの入力、信頼するプロキシの段数の設定値を検証する | NFR6.1、NFR6.6 |
| 暗号 | Node.js 標準の暗号 | 観察者用コードは、128 ビット以上の暗号論的乱数で作る（U1 の発行の仕組みを使う）。照合は U1 の方式のまま | NFR6.1 |
| ログ | 構造化ログ（JSON） | 3 種類の拒否の行と、拒否の件数のカウンタを足す。資格情報は出さない | NFR9.1、NFR9.2 |
| 画面 | React、Vite | 参加画面に観察者の入口、観察画面（ObserverView）、小売店の顧客需要の表示、切断中の表示を足す。取り直しは 1 秒のまま | NFR3.1、NFR3.5、NFR5.4 |
| 構造の検査 | ESLint、Vitest | 入口から GameSession への直接 import を、lint と構造の試験で検出する。全入口の拒否を網羅する試験を置く | NFR6.7、NFR6.8 |
| 試験 | Vitest、Testing Library、Playwright | 境界（9・10・11 回目）、並行した試行、2 つのアプリケーション、再起動を挟んだ復元、24 時間の境界、投影の項目を試験する | NFR1.1、NFR5.1、NFR6.5 |

## 方針

- 時刻は注入した時計から得る（token の期限、lastUsedAt、窓の 60 秒）。試験は、時計を進めて 24 時間と 60 秒の境界を確かめる。接続元の特定は、設定値（段数）と要求の情報から得る形にして、試験で差し替えられるようにする。
- 窓の検査と追加は、PostgreSQL の機能で原子的に行う。窓が空のときは行ロックが掛からず、並行した追加で通れる件数が 10 を超えうるため、行ロックや 1 文での条件付きの追加だけに頼らず、アドバイザリロック（接続元の鍵）または直列化できる分離レベルを使う。具体的な方法は NFR 設計の工程で決める。アプリケーションの複数起動で成り立つことが条件である。
- 接続元の鍵は、IPv4 は完全なアドレス、IPv6 は /64、IPv4 射影アドレスは IPv4 に正規化する（`security-requirements.md` の NFR6.6）。
- 信頼するプロキシの設定の名前と、ALB の段数の確定は、NFR 設計とインフラの設計の工程で決める。
- 版は U1 と同じく、実装（Code Generation）の時点で公式情報で確かめて決める。

## 却下した案

- 試行の窓をアプリケーションのメモリに置く案: 台数に比例して制限が緩くなり、再起動で窓が消える（Q1）。窓の大きさを接続元の数の上限（1 万件）で抑える必要もあり、却下した。
- 信頼するプロキシを既定で 1 段にして設定なしでも起動する案: 段数が違う構成では接続元を誤り、全員が 1 つの接続元になる恐れがある（Q2）。staging と production では必須の設定にする。
- 外部のレート制限の基盤（Redis など）を足す案: 新しい基盤は運用を増やす。PostgreSQL で足りる規模のため、却下した。
