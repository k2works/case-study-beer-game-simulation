# 信頼性の要件 - U4 u4-access-recovery

U4（復帰と権限）の正確性、整合性、可用性の要件です。元の要件は `requirements.md` の NFR1、NFR2、NFR5 です。U4 は、サービスの再起動と参加者の切断からの復帰が中心です。保存の版の検査、ゲーム単位の直列処理、障害の扱いは、U1 の `reliability-requirements.md` を、操作と履歴を同時に保存する要件は、U3 の `reliability-requirements.md` を引き継ぎます。

出典: `requirements.md`（NFR1、NFR2、NFR5）、`functional-spec.md`、`rules.md`（BR17.1〜BR17.6、BR18.2、BR20.1〜BR20.3）、`entities.md`、`contract-summary.md`（C3）。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR1.1 | サービスを再起動しても、同じ初期状態と意思決定系列からは、常に同じ週次状態と費用を再現する。再起動を挟んだゲームと挟まないゲームで、確定後の状態（在庫、受注残、遅延、履歴、費用）が一致する。集約は要求のたびに PostgreSQL から読み直し、メモリの状態に依存しない | 第 10 週まで確定して再起動したゲームと、再起動しないゲームで、第 11 週以降の状態と費用が一致する試験（BR20.2） |
| NFR2.1 | 復帰用 token の lastUsedAt の延長は、return_tokens の行だけを更新し、GameSession の集約の版の検査と履歴の対象にしない。延長の書き込みが失敗しても要求は拒否せず、ログに出す。期限の判定は、直前の値で続く。書き込みの競合は、後の時刻を採用する | lastUsedAt の書き込みの失敗を注入して、要求が成功し、ログが出ることの試験。集約の版が増えないことの試験（BR17.2） |
| NFR2.2 | 試行の窓への追加は、参加の要求の結果（403 または 429）と整合する。窓への追加に失敗した場合は、要求を拒否する側（安全な側）に倒し、参加を成功させない。窓の読み取りに失敗したら 503 `unavailable` を返し、制限なしで通さない | 窓の保存の失敗を注入して、参加が成功しないことの試験（BR18.1） |
| NFR2.3 | 窓の検査と追加は、同じ接続元から同時に届いた試行でも、通れるのが 10 件までになるよう、原子的に行う。アプリケーションが複数でも同じである。窓が空のときも排他が効く方法で行い、排他の待ち時間は最大 3 秒、超えたら 503 `unavailable` を返す（`security-requirements.md` の NFR6.5） | 同じ接続元からの並行した試行の試験（アプリケーション 2 つ）（BR18.2、`scalability-requirements.md` の NFR4.3） |
| NFR5.1 | サービスが再起動しても、確定済みの週の状態、確定前の入力、割当て、復帰用 token、冪等の記録が、再起動の前と一致する。復元のための新しい仕組み（復元の操作、起動時の検査）は設けず、保存済みの集約の読み直しが復元である。再起動の前に成功した識別子の再送には、前回と同じ結果を返す | 第 10 週まで確定したゲームの再起動の試験。第 5 週で小売店が入力済みで未確定のゲームの再起動の試験。再起動の前に成功した識別子の再送の試験（AC3.1.1〜AC3.1.3、BR20.1、BR20.2） |
| NFR5.2 | 参加者のブラウザが 30 分以内に切断されても、同じ token で再接続すれば、同じ参加者・同じ役割に戻れ、確定済みのデータと確定前の入力は失われない。token は最後の操作から 24 時間有効で、再接続しても作り直さない。同じ token を複数のタブで使っても、同じ参加者として扱う。24 時間を超えた、入れ替えで失効した、不明な token は、理由を区別せず拒否し、進行役による入れ替えを案内する | 30 分の切断のあとの再接続の試験。24 時間の境界の前後の試験（lastUsedAt の間引きにより、期限は最大 1 分短くなることを許容する。24 時間 − 1 分の前は有効、24 時間 + 1 分の後は無効）。複数のタブで同じ token を使う試験（AC3.2.1〜AC3.2.3、BR17.1〜BR17.5） |
| NFR5.3 | 入れ替えで発行された新しい token は、発行の時刻から 24 時間を数える。以前の担当者の token は失効する | 入れ替え直後の新しい token での再接続と、旧 token の拒否の試験（BR17.6） |
| NFR5.4 | 画面は、状態の取り直しに失敗している間、「接続が切れています。自動で再接続を試みます」と示して取り直しを続ける。送信に失敗した入力は欄に残し、送信前の値をブラウザの保存に書かない（下書きは保存しない）。再起動の直前に保存に失敗した入力は残らず、画面が失敗を示して欄の値を残す | ネットワークの遮断と復旧の画面の試験（AC3.2.4）。入力の送信の失敗の画面の試験（BR20.3） |

## 障害の扱い

| 障害 | 振る舞い |
| :--- | :--- |
| アプリケーションの再起動 | 保存済みの状態（一時停止、終了、token、冪等の記録を含む）から続けられる。新しい復元の仕組みは動かさない |
| lastUsedAt の書き込みの失敗 | 要求は成功させ、ログに出す。期限の判定は直前の値で続く |
| 試行の窓の読み書きの失敗 | 参加を成功させない（窓の追加の失敗は拒否、読み取りの失敗は 503）。制限なしで通さない |
| 順番待ちの時間切れ | 最大 3 秒待って、超えたら `unavailable`（503）を返す（U1 の NFR3.7）。画面が取り直す |
| 信頼するプロキシの設定の欠落 | staging と production では起動しない（`security-requirements.md` の NFR6.6） |
| 切断中の画面 | 接続が切れていることを示し、1 秒周期の取り直しを続ける |

## 可用性の目標

U1 と同じく、U4 でも可用性の数値目標（SLA）を置かない。教室の数時間の利用が中心で、一時的な停止（再起動、切断）の後に、確定済みのデータと確定前の入力を失わずに続けられることを目標にする。本番の目標値は、後の Operation で定める。

## バックアップと復旧

token、割当て、試行の窓は PostgreSQL にだけ置く。バックアップと復元の手順は、後の Operation で定める。
