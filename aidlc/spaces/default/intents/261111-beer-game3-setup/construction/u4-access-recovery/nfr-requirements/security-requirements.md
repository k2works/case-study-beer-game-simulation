# セキュリティの要件 - U4 u4-access-recovery

U4（復帰と権限）のセキュリティの要件です。元の要件は `requirements.md` の NFR6 と NFR7 です。U4 は、観察者という新しい資格情報、小売店だけが見られる顧客需要、復帰用 token の有効期間、参加の無効な試行の制限、全要求の認可を受け持ちます。コードと token の発行、鍵付きハッシュ、暗号化、CSP、HTTPS などの共通の要件は、U1 の `security-requirements.md` を引き継ぎます。U3 の進行役の操作の認可（U3 の NFR6.1）も、そのまま引き継ぎます。

出典: `requirements.md`（NFR5、NFR6、NFR7）、`functional-spec.md`、`rules.md`（BR15.1〜BR15.4、BR16.1、BR16.2、BR17.1〜BR17.6、BR18.1〜BR18.3、BR19.1〜BR19.3）、`entities.md`、`contract-summary.md`（C1、C3、C4）、`nfr-requirements-questions.md`（Q2 信頼するプロキシ、Q4 拒否の記録）。

## 認可の前提

- 資格情報の種類は、参加者の token、進行役用コード、観察者用コード、参加コード（参加の要求だけ）の 4 つである。要求ごとに、サーバー側で種類と、要求のゲーム・役割への権限を検証する。画面で隠すだけにしない（BR19.1）。
- 検査の順は、資格情報の特定、ゲーム・役割への権限、入力の検証（422）、状態の検査（409）の順で、認可を必ず先に行う。権限のない人には、422 や 409 の違いでゲームや役割の存在・状態が分からない（BR19.1）。
- 観察者は、状態の取得だけができる。ほかの要求はすべて 403 で拒否する（BR15.2）。

## 要件

| ID | 要件 | 確かめ方 |
| :--- | :--- | :--- |
| NFR6.1 | 観察者用コードを、観察者の資格情報として受け付ける。コードは暗号論的乱数による 128 ビット以上で、そのゲームのものだけを認める。別のゲームのコード、不明なコードは 403 `forbidden` で拒否する。観察者は状態の取得だけができ、入力、代理入力、週の確定、一時停止、再開、終了、担当者の入れ替え、役割の割当て、開始、履歴の取得は、状態を変えずに 403 で拒否する | 観察者のコードで、全書き込み系の入口を呼ぶ自動試験（AC2.9.2、BR15.1、BR15.2）。別のゲームのコードの拒否の試験 |
| NFR6.2 | 観察者の投影（ObserverView）は、currentWeek、status、入力済みの役割の数、4 役割の費用の合計（当週と累積）、週末の在庫の合計、週末の受注残の合計だけを返す。役割別の値、意思決定値、受注、出荷、将来の需要、参加者の表示名、コードと token は返さない。合否の基準は、次の 3 つをすべて満たすことである。（a）応答の項目が固定のリストと完全に一致する。（b）役割の名前や番号を鍵にした項目、役割ごとの配列、週ごとの系列が無い（どの値も特定の役割に結びつけられない）。（c）「入力済みの役割の数」は数だけで、どの役割かを示さない。合計は 4 役割の和であり、1 役割だけが非ゼロの週でも値は役割に結びつかないため、逆算できないとみなす。この基準を超えて役割を特定できる項目を足す変更は、この要件の違反とする（`functional-spec.md` の前提の確認） | 投影の項目の完全一致の試験（含めてはならない項目が無いこと）。50 週の golden の系列と、3 役割が 0 で 1 役割だけ非ゼロの週を含む入力で、応答が（a）〜（c）を満たす試験（BR15.3） |
| NFR6.3 | 小売店の参加者だけが、第 1 週から currentWeek までの顧客需要を状態の投影の項目として見られる。currentWeek より後の週の値は返さない。小売店以外の参加者、観察者の投影には項目自体を含めず、顧客需要の専用の経路は設けない。資格情報なし、別のゲームの資格情報は、状態の取得自体を 403 で拒否する | 全役割・観察者・無資格の投影の自動試験。将来の週の値が応答に無いことの試験（AC2.1.1〜AC2.1.3、BR16.1、BR16.2） |
| NFR6.4 | 無効な参加者 token（期限切れ、入れ替えで失効、不明）は、理由を区別せず、同じ文言と同じ形の 403 で拒否する。応答の内容（状態コード、本文、ヘッダ）の違いで、期限切れか、失効か、存在しないかを明かさない。応答時間の差の隠蔽は要件にしない（検索の経路の違いによる時間差は受け入れた残余リスクで、token は 128 ビット以上のため時間差から token を割り出せない）。期限の判定は、行を変えずに、判定のたびに時刻を比べる。有効期間は最後の操作から 24 時間、延長の書き込みは 1 分に 1 回までとする | 3 つの無効の場合の応答が完全に一致する試験（BR17.1〜BR17.3）。24 時間の境界の前後と、1 分の間引きの試験。間引きのため、実際の期限は最後の操作から 24 時間より最大 1 分短くなることを許容し、境界の試験は 24 時間 − 1 分の前は有効、24 時間 + 1 分の後は無効を確かめる |
| NFR6.5 | 参加コードによる無効な参加の試行を、同じ接続元から直近 60 秒で 10 回までとし、11 件目は、コードを検証せずに 429 `rate_limited` で拒否する（有効なコードでも拒否する）。拒否された試行も窓に加え、60 秒間試行しなければ自動で解除される。数えるのは参加コードの試行だけで、無効な token、進行役用コード、観察者用コードは数えない（128 ビット以上で総当たりが現実的でないため）。窓の保存先は PostgreSQL とし、アプリケーションが複数あっても同じ接続元の試行が通算で数えられる。同じ接続元からの同時の試行でも、通れるのは 10 件までとする。窓が空のときも排他が効くよう、接続元ごとの排他は行ロックに頼らず、アドバイザリロックまたは直列化できる分離レベルで行う。排他の待ち時間は最大 3 秒とし、超えたら 503 `unavailable` で拒否する（制限なしで通さない。U1 の NFR3.7 と同じ）。窓は接続元ごとに最新 11 件までを保持し、60 秒を過ぎた行は書き込みのときに削除する | 境界の試験（9 回目と 10 回目は 403、11 回目は 429、有効なコードでも 429、60 秒後に解除）。同じ接続元からの並行した試行の試験。アプリケーションを 2 つ起動した試験（BR18.1、BR18.2、AC5.4.2） |
| NFR6.6 | 接続元は、信頼するプロキシの設定に従って特定する。staging と production では、信頼する段数を必須の設定にし、未設定ならアプリケーションを起動しない（暗号化の鍵の欠落と同じ扱い。U1 の NFR6.11）。開発とテストでは、接続の相手のアドレスを使う。利用者が付けた転送元のヘッダは、設定された段数の範囲でしか信じず、窓の回避に使わせない。窓の鍵になる「接続元」は、次のように正規化する。IPv4 は完全なアドレス、IPv6 は上位 64 ビット（/64）に丸める、IPv4 射影アドレス（`::ffff:a.b.c.d`）は IPv4 に直す、ポート番号は含めない。同じ /64 の別アドレスから 11 回目の試行を送っても 429 になる | 設定がない staging 相当の起動の拒否の試験。段数の設定ごとに接続元が期待どおり特定される試験。利用者が偽の転送元のヘッダを付けても、窓が回避されない試験。IPv6 の同じ /64 の別アドレスと、IPv4 射影アドレスの正規化の試験（BR18.3） |
| NFR6.7 | HTTP の入口のモジュールは、GameSession を直接 import できず、外へ出る経路を AccessControl に限る。lint と構造の自動試験で強制し、違反はマージを止める | 入口のモジュールから GameSession への import を検出する構造の試験。違反を含むコードで試験が失敗することの確認（BR19.2） |
| NFR6.8 | 全ての入口について、無資格、別のゲーム、別の役割、観察者の各資格情報での拒否（403）を確かめる網羅試験を置く。入口が追加されたら、網羅試験の対象の表に加わらない限り試験が失敗する。表の各行は、期待する拒否を持つ | 入口の一覧と網羅試験の表の差分を検出する試験（AC5.4.1、BR19.3）。他のゲームの役割の識別子が、そのゲームのコードや token では通らない試験 |
| NFR6.9 | 認可の拒否（403）、無効な参加コード、レート制限（429）は、構造化ログに残す。ログには種類（`invalid_token`、`invalid_code`、`rate_limited`。意味は `observability-requirements.md` の NFR9.1。無効な進行役用コードと観察者用コードは `invalid_token`）、接続元、ゲームの識別子、要求の識別子を出し、コード、token、鍵は出さない。履歴（OperationLogEntry）には残さない（U3 の NFR6.6 と同じ方針）。拒否の応答は、存在や状態を明かさない形のままにする | ログの出力の自動試験（種類ごとに行が出ること、資格情報の文字列が出ないこと）。履歴に拒否が残らないことの試験 |
| NFR6.10 | 観察者用コードは、ブラウザに保存して以後の要求の `Authorization` ヘッダで送る。URL に含めない。画面の入口は、無効なコードに理由を示し、保存はしない。復帰用 token は、無効と分かったら画面が保存した値を消し、参加画面に戻す。観察者用コードの失効の操作は U4 では設けない | 画面の試験（コードが URL に出ないこと、無効な token で保存が消えること）（BR15.4、BR17.3）。応答ヘッダの検査は U1 の NFR6.10 を引き継ぐ |
| NFR7.1 | 表示名以外の個人情報を集めない。試行の窓の表に保存する接続元（正規化した IP アドレス。NFR6.6）は、レート制限の判定のためだけに使い、ゲームの履歴、投影、応答には出さない。保持は U4 自身が次のとおり行い、U5 には送らない。（a）接続元ごとに最新 11 件まで。（b）参加の要求のたびに、接続元に関わらず 60 秒を過ぎた行を削除する。そのため表の行数は、直近 60 秒の参加の試行の数を超えない（接続元の数に上限は置かないが、行は 60 秒で消えるため、IPv6 を回転させても表は増え続けない）。（c）参加の要求が長く無い間に残る行のために、起動のときに 60 秒を過ぎた行を削除し、残りの行は最大 24 時間で削除する（定期の削除の処理を U4 が持つ）。構造化ログに出す接続元の保持期間は Operation で定め、ゲームの保持期間（既定 30 日。U1 の NFR7.2）を超えない。「判定のためだけ」は、窓の表についての要件である | 窓の保持の上限（11 件）、60 秒を過ぎた行の削除、起動時と定期の削除の試験。IPv6 を回転させた 1,000 件の試行のあとに、60 秒後に行が残らない試験。窓の行が投影・履歴に出ないことの確認 |

## 脅威の考慮

| 脅威 | 対処 |
| :--- | :--- |
| 参加コードの総当たり | NFR6.5。直近 60 秒で 10 回までに制限し、拒否中も窓に加える。複数のアプリケーションでも通算で数える |
| 偽の転送元のヘッダによる、窓の回避 | NFR6.6。信頼する段数だけ転送元を信じ、staging と production では設定を必須にする |
| 設定の誤りで全員が 1 つの接続元になる | NFR6.6。未設定なら起動しない。段数が違う構成での接続元の誤りは、デプロイの前提としてインフラの設計で確かめる |
| 同じ NAT の背後（教室）の利用者が、1 人の誤入力で参加できなくなる | NFR6.5 の受け入れたトレードオフ。60 秒待てば解除される。10 回を超える誤入力が同じ教室で重なる場合は、運用で 60 秒待つ。回数と窓の見直しは、構造化ログの `rate_limited` の件数（`observability-requirements.md` の NFR9.4）から Operation で行う |
| 観察者による入力、進行役の操作 | NFR6.1。状態の取得以外は 403 |
| 観察者の合計から役割別の値を逆算する | NFR6.2。合計だけを返し、小さな値の組合せの推測をレビューで確かめる。逆算できる場合は、投影の項目を減らす |
| 小売店以外が顧客需要を知る | NFR6.3。専用の経路を設けず、投影の項目として小売店だけに返す。将来の週の値は誰にも返さない |
| token の無効の理由から、入れ替えや期限の情報を推測する | NFR6.4。理由と応答時間を区別しない |
| 他のゲームの役割の識別子の指定 | NFR6.8。網羅試験で全入口を保証する |
| 入口が GameSession を直接呼んで、認可を飛ばす | NFR6.7。直接 import を禁止し、構造の試験で止める |
| 認可の前の 422・409 の違いから、ゲームや役割の存在を知る | 認可を先に行う順序（BR19.1）。権限のない人には 403 のみ |
| ログからの漏えい | NFR6.9。資格情報をログに出さない |

## コンプライアンス

個人情報は表示名のみで、窓の表の接続元（IP アドレス）はレート制限の判定のためだけに、60 秒で削除する（残る行も最大 24 時間。NFR7.1）。ゲームの保持期間と削除は U5 が足す。
