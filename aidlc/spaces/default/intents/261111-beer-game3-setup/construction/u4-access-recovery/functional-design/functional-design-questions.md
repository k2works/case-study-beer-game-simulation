# Functional Design 質問 - U4 u4-access-recovery

U4（復帰と権限）の機能の設計に入る前に、要件や前の工程で決まっていなかった点を確認します。U4 が受け持つのは、小売店だけの顧客需要（US2.1）、観察者（US2.9）、中断からの復元（US3.1）、切断後の復帰（US3.2）、サーバー側の権限の検証と試行回数の制限（US5.4）です。要件と契約で決まっていること（観察者に出すのはチーム全体の値だけ、観察者は入力できない、復帰用 token は最後の操作から 24 時間・仮の値、無効なコードの試行は同じ接続元から 1 分あたり 10 回まで・仮の値、観察者用コードは作成時に発行する、など）は質問しません。仮の数値そのものは NFR 要件の工程で確定するため、ここでは「何を数えるか」「どう作用するか」だけを決めます。

## Q1. [プロダクト] 観察者に見せるチーム全体の値の範囲

観察者に見せるのは、役割別の非公開情報を逆算できない、チーム全体の集計値と現在週です（FR4.3、AC2.9.1）。具体的にどの値を出すかを決めます。

A. 現在週、ゲームの状態、入力済みの役割の数（0〜4）、チーム全体の当週費用と累積費用（4 役割の合計）。役割別の値は出さない
B. A に、チーム全体の在庫の合計と受注残の合計を加える
C. 現在週、ゲームの状態、入力済みの役割の数だけ。費用などの数値は出さない
X. Other (please specify)

[Answer]: B

## Q2. [デベロッパー] 観察者の入口

観察者用コードは、ゲーム作成時に発行済みで、進行役が確認して配ります（ADR-005）。今は U1 の資格情報として受け付けていません。観察者が画面に入る方法を決めます。

A. 参加画面に「観察者として見る」の入口を足し、観察者用コードを入力する。コードはブラウザに保存し、以後の要求にそのまま資格情報として付ける。コードはゲームが削除されるまで有効で、期限は付けない
B. 観察者用コードを URL に含め、その URL を開くだけで入れるようにする。ブラウザの履歴や共有で漏れやすくなる
X. Other (please specify)

[Answer]: A

## Q3. [アーキテクト] 「最後の操作」として復帰用 token の有効期間を延ばす要求

復帰用 token は最後の操作から 24 時間有効です（NFR5、仮の値）。画面は数秒おきに状態を取り直すため（ポーリング）、「どの要求を最後の操作と数えるか」で、書き込みの量と token の寿命が変わります。

A. 認証に成功したすべての要求を数えるが、時刻の書き込みは 1 分に 1 回までに間引く。画面を開いている間は期限が延び、取り直しのたびに書き込みは起きない
B. 認証に成功したすべての要求を、そのつど数える。単純だが、ポーリングのたびにデータベースへ書き込む
C. 入力など参加者が書き込む操作だけを数える。画面を開いて眺めているだけでは期限は延びない
X. Other (please specify)

[Answer]: A

## Q4. [プロダクト] 無効な復帰用 token での再接続の案内

24 時間を超えた token での再接続は拒否し、進行役による入れ替えが必要と案内します（AC3.2.3）。token が無効になる理由には、期限切れ、進行役の入れ替えによる失効、保存した値の誤り（不明）があります。理由の見せ方を決めます。

A. 理由は区別せず、同じ文言で案内する。「この端末の参加情報は使えません。進行役に担当者の入れ替えを依頼してください」。どの理由かで画面が変わらないため、token の有効性を試す手がかりを減らせる
B. 期限切れと入れ替え済みは区別して案内し、不明は「無効」とする。本人が理由を知りやすい

[Answer]: A

## Q5. [アーキテクト] 試行回数の制限の対象

無効なコードによる参加の試行は、同じ接続元から 1 分あたり 10 回までで、超えたら一時的に拒否します（NFR6、AC5.4.2）。この制限を、何に適用するかを決めます。

A. 参加コードによる参加（`POST /games/join`）の無効な試行だけを数える。要件の文言のとおり。ほかの要求は、無効な資格情報なら 403 を返すが、回数は数えない
B. A に加えて、無効な参加者 token、進行役用コード、観察者用コードによる要求も、同じ接続元ごとに数える。コードの総当たりを、すべての入口で抑える
X. Other (please specify)

[Answer]: A

## Q6. [アーキテクト] 試行回数の数え方と解除

「1 分あたり 10 回まで」を、どの窓で数えるかを決めます。保存先（アプリ内のメモリか PostgreSQL か）は、デプロイの台数に関わるため、インフラの設計の工程で決めます。ここでは数え方だけを決めます。

A. 直近 60 秒の無効な試行を数える（移動窓）。11 回目の試行で拒否し、古い試行が 60 秒の窓から出れば、自動で解除される。拒否されている間の試行も窓に数える
B. 1 分ごとに区切って数える（固定窓）。区切りが変わると回数が 0 に戻る。境界をまたぐと、短時間に最大で約 2 倍の試行ができる
X. Other (please specify)

[Answer]: A

## Q7. [アーキテクト] 中断からの復元の方法

サーバーはゲームの状態をすべて PostgreSQL に保存し、確定前の入力もその場で保存しています（FR12.3、契約 C3）。そのため、再起動後に集約を読み直すだけで、復元の機能が足りる見込みです（US3.1）。U4 で何を足すかを決めます。

A. 新しい復元の仕組みは足さない。保存済みの集約を読み直すことが復元であり、U4 はそれが成り立つことを試験で保証する（確定済みの週、確定前の入力、割当て、token、冪等の記録が再起動の前後で一致する）
B. A に加えて、起動時に進行中のゲームの整合性（週の記録、遅延の枠、割当て）を検査し、食い違うゲームをログに出す
C. 進行役が「復元」を明示的に操作する入口を足す。再起動後に進行役が操作するまで、ゲームは止まったままにする
X. Other (please specify)

[Answer]: A

## Q8. [プロダクト] 切断中の画面の扱い

サーバー側では、入力済みの値は保存済みで、切断から戻っても残ります（AC3.2.2）。画面側で、回線が切れている間と、送信に失敗した入力の扱いを決めます。

A. 状態の取り直しに失敗している間は「接続が切れています。自動で再接続を試みます」と示し、取り直しを続ける。送信に失敗した入力は、入力欄に値を残したまま失敗を示す。ブラウザへの下書きの保存はしない
B. A に加えて、送信前の入力値をブラウザに下書きとして保存し、再読み込み後も入力欄に戻す

[Answer]: A

## Q9. [アーキテクト] GameSession を AccessControl 経由に限る規則の強制

GameSession を直接公開せず、外へ出る経路を AccessControl に限る規則を、構造で強制します（ADR-002、U4 の実装メモ）。どう強制するかを決めます。

A. 構造と試験の両方で強制する。モジュールの境界で、HTTP の入口が GameSession を直接 import できないようにし（lint の import 制限と、構造を調べる自動試験）、さらに全ての経路について、無資格、別のゲーム、別の役割、観察者で拒否されることを網羅する試験を置く
B. 試験だけで強制する。全ての経路の網羅試験を置くが、import の制限は設けない
X. Other (please specify)

[Answer]: A

## Q10. [アーキテクト] 復帰用 token を再接続のたびに作り直すか

復帰用 token は、参加時に一度発行して、ブラウザに保存します（FR2.3）。再接続のときの扱いを決めます。

A. 作り直さない。同じ token を使い続け、有効期間だけを延ばす（Q3）。同じ token を 2 つのタブで使っても、同じ参加者として扱う。token が漏れた疑いは、進行役の入れ替えで失効させる
B. 再接続のたびに新しい token を発行し、前の token を失効させる。漏れた token の悪用を抑えられるが、複数のタブや、再接続の途中で切れたときに、締め出される恐れがある
X. Other (please specify)

[Answer]: A
