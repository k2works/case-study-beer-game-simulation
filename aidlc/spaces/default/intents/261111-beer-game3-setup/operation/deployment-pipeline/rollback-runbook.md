# 巻き戻しの手順 - beer-game3

設計だけで、まだ実行できる環境はありません。Environment Provisioning と Deployment Execution のあとに、この手順を実際に試す（staging で巻き戻しを 1 回行う）。

## 巻き戻しの判断

| きっかけ | 判断 | 動作 |
| :--- | :--- | :--- |
| 配備の失敗（新しいタスクが健全にならない） | 自動 | ECS のサーキットブレーカーが直前の版へ戻す |
| 配備の直後のスモーク試験の失敗 | 自動でワークフローが失敗。production は人が判断 | 直前の版へ手動で戻す（下） |
| 配備のあとの異常（エラー率の上昇、応答の悪化、データの崩れ） | 人（運営者） | 直前の版へ手動で戻す。データの崩れが疑われるときは、書き込みを止めてから調べる |

## 手動の巻き戻しの手順

| 手順 | 内容 |
| :--- | :--- |
| 1 | 直前の健全だったイメージの版（コミットの識別子）を、デプロイの記録から確認する |
| 2 | ECS のサービスのタスク定義を、その版に戻して更新する（ワークフローの手動実行で版を指定する） |
| 3 | `GET /health` と短い通しで確かめる |
| 4 | 原因を記録し、修正は通常の PR（`gate` を通過）で行う |

## データベースの扱い

| 事項 | 方針 |
| :--- | :--- |
| 移行 | 前方にだけ進める。アプリケーションの巻き戻しでは、移行を戻さない。新しい版の移行は後方互換のため、古い版がそのまま動く |
| 戻す移行（`migrate:down`） | 自動では実行しない。データの損失が起きうるため、必要なときは人が内容を確認して、承認を得てから行う |
| バックアップ | RDS の自動バックアップとスナップショット。配備の前にスナップショットを取る（production）。保持は 30 日以内（U5 の設計） |
| 復旧 | 重大なデータの崩れは、スナップショットからの復元。復元の手順は Observability Setup と Incident Response で整える |

## 巻き戻しの後

| 項目 | 内容 |
| :--- | :--- |
| 連絡 | 運営者へ。授業の途中なら、進行役へ（ゲームの状態は確定済みの週から復元できる） |
| 記録 | 巻き戻しの理由、版、時刻をリポジトリの記録に残す |
| 再発防止 | 原因を試験に足す（回帰の試験）。P1 と P2 の事故は事後の振り返りを書く（Incident Response） |

## 試験

巻き戻しの手順は、staging で 1 回、意図的に失敗する版を配備して自動の巻き戻しを確かめ、手動の手順も 1 回行う。結果を記録する。
