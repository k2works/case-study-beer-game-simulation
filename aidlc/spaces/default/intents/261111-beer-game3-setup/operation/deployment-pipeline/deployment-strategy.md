# 配備の戦略 - beer-game3

## 方式: ローリング（Q2 の A）

| 項目 | 内容 |
| :--- | :--- |
| 更新の方法 | ECS のサービスを、新しいタスクを起動して健全性の確認が通ってから古いタスクを止める形で、1 台ずつ入れ替える。最小の健全な台数を保つ（`minimumHealthyPercent`）。追加の環境は作らない |
| 自動の巻き戻し | 配備の失敗（新しいタスクが健全にならない）を ECS の配備の安全装置（サーキットブレーカー）で検知し、直前の版へ自動で戻す |
| 版の混在 | 更新の途中は新旧の版が同時に動く。データベースの移行は後方互換にする（拡張して縮小する）。1 つの版では、新しい列や表を足すだけにし、古い版が壊れない |
| 切り替えの途切れ | 画面は 1 秒おきに取り直すため、短い切り替えの途切れは再取得で吸収される。保持の定期処理は、複数台のときアドバイザリロックで 1 台だけが動く |
| 停止の待ち | 停止の信号で、HTTP、接続プールの順に閉じ、定期処理の終了を最大 10 秒待つ（U5 の設計）。ECS の停止の待ち時間をこれ以上にする |
| 移行の適用 | 配備の手順の専用のタスクで、前方にだけ適用する。戻す移行（`migrate:down`）は自動では実行しない |

## 検証（スモーク試験）

| 段階 | 内容 |
| :--- | :--- |
| 配備の直後 | `GET /health`（アプリケーションとデータベース）が 200 |
| staging | 作成、参加、割当て、開始、入力、週の確定の短い通し（U6 の画面の試験の主要な操作を、staging に向けて動かす。接続先の許可は明示する） |
| production | `GET /health` と、作成したゲームを後で削除できる範囲の最小の確認。授業中は配備しない |

## 配備の時間帯

授業での利用中は、production を更新しない。リリースの承認のときに、授業の予定を確認する。

## 採用しなかった案

- Blue/Green: 巻き戻しは即座だが、環境が一時的に 2 倍になり、データベースの移行との整合が難しい（Q2 の B）。
- 機能フラグ（AppConfig）: 仕組みと費用と運用が増えるため、使わない（Q4 の B）。
