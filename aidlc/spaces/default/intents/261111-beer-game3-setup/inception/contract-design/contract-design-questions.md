# Contract Design 質問

Unit 間と外部（ブラウザ）の境界で守る約束（契約）を決めるための確認です。6 つの Unit は 1 つのアプリケーションにまとめてデプロイするため（Units Generation の Q2）、Unit 間の多くの境界は、通信ではなく、アプリケーション内の公開インターフェースと共有のデータベースになります。外部へ出る境界は、ブラウザから呼ぶ API です。

A. REST と JSON。操作ごとに入口を分け、OpenAPI で仕様を書く
B. GraphQL。画面が欲しい項目を指定して取得する

## Q2. [アーキテクト] 画面への反映の方法

ほかの参加者が入力した状況や、週の確定後の新しい状態を、画面にどう反映しますか？ 週の確定後 2 秒以内の反映が目標です（NFR3、仮の値）。

A. 定期的な再取得（ポーリング）。画面が数秒おきに状態を取り直す。仕組みが単純で、再接続後の復帰も同じ入口で済む
B. サーバーからの一方向の通知（Server-Sent Events）。変化があったときだけ画面へ送る
C. 双方向の常時接続（WebSocket）。入力も反映も同じ接続で行う
X. Other (please specify)

[Answer]: A

## Q3. [アーキテクト] Unit 間の境界の形と、仕様の持ち主

同じアプリケーションの中の Unit 同士は、どの形で境界を約束しますか？ 共有のデータベースは PostgreSQL 1 つです。

A. アプリケーション内の公開インターフェース（型付き）と、共有のデータベーススキーマで約束する。仕様は提供する Unit が持ち、U1 がスキーマの土台を持って、後続の Unit が移行を足す
B. Unit 同士も HTTP で呼び合う。Unit ごとに OpenAPI を持つ

## Q4. [アーキテクト] 変更の取り決め

契約を変えるとき、どう扱いますか？ 外部の API を使うのは自分たちの画面だけで、同時に配信されます。

A. 追加は後方互換にし（使う側は未知の項目を無視）、削除と意味の変更は、同じ変更の中で使う側もすべて直す。API の版番号は付けない
B. API のパスに版番号（/v1）を付け、版を分けて並行して維持する

[Answer]: A

## Q5. [デベロッパー] 失敗と再送の扱い

境界での失敗、二重送信、時間切れをどう扱いますか？ 入力の二重送信と週確定の再送で重複して計上しないことが要件です（FR7.3、FR9.1）。

A. 共通のエラー形式（種類、理由、直し方）を 1 つ定める。入力と週確定は、利用者が付ける識別子で冪等にし、同じ識別子の再送には前回と同じ結果を返す。時間切れは画面が取り直し、サーバーは自動で再試行しない
B. エラー形式は操作ごとに決める。冪等性は、週と役割の組み合わせが同じなら重複とみなして防ぐ。識別子は使わない
