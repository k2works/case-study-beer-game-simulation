# 要件定義 - beer-game3

beer-game3 の要件を、元の要件定義書と、面談の回答（Q1〜Q7）から整理しました。要件の ID は、後続の工程で追跡できるよう `FR{n}`、`FR{n}.{m}`、`NFR{n}` の形に付け替えています。元の ID（FR-01 など）との対応は末尾の表にあります。

- 元の要求: `docs/requirements/beer-game/requirements_definition.md`（v1 の要件。FR-01〜15、NFR-01〜10、BR-01〜14、UC-01〜15、ASM-01〜05）
- 依頼文: 「docs/requirements/beer-game/requirements_definition.md をもとに beer-game3 開発プロジェクトを１からたてる」
- 面談の回答: `requirements-analysis-questions.md`（Q1〜Q7）
- 進め方の決定: `team-practices.md`（範囲は v1 のみ、土台なしで 1 から作る、薄い一通りを最初に作る、カバレッジは行 80%、Node 26 / PostgreSQL 18）
- 既存の調査結果: `business-overview.md`、`architecture.md`、`code-structure.md`（`apps/beer-game3/` は未作成であること、beer-game2 は設計の参考にとどめること）
- 過去の決定の引き継ぎ（Q7）: 観察者に公開する集計値はチーム全体の値に限る。参加者の再接続はブラウザに保存した復帰用 token で行う

## 意図の分析

日本システム・ダイナミクス学会（JSD）の改訂版ビールゲームを、複数人で遊べるデジタルシミュレーションとして、beer-game3 の名前で新しく作ります。第一の目的は勝敗ではなく、情報遅延と配送遅延のもとで在庫と受注残の振動が増幅する過程（Bullwhip Effect）を体験し、「構造が行動を生む」ことを学ぶことです。

- 利用者: 参加者（工場・一次卸・二次卸・小売店の 4 役割）、進行役、観察者
- 範囲: v1 の要件（FR1〜FR15、NFR1〜NFR10）だけ。v2 で増えた共同入力、観察者の拡張、自動確定などは含めない
- 作り方: 土台コードなしで 1 から作る。最初の動くコードは「1 ゲーム、4 役割、1 週分を確定して状態を表示する」薄い一通り
- 複雑さ: 中程度。業務ルールは明確で、未確定なのは既定の需要系列だけ

## 機能要件

受入基準は Given/When/Then で書きます。ここで確定した基準は、`team-practices.md` の方針に従い、実装の前に実行可能な振る舞いの例として固定します。

### FR1 ゲーム設定の作成（元 FR-01）

- FR1.1 進行役はゲームを作成でき、週数を 1〜50 の範囲で設定できる。既定はキット準拠の 50 週とする。
  - Given 進行役がゲーム作成画面を開いている / When 週数に 0 または 51 を入力して保存する / Then 範囲外として拒否し、1〜50 を案内する。入力済みの他の項目は残る
  - Given 同じ画面 / When 週数に 1 と 50 を入力する / Then どちらも保存できる
- FR1.2 進行役は顧客需要系列を設定できる。系列の値は週数と同じ長さである。
  - Given 週数 50 のゲーム設定 / When 需要系列を 49 週分だけ入力して保存する / Then 長さ不一致として拒否する
- FR1.3 既定の需要系列は、階段状の例（初期は一定、途中から増える）を仮の既定とし、「カスタム」と明示する。JSD 準拠とは表示しない（Q1）。
  - Given 進行役が需要系列を指定せずにゲームを作成する / When 保存する / Then 仮の既定の系列が入り、ゲームは「カスタム」と表示される
- FR1.4 初期在庫、初期パイプライン数量（各遅延の枠に最初から入っている数量）、費用単価、公開範囲を設定として保存できる。遅延の週数は設定項目にしない（FR8.1 で固定）。
  - Given 進行役が初期在庫に負数を入力する / When 保存する / Then 拒否し、非負の整数を案内する
  - Given 進行役が設定画面を開く / When 項目を確認する / Then 遅延の週数を変更する項目はなく、初期パイプライン数量の項目がある
- FR1.5 キット準拠のプリセットを提供し、初期値・需要系列・週数・費用単価のどれかを変えたゲームは「カスタム」と明示して区別する（元 BR-13、BR-14）。プリセットの値は次のとおり。

  | 項目 | キット準拠の値 |
  | :--- | :--- |
  | 各役割の初期在庫 | 12（工場を含む） |
  | 各配送遅延の枠ごとの初期パイプライン数量 | 4 |
  | 工場の各生産遅延の枠ごとの初期パイプライン数量 | 4 |
  | 各注文遅延の枠ごとの初期パイプライン数量 | 4 |
  | 遅延の週数（配送、注文、生産） | 各 2（固定） |
  | 週数 | 50 |
  | 費用単価 | 在庫 $0.50、受注残 $1.00 |
  | 需要系列 | JSD の既定の系列（確定するまで未提供） |

  - Given キット準拠のプリセットでゲームを作成した / When 週数を 30 週に変更して保存する / Then ゲームは「カスタム」と表示され、結果の出力にも同じ区別が残る
  - Given キット準拠のプリセットで作成した直後のゲーム / When 第 1 週と第 2 週を確定する / Then 各役割の入荷は、それぞれの配送遅延の枠に最初から入っている数量（4）になり、第 3 週の入荷から、第 1 週以降の出荷が加わる
- FR1.7 「キット準拠」と表示できるのは、プリセットの全項目（需要系列を含む）が一致するゲームだけである。JSD の既定の需要系列が確定するまでは、キット準拠のゲームは作成できず、すべて「カスタム」になる。キット準拠の側の検証は、試験用の仮の系列と、プリセットを模した試験用の設定で行う。
  - Given JSD の既定の需要系列が未確定の間 / When キット準拠のプリセットで作成する / Then ゲームは「カスタム」と表示され、キット準拠とは表示されない
  - Given 試験用に、プリセットの全項目と一致する設定を与えた自動試験 / When 判定する / Then 「キット準拠」と判定される
- FR1.6 ゲーム作成時に、推測困難な参加コードと、進行役用コードを発行する（Q3）。進行役の操作（設定変更、役割割当て、代理入力、週確定、停止・再開・終了）は進行役用コードを持つ人だけができる。
  - Given ゲームが作成された / When 参加コードだけを持つ人が週確定を要求する / Then 権限がないとして拒否される

### FR2 参加コードでの参加（元 FR-02）

- FR2.1 参加者は有効な参加コードと表示名でロビーへ参加できる。表示名以外の個人情報は必須としない。
  - Given 準備中のゲームの有効な参加コード / When 参加者が表示名を入力して参加する / Then ロビーの参加者一覧に表示名が加わる
- FR2.2 無効なコード、終了済みのゲームのコード、準備中でないゲームのコードでは参加を拒否し、理由を表示する。進行中の途中参加は、参加コードではなく、FR3.2 の担当者の入れ替えで行う。
  - Given 終了済みのゲームの参加コード / When 参加を試みる / Then 「終了済み」という理由で拒否される
  - Given 進行中のゲームの参加コード / When 新しい人が参加を試みる / Then 「進行中のため参加できない」という理由で拒否される
- FR2.4 同じ表示名の参加者がいても参加できる。内部では別の参加者として区別し、ロビーと進行管理の画面には、区別できる印（参加順の番号など）を併記する。
  - Given 「太郎」という表示名の参加者がいる / When 別の人が「太郎」で参加する / Then 2 人とも参加でき、画面で区別できる
- FR2.3 参加時に、再接続用の復帰 token を発行し、参加者のブラウザに保存する（Q7、元 UC-14）。
  - Given 参加者が参加した / When ブラウザを閉じて同じブラウザで再度開く / Then 同じ参加者・同じ役割として復帰できる

### FR3 役割の割当て（元 FR-03）

- FR3.1 工場・一次卸・二次卸・小売店の 4 役割を重複なく割り当てる。
  - Given 4 役割のうち 1 つが未割当て / When 進行役がゲームを開始する / Then 開始できず、未割当ての役割を示す
- FR3.2 進行役は、準備中は役割の割当てを自由に変更できる。進行中と一時停止中は、同じ役割の担当者の入れ替え（復帰用 token の再発行を含む）だけを許し、役割の増減や、他の役割への移動は許さない（Q5）。
  - Given ゲームが準備中 / When 進行役が参加者を別の役割へ移す / Then 変更できる
  - Given ゲームが進行中 / When 進行役が小売店の担当者を別の人に入れ替える / Then 入れ替えられ、以前の担当者の復帰用 token は無効になり、役割の在庫・受注残・履歴は変わらない
  - Given ゲームが進行中 / When 進行役が小売店の担当者を工場へ移そうとする / Then 拒否される
- FR3.3 同じ役割を複数人が担当する場合、その役割に入力する値は 1 つで、共同で決める。投票・多数決は行わない（元 ASM-04）。1 つの役割に割り当てられる人数の上限は 4 人とする。
  - Given 1 つの役割に 2 人が割り当てられている / When 2 人が別々の発注数を入力する / Then 役割の入力として、最後に確定した 1 つの値だけが扱われ、もう一方の人の画面には、置き換わったことが示される
  - Given 1 つの役割に 4 人が割り当てられている / When 5 人目を割り当てようとする / Then 拒否される

### FR4 役割に応じた情報表示（元 FR-04）

- FR4.1 プレイ中、参加者は自分の役割の情報（在庫、受注残、入荷、受注、履歴）だけを見られ、他役割の在庫・受注残・意思決定値と将来需要は取得できない。画面で隠すだけでなく、サーバー側で応答に含めない。
  - Given 小売店の参加者 / When 他役割の在庫を取得する要求を直接送る / Then 拒否され、値は返らない
- FR4.2 顧客需要は、プレイ中は当該週の値だけを小売店に開示する（元 BR-11）。
  - Given 第 3 週のプレイ中 / When 小売店が需要を見る / Then 第 3 週までの値だけが見え、第 4 週以降は見えない
- FR4.3 観察者には、進行役が許可した、チーム全体の集計値と進行状況だけを入力不可で表示する。役割別の非公開情報を逆算できる値は含めない（Q7、元 UC-13）。
  - Given 観察者が観察画面を開いている / When プレイ中 / Then チーム全体の集計値と現在週が見え、役割別の在庫・受注残・意思決定値は見えない
- FR4.5 進行役は、プレイ中、進行管理のために、全役割の入力完了状況と、代理入力に必要な各役割の現在の状態（在庫、受注残、受注、入荷）を見られる。ただし、将来の需要系列の値は、設定として知っているため見られるが、他の参加者には開示しない。
  - Given 進行役が進行管理画面を開いている / When プレイ中 / Then 4 役割の入力完了状況と各役割の現在の状態が見える
  - Given 参加者が自分の役割の画面を開いている / When 進行管理画面の URL を直接要求する / Then 進行役用コードがないため拒否される
- FR4.4 ゲーム終了後は、チーム全体の需要、注文、在庫、受注残、出荷、費用を全員に開示する。
  - Given ゲームが終了した / When 参加者が結果画面を開く / Then 全役割の時系列が見える

### FR5 12 ステップ順の週の進行（元 FR-05）

- FR5.1 改訂版キットの 12 ステップの順に週を進める。各ステップの実行者と、週の確定に必須かどうかは次のとおり。

  | ステップ | 内容 | 実行者 | 確定の必須条件 |
  | :--- | :--- | :--- | :--- |
  | ① | 到着予定の入荷数を確定する | システム | 必須（自動） |
  | ② | 入荷数を確認・記録する | 各役割 | 必須ではない（表示のみ。確認の操作は求めない） |
  | ③ | 入荷して在庫へ加算する | システム | 必須（自動） |
  | ④ | 配送遅れを前進する（工場は生産遅れも） | システム | 必須（自動） |
  | ⑤ | 顧客または下流から受注する | システム | 必須（自動） |
  | ⑥ | 受注数を確認・記録する | 各役割 | 必須ではない（表示のみ。確認の操作は求めない） |
  | ⑦ | 注文情報を処理済みにする | システム | 必須（自動） |
  | ⑧ | 在庫数と受注残数を計算する | システム | 必須（自動） |
  | ⑨ | 在庫の範囲で出荷する | システム | 必須（自動） |
  | ⑩ | 注文遅れを前進する（工場は生産要請の受理も） | システム | 必須（自動） |
  | ⑪ | 発注数または生産要請数を決める | 各役割 | 必須（4 役割すべての入力が揃うこと） |
  | ⑫ | 上流へ発注または生産要請する | システム | 必須（自動。⑪の後に実行） |

  確定を拒否する条件は、⑪が 4 役割のうち 1 つでも未入力であること、または、システムのステップが順序どおりに完了していないことである。⑤は、小売店では顧客需要、卸と工場では下流からの注文である。
  - Given 第 5 週で小売店の発注数だけが未入力 / When 週の確定を要求する / Then 拒否され、未入力の役割として小売店を示す
  - Given 第 5 週で 4 役割すべての発注数または生産要請数が入力済みで、参加者が入荷数の確認の操作をしていない / When 週の確定を要求する / Then 確定できる
- FR5.2 小売店、卸、工場で存在しないステップはスキップし、全役割が同じステップ番号で同期する。
  - Given 工場の週 / When ステップ 5（顧客または下流から受注）に至る / Then 工場は一次卸からの注文を受注として扱い、番号は他役割と同じになる

### FR6 入荷・受注・在庫・受注残の自動計算（元 FR-06）

- FR6.1 当週の利用可能量は「前週末在庫 + 当週入荷」、充足対象は「前週末受注残 + 当週受注」、出荷は両者の小さい方、週末在庫は `max(0, 利用可能量 - 充足対象)`、週末受注残は `max(0, 充足対象 - 利用可能量)` とする（元 BR-05〜BR-08）。
  - Given 前週末在庫 12、当週入荷 4、前週末受注残 0、当週受注 20 / When 週を確定する / Then 出荷 16、週末在庫 0、週末受注残 4
  - Given 前週末在庫 12、当週入荷 0、前週末受注残 0、当週受注 4 / When 週を確定する / Then 出荷 4、週末在庫 8、週末受注残 0
  - Given 利用可能量と充足対象が等しい場合 / When 週を確定する / Then 週末在庫 0、週末受注残 0
- FR6.2 負の在庫・負の受注残は保存しない。

### FR7 発注数・生産要請数の入力（元 FR-07）

- FR7.1 各役割は非負の整数の発注数（工場は生産要請数）を入力する。小数、負数、未入力は拒否する。入力できる値は役割の発注または生産要請の 1 つだけとする（元 BR-10）。
  - Given 発注数の入力欄 / When 2.5、-1、空欄、「abc」を入力する / Then いずれも拒否され、入力した他の値は残る
  - Given 同じ入力欄 / When 0 を入力する / Then 受け付ける
- FR7.2 週の確定前は、入力した値を変更できる。
  - Given 第 5 週で発注数 10 を入力済みで、まだ週が確定していない / When 12 に変更する / Then 12 が有効になる
- FR7.3 同じ入力の二重送信で、入力が重複して扱われない。
  - Given 発注数の入力の送信が 2 回届いた / When 処理する / Then 入力は 1 件として扱われる

### FR8 遅延の保持（元 FR-08）

- FR8.1 配送は 2 週、注文情報は 2 週、工場の生産は 2 段階の遅延を、週単位で保持する。遅延の週数は固定で、設定では変えられない。この期間より早く到着しない（元 BR-02〜BR-04）。各遅延の枠に最初から入っている数量は、FR1.4・FR1.5 の初期パイプライン数量で決まる。
  - Given 第 3 週に工場が一次卸へ出荷した / When 第 4 週を確定する / Then 一次卸の入荷にはまだ加わらず、第 5 週に加わる
  - Given 第 3 週に小売店が発注した / When 第 4 週を確定する / Then 二次卸の受注にはまだ加わらず、第 5 週に加わる

### FR9 週確定の一度きりの原子的な実行（元 FR-09）

- FR9.1 週の確定は、4 役割の意思決定が揃ってから、一度だけ原子的に行う（元 BR-12）。再送や同時操作でも在庫、注文、出荷、費用が二重に計上されない。
  - Given 第 5 週の確定が完了している / When 同じ週の確定がもう一度届く / Then 状態は変わらず、前回と同じ結果を返す
  - Given 進行役 2 人の端末から同時に確定が届く / When 処理する / Then 週は一度だけ確定される
- FR9.2 確定の途中で障害が起きても、一部だけ更新された状態を残さない（元 NFR-02）。
  - Given 週確定の処理の途中で保存に失敗した / When 復旧後に状態を取得する / Then 確定前の状態のままで、確定済みの一部は残らない

### FR10 週次費用と累積費用（元 FR-10）

- FR10.1 各週・各役割の費用を `週末在庫 × $0.50 + 週末受注残 × $1.00` で計算し、累積する。チーム費用は 4 役割の合計とする（元 BR-09）。
  - Given 週末在庫 8、週末受注残 4 / When 週を確定する / Then その週の費用は $8.00（8×0.50 + 4×1.00）
  - Given 費用単価をカスタムで変更した場合 / When 週を確定する / Then 変更後の単価で計算される
- FR10.2 金額は、浮動小数点ではなく、整数の最小単位または固定小数で扱い、表示の合計は端数の誤差なく一致する。

### FR11 一時停止・再開・終了（元 FR-11）

- FR11.1 進行役は、ゲームを一時停止、再開、終了できる。一時停止中と終了後は、参加者の新規の確定操作を拒否する。閲覧と再開は一時停止中も許可する。
  - Given ゲームが一時停止中 / When 参加者が発注数を確定する / Then 拒否され、一時停止中であることが示される
  - Given ゲームが終了した / When 参加者が入力を試みる / Then 拒否される
- FR11.2 終了週に達したら、ゲームは自動で終了する。

### FR12 中断からの復元（元 FR-12）

- FR12.1 確定済みの週から、中断したゲームを復元できる。復元の前後で、在庫、受注残、遅延、履歴、費用が一致する。
  - Given 第 10 週まで確定したゲーム / When サービスが再起動して復元する / Then 第 10 週の状態が再起動前と一致し、第 11 週から続けられる
- FR12.2 参加者の端末が切断されても、確定済みのデータを失わず、復帰用 token で同じ役割に戻れる。token を失った場合は、進行役が FR3.2 の担当者の入れ替え（復帰用 token の再発行）で復帰させる（元 ASM-05、UC-14）。
  - Given 参加者のブラウザが閉じられた / When 同じブラウザで復帰用 token により再接続する / Then 同じ役割の画面に戻り、入力済みの未確定値は残る
  - Given 参加者が復帰用 token を失った / When 進行役が同じ役割の担当者の入れ替えをする / Then 新しい token で同じ役割に戻れる
- FR12.3 週の確定前でも、入力した値は入力した時点で保存される。サービスが再起動しても、確定前の入力は残る。
  - Given 第 5 週で小売店が発注数 10 を入力済みで未確定 / When サービスが再起動する / Then 再起動後も小売店の入力は 10 のまま残っている

### FR13 結果の比較表示（元 FR-13）

- FR13.1 ゲーム終了後、需要と全役割の注文、在庫、受注残、出荷、費用を、1 つの時間軸で、役割別に切り替えて比較表示する。
  - Given 終了したゲーム / When 結果画面で「受注残」を選ぶ / Then 4 役割の受注残が同じ週の軸で重なって表示される
- FR13.2 色だけに頼らず、系列を区別できる（元 NFR-08 に基づく）。

### FR14 ゲーム設定と全週記録の出力（元 FR-14）

- FR14.1 進行役は、ゲーム設定と全週の記録を、CSV と JSON の両方で出力できる（Q5）。出力から、週、役割、各数量、費用、意思決定を識別でき、キット準拠かカスタムかも識別できる。
  - Given 終了したゲーム / When CSV で出力する / Then 週ごと・役割ごとに入荷、受注、出荷、在庫、受注残、発注または生産要請、費用の列があり、キット準拠かカスタムかの区別が含まれる
  - Given 同じゲーム / When JSON で出力する / Then CSV と同じ数値が一致する
- FR14.2 値に区切り文字や改行が含まれる場合でも、出力は壊れない（表示名など）。
  - Given 表示名にカンマと改行を含む参加者 / When CSV で出力する / Then 行が崩れず、値は元のまま読み戻せる

### FR15 代理入力の記録（元 FR-15）

- FR15.1 進行役は不在の役割に代わって入力でき、誰が、どの役割へ、いつ、何を入力したかが履歴に残る（元 ASM-03。自動補充の戦略は対象外）。
  - Given 工場の参加者が不在 / When 進行役が工場の生産要請数 8 を代理入力する / Then 値が入力され、履歴に進行役・工場・時刻・8 が残る

## 非機能要件

測定の数値は、元の要件定義書の値を使います。元の書に数値がなかった項目には、レビューの指摘を受けて、仮の測定基準を置きました（「仮の値」と明記）。仮の値は NFR 要件の工程で確定します。

- NFR1 正確性（元 NFR-01）: 同じ初期状態と意思決定系列からは、常に同じ週次状態・費用を再現する。
  - Given 既知の初期状態と意思決定系列 / When 2 回実行する / Then 50 週すべての在庫、受注残、注文、出荷、遅延、費用が両方とも期待値と一致する
- NFR2 整合性（元 NFR-02）: 週確定は All-or-Nothing とし、障害時に部分更新を残さない（FR9.2 に対応）。
- NFR3 応答性（元 NFR-03）: 通常負荷で、入力確定の 95 パーセンタイルを 1 秒以内、週確定後の画面反映を 2 秒以内とする。通常負荷は、15 チーム（各 4 役割と進行役）が同時に接続し、各チームが 1 分あたり 1 週を確定する状態とする（仮の値）。
  - Given 通常負荷（15 チームの同時接続、各チーム 1 分あたり 1 週の確定）/ When 10 分間の負荷試験を行う / Then 入力確定の 95 パーセンタイルが 1 秒以内、週確定後の画面反映が 2 秒以内
- NFR4 同時利用（元 NFR-04）: 少なくとも 15 チーム、各チーム 4 役割と進行役の同時利用を支える。
- NFR5 可用性（元 NFR-05）: セッション中の一時的な切断後、確定済みデータを失わず再接続できる（FR12.2 に対応）。一時的な切断は 30 分以内とし、復帰用 token は最後の操作から 24 時間有効とする（仮の値）。
  - Given 参加者が 30 分間切断された / When 同じブラウザで再接続する / Then 確定済みのデータは失われず、同じ役割に戻れる
  - Given 最後の操作から 24 時間を超えた復帰用 token / When その token で再接続する / Then 拒否され、進行役による入れ替えが必要と案内される
- NFR6 セキュリティ（元 NFR-06）: 推測困難な参加コードと進行役用コードを使い、ゲーム・役割単位で操作権限をサーバー側で検証する。参加コードは 8 文字以上の英数字、進行役用コードと復帰用 token は暗号論的乱数による 128 ビット以上とする。無効なコードによる参加の試行は、同じ接続元から 1 分あたり 10 回までとし、超えたら一時的に拒否する（仮の値）。
  - Given 他のゲームの役割の識別子 / When その役割の入力を送る / Then 拒否される
  - Given 同じ接続元が 1 分間に 11 回、無効なコードで参加を試みた / When 11 回目を送る / Then 一時的に拒否される
- NFR7 プライバシー（元 NFR-07）: 表示名以外の個人情報を必須としない。保持期間は運営者が設定でき、設定しない場合の既定は、ゲーム終了後 30 日とする（Q4）。保持期限を過ぎたデータは削除する（元 UC-15）。運営者は、アプリケーションの設定として保持期間の既定を指定する人であり、画面を持つ利用者ではない。終了しないまま放置されたゲームは、最後の操作から 30 日で自動的に終了させ、その時点から保持期間を数える（仮の値）。
  - Given 終了から 31 日が経過し、保持期間を設定していないゲーム / When 削除の処理が動く / Then ゲームのデータは削除され、参加コードは無効になる
  - Given 保持期間を 7 日に設定したゲーム / When 終了から 8 日が経つ / Then 設定の期間に従って削除される
- NFR8 アクセシビリティ（元 NFR-08）: 色だけに依存せず状態を示し、すべての機能をキーボードで操作でき、WCAG 2.2 の達成基準 AA のコントラスト（通常の文字で 4.5:1 以上）を満たす（仮の値）。
  - Given 任意の画面 / When キーボードだけで、ゲーム作成から週の確定まで操作する / Then すべて完了できる
  - Given 任意の画面の文字と背景 / When コントラスト比を測る / Then 通常の文字で 4.5:1 以上
- NFR9 監査性（元 NFR-09）: ゲーム設定、役割変更、代理入力、週確定、停止、再開、終了の履歴を追跡できる。
- NFR10 可搬性（元 NFR-10）: 最新 2 世代の主要デスクトップブラウザ（Chrome、Edge、Firefox、Safari）で利用でき、参加者側に専用ソフトの導入を不要とする（ブラウザ名は仮の値）。
  - Given 4 つのブラウザの最新 2 世代 / When ゲーム作成から週の確定までの主要な操作を行う / Then いずれでも完了できる
- NFR11 画面と出力の言語: 日本語のみとする（Q6）。

## 制約

- 技術: Node.js 26、PostgreSQL 18（`team-practices.md`）
- 土台: 土台コードなしで 1 から作る。`apps/beer-game2/` は設計の参考にとどめ、コードは複製しない
- 範囲: v1 の要件だけ。v2 の追加分（共同入力、観察者の拡張、自動確定、観測性・運用性の追加要件）は含めない
- 方針: 週次の計算は副作用のない決定論的な処理として分離する（過去の決定の引き継ぎ）
- 品質: 行カバレッジ 80% を下限とする。週次計算には既知系列の golden test を用意する
- 規則: キット準拠の学習構造（4 役割、遅延、情報制約、費用、12 ステップ）を損なわない（元 SR-08）
- デプロイ: main への merge で staging へ自動反映し、production は手動承認後。AWS は beer-game3 専用

## 前提 (Assumptions)

- [assumption] 仮の既定の需要系列は、階段状の例の値（例: 週 1〜4 は一定、週 5 以降は増える）で、具体的な値は実装前に JSD の運営条件と照合して決める。照合までは「カスタム」と表示する（FR1.3、FR1.7）
- [assumption] 各遅延の枠に最初から入っている数量（初期パイプライン数量）は、キット準拠で 4 とする。キットの盤面（SRC-02、SRC-04）と照合して確認する（FR1.5）
- [assumption] 確認のステップ（②入荷数の確認、⑥受注数の確認）は、表示のみとし、確定の必須条件にしない（FR5.1）
- [assumption] 単一の学習セッションの利用が中心で、1 ゲームの寿命は数時間から数日。長期の運用や大規模な課金はない
- [assumption] 発注数・生産要請数の上限は、要件では設けない。極端に大きな値の扱いは設計の段階で決める
- [assumption] 同じ役割に複数人が同時に入力した場合は、最後に確定した値を採用する（後勝ち）。FR3.3 の受入基準はこの前提による。入力が置き換わったことを通知する画面の詳細は UI 設計で決める
- [assumption] 時刻は 1 つの基準（UTC）で保存し、画面では閲覧者の地域の時刻で表示する
- [assumption] 仮の測定値（NFR3、NFR5、NFR6、NFR7、NFR8、NFR10 に「仮の値」と記した数値）は、NFR 要件の工程で確定する
- [assumption] ゲームの作成は、進行役を務める人なら誰でもできる。運営者は画面を持たず、保持期間の既定をアプリケーションの設定として指定する
- [assumption] 進行役用コードを紛失した場合、再発行はしない。進行役を続けられないゲームは、放置されたゲームとして自動終了の対象になる（NFR7）

## 対象外

- 実物キットの印刷・組立、金銭決済、教材販売
- 汎用のサプライチェーン管理、実在企業の需給計画
- プレイヤー不在時の自動補充の戦略（元 ASM-03）
- 同一役割の複数人による投票・多数決（元 ASM-04）
- v2 の追加要件（共同入力の拡張、観察者の拡張、自動確定、観測性・運用性の追加要件）
- アカウント登録とログイン
- 日本語以外の言語（Q6）
- JSD 準拠の受入判定（既定の需要系列が確定するまで保留）
