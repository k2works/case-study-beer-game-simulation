# ユーザーストーリー評価

## 決定

Execute（ユーザーストーリーを作成する）

## 理由

beer-game3 は、複数の利用者（進行役、参加者、観察者）が、それぞれ別の画面と権限で使うシミュレーションです。参加者は 4 つの役割に分かれ、見られる情報も入力できる内容も異なります。週次の進行や情報公開の規則は複雑で、「誰が」「何のために」「どの条件で」を利用者の言葉で残さないと、後の設計と試験で意図が失われます。要件定義（`requirements.md`）だけでは、利用者ごとの価値と、独立して試験できる単位が見えにくいため、ストーリーで補います。

## 考慮した要因

- 種別: 新規開発（土台コードなしで 1 から作る）。利用者が直接触る機能が中心
- 利用者の多様性: 進行役、参加者（4 役割）、観察者、運営者（保持期間の設定と削除）
- 複雑さ: 12 ステップの週次進行、遅延、情報の制約、週確定の冪等性と原子性
- 進め方: BDD。業務ルールを Given/When/Then で先に固定する（`team-practices.md`）
- 最初の実装: 1 ゲーム、4 役割、1 週分の確定と状態表示の薄い一通り（ウォーキングスケルトン）

## ストーリーが最も価値を持つ領域

- 役割別の情報制約（他役割の非公開情報を見せない）
- 週の確定（一度だけ、原子的に）と、中断からの復元
- 進行役の運営操作（設定、割当て、停止・再開、代理入力）
- 終了後の振り返り（比較表示と出力）
