研修（ビールゲーム）の業務ルールで、設計レビューの判断基準にしているもの（2026-11-14 時点、beer-game2 要件が正本）。

- US3.1 は「停止 → 必要な代理入力 → 再開」の順。停止中に進行役が代理入力できることが業務の前提。参加者の保存だけが停止中に拒否される（FR-11、AC3.1.1）。
- 自動確定（FR-18、BR-16）は既定無効。一時停止中は確定しない。再開時にそろっていれば確定する。
- 共同入力は変更を黙って失わない（最新値と最後の保存者を示す）。
- 開始後の参加者の追加・入れ替えは beer-game2 では不可（未決）。現場では遅刻・途中離脱が普通にあるため、要望が出やすい論点。
- 保持期間は既定 90 日。バックアップに最大 7 日残る旨を進行役へ示す（NF-S16）。

**Why:** beer-game-kotlin（2026-11-14 レビュー）で、ドメインモデルが代理入力を「進行中のみ」とし US3.1 の流れと食い違っていた。最終週の確定が出力生成の失敗で落ちうる設計、研修中は投影の再構築をしない一方で RTO 15 分を掲げる矛盾も指摘した。
- beer-game-rust（2026-11-21 レビュー）: 業務ルールは Kotlin 版を参照で引き継ぐ差分文書。新障害（OOM kill、接続プール枯渇＝パターン 17）に進行役への依頼文言がない。運用手順書は運用担当向けのみで、進行役向けの「研修中にシステムが止まったら」の案内が beer-game2 から一貫して無い。Rust 版の各文書が他文書を「未着手」と書く古い記述が残っていた。

**How to apply:** ES 化・言語移植などの再設計レビューでは、停止中の操作可否、週切り替え時の入力欄の扱い、最終週の確定の失敗要因を必ず確認する。関連: [[beer-game-review-history]]
